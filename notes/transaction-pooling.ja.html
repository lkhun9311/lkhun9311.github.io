Transaction Pooling
Connection Pooler が Transaction 単位で Connection を貸し出して返してもらう方式。

データベース · #Transaction Pooling

Connection Pooler が後ろの Connection を再利用する方式の一つで、Transaction 単位で貸し出して返してもらいます。Transaction が終わってはじめて、その Connection は次のクライアントに渡ります。

三つのモード#

PgBouncer では三つあります。後ろへ行くほど再利用は効きますが、使える機能は減ります。

  • セッションプーリング — クライアントが切断するまで Connection を握ります。再利用はほとんどありません。
  • Transaction Pooling — Transaction 単位。実務でいちばん使われるモードです。
  • ステートメントプーリング — クエリ一つ単位。Transaction は使えません。

核心的な性質 — いつ固定されるか#

この一行がすべてです。

Connection の再利用は Transaction と Transaction のあいだでしか起きない。 Transaction が開いているあいだ、その Connection はそのクライアントに固定される(Pin)。

当然の話です。Transaction は状態であり、開いている途中で別のセッションに貸せば分離が壊れます。

そこでこうなります。

transaction が 10 秒開いている
  → 後ろの connection も 10 秒固定される
  → アプリの connection 1 本につき DB の connection 1 本
  → pooler がまとめる余地がない

つまり短い Transaction が多いときに値打ちがある道具です。Transaction の中で外部 API を待つ コードには効きません。

ピン(Pin)がかかるパターン#

次のパターンがコードにあると、Transaction が終わっても Connection は固定されたままで、Pooler は無力になります。

  • セッションスコープの Advisory Lock (pg_advisory_lock) — pg_advisory_xact_lock は問題ありません(Transaction 終了時に解放)
  • 一時テーブル
  • SET · set search_path
  • サーバサイドのプリペアドステートメント(Pooler とバージョンによる)

ですから Pooler を導入する前にこの四つがコードにあるかを先に確かめます。導入後に知れば、 お金はすでに出ていて効果はありません。
