Cache Stampede

Cache Stampede は、あるキーが空になった瞬間に、それを必要としていた複数が同時に原本を呼ぶ事象です。 Cache はあるのに、いちばん忙しい瞬間だけ無いかのように振る舞います。

検査と充填のあいだが空いています#

自作の Cache はたいていこうです。空かどうかを見て、空なら呼んで詰めます。 その二行のあいだに他の Thread が入る隙があります。

並列化された N 個の Thread が同じ瞬間に検査を通過すれば、N 個すべてが外部 API を呼びます。 一度だけ呼ぶために作った Cache の前で N 回呼ぶことになります。負荷が集まるほど N が大きくなるので いちばん忙しいときにいちばん悪くなります。

「無い」も値です#

同じ場所にもっと長生きする欠陥がもう一つ出ます。取得結果が 0 件なら詰めるループが一度も回らず、 Cache には何も保存されません。次の要求も Cache を空だと見てまた呼びます。

「値が無い」と「まだ訊いていない」を同じ検査で潰したのです。0 件がよくある経路なら、 最も頻繁な場合に Cache がまるごと効きません。それでもコードには Cache があるので誰も疑いません。 詰まっているかを数えてみるまでは、そうです。

止める場所はロックではなくデータ構造です#

Caffeine の LoadingCache は Cache ミスでキーごとにローダーをちょうど一度実行し、残りの呼び出し側は その結果を待ちます。ローダーが空のリストを返せばその空のリストを値として保存します。 上の二つの欠陥が同時に消える理由です。

computeIfAbsent でも一度だけ呼ばせられますが、そちらは別の代価を払います。 待つ Thread がマップのバケットを握ったまま立っています。Bin Lock に書いておきました。
