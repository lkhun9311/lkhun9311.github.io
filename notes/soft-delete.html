Soft Delete

Sep 2026

Contents

  • The marker is not always zero and one
  • The main table is not where you delete
  • Where it is used on this site

Soft delete flips a deletion marker instead of removing the row. Reads filter on that marker, so the row looks gone on screen and stays in the table.

It is hidden, not deleted#

Being able to restore it, and keeping the history, is what the approach buys. What it costs is that the table never shrinks. A screen can want 20 rows while the table holds 1,041.

Child tables grow alongside it. Judging the pile from the main table alone undercounts what is actually there.

The marker is not always zero and one#

It is easy to assume the marker holds 0 or 1. Nova's instances does not. On deletion, deleted receives that row's own id, so every deleted row carries a different value.

Which makes GROUP BY deleted return as many groups as there are deleted rows. With 20 live rows and 1,021 marked deleted, that is 1,022 groups and 1,041 rows. Read 1,022 as a row count and 19 rows vanish from your picture. A query written without reading the schema will not tell you what it counted.

The main table is not where you delete#

Under pressure, a DELETE against the main table is tempting. That road comes with a moment of switching foreign key checks off, and in a session with them off every referential violation passes, while switching them back on does not revisit the ones already created.

The real road moves rows sideways: archive into a shadow table, same shape and out of the read path, then purge once the window passes. Deleting by hand covers today only, because soft deletes keep arriving tomorrow.
