Bin Lock

Sep 2026

Contents

  • Where it is used on this site

A bin lock is how ConcurrentHashMap locks one bucket, the one the key falls into, rather than the whole map. The mapping function of computeIfAbsent runs inside that lock.

Bins, not segments#

Plenty of writing still calls this a segment lock. Segments are Java 7 vocabulary. Since Java 8, ConcurrentHashMap has dropped them and locks per bin.

What changed is the scope of the lock. That something is locked at all did not change. A narrower scope is not permission to do slow work inside it.

Wait inside the lock and parallel becomes a queue#

A mapping function that reads the map and returns holds the lock for nanoseconds. Call an external API there and the bin stays locked for the entire network round trip.

With M tasks on the same key, one makes the round trip while the other M−1 line up at that bin. The queue that existed in the sequential version is still there in the parallel one, and thread pool slots stay pinned throughout. What grew is not the number of calls but pool occupancy and context switching. Bins for other keys stay unlocked, so that work proceeds.

Safe and fast are different claims#

“We used ConcurrentHashMap, so it is safe” is true. The question is what the safety was bought with. Here it was bought with a round trip's worth of serialization.

The fix is to stop handling the lock yourself. Caffeine's LoadingCache runs the loader exactly once per key and lets the other callers wait on that result. It gives the same “called only once” guarantee while the waiters hold no bucket of the map. The companion problem here is cache stampede.
