Harness

harness は負荷を作って対象システムにかけ、その結果を同じやり方で繰り返し測れるようにまとめた道具一式です。負荷ツール一つではなく、準備 → 実行 → 収集 → 集計までの手順全体を指します。

言葉そのものの意味#

もともと harness は馬に着ける馬具です。馬の力を馬車に伝えつつ、 勝手な方向へ行かないように押さえて方向を定める装置です。ソフトウェアでも意味は同じです — システムに力(負荷)をかけつつ、その力が毎回同じかかり方をするように押さえておくことです。

ですから「負荷ツール」と「harness」は別物です。JMeter・k6・Gatling は負荷ツールであり、 harness はそれを含めて依存の確認 → 対象の起動 → トークン発行 → 負荷の実行 → 結果の収集 → 集計までを 一つのコマンドで再現できるようにまとめたものです。

何が harness を harness にするのか#

三つが揃っている必要があります。一つでも欠ければ「一度回してみたもの」であって harness ではありません。

  1. 再現性。同じコマンドが同じ条件を作る。条件が実行ごとに違えば二つの結果は比べられません。
  2. パラメータ化。変えるもの(thread 数・時間・遅延)は引数に出し、シナリオはハードコードしません。
  3. 失敗が見えること。準備の段階が失敗したのに進むと0 という数字が結果に 化けます。負荷試験では静かな失敗はただの失敗より悪いです。

三つ目がいちばんよく抜けます。たとえば対象のアプリが起動していないのに負荷ツールがそのまま回ると、 「エラー率 100%」ではなく「サンプル 0 件」になり、集計がそれを黙って通すと 何も起きなかったように見えます。

どう回るか — 実行一回の流れ#

実際に立てた harness(perf/run.sh)の順序です。各段階が実際にできたか確認してから 次に進みます。

① 依存の確認        docker · java · python3 · JMeter があるか
② 専用 DB の起動     開発 DB と別のポート・コンテナ(負荷データが混ざると戻せない)
③ 外部 stub の起動   遅延をアプリの外で作る + stub が「自分のもの」か身元確認
④ 対象アプリの起動   設定を引数で注入(pool サイズ・レート制限・HTTP クライアント)
⑤ トークン・シード   ログイン → 読み取り対象の投稿を 1 件作成
⑥ 負荷の実行        書き込みと読み取りを別の thread グループで
⑦ 収集・集計        ウォームアップ区間を捨てて p50/p95/p99・エラー率・スループット

③ の「身元確認」は実際に起きた事故から来ています。前の実行の stub がポートに残っていて、新しい stub は 静かに死に、アプリは他人の stub と話していました。遅延 0 を指定した実行が実際には 800ms で、 その結論はすべて破棄することになりました。

よくある誤解#

「負荷は多いほど良い測定」 — 違います。システムが飽和すると、ボトルネックでないものを直しても 数字は動きません。実際、書き込み 16 で測った改善は「効果なし」に見えましたが、飽和しない書き込み 4 で 測り直すと 2 倍がそのまま出ました。

「絶対値が性能だ」 — 負荷ツールと対象が同じマシンにあるなら絶対スループットに意味はありません。 意味があるのは同じ条件での比較だけです。

「回ったから測れた」 — harness 自体が静かに間違っていれば、出てくる数字はすべて偽です。 ですから部品ごとにわざと壊して失敗が見えるかを先に確かめます。
