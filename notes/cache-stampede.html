Cache Stampede

Performance measurement · #Warm-up

Contents

  • Where it is used on this site

A cache stampede is what happens when one key goes missing and everyone who needed it calls the origin at once. The cache exists, and behaves as if it did not, precisely when things are busiest.

There is a gap between checking and filling#

A hand-written cache usually looks like this: check whether it is empty, and if it is, fetch and fill. Between those two lines there is room for another thread.

When N parallel threads clear the check in the same moment, all N call the external API. A cache built to make one call ends up making N. N grows with load, so it is worst exactly when you are busiest.

“Nothing” is also a value#

A longer-lived defect lives in the same place. If the lookup returns zero rows, the filling loop never runs and nothing lands in the cache. The next request reads the cache as empty and calls again.

“There is no value” and “we have not asked yet” were flattened into one check. If zero rows is a common answer on that path, the cache does nothing at all in the most frequent case. And nobody suspects it, because the code plainly has a cache in it. Not until somebody counts whether it ever gets filled.

The fix belongs to the data structure, not to a lock#

Caffeine's LoadingCache runs the loader exactly once per key on a miss and lets the other callers wait on that result. If the loader returns an empty list, the empty list is stored as the value. That is why both defects above disappear together.

computeIfAbsent can also force a single call, but it charges separately for it: the waiting threads stand there holding a bucket of the map. That is written up in bin lock.
