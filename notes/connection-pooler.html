Connection Pooler

Sep 2026

Contents

  • Why it exists
  • It is not the same as a connection pool
  • What it cannot fix

A middle server that folds the thousands of connections an application opens into dozens of database connections. RDS Proxy, PgBouncer, Supavisor.

Why it exists#

PostgreSQL creates one backend process per connection. That process uses memory even while it does nothing. So the more app instances there are, the sooner the database side hits its limit.

100 app instances × pool size 20 = 2,000 connections
but only 50 are actually running a query right now
the other 1,950 are merely open

A connection pooler takes those 2,000 and lays only the ones with work onto 50 backend connections. It removes the cost of connections that are merely open.

It is not the same as a connection pool#

The names are close enough to be confused often.

  • connection pool (HikariCP and friends) — lives inside the app. It is the list the app holds so it can reuse database connections.
  • connection pooler (RDS Proxy and friends) — a separate server between the app and the database. It merges connections from many apps.

So a pool is "one app economising on its own connections" and a pooler is "many apps' connections merged in front of the database".

What it cannot fix#

Connection shortage has two causes, and a pooler fixes only one of them.

  • too many connections — this is exactly what a pooler is for.
  • connections held for too long — a pooler cannot fix this, structurally.

The reason is in the definition of transaction pooling. Reuse happens only between transactions, and while a transaction is open its connection is pinned to one client. A transaction open for ten seconds pins the backend connection for ten seconds.
