Bin Lock

性能測定 · #Warm-up

目次

  • セグメントではなくバケットです
  • ロックの中で待てば並列が行列になります
  • 安全なことと速いことは別です
  • このサイトで使われている記事

Bin Lock は ConcurrentHashMap がマップ全体ではなくキーの属するバケット一つだけをロックする方式です。 computeIfAbsent のマッピング関数はそのロックの中で回ります。

セグメントではなくバケットです#

この構造をセグメントロックと呼ぶ文書をよく見ます。セグメントは Java 7 の頃の用語です。 Java 8 以降の ConcurrentHashMap はセグメントを無くしバケット(Bin)単位でロックします。

変わったのはロックの範囲です。ロックされること自体は同じです。 範囲が狭くなったことは、その中で時間のかかる仕事をしてよいという意味ではありません。

ロックの中で待てば並列が行列になります#

マッピング関数がマップを読んで終わる計算なら、ロック区間はナノ秒単位です。そこで外部 API を呼べば ネットワークの往復のあいだずっとそのバケットがロックされます。

同じキーを使う仕事が M 個あれば、一つが往復するあいだ残りの M−1 個がそのバケットの前に並びます。 逐次コードで並んでいた行列が並列コードでもそのまま並び、そのあいだ Thread Pool の席は塞がったままです。 増えたのは呼び出し回数ではなくPool の占有とコンテキストスイッチです。 他のキーのバケットはロックされないので、そちらの仕事は進みます。

安全なことと速いことは別です#

ConcurrentHashMap を使ったから安全だ、というのは正しいです。問うべきはその安全性を何で買ったかです。 ここでは往復時間分の直列化で買いました。

直し方はロックを自分で扱うのをやめることです。Caffeine の LoadingCache はキーごとにローダーを ちょうど一度だけ実行し、残りの呼び出し側はその結果を待ちます。同じ「一度だけ呼ぶ」を保証しながら 待つ側がマップのバケットを握っていません。 ここで一緒に出てくるのが Cache Stampede です。
