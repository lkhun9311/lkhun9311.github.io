Admission Control

Performance measurement · #Warm-up

Contents

  • Standing in front changes the population
  • A report of zero rejections is not evidence
  • Write down what it protects, before turning it on
  • Where it is used on this site

Admission control decides whether to take work before the work starts. For inference that is a token bucket at the gateway; for training it is the queue's admission decision.

Standing in front changes the population#

Latency metrics are computed over requests that finished. Admission control stands in front of the engine and refuses some of them. A refused request never completes, so it never enters that percentile.

Which makes “p99 improved” one of two things: the surviving requests really did get faster, or the slow ones left the population. Without separating those, dropping work reads as protecting it.

A report of zero rejections is not evidence#

When rejections are counted in one place and requests in another, the two drift. A report can say zero rejections while that run's completions are fewer than the requests sent, and then something disappeared somewhere.

So a verdict needs three numbers, not one: sent, completed, rejected. A run where those three do not reconcile is better treated as disqualified than read for latency.

Write down what it protects, before turning it on#

What admission control protects is usually the engine from saturation, not one tenant's tail. Those are different promises tuned by the same knob, which is why they get read as one.

So write the sentence first: whose what is held to which value, and what gets refused to pay for it. Without it, the numbers that come later are neither evidence that it held nor evidence that it did not.
