Percentile

Performance measurement · #Percentile

The value at one position once the response times are lined up. p95 is the time of the 95th fastest request out of 100, which is to say 5% were slower than this.

Why not the average#

An average hides the few very slow requests. If 99 of 100 take 5 ms and one takes 6 seconds, the average is 65 ms. That reads as "65 ms, fine", when in fact one person in a hundred waited six seconds.

That one person is a different person each time, and a user who makes several requests eventually meets that stretch. So the experience is set by the tail, not the average.

There are two ways to compute it#

The same data gives a different p95 in different tools, because the definitions differ.

  • Nearest-rank — take the ceil(0.95 × N)-th value of the sorted sample as it is. The result is always a value that was actually observed.
  • Linear interpolation — fill between the two neighbouring values proportionally. The result may be a value never observed.

Mix the two and you are comparing values with different definitions. So the summariser uses one and prints which one it used. For a sample of 1..20, nearest-rank p95 is the ceil(19) = 19th value = 19.

Which one to read#

p50 says "this is normal"; p95 and p99 say "this is what bad looks like". You need both.

When p50 and p95 are close the system is steady — every request is handled much the same. A low p50 with a far larger p95 is the signature of a queue: most are served quickly and some are standing in line.

A real example: in a run where the connection pool was exhausted, the feed read went from a p50 of 4 ms to 6,047 ms while the error rate stayed at 0%. It was waiting, not failing. Read the error rate alone and nothing looks wrong.
