Harness

A harness is a set of tools bundled so that load can be put on the system under test and the result measured the same way, repeatedly. Not one load generator, but the whole procedure: prepare → run → collect → summarise.

What the word means#

A harness is the tack put on a horse. It carries the horse's power to the cart while holding it and setting its direction so it cannot wander. The software sense is the same: put force (load) on a system, and hold that force so it lands the same way every time.

So a "load tool" and a "harness" are different things. JMeter, k6 and Gatling are load generators; a harness wraps one of them together with checking dependencies → starting the target → issuing tokens → running the load → collecting results → summarising, reproducibly, behind one command.

What makes a harness a harness#

Three things have to be there. Missing any one of them, it is "a run I did once", not a harness.

  1. Reproducibility. The same command builds the same conditions. If they differ per run, two results cannot be compared.
  2. Parameters. What changes — thread count, duration, latency — comes in as arguments; the scenario is not hard-coded.
  3. Failures must be visible. Carry on after a setup step failed and the number zero disguises itself as a result. In load testing a silent failure is worse than a failure.

The third is the one most often missing. If the target app never came up and the generator runs anyway, the result is not "100% errors" but "0 samples", and when the summariser lets that pass quietly it looks as though nothing happened at all.

How one run goes#

The order in the harness actually built (perf/run.sh). Each step moves on only after checking that it really happened.

① check dependencies    docker · java · python3 · JMeter present?
② start a dedicated DB  its own port and container (mixing load data in cannot be undone)
③ start the stub        make the latency outside the app + confirm the stub is ours
④ start the target      inject configuration as arguments (pool size, rate limit, HTTP client)
⑤ token and seed        log in → create one post to read
⑥ run the load          writes and reads in separate thread groups
⑦ collect, summarise    drop the warm-up, then p50/p95/p99 · error rate · throughput

The "confirm it is ours" in ③ came out of an actual incident. A stub from the previous run was still on the port, the new stub died quietly, and the app talked to somebody else's stub. A run that asked for zero latency was actually running at 800 ms, and every conclusion from it had to be thrown away.

Common misreadings#

"More load makes a better measurement" — no. Once the system is saturated, fixing something that is not the bottleneck moves no number. An improvement measured at 16 writers looked like "no effect"; measured again at 4 writers, where nothing was saturated, the factor of two was there.

"The absolute number is the performance" — when the generator and the target share a machine, absolute throughput means nothing. What means something is a comparison under the same conditions.

"It ran, so it measured" — if the harness itself is quietly wrong, every number it prints is false. So each part is broken on purpose first, to see whether the failure shows.

Related terms#

  • arm — the unit of a comparison run
