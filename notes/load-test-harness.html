Harness: 하네스란?

하네스(harness)는 부하를 만들어 대상 시스템에 걸고, 그 결과를 같은 방식으로 반복 측정할 수 있게 묶어 둔 도구 모음입니다. 부하기 하나가 아니라 준비 → 실행 → 수집 → 요약까지의 절차 전체를 말합니다.

말 자체의 뜻#

원래 harness는 말(馬)에 씌우는 마구입니다. 말의 힘을 마차에 전달하되, 말이 아무 데로나 가지 못하게 붙들어 방향을 정해 주는 장치입니다. 소프트웨어에서도 뜻이 같습니다 — 시스템에 힘(부하)을 걸되, 그 힘이 매번 같은 방식으로 걸리도록 붙들어 두는 것입니다.

그래서 "부하 도구"와 "하네스"는 다릅니다. JMeter·k6·Gatling 은 부하기이고, 하네스는 그 부하기를 포함해 의존성 확인 → 대상 기동 → 토큰 발급 → 부하 실행 → 결과 수집 → 요약까지를 한 번의 명령으로 재현 가능하게 묶은 것입니다.

무엇이 하네스를 하네스로 만드나#

세 가지가 있어야 합니다. 하나라도 없으면 "한 번 돌려 본 것"이지 하네스가 아닙니다.

  1. 재현성. 같은 명령이 같은 조건을 만든다. 조건이 실행마다 다르면 두 결과를 비교할 수 없습니다.
  2. 파라미터화. 바꿀 것(스레드 수·시간·지연)은 인자로 빼고, 시나리오는 하드코딩하지 않습니다.
  3. 실패가 보일 것. 준비 단계가 실패했는데 계속 진행하면 0 이라는 숫자가 결과로 둔갑합니다. 부하 시험에서 조용한 실패는 그냥 실패보다 나쁩니다.

세 번째가 제일 자주 빠집니다. 예를 들어 대상 앱이 안 떴는데 부하기가 그대로 돌면 "오류율 100%"가 아니라 "샘플 0건"이 나오고, 요약기가 그걸 조용히 통과시키면 아무 일도 없었던 것처럼 보입니다.

어떻게 도나 — 실행 한 번의 흐름#

실제로 세운 하네스(perf/run.sh)의 순서입니다. 각 단계가 실제로 됐는지 확인한 뒤에만 다음으로 넘어갑니다.

① 의존성 확인      docker · java · python3 · JMeter 가 있나
② 전용 DB 기동     개발 DB 와 다른 포트·컨테이너 (부하 데이터가 섞이면 되돌릴 수 없다)
③ 외부 스텁 기동    지연을 앱 밖에서 만든다 + 스텁이 "우리 것"인지 신원 확인
④ 대상 앱 기동     설정을 인자로 주입 (풀 크기·레이트리밋·HTTP 클라이언트)
⑤ 토큰·시드 준비    로그인 → 읽기 대상 글 1건 생성
⑥ 부하 실행        쓰기·읽기를 별도 스레드 그룹으로
⑦ 수집·요약        워밍업 구간을 버리고 p50/p95/p99·오류율·처리량

③의 "신원 확인"은 실제로 겪은 사고에서 나왔습니다. 이전 실행의 스텁이 포트에 남아 있었는데 새 스텁은 조용히 죽었고, 앱은 남의 스텁과 이야기했습니다. 지연 0을 요청한 실행이 사실 800ms 였고 그 결론은 전부 폐기해야 했습니다.

흔한 오해#

"부하를 많이 걸수록 좋은 측정" — 아닙니다. 시스템이 포화되면 병목이 아닌 것을 고쳐도 숫자가 안 움직입니다. 실제로 쓰기 16으로 잰 개선이 "효과 없음"으로 보였는데, 포화되지 않는 쓰기 4에서 다시 재니 2배가 그대로 나왔습니다.

"절대 수치가 성능이다" — 부하기와 대상이 같은 기계에 있으면 절대 처리량은 의미가 없습니다. 의미가 있는 것은 같은 조건에서의 비교뿐입니다.

"돌아갔으니 잰 것이다" — 하네스 자체가 조용히 틀리면 나오는 숫자가 전부 거짓입니다. 그래서 부품마다 일부러 깨뜨려 실패가 보이는지 먼저 확인합니다.
