アプリが DB connection を毎回作り直さず再利用するために持っている一覧です。Spring Boot の既定は HikariCP です。

なぜ再利用するのか#

DB connection を新しく開くのは高くつきます — TCP 接続、認証、セッション初期化が毎回起きます。リクエストごとにやると クエリの時間より接続の時間の方が長くなります。そこであらかじめ何本か開いておき、貸し出して返してもらいます。

ブロッキング JDBC ではこれが同時実行の上限#

ここが見落とされがちです。thread がいくら多くても connection をもらえなければ仕事はできません。

Tomcat の thread が 200 で connection pool が 20 なら、同時に実際に DB 作業ができるリクエストは 20 件です。 残りの 180 件は connection を待ち、timeout の後に失敗します。

方向自体は正しいです — 速く失敗するから残りが生きます。問題はその二つの数字を誰が選んだのかです。 どちらもフレームワークの既定値なら、その二つが作った同時実行の方針は方針ではありません。

不変条件が一つ#

pool を大きくするのは緩和であって修理ではなく、大きくすることにも上限があります。

pool のサイズ × 最大インスタンス数 ≤ DB の connection 上限

アプリは自分のインスタンスが何台あるか知らないので、この不変条件はコードで強制できません。 インフラコードのコメントが唯一の防御であることが多いです。
