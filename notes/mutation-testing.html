Mutation Testing

Verification · #Mutation Testing

Contents

  • Where it is used on this site
  • Related terms

Break the code on purpose and see whether a test goes red. If it stays green, the code is not safe — the guard is not aimed at it.

Why it is needed#

A green test can mean one of two things.

  1. the code is correct
  2. the test is not looking at that code

Green alone cannot tell them apart. The only way to tell is to revert the repair and see whether a test goes red.

The usual shape: the assertion is there and checks the right value, but it is not aimed at what was just repaired. Check "is the call outside the transaction" when there were no calls at all and containsOnly(false) is true of the empty list, so it passes vacuously.

How to do it#

There are tools (PIT and others), but the highest-value move in practice is reverting it once by hand.

① revert the repair you just made (one line if it was one line)
② run the tests
③ red   → a guard is holding that repair
   green → nothing is holding it. Write the guard now.

You can also reverse the order: apply the mutation first, confirm red, then restore and see green. This is especially good when writing a new guard — you see what it catches from the start.

Do it one path at a time#

Break everything at once and you settle for "it went red, good enough". Remove them one at a time and it becomes visible which guard holds what.

A real case: three paths were repaired and mutated. Two turned the matching guard red; the third came back green. The condition that guard aims at was never created inside the test, and only after constructing it did the red appear.
