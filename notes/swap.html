Swap

Sep 2026

Swap is the place the kernel parks pages on disk when RAM runs short. Going down is a Swap Out, coming back is a Swap In. The process never learns which happened. Only the cost of a single read quietly changes.

It did not give you more RAM#

Swap looks like a way to have more memory, but what grew is address space, not speed. A read that would have ended in RAM becomes a disk round trip, so the same query gets slower while staying exactly the same query. In orders of magnitude, RAM is the 0.0001ms side and swap is the 10ms side.

Which means performance on a swapping box depends not on the query or the code but on where the page happens to live. This is where the kind of slowness comes from that never explains itself no matter how long you stare at the layer above.

Full is circumstance, not cause#

free -h reporting Swap 8.0Gi 8.0Gi is hard to miss. But it says pages that went down at some point are still down there. Fill it with pages that went out long ago and nobody asks for any more and the number still reads 8.0 GiB.

To claim swap is why it is slow now, measure the flow: how many KiB per second si and so report in vmstat, and how many major page faults per second the process in question takes. Without those two you are left with “it was full” and “clearing it made things fast”, and the link between them is a guess.

Turning it off needs an undo written first#

swapoff -a pulls everything in swap back into RAM. Without room for it the command fails, or the kernel reclaims memory by killing a process (the OOM killer). Look at available in free -h first; it has to exceed swap's used.

swapoff -a && swapon -a holds one more trap. With several devices, some can stay on while swapoff exits non-zero, and && runs the right side only on a zero exit. Half a failure leaves swap switched off. Write the way back before you touch this one.
