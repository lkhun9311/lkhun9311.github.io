GPUaaS Platform Control Plane

Project · Kubernetes-native · Go

One line. A Kubernetes control plane that lets several teams share one GPU pool, deciding who gets capacity, when a waiting job is let in, and what happens when a node or a backend fails.

Status. Runs on a local three-node kind cluster against simulated nvidia.com/gpu capacity. No real GPU, no production traffic, inference backend is a stub. Everything below is control-plane behaviour, verified as described and with the gaps listed.

Source on GitHub

The problem it addresses

Training and inference behave in opposite ways under contention, and that single fact shapes the whole design.

InferenceTraining
durationmilliseconds to secondshours to days
can it waitno, a user is waitingyes, overnight is fine

if you reject itthe client retriesa human must resubmit, and nobody is there at 3am
enforcement pointgateway, at the requestadmission, at the job

A Kubernetes ResourceQuota cannot express the training half. It refuses the creation outright, so there is no queue: kubectl apply simply fails. That is correct for a request and wrong for a job.

The decision that shaped it: quota counted twice

Two systems can each be correct about GPU usage and still leave half the budget unusable.

Kueue counts a GPU when it admits a workload. A ResourceQuota counts a GPU when the pod exists. Kueue admits a 4-GPU job and unsuspends it, pods appear, and the ResourceQuota charges the same 4 GPUs again. On an 8-GPU budget the tenant is blocked at 4, and neither system reports an error, because each is accurate about its own ledger.

Resolution. When trainingQuota is on, the ResourceQuota stops counting GPUs and the Kueue ClusterQueue is the single authority. CPU and memory stay with the ResourceQuota, where nothing overlaps.

What that costs. Two things, both worth stating before an interviewer finds them. A safety net disappears: if the Kueue controller is down, nothing stops GPU consumption. And a bypass opens: a pod created without the queue label takes GPUs with no limit at all. Closing the second needs an admission webhook that rejects GPU pods lacking a queue label, and that is not built yet.

Longer write-up: designing the quota control plane

Where this sits against existing tools

Serving deployment overlaps KServe directly, and KServe is better at it: autoscaling, scale-to-zero, canary traffic splitting, model-storage integration and runtime abstraction are all there. Rebuilding them is not a defensible use of time.

The obvious next move looked like a quota unification layer: a controller making KServe GPU consumption visible to Kueue, so training and inference draw on one tenant budget. Before writing it I checked whether Kueue already did this. It does.

Kueue v0.18.3 ships a deployment integration. Each pod of a Deployment carrying the kueue.x-k8s.io/queue-name label becomes its own Workload charged against the same ClusterQueue a training Job uses. KServe in Standard mode produces ordinary Deployments, so the whole controller collapses to setting one label.

Measured on kind with a ClusterQueue holding a single GPU of nominal quota, one serving Deployment and one training Job both requesting it:

workloads   pod-serving-...     admitted: True
            job-training-...    admitted: (pending)

ClusterQueue   used=1   admitted=1   pending=1

One budget, shared, with no custom code. The experiment runs on a laptop and needs no GPU, because Kueue reserves quota at admission, before the scheduler looks for a node.

What is actually left. KServe owns the generated Deployment and reconciles it continuously, so whether that queue label survives is a field-ownership question, not an accounting one. If the label does not propagate from the InferenceService, the legitimate contribution is propagation or an admission mutation, not a second ledger competing with Kueue's. That is the open question, and it is smaller and more honest than the layer originally planned.
