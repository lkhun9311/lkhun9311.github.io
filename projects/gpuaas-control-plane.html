GPUaaS Platform Control Plane

Project · Kubernetes-native · Go · 6 min read

Four Go controllers and a request gateway that coordinate Kueue admission, tenant GPU quota, node quarantine and backend failover. Verification found ten defects that no test caught; an indexed cache lookup cut a per-reconcile cost from 1.64 ms to 1.09 us at 2,000 objects.

gpu-platform-control-plane engineering journal

Scope. A three-node kind cluster with simulated nvidia.com/gpu capacity and a stub inference backend. What is measured is control-plane behaviour.

The problem it addresses#

Training and inference behave in opposite ways under contention, and that single fact shapes the whole design.

A Kubernetes ResourceQuota cannot express the training half. It refuses the creation outright, so there is no queue: kubectl apply simply fails. That is correct for a request and wrong for a job.

The decision that shaped it: quota counted twice#

Two systems can each be correct about GPU usage and still leave half the budget unusable.

Kueue counts a GPU when it admits a workload. A ResourceQuota counts a GPU when the pod exists. Kueue admits a 4-GPU job and unsuspends it, pods appear, and the ResourceQuota charges the same 4 GPUs again. On an 8-GPU budget the tenant is blocked at 4, and neither system reports an error, because each is accurate about its own ledger.

Resolution. When trainingQuota is on, the ResourceQuota stops counting GPUs and the Kueue ClusterQueue is the single authority. CPU and memory stay with the ResourceQuota, where nothing overlaps.

What that costs. Two things. A safety net disappears: if the Kueue controller is down, nothing stops GPU consumption. And a bypass opens: a pod created without the queue label takes GPUs with no limit at all. Closing the second needs an admission webhook that rejects GPU pods lacking a queue label, and that is not built yet.

Where this sits against existing tools#

Serving deployment overlaps KServe directly, and KServe is better at it: autoscaling, scale-to-zero, canary traffic splitting, model-storage integration and runtime abstraction are all there. Rebuilding them is not a defensible use of time.

During design review, before writing any of it, I tested whether the combination already did this. Two experiments on kind, no GPU needed, because Kueue reserves quota at admission rather than at scheduling.

Does Kueue charge a serving Deployment against the training budget? Yes. One ClusterQueue with a single GPU, one serving Deployment and one training Job both requesting it: used=1 admitted=1 pending=1, the serving pod holding the GPU and the Job queued behind it.

Does a queue label on an InferenceService reach the Deployment KServe generates, and stay there? Yes to both. The label arrives on label-probe-predictor and survives a forced reconcile, and Kueue creates a Workload for the serving pod. Survival was checked separately from arrival, because a label that lands once and is stripped later holds quota until something triggers a reconcile and then stops with no error.

So the budget unifies through configuration. The planned controller came out of the design before any of it existed: it would have been a second ledger beside Kueue's, wrong the first time a replica scaled or a rollout overlapped. Two scripts replaced an implementation. Experiment one, experiment two.

Prototype boundary#

Tested against simulated GPU capacity and a stub backend. Running this for real would need queue-label enforcement at admission, rate limiting that survives more than one gateway replica, validation on actual devices, and alerts routed somewhere a human reads, which Prometheus alone does not do. The write-up carries the full claim-by-claim table of what is measured and what is not.
