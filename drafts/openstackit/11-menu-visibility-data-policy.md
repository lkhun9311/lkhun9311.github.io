# 72개의 메뉴 숨김 규칙을 프론트엔드에서 데이터로 옮기기

> 상태: 초안 · 실제 메뉴 URL/고객명 제거 · 공개 미등록

현장별로 감춰야 하는 사이드바 메뉴가 수십 개로 늘어나면서 프론트엔드 배열이 사실상 권한 데이터베이스가 됐다. URL 문자열을 코드에서 필터링하는 방식은 빠르게 시작할 수 있지만, 새 배포마다 번들을 다시 만들고 기준 데이터와 쉽게 어긋난다.

이미 서버의 메뉴 조회에는 두 개의 축이 있었다. `used`는 메뉴 자체의 사용 여부를, `allowed`는 역할별 접근 가능 여부를 표현했다. 따라서 현장 범위에서 제공하지 않는 메뉴는 DB의 `used=false`로 옮기고, 역할 차이는 기존 차단 목록으로 유지하는 편이 모델에 맞았다. 프론트엔드는 서버가 준 트리에서 자식이 모두 사라진 빈 그룹만 정리하면 됐다.

이관 과정에서 가장 위험했던 것은 URL 목록의 출처였다. 개발 DB의 오래된 메뉴 구조에서 가져온 하위 경로 일부가 실제 배포 시드와 달랐다. 개별 경로를 모두 나열하면 이름이 바뀔 때 조용히 누락된다. 공통 접두사가 명확한 하위 트리는 제한된 prefix 조건으로 묶고, 그 외 메뉴만 정확한 목록으로 유지했다.

패치는 다음 성질을 갖도록 만들었다.

- 여러 번 실행해도 결과가 같은 멱등 업데이트
- 어떤 현장 패치가 값을 바꿨는지 추적할 작성자/시각 기록
- 없는 메뉴 행에서는 무해한 no-op
- 기본 시드와 현장 패치를 구분할 수 있는 검증 쿼리
- 로그인 시 한 번 읽는 메뉴 캐시를 고려한 재로그인 안내

또 하나의 함정은 설치 모델이었다. 초기 SQL은 데이터베이스 컨테이너 최초 기동 때만 자동 적용되고, 패치 디렉터리는 자동 실행되지 않았다. 저장소에 SQL 파일이 존재한다는 사실과 현장 DB에 적용됐다는 사실은 다르다. 표준 실행 명령, stdin 전달 옵션, 적용 후 검증 쿼리를 런북에 함께 남겼다. 컨테이너 실행 명령에서 표준 입력 옵션 하나가 빠져 SQL이 아무 오류 없이 실행되지 않는 사례도 있었다.

모든 화면 요소를 DB 메뉴로 옮기지는 않았다. 탭, 버튼, 컬럼, 생성 마법사의 필드는 메뉴 엔티티가 아니므로 컴포넌트 코드에 남겼다. 데이터 기반 제어의 범위를 억지로 넓히지 않고 “탐색 메뉴”라는 모델 경계를 지킨 것이다.

코드에서 데이터로 옮기면 운영이 쉬워지지만, 그 순간 데이터 패치가 제품 코드만큼 중요한 배포 자산이 된다. 기준 데이터와의 대조, 멱등성, 적용 자동화, 캐시 갱신까지 설계해야 진짜 이관이 끝난다.
