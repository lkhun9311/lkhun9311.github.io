# 두 인증 방식에 하나의 세션 정책을 강요하면 생기는 일

> 상태: 초안 · 고객별 설정명 제거 · 공개 미등록

하나의 프론트엔드가 자체 ID/비밀번호 로그인과 외부 SSO를 함께 지원했다. 현장 커스터마이징에서 전역 토큰 갱신을 껐더니 SSO는 의도대로 동작했지만 자체 로그인 사용자는 액세스 토큰이 만료될 때마다 작업 중 로그인 화면으로 쫓겨났다.

원인은 인증 방식마다 다른 생명주기를 하나의 불리언 설정으로 제어한 것이었다. SSO 세션은 상류 포털이 만료와 로그아웃을 결정하고, SSE와 상태 확인으로 그 결정을 전달한다. 자체 로그인은 애플리케이션이 refresh token을 통해 세션을 연장해야 한다. 둘 모두 “로그인됨”이지만 갱신 권한과 만료 주체가 다르다.

전역 refresh 비활성화는 다음 연쇄를 만들었다.

1. 자체 로그인 액세스 토큰이 만료된다.
2. 클라이언트는 refresh 설정이 꺼져 있으므로 갱신을 시도하지 않는다.
3. 다음 API가 401을 반환한다.
4. 공통 인터셉터가 세션 이탈로 처리한다.

해결은 현장 설정을 다시 전부 켜는 것이 아니라 인증 전략별로 정책을 분리하는 것이었다. 자체 로그인은 기존 refresh 경로를 사용하고, SSO는 상류 세션의 liveness와 강제 로그아웃 신호를 따른다. 백엔드도 refresh 요청이 어떤 인증 방식에서 온 것인지 확인해 잘못된 토큰 교환을 막았다.

```text
if session.authType == LOCAL:
    refresh locally before access token expires
elif session.authType == SSO:
    follow upstream liveness and logout signals
```

수정 범위는 작았지만 검증 범위는 넓었다. 자체 로그인 만료 직전 갱신, refresh 실패, SSO 정상 만료, 상류 로그아웃, 관리자 강제 종료, 유휴 시간 만료가 서로의 경로를 침범하지 않는지 확인해야 했다. 특히 공통 401 인터셉터가 먼저 동작하면 올바른 인증 전략이 선택되기 전에 화면 이동이 일어날 수 있었다.

같은 폴더에서 조사한 콘솔 로그 미표시, CPU 100%, 빈 사이드바 같은 이슈는 각각 이미지 설정, 런타임 크래시, 권한 데이터 문제로 수렴했다. 이것도 중요한 대비다. 동시에 나타난 현상을 하나의 세션 버그로 묶지 않고 증거별로 분리해야 한다.

인증 방식이 둘 이상이면 `refresh.enabled` 같은 전역 스위치는 지나치게 거칠다. 필요한 것은 전략별 상태 머신이다. 누가 토큰을 발급하고, 누가 연장하며, 어떤 신호가 세션을 끝내는지를 인증 방식마다 명시해야 한다. 세션 정책은 로그인 화면의 분기가 아니라 인증 주체의 소유권을 표현해야 한다.
