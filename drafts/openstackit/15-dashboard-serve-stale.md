# 사용자가 기다린 것은 REST가 아니라 SSE의 첫 데이터였다

> 상태: 비공개 초안 · 내부 시스템명, 주소, 코드 식별자 제거 · 공개 목록 미등록

OpenStack 관리 콘솔의 통합 모니터링 대시보드는 느렸다. 운영자가 화면에 들어오면 짧게는 5초, 재기동 직후에는 9초 넘게 빈 화면을 봤다. 이미 인프라 구조를 캐시했고 스케줄러도 비동기로 돌고 있었기 때문에 처음에는 남은 병목이 명확하지 않았다.

결론부터 말하면 사용자가 기다린 경계와 처음 측정한 경계가 달랐다. REST 조회는 이미 수십 ms였지만 화면은 SSE(Server-Sent Events)의 첫 업무 데이터가 와야 로딩을 끝냈다. 느린 쿼리를 조금 더 빠르게 만든 것이 아니라, 요청 경로에서 그 쿼리를 완전히 떼어 내자 첫 데이터 중앙값이 6.8초에서 약 10ms로 줄었다.

## 빠른 API를 측정하고도 화면이 느렸던 이유

첫 번째 성능 측정은 대시보드가 함께 호출하는 REST API를 대상으로 했다. 구조 정보 API는 약 20ms였고, 자원 사용량 API는 2~3초였다. 그런데 브라우저에서는 5~10초를 기다렸다. 숫자가 체감과 맞지 않았다.

화면 코드를 다시 따라가 보니 완료 조건은 다음과 같았다.

1. REST로 화면의 구조 정보를 받는다.
2. EventSource가 연결된다.
3. 연결 직후 `connection` 이벤트를 받는다.
4. 노드와 가상서버 메트릭이 담긴 첫 `data` 이벤트를 받는다.
5. 프론트엔드가 로딩 레이어를 해제한다.

일반 HTTP 샘플러는 1~3까지만 보고 성공으로 끝났다. 실제 사용자가 기다린 것은 4였다. 그래서 SSE에 연결한 뒤 첫 `data` 프레임에서 연결을 닫고 경과 시간을 기록하는 작은 계측기를 만들었다. 이 값을 JTL로 변환해 같은 방식으로 퍼센타일과 Apdex를 계산했다.

개선 전 단일 사용자 30회 측정 결과는 체감과 일치했다.

| 지표 | 개선 전 |
|---|---:|
| 콜드 첫 데이터 | 약 9.3초 |
| 중앙값 | 약 6.8초 |
| p95 | 약 8.5초 |
| p99 | 약 8.6초 |
| Apdex | 0.100 |

분포는 빠른 표본과 6~9초 표본으로 갈라졌다. 직전 계산과 타이밍이 맞으면 빨랐고, 그렇지 않으면 새 계산을 통째로 기다렸다.

## 접속이 곧 메트릭 계산이었다

SSE 연결은 즉시 맺어졌지만 실제 데이터는 15초 주기의 작업이 보냈다. 데이터 생성 경로에는 노드와 인스턴스의 여러 measurement를 합치는 Flux 쿼리, 전역 자원 목록 조회, 인증, DTO 조립이 직렬로 놓여 있었다. 접속 시점과 스케줄러 실행 시점에 따라 사용자는 다음 틱까지 기다린 뒤 수초짜리 계산까지 기다렸다.

이미 있던 캐시는 “누가 존재하는가”를 나타내는 토폴로지만 보관했다. 화면이 실제로 필요로 하는 “각 자원이 지금 얼마를 쓰는가”는 캐시 밖에서 매번 계산했다. 캐시를 넣었다는 사실보다 비싼 층이 캐시 안에 들어갔는지가 중요했다.

예외 처리도 문제를 숨겼다. SSE 전송 경로가 계산 예외를 삼키면 연결은 살아 있지만 데이터는 오지 않는다. 프론트엔드는 연결 오류만 기록하고 로딩 레이어를 해제하지 않아 사용자는 오류 메시지 대신 무한 로딩을 봤다.

## 요청 경로에서 계산을 제거했다

대시보드 데이터는 사용자별로 다르지 않고 모든 세션에 같은 값이 브로드캐스트됐다. 그렇다면 접속마다 같은 계산을 반복할 이유가 없다. 15초에 한 번만 완성 payload를 만들고, 접속에는 마지막으로 완성된 값을 즉시 보내는 구조로 바꿨다.

```text
주기 작업 또는 워밍업
    → 제한 시간 안에서 메트릭 수집
    → 화면에 필요한 payload 완성
    → 완성된 스냅샷을 원자적으로 교체
    → 현재 세션에 브로드캐스트

새 SSE 연결
    → 마지막 완성 스냅샷 즉시 전송
    → 값이 없거나 오래됐으면 백그라운드 갱신 요청
```

스냅샷은 참조 하나로 교체해 독자가 절반만 갱신된 값을 보지 않게 했다. 애플리케이션 기동 시 워밍업을 실행해 첫 사용자가 초기 계산 비용을 내지 않게 했다. 수집 작업은 다른 짧은 주기 작업과 별도 실행 lane으로 분리했고, 외부 메트릭 저장소에는 연결·읽기 타임아웃을 뒀다.

갱신에 실패하면 이전 스냅샷을 지우지 않았다. 새 값이 확인될 때까지 마지막 정상값을 제공하는 serve-stale 정책이다. 다만 이 정책이 장애를 감춰서는 안 된다. 계산 시각과 저하 상태를 함께 전달해 값의 신선도를 구분할 수 있게 했다.

## 단순한 캐시에 숨어 있던 세 가지 레이스

구현 리뷰에서는 해피패스에서 보이지 않던 문제를 찾았다.

첫째, 부팅 워밍업 중 사용자가 접속하면 접속이 요청한 갱신은 “이미 갱신 중”이라 취소될 수 있었다. 워밍업이 결과를 캐시에만 넣고 브로드캐스트하지 않으면 사용자는 다음 15초 틱까지 기다린다. 워밍업, 주기 작업, 접속 갱신을 한 함수로 수렴시키고 실제 갱신 승자가 항상 결과를 게시하도록 바꿨다.

둘째, 오래된 캐시를 가진 상태에서 동시 접속 N개가 각각 기존 값을 전체 세션에 다시 보낼 수 있었다. 접속에는 해당 세션만 즉시 응답하고, 새 계산 결과의 전체 브로드캐스트는 갱신 승자 한 번만 수행하게 분리했다.

셋째, 메트릭 클라이언트에 전체 요청 타임아웃을 넣으면 같은 클라이언트를 쓰는 장기 리포팅 쿼리까지 끊을 수 있었다. 전역 총시간 제한 대신 연결과 읽기 단계의 상한만 두고, 기능별 클라이언트 정책을 분리했다.

프론트엔드에서도 SSE를 기다리며 전체 화면을 가리는 게이트를 제거했다. 화면 골격을 먼저 보여 주고 데이터가 오면 채우도록 바꾸자 연결 실패 시 게이트가 영원히 풀리지 않던 기존 버그도 함께 사라졌다.

## 결과와 해석

동일한 첫 `data` 정의로 다시 측정했다.

| 지표 | 개선 전 | 개선 후 |
|---|---:|---:|
| 중앙값 | 약 6,776ms | 약 10ms |
| p95 | 약 8,454ms | 약 20ms |
| p99 | 약 8,607ms | 약 23ms |
| 콜드 첫 데이터 | 약 9,342ms | 약 87ms |
| 오류율 | 0% | 0% |
| Apdex | 0.100 | 1.000 |

이 측정은 순차 단일 사용자 지연 측정이다. 따라서 throughput을 동시 사용자 처리량으로 해석하지 않았다. 의미 있는 값은 첫 업무 데이터까지의 지연 분포, 오류율과 Apdex다.

부속 자원 사용량 REST API는 이 변경 뒤에도 초 단위였다. 프로젝트마다 쿼터 API를 호출하는 별도 N+1이 남았기 때문이다. 대시보드 SSE가 빨라졌다는 결과를 전체 모니터링 화면의 모든 경로가 빨라졌다고 확대하지 않았다.

## 무엇을 하지 않았는가

15초 수집 주기를 5초로 줄이지 않았다. 원천 에이전트도 15초마다 새 표본을 만들기 때문에 같은 표본을 세 번 다시 읽을 가능성이 컸다. 신선도는 좋아지지 않고 저장소 부하만 늘어난다.

스냅샷의 계산 시각과 원천 메트릭의 관측 시각도 하나로 합치지 않았다. 전자는 캐시 갱신 정책을 위한 값이고 후자는 사용자가 데이터의 나이를 판단하는 값이다. 원천이 조용한 상태에서 둘을 섞으면 모든 접속이 캐시를 오래됐다고 판단해 재계산 폭주를 만들 수 있다.

## 남은 교훈

성능 최적화의 첫 질문은 “어떤 API가 느린가”가 아니라 “사용자는 어떤 사건을 기다리는가”여야 한다. HTTP 응답, SSE 연결, 첫 업무 이벤트, 첫 유효 렌더는 서로 다른 완료 조건이다.

그리고 캐시의 목적은 쿼리를 덜 호출하는 데서 끝나지 않는다. 외부 시스템의 지연과 실패를 사용자 요청에서 분리하고, 실패하더라도 마지막으로 확인된 상태를 정직하게 제공하는 데 있다. 이 경계를 세운 뒤에야 대시보드 지연은 외부 쿼리 시간이 아니라 메모리 읽기와 전송 시간으로 바뀌었다.
