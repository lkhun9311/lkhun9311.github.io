# 애플리케이션 자격증명에 RBAC를 붙일 때의 경계

> 상태: 초안 · 내부 권한 코드와 API 경로 제거 · 공개 미등록

사람이 로그인하는 세션에는 역할 정보와 메뉴 권한이 있지만, 자동화용 애플리케이션 자격증명은 흔히 “유효하면 호출 가능”으로 끝난다. 여기에 RBAC를 붙이는 일은 역할 문자열 하나를 추가하는 문제가 아니다. 발급, 저장, 토큰 해석, API 집행, 기존 자격증명 호환까지 한 경계를 설계해야 한다.

먼저 위협 모델을 분리했다. 자격증명이 유출됐을 때 공격자가 무엇을 할 수 있는지, 발급자가 가진 권한보다 넓은 범위를 선택할 수 있는지, 역할이 나중에 회수돼도 오래된 자격증명이 계속 동작하는지 확인했다. 핵심 원칙은 “자격증명에 기록된 역할”만 믿지 않고 현재 정책과 함께 평가하는 것이었다.

설계 선택지는 크게 세 가지였다.

- 발급 시 역할을 복사해 영구 고정한다. 빠르지만 이후 회수가 반영되지 않는다.
- 요청마다 현재 사용자 역할을 조회한다. 최신이지만 자동화 주체와 사람 계정의 생명주기가 강하게 결합된다.
- 자격증명 자체에 제한된 역할 집합을 부여하고, 요청 시 그 범위와 현재 유효 상태를 교차 검증한다.

선택한 방향은 최소 권한의 자격증명 역할을 명시하고 서버가 모든 보호 API에서 이를 일관되게 해석하는 것이었다. 발급자는 자신이 위임할 수 없는 역할을 선택할 수 없어야 하고, 역할이 비어 있을 때의 기본값은 관대하게 기존 권한 전체를 허용하기보다 호환 정책을 명시적으로 분리해야 한다.

데이터 모델에는 자격증명과 역할 매핑의 소유권, 삭제 연쇄, 중복 방지 제약이 필요했다. API 응답은 비밀값을 최초 한 번만 보여 주고 이후에는 식별자와 권한 범위만 반환해야 한다. 감사 로그에는 원래 사용자와 자동화 자격증명을 구별할 수 있는 주체 식별자가 남아야 한다.

가장 까다로운 부분은 기존 UI와 OpenStack 대시보드의 동작을 맞추는 일이었다. 같은 이름의 역할이라도 전역 역할과 프로젝트 역할의 의미가 다를 수 있고, 메뉴 노출 권한과 실제 API 권한이 항상 같지 않다. 따라서 “화면에 버튼이 보인다”를 권한 테스트로 삼지 않고, 역할별로 허용·거부 API 행렬을 만들었다.

테스트는 다음 경계를 포함했다.

- 발급자가 가진 범위를 넘는 역할 요청 거부
- 역할 없는 기존 자격증명의 호환 동작
- 폐기·만료·소유자 비활성화 후 즉시 거부
- 전역과 프로젝트 스코프 혼동 방지
- 목록 응답에서 비밀값 비노출
- UI가 아닌 직접 API 호출에서도 동일한 집행

자동화 자격증명은 사람의 세션보다 오래 살고 눈에 덜 띈다. 그래서 RBAC를 붙일 때는 편리한 토큰 발급 기능이 아니라 “누가 무엇을 얼마나 오래 위임할 수 있는가”라는 보안 경계로 다뤄야 한다.
