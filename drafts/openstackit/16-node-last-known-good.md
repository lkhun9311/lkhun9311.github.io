# 물리 노드 모니터링에서 빈 배열은 성공이 아니었다

> 상태: 비공개 초안 · 내부 코드와 환경값 일반화 · 공개 목록 미등록

대시보드의 첫 화면을 serve-stale로 바꾼 다음 같은 문제를 물리 노드 화면에서 발견했다. SSE 연결 때마다 노드 메트릭을 계산했고, 첫 `data` 중앙값은 약 3.9초였다. 패턴을 그대로 이식하면 될 것 같았지만, 물리 노드는 “마지막 값을 얼마나 믿을 것인가”라는 더 까다로운 문제를 드러냈다.

핵심은 빈 결과의 의미였다. 메트릭 쿼리가 빈 목록을 반환했다는 사실만으로 노드가 0대라고 결론 내릴 수 없다. 실제 대상이 없는 정상 상태일 수도 있고, 메트릭 수집 실패나 구조 정보 부재로 아무것도 매칭하지 못한 상태일 수도 있다. 두 경우를 구분하지 않으면 장애 순간에 정상 화면을 0대로 덮는다.

## 기존 경로와 측정

물리 노드 화면은 REST로 구조를 받고 SSE로 CPU, 메모리, 디스크 등의 실시간 값을 갱신했다. 연결 이벤트 리스너는 메트릭 저장소의 여러 measurement를 합치는 쿼리를 동기로 실행한 뒤 첫 데이터를 보냈다. 같은 사용자가 재접속할 때도 계산을 반복했다.

단일 사용자 30회 기준 개선 전 첫 데이터는 다음과 같았다.

| 지표 | 개선 전 |
|---|---:|
| 중앙값 | 약 3,938ms |
| 최소 | 약 846ms |
| 최대·p99 | 약 5,130ms |
| Apdex | 0.050 |

대시보드보다 계산 범위는 작았지만 사용자가 보는 지연은 여전히 초 단위였다.

## serve-stale의 최소 계약

구조는 대시보드와 같았다. 백그라운드 워커가 15초마다 완성 스냅샷을 만들고, 새 연결에는 마지막 값을 즉시 보낸다. 갱신 실패 시 기존 참조를 유지한다.

```text
snapshot = atomic reference to last completed payload
refreshing = compare-and-set guard

on connect:
    if snapshot exists: send it immediately
    if missing or stale: request refresh

refresh:
    if another refresh is running: return
    try:
        next = collect and assemble
        publish(next)
        broadcast(next)
    catch:
        keep previous snapshot
```

여기서 원자 참조가 보장하는 것은 “완성된 참조의 안전한 교체”까지다. 목록 안의 DTO가 다른 캐시와 공유되고 제자리에서 변경된다면 참조가 원자적이어도 직렬화 중 내용이 찢어질 수 있다. 초기 구현은 구조 DTO를 여러 화면이 공유했기 때문에 이 한계가 남았다. 이후 공유 producer에서 완성 payload를 세대별로 새로 만들고 동결하는 방향으로 해결했다.

갱신 CAS도 과장해서는 안 된다. 실행 함수 안에서 CAS를 잡으면 동시에 수행되는 계산은 막지만 실행기 큐에 이미 쌓인 중복 작업을 합치지는 못한다. 반대로 제출 전에 플래그를 잡으면 작업이 거부됐을 때 플래그를 해제하지 못해 갱신이 영구 정지할 수 있다. 거부 시 반드시 토큰을 반환하는 경로가 필요하다.

## 빈 결과를 세 상태로 나눴다

새 수집이 비었다고 무조건 게시하지 않았다. 인프라 구조의 가용성, 메트릭 fetch 성공 여부, 실제 수집 대상 수와 매칭된 표본 수를 함께 봤다.

```text
if infrastructure is unavailable:
    INFRA_UNAVAILABLE
else if metric fetch failed:
    FETCH_FAILED
else if matched sample count > 0:
    FRESH
else if expected running resource count == 0:
    EMPTY_VALID
else:
    NO_VALID_METRICS
```

`EMPTY_VALID`는 새 값으로 게시할 수 있다. 실제 대상이 0이기 때문이다. `INFRA_UNAVAILABLE`, `FETCH_FAILED`, `NO_VALID_METRICS`에서는 마지막 정상 데이터를 유지하고 degraded 상태와 실패 시각만 갱신한다. 값의 세대와 마지막 시도 결과를 분리하면 오래된 데이터를 새 데이터처럼 가장하지 않으면서 화면을 비우지 않을 수 있다.

초기 물리 노드 구현에서는 이 세분화가 완전하지 않아 “fetch는 성공했지만 결과가 빈 경우”를 정상으로 볼 여지가 있었다. 이 위험을 문서화한 뒤 세 화면을 통합하는 공유 캐시 작업에서 공통 판정 타입으로 끌어올렸다. 한 화면만의 예외 규칙으로 두면 대시보드와 물리 노드가 같은 원천을 서로 다르게 해석하기 때문이다.

## 접속과 갱신의 순서도 데이터다

접속 직후 캐시된 값이 전송되고 거의 동시에 새 브로드캐스트가 도착할 수 있다. 비동기 이벤트 리스너의 실행 순서는 보장되지 않으므로 더 오래된 on-connect 응답이 새 브로드캐스트 뒤에 도착할 수도 있다. 프론트엔드는 payload의 생성 시각 또는 단조 증가하는 generation으로 역전된 프레임을 버려야 한다.

단순히 `HH:mm:ss` 문자열을 차트 키로 사용하는 것으로는 부족하다. 같은 초에 두 세대가 만들어질 수 있고 프로세스 재기동 후 시계가 되감길 수도 있다. 초기 단계에서는 생성 시각 비교와 재기동 재기준화 가드를 사용했고, 이후 설계에서는 표시 시각과 정렬용 generation, 실행 간격용 monotonic 시간을 분리했다.

## 프론트엔드는 값과 신뢰도를 따로 렌더링한다

마지막 정상값을 보여 주는 동안 사용자가 그것을 최신으로 오해하면 안 된다. payload에는 다음 정보를 별도로 실었다.

- 실제 데이터와 데이터가 만들어진 시각
- 마지막 수집 시도의 상태와 시각
- 이전 값을 carry했는지 나타내는 degraded 표시
- 연결 수명 안에서 순서를 판정할 generation

프론트엔드는 `degraded=true`일 때 기존 값을 유지하고 오래된 상태임을 표시한다. `degraded=false`이면서 빈 결과일 때만 실제 0대로 렌더링한다. 이 구분 없이는 “장애를 0으로 표시”하거나 “정상적인 0을 과거 값으로 가림” 중 하나를 피할 수 없다.

## 결과

개별 화면 개선 직후에는 첫 데이터가 수십 ms 범위로 내려갔다. 이후 세 화면을 공유 캐시로 통합한 상태에서 다시 측정한 결과는 다음과 같았다.

| 지표 | 개선 전 | 공유 캐시 반영 후 |
|---|---:|---:|
| 중앙값 | 약 3,938ms | 약 23ms |
| p95 | 약 4,968ms | 약 40ms |
| p99 | 약 5,130ms | 약 43ms |
| 오류율 | 0% | 0% |
| Apdex | 0.050 | 1.000 |

이 측정 역시 동시 사용자 부하시험이 아니라 첫 데이터 지연을 보는 순차 하니스다. 결과는 “몇 명까지 처리한다”가 아니라 요청 경로에서 수집 비용이 제거됐음을 보여 준다.

## last-known-good가 필요한 이유

모니터링 화면은 가장 최신의 숫자만 보여 주는 곳이 아니다. 관측 시스템 일부가 실패했을 때 거짓 0, 빈 화면, 무한 로딩 가운데 무엇을 피할지도 결정해야 한다.

last-known-good는 가용성을 높이지만 데이터의 나이를 감춘다면 위험하다. 반대로 새 수집 실패 때마다 화면을 비우면 운영자가 가장 정보가 필요한 순간에 마지막으로 확인된 상태까지 잃는다. 데이터와 수집 상태를 분리해 모델링해야 “마지막 값은 보여 주되 현재 수집은 실패했다”는 정직한 화면을 만들 수 있다.
