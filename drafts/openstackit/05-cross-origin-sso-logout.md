# CSP를 풀지 않고 교차 오리진 로그아웃을 고친 방법

> 상태: 초안 · URL/설정명/사내 코드 제거 · 공개 미등록

SSO 로그아웃은 성공했지만 사용자는 외부 포털로 돌아가지 못했다. 서버 세션은 끊겼고 응답도 302였으므로 처음에는 프록시나 포털 설정 문제처럼 보였다. 브라우저 콘솔이 알려 준 실제 원인은 CSP의 `form-action 'self'`였다.

기존 흐름은 숨은 폼으로 현재 애플리케이션의 로그아웃 주소에 POST한 뒤, 서버가 다른 오리진의 포털로 리다이렉트하는 방식이었다. 브라우저는 폼 제출의 최종 목적지까지 `form-action` 정책으로 검사한다. 목적지가 다른 오리진이면 세션 종료는 끝났어도 화면 이동은 차단될 수 있다.

빠른 우회는 포털 오리진을 CSP 허용 목록에 넣는 것이다. 그러나 배포 설정에서 URL 문자열을 파싱해 CSP 헤더에 동적으로 삽입하는 방식은 새로운 입력 경계를 만든다. 따옴표, 세미콜론, 치환 문자가 충분히 검증되지 않으면 헤더나 웹 서버 설정 인젝션으로 이어질 수 있다. 또한 고정 라인 번호를 `sed`로 고치는 배포 스크립트는 설정 파일 한 줄만 바뀌어도 깨진다.

해결은 CSP를 느슨하게 하는 대신 이동의 종류를 바꾸는 것이었다.

```text
POST /logout
→ 200 { "redirectUrl": "https://portal.example" }
→ 브라우저가 window.location으로 이동
```

POST는 같은 오리진 fetch이므로 세션 쿠키를 정상적으로 정리한다. 이후의 `window.location`은 폼 제출이 아니라 최상위 내비게이션이므로 `form-action`의 대상이 아니다. 서버가 관리하는 설정에서 목적지를 내려 주기 때문에 클라이언트가 임의 URL을 받는 공개 리다이렉터도 만들지 않는다.

구현 후에는 새로 생긴 경계 조건을 다시 검토했다. 로그아웃 fetch가 진행되는 동안 다른 API의 401 인터셉터가 로그인 흐름을 다시 시작하는 레이스, 네트워크가 멈춰 사용자가 대기하는 문제, JSON이 깨졌을 때의 폴백 목적지가 있었다. first-wins 로그아웃 가드, 짧은 요청 타임아웃, 같은 목적지로 가는 서버 엔드포인트 폴백으로 보완했다.

비슷한 원리로 브라우저가 직접 호출하는 백엔드 경로가 프록시 허용 접두사 밖에 있어 SPA 문서가 반환되던 문제도 있었다. 전용 프록시 규칙을 한 줄 더 주입하는 대신, API 경로 규약 아래로 엔드포인트를 옮겨 기존 라우팅에 포함시켰다.

보안 정책과 기능이 충돌할 때 첫 선택이 정책 완화일 필요는 없다. CSP가 막는 동작이 정말 필요한지, 같은 결과를 더 정확한 브라우저 동작으로 표현할 수 있는지 먼저 봐야 한다. 이 사례에서는 “외부 폼 리다이렉트”를 “세션 종료 응답 + 명시적 내비게이션”으로 분리하자 보안 정책을 유지하면서 기능도 단순해졌다.
