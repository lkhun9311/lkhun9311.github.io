# 요구사항을 받자마자 코딩하지 않는 법

> 상태: 초안 · 여러 운영 검토 기록을 하나의 방법론으로 통합 · 공개 미등록

운영 요구사항 열세 건을 연속으로 검토하면서 가장 많이 한 일은 코드를 쓰는 것이 아니라 “이것이 실제 결함인가”를 판정하는 일이었다. 화면에서 이상해 보이는 동작은 제품 버그, OpenStack 표준 정책, 환경 데이터, 캐시, 단순 노출 요구가 같은 모습으로 나타날 수 있다.

예를 들어 잠긴 인스턴스가 재시작되는 현상은 관리자에게는 OpenStack의 정상적인 override였다. 일반 사용자는 프론트엔드에서 이미 차단되고 있었다. 실제 남은 위험은 UI가 아니라 API 직접 호출 시 서버가 같은 정책을 집행하지 않는 방어심층의 빈틈이었다. 원래 티켓을 그대로 구현했다면 관리자 동작을 깨뜨릴 수 있었다.

역할을 데이터베이스에서 바꿨는데 관리자 화면이 계속 보이는 현상도 역할 갱신 코드의 문제가 아니었다. 애플리케이션을 통한 변경은 캐시를 무효화하지만 SQL 직접 변경은 그 경로를 우회했다. 재로그인도 캐시를 지우지 않아 이전 권한이 TTL 동안 남았다. 해결은 전역 캐시 삭제가 아니라 로그인한 사용자 키의 정확한 접두사만 무효화하는 것이었다.

메뉴 숨김, 전화번호 필드, 장치 정보, 볼륨 타입 설명처럼 어떤 요구는 코드보다 데이터나 문서의 문제였다. 반대로 화면에서는 정상처럼 보이지만 서비스 계정으로 모든 OpenStack 호출을 수행해 사용자 정책이 우회되는 구조는 서버 보강 후보였다.

이 경험에서 만든 판정 순서는 다음과 같다.

1. 관찰한 사용자 역할과 프로젝트 스코프를 고정한다.
2. UI 조건, 백엔드 권한 검사, OpenStack 정책을 따로 추적한다.
3. 실제 응답과 DB 상태를 먼저 보고 추측을 줄인다.
4. 캐시와 비동기 작업처럼 “현재 코드가 읽지 않는 최신 상태”가 있는지 확인한다.
5. 표준 동작, 제품 정책, 현장 커스터마이징을 구분한다.
6. 무변경, 설정/데이터 수정, 최소 코드 변경, 구조 개선을 대안으로 함께 적는다.
7. 완료 조건을 역할별·경로별 테스트로 표현한다.

“코드 수정 불필요”는 아무것도 하지 않았다는 뜻이 아니다. 정상 동작의 근거, 운영 전제, 남은 보안 갭과 후속 조건을 기록해야 비로소 결론이 된다. 반대로 작은 UI 요구처럼 보여도 데이터 원천과 권한 경계가 흔들리면 코드 몇 줄로 끝내서는 안 된다.

좋은 요구사항 분석은 티켓 문장을 구현 명세로 받아들이지 않는다. 관찰을 재현하고, 시스템의 각 계층이 어떤 계약을 지키는지 확인한 뒤, 가장 작은 올바른 변경을 고른다. 때로 그 답은 코드이고, 때로는 데이터 패치이며, 때로는 “현재 동작이 맞다”는 증거다.
