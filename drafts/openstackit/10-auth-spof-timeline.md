# 60초 토큰이 인증 의존점을 장애 증폭기로 만든 과정

> 상태: 초안 · IP/사용자/요청 식별자 제거 · 공개 미등록

사용자는 “로그인 직후 다시 인증 만료가 뜬다”고 보고했다. 애플리케이션 로그만 보면 refresh가 401을 반환했으니 로컬 토큰 문제처럼 보였다. 여러 시스템의 로그를 같은 시계열에 놓자 원인은 상류 사용자 조회 서비스의 짧은 500 오류였다.

흐름은 이랬다.

1. 사용자가 외부 포털 로그인에 성공한다.
2. 포털이 하위 애플리케이션용 OAuth 토큰을 발급한다.
3. 약 60초 뒤 액세스 토큰이 만료된다.
4. refresh 과정이 다시 사용자 조회 서비스를 호출한다.
5. 조회 서비스의 500이 refresh 실패로 변환된다.
6. 하위 애플리케이션은 401을 받고 정상적으로 세션을 종료한다.
7. 사용자가 재로그인해도 같은 조회 서비스가 실패해 로그인 자체가 500이 된다.

하위 애플리케이션의 경고창은 원인이 아니라 결과였다. 진짜 문제는 로그인과 refresh가 매번 같은 사용자 조회 의존점을 통과하고, 짧은 토큰 TTL 때문에 그 의존점을 매우 자주 호출한다는 구조였다. 잠깐의 장애가 유효 세션 전체로 빠르게 퍼지는 장애 증폭기가 된 것이다.

이 분석에서 중요한 것은 오류 코드보다 사건의 시간 관계였다. 발급 시각과 만료 시각, 첫 refresh, 상류 500, 사용자 로그아웃, 재로그인 실패를 한 표에 놓았다. 그러자 “로그인은 성공했으니 상류는 정상”이라는 가정이 깨졌다. 로그인 순간에는 정상이었고 1분 뒤 refresh 순간에는 장애였을 뿐이다.

같은 실패도 경로마다 다르게 표현됐다. refresh는 인증 실패 401로, 신규 로그인은 사용자 없음에 가까운 500으로 바뀌었다. 상류의 기술적 실패를 도메인상의 “사용자 없음”으로 번역하면 운영자는 데이터 문제를 의심하게 된다. 의존 서비스 오류, 사용자 부재, 자격 증명 오류를 서로 다른 사유로 보존해야 한다.

개선 지점은 여러 층에 있다.

- 상류 서비스의 이중화와 헬스체크
- refresh의 제한적 재시도와 짧은 그레이스 구간
- 안정적으로 검증된 사용자 정보의 제한적 캐시
- 위험 모델에 맞는 토큰 TTL 재조정
- 하위 애플리케이션에 `UPSTREAM_UNAVAILABLE` 같은 사유 전달
- SSE 연결 종료 중 발생하는 부수 예외를 원인 로그와 분리

재시도는 무조건 정답이 아니다. 인증 실패 자체를 재시도하면 공격이나 폐기된 세션을 오래 살릴 수 있다. 네트워크/5xx 같은 일시 실패에만 제한하고, 마지막으로 성공한 검증 시각과 토큰 만료를 함께 고려해야 한다.

인증 시스템의 가용성은 로그인 API 하나의 가용성이 아니다. 토큰 수명 동안 반복되는 검증과 refresh 의존성의 곱이다. 짧은 TTL은 보안 통제를 강화할 수 있지만, 그만큼 상류 의존점의 장애를 사용자 세션으로 더 빨리 전파한다.
