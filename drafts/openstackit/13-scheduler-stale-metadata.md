# 스케줄러가 실행됐다는 로그만 믿으면 안 되는 이유

> 상태: 초안 · 환경 주소/실제 경로 제거 · 공개 미등록

스냅샷 스케줄러 로그에는 매분 잡이 시작되고 완료됐다고 찍혔지만 스냅샷은 하나도 생성되지 않았다. 잡 스케줄링과 업무 실행이 같은 성공 로그에 가려진 사례였다.

첫 번째 원인은 Quartz에 직렬화된 `JobDataMap`이었다. 업무 DB의 사용 여부는 활성으로 바뀌었지만 이미 등록된 Quartz 잡에는 오래된 비활성 값이 남아 있었다. 트리거는 정상 발화했고 잡 래퍼도 완료됐지만, 런처가 오래된 값으로 태스크릿 실행을 건너뛰었다. “잡이 실행됨”과 “업무 스텝이 실행됨”을 구분하는 로그가 없었다면 더 오래 헤맸을 것이다.

두 번째 원인은 스키마 드리프트였다. 새 엔티티가 저장하려는 두 컬럼이 운영 DB에는 없었다. 스케줄러가 정상화돼 외부 스냅샷을 만든 다음 내부 이력을 저장하는 단계에서 실패할 수 있는 상태였다. 저장소의 초기 스키마와 패치 파일, 실제 DB를 함께 비교해 누락 패치를 확인했다.

조치는 Quartz 메타데이터를 현재 업무 설정에서 다시 등록하고, 필요한 DB 패치를 적용한 뒤 프로세스를 재기동하는 것이었다. 검증은 `STARTED/COMPLETED` 로그로 끝내지 않았다.

- 트리거가 잡을 획득했는가
- 잡 파라미터가 현재 활성 값을 담는가
- 실제 Step이 시작되고 유의미한 시간이 걸렸는가
- 외부 클라우드에 스냅샷이 생겼는가
- 내부 이력 INSERT에 새 컬럼이 포함됐는가
- 최종 자원 상태가 `available`인가

이 다섯 층을 확인한 뒤에야 정상화로 판정했다.

실제 실행이 살아나자 숨은 부수 문제도 드러났다. 로컬 백업 기능이 스냅샷에서 임시 볼륨을 만들다가 프로젝트 볼륨 쿼터에 막혔고, 설정에는 개발자 PC 경로가 남아 있었다. 핵심 스냅샷과 DB 기록은 성공했지만 선택적 후처리가 실패한 것이다. 이런 경우 잡 전체를 성공 하나로 표시하면 운영자는 부분 실패를 놓친다.

코드 리뷰에서는 더 위험한 잠재 결함도 찾았다. 인스턴스 이미지 정리 로직이 관리자 전역 목록에서 `queued` 상태까지 삭제했고, 생성 완료 대기 시간이 이미지 크기와 직접 연결돼 지나치게 짧았다. 타임아웃 뒤 방금 만든 `queued` 이미지를 “쓸모없음”으로 삭제할 수 있는 조합이었다. 성공 경로 복구와 별개로 정리 범위, 프로젝트 스코프, 상태 정의를 다시 설계해야 했다.

스케줄러 운영에서 최소 관측 단위는 “잡 실행”이 아니다. 트리거, 업무 스텝, 외부 부작용, 내부 기록, 후처리를 따로 봐야 한다. 하나의 COMPLETED는 이 모든 계약을 증명하지 못한다.
