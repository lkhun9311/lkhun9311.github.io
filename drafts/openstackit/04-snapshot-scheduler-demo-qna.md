# 스냅샷 스케줄러를 설명하며 드러난 제품의 진짜 계약

> 상태: 초안 · 공개 미등록

기능 시연을 준비하며 예상 질문을 정리했더니 코드보다 더 중요한 것이 보였다. 사용자가 궁금한 것은 cron 표현식이나 배치 클래스가 아니라 “언제 만들어지고, 실패하면 어떻게 되며, 무엇까지 보존되는가”였다. Q&A를 만드는 일은 기능의 외부 계약을 역으로 명세하는 작업이었다.

스냅샷 스케줄러의 계약은 대략 다음과 같다.

- 사용자는 대상 자원, 실행 주기, 시작 시각과 최대 보관 개수를 정한다.
- 스케줄을 일시 중지하고 다시 시작할 수 있다.
- 실행 실패는 해당 주기에 기록되며 다음 정규 주기에 다시 시도한다.
- 대상 자원이 사라지면 무의미한 반복을 막기 위해 스케줄을 정지한다.
- 자동 생성된 결과는 원래 자원 유형의 스냅샷 목록에서 확인한다.
- 보관 정책은 개수 기반이며, 용량 기반 정책은 별도 기능이다.

이 설명을 쓰면서 모호한 부분도 드러났다. “인스턴스 스냅샷”이 이미지 한 개만 의미하는지, 부팅 볼륨과 데이터 볼륨까지 포함하는지 제품 경로마다 달랐다. 실행이 실패했을 때 로그만 남는지 화면에서도 보이는지, 즉시 재시도가 없는 이유가 무엇인지도 명확히 써야 했다. 이름을 수정하지 못하는 제약은 UI의 우연이 아니라 스케줄러 내부 키로 이름을 사용하는 설계와 연결돼 있었다.

좋은 Q&A는 기능을 과장하지 않는다. in-use 볼륨 처리, 최대 보관 용량, 관리자와 프로젝트 사용자의 가시성처럼 지원 범위를 정확히 나눈다. 구현되지 않은 기능을 “가능”으로 말하지 않고, 우회 절차와 한계를 함께 제시한다.

시연 문서에는 성공 경로뿐 아니라 다음 질문도 반드시 포함해야 한다.

1. 실행 시각을 놓치면 어떻게 되는가?
2. 생성은 성공했지만 후처리가 실패하면 결과는 무엇인가?
3. 쿼터가 부족하면 기존 백업을 먼저 지우는가?
4. 대상이 일시적으로 조회되지 않는 것과 실제 삭제된 것을 구분하는가?
5. 스케줄 이름과 내부 잡 식별자는 분리돼 있는가?

당시 Q&A는 이후 실제 결함을 찾는 체크리스트가 됐다. 실패 상태 미표시, 대상 조회 오류를 삭제로 오판하는 문제, 보관 개수와 쿼터 헤드룸의 충돌 같은 항목이 바로 이 질문들에서 이어졌다.

기술 문서가 코드 설명에서 끝나면 독자는 구현을 알게 되지만 제품을 이해하지는 못한다. 사용자의 질문으로 기능을 다시 쓰면 상태 전이, 실패 정책, 보존 범위라는 진짜 계약이 보인다. 시연 Q&A는 발표 자료가 아니라 가장 가벼운 형태의 제품 명세가 될 수 있다.
