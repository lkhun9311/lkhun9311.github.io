# 세 개의 serve-stale 캐시를 하나로 합치며 다시 배운 공유 상태의 의미

> 상태: 비공개 초안 · 사내 코드명과 저장소 경로 제거 · 공개 목록 미등록

대시보드, 물리 노드, 가상자원 화면을 각각 serve-stale로 바꾸자 첫 데이터는 모두 빨라졌다. 하지만 같은 원천 메트릭을 페이지마다 따로 수집했다. 노드 메트릭은 대시보드와 물리 노드가 중복 조회했고, 인스턴스 메트릭은 대시보드와 가상자원이 중복 조회했다.

세 캐시를 하나로 합치면 중복 수집을 제거할 수 있다. 실제 작업은 자료구조 세 개를 하나로 바꾸는 것보다 훨씬 컸다. 분리된 캐시가 우연히 지키던 경로별 보존, 부분 실패 격리와 전송 순서가 공유 상태의 명시적 계약이 되어야 했다.

## 통합 전 구조가 가진 세 가지 문제

첫째는 중복 외부 쿼리다. 세 화면의 15초 주기가 겹치면 같은 노드와 인스턴스 데이터를 여러 번 수집했다. 화면이 늘어날수록 원천 부하는 소비자 수에 비례했다.

둘째는 가변 DTO 공유였다. 구조 캐시가 반환한 객체를 각 페이지가 제자리에서 메트릭으로 보강했다. 한 스레드가 값을 바꾸는 동안 다른 스레드가 SSE JSON으로 직렬화하면 한 payload 안에 서로 다른 시점이 섞일 수 있었다. 원자 참조로 스냅샷 포인터를 교체해도 내부 객체가 공유·가변이면 불변 스냅샷이 아니다.

셋째는 장애를 빈 값으로 확정하는 문제였다. 인프라 조회나 메트릭 fetch가 실패했는데 빈 목록을 새 정상 스냅샷으로 게시하면 마지막 정상 화면이 0으로 덮였다.

## 단일 producer와 불변 발행

최종 구조는 수집, 판정, 조립, 발행, 전송을 분리했다.

```text
refresh triggers
    ├─ 15-second scheduler
    ├─ application startup
    └─ cold or stale connection
            ↓
single collect worker
    → read infrastructure once
    → collect each required metric once
    → judge each item independently
    → assemble each page once
    → freeze immutable payloads
    → publish one generation
            ↓
fair session transmitter
    → send latest generation per session
```

한 generation에서 원천 메트릭은 한 번만 수집하고 각 화면의 완성 payload도 한 번만 조립한다. 접속 경로는 완성된 바이트 수준의 payload를 읽어 전송만 한다. 새 세대는 이전 세대의 DTO를 변경하지 않고 새 객체로 만든다.

시간도 하나의 값에 여러 의미를 싣지 않았다.

- `nanoTime`: 최소 수집 간격 판정. 시스템 시각 보정의 영향을 받지 않는다.
- epoch millisecond: 사용자에게 데이터 시각 표시.
- 순번 generation: 전송 순서와 중복 제거.

최초 실행을 `Long.MIN_VALUE`로 표시한 뒤 현재 값과 빼는 구현은 오버플로로 첫 수집을 영구 차단할 수 있었다. “아직 실행하지 않음”은 숫자 센티널 대신 Optional 상태로 표현했다.

## 부분 실패는 항목별로 carry한다

대시보드는 노드와 인스턴스 결과를 결합한다. 인스턴스 메트릭만 실패했다고 성공한 노드까지 이전 세대로 되돌리면 한 의존성 장애가 전체 화면을 늙게 만든다. 반대로 빈 인스턴스 목록을 새 값으로 받으면 실제 VM 수를 0으로 덮는다.

수집 결과는 데이터뿐 아니라 fetch 성공 여부를 포함했고, 공통 판정기는 인프라 가용성, 예상 대상 수와 매칭 표본 수를 봤다.

```text
FRESH             새 데이터와 새 data generation 게시
EMPTY_VALID       실제 대상이 0이므로 정상 빈 데이터 게시
INFRA_UNAVAILABLE 이전 데이터 carry + degraded
FETCH_FAILED      이전 데이터 carry + degraded
NO_VALID_METRICS  이전 데이터 carry + degraded
```

carry할 때 데이터와 그것이 만들어진 generation은 유지하고, 마지막 시도 상태와 시각만 새로 기록했다. “이 데이터는 이전 것이지만 방금 갱신 시도는 실패했다”를 표현하기 위해서다. 판정과 실제 DTO 매칭은 같은 resolver를 사용했다. 판정은 UUID로 찾고 조립은 다른 id로 찾는 식의 불일치를 막았다.

## 공유 캐시가 경로별 값을 지워 버린 회귀

통합 후 가장 눈에 띈 회귀는 페이지 전환 뒤 재진입이었다. 단일 producer는 현재 구독 중인 경로만 계산해 한 `pages` 맵으로 게시했고, 게시할 때 이전 맵을 통째로 교체했다.

물리 노드 화면만 열어 둔 채 갱신이 실행되면 최신 generation에는 노드 페이지만 남는다. 이전 대시보드 값은 캐시에서 사라진다. 이후 대시보드에 접속하면 즉시 보낼 값이 없어 수집 한 사이클을 기다렸다. 실측 재진입은 약 5,115ms였고 바로 다시 접속하면 16ms였다.

분리된 캐시가 갖고 있던 계약은 “다른 경로의 갱신이 내 마지막 값을 지우지 않는다”였다. 이를 다음처럼 복원했다.

```text
latestGeneration = 이번 수집에 포함된 페이지 집합
lastPageByPath[path] = 각 경로의 마지막 성공 payload

publish(generation):
    replace latestGeneration
    merge included pages into lastPageByPath

onConnect(path):
    send lastPageByPath[path] immediately
    if path is absent from latestGeneration:
        request refresh
```

같은 재현 조건에서 5,115ms가 17ms로 줄었다. 접속 직후 오래된 값이 잠깐 보일 수 있지만 refresh를 즉시 요청해 곧 새 값으로 바꾼다. “5초 빈 화면”보다 “즉시 last-known-good, 곧 fresh”를 선택했다.

## 느린 소비자를 수집에서 분리했다

SSE의 `send()`는 느린 클라이언트에서 블로킹될 수 있다. 수집 락을 브로드캐스트가 끝날 때까지 잡으면 한 클라이언트의 네트워크가 다음 메트릭 수집을 늦춘다. 그래서 새 generation을 게시한 직후 수집 토큰을 해제하고 전송은 별도 컴포넌트에 넘겼다.

일반 실행기 큐에 세션별 작업을 넣으면 작은 풀에서 앞 세션만 반복 수락되고 뒤 세션은 계속 거부되는 기아가 생길 수 있었다. 전송기는 준비 deque와 상주 워커를 사용했다.

- 세션마다 pending payload는 가장 큰 generation 하나만 유지한다.
- 세션은 큐에 한 번만 들어간다.
- 워커가 한 번 전송한 뒤 새 pending이 있으면 tail에 다시 넣는다.
- 이미 보낸 generation 이하의 값은 버린다.
- 종료된 세션은 전송 직전에도 다시 확인한다.

이 구조는 느린 세션이 수집을 막지 않고 여러 세션이 round-robin으로 기회를 얻도록 한다. 다만 동기 send 자체가 사라진 것은 아니다. 동시에 블로킹된 세션 수가 워커 수를 넘으면 전송은 여전히 늦어진다. 비동기 I/O나 느린 세션 선제 축출은 별도 과제로 남겼다.

## 통합 결과

공유 캐시와 재진입 수정까지 반영한 뒤 세 화면의 첫 SSE 데이터를 다시 측정했다.

| 화면 | 개선 전 중앙값 | 최종 중앙값 | 개선 전 p99 | 최종 p99 |
|---|---:|---:|---:|---:|
| 대시보드 | 약 6,776ms | 약 23ms | 약 8,607ms | 약 55ms |
| 물리 노드 | 약 3,938ms | 약 23ms | 약 5,130ms | 약 43ms |
| 가상자원 | 약 1,436ms | 약 23ms | 약 1,742ms | 약 37ms |

세 경로 모두 오류율 0%, Apdex 1.000이었다. REST 구조·자원 조회도 수십 ms 이내를 유지해 이전 개선의 회귀가 없음을 확인했다. 다만 가상자원 재측정 당시 일부 메트릭이 없는 환경이었으므로, 데이터가 있는 조건의 직접 Before/After는 앞선 개별 개선 측정을 기준으로 삼았다.

## 공유 상태를 합칠 때 확인할 것

캐시 통합은 객체 수를 줄이는 리팩터링이 아니다. 다음 질문에 답해야 한다.

- 특정 소비자가 현재 구독되지 않아도 마지막 값은 보존되는가?
- 한 원천의 실패가 다른 원천의 성공을 되돌리는가?
- 빈 값은 정상적인 0인가, 판단 불가인가?
- payload 내부 객체까지 세대별로 불변인가?
- 새 값과 오래된 값이 역전 전송될 수 있는가?
- 느린 소비자가 producer를 막는가?
- 프로세스가 여러 대라면 producer도 여러 개인가?

중복 수집을 없애 얻은 성능 이득보다 더 중요한 결과는 이 의미들을 코드와 테스트로 명시한 것이다. 공유 상태는 한 곳에 모았다고 단순해지는 것이 아니라, 암묵적이던 계약을 모두 드러냈을 때 비로소 관리할 수 있다.
