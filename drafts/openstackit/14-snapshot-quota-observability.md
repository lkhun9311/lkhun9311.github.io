# 쿼터 실패를 상태와 이력으로 바꾸는 스케줄러 설계

> 상태: 초안 · 내부 API/테이블명 일반화 · 공개 미등록

프로젝트의 스냅샷 쿼터가 가득 차면 스케줄러는 매 실행마다 실패했지만 화면의 상태는 계속 “실행 중”이었다. 사용자는 결과가 만들어지지 않는 이유를 알 수 없고 운영자는 배치 로그를 찾아야 했다. 더 나쁜 것은 등록 시 검증이 대상 프로젝트가 아닌 기본 쿼터와 다른 스코프의 사용량을 보고 있었다는 점이다.

문제는 세 층으로 나뉘었다.

1. 등록·수정 검증의 데이터 원천이 틀렸다.
2. 실행 시점에는 쿼터가 변할 수 있는데 별도 게이트가 없었다.
3. 외부 API 실패를 스케줄 상태와 사용자 메시지로 보존하지 않았다.

검증은 대상 프로젝트의 실제 `limit`, `in_use`, `reserved`를 읽도록 바꿨다. 생성뿐 아니라 수요를 늘리는 수정에도 같은 검증을 적용했다. 그래도 등록과 실행 사이에는 TOCTOU가 남는다. 그래서 배치가 생성하기 직전에 개수와 용량 쿼터를 다시 확인하고, 외부 서비스가 최종적으로 413을 반환하는 경우도 예상 가능한 실패로 분류했다.

실패 모델에는 상태, 사유 코드, 상세 설명과 시각을 추가했다. `FAILED`라는 enum이 이미 있어도 실제 저장 경로와 컬럼이 없으면 기능은 존재하지 않는 것과 같다. 화면은 번역 가능한 사유 코드와 구체적인 필요량/여유량을 함께 보여 주도록 했다.

작업 중 가장 큰 위험은 쿼터와 직접 관련 없어 보이는 보관 순서에서 발견됐다. 기존 코드는 부착 볼륨의 오래된 백업을 먼저 지운 뒤 새 스냅샷을 만들었다. 바로 그 다음 생성이 쿼터나 외부 오류로 실패하면 마지막 정상 백업까지 사라진다. 순서를 “새 결과 생성 → 사용 가능 상태 확정 → 오래된 결과 정리”로 바꿨다.

이 안전한 순서는 새로운 트레이드오프를 만든다. 최대 보관 개수가 쿼터 한도와 같으면 새 결과를 만들 여분 한 칸이 없어 계속 실패한다. 따라서 개수 기반 보관 정책은 최소 `보관 개수 + 1`의 헤드룸을 요구한다. 기존 백업을 먼저 지우면 헤드룸은 필요 없지만 데이터 손실 위험이 커진다. 자동 백업에서는 안전한 순서와 명시적인 용량 요구를 택했다.

또 대상 자원이 없다는 판단과 일시적인 조회 실패를 분리했다. 둘을 모두 `false`로 반환하면 OpenStack 통신 장애 한 번에 스케줄이 영구 정지한다. 실제 부재는 실패 이력을 남기고 정지하지만, 조회 오류는 이번 실행만 실패로 기록하고 다음 주기에 재시도한다.

스케줄러의 품질은 성공 횟수만으로 평가할 수 없다. 실패가 예상 가능한 상태로 모델링되고, 이전 백업을 보존하며, 사용자가 다음 행동을 결정할 수 있는 정보를 제공해야 한다. 로그 속 예외를 제품의 상태와 계약으로 끌어올리는 것이 관측 가능성의 핵심이다.
