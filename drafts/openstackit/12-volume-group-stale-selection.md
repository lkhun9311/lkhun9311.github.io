# 서버 데이터는 최신인데 버튼은 비활성인 이유

> 상태: 초안 · 내부 컴포넌트명 제거 · 공개 미등록

볼륨 그룹에 볼륨을 추가한 뒤 “그룹 스냅샷 생성” 버튼이 계속 비활성 상태였다. 네트워크 응답에는 그룹의 볼륨 목록이 정확히 들어 있었고, 페이지를 완전히 새로고침하면 버튼이 활성화됐다. 서버가 최신 값을 줬는데 화면은 이전 값을 보고 있었다.

버튼 조건은 선택된 행의 `volumes` 배열이 비어 있는지를 확인했다. 문제는 목록을 다시 가져왔을 때 데이터 그리드가 새 행과 기존 행을 같은 엔티티로 연결하지 못한 것이었다. 화면은 행 식별자 함수를 전달했지만 공통 그리드 래퍼에서 그 속성이 실제 그리드까지 전달되지 않았다.

그 결과 in-place refetch 후에도 선택 상태 객체는 볼륨 추가 전의 스냅샷을 계속 가리켰다.

```text
서버 응답: selected group, volumes=[new volume]
화면 목록: 최신 행 데이터로 교체됨
선택 상태: 이전 행 객체, volumes=[]
버튼 조건: selected.volumes is empty → disabled
```

전체 새로고침이 문제를 고치는 이유도 설명된다. 처음부터 최신 행을 선택하므로 오래된 객체 참조가 없다. 이런 증상은 캐시 문제로 오해하기 쉽지만 실제로는 클라이언트 상태의 객체 identity 문제다.

근본 수정은 그리드에 안정적인 `getRowId`를 연결해 refetch 시 같은 행의 데이터가 갱신되게 하는 것이다. 작업 성공 후 선택된 행을 최신 목록에서 다시 찾아 동기화하는 보강도 가능하다. 중요한 것은 버튼에서 서버를 다시 호출하거나 강제로 활성화하지 않는 것이다. 그렇게 하면 표시만 고쳐지고 다른 선택 기반 액션은 여전히 오래된 데이터를 사용한다.

같은 조사에서 in-use 볼륨을 포함한 그룹 스냅샷의 한계도 확인했다. 개별 볼륨 스냅샷 API에는 강제 생성 옵션이 있지만 그룹 스냅샷 API와 사용 중인 SDK 모델에는 같은 옵션이 없었다. 따라서 백엔드 드라이버가 지원하지 않으면 애플리케이션 코드로 억지로 강제할 수 없다. 볼륨을 분리하거나 개별 스냅샷으로 전환하는 것이 현실적인 우회다.

이 사례의 디버깅 순서는 재사용할 만하다.

1. API 응답이 최신인지 확인한다.
2. 목록 행 데이터와 선택 상태 객체를 따로 본다.
3. refetch 전후 객체 identity와 행 키를 확인한다.
4. 전체 새로고침과 in-place 갱신의 차이를 이용해 범위를 좁힌다.

리액티브 UI에서 “서버 값이 맞다”는 화면이 맞다는 뜻이 아니다. 파생 상태가 어떤 객체를 참조하는지, 공통 래퍼가 라이브러리의 identity 계약을 실제로 전달하는지까지 확인해야 한다.
