# 가상자원 화면은 두 개의 병목을 모두 없애야 빨라졌다

> 상태: 비공개 초안 · API/클래스/환경 식별정보 제거 · 공개 목록 미등록

가상자원 모니터링 화면에는 서로 독립적으로 시작하는 두 데이터 경로가 있었다. REST는 프로젝트별 할당량과 사용량을 만들었고, SSE는 가상서버 메트릭을 보냈다. 개선 전 REST 중앙값은 약 2.6초, SSE 첫 데이터는 약 1.4초였다.

한쪽만 고치면 화면은 빨라지지 않는다. 전체 로딩 시간은 두 요청의 합이 아니라 늦게 끝나는 쪽이기 때문이다.

```text
pageReady = max(REST usage, SSE first data, small configuration request)
```

REST만 고치면 SSE의 1.4초가 남고, SSE만 고치면 REST의 2.6초가 남는다. 이 화면의 성능 작업은 단일 병목 최적화가 아니라 서로 다른 두 게이트를 제거하는 일이었다.

## 첫 번째 병목: 프로젝트 수만큼 늘어나는 할당량 조회

REST 경로는 프로젝트 목록을 순회하며 각 프로젝트의 컴퓨트와 네트워크 또는 스토리지 할당량을 차례로 조회했다. 프로젝트가 N개면 외부 호출이 약 2N개가 됐다. 클라이언트 팩터리가 호출 때마다 인증까지 수행하는 경로라면 비용은 더 커진다.

처음 떠오르는 해결은 병렬화다. 그러나 무제한 병렬 호출은 인증 서비스와 OpenStack API, 애플리케이션 스레드 풀에 순간 부하를 몰아넣는다. 중앙값은 줄어도 p99와 오류율이 나빠질 수 있고, 요청이 몰리면 사용자 수만큼 같은 팬아웃이 복제된다.

선택한 방법은 팬아웃을 사용자 요청에서 떼어 내는 것이었다.

```text
background usage loader:
    read current project list
    for each project:
        fetch required quota values
    publish one coherent usage snapshot

REST request:
    return last completed snapshot
```

로더는 단일 실행 문맥에서 서비스 클라이언트를 만들고 사용했다. SDK가 스레드 로컬 세션에 의존할 수 있어, 한 스레드에서 만든 클라이언트를 다른 비동기 작업에 넘기지 않았다. 외부 호출에는 이 로더 범위에서만 연결·읽기 제한을 적용했다.

캐시는 `refreshAfterWrite` 방식으로 갱신했다. 갱신이 실패해도 마지막 값을 유지하고, 호출자는 짧은 콜드 상한을 넘으면 빈 초기 응답을 받을 수 있게 했다. 여기서 중요한 리뷰 지적이 나왔다. 인프라 구조 캐시가 저하돼 빈 프로젝트 목록을 반환했을 때 로더가 이를 정상 성공으로 받아들이면 `0/0` 사용량이 새 정상값으로 저장된다.

수정은 구조 정보가 없을 때 예외를 내도록 하는 것이었다. 실패는 기존 값을 보존하지만, 빈 목록의 성공은 기존 값을 0으로 덮는다. serve-stale에서는 실패를 정확히 실패로 표현해야 캐시 라이브러리가 마지막 정상값을 지킬 수 있다.

REST 중앙값은 약 2,627ms에서 5~12ms 범위로, p99는 약 3,005ms에서 10~20ms대로 내려왔다.

## 두 번째 병목: 접속할 때 계산하는 SSE

SSE도 다른 모니터링 화면과 같은 문제를 갖고 있었다. 연결 시 메트릭을 새로 수집해 첫 데이터를 보냈다. 15초 워커가 미리 완성 스냅샷을 만들고 접속 시 즉시 재생하는 구조로 바꿨다.

구현에는 세 가지 안전장치가 필요했다.

첫째, 접속 응답과 주기 브로드캐스트가 역전될 수 있으므로 프론트엔드가 생성 시각으로 오래된 프레임을 버렸다. 둘째, 프로세스 재기동으로 시각 기준이 되감기는 경우 새 스트림을 받아들일 수 있도록 재기준화했다. 셋째, 접속 때 SSE가 REST보다 먼저 도착해도 첫 프레임으로 프로젝트와 VM 목록을 초기화하게 했다.

마지막 항목은 실제 회귀 후보였다. 기존 화면은 REST가 먼저 도착한다는 암묵적 순서에 기대고 있었다. 이전 상태가 비어 있으면 SSE 병합 함수를 일찍 반환했고, 느렸던 REST가 우연히 그 상태를 먼저 채워 줬다. SSE를 수십 ms로 줄이면 순서가 뒤집혀 다음 15초 브로드캐스트까지 화면이 비게 된다. 성능 개선이 숨은 순서 의존성을 드러낸 것이다.

SSE 중앙값은 약 1,436ms에서 24ms, p99는 약 1,742ms에서 70ms 이내로 줄었다.

## 전체 화면은 왜 24ms가 됐는가

두 증분의 결과를 화면 완료 기준으로 다시 계산했다.

| 경로 | 개선 전 중앙값 | 개선 후 중앙값 |
|---|---:|---:|
| REST 할당량/사용량 | 약 2,627ms | 약 5~12ms |
| SSE 첫 메트릭 | 약 1,436ms | 약 24ms |
| 전체 화면의 지배값 | 약 2,627ms | 약 24ms |

개선 전에는 REST가 최대값이었고, 개선 후에는 SSE가 최대값이었다. 결과적으로 첫 화면은 약 2.6초에서 24ms, p99는 약 3초에서 70ms 안쪽으로 줄었다. Apdex도 0에서 1.0으로 바뀌었다.

이 계산은 두 경로가 병렬로 시작한다는 사실을 반영한다. 성능 보고서에서 독립 요청의 시간을 무조건 합산하면 사용자가 실제로 기다린 시간보다 크게 나온다. 반대로 가장 빠른 한 경로만 제시하면 나머지 게이트를 숨긴다. 프론트엔드의 완료 조건을 식으로 먼저 표현해야 올바른 대표값을 고를 수 있다.

## 리뷰에서 남긴 한계

개별 화면 캐시는 여전히 다른 화면과 같은 가변 구조 DTO를 공유했다. 한 화면이 제자리에서 DTO를 갱신하는 동안 다른 화면이 직렬화하면 세대가 섞일 수 있었다. 또 인프라가 저하됐을 때 SSE가 빈 스냅샷을 정상으로 게시하는 문제는 세 화면에 공통이었다. 한 화면에만 예외 처리를 붙이면 같은 원천을 화면마다 다르게 해석하게 된다.

이 두 문제는 다음 공유 캐시 작업으로 넘겼다. 단일 producer가 구조와 메트릭을 한 번만 읽고, 세대별 완성 payload를 새 객체로 만들어 불변 발행하며, 빈 결과를 공통 상태 타입으로 판정하도록 했다.

프로젝트 집합 변경도 남은 과제였다. 프론트엔드가 기존 프로젝트에 메트릭만 합치는 방식이면 최초 스냅샷 이후 추가된 프로젝트가 새로고침 전까지 보이지 않고 삭제된 프로젝트가 남을 수 있다. SSE 스냅샷을 권위 있는 전체 집합으로 볼지, REST 구조와 병합할지 계약을 명시해야 한다.

## 교훈

N+1 최적화의 가장 좋은 결과는 N개의 호출을 더 빨리 끝내는 것이 아니다. 사용자 요청과 외부 시스템의 N개 호출 사이의 동기 결합을 끊는 것이다.

또한 화면 성능은 가장 눈에 띄는 API 하나의 시간이 아니다. 병렬 경로 가운데 마지막으로 끝나야 하는 게이트가 사용자 지연을 결정한다. 각 경로를 따로 재고 전체 완료식을 함께 기록해야 “한쪽만 빨라진 최적화”를 완료로 착각하지 않는다.
