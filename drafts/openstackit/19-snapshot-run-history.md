# 배치 로그를 사용자에게 보여 준다고 실행 이력이 되지는 않는다

> 상태: 비공개 초안 · 고객/환경/내부 코드 식별정보 제거 · 공개 목록 미등록

스냅샷 스케줄러는 자동으로 인스턴스 이미지와 볼륨 스냅샷을 만들고 보관 개수를 맞춰 오래된 결과를 정리한다. 실패 사유는 배치 로그에 있었지만 화면의 스케줄 상태만으로는 이번 실행이 성공했는지, 일부만 성공했는지, 왜 실패했는지 알 수 없었다.

처음 계획은 실행이 끝날 때 이력 테이블에 한 행을 넣고 화면에 탭을 추가하는 것이었다. 그러나 2천 줄이 넘는 배치 흐름의 모든 `return`, `continue`, `catch`를 따라가자 “실행했지만 이력이 없는” 경로와 성공으로 표시되지만 후처리가 실패한 경로가 나타났다. 실행 이력은 로그의 복사본이 아니라 배치 상태 머신의 외부 계약이어야 했다.

## 한 실행의 결과는 세 가지가 아니다

화면에는 성공, 일부 작업 실패, 실패의 세 결과를 보여 주기로 했다. 이 세 값만 저장하면 충분해 보이지만 한 번의 실행에는 여러 대상과 여러 단계가 있다.

인스턴스 유형에 따라 생성 대상은 달라진다.

- 이미지 기반 인스턴스: 인스턴스 이미지
- 이미지 기반 인스턴스와 데이터 볼륨: 이미지와 마운트 볼륨 스냅샷
- 볼륨 부팅 인스턴스: 루트 볼륨 스냅샷
- 볼륨 부팅 인스턴스와 데이터 볼륨: 루트와 마운트 볼륨 스냅샷
- 단일 볼륨 스케줄: 볼륨 스냅샷

생성 후에는 최대 보관 개수를 맞추는 정리와 선택적 로컬 저장도 수행한다. 따라서 “생성 2개 중 2개 성공, 오래된 백업 정리 실패”는 단순 성공이 아니다. 반대로 성공/전체 카운트의 분모에 정리와 저장을 섞으면 이 숫자가 매번 다른 종류의 작업을 세게 된다.

최종 의미는 이렇게 정했다.

- 성공/전체 카운트는 이번 실행의 스냅샷 생성 시도만 센다.
- 생성 하나라도 실패하면 실패 또는 일부 작업 실패가 된다.
- 생성이 전부 성공해도 정리나 로컬 저장이 실패하면 일부 작업 실패로 내린다.
- 원인에는 대표 실패를, 설명에는 모든 생성·정리·저장 결과를 남긴다.

이렇게 하면 결과 칩은 짧게 유지하면서 카운트의 의미도 안정적이다.

## 가장 위험한 구멍: 대상 없음과 조회 실패가 같았다

기존 대상 확인 함수는 인스턴스나 볼륨이 없으면 `false`를 반환했다. 외부 API 호출이 예외를 내도 catch에서 같은 `false`를 반환했다. 호출자는 둘 다 “대상 삭제”로 해석해 스케줄을 정지하고 일찍 반환했다. 이 경로는 실제 생성 함수를 실행하지 않았다는 이유로 이력도 남기지 않았다.

결과적으로 일시적인 OpenStack 장애 한 번이 다음 상태를 만들 수 있었다.

```text
외부 조회 실패
    → 대상이 없다고 오판
    → 스케줄 영구 정지
    → 실행 이력 없음
```

불리언을 세 상태로 바꿨다.

```text
EXISTS
    → 실행 계속

ABSENT
    → TARGET_NOT_FOUND 이력 기록
    → 실제 대상이 없으므로 스케줄 정지

CHECK_ERROR
    → 이번 실행 ERROR 이력 기록
    → 일시 오류일 수 있으므로 다음 주기 재시도
```

“없음”과 “확인하지 못함”을 구분한 것만으로 추적성과 복구 정책이 함께 좋아졌다. 분산 시스템에서 unknown을 false로 접어 버리면 fail-closed가 아니라 잘못된 확정이 된다.

## 준비 단계 실패에는 생성 카운트가 없어야 한다

전용 사용자 조회, 역할 확인, 프로젝트와 스케줄 설정 검증 중 실패하면 아직 스냅샷을 한 번도 시도하지 않았다. 이 예외들은 바깥 catch에서 일반 오류와 원시 메시지로만 기록됐고, 잘못하면 `0/1`처럼 실제로 존재하지 않은 시도를 표시할 수 있었다.

준비 실패를 별도 함수로 기록하고 성공/실패 카운트를 증가시키지 않았다. 설명도 내부 예외 문자열을 그대로 내보내지 않고 다음처럼 사용자가 조치할 수 있는 범주로 바꿨다.

- 스냅샷 스케줄러 설정 오류
- 실행 주체 생성 또는 조회 실패
- 필요한 역할 확인 실패
- 프로젝트 정보 부재
- 지원하지 않는 대상 유형

`total == 0`은 “모두 실패”가 아니라 “생성 단계 전에 중단”일 수 있다. 데이터 모델이 이를 구분해야 화면도 정직해진다.

## 성공은 외부 접수가 아니라 상태 확정 뒤에 기록한다

OpenStack의 생성 API는 비동기 작업을 접수한 뒤 식별자를 반환한다. 이 응답만으로 성공을 기록하면 나중에 `error`가 되거나 제한 시간 안에 `available` 또는 `active`가 되지 않은 결과도 성공으로 남는다.

생성 성공 카운트는 다음 조건 뒤에만 증가시켰다.

1. 외부 API가 유효한 식별자를 반환한다.
2. 스냅샷이 완료 상태에 도달한다.
3. 내부 생성 기록이 저장된다.

대기 결과는 시간 초과, 오류 상태, 잘못된 API 응답과 일반 오류로 나눴다. 쿼터도 개수 부족과 용량 부족을 구분했다. 화면의 원인 칼럼은 “할당량 부족”처럼 짧게 유지하고, 설명에는 `필요 1개 / 남은 여유 0개`처럼 실제 판단 수치를 넣었다.

## 설명은 시스템이 수행한 순서대로 쓴다

처음 설명 문구는 실패 사유를 이어 붙이는 형태였다. 사용자 피드백을 거쳐 실제 동작 순서로 재구성했다.

```text
생성 결과
    → 인스턴스/루트 볼륨/마운트 볼륨/단일 볼륨의 종류와 이름

보관 정리 결과
    → 어떤 이전 스냅샷을 지웠고 무엇이 실패했는가

로컬 저장 결과
    → 어떤 종류와 이름의 결과를 저장하지 못했는가
```

예를 들어 루트 볼륨은 성공하고 마운트 볼륨 하나가 시간 초과됐으며 이전 백업 하나는 정상 정리된 상황을 한 줄의 일반 오류로 접지 않는다. 각 작업의 종류와 결과를 순서대로 남긴다.

로컬 저장 실패는 원래 내부에서 예외를 삼켜 잡 전체를 계속 진행했다. 이 동작 자체는 핵심 스냅샷 생성을 보존한다는 점에서 합리적일 수 있지만, 이력까지 성공으로 남아서는 안 된다. 성공과 실패 이름 목록을 독립적으로 모으고, 후처리 실패가 하나라도 있으면 최종 결과를 “일부 작업 실패”로 내렸다.

대표 원인은 생성 실패, 로컬 저장 실패, 보관 정리 실패 순서로 선택했다. 대표 하나를 고르는 것은 나머지를 버린다는 뜻이 아니다. 그리드의 좁은 원인 칼럼과 상세 설명의 책임을 나눈 것이다.

## 부팅 형태 판별에서 조회가 오히려 정확도를 낮췄다

인스턴스가 이미지 부팅인지 볼륨 부팅인지에 따라 스냅샷 대상이 달라진다. 기존 판별은 원본 이미지 객체를 조회했다. 원본 이미지가 삭제됐거나 이미지 서비스가 일시적으로 실패하면 SDK가 예외를 삼키고 `null`을 반환해 이미지 기반 인스턴스를 볼륨 부팅으로 오판할 수 있었다.

판별에 필요한 것은 이미지 객체 전체가 아니라 인스턴스 응답에 이미 있는 이미지 식별자의 존재 여부였다. 외부 조회 없는 식별자를 우선 사용하고 볼륨의 bootable 속성을 보조 근거로 남겼다. 삭제된 원본 이미지도 인스턴스 메타데이터에는 식별자가 남기 때문에 오히려 더 안정적이었다.

이 변경은 “더 많은 데이터를 조회하면 더 정확하다”는 직관이 항상 맞지 않음을 보여 준다. 판정에 필요한 최소 사실이 현재 응답에 있다면, 실패 가능한 원격 조회는 정확도를 높이는 것이 아니라 새로운 unknown을 만든다.

## 저장과 조회의 경계

이력에는 실행 식별자, 스케줄 식별자, 결과, 사유 코드, 상세 설명, 성공·전체 개수, 시작·종료 시각을 저장했다. 스케줄이 삭제될 때 이력도 함께 정리되게 소유권을 명확히 했다.

조회 API는 페이지네이션을 사용하고 프로젝트 사용자가 다른 프로젝트의 이력을 볼 수 없도록 스케줄 소유권을 먼저 검사했다. 관리자와 프로젝트 화면은 같은 그리드 컴포넌트를 재사용하되 진입 경로의 권한 계약은 유지했다.

UI는 다음 원칙으로 정리했다.

- 결과는 색상 칩으로 빠르게 구분한다.
- 성공/전체 배지에는 “이번 실행의 스냅샷 생성 개수”라는 뜻을 툴팁으로 밝힌다.
- 원인은 짧은 번역 문구, 설명은 실제 대상과 수치를 담는다.
- 시작·종료 시각을 함께 보여 실행 시간도 추적한다.
- 서버 페이지네이션으로 이력이 늘어도 전체를 브라우저에 올리지 않는다.

## 검증은 행 하나 삽입에서 끝나지 않았다

배치 단위 테스트는 성공, 일부 실패, 완전 실패, 각 대기 결과, 동적 제한 시간, 보관 삭제 순서를 검증했다. 조회 테스트는 페이지 구조와 다른 프로젝트 접근 거부를 확인했다. 부팅 형태와 후처리 결과까지 포함해 관련 배치 테스트는 최종적으로 30개 이상을 통과했다.

브라우저 검증에는 성공, 일부 작업 실패, 개수 할당량 부족, 용량 할당량 부족, 시간 초과를 포함한 합성 이력을 사용했다. 데이터베이스, 백엔드, 프론트엔드를 연결해 결과 칩, 카운트, 번역, 설명과 페이지네이션을 확인했다. 합성 데이터라는 사실과 실제 발화 검증이 별도라는 것도 기록했다.

배포에는 새 이력 테이블 패치가 필요하다. 패치는 재실행 가능하게 만들고, 구 버전으로 롤백해도 사용하지 않는 테이블이 남는 것은 무해하도록 설계했다. 애플리케이션 코드와 DB 패치의 적용 순서, 배치 프로세스 재기동도 런북에 포함했다.

## 실행 이력의 완료 조건

믿을 수 있는 이력은 “잡이 끝났다”는 한 줄이 아니다. 다음 질문에 답할 수 있어야 한다.

- 무엇을 시도했는가?
- 어느 단계까지 성공이 확정됐는가?
- 무엇이 실패했고 다음 주기에 재시도하는가?
- 대상이 없어 스케줄이 멈춘 것인가, 일시적으로 확인하지 못한 것인가?
- 새 백업이 완성되기 전에 이전 백업을 지우지 않았는가?
- 생성은 성공했지만 정리나 로컬 저장이 실패하지 않았는가?

이력 탭을 추가하면서 실제로 만든 것은 화면이 아니라 이 질문에 답하는 상태 모델이었다. 로그는 개발자가 사건을 재구성하는 재료다. 제품의 실행 이력은 사용자가 별도의 로그 접근 없이 현재 상태와 다음 행동을 판단할 수 있게 해야 한다.
