# 가속기 서비스를 붙이기 전에 조사 기준부터 만든 이유

> 상태: 초안 · 제품/사이트 식별정보 제거 · 공개 미등록

새로운 OpenStack 가속기 서비스를 관리 포털에 연결하는 조사를 시작하면 API 목록부터 정리하기 쉽다. 하지만 “조회된다”와 “제품 기능으로 제공할 수 있다”는 전혀 다른 판정이다. 그래서 구현보다 먼저 공통 조사 기준을 만들었다.

첫째는 배포 현실성이다. 컨트롤 플레인 서비스가 설치돼 있는지, 대상 릴리스와 드라이버 조합이 맞는지, 하드웨어 탐색 에이전트가 실제 자원을 보고하는지 확인한다. API 문서가 존재해도 현재 클라우드에 서비스 카탈로그와 엔드포인트가 없으면 기능은 시작조차 못 한다.

둘째는 권한과 스코프다. 관리자 조회와 프로젝트 사용자 조회가 같은 결과를 내는지, 정책 파일에서 어떤 역할이 create/bind/unbind/delete를 수행할 수 있는지, 포털의 내부 RBAC와 OpenStack 정책이 충돌하지 않는지 본다. 관리용 공용 계정으로 모든 요청을 보내는 제품이라면 사용자 권한을 애플리케이션 계층에서 다시 집행해야 할 수도 있다.

셋째는 생명주기다. 가속기 자원은 단순 CRUD가 아니다. 프로파일 생성, 장치 발견, 인스턴스 바인딩, 해제, 장애 복구가 서로 다른 서비스와 상태 머신을 거친다. Nova 스케줄링과 Placement trait, 이미지 속성, flavor extra spec까지 이어지는 실제 호출 경로를 그려야 한다.

넷째는 실패 의미다. “지원 장치 없음”, “요청과 일치하는 프로파일 없음”, “바인딩 실패”, “드라이버 응답 지연”을 하나의 500으로 합치면 운영할 수 없다. 재시도 가능한 실패와 사용자 입력 오류, 운영자 조치가 필요한 상태를 구분해야 한다.

각 하위 조사에는 같은 판정표를 적용했다.

- 확인한 사실과 아직 가정인 항목
- 코드와 API에서 확인한 근거
- 최소 구현 범위와 제외 범위
- 선행 인프라 조건
- 보안·운영 리스크
- 검증 가능한 완료 조건

이 형식을 쓰자 “SDK에 메서드가 있으니 가능하다” 같은 낙관을 빠르게 걸러낼 수 있었다. 반대로 당장 구현할 수 없는 항목도 막연한 보류가 아니라, 어떤 인프라 조건이 충족되면 재개할 수 있는지 남길 수 있었다.

조사 문서의 목적은 많이 아는 모습을 보여 주는 것이 아니다. 구현자가 같은 전제를 반복해서 확인하지 않게 하고, 의사결정자가 무엇이 코드 문제이고 무엇이 클라우드 구성 문제인지 구분하게 하는 것이다. 불확실성이 큰 통합일수록 먼저 “어떻게 판정할 것인가”를 합의해야 조사 결과가 설계 입력으로 바뀐다.
