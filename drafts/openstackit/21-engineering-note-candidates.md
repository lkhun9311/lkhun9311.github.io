# 운영 기록에서 재사용 가능한 여섯 가지 기술 노트

> 상태: 초안 인덱스 · 기존 후보 메모를 하나의 글감 지도으로 정리 · 공개 미등록

긴 장애 보고서에는 한 문단으로 지나가지만 독립된 기술 글이 될 만한 패턴이 있다. 후보 메모 여섯 개를 다시 읽어 보니 모두 “겉으로 보이는 성공과 실제 계약의 차이”라는 공통점을 가졌다.

## 1. Fail-closed 검증자의 역설

상류 인증 검증이 실패했을 때 무조건 로그아웃하면 보안적으로 엄격해 보인다. 그러나 네트워크 오류와 명시적 무효를 구분하지 않으면 가용성 장애가 대규모 세션 종료가 된다. 마지막 성공 시각, 제한된 그레이스, 명시적 deny와 unknown의 구분으로 fail-closed의 적용 경계를 설명할 수 있다.

## 2. Squash된 장수 브랜치의 동기화 함정

장수 브랜치를 squash merge한 뒤 원본 커밋 계보는 대상 브랜치에 남지 않는다. 이후 merge-base만 믿고 동기화하면 이미 반영된 변경이 다시 충돌하거나 사라진 것처럼 보일 수 있다. 패치 내용과 파일 상태로 포함 여부를 검증하고, 재베이스 전에 백업과 비교 기준선을 만드는 방법이 주제다.

## 3. 코드에서 지운 enum이 DB에 남아 기동을 막을 때

애플리케이션 enum 값을 삭제해도 데이터베이스의 기존 행은 자동으로 사라지지 않는다. ORM은 시작하면서 그 값을 역직렬화하다 실패할 수 있다. 코드 검색, 데이터 검색, 변환 패치, 롤백 가능한 값 매핑을 하나의 변경으로 다뤄야 한다.

## 4. 느린 것은 쿼리가 아니었다

JMeter가 빠른 REST API만 재고도 화면은 느릴 수 있다. 브라우저가 실제로 기다리는 것이 SSE 첫 이벤트, 후속 fan-out, 렌더 조건일 수 있기 때문이다. 성능 측정은 엔드포인트 목록이 아니라 사용자 완료 조건에서 시작해야 한다.

## 5. CSP `form-action`과 교차 오리진 로그아웃

서버의 302가 정상이어도 폼 제출의 최종 목적지는 CSP에 막힐 수 있다. 허용 목록을 넓히는 대신 세션 종료와 외부 이동을 200 JSON 및 최상위 내비게이션으로 분리하는 설계가 핵심이다.

## 6. 루프 안의 서비스 클라이언트

SDK의 `serviceClient()`가 가벼운 getter처럼 보여도 내부에서 매번 인증한다면 반복문은 Keystone N+1이 된다. 클라이언트의 생성 비용과 스레드 안전성, 토큰 만료, 스코프를 확인한 뒤 작업 단위 재사용 또는 안전한 토큰 캐시를 선택해야 한다.

## 묶어서 볼 때의 편집 원칙

각 노트는 “증상 → 잘못된 첫 가설 → 실제 경계 → 최소 재현 → 일반화된 원칙”의 다섯 절로 쓰는 것이 적합하다. 사내 로그와 코드는 증거 확인에만 쓰고, 공개 가능한 글에는 합성 로그와 의사코드를 사용한다. 이미 별도 초안으로 확장된 네 번째와 다섯 번째 주제는 이 파일을 새 글로 게시하기보다 해당 글의 편집 체크리스트로 활용한다.

짧은 기술 노트의 가치는 사건의 크기가 아니라 다른 시스템에서도 다시 만날 수 있는 모양을 추출하는 데 있다. 운영 일지를 그대로 공개하는 대신, 실패한 가정과 경계 조건을 남겨야 재사용 가능한 지식이 된다.
