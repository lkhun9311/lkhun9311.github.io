# 성능 개선 연재를 만드는 측정 자료 구성법

> 상태: 초안 · 이 글은 공개 글이 아니라 집필 기록 자체를 다룸 · 공개 미등록

통합 모니터링 성능 개선은 한 편으로 쓰기에는 문제, 설계, 회귀, 측정 방법이 너무 컸다. 그래서 원본 작업 폴더는 다섯 부분과 재현 자료로 나뉘었다. 이 분리는 단순히 글을 짧게 만들기 위한 것이 아니라 주장과 증거를 연결하기 위한 구조였다.

첫 부분은 Before만 다뤘다. 화면 세 개의 SSE 첫 데이터 중앙값과 p99, Apdex, 분포 형태를 기록하고 “느리다”를 측정 가능한 문제로 바꿨다. REST가 아니라 첫 업무 이벤트를 측정해야 한다는 정정도 여기에 포함했다.

두 번째는 설계다. 페이지마다 중복 수집하던 구조를 단일 producer, 불변 스냅샷, serve-stale 캐시, 세션 전송기로 나눈 이유를 설명했다. 각 컴포넌트의 책임과 신선도·메모리·장애 격리의 trade-off를 적었다.

세 번째는 성공담이 아니라 회귀를 모았다. 부분 수집 실패가 0으로 덮이는 문제, 느린 SSE 소비자가 전송 워커를 막는 문제, 다른 화면을 본 뒤 재진입하면 경로별 캐시가 사라지는 문제를 재현 조건과 함께 기록했다. 최종 설계만 보여 주는 것보다 어떤 불변식을 놓쳤는지 드러내는 편이 재사용 가치가 높았다.

네 번째는 측정 방법론이다. SSE를 일반 HTTP 샘플러로 재기 어려운 이유, 첫 `data`까지의 실측을 JTL로 변환하고 JMeter 리포트를 생성한 과정, Apdex 기준, Before 30회와 After 50회를 비교할 수 있는 이유와 한계를 적었다. 순차 단일 사용자 측정의 throughput은 의미 있는 부하 지표가 아니라는 점도 명시했다.

다섯 번째는 코드 설명이다. 실제 사내 소스를 복제하지 않고 문제가 된 제어 흐름을 최소 의사코드로 재작성했다. 클래스명과 경로 대신 “producer”, “snapshot cache”, “session transmitter” 같은 책임 이름을 사용했다.

자료 폴더에는 원시 측정, 요약 통계, 생성된 HTML 리포트, 그래프와 다이어그램 소스를 함께 보존했다. 다만 생성형 리포트의 라이브러리 파일은 글의 근거가 아니라 뷰어 자산이다. 읽어야 할 핵심은 `statistics.json`, JTL, 측정 조건과 요약표다.

좋은 성능 글의 최소 증거 묶음은 다음과 같다.

- 사용자가 기다리는 정확한 경계
- Before/After의 동일한 측정 정의
- 중앙값과 꼬리 지연, 오류율, 표본 수
- 캐시의 콜드/웜 조건과 데이터 유무
- 결과를 설명하는 아키텍처 변화
- 개선 중 생긴 회귀와 남은 한계
- 다시 생성할 수 있는 원시 자료와 절차

성능 수치만 있으면 벤치마크이고, 설계만 있으면 주장이다. 측정 경계, 원시 자료, 실패했던 가설과 회귀까지 연결해야 기술 기록이 된다.
