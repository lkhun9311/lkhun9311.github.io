# 버전 업그레이드는 바이너리 교체가 아니라 데이터 보존 문제다

> 상태: 초안 · 고객/환경 정보 제거 · 공개 미등록

오래 운영한 IaaS 관리 시스템을 여러 마이너 버전 건너 업그레이드해야 했다. 처음 질문은 “새 버전을 설치하면 되는가”였지만, 실제 질문은 “기존 데이터를 잃지 않고 새 코드가 기대하는 스키마와 기준 데이터를 어떻게 만들 것인가”였다.

신규 설치 SQL을 기존 데이터베이스에 적용하는 것은 업그레이드가 아니다. 초기화 스크립트는 테이블을 만들고 기준 데이터를 넣는 데 최적화돼 있으며, 운영 데이터와 현장별 설정을 보존한다는 계약이 없다. 반대로 애플리케이션 파일만 바꾸면 새 엔티티가 요구하는 컬럼과 새 기능의 기준 행이 없어 기동 또는 실행 중 실패한다.

먼저 세 가지 기준선을 분리했다.

1. 소스 태그와 실제 배포 아티팩트의 버전
2. 데이터베이스에 기록된 제품 버전
3. 현장에 추가된 설정·사용자·권한·업무 데이터

그다음 구 버전과 신 버전 스키마를 빈 데이터베이스에 각각 재현하고 차이를 비교했다. 단순 DDL diff만으로는 부족했다. 열 추가 순서, enum 값, 인덱스, 기준 메뉴와 설정 행, 패치의 멱등성까지 확인해야 했다. 삭제된 enum이 테이블에 남아 애플리케이션 기동을 막는 것처럼 “코드에는 없지만 DB에는 남은 상태”도 있기 때문이다.

실행 절차는 다음 원칙으로 만들었다.

- 원본 데이터베이스를 직접 시험하지 않는다. 백업을 복제한 로컬 환경에서 먼저 재현한다.
- 전체 초기화 파일이 아니라 버전 사이의 패치만 순서대로 적용한다.
- 각 단계 전후로 스키마와 핵심 행 수를 기록한다.
- 패치가 중간에 실패해도 재실행 가능한지 확인한다.
- 애플리케이션 기동, 로그인, 권한, 주요 자원 조회를 데이터 검증과 함께 수행한다.
- 롤백은 “이전 바이너리 복원”이 아니라 “DB 백업 복구 + 이전 아티팩트 복원”으로 정의한다.

자동 재현 스크립트는 빈 구 버전 DB를 만들고, 표본 데이터를 심고, 패치 적용 후 신 버전 애플리케이션이 읽을 수 있는지 검사했다. 성공 로그만 남기지 않고 어떤 데이터가 반드시 보존돼야 하는지도 체크리스트로 고정했다. 사용자와 역할, 프로젝트 매핑, 환경별 설정, 스케줄 정의처럼 재생성하기 어려운 데이터가 핵심이었다.

업그레이드의 완료 조건은 새 버전 문자열이 보이는 것이 아니다. 기존 상태를 보존한 채 새 코드의 계약을 만족하고, 같은 절차를 다른 환경에서도 반복할 수 있어야 한다. 버전 업그레이드는 배포 작업처럼 보이지만 본질은 데이터 마이그레이션과 검증 가능한 런북의 문제다.
