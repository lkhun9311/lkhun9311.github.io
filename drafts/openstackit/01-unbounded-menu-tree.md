# SQL 버킷을 없애자 메뉴 트리의 깊이 제한도 사라졌다

> 상태: 초안 · 비식별화 완료 · 공개 미등록

4단계 메뉴를 추가했는데 API 응답에는 아무 오류 없이 사라졌다. 데이터베이스에는 행이 있었고 쓰기 API도 성공했다. 문제는 조회와 조립 사이에 숨어 있던 “메뉴는 최대 3단계”라는 가정이었다.

기존 구현은 메뉴를 1·2·3단계용 SQL로 따로 읽었다. 마지막 쿼리는 부모가 루트가 아닌 모든 행을 가져왔다. 이름은 3단계 쿼리였지만 실제 의미는 “3단계 이상”이었다. 따라서 3단계 부모와 4단계 자식이 같은 목록에 들어갔다. 서비스는 각 자식의 부모를 바로 앞 단계 목록에서만 찾았다. 4단계 자식의 부모는 같은 목록에 있었으므로 찾지 못했고, 예외도 없이 버려졌다.

이 버그의 중요한 특징은 두 계층의 가정이 결합해야만 나타난다는 점이다.

- SQL은 깊이를 정확히 계산하지 않은 채 세 버킷으로 나눴다.
- 조립기는 각 버킷이 정확한 깊이라고 믿었다.
- 부모를 못 찾는 경우를 오류로 취급하지 않았다.

4단계 쿼리를 하나 더 추가하는 방법은 가장 빠르지만 같은 문제를 다음 단계로 미룬다. 재귀 CTE는 깊이를 정확히 계산할 수 있지만, 권한과 차단 목록을 함께 처리하는 기존 SQL을 더 복잡하게 만들었다. 선택한 방법은 전체 메뉴를 한 번에 평탄하게 읽고 서비스에서 부모 체인을 따라 깊이를 계산하는 것이었다.

```text
byId = 모든 메뉴를 id로 색인
for menu in menus:
    depth = 부모가 없을 때까지 따라간 횟수
    buckets[depth].append(menu)
깊은 버킷부터 부모의 children에 연결
```

방문 집합으로 순환을 막고, 부모가 없는 고아 데이터는 도달 가능한 깊이까지만 계산했다. 입력이 이미 표시 순서로 정렬돼 있으므로 같은 깊이의 형제 순서는 유지했다. 결과적으로 흐름마다 세 벌이던 조회를 한 벌로 줄였고, 조립기는 원래 갖고 있던 임의 깊이 처리 능력을 그대로 재사용했다.

테스트도 “4단계가 보인다” 한 건으로 끝내지 않았다. 한 단계, 두 단계, 다섯 단계, 형제 순서, 고아 부모, 순환 가능성을 각각 고정했다. 특정 메뉴를 위한 패치가 아니라 트리 자료구조의 불변식을 테스트한 것이다.

여기서 얻은 교훈은 단순하다. 단계 수가 SQL 메서드 수나 함수 인자 수로 표현된다면 그 제한은 도메인 규칙이 아니라 구현의 우연일 가능성이 높다. 새 단계를 한 칸 더 만드는 대신, 데이터가 이미 가진 부모 관계에서 구조를 계산하는 편이 더 작고 오래가는 변경이 된다.
