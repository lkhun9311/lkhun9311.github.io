社内クラウド管理コンソールの Backend を作っています。ボリューム一覧の画面が 10 分を超えて Timeout していました。6 回開けば 5 回はそう終わる画面でした。

原因はボリューム 1 つごとに外部 API を順に呼ぶループで、処方は明らかに見えました。 並列で回して Cache を付ければよい。実際に両方入れると p99 が 10 分から 23ms になりました。

ところがその一文では、次の画面に持っていけるものがありません。何がどれだけ減らしたのか、 入れたもののうち逆に増やしたものがあったのかが残らないからです。そこで直したあと、構成を 6 通りに分けて同じ負荷条件で別々に測りました。その表で 1 マスが逆に出ました。 Cache を固定したまま逐次を並列にだけ変えると、中央値は 21 倍速くなり p99 は 1.9 倍遅く なりました。この記事はその 6 行と、逆に出た 1 マスの話です。

想定読者#

  • 一覧の取得が遅くて CompletableFuture で並列化してみたことがある方
  • Cache を自作しながら ConcurrentHashMap.computeIfAbsent を使ったことがある方
  • 「Thread Pool を大きくすればいいのでは」と考えたことがある方

どんな画面#

管理者が 全ボリュームの一覧を見る画面です。ボリューム 1 件ごとに名前・サイズのほか、 どのプロジェクトのものか、どのボリュームグループに属するか、 最近のエラーメッセージがあるかも一緒に表示します。この 3 つはすべて別の API から来ます。

つまり一覧を 1 回描くのに、これだけの呼び出しが出ます。

ボリューム N 個を描くには
  プロジェクト取得       N 回
  ボリュームグループ取得  N 回
  エラーメッセージ取得    N 回
= 外部 API 呼び出し 3N 回

ボリュームが増えるほど線形に遅くなります。試験環境でこの画面は 10 分を超えて Timeout し、エラー率は 83.3% でした。

仮説: 逐次呼び出しが問題だと思っていました#

3N 回を順番に呼んでいたので、診断は簡単に見えました。

呼び出しが逐次だから遅いのだ。並列にすれば N 倍とはいかなくても大きく減る。

CompletableFuture.supplyAsync でボリュームごとに task を作り Executor に投げました。 そして繰り返しの呼び出しを減らすため、ConcurrentHashMap で Cache を 1 つ置きました。 同じグループ id は 1 回呼べば足りるからです。

結論: 6 通りの構成を別々に測りました#

1 行にまとめるとこうです。

「直す前と後」だけを測ると、何が効いたのか分かりません。 6 通りの構成を順に測って、並列化が中央値と裾を逆方向に動かすことが見えました。

まず表を見ます。負荷条件は 6 回とも同じです。 中央値はリクエストを速い順に並べたときの真ん中の値、 P99 は遅い側から 1% が掛かる線です。TPS は 1 秒あたりに終わったリクエスト数。 あとで出てくる Apdex は、0.5 秒以内に終わったリクエストと 1.5 秒以内に終わった リクエストの割合で、1 に近いほど良い値です。

真ん中にいるリクエストは速くなりました。代わりに 遅い側の 1% が 79 秒の向こうへ押し出されました。 P99 は「100 人に 1 人が 79 秒待った」ではなく、リクエストを遅い順に並べたとき 上から 1% が掛かる線です。ユーザー 1 人が何度も呼ぶので、人数とそのまま置き換えられません。

Apdex も 0.014 から 0.526 に上がりました。Apdex は 0.5 秒以内に終わったリクエストと 1.5 秒以内に終わったリクエストの割合で、中央値から出る値ではありません。 この区間に入ったリクエストが増えたから上がったのです。 平均だけを見ると「1.13 倍遅くなった」で、その一行が両方向を消します。

どの構成がどれだけ稼いだかは、どの指標で見るかによって答えが変わります。 平均で測ると秒を最も減らしたのは ①→②です。579.0 秒が 13.1 秒になり、565.9 秒を減らしました。 Cache を 1 つ入れただけです。倍率で最も減らしたのは ⑤→⑥で、1.0 秒を 5.3ms にしました。 どちらの文も平均基準です。中央値で測ると順位が変わります。

⑤ の中で何がどれだけ稼いだかは、この記録では切り分けられません。 原本には addMoreInfo() optimized としか書かれておらず、ボリューム 1 件を作る関数の中を まとめて直したもの、というところまでが確認できた範囲です。

原因 ①: Lock の中でネットワークを待っていました#

問題の形はこうです。

final Map<String, VolumeGroup> groupCache = new ConcurrentHashMap<>();

final List<VolumeDto> dtos = volumes.stream()
    .map(v -> CompletableFuture.supplyAsync(() -> {

        // ← 複数の thread が同時にこのブロックに入る
        final VolumeGroup group = groupCache.computeIfAbsent(
            v.getGroupId(),
            gid -> client.groups().get(gid)   // 外部 I/O を lock の中で呼ぶ
        );
        ...
    }, executor))
    .map(CompletableFuture::join)
    .collect(Collectors.toList());

ボリュームが N 個なら Executor に task が N 個入ります。そのうち 同じグループ id を持つものが M 個あれば、M 個の Thread が同時に同じキーで computeIfAbsent に入ります。 1 つが外部 API を往復するあいだ、残りの M−1 個はその場で待ちます。

待っているあいだも、その Thread たちは Executor の席を握っています。 そのため別のボリュームの task が後ろに詰まります。

この因果はコードを読んで立てたもので、試験が証明したものではありません。 6 通りの試験が示すのは「Cache を固定したまま並列にすると悪化した」までです。 その悪化が Lock 競合によるものか、Thread 切り替えのコストか、外部 API 側の制限かは この試験では切り分けられません。切り分けるには Lock を外した並列 Arm を別に回す 必要がありますが、それはしていません。

原因 ②: 0 件の答えを Cache に入れていませんでした#

自作の Cache には欠陥がもう 1 つありました。エラーメッセージを読む側です。 この欠陥は同じ製品の別画面(プロジェクトのボリューム)でまとめたもので、 構造が同じなのでここに併せて書きます。上の 6 通りの表は管理ボリューム画面の数値です。

List<Message> messages = manager.list(Message.class);

// 空なら毎回また外部 API を呼ぶ
if (messages == null || messages.isEmpty()) {
    client.messages().list(...)
          .forEach(r -> manager.set(Message.class, r.getResourceUuid(), r));
}

2 つが重なっています。

  • 0 件なら何も保存されません。forEach が一度も回らないからです。 取得結果が 0 件だとその答えが Cache に残らないので、次のリクエストがまた外部 API を呼びます。 原本には「0 件がどれくらい頻繁だったか」が残っていません。構造がそうだ、というところまでが 確認できた範囲です。
  • 検査と保存のあいだが開いています。複数の Thread が同時に isEmpty() を通過すると、全部が外部 API を呼びます。

「無い」を入れない Cache は、その答えについては Cache ではありません。

理由: ConcurrentHashMap でも列はできます#

ConcurrentHashMap はマップ全体を Lock しません。だから「並行データ構造を使ったから 大丈夫」と読みやすいのです。ところが computeIfAbsent は そのキーが住む枠(bin)を Lock してマッピング関数を回します。

同じキーは完全に塞がります。そしてその時間は、マッピング関数がする仕事の 時間です。別のキーでも hash が同じ枠に落ちれば一緒に塞がります。

マッピング関数がメモリ上の計算なら、その時間はマイクロ秒です。ところがここでは ネットワークの往復でした。ミリ秒単位ではなく、数十・数百ミリ秒です。

社内文書ではこれを「セグメント Lock」と書いていましたが、正確ではありません。 セグメントは Java 7 の実装で、Java 8 から ConcurrentHashMap は bin 単位で Lock します。誤った名前を使うと、次の人が間違った場所を探しに行くことになります。

修正: Lock をうまく扱うのではなく、Lock に入る理由をなくしました#

先にはっきりさせておくことがあります。computeIfAbsent も同じキーの マッピング関数は 1 つだけ実行し、残りは待ちます。Caffeine の LoadingCache に 変えても列が消えるわけではありません。2 つの違いは「並ぶかどうか」ではなく マップの Lock を握ったまま待つかどうかで、その差だけで 10 分が 23ms になるわけでもありません。 (マッピング関数が null を返すと何も保存されず、次の呼び出しがまた計算します。 削除済みのグループを引く経路がそれです。)

ですからこの画面でやったことは、Lock をうまく扱う方ではなく Lock に入る理由をなくす方 でした。自作の Cache と synchronized ブロックを取り除いて Caffeine に替えました。 キーごとに Loader が 1 つと保証されるので、stampede を防ぐために別途 Lock を掛ける必要がなくなります。

⑥ で得たのは 更新の方式です。値が古くなったら消して次の人に埋めさせる代わりに、 古い値をそのまま返しながら裏で読み直します。 この性質は 値がすでにあるときにだけ現れます。そのキーを最初に引くリクエストは Loader が終わるまで待ちます。

この画面で実際に変えたのは 5 つです。

  • 自作の Cache を Caffeine に替えました。CacheManager と synchronized ブロックがしていた仕事を、ライブラリがします。
  • 更新を裏に回しました。refreshAfterWrite(5s) により、 一覧の取得は持っている値をすぐ返し、更新は裏で起きます。
  • サーバー起動時に先に埋めます。ApplicationReadyEvent を受けて CompletableFuture.runAsync で埋めます。起動を止めません。 ですからこれはコールドスタートを無くす仕掛けではなく、出くわす確率を下げる仕掛けです。 warming が終わる前に来た最初のリクエストは、やはり自分で読みます。warming が失敗したときも同じです。 設計文書ではこの段階を「同期 warming」と書いていましたが、コードは runAsync でした。 文書ではなくコードを書きました。
  • ボリュームを作成・削除したら Cache を無効化します。ただし消して空のままにはしません。 持っていた値を残したまま裏で読み直し、原子的に差し替えます。
  • volume group を修正する経路が、ボリュームの Cache を無効化していませんでした。 自分の Cache だけ消して、ボリュームの DTO Cache はそのままでした。修正の経路で両方を一緒に 無効化するよう直しました。

整合性: Cache を消すと、次の人が遅くなります#

Cache を入れると いつ消すのかが付いてきます。ボリュームを作成・削除すると一覧が 変わるので、無効化しなければなりません。ところが 無効化した直後の取得は外部 API を通ります。 消した本人ではなく、その次に入ってきた人がそのコストを払います。

そこで 既存の値を残したまま裏で埋め直す方式にしました。しばらく古い値を見せることと、 誰か 1 人が遅くなることのあいだの取引です。5 秒という数字には根拠があります。 画面が 5 秒ごとに一覧を取り直しているので、その周期のあいだだけ古ければよい、とチームで合意した値です。

ただし 「5 秒」は上限ではありません。ボリューム一覧に掛けてあるのは refreshAfterWrite(5s) だけで、期限切れはありません。読み直しは 5 秒が過ぎたあとに誰かがその値をまた引いたときに始まり、その人は古い値を受け取ります。 誰も引かなければ更新も起きません。読み直しに失敗すれば古い値がそのまま残ります。 つまり値がどれだけ古くなりうるかに 決まった天井がありません。 期限切れも一緒に掛ければ天井はできます。ところがその瞬間、この節の最初の段落に戻ります。 誰か 1 人がそのコストを払います。

反論: 「Thread を増やせばいいのでは?」#

まっさきに出てくる処方で、ここでは間違いです。

塞いでいるのが Thread の数ではなく キー 1 つだからです。Thread を増やしても、 同じキーの前に並ぶ人が増えるだけです。② と ④ がまさにそこで分かれます。 並列に変えると 中央値は 21 倍速くなり、P99 は 1.9 倍遅くなりました。 列が短くなったのではなく、分布が広がったのです。 リクエストがどの順で終わったかは測っていません。2 つのパーセンタイルが逆に動いた、 というところまでがこの試験の言えるすべてです。

同じ理由で Executor を大きくするのも答えではありません。列が短くなるのではなく、 並ぶ人が席をより多く占めるだけです。

限界: この記事が主張しないこと#

  • 運用の数値ではありません。隔離した試験環境で JMeter により測った値です。 「10 分」は負荷試験の Timeout 上限で、ユーザーが実際に待った時間ではありません。
  • 並列化が悪いという話ではありません。このコードで並列化が害になった理由として Lock の中のネットワークを疑い、その Lock を外したあとは並列化が効きます。 ただし疑いの根拠はコードであって、この試験ではありません。
  • Caffeine でなければならないわけでもありません。必要な性質は「キーごとに Loader 1 つ」 であって、特定のライブラリではありません。自作でもよいのですが、自作したことがこの記事の原因でした。
  • 4 画面の数値を 1 つの原因に帰しません。画面ごとに枝葉の原因が少しずつ違い、 この記事が詳しく書いたのは最初の画面だけです。
  • 23ms は 7,658 件全体の集計 P99 であって、Cache ヒットのサンプルだけを選んだ値では ありません。原本が Cache hit として説明しているのは中央値 4ms のほうです。
  • ⑤ と ⑥ の改善を 1 つずつ帰属できません。原本は ⑤ を addMoreInfo() optimized としか書いておらず、その中に複数の修正が一緒に入っています。
  • 並列が悪化した理由は、この試験では切り分けられません。Lock 競合という説明は コードを読んで立てたものです。

おわりに#

  • 並列化が遅くする側に回ることがあります。無かった競合を作ってしまえばそうなります。
  • computeIfAbsent のマッピング関数は 短く単純であるべきです。 Java の文書がそう書いています。その中に I/O があれば、そのキーは往復の時間だけ Lock されます。
  • 「無い」も値です。0 件を入れない Cache は、取得結果が 0 件のあいだ Cache ではありません。
  • 並行データ構造を使ったことと、競合が無いことは別の主張です。

最後に 1 行だけ残すなら、これです。 「直す前と後」だけを測ると、何が効いたのか分かりません。 6 通りの構成を分けて測って初めて、並列化がこのコードで害になる区間があると見えました。

次回は同じ製品の別の画面です。今度は コードに問題が無かったのに Instance 20 個の取得に 54 秒かかりました。
