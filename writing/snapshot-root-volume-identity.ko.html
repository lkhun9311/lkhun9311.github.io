둘 다 bootable인 Volume 중 실제 Root를 어떻게 찾았나
OpenStack4j에 root_device_name을 직접 확장하고 API session 경계까지 바로잡았습니다.

스냅샷 실행 이력 설계 연작의 한 편입니다. 여기서는 복구할 자원을 어떻게 정확히 짚어냈는지를 다룹니다. 전체 개요와 글 순서를 먼저 볼 수 있습니다.

Volume으로 부팅한 Instance에 데이터 Volume 하나를 더 붙였습니다. 둘 다 Cinder에서 bootable=true였습니다. 기존 Scheduler는 둘을 모두 Root Volume으로 판정했습니다.

분류 하나가 틀린 것으로 끝나지 않았습니다. Root Snapshot 이름에는 Mount Device가 없었습니다. 같은 분에 두 Volume을 처리하면 이름이 충돌할 수 있고 둘 다 Root 보관 묶음으로 들어가 서로의 오래된 Snapshot을 정리할 수 있었습니다. 잘못된 식별이 이름, 원장, retention 경계를 함께 오염시켰습니다.

이 글은 실행 결과 모델과 삭제 뒤에도 남는 이력에 이은 세 번째 글입니다. 이를 해결하기 위해 저는 Nova가 제공하는 권위 신호의 microversion과 권한을 확인하고 프로젝트에 포함된 OpenStack4j model을 직접 확장했습니다. Client 객체가 있어도 실제 호출 session은 ThreadLocal current를 따라간다는 점까지 추적해 API 호출 순서도 함께 고쳤습니다.

이 글의 예상 독자#

  • Cloud API의 여러 속성 가운데 자원 identity를 판별할 신호를 고르시는 분
  • SDK의 전역 또는 ThreadLocal context 때문에 Client가 예상과 다르게 동작한 경험이 있는 분
  • 호환성 폴백과 Fail-closed 사이의 설계 판단을 실제 사례로 보고 싶은 분

두 Volume을 모두 Root로 분류했습니다#

기존 판별은 Volume의 bootable을 먼저 봤습니다. 일반적으로 Root Volume은 bootable이므로 자연스러운 조건처럼 보입니다. 하지만 Image에서 만들어져 bootable 속성을 유지한 데이터 Volume을 Mount하면 Root가 아닌데도 true입니다.

오분류 뒤 두 자원의 이름은 같은 ROOT_VOLUME_<schedule>_snapshot_<minute> 형태가 됐습니다. Mount 경로라면 이름에 dev_vdb가 들어가야 합니다. 이름 충돌은 단순 표시 문제가 아니라 내부 원장 저장 실패와 관리 밖 Snapshot 누적으로 이어질 수 있습니다.

bootable은 Root의 식별자가 아닙니다#

bootable은 그 Volume으로 부팅할 수 있다는 속성입니다. 어느 Instance의 어느 Device로 연결돼 현재 Root 역할을 하는지는 말하지 않습니다. 판별 질문이 「부팅 가능한가」에서 「이 Instance의 Root인가」로 바뀌면 필요한 데이터의 소유자도 Cinder Volume에서 Nova Server attachment로 바뀝니다.

OpenStack4j에 root_device_name을 직접 확장했습니다#

Nova Server 응답의 OS-EXT-SRV-ATTR:root_device_name은 예를 들어 /dev/vda를 줍니다. Attachment의 Device와 같으면 Root, 다르면 Mount입니다. 다만 이 속성은 Nova API microversion 2.3 이상과 관리자 정책이 필요했습니다. Snapshot 전용 member 계정으로는 보이지 않을 수 있었습니다.

사용 중인 OpenStack4j의 Server model에는 이 필드가 없었습니다. 외부 라이브러리가 값을 버리면 Scheduler에서 아무리 판별 로직을 작성해도 사용할 수 없습니다. 저는 프로젝트에 포함된 server/openstack4j module의 인터페이스와 구현을 함께 수정했습니다.

// org.openstack4j.model.compute.Server
default String getRootDeviceName() {
    return null;
}

// org.openstack4j.openstack.compute.domain.NovaServer
@JsonProperty("OS-EXT-SRV-ATTR:root_device_name")
private String rootDeviceName;

@Override
public String getRootDeviceName() {
    return rootDeviceName;
}

인터페이스에는 default getter를 추가해 기존 구현과 테스트 목 객체가 한꺼번에 깨지지 않게 했고 NovaServer에는 실제 JSON field mapping을 추가했습니다. 그 다음 서비스 관리자 Client에 X-OpenStack-Nova-API-Version: 2.3 header를 붙여 Server를 조회했습니다. 지원하지 않는 환경이나 권한 부족에서는 null을 반환하고 기존 휴리스틱으로 내려가도록 호환성 경계도 남겼습니다.

OSClient.OSClientV3 admin = serviceClient()
    .headers(Map.of("X-OpenStack-Nova-API-Version", "2.3"));
Server server = admin.compute().servers().get(instanceId);
String rootDevice = server != null ? server.getRootDeviceName() : null;

Client 변수는 session을 격리하지 않았습니다#

여기서 예상 밖의 문제가 하나 더 있었습니다. 코드만 보면 admin 변수에 microversion 헤더를 붙였으니 그 객체의 Nova 요청에만 적용될 것 같습니다. 하지만 사용 중인 OpenStack4j 경로는 session을 ThreadLocal current에 둡니다. 새 Client를 만들 때 current가 교체되고 service proxy는 호출 시점의 current에서 token과 header를 가져옵니다.

관리자 조회 뒤 예전에 만들어 둔 member Client 변수로 Cinder를 호출해도 current가 관리자 session이면 요청은 관리자 token과 Nova header context를 물고 갈 수 있습니다. 변수의 타입과 실제 전송 context가 일치한다는 보장이 없었습니다.

수정은 Root Device 조회를 먼저 하고 그 다음 대상 프로젝트의 member Client를 새로 만드는 순서로 배치했습니다. 이미지 부팅이나 무 Volume 경로에서는 조회 결과를 쓰지 않지만 session 복원 순서를 단순하게 유지하려고 같은 순서를 택했습니다. 불필요한 Nova 한 번과 context 안전성 사이의 선택입니다.

권위 신호 우선, 휴리스틱 폴백으로 정리했습니다#

최종 판별은 root_device_name이 있으면 Device 일치만 봅니다. 이때 다른 Volume이 bootable이어도 Mount입니다. 권위 신호가 없을 때만 bootable, 마지막으로 알려진 Root Device 이름 목록을 봅니다.

boolean isRootVolume(String device, String rootDevice, Volume volume) {
    if (rootDevice != null && !rootDevice.isBlank() && device != null) {
        return device.equals(rootDevice);       // authoritative
    }
    if (volume != null) {
        try { return volume.bootable(); }       // compatibility fallback
        catch (Exception ignored) { }
    }
    return device != null && ROOT_DEVICE_LIST.contains(device);
}

단위 테스트와 실제 OpenStack 검증에는 Root와 Mount가 모두 bootable인 반례를 사용했습니다. 수정 뒤에는 /dev/vda만 Root, /dev/vdb는 Mount로 분류됐고 실행 이력도 SUCCESS 2/2로 두 종류를 구분해 남겼습니다.

트레이드오프와 남은 위험#

  • 정확성: 가능성을 뜻하는 bootable보다 실제 Attachment를 뜻하는 root_device_name을 우선했습니다.
  • 호환성: microversion을 지원하지 않는 환경을 위해 휴리스틱 폴백은 남겼습니다.
  • 호환성 구현: OpenStack4j interface에는 default getter를 추가해 기존 구현과 테스트의 파급을 줄였습니다.
  • 개선 과제: 호출 순서에 기대는 ThreadLocal Session 대신 Token과 Header가 Client에 귀속되는 경계가 필요합니다.

마치며#

속성 이름이 그럴듯하다고 identity 신호가 되는 것은 아닙니다. bootable은 가능성을, root_device_name은 이 Instance의 실제 attachment를 말했습니다.

그리고 정확한 필드를 찾은 뒤에도 끝이 아니었습니다. 그 값을 읽기 위해 바꾼 API microversion과 권한 context가 다음 호출에 어떻게 전파되는지까지 봐야 했습니다. 분산 시스템의 판별 오류는 종종 조건문보다 조건문에 데이터를 가져오는 경계에서 시작합니다.
