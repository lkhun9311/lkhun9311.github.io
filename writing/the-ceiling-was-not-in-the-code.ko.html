처리량 상한은 코드에 없었습니다
S3 때문에 들어온 라이브러리의 기본값 5 — 소셜 투표 플랫폼 콘텐츠 검열 경로

2026년 9월

안녕하세요. 소셜 투표 플랫폼을 만들고 있습니다. 지난 글에서 트랜잭션 경계를 고치고 하네스를 세워 수치를 만들었는데, 그 하네스가 곧바로 다음 질문을 던졌습니다 — “글 생성 처리량이 왜 6.27 req/s 에서 안 올라가지?”

쓰기 스레드를 4배로 올려도, DB 커넥션 풀을 3배로 키워도 그 숫자는 움직이지 않았습니다. 범인은 제가 쓴 적도, 고른 적도, 이름을 본 적도 없는 라이브러리의 기본값이었습니다.

이 글의 예상 독자#

  • Spring Boot 에서 RestClient 나 RestTemplate 으로 외부 API 를 부르고 있는 분
  • 처리량이 어떤 숫자에서 딱 멈춰 있는데, 스레드도 DB 풀도 늘려 봤지만 안 움직이는 분
  • “내가 안 넣은 라이브러리가 내 서비스 동작을 정하고 있나?”가 궁금하신 분

무슨 내용인가요?#

  • 콘텐츠 검열 경로의 처리량이 6.27 req/s 에서 멈춰 있었습니다. 쓰기 스레드를 4배로 올려도, DB 커넥션 풀을 3배로 키워도 그대로였습니다.
  • 원인은 S3 를 쓰려고 넣은 AWS SDK 가 끌고 들어온 HTTP 클라이언트의 기본값 “대상 호스트당 커넥션 5개”였습니다.
  • 이 라이브러리는 런타임 클래스패스에만 있습니다. 코드 어디에도 이름이 나오지 않아서 읽어서는 찾을 수 없고, 재야만 나옵니다.
  • 고친 방식은 상한을 없애는 것이 아니라 정하는 것이었습니다. 상한을 지우면 처리량은 똑같이 오르지만, 아무도 안 고른 5 가 아무도 안 고른 무한대로 바뀔 뿐입니다.
  • 결과는 외부 호출 동시 실행 10 → 32, 글 생성 p50 2,592 → 805ms, 처리량 6.27 → 19.89 req/s(3.17배), 오류율 0% 였습니다.

코드는 비공개 저장소에 있습니다. 아직 출시 전이라 저장소를 열어 두지 않았습니다. 그래서 절마다 GitHub 링크 대신 파일 경로와 심볼 이름을 적어 뒀습니다.

⚠️ 미리 말씀드릴 것이 있습니다. 이 글의 수치는 전부 로컬 하네스로 잰 것입니다. 부하기·애플리케이션·외부 API 스텁·PostgreSQL 이 전부 한 기계에서 CPU 를 나눠 씁니다. 그래서 절대 처리량에는 의미가 없고 비교에만 의미가 있습니다. 외부 호출 800ms 는 스텁에 설정한 값이지 실제 지연 분포가 아니고, 조건당 1회 실행입니다.

어떤 경로에서 생긴 일인가요?#

사업화를 목표로 만들고 있는 소셜 투표 플랫폼입니다. 사용자가 질문을 올리면 다른 사람들이 투표하고, 그 결과 차트를 앱 밖으로 공유합니다. Kotlin 과 Spring Boot 로 만든 단일 모놀리스이고, 데이터베이스는 관리형 PostgreSQL 하나를 씁니다.

사용자가 올린 글은 모더레이션 게이트를 통과해야 게시됩니다. 게이트는 네 겹이고, 그중 ③ 유해분류와 ④ 저격판정 두 겹이 외부 API 를 부릅니다. 게이트는 fail-closed 라서, 이 호출이 실패하면 글은 게시되지 않습니다.

그림이 말하지 않는 것을 하나 덧붙이면, ③과 ④는 같은 호스트로 나갑니다. 뒤에서 이 사실이 “대상 호스트당 5개”라는 기본값과 만나면서 문제가 됩니다.

처음엔 DB가 병목인 줄 알았습니다#

하네스가 처음 내놓은 수치는 이랬습니다. 쓰기 16 스레드, DB 커넥션 풀 10, 외부 스텁 지연 800ms.

지표값

글 생성 p502,592 ms
피드 조회 p504 ms
오류율0%

가장 먼저 떠오른 가설은 흔한 쪽이었습니다.

쓰기가 16개인데 DB 커넥션 풀이 10개니까, 커넥션을 기다리느라 느린 것 아닐까? 아니면 INSERT 자체가 무거운 것 아닐까? 그러면 쓰기를 큐로 빼거나 Redis 를 붙여야 하나?

세 가설 모두 틀렸습니다. 그리고 틀렸다는 것은 추론이 아니라 하네스가 알려 줬습니다.

결론부터 말씀드리자면#

병목은 DB 도, INSERT 도, 애플리케이션 스레드도 아니었습니다. 밖으로 나가는 HTTP 호출의 동시 실행이 10개로 묶여 있었습니다.

그리고 그 10 은 이렇게 만들어진 숫자였습니다.

S3 를 쓰려고 넣은 AWS SDK
  → software.amazon.awssdk:apache5-client
     → org.apache.httpcomponents.client5:httpclient5      ← 전이 의존성
        → Spring 의 RestClient 가 클래스패스에서 이걸 고른다
           → 커넥션 풀의 기본값: 대상 호스트당 5개
              → 같은 호스트를 보는 RestClient 2개 × 5 = 동시 10

이 사슬에서 제가 고른 것은 첫 줄뿐입니다. 파일 업로드를 하려고 S3 를 붙였을 뿐인데, 그것이 딸려 온 HTTP 클라이언트를 통해 콘텐츠 검열의 처리량 상한을 정하고 있었습니다.

쓰기는 무겁지 않았습니다#

“쓰기가 무거운가”는 하네스로 바로 대답할 수 있는 질문이었습니다. 외부 스텁의 지연을 0ms 로 두고 나머지 조건을 그대로 두면, 남는 것은 애플리케이션과 DB 의 순수한 쓰기 비용뿐입니다.

조건글 생성 p50글 생성 처리량
외부 지연 800ms2,592 ms6.27 req/s
외부 지연 0ms8 ms1,398 req/s

→ 표를 옆으로 넘길 수 있습니다

INSERT 경로 자체는 8밀리초입니다. 초당 1,398건을 받습니다. 쓰기는 이 시스템의 문제가 아니었고, 따라서 쓰기를 큐로 빼는 설계는 고칠 것이 없는 곳을 고치는 일이 됩니다.

⚠️ 이 측정은 처음에 틀렸습니다. 지연 0 을 요청했는데 이전 실행의 800ms 스텁이 포트에 그대로 살아 있었습니다. 하네스에는 “스텁이 정말 그 지연으로 응답하는가”를 보는 왕복 검사가 있었는데, 조건이 왕복시간 < 요청지연 × 0.8 이라서 요청지연이 0이면 항상 거짓이 됩니다. 검사가 공허하게 통과한 겁니다. 그래서 800ms 실행을 0ms 실행으로 기록해 놓고 결론을 냈습니다.

고친 방법은 시간이 아니라 신원을 보는 것이었습니다. 스텁이 자기 설정값을 보고하게 하고, 그것을 요청값과 대조합니다.

$ curl -s localhost:18080/__stub/health
{"ok": true, "delay_ms": 800, "jitter_ms": 0, "max_in_flight": 10}
#            ↑ 요청한 값과 다르면 실행을 중단한다

그리고 일부러 틀린 스텁을 띄워 두고 돌려서 실행이 실제로 멈추는지 확인한 뒤에 다시 쟀습니다. 이 리포에서 가장 자주 나온 결함이 “실패했는데 통과처럼 보이는 검사”라, 검사를 넣으면 일부러 실패시켜 보는 것을 규칙으로 두고 있습니다.

무엇을 바꿔도 10에서 안 움직였습니다#

다음으로 스텁에 계측을 넣었습니다. 요청이 들어올 때 세고 나갈 때 빼서, 동시에 처리 중인 외부 호출의 최고치를 기록하게 했습니다. 이 숫자 하나가 나머지를 전부 설명합니다.

쓰기 스레드DB 풀외부 호출 최고 동시 실행글 생성 처리량글 생성 p50
1610106.27 req/s2,592 ms
1630106.27 req/s2,595 ms
3230106.26 req/s5,119 ms

→ 표를 옆으로 넘길 수 있습니다

표를 읽는 법은 이렇습니다. 쓰기를 4배로 올려도, DB 풀을 3배로 키워도 동시 실행은 10에서 움직이지 않습니다. 늘어나는 것은 응답시간뿐입니다(2,592 → 5,119ms). 이건 전형적인 대기열 신호입니다 — 일이 더 되는 게 아니라 줄만 길어진 겁니다.

스텁이 범인일 가능성은 따로 지웠습니다. 같은 스텁을 앱 없이 32 워커로 20초 두드리면 동시 32 · 40 req/s 를 냅니다. 그러니 10은 스텁의 한계가 아니라 앱이 밖으로 나가는 길의 한계입니다.

여기서 산수가 맞아떨어집니다. 글 1건이 호출 2개를 내므로, 동시 10은 동시에 검열 중인 글 5건입니다. 호출 한 번이 800ms 니까 5 ÷ 0.8초 = 약 6.3 req/s. 관측된 6.27 과 같습니다.

스레드 덤프가 어디서 멈췄는지 알려 줬습니다#

“앱 어딘가에 10이 있다”까지는 왔는데, 그게 어디인지는 코드를 읽어서 찾지 못했습니다. 제 코드에는 10 도, 5 도 적혀 있지 않기 때문입니다.

그래서 부하가 걸린 상태에서 스레드 덤프를 떴습니다. 톰캣 워커 16개 중 5개는 소켓 입출력 중(RUNNABLE) 이었고, 11개는 park 상태였습니다. park 한 쪽의 스택이 답이었습니다.

at org.apache.hc.core5.pool.StrictConnPool$1.get(StrictConnPool.java:183)
at org.apache.hc.client5.http.impl.io.PoolingHttpClientConnectionManager$3.get(...)
at org.apache.hc.client5.http.impl.classic.InternalExecRuntime.acquireEndpoint(...)

Apache HttpClient 5 의 커넥션 풀에서 대기하고 있었습니다. 저는 이 라이브러리를 넣은 기억이 없었습니다.

사슬을 거슬러 올라가면 S3가 나옵니다#

의존성 트리를 뽑아 보니 사슬이 이랬습니다.

그림이 말하지 않는 것을 하나 짚겠습니다. httpclient5 는 런타임 클래스패스에만 있습니다. 컴파일 클래스패스에 없으니 제 코드에서는 이름조차 쓸 수 없습니다. 실제로 설정 코드를 먼저 써 보려다 Unresolved reference 'hc' 로 막혔습니다.

그래서 이 층은 읽어서는 찾을 수 없습니다. 코드 검색으로도, 리뷰로도 안 나옵니다. 재야만 나옵니다.

한 줄 설정으로 확인했습니다#

가설이 맞는지는 한 줄로 확인할 수 있었습니다. Spring 에게 Apache 말고 JDK 클라이언트를 쓰라고 지정하고, 다른 조건은 전부 그대로 뒀습니다.

# application.yml — 진단용 한 줄
spring:
  http:
    client:
      factory: jdk

그런데 이대로 두면 안 됩니다#

여기서 멈추고 싶은 유혹이 있었습니다. 한 줄로 3.17배가 나왔으니까요. 그런데 jdk 클라이언트에는 호스트당 상한이 없습니다.

즉 이 한 줄이 한 일은 아무도 안 고른 5 를 아무도 안 고른 무한대로 바꾼 것입니다. 이 글이 처음부터 하고 있는 이야기와 정확히 반대입니다.

상한이 없으면 부하가 몰릴 때 외부 API 로 무제한 동시 호출이 나갑니다. 그건 상대 서비스에 대한 부하이자 제 비용입니다. 유입 제어는 상한을 없애는 것이 아니라 의도적으로 정하는 것입니다.

덧붙이면, 이 저장소는 같은 형태의 결함을 이미 한 번 겪었습니다. 톰캣 스레드 200 과 커넥션 풀 기본값이 둘 다 프레임워크가 정한 값이었고, 그 둘이 만든 동시성 정책은 정책이 아니었습니다. 아웃바운드에도 같은 일이 있었고, 이번에는 아무도 그 층을 보고 있지 않았습니다.

그래서 상한을 정했습니다#

택한 방식은 두 가지였습니다.

  1. httpclient5 를 명시 의존성으로 올립니다. 이미 런타임에 쓰고 있던 라이브러리를 이름으로 적는 것이고, 그래야 설정 코드를 쓸 수 있습니다.
  2. 커넥션 풀을 하나만 만들어 모든 RestClient 가 공유하게 합니다. 클라이언트마다 자기 풀을 가지면 “호스트당 N”이 실제로는 “클라이언트 수 × N”이 됩니다. 그게 5가 10이 되어 있던 이유입니다.
@Configuration
class OutboundHttpConfig {
    @Bean
    fun outboundConnectionManager(
        @Value("\${oxy.http.outbound.max-per-route:50}") maxPerRoute: Int,
        @Value("\${oxy.http.outbound.max-total:100}") maxTotal: Int,
        // 스프링이 붙여 주던 타임아웃을 여기서 다시 붙인다 — 같은 속성 키를 읽는다.
        @Value("\${spring.http.client.connect-timeout:3s}") connectTimeout: Duration,
        @Value("\${spring.http.client.read-timeout:10s}") readTimeout: Duration,
    ): PoolingHttpClientConnectionManager = ...

    @Bean
    fun outboundHttpCustomizer(cm: PoolingHttpClientConnectionManager): RestClientCustomizer {
        // 팩토리도 하나만 만들어 모든 빌더가 같은 풀을 쓰게 한다.
        val factory = HttpComponentsClientHttpRequestFactory(
            HttpClients.custom().setConnectionManager(cm).build())
        return RestClientCustomizer { builder -> builder.requestFactory(factory) }
    }
}

50이라는 숫자의 근거도 주석에 적어 뒀습니다. 글 1건이 호출 2개를 내므로 50은 동시에 검열 중인 글 25건에 해당하고, 외부 호출이 800ms 라면 초당 약 31건까지 받습니다. 지금 세운 어떤 트래픽 가정보다도 크되 무한은 아닙니다.

다시 쟀습니다. 조건은 앞과 동일합니다.

⚠️ 32는 새 상한이 아닙니다. 적어 둔 상한은 50인데 관측된 최고 동시 실행은 32입니다. 32는 부하의 모양이지 상한이 아닙니다 — 쓰기 스레드 16개가 글 1건당 호출 2개를 내므로 16 × 2 = 32 입니다. 즉 이 실행에서 천장은 아웃바운드 풀에서 떠났고, 지금 처리량을 정하는 것은 유입 동시성입니다. 50이 실제로 걸리는지는 쓰기 스레드를 25 이상으로 올려야 보이는데, 재지 않았습니다.

그리고 factory=jdk(19.89 req/s)와 이 처방(19.89 req/s)은 처리량이 같습니다. 둘을 가르는 것은 성능이 아니라 상한이 적혀 있는가입니다.

첫 구현이 타임아웃을 날렸습니다#

첫 구현은 requestFactory 를 통째로 갈아치웠습니다. 그랬더니 스프링 자동설정이 붙여 주던 spring.http.client.* 타임아웃이 같이 사라졌습니다.

이건 조용히 지나갈 수도 있는 종류의 사고입니다. 타임아웃이 없어도 정상 응답은 정상적으로 돌아오니까요. 문제는 응답이 안 오는 서버를 만났을 때만 드러납니다.

다행히 이 저장소에는 그걸 겨누는 테스트가 이미 있었습니다. “응답 없는 서버에 매달리지 않는다”는 가드가 40초 만에 실패했습니다. 그 가드가 없었으면 무한 대기가 조용히 돌아왔을 겁니다.

고친 방법은 값을 복제하지 않는 것이었습니다. 같은 속성 키를 읽습니다. 복제하면 언젠가 한쪽만 바뀌는 날이 옵니다.

설정은 그 자체로 아무것도 실패시키지 않습니다#

이번 수정에는 다른 수정과 구별되는 성질이 하나 있었습니다. 결과물이 설정값이라는 겁니다. 로직을 고치면 그 로직을 겨누는 테스트가 빨간불이 나지만, 설정은 지워도 아무것도 실패하지 않습니다. 그냥 기본값으로 조용히 돌아갈 뿐입니다.

그리고 그 “조용히 돌아간 기본값”이 바로 이 글 전체의 원인이었습니다. 그래서 값이 실제로 붙었는지를 단언하는 테스트를 두 개 넣었습니다.

// ① 기본값(5)이 아니라 우리가 준 값이 붙어야 한다.
assertThat(manager.defaultMaxPerRoute).isEqualTo(37)
assertThat(manager.maxTotal).isEqualTo(91)
// route 별 조회도 같은 값이어야 한다 — 갈리면 실제 상한이 달라진다.
assertThat(manager.getMaxPerRoute(route)).isEqualTo(37)

// ② 클라이언트마다 풀을 따로 가지면 "호스트당 N" 이 "클라이언트 수 × N" 이 된다.
//    그게 5 가 10 이 되어 있던 이유이므로, 같은 팩토리를 공유하는지를 단언한다.
assertThat(factories[0]).isSameAs(factories[1])

그리고 이 단언들이 정말 겨누고 있는지는 뮤테이션으로 확인했습니다. setMaxConnPerRoute 를 지우면 첫 번째가 5를 보고 빨간불이 나고, 팩토리를 빌더마다 새로 만들면 두 번째가 빨간불이 납니다. 둘 다 실제로 확인했습니다.

“Redis나 큐를 쓰면 되지 않나요?”#

이 작업을 하면서 실제로 받은 질문입니다. 아키텍처를 바꿔서 푸는 것이 맞지 않냐는 이야기였습니다. 하네스가 있으니 답을 고르기 전에 재는 순서로 갈 수 있었습니다.

큐잉에 대해서만 한 가지 더 적겠습니다. 검열을 큐로 빼는 것은 실제로 무언가를 바꿉니다. 다만 바뀌는 것은 성능이 아니라 제품의 약속입니다.

게이트는 fail-closed 라서 검열 전에 글이 보이면 안 됩니다. 그러니 가능한 형태는 “먼저 게시하고 나중에 검열” 이 아니라 “검열이 끝날 때까지 게시되지 않는 비동기 작업” 입니다. 지연을 없애는 게 아니라 요청 스레드에서 떼어내는 것이고, 아웃바운드 상한은 그대로입니다. 대신 상태 표시·재시도·중복 방지·실패 통지가 전부 새로 생깁니다.

그래서 언제 그 설계가 정당해지는지를 미리 적어 뒀습니다. 나중에 “느낌”으로 도입하지 않기 위해서입니다 — 상한을 의도적으로 올린 뒤에도 글 생성 p95 가 목표를 넘거나, 외부 API 의 p99 가 자체 타임아웃에 근접하면 그때 비동기로 갑니다.

이 글이 주장하지 않는 것#

  • 운영 수치가 아닙니다. 부하기·앱·스텁·DB 가 한 기계에서 CPU 를 나눠 씁니다. 절대 처리량은 의미가 없고 비교만 의미가 있습니다.
  • 800ms 는 스텁에 설정한 값입니다. 실제 외부 API 의 지연 분포가 아닙니다. 실제 이득은 그 분포에 달려 있습니다.
  • 조건당 1회 실행입니다. 반복 실행으로 분산을 보지 않았습니다.
  • 3.17배는 이 조건에 딸린 숫자입니다. 외부 호출 지연과 유입 동시성이 바뀌면 같은 배수가 나오지 않습니다.
  • max-per-route = 50 은 실 트래픽으로 재본 값이 아닙니다. “아무도 안 고른 5”를 “근거를 적은 50”으로 바꾼 것이고, 실측이 생기면 다시 정합니다.
  • 50이 실제로 걸리는 것을 보지 못했습니다. 이 부하에서는 유입이 먼저 32로 묶입니다.
  • 장애가 난 적은 없습니다. 출시 전 점검에서 나온 것이고, 운영에서 이 상한에 부딪힌 기록은 없습니다.
  • AWS SDK 나 Apache HttpClient 를 탓하는 글이 아닙니다. 라이브러리는 자기 기본값을 가질 자유가 있습니다. 문제는 그 기본값이 내 서비스의 정책이 되어 있는데 아무도 모르고 있었다는 쪽에 있습니다.
  • 아직 병합하지 않았습니다. 보안 게이트에 닿는 경로라 저장소 규약대로 서면 검토가 먼저입니다.

마치며#

정리하면 이렇습니다.

  • 처리량이 어떤 숫자에 붙어 움직이지 않으면, 그 숫자를 만든 층을 먼저 찾아야 합니다. 스레드나 DB 풀을 늘리는 것은 그다음입니다.
  • 제가 고르지 않은 라이브러리가 제 서비스의 동시성 정책을 정하고 있었습니다. 그 층은 런타임 클래스패스에만 있어서 읽어서는 찾을 수 없고 재야만 나옵니다.
  • 상한을 없애는 것과 정하는 것은 다릅니다. 처리량은 똑같이 오르지만, 하나는 숫자가 적혀 있고 하나는 없습니다.
  • 설정으로 고친 것은 지워도 아무것도 실패하지 않습니다. 그래서 값이 붙었다는 것 자체를 단언해야 합니다.

마지막으로 한 줄만 남긴다면 이겁니다. 아무도 고르지 않은 기본값도 정책처럼 동작합니다. 다만 그건 아무도 책임지지 않는 정책이고, 대개 재 보기 전까지는 있는 줄도 모릅니다.
