Instance HA ⑤: Quorum Cannot Cut the Power
I compared three architectures against one yardstick. What separated them was not whether they ran a consensus algorithm, but whether they had a way to turn a machine off.

In part four I set out the procedure for cutting power and confirming that it went down. The question left over is who runs that procedure.

The design document put three setups side by side: controlling execution with Galera and ShedLock, using leader election in etcd, and layering Pacemaker and Corosync on top.

When I first wrote this up, I said the axis of the comparison was whether a distributed consensus algorithm was present. Reading it again, that was wrong. What separated the three was not consensus but whether they had a way to turn a machine off.

Who this is for#

  • Anyone deciding which foundation to build instance HA on
  • Anyone blocking duplicate execution with a DB lock who wonders whether that is enough
  • Anyone who needs an argument for why Pacemaker and Corosync is the heavy choice
  • Anyone who read part four and wondered who executes that procedure

What separated the three was not consensus#

The design document opened with this: a DB lock is not distributed consensus, so it cannot structurally prevent split brain. That sentence collapses under one question: what about Galera's own quorum? Galera decides a Primary Component through quorum over wsrep group communication.

In practice a Galera cluster that loses quorum drops to non-Primary and refuses writes in that state. ShedLock sits on top of those writes, so acquiring the lock fails along with them. Duplicate execution is blocked.

What is not blocked is something else. Stopping two nodes from running the same recovery is one thing; severing a node that is alive and still writing to disk is another. Quorum protects the database, but it cannot cut the power.

Of the three I recommended Pacemaker and Corosync first, with etcd as the fallback if that was not feasible. Galera and ShedLock is a stopgap. It blocks duplicate execution, but it holds nothing that can enforce the rule from part four.

When STONITH fails, a person steps in#

Choosing Pacemaker still leaves a hole. When a network partition and a STONITH failure happen together, the cluster enters a freeze state. The command to cut power went out, but nothing can confirm it landed, so everything stops.

Only a person can release that stop. I wrote the procedure out in five steps.

# 1. Confirm the failure
crm_mon -1

# 2. At the BMC console, confirm with your own eyes that the node is powered off

# 3. Only after that, record the fencing in the cluster
crm node fence <nodename>

# 4. Bring the node back into the cluster
crm node online <nodename>

# 5. Restart the STONITH resource
crm resource restart stonith-<nodename>

Step three must never run without step two. crm node fence does not cut power; it tells the cluster that power has already been cut. Recording it without confirming first means opening by hand the double attachment that part four was built to prevent.

I recommended two settings alongside it. The default for stonith-action is a reboot, and a reboot puts the target node into a state where it comes back up. Leaving it powered off narrows the window for a double attachment.

Narrowing the set of nodes allowed to execute#

For environments where Pacemaker cannot be adopted right away, I added one more control at the operations level: restricting which nodes are allowed to run a recovery at all.

# The default is reboot. I recommended changing it to off
stonith-timeout=60s
stonith-action=off

# Restrict which nodes are allowed to run a recovery
EVACUATION_MANAGERS=("controller-a" "controller-b" "controller-c")

The incident in part one began with an isolated controller that considered itself healthy. Even if such a controller is elected leader, a recovery does not spread from it while it is absent from that list.

This is not a substitute for fencing. It narrows how far a wrong call can spread by shrinking the set of executors, and it still cannot sever a node that is alive. It belongs to a different layer, so it does not belong in the same cell.

Limits: what this post does not claim#

  • ⚠️ What this series comes from is a design document. I compared the three setups and made a recommendation. I did not adopt or operate Pacemaker.
  • The three detection times come from each project's defaults, not from measurements taken side by side on the same hardware. They shift with configuration.
  • Masakari integration means that the OpenStack documentation describes that setup, not that other setups are impossible.
  • The executor list is an operational convenience and does not replace fencing.
  • This came from internal material, so product names, customers, addresses, accounts and hostnames are left out.

Wrapping up#

The conclusion of this part is one line. Consensus settles who executes, and fencing settles whether executing is allowed at all. A setup that has only the first blocks duplicate execution while leaving double attachment open.

While it sat in one table row called consensus mechanism, that difference was invisible. Only after the layers were separated did it become clear which cell was empty.
