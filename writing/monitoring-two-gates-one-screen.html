Fixing Only REST or Only SSE Left the Screen Where It Was
Whichever of the two finishes last sets when the screen is done.

I build the backend of an internal cloud admin console. Two screens were done by part three. The third one, virtual resources, was different from the other two.

This screen had two data paths that start independently. REST builds the per-project quota and usage; SSE pushes the virtual machine metrics. Before the change REST was about 2.6 seconds and SSE first data about 1.4 seconds. So fixing one of them does not make the screen faster by that much. The screen finishes not at the sum of the two but at whichever finishes last, so fix REST and SSE's 1.4 seconds becomes the floor. I wrote that expression down before starting.

After the fix something that had been hiding came out. Once SSE dropped to 24 ms it arrived ahead of REST and the screen went blank. The slow path had been keeping the order.

Who this is for#

  • Anyone whose single screen is filled by several requests
  • Anyone with code that walks a list and calls an external API per item
  • Anyone who has made one side fast and watched the screen stay the same

I wrote the completion condition as a formula#

page ready = max(REST usage, SSE first metric, small configuration request)

Fix only REST and SSE's 1.4 seconds remain. Fix only SSE and REST's 2.6 seconds remain. The performance work on this screen was not a single-bottleneck optimisation but the removal of two different gates.

The first gate, one call per project#

The REST path walked the project list and fetched each project's compute and network or storage quota in turn. With N projects that is about 2N external calls. If the client factory authenticates on every call, the cost is higher still.

The first idea is parallelism. But unbounded parallel calls push a burst at the authentication service, the external API and the application thread pool at once. The median falls while p99 and the error rate can worsen, and under load the same fan-out is duplicated per user.

What I chose was taking the fan-out off the user request.

background usage loader
    read the current project list
    fetch the required quota values per project
    publish one coherent usage snapshot

REST request
    return the last completed snapshot

A review caught one thing here. When the structure cache degraded and returned an empty project list, the loader taking that as a successful result stored 0/0 usage as the new healthy value. The same shape as part three.

The fix was throwing when the structure information is missing. A failure preserves the existing value, while a successful empty list overwrites it with zero. Under serve-stale, a failure has to be expressed exactly as a failure for the cache to keep the last good value.

The REST median went from about 2,627 ms to 5 to 12 ms, and p99 from about 3,005 ms into the 10 to 20 ms range.

The second gate, and what speed exposed#

The SSE side matched the other two screens: it collected metrics at connection time and sent first data. A 15 second worker now builds it ahead and the connection replays it at once. The median went from about 1,436 ms to 24 ms.

And here a regression candidate appeared.

The existing screen leaned on an implicit assumption that REST arrives first. If the previous state was empty, the SSE merge function returned early, and the slow REST happened to fill that state first. Once SSE dropped to tens of milliseconds the order flipped and the screen stayed blank until the next 15 second broadcast.

So three guards went in. Connection replies and periodic broadcasts can invert, so frames older by creation time are dropped; a process restart can move the time base backwards, so the client rebaselines and accepts the new stream; and if SSE arrives before REST, the first frame initialises the project and VM lists.

Limits the review left standing#

  • Each screen's cache still shared a mutable structure DTO with the other screens. If one screen updates it in place while another serialises, generations can mix.
  • The problem of SSE publishing an empty snapshot as healthy when the infrastructure degrades was common to all three screens. Handling it on one screen only means the same source is interpreted differently per screen.
  • There was no contract for a changing project set. If the front end merges only metrics into existing projects, a project added later stays invisible until a refresh and a deleted one lingers.

The first two went to the shared cache work in the next part.

What this article does not claim#

  • These are not production statistics. Sequential single-user measurements.
  • I am not saying parallelism is bad. I chose not to use unbounded parallelism, and I did not measure what p99 would have done if I had.
  • I do not claim the ordering dependency broke in production. It was found during the change and blocked, and there is no record of a user seeing a blank screen.
  • The project set contract still does not exist. It is written down as remaining work.

Wrapping up#

  • Screen performance is not the time of the most visible API. Among parallel paths, the gate that has to finish last sets the user's delay.
  • The best outcome of an N+1 fix is not finishing N calls faster. It is breaking the synchronous coupling between the user request and those N calls.
  • The slow thing may have been holding the order for you. Speed removes that accident.

Measure each path separately and write down the whole completion formula next to them, or you will mistake half a fix for a finished one.

The next part is the last. Merging the three screens' caches into one turned things that separation had been protecting by accident into contracts. Thank you for reading.
