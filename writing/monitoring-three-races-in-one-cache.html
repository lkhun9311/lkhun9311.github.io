Adding One Cache to a Monitoring Screen Created Three Races
A startup warm-up, a scheduled job and a new connection all refreshed the same slot. An internal cloud admin console. Unified Monitoring, part two

I build the backend of an internal cloud admin console. In part one I wrote that first data on the dashboard took 6.8 seconds, and that taking the computation off the request path brought it to 23 ms.

In one line, the fix was “build the snapshot ahead of time and hand it to the connection.” One line makes it sound easy. The implementation review turned up three races that the happy path never shows.

This part is about those three.

Who this is for#

  • Anyone about to add a “compute it in advance and serve it” layer
  • Anyone whose startup warm-up, scheduled job and request trigger all refresh the same slot
  • Anyone broadcasting the same value to many sessions over SSE or WebSocket

What is in here#

  • It was slow because connecting was computing. The cache that existed held “who is there”, and the “how much is each using right now” that the screen needed was outside it.
  • An exception was being swallowed, so the connection stayed alive while no data came and the screen showed an endless spinner instead of an error.
  • Once the computation moved off the request path, three races appeared: a refresh being cancelled, the same value broadcast to everyone several times, and one timeout cutting somebody else's query.
  • The median went from 6,776 ms to 10 ms. I also wrote down what I did not do.

This is an internal product, so the code and the screens are not reproduced literally. Product names, customers and internal addresses are out; the structure and the configured values stay.

⚠️ These are 30 sequential runs by a single user. Not concurrent throughput, so I did not read throughput here as scalability. What means something is the latency distribution to first business data, and the error rate.

Connecting was computing#

The SSE connection itself was established immediately. But the path that produced the data had a query joining several time-series measurements, a global resource listing, authentication and DTO assembly lined up in series.

The distribution had that shape too. When the timing lined up with the previous computation it was fast, and when it did not the user waited for the next tick and then for a computation lasting seconds. That is why the samples split into fast ones and 6 to 9 second ones.

It looked like an endless spinner, not an error#

When the send path swallowed a computation exception, the connection stayed alive and no data arrived. The front end logged only connection errors and never dropped the loading layer, so what the user got was a spinner that never stopped rather than a message.

Slow and never-arriving looked identical on screen. That got fixed alongside the rest.

I took the computation off the request path#

Dashboard values do not differ per user. Every session gets the same payload. So there is no reason to repeat the same computation per connection.

scheduled job or startup warm-up
    → collect metrics within a time budget
    → assemble the payload the screen needs
    → swap the completed snapshot through a single reference
    → broadcast to current sessions

new connection
    → send the last completed snapshot to that session only
    → if it is missing or stale, ask for a background refresh

Swapping through a single reference is the point: a reader never sees a half-updated value. A failed refresh does not clear the previous snapshot. That must not hide an outage, so the computation time and a degraded flag ride along with the value.

Then there were three races#

That was the design. These three came out of the implementation review, and none of them shows on the happy path.

First, a cancelled refresh leaves somebody waiting. If a user connects while the startup warm-up is running, the refresh that connection asked for is cancelled because one is already in flight. And if the warm-up puts its result in the cache without broadcasting, that user waits for the next 15 second tick. I collapsed warm-up, scheduled job and connection refresh into one function and made whoever actually wins the refresh always publish the result.

Second, the same value gets broadcast several times. With a stale cache and N connections arriving together, each of them could re-send the existing value to every session. Now a connection is answered on its own session only, and the full broadcast of a new result happens once, from the refresh winner.

Third, one timeout cuts somebody else's query. Putting a total request deadline on the metrics client also cuts long reporting queries that share the client. Instead of a global total, I set bounds on the connect and read stages and separated the client policy per feature.

⚠️ None of the three was found by measurement. They came out of reading the code during review. I did not reproduce them under load; I judged that they could happen and fixed them. So I will not write that these three were occurring.

What I did not do#

I did not shorten the 15 second collection interval to 5. The source agent also produces a new sample every 15 seconds. At 5 seconds I would likely read the same sample three times. Freshness would not improve and the store would carry more load.

I did not merge the computation time with the observation time. The first exists for the cache refresh policy; the second is how a user judges the age of the data. With a quiet source, merging them lets every connection decide the cache is stale and pile recomputations on top of each other.

What this article does not claim#

  • These are not production statistics. Thirty sequential runs by a single user, with no concurrent throughput measured.
  • I do not claim the three races were occurring. I read the code, judged, and fixed; I did not reproduce them.
  • This is not “monitoring got faster”. It is one SSE path on one screen.
  • 10 ms is not a constant. It is the cost of reading a snapshot from memory and serialising it, and it follows the size of the data.

Wrapping up#

  • What matters is whether the expensive layer went into the cache, not that a cache exists. “Who is there” was inside. “How much right now” was outside.
  • A duplicate guard can cancel the person who is waiting. “Cancel if a refresh is running” is correct, and if the cancelled side cannot publish, that person waits a full cycle.
  • A bound on a shared client applies to other paths too. What was needed was per-stage bounds, not a total deadline.

If one line survives, this one. “Build it ahead and serve it” is one line, but it stops being one line until you decide who builds and who publishes.
