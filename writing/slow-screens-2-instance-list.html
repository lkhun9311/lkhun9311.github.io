Listing Instances: 54 Seconds → One
The cause was not the application code but a full swap and 1,021 rows left marked as deleted.

I write the backend of an internal cloud admin console. Its instance list screen spun and spun and then timed out. There were 20 instances running at the time. This was not code that could fail on 20 rows.

So before opening a source file I fetched the same list from the CLI. That took 54 seconds too. If it is 54 seconds without going through our backend, the slow stretch is below us.

Below us, two abnormal things were visible at once. Swap was using all 8.0 GiB, and the instances table still held 1,021 rows that were only marked as deleted. Clearing both brought the same CLI query to 1.0 second. And the command I used that day was one you must not run in production. A month later I wrote the proper answer to the same problem as a document. This article records both.

Who this is for#

  • You run OpenStack, or anything else, and have met “we deleted the data and it is still slow”.
  • Your first move on a slow screen is to open the application code.
  • You have typed a DELETE straight into a database because it was urgent.

The screen#

It shows the instance list inside a project. Asking for the list sends the admin console backend to OpenStack’s compute API, which in turn reads the instances table in its own database (MariaDB).

The fork: the CLI took 54 seconds too#

The first thing I did about a screen that would not load was ask for the same thing down a different path.

$ openstack server list

It took 54 seconds.

Before and after are not guaranteed to be the same request. What the record holds is openstack server list before and openstack server list --all-projects after. The options differ. And for the before run there is no terminal capture, only the number.

Still, that one line bought something. A path that does not go through the admin console backend also took 54 seconds, which means there is at least one slow stretch below the compute API. It is not proof that our backend added no delay of its own. I did not measure that side.

Opening the application code first on a slow screen is a habit, not a diagnosis. Ask the same question down a second path and there is less left to search.

Cause 1: swap was full, all 8.0GiB of it#

I logged into the box and looked at memory first.

[root@host ~]# free -h
               total   used   free   shared  buff/cache   available
Mem:            62Gi   44Gi  8.1Gi    1.3Gi        12Gi        18Gi
Swap:          8.0Gi  8.0Gi  2.0Mi

Swap is using 8.0GiB out of 8.0GiB. What is left is 2.0MiB. That much is observed.

From here on it is a hypothesis. If a page MariaDB needs sits in swap, a read that would have ended in memory becomes a round trip to disk. The query would be unchanged and slower.

I never measured that hypothesis. There is no vmstat, no iostat, no page-fault record for the MariaDB process. So this article can state two facts: swap was full, and clearing it made things faster. What joins them is a guess, not evidence. The internal document’s “RAM 0.0001ms, swap 10–100ms” is likewise a cited order of magnitude, not a measurement from this machine.

Cause 2: 1,021 rows marked deleted and still there#

Next, the table. When Nova deletes an instance it does not remove the row. It changes the deleted column. A soft delete.

SELECT deleted, COUNT(*) FROM instances GROUP BY deleted;

And here the source document misread its own screenshot. It says “a full scan of 1,022 rows”. But 1022 rows in set is not a row count. It is the number of groups GROUP BY returned.

What 1,022 and 1,041 each count.
NumberWhat it countsHow it adds up
1,022groups returned by GROUP BYone group for deleted = 0 plus 1,021 deleted rows
1,041rows in the instances table20 live rows plus 1,021 marked deleted

A soft-deleted Nova instances row gets its own id written into deleted (this is not a claim about every service or every table). Each deleted row therefore carries a different value, and one group appears per row. The screenshot shows it: only deleted = 0 has COUNT(*) = 20, every other group has 1. The 1,041 in the summary table is the row count, and that one is right.

So the screen wanted 20 rows and the table held 1,041. And not only instances: the same had piled up in the tables hanging off it, such as instance_actions_events, instance_faults and instance_system_metadata.

No execution plan was kept. The internal document calls this a full scan, but there is no recorded EXPLAIN, so whether everything was really scanned is not something I verified. What was verified is that the table held 1,041 rows and not 20.

The fix: I used commands I could not undo#

First I cleared swap.

$ swapoff -a && swapon -a

This command pulls everything in swap back into RAM. Which means RAM has to have room for it. If it does not, swapoff fails or the kernel starts killing processes to reclaim memory (the OOM killer). Here available (the kernel’s estimate of what a new process could use without swapping) was 18GiB, so there was room for 8.0GiB.

And this one line has a trap I did not know about at the time. swapoff -a turns off every registered swap, and it can fail for reasons other than memory. If only some of them come off, swapoff exits non-zero, and && runs the second command only on a zero exit. So if it half fails, swapon -a never runs at all and swap stays off. On a production box this is a command to touch only after checking headroom, checking each device separately, and having a way back.

[root@host ~]# free -h
               total   used   free   shared  buff/cache   available
Mem:            62Gi   51Gi  787Mi    1.3Gi        11Gi        10Gi
Swap:          8.0Gi     0B  8.0Gi

And it used all of that room. available went from 18GiB to 10GiB.

That 8GiB cannot all be pinned on the swap-in. free -h rounds, available is an estimate rather than a usage figure, and other processes were running throughout. And what shrank is the RAM headroom at that moment, not the swap capacity. swapon -a put the 8.0GiB of swap back. Whether it fills again is something I did not measure afterwards.

Then the table.

SET FOREIGN_KEY_CHECKS = 0;

DELETE FROM instance_actions_events    WHERE deleted != 0;
DELETE FROM instance_actions           WHERE deleted != 0;
DELETE FROM instance_faults            WHERE deleted != 0;
DELETE FROM instance_system_metadata   WHERE deleted != 0;
-- … and the rest of the dependent tables
DELETE FROM instances                  WHERE deleted != 0;

SET FOREIGN_KEY_CHECKS = 1;

The application side changed too. The list-all API now filters out the DELETED state when it asks. How much that actually defends, though, I did not measure. openstack server list already excludes deleted rows by default. What our backend was sending before, and what changed after, is recorded neither as a request nor as a query plan.

Do not run these in production#

I did not run that block of DELETEs because it was right. QA could not use the dashboard, and I judged that deleted data did not need to survive. Even if that judgement was correct, the method was bad.

  • I turned foreign key checks off. This is not a “be careful with the order” problem. In a session with checks off, every reference violation simply passes, and switching them back on does not go back and validate what already happened. A child table I missed, another write landing in between, an execution cut short. Any of these can leave rows with broken references, and you find out much later.
  • I did not take a backup first. “It does not need to survive” is a safe judgement only while you can still undo it.
  • It does not stop this recurring. Soft deletes keep accumulating. What I cleared, I cleared up to that day.

So a month later I wrote the proper answer down separately.

A month later: the answer was already in the docs#

The OpenStack documentation has a section called Soft Delete and Shadow Tables. That accumulated deleted rows affect performance, and that you should archive and purge them periodically, were already written there. Deleting by hand was what I did instead of reading it.

What the document describes is moving rows aside rather than deleting them out of the main table. The place they move to is a shadow table: a table of the same shape whose name starts with shadow_, sitting outside the query path.

Scroll sideways to see the rest

Retention stages and periods for deleted rows.
StageWhere it livesHow longWhat for
soft deletemain table0–30 days after deletionrecent history
archiveshadow table30–90 days after deletionkeeping history
purgenowherefrom 90 days after deletionreclaiming space

Nothing is deleted straight out of the main table; there is a stage in between, and the main table already shrinks at archive time. Every period here counts from the day the row was deleted. Archive at 30 days and purge at 90 and a row spends 60 days in shadow. And shadow tables are not a recovery mechanism Nova guarantees. They are history kept out of the query path, and not every table has one. Do not read this as “90 days to undo”.

# 1) move rows older than 30 days into shadow tables. the main table shrinks here
nova-manage db archive_deleted_rows \
  --max_rows 10000 --verbose --all-cells \
  --before "$(date -d '30 days ago' '+%Y-%m-%d')"

# 2) delete from shadow what is older than 90 days. space comes back
nova-manage db purge \
  --verbose --all-cells \
  --before "$(date -d '90 days ago' '+%Y-%m-%d')"

The proposal had --all on purge. That does not mean “all shadow tables”; it means delete everything left, which pulls against --before. It is gone here.

And I wrote that this should not be something a person has to remember. The proposal runs it in small batches in the quiet hours.

Except the cron example in my own proposal contradicted my own retention policy. I found that writing this article. Three things.

  • --before was missing. The table above promises 30 days, and the cron moves rows deleted yesterday that same night.
  • --sleep only means something alongside --until-complete. In this shape the command runs one batch and exits, so there is nowhere to sleep.
  • There was no purge cron. Archive alone lets shadow grow forever. The main table shrinks and the disk does not.

Corrected, it looks like this.

# /etc/cron.d/nova-db-archive
# every day at 02:00: move only rows deleted more than 30 days ago
0 2 * * * nova /usr/bin/nova-manage db archive_deleted_rows \
  --max_rows 5000 --all-cells \
  --before "$(date -d '30 days ago' '+%Y-%m-%d')" \
  >> /var/log/nova/db-archive.log 2>&1

# every Sunday at 03:00: drop what has been in shadow past 90 days
0 3 * * 0 nova /usr/bin/nova-manage db purge --all-cells \
  --before "$(date -d '90 days ago' '+%Y-%m-%d')" \
  >> /var/log/nova/db-purge.log 2>&1

And whether 5,000 rows a day is enough is a separate question. If more than that is deleted per day, the main table keeps growing. What clears has to outpace what accumulates.

Take a backup before running it. That is the step I skipped.

mysqldump --single-transaction nova       > nova_backup.sql
mysqldump --single-transaction nova_cell0 > nova_cell0_backup.sql

That backup is not enough. I copied it from the proposal as written, but --all-cells touches every registered cell database (a cell is the database unit Nova splits compute resources across), and archiving instances also removes rows on the nova_api side. Two dumps will not restore that. List the cells first, then dump every database in that list along with nova_api.

Limits: what this article does not claim#

  • How much each of the two changes cut, I cannot separate. Clearing swap and deleting rows went in together, and whether they affected each other is also unknown. Seeing that would take four combinations run separately, and I ran none of them. Measuring six configurations separately in the previous part was exactly for this, and here the situation was urgent enough that I did not.
  • I am not claiming 1,041 rows caused 54 seconds. Nor that they did not. The row count was never varied on its own, so there is nothing here to decide it with.
  • Clearing swap did not remove a cause. It reversed the state at that moment. ⚠️ And I never checked what was holding that much memory. So this article cannot say “add RAM” or “tune MariaDB” either. The first step would be finding which process held what.
  • “Under 500 ms once the cache applies” is the source’s sentence. No measurement behind it survives in the record, so it is not in the table.
  • These are not production numbers. They are measurements from a QA test environment.
  • The second half is a proposal, not a result. Archive, purge and cron are what I proposed in a document; I have no record that any of it was actually scheduled and ran. The only part of this article with measurements attached is the first half, the hurried fix.
  • It may not be only about OpenStack. Any system that leaves deleted rows in the main table can hit something similar, depending on its schema and query plans. What this article verified, though, is one machine.

Closing#

  • Ask the same question down a second path and there is less left to search. Knowing the CLI took 54 seconds moved the first place to look below the backend.
  • Deleted data is still in the main table. A soft delete looks like a deletion and is not one. How many of those rows a query actually reads depends on the schema and the plan, and that has to be checked separately.
  • With swap full, judgements above it get hard to trust. The query is unchanged while what a single read costs may not be, and confirming that means measuring the memory side.
  • Do not leave an emergency command standing as the answer. If you do not write that down, the next person learns it as the procedure.

Fixing it and fixing it properly are different things. The commands that turned 54 seconds into one second were not the answer I wrote up a month later.
