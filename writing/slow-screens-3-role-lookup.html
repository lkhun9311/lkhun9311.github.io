A Project Role Lookup: 1,409 ms → 1 ms
Every project id it failed to resolve pulled the whole project list again.

I write the backend of an internal cloud admin console. Open one user and a table at the bottom shows which projects they belong to and in what role. That table was spinning for over a second.

The roles are in our own database, but the project names live on the OpenStack side, in Keystone, which owns users and projects. So every role row needs one project lookup, and that lookup already had a cache in front of it: the same CacheManager from part one, with a ten-minute retention. So this article is not “we added a cache and it got faster”. There was a cache, and the cache was why it was slow.

Hit-or-miss and elapsed time were already being logged for every lookup. Opening the log of a pre-fix run: of 14 role rows, eight were 0 ms and the remaining six were around 230 ms each. Adding those six gives 1,409 ms, exactly the total the timer recorded for that run. That changed the question. Not “why is the cache not helping” but “why does one miss cost 235 ms”.

Who this is for#

  • You have added a cache and not got the speed you expected.
  • You have had to decide what to reload when a cache lookup fails.
  • You have missed the fact that some lookups are searching for something that is not there.

The screen#

Open one user and the lower half shows a table of which role they hold in which project. The roles live in our own database; the project names live on the OpenStack side, specifically in Keystone, the service that owns users and projects there. So every role row has to resolve a project.

There was a cache at that resolving step. Hand-rolled (the same CacheManager that appears in part one) with a retention of 10 minutes.

The log had already recorded where the time went#

Every lookup was already logging whether it resolved and how long it took. One run from before the fix, transcribed, looks like this.

There is only one thing to do with that.

247 + 235 + 238 + 228 + 233 + 228 = 1,409
The six unresolved rows sum to the total for this run. The eight resolved rows were 0 ms.

This is one run at millisecond resolution, so “the rest is exactly zero” is more than it supports. Building, filtering and sorting the DTOs happens outside each row's own span, and anything under a millisecond looks like this. What it does support is that at this resolution the six recorded spans summed to the total.

It still settles where to look. The question is not “why isn't the cache helping” but “why does one unresolved row cost 235 ms”.

The cause: one failed lookup pulled the whole list#

The code that resolves a project looked like this.

public static Project project(final String projectId) {
    CacheManager manager = CacheManager.getInstance().init(Project.class, 10);
    final Project project = manager.get(Project.class, projectId);

    if (project == null) {                       // ← one key is missing
        client.identity().projects().list()      // ← fetch the whole list again
              .forEach(r -> manager.set(Project.class, r.getId(), r));
        return manager.get(Project.class, projectId);   // ← and look once more
    }
    return project;
}

It reads reasonably. If it is not there, fill the cache and look again. It is the shape a cache naturally takes the first time you write one, and for the first call it is right.

The problem is a key that filling the cache will never produce.

Those six were not there to be found#

The role table lives in our database and the projects live in OpenStack. Delete a project on the OpenStack side and the row in our role table stays exactly where it was. The project id it points at now exists nowhere.

Which makes the code above run like this.

  1. look in the cache → not there
  2. fetch the whole list again → 235 ms
  3. look again → still not there, because the project is gone
  4. the next row hits another missing id → back to step 1

Every missing id fetched the entire project list afresh. And since those six ids are not in the list however fresh it is, the next row fetches it again.

The six unresolved rows were the same six ids in all three runs I have: one before the fix and two after, a day apart. That does not look like a cache that happened to be cold; it looks like positions that cannot be filled. Three runs is three runs. I did not run it more than that.

The fix: filter a list instead of asking for a key#

What changed is one thing: how it looks the project up.

// before: ask the cache for one key. if absent, call the external API
var project = CacheBox.project(roleAssignment.getProjectId());

// after: take the list from the cache and filter it. absent simply ends there
var project = CacheBox.projects().stream()
        .filter(p -> p.getId().equalsIgnoreCase(roleAssignment.getProjectId()))
        .findFirst();

projects() can call the external API too. What differs is that “this id is absent” is no longer the condition that triggers the call.

Precisely: projects() takes the list from the cache, and while doing so it drops expired entries one by one. Only when what remains is completely empty does it call the external API.

There is a trap in that. Partial expiry does not trigger it. If even one entry survives, the incomplete list is returned as it is, and a project that fell out in between is reported unresolved despite existing. In these runs the entries were filled together and expired together, so it did not show. Not showing is not the same as not being there.

The log shows it directly. One run with the cache expired:

[Miss] projectId=project-A   elapsed  246 ms   ← the call that fetches the list
[Miss] projectId=project-B   elapsed    0 ms
[Hit ] projectId=project-C   elapsed    0 ms
…
[Miss] projectId=project-J   elapsed    0 ms
[Result] Total elapsed time: 250 ms

Six rows still fail to resolve. Five of them now cost 0 ms. With the cache valid the first one is 0 ms as well and the total is 1 ms.

What it cost: new projects show up late#

The old code had a use nobody was counting on. Meeting an unknown id, it refetched the list, so a project created moments ago showed up immediately. It was slow, and it was current.

After the fix an unknown id does nothing at all. So a new project does not appear until the cache is refilled.

And “until the cache is refilled” is not something I can Pin at 10 minutes. Retention hangs on the write time recorded per entry, not on the list as a whole. And project() is still there, so one call to it from another screen refills every entry at once. That can push the timestamps forward and make a new project appear later, or land at just the right moment and make it appear sooner. What I can say is that absent any other refill, it shows up on the first lookup after the last entry expires.

The latency was not removed. It was traded against freshness. This screen is a list a person reads, so ten minutes was acceptable. Not every screen can make that trade.

And the data condition is still there#

The direct cause of the delay was the lookup policy that refetched the whole list on every failure. The data condition that made it run six times was six role rows pointing at projects that no longer exist. Those are two different things.

I fixed the first one. The second is still there. Those rows are merely no longer expensive; they have not gone away. Making our role table clean itself up when a project is deleted on the OpenStack side is the actual job, and it was not part of this work.

Limits: what this article does not claim#

  • The 1,409 ms is not the screen's response time. The timer starts after the database query returns and covers only the stretch that turns role rows into DTOs; the query, serialisation and transport all sit outside it. What the user waited is longer than this.
  • The measurement is System.currentTimeMillis() plus log.info. currentTimeMillis() is not a monotonic clock; change the system time and the value moves. One log call sits inside each row's span while the one after it falls outside. 0 ms means “under a millisecond”, not “free”. Doing this properly means System.nanoTime() or a timer metric, and counting external API calls separately.
  • These are single runs. One log per state, with no repetition and no distribution. The 235 ms is just the average of those six.
  • Why one list call costs 235 ms is not something I dug into. Network, Keystone-side processing, the number of projects. None of those were separated.
  • The record does not say how many projects there were. So whether the list was slow because it was large, or because the call itself is expensive, is not something this log settles.
  • The fixed code is not finished either. It calls projects() once per role row. While the cache is warm that is 0 ms and invisible, but with many rows the cost of scanning the list repeatedly remains. Hoisting it out of the loop would be better.
  • This cache still carries part one's problem. projects() takes no lock, so if several requests arrive the moment the cache empties, each of them calls the external API. ⚠️ That comes from reading the code, not from this log. These runs opened one user, so there were no concurrent requests.
  • Not production statistics. These are logs from opening one user in a test environment.

Closing#

  • Having a cache and being fast are different things. Here every resolved row was 0 ms and the span was still 1,409 ms.
  • What you do on a failed lookup is half of cache design. “If it is absent, refetch everything” is right for the first call and the worst possible choice in front of an id that refilling will never produce.
  • There are two things you can reduce: how often a lookup fails, and what a failure costs. This work reduced the second and left the first alone.
  • Write down what the speed cost you. Here it cost ten minutes of freshness.

It only needed adding up a log that was already being written. Until I added those six rows up, I was staring at “why isn't the cache helping”.
