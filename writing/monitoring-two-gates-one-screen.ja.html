REST と SSE の片方だけ直しても画面はそのままでした
画面が終わる時刻は、遅く終わるほうが決めます。

社内クラウド管理コンソールの Backend を作っています。③編までで画面を二つ直しました。 三つ目の仮想リソース画面は、前の二つとは違いました。

この画面には別々に始まるデータ経路が二つありました。REST がプロジェクトごとのクォータと 使用量を作り、SSE が仮想サーバーのメトリックを送ります。改善前、REST は約 2.6 秒、SSE の 最初のデータは約 1.4 秒でした。片方を直しても画面はその分だけ速くはなりません。 画面が終わる時刻は二つの和ではなく、遅く終わるほうが決めるからです。REST を直せば、今度は SSE の 1.4 秒が床になります。 この式を先に書き留めてから始めました。

直したあとで、隠れていたものが一つ出てきました。SSE が 24ms になると REST より先に着いて、 画面が空になりました。遅いほうが順序を守ってくれていたのです。

この記事の想定読者#

  • 一つの画面が複数のリクエストで埋まる構造をお持ちの方
  • 一覧を回して項目ごとに外部 API を呼ぶコードをお持ちの方
  • 「片方を速くしたのに画面はそのまま」を経験した方

完了条件を式で書きました#

画面完了 = max(REST 使用量, SSE 最初のメトリック, 小さな設定リクエスト)

REST だけ直せば SSE の 1.4 秒が残り、SSE だけ直せば REST の 2.6 秒が残ります。 この画面の性能作業は単一ボトルネックの最適化ではなく、別々の二つのゲートを取り除くことでした。

一つ目のゲート、プロジェクトの数だけ回る呼び出し#

REST 経路はプロジェクト一覧を回り、各プロジェクトのコンピュートとネットワークまたはストレージの クォータを順に取得していました。プロジェクトが N 個なら外部呼び出しは約 2N 個になります。 クライアントを作るたびに認証まで行う経路なら、費用はさらに大きくなります。

最初に浮かぶ解は並列化です。ところが制限のない並列呼び出しは、認証サービスと 外部 API とアプリケーションの Thread Pool に一気に負荷を集めます。中央値は下がっても p99 とエラー率が悪くなりうるし、リクエストが集まると 利用者の数だけ同じファンアウトが複製されます。

選んだのはファンアウトを利用者のリクエストから外すことでした。

バックグラウンドの使用量ローダー
    現在のプロジェクト一覧を読む
    プロジェクトごとに必要なクォータ値を取得する
    一貫した使用量スナップショットを一つ公開する

REST リクエスト
    最後に完成したスナップショットを返す

ここでレビュー指摘が一つ出ました。構造 Cache が劣化して空のプロジェクト一覧を 返したとき、ローダーがそれを正常な成功として受け取ると 0/0 の使用量が 新しい正常値として保存されます。③編で見たのと同じ形です。

直し方は構造情報が無いときに例外を投げることでした。 失敗は既存の値を守りますが、空のリストの成功は既存の値を 0 で塗り替えます。 serve-stale では失敗を正確に失敗として表さないと、Cache が最後の正常値を守れません。

REST の中央値は約 2,627ms から 5〜12ms に、p99 は約 3,005ms から 10〜20ms 台に 下がりました。

二つ目のゲート、そして速くなって表に出たもの#

SSE 側は前の二画面と同じでした。接続時にメトリックを新しく収集して最初のデータを送っており、 15 秒の Worker が先に作っておいて接続時に即時再生する構造に変えました。 中央値は約 1,436ms から 24ms になりました。

ところがここで回帰の候補が一つ出ました。

既存の画面はREST が先に届くという暗黙の順序に頼っていました。 以前の状態が空なら SSE のマージ関数が早めに戻り、遅かった REST が偶然 その状態を先に埋めていました。SSE を数十 ms に縮めると順序が逆転し、 次の 15 秒配信まで画面が空になります。

そこで安全装置を三つ置きました。接続応答と定期配信が逆転しうるので 作った時刻で古いフレームを捨て、プロセス再起動で時刻の基準が巻き戻ったら 新しいストリームを受け入れるよう基準を取り直し、SSE が REST より先に届いても 最初のフレームでプロジェクトと VM の一覧を初期化するようにしました。

結果#

横にスクロールすると残りが見えます

仮想リソース画面の二つの経路と支配値。
経路改善前の中央値改善後の中央値
REST クォータ · 使用量約 2,627ms約 5〜12ms

改善前はREST が最大で、改善後はSSE が最大です。 支配する側が入れ替わりました。

レビューが残した限界#

  • 画面ごとの Cache が依然として他の画面と同じ可変の構造 DTO を共有していました。 一つの画面がその場で更新しているあいだに別の画面が直列化すると、世代が混ざりえます。
  • インフラが劣化したときSSE が空のスナップショットを正常として公開する問題は 三画面に共通でした。一画面だけに例外を付けると、同じ源を画面ごとに違うふうに解釈します。
  • プロジェクト集合が変わるときの契約がありませんでした。フロントエンドが既存の プロジェクトにメトリックだけを合わせると、後から追加されたプロジェクトは再読み込みまで見えず、 削除されたものが残ります。

前の二つを次の編の共有 Cache の作業に回しました。

この記事が主張しないこと#

  • 運用統計ではありません。単一利用者の逐次測定です。
  • 並列化が悪いという話ではありません。制限のない並列化を選ばなかっただけで、 選んでいたら p99 がどうなったかは測っていません。
  • 順序依存が運用で表面化したとは言いません。改善の途中で見つけて塞いだもので、 利用者が空の画面を見た記録はありません。
  • プロジェクト集合の契約はまだありません。残った課題として書いておきます。

おわりに#

  • 画面の性能は、目立つ API 一つの時間ではありません。 並列な経路のうち最後に終わらなければならないゲートが利用者の遅延を決めます。
  • N+1 のいちばん良い結果は N 個を速く終えることではありません。 利用者のリクエストとその N 個のあいだの同期的な結合を切ることです。
  • 遅いものが順序を守ってくれていたのかもしれません。 速くなると、その偶然が消えます。

各経路を別々に測り、全体の完了式を一緒に書き残しておかないと、片方だけ速くなったものを 完了だと勘違いします。

次回が最終編です。三画面の Cache を一つにまとめると、 別々だったから偶然守られていたことが契約として表に出ました。 お読みいただきありがとうございました。
