Instance 一覧が 54 秒から 1 秒になりました
原因はアプリケーションのコードではなく、Swap の飽和と削除の印が残った 1,021 行でした。社内クラウド管理コンソール · 連載「遅い画面」②

社内クラウド管理コンソールの Backend を作っています。Instance 一覧の画面が読み込み中の まま Timeout しました。そのとき動いていた Instance は 20 個でした。20 個を描けないコードでは ありません。

そこでソースを開く前に、CLI で同じ一覧を呼んでみました。そちらでも 54 秒かかりました。 こちらの Backend を通らなくても 54 秒なら、遅い区間はその下にあります。

下を覗くと、異常が二つ同時に見えました。Swap が 8.0GiB を使い切っていて、instances テーブルには削除済みの印だけが付いた行が 1,021 件残っていました。二つを片づけると、同じ CLI の照会が 1.0 秒になりました。そしてそのとき私が使ったコマンドは、本番で使っては いけないものでした。1 か月後、同じ問題に対するまともな答えを文書にしました。 この記事はその両方を書きます。

想定読者#

  • OpenStack や他のシステムを運用していて「データは消したのに遅い」に出会ったことがある方
  • 遅い画面に当たると、まずアプリケーションのコードを開く方
  • 急ぎのときに DB へ直接 DELETE を打ったことがある方

どんな画面#

プロジェクト内の Instance 一覧を見る画面です。一覧を呼ぶと管理コンソールの Backend が OpenStack の compute API に問い合わせ、そちらはさらに自分の DB(MariaDB)の instances テーブルを読みます。

分かれ道: CLI でも 54 秒でした#

画面が出ないとき最初にやったのは、同じものを別の道から呼んでみることでした。

$ openstack server list

54 秒かかりました。

ここで 前後を同じリクエストとして保証できません。記録に残っているのは 修正前が openstack server list、修正後が openstack server list --all-projects です。オプションが違います。 そして修正前はターミナルのスクリーンショットがなく、「54 秒」という数字だけが 残っています。

それでもこの 1 行が得たものがあります。管理コンソールの Backend を通らない経路でも 54 秒かかったということです。遅い区間が compute API より下に少なくとも 1 つある という意味です。これは私たちの Backend が何の遅延も足していないという証明ではありません。 そちらは別に測っていません。

画面が遅いときにアプリケーションのコードから開くのは、習慣であって診断ではありません。 同じ問いを別の経路から 1 回投げれば、探す場所が減ります。

原因 ①: Swap が 8.0GiB すべて埋まっていました#

マシンに入って、まずメモリを見ました。

[root@host ~]# free -h
               total   used   free   shared  buff/cache   available
Mem:            62Gi   44Gi  8.1Gi    1.3Gi        12Gi        18Gi
Swap:          8.0Gi  8.0Gi  2.0Mi

Swap が 8.0GiB のうち 8.0GiB を使っています。残りは 2.0MiB です。 ここまでが 見たことです。

ここから先は 仮説です。MariaDB が読むべきページが Swap に入っていれば、 メモリで終わる読み取りがディスクの往復になります。だとすればクエリはそのままで遅くなります。

その仮説を測っていません。vmstat も iostat も MariaDB プロセスの page fault も残っていません。ですからこの記事が言えるのは 「Swap が埋まっていた」と「Swap を空けたら速くなった」の 2 つの事実までで、 その間をつなぐのは証拠ではなく当て推量です。社内文書の「RAM 0.0001ms、Swap 10〜100ms」も このマシンで測った値ではなく、一般的な桁の引用です。

原因 ②: 削除の印だけが付いた行が 1,021 件#

次はテーブルです。Nova は Instance を消すとき、行を 削除しません。 deleted カラムだけを変えます。soft delete です。

SELECT deleted, COUNT(*) FROM instances GROUP BY deleted;

ここで 原本の文書が自分のスクリーンショットを読み違えました。文書には 「1,022 行をフルスキャン」と書かれています。ところが 1022 rows in set は 行数ではなく GROUP BY が返したグループの数です。

横にスクロールすると残りが見えます

1,022 と 1,041 がそれぞれ何を数えた値か。
数字何を数えたか内訳
1,022GROUP BY が返したグループdeleted = 0 の 1 グループ + 削除された行 1,021 グループ
1,041instances テーブルの行生きている 20 行 + 削除の印 1,021 行

Nova の instances の行は soft delete されるとき deleted に その行の id が入ります(ほかのサービスや他のテーブルまで そうだという話ではありません)。だから削除された行はそれぞれ違う値を持ち、グループが行数だけできます。 スクリーンショットでも deleted = 0 だけが COUNT(*) = 20 で、残りはすべて 1 です。 要約表にある 1,041 が行数で、こちらが正しい値です。

つまり画面が求めたのは 20 行なのに、テーブルには 1,041 行が入っていました。そして instances だけでなく、instance_actions_events・instance_faults・ instance_system_metadata のような付随テーブルにも同じものが溜まっていました。

実行計画は残っていません。社内文書はこれを「フルスキャン」と書きましたが、 EXPLAIN を取った記録がなく、本当に全部を走査したのかは確認できていません。 確認できたのは テーブルが 20 行ではなく 1,041 行を抱えていたまでです。

修正: 取り消せないコマンドを使いました#

まず Swap を空けました。

$ swapoff -a && swapon -a

このコマンドは Swap にあったものを全部 RAM に引き上げます。ですから RAM にその分の空きが必要です。なければ swapoff が失敗するか、 カーネルがメモリを取り戻そうとプロセスを殺します(OOM killer)。ここでは available(新しいプロセスが Swap なしで使えるとカーネルが見積もった量)が 18GiB だったので、8.0GiB の入る余地がありました。

ところが この 1 行には、当時の私が知らなかった落とし穴があります。 swapoff -a は 登録された Swap を全部止め、メモリ不足以外の理由でも 失敗しえます。一部だけ止まっても swapoff は 0 以外で終わり、 && は前が 0 のときだけ後ろを実行します。つまり 半端に失敗すると swapon -a が実行されず、Swap が止まったまま残ります。 本番のマシンでは、余裕を先に確認し、デバイスごとの状態を個別に見て、失敗したときに戻す手順まで 用意してから触るコマンドです。

[root@host ~]# free -h
               total   used   free   shared  buff/cache   available
Mem:            62Gi   51Gi  787Mi    1.3Gi        11Gi        10Gi
Swap:          8.0Gi     0B  8.0Gi

そしてその余地を使い切りました。available が 18GiB から 10GiB になりました。

この 8GiB を全部 Swap から上がってきた分だと言い切ることはできません。 free -h は丸めて表示し、available は実使用量ではなく 見積もりで、その間ほかのプロセスも動いていました。そして 減ったのはその時点の RAM の余裕であって、Swap の容量ではありません。 swapon -a で 8.0GiB の Swap は戻してあります。また埋まるかどうかは、その後測っていません。

次はテーブルです。

SET FOREIGN_KEY_CHECKS = 0;

DELETE FROM instance_actions_events    WHERE deleted != 0;
DELETE FROM instance_actions           WHERE deleted != 0;
DELETE FROM instance_faults            WHERE deleted != 0;
DELETE FROM instance_system_metadata   WHERE deleted != 0;
-- … 付随テーブルを順に
DELETE FROM instances                  WHERE deleted != 0;

SET FOREIGN_KEY_CHECKS = 1;

アプリケーション側も一緒に直しました。全件取得の API が DELETED 状態を除いて呼ぶように変えました。 ただしこれが どれだけ防いでくれるのかは測っていません。 openstack server list はもともと削除済みを除いて呼びます。私たちの Backend が その前に何を送っていて、変えたあと何が変わったのか、リクエストもクエリ計画も残していません。

このコマンドは本番で使ってはいけません#

上の DELETE の束は 正しいから使ったのではありません。 QA がダッシュボードを使えずにいて、消えたデータだから戻す必要はないと判断して使ったものです。 その判断が正しかったとしても、やり方は悪かったのです。

  • 外部キー検査を切りました。これは「順番に気をつければよい」話ではありません。 検査を切ったセッションでは すべての参照違反がそのまま通り、 戻してもすでに生じた不整合をさかのぼって検査してくれません。 抜けた子テーブル、その間に入った別の書き込み、途中で切れた実行——どれも参照の切れた行を 残しえますし、それが分かるのはずっと後です。
  • 先にバックアップを取りませんでした。「戻す必要はない」という判断は、 戻せるうちにしてこそ安全な判断です。
  • 再発を止められません。soft delete は溜まり続けます。今日消したものは今日までです。

そこで 1 か月後に まともな答えを別に書きました。

1 か月後: 答えはすでに公式文書にありました#

OpenStack の公式文書に Soft Delete and Shadow Tables という項目があります。 削除の印が付いた行が溜まると性能に影響すること、定期的に保管して取り除くことが すでに書かれていました。私が手で消したのは、その文書を読まずにやったことでした。

文書が言う方法は 本テーブルから直接消さず、横へ移すことです。移し先を shadow テーブルと呼びます。名前が shadow_ で始まる同じ形のテーブルで、 取得の経路から外れています。

横にスクロールすると残りが見えます

削除された行の保存段階と期間。
段階どこにあるかどれだけ何のために
soft delete本テーブル削除から 30 日直近の履歴照会
archiveshadow テーブル削除から 30〜90 日履歴の保管
purge残らない削除から 90 日以降保存領域の確保

本テーブルから直接消さず、1 段階を挟みます。 本テーブルは archive の時点ですでに小さくなります。期間はすべて 行が削除された日を 基準に数えます。30 日で archive し 90 日で purge すると、shadow にいるのは 60 日です。 そして shadow テーブルは Nova が保証する復旧手段ではありません。 取得の経路から外しておく履歴の保管用で、すべてのテーブルに shadow があるわけでもありません。 「消す前に 90 日戻せる」と読んではいけません。

# 1) 30 日を過ぎたものを shadow テーブルへ移す。本テーブルはここで小さくなる
nova-manage db archive_deleted_rows \
  --max_rows 10000 --verbose --all-cells \
  --before "$(date -d '30 days ago' '+%Y-%m-%d')"

# 2) shadow から 90 日を過ぎたものを完全削除する。領域が戻る
nova-manage db purge \
  --verbose --all-cells \
  --before "$(date -d '90 days ago' '+%Y-%m-%d')"

提案書では purge に --all が付いていました。あれは 「すべての shadow テーブル」という意味ではなく 残りを全部消せという意味なので、 --before と一緒に使うと意図がぶつかります。外しました。

そして 人が覚えてやる仕事にしないと書きました。負荷の低い夜明けに、 少しずつ回すように仕掛ける案です。

ところが私が出した提案書の cron 例は、自分の保存方針と食い違っていました。 この記事を書きながら気づきました。3 か所です。

  • --before が抜けていました。上の表は 30 日置くと言いながら、 cron は 昨日消した行までその日のうちに移します。
  • --sleep は --until-complete と一緒のときだけ意味を持ちます。 1 回回して終わる今の形では、5 秒休む場所がありません。
  • purge を仕掛ける cron がありませんでした。archive だけ回れば shadow は 溜まり続けます。本テーブルは小さくなり、ディスクは減りません。

直すとこうなります。

# /etc/cron.d/nova-db-archive
# 毎日 2 時: 削除から 30 日を過ぎた行だけを shadow へ移す
0 2 * * * nova /usr/bin/nova-manage db archive_deleted_rows \
  --max_rows 5000 --all-cells \
  --before "$(date -d '30 days ago' '+%Y-%m-%d')" \
  >> /var/log/nova/db-archive.log 2>&1

# 毎週日曜 3 時: shadow で 90 日を過ぎたものを消す
0 3 * * 0 nova /usr/bin/nova-manage db purge --all-cells \
  --before "$(date -d '90 days ago' '+%Y-%m-%d')" \
  >> /var/log/nova/db-purge.log 2>&1

そして 1 日 5,000 行で足りるのかが別に残ります。1 日に消える量がそれより多ければ、 本テーブルは育ち続けます。片付ける速さが溜まる速さより速くなければなりません。

実行の前にはバックアップを取ります。今回、私が飛ばした手順です。

mysqldump --single-transaction nova       > nova_backup.sql
mysqldump --single-transaction nova_cell0 > nova_cell0_backup.sql

このバックアップでは足りません。提案書に書いたそのまま載せましたが、 --all-cells は 登録されたすべての cell DB に触れ(cell は Nova が compute リソースを分けて持つ DB の単位です)、Instance を archive するときは nova_api 側の行も一緒に消えます。2 つ取っただけでは戻せません。 cell の一覧をまず出し、そこにある DB 全部と nova_api を一緒に取る必要があります。

横にスクロールすると残りが見えます

いちばん下の行は 悪くなった値です。表から消していません。

[root@host ~]# time openstack server list --all-projects
...
real    0m1.002s

Timeout していた画面は表示されるようになりました。画面そのものの所要時間は 測っていません。修正前は終わらないので測れず、修正後は改めて測りませんでした。 54 秒は CLI の実測値です。

限界: この記事が主張しないこと#

  • 2 つの変更がそれぞれどれだけ縮めたのか、切り分けられません。Swap を空けるのと 行を消すのが一度に入りました。2 つが 互いに影響したかも分かりません。それを見るには 4 通りの組み合わせを別々に回す必要があり、1 つも回していません。 前編で 6 通りの構成を別々に測ったのはこのためですが、 急ぎの状況でここではそうしませんでした。
  • 1,041 行が 54 秒の原因だとは言いません。逆に原因ではないとも言いません。 行数だけを別に変えてみたことがないので、判定のしようがありません。
  • Swap を空けたのは原因を無くしたことではありません。その時点の状態を戻しただけです。 そして 何がそれだけのメモリを使っていたのかを確かめていません。 ですから「RAM を増やすべきだ」も「MariaDB の設定を直すべきだ」も、この記事は言えません。 まずどのプロセスがどれだけ握っていたのかを見るところからです。
  • 「Cache が効けば 500ms 以内」は原本の文です。その実測値は記録に残っておらず、 表には入れていません。
  • 運用環境の数値ではありません。QA 試験環境の実測です。
  • 後半は提案であって結果ではありません。archive・purge・cron は私が文書として出した 提案で、それが実際に仕掛けられて回ったという記録は手元にありません。 この記事で実測が付いているのは前半、急いで直したほうだけです。
  • OpenStack だけの話ではないかもしれません。消した行を本テーブルに残す システムなら、schema とクエリ計画しだいで似たことが起こりえます。 ただしこの記事が確認したのは この 1 台のマシンです。

おわりに#

  • 同じ問いを別の経路から 1 回投げれば、探す場所が減ります。CLI が 54 秒だった という一点で、先に見る場所が Backend より下へ移りました。
  • 消したデータも本テーブルには残っています。soft delete は消したように見えるだけで、 消えてはいません。クエリがその行を実際に何件読むかは schema とクエリ計画しだいで、 それは別に見る必要があります。
  • Swap が埋まっていると、その上の判断が信じにくくなります。クエリはそのままで 読み取り 1 件の値段が変わっているかもしれず、それを確かめるにはメモリ側を別に測る必要があります。
  • 急ぎで使ったコマンドを、答えとして残してはいけません。書き留めておかないと、 次の人がそれを手順として覚えます。

最後に 1 行だけ残すなら、これです。 直したことと、正しく直したことは違います。 54 秒を 1 秒にしたコマンドと、1 か月後に文書として出した答えは、同じものではありませんでした。

次回も同じ製品の別の画面です。今度は Cache がすでにあったのに その Cache のせいで遅くなっていました。
