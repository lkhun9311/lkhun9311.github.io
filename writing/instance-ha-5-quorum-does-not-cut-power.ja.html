Instance HA ⑤: Quorum は電源を落とせません
三つのアーキテクチャを同じ物差しで比べました。分けたのは合意アルゴリズムの有無ではなく、電源を落とす手段があるかどうかでした。

④編で電源を落とし、落ちたかを確認する 手順を立てました。残る問いは、その手順を誰が実行するのかです。

設計書は三つの構成を並べて比べました。Galera と ShedLock で実行を制御する案、etcd の Leader Election を使う案、Pacemaker と Corosync を載せる案です。

最初にまとめたとき、私はこの比較の軸を分散合意の有無だと書きました。読み返すと違いました。 三案を分けたのは合意ではなく、電源を落とす手段でした。

この記事の想定読者#

  • Instance HA をどの構成の上に載せるか決める方
  • DB Lock で重複実行を防いでいて、それで足りるのか気になる方
  • Pacemaker と Corosync がなぜ重い選択なのか、根拠が要る方
  • ④編を読んで、その手順の実行主体が気になった方

三案を分けたのは合意ではありませんでした#

設計書の最初の一文はこうでした。「DB Lock は Distributed Consensus ではないので Split-Brain を 構造的に防げない」。この一文は「では Galera の Quorum は」の一言で崩れます。Galera は wsrep グループ 通信の上で Primary Component を判定する自前の Quorum を持っています。

実際に Galera クラスタは Quorum を失うと non-Primary に落ち、その状態では Write を拒否します。 ShedLock はその Write の上に載っているので、Lock の取得も一緒に失敗します。 重複実行は防がれます。

防がれないのは別のほうです。二つのノードが同じ復旧を同時に走らせるのを止めることと、すでに 生きてディスクへ書いているノードを切り離すことは、別の仕事です。 Quorum はデータベースを守りますが、電源を落とすことはできません。

検知時間は各ソフトウェアの既定設定から取った値で、この環境で測った値では ありません。OpenStack の Masakari ドキュメントが説明する Instance HA 構成は、Pacemaker と Corosync を前提にしています。

三つのうち Pacemaker と Corosync を優先して推奨し、難しければ etcd を使おうと書きました。 Galera と ShedLock は暫定対応です。重複実行を防ぐところまではしますが、④編の原則を強制する手段が その中にないからです。

STONITH が失敗したら人が入ります#

Pacemaker を選んでも穴は残ります。Network Partition と STONITH の失敗が重なると、クラスタは freeze 状態に入ります。電源を落とせと送ったのに、落ちたかを確認できないので止まるのです。

この停止を解けるのは人だけです。手順を五段階で書いておきました。

# 1. 失敗を確認します
crm_mon -1

# 2. BMC コンソールで対象ノードが Power OFF かを目で確認します

# 3. 確認したあとにだけクラスタへ fencing を記録します
crm node fence <nodename>

# 4. ノードをクラスタに戻します
crm node online <nodename>

# 5. STONITH リソースを再起動します
crm resource restart stonith-<nodename>

三番目は二番目なしに実行してはいけません。crm node fence は電源を 落とす命令ではなく、落ちたとクラスタに伝える命令です。確認せずに記録すれば、④編で塞ごうとした 二重接続を人の手で開くことになります。

設定も二つ併せて推奨しました。stonith-action の既定値は再起動で、再起動は対象ノードが また上がってくる状態を作ります。電源が落ちたまま置くほうが、二重接続の余地を狭めます。

復旧を実行できるノードを一覧で絞りました#

Pacemaker をすぐに載せられない環境のために、運用レベルの仕掛けをもう一つ置きました。復旧を 実行できるノードを一覧で絞ることです。

# 既定値は reboot です。off へ変えることを推奨しました
stonith-timeout=60s
stonith-action=off

# 復旧を実行できるノードを一覧で制限します
EVACUATION_MANAGERS=("controller-a" "controller-b" "controller-c")

①編で見た事故は、孤立した Controller が自分を正常だと思うところから始まりました。その Controller が Leader に選ばれても、実行の一覧になければ復旧までは広がりません。

ただしこれは Fencing の代わりではありません。実行主体を減らして誤判定が広がる 範囲を狭めるだけで、すでに生きているノードを切り離すことは相変わらずできません。層が違う仕掛けなので、 同じ枠には置けません。

実装が選んだのは一つのロックでした#

三案のうち実際に作られたのは一つ目の案です。共用の保管所の一行を先に取ったノードがリーダーに なり、そのノードだけが復旧を実行します。合意の手続きはありません。

ロックには有効期限を置きます。リーダーは生きている間ずっと期限を延ばし、延ばせなくなると期限が 切れて他のノードがロックを取ります。リーダーが決まったら各ノードへ一度に知らせ、ノードごとに保管所へ 尋ねなくてよいようにしました。

横にスクロールすると残りが見えます

リーダー選出を作る四つの部分と、それぞれが止まったとき。
部分すること止まると
ロックを取る共用の保管所の一行を先に取った側がリーダーになる誰もリーダーになれず復旧が始まらない
有効期限の更新リーダーが生きている間、期限を延ばす期限が切れて他のノードがロックを取る
全体への公表誰がリーダーかを一度に知らせる各ノードが保管所へ個別に尋ねることになる
リーダーの健全性確認リーダー自身も判定の対象に入れる壊れたリーダーが席を握り続ける

四つのうち一つを抜くと残りが代わりをしてくれません。更新だけあって健全性の 確認がなければ、壊れたリーダーが期限だけ延ばして席を握ります。

この方式は共用の保管所が生きていることを前提にしています。保管所が分かれれば ロックも分かれ、両側がそれぞれのリーダーを持ちます。この記事が前半で述べたことがここでもそのまま 戻ってきます。リーダーを決めることと電源を落とすことは別の問題です。

限界: この記事が主張しないこと#

  • ⚠️ この連作の成果物は設計書です。私は三つの構成を比べて推奨しただけで、Pacemaker を導入したり 運用したりしたわけではありません。
  • 検知時間の三つの値は各ソフトウェアの既定設定から取ったもので、同じハードウェアで並べて測った 値ではありません。構成によって変わります。
  • Masakari との連携は、OpenStack のドキュメントがその構成を前提に説明しているという意味で、 ほかの構成が不可能という意味ではありません。
  • 実行ノードの一覧は運用上の仕掛けで、Fencing の代わりにはなりません。
  • 社内資料なので、製品名と顧客名とアドレスとアカウントとホスト名は書いていません。

おわりに#

この編の結論は一行です。合意は誰が実行するかを決め、Fencing は実行してよいかを決めます。 前者だけを備えた構成は重複実行を防ぎますが、二重接続は防げません。

表の一行に「合意方式」と書いていたあいだ、この違いは見えませんでした。層を分けてはじめて、 どの枠が空いているのかが表に出ました。

⑥編は、この構成で復旧にどれだけかかるのかを段階ごとに分けてみた話です。
