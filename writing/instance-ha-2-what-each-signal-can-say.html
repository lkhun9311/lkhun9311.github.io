Instance HA ②: Each Signal Can See Something Different
Instead of sharpening detection, we first decided what each signal can actually see. Second part of the series on the Instance HA failure-response design.

What part one showed was a controller reading its own isolation as the compute node's death. Hearing that story, most people reach for the same prescription first: make detection sharper. That was my first instinct too.

It does not work on this incident. When the observer is isolated, no amount of extra precision makes its observation trustworthy. Raising accuracy and asking what a signal can see are different jobs.

So the first decision in the design was not to touch the detector. It was to decide what each signal can actually see. This part is that tier list, and the six parameters of the EXT probe that we pushed to the bottom tier, each with a reason attached.

Who this is for#

  • Anyone designing a system that mixes several signals into one failure judgement
  • Anyone whose setup decides a node is alive from an external reachability check
  • Anyone who wants a recorded reason behind timeout and retry values
  • Anyone who read part one and wants to know what changed because of it

Sharper detection was not the answer#

The usual prescription is to shorten the probe interval or add more checks. Both raise the resolution of the observation. What went wrong in part one was not resolution. It was the observer's awareness of its own state. An isolated controller can poll as often as it likes and keep getting the same answer back.

So we changed the question. Not what to observe more closely, but which of the things already being observed can actually see what. That question has a different answer, because each signal is collected at a different point, and where it is collected decides what it can see.

We graded the signals into four tiers#

The four signal tiers and the role of each.
SignalTierWhat it can speak to
Agent HeartBeatHighestThe actual state of the Compute node
Controller QuorumHighWhether the controller cluster still agrees
Network HeartBeatMediumThe link between controller and compute
EXT ProbeLowThe controller's external reachability (possible isolation)

The ordering follows the collection point. The agent heartbeat runs on the compute node and is emitted by the node itself, so it speaks directly about the target. The EXT probe, by contrast, goes outward from the controller and never touches the compute node at all.

The EXT probe never looks at Compute#

That sentence is the core of this part. The EXT probe confirms reachability from the controller to an outside address and nothing else. Judging whether a compute node is up from that result reproduces exactly the mistake from part one: reading the observer's isolation as the target's failure.

So we did not remove the EXT probe. We kept it and changed its job. It no longer answers "is that node dead". It answers "am I in a position to judge right now". The same check stays in place and only the question changes.

Six values, each with a reason#

Once the role is fixed, the values remain: how often to probe and how many failures should be promoted to a judgement. We set six, and wrote down why each is what it is.

The six EXT probe parameters and their reasons.
ParameterValueReason
probe directioncontroller outwardConfirms the controller's external reachability, not the compute node
probe interval10sKept in step with the heartbeat period
consecutive failures3Keeps one or two jitter-induced failures from becoming a judgement
judgement TTL30sInterval of 10s times three
minimum EXT addresses3 or moreTwo can still fail together
judgement threshold2 of 3 failingA single failure may belong to that address alone

The build used OR rather than grades#

That was the design. Reading the build, the verdict works differently. Rather than grading the signals, every condition is combined with OR and any one of them makes it a failure.

The agent on the node looks at four things: no status request arriving from the control side for a set time, the configured gateway not answering, an unreachable VIP, and a configured network interface that is down or is a loopback.

The third of those changed once. Sites where the ping to the gateway is blocked outright turned out to be common, and the ping alone could not reach a verdict there. A TCP check against a configured address and port was added for exactly that. Where ping cannot be used the value is left empty and only the TCP connection is checked.

In a redundant setup each kind is checked differently. One thing caught here: without telling the kinds apart, a break on the service side cannot be separated from a break on the management side. An external review raised exactly that, and it stays an open item outside the scope of this series.

Why ten seconds and why three times#

The three values are not independent. Fix the interval and the count, and the TTL follows by multiplication. So if you want recovery to start sooner you have to shrink one of them, and that tilts the design toward letting a single hiccup stand as a judgement. That is why the way to shorten it and the price of shortening it are written down together.

Requiring three or more addresses and two failures among them has the same shape. With one address you cannot separate that address failing from your own isolation, and with two there is still the case where both die together. The design is not in the numbers. It is in what each number is trying to tell apart.

Limits: what this post does not claim#

  • ⚠️ What this series produced is a design document. Implementation was picked up by another engineer, and how these values were tuned in operation is outside this post.
  • The six values are proposals rather than numbers tuned against measurement. They were derived backwards from the situations they need to tell apart, not chosen by running load.
  • The tier list comes from this product's signal set. Where no agent exists the top row is empty, so the table does not transfer unchanged.
  • This is internal material. Product names, customers, addresses and accounts are not used.

Closing#

One line carries this part. Raising detection accuracy and deciding what a signal can see are different jobs. An isolated observer is wrong precisely when it looks carefully, and a signal with a defined scope can tell you that you are not the one who should be judging.
