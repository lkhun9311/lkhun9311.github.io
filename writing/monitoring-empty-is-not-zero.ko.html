빈 목록이 노드가 0대인지 조회가 실패한 것인지 구분하지 못했습니다
대상이 없어서 빈 것과 못 가져와서 빈 것이 같은 모양으로 옵니다.

2026년 9월

목차

  • 같은 패턴, 다른 질문

  • 이 글이 주장하지 않는 것
  • 마치며

사내 Cloud 관리 Console의 Backend를 만들고 있습니다. ②편에서 대시보드의 계산을 요청 경로 밖으로 옮겼습니다. 같은 패턴을 물리 노드 화면에 그대로 옮기면 될 것 같았습니다.

옮기다가 질문 하나에서 멈췄습니다. 메트릭 쿼리가 빈 목록을 돌려줬을 때, 그것을 ‘노드 0대’로 발행해도 되는가.

안 됩니다. 진짜로 대상이 없어서 빈 것일 수도 있고 수집이 실패해서 빈 것일 수도 있습니다. 둘을 안 가르면 장애가 난 순간에 멀쩡하던 화면을 0대로 덮습니다.

그래서 ‘비었다’를 다섯 갈래로 갈랐습니다. ‘정상 수집’과 ‘대상이 정말 0대’ 둘만 새 값으로 발행하고 나머지 셋에서는 마지막 정상값을 그대로 둡니다. 그리고 값과 수집 상태를 따로 실어 보냅니다. 그래야 ‘마지막 값은 보여 주되 지금 수집은 실패했다’는 화면이 만들어집니다. 첫 데이터가 오는 시각의 중앙값은 3,938ms에서 23ms로 줄었습니다.

이 글의 예상 독자#

  • 마지막 값을 보여 주는 화면(last-known-good)을 만들려는 분
  • ‘결과가 비었다’를 정상으로 쓸지 실패로 쓸지 정해야 하는 분
  • 장애일 때 거짓 0 · 빈 화면 · 무한 로딩 중 무엇을 피할지 골라야 하는 분

같은 패턴, 다른 질문#

구조는 대시보드와 같습니다. 뒤에서 도는 Worker가 15s마다 완성 스냅샷을 만들고 새 접속에는 마지막 값을 즉시 보냅니다. 개선 전 첫 데이터는 이랬습니다.

대시보드보다 계산 범위는 작았는데 사용자가 보는 지연은 여전히 초 단위였습니다.

그런데 물리 노드에는 대시보드에 없던 성질이 있습니다. 노드는 ‘지금 몇 대인가’ 자체가 화면의 내용입니다. 그래서 ‘빈 결과’가 곧 ‘0대’로 읽힙니다.

‘비었다’에는 뜻이 다섯 개 있었습니다#

새로 수집한 것이 비었다고 무조건 발행하지 않았습니다. 인프라 구조를 읽을 수 있었는지, 메트릭 가져오기가 성공했는지, 기대한 대상 수와 매칭된 표본 수가 몇인지를 같이 봤습니다.

if 인프라 구조를 못 읽었다:        INFRA_UNAVAILABLE
else if 메트릭 가져오기 실패:      FETCH_FAILED
else if 매칭된 표본 수 > 0:        FRESH
else if 기대한 대상 수 == 0:       EMPTY_VALID
else:                              NO_VALID_METRICS

갈라 놓고 보면 규칙은 간단합니다. FRESH와 EMPTY_VALID는 새 값으로 발행합니다. 나머지 셋은 마지막 정상값을 그대로 두고 저하 상태와 실패 시각만 갱신합니다.

값의 세대와 마지막 시도 결과를 갈라 놓는 것이 요점입니다. 그래야 오래된 데이터를 새 데이터인 척하지 않으면서도 화면을 비우지 않습니다.

도착 순서도 데이터입니다#

접속 직후 Cache된 값이 나가고 거의 동시에 새 방송이 도착할 수 있습니다. 비동기 리스너의 실행 순서는 보장되지 않으므로 더 오래된 응답이 새 방송보다 늦게 도착할 수 있습니다. 그러면 화면이 뒤로 갑니다.

여기서 HH:mm:ss 문자열을 차트 키로 쓰는 것으로는 모자랍니다. 같은 초에 두 세대가 만들어질 수 있고 프로세스가 재기동하면 시계가 되감길 수도 있습니다. 표시용 시각, 정렬용 세대 번호, 실행 간격용 단조 증가 시간을 서로 다른 값으로 뒀습니다.

값과 신뢰도를 따로 그립니다#

마지막 정상값을 보여 주는 동안 사용자가 그것을 최신으로 오해하면 안 됩니다. 그래서 Payload에 이 넷을 따로 실었습니다.

  • 데이터와 그 데이터가 만들어진 시각
  • 마지막 수집 시도의 상태와 시각
  • 이전 값을 이어서 쓰고 있는지 나타내는 저하 표시
  • 연결 수명 안에서 순서를 판정할 세대 번호

프런트엔드는 저하 표시가 켜져 있으면 기존 값을 유지하고 오래됐다는 것을 같이 보여 줍니다. 저하 표시가 꺼져 있으면서 결과가 빈 경우에만 진짜 0대로 그립니다. 이 구분이 없으면 ‘장애를 0으로 표시’와 ‘정상인 0을 과거 값으로 가림’ 중 하나는 반드시 일어납니다.

‘개선 후’는 ⑤편의 공유 Cache까지 들어간 상태에서 잰 값입니다. 이 편의 변경만으로 잰 값이 아닙니다. 개별 화면 개선 직후에도 수십 ms 범위였지만 그 시점의 표는 따로 남기지 않았습니다.

이 글이 주장하지 않는 것#

  • 이 편에는 제가 처음에 못 한 것이 들어 있습니다. 물리 노드 구현에서는 이 다섯 갈래가 완전하지 않았습니다. ‘가져오기는 성공했는데 결과가 빈 경우’를 정상으로 볼 여지가 남아 있었고 그것을 ⑤편의 공유 Cache 작업에서야 공통 판정으로 끌어올렸습니다.
  • 사내 제품이라 코드와 화면을 그대로 옮기지 않았습니다. 제품명·고객사·내부 주소는 빼고 구조와 판정 규칙만 남겼습니다.
  • 운영 통계가 아닙니다. 첫 데이터 지연을 보는 순차 Harness이고 동시 사용자 부하 테스트가 아닙니다.
  • 이 편의 기여분만 재지 않았습니다. 표의 ‘개선 후’에는 ⑤편의 공유 Cache가 같이 들어 있습니다.
  • 이 다섯 갈래가 처음부터 완전했다고 말하지 않습니다. 물리 노드 구현 시점에는 ‘가져오기 성공 + 빈 결과’를 정상으로 볼 여지가 남아 있었고 ⑤편에서야 공통 판정으로 끌어올렸습니다.
  • last-known-good이 항상 옳다는 말이 아닙니다. 데이터의 나이를 감추면 가용성을 높이는 대신 거짓말을 오래 하게 됩니다.

마치며#

  • ‘비었다’는 관측이 아니라 해석이 필요한 값입니다. 대상이 없어서 빈 것과 못 가져와서 빈 것은 같은 자료구조로 옵니다.
  • 값과 수집 상태를 갈라 놓아야 정직한 화면이 됩니다. ‘마지막 값은 보여 주되 지금 수집은 실패했다’는 둘을 합쳐 놓으면 쓸 수 없는 문장입니다.
  • 도착 순서로 최신을 판정하면 화면이 뒤로 갑니다. 만든 순서를 값에 실어야 합니다.

모니터링 화면이 정해야 하는 것은 최신 숫자가 아니라, 관측이 실패했을 때 거짓 0과 빈 화면과 무한 로딩 중 무엇을 피할 것인가입니다.

다음 편은 가상자원입니다. 이 화면은 병목이 하나가 아니라 둘이었습니다. 읽어 주셔서 감사합니다.
