Instance HA ③: We Split Failure Detection from Execution Readiness
Two questions of different kinds had been tangled into one verdict. Separated, eight failure scenarios produced exactly one case where recovery was allowed to run.

Part two decided what each signal is entitled to say. Grading them is not yet a verdict, though. When a high-standing signal reports that all is well, what you are then allowed to do is still open.

This was the part of the design document I spent longest on. The existing verdict had two questions of different kinds welded into one: has it really failed, and may recovery run right now. They are answered at different moments on different evidence, and they were being decided in a single line.

This part is about splitting them into Phase 1 and Phase 2. Once split, judging eight failure scenarios against the same criteria left exactly one where recovery was allowed to run.

Who this is for#

  • Anyone designing or revising the conditions behind automatic recovery
  • Anyone who has seen a storage or message-queue fault read as a node fault
  • Anyone weighing whether to record decision logic as a table or as code
  • Anyone who read part two and wants to see the tiers become an actual verdict

Two questions were tangled into one verdict#

One case shows what tangling costs. The Compute is perfectly healthy but cannot reach storage. The old verdict took that as a failure signal and promoted it to a recovery target. Yet moving a VM while storage is unreachable means it cannot write its disk at the destination either.

So the two were separated. The first asks only whether the target is alive; the second asks only whether acting is possible. The split had one immediate effect: moving the storage condition to the back closed the path by which a storage fault contaminated the failure verdict.

Phase 2 asks only whether we may act#

ConditionWhy it is checked
Storage reachableThe evacuated VM has to be able to write its disk
RabbitMQ healthyThe recovery command has to be deliverable
Nova API healthyThe recovery has to be callable

None of the three says anything about whether the target is alive. All of them ask whether this is a state in which recovery can be carried out. If one fails, nothing runs even when the failure itself is confirmed.

The order is pinned in code#

Left as tables alone, every reader reconstructs a different order. So the design document wrote the order out as pseudocode. Its point is that there is exactly one way out.

[Phase 1 - did it fail]
1. Check quorum
   quorum lost -> the verdict cannot be trusted -> Hold

2. Check the agent heartbeat
   within TTL -> the Compute is up -> Hold

3. If the TTL expired, check further
   EXT probe result - nova-compute state - storage session
   if certainty is missing -> Hold (notify an operator)

[Phase 2 - may we act now]
1. Storage unreachable -> Hold
2. RabbitMQ unhealthy  -> Hold
3. Nova API unhealthy  -> Hold
4. all clear           -> proceed to fencing

Seven of eight stop#

Eight failure scenarios were judged against these criteria. The result was one fencing and seven holds.

Seven holds does not mean seven were wrong. It means the signals in hand do not support saying that recovery may run. A wrongly executed recovery cannot be undone, while a hold leaves time for a human to step in.

Limits: what this post does not claim#

  • ⚠️ What this series produced is a design document. Implementation was picked up by another engineer. This is not "the misjudgement went away" but a proposed design that closes the path to it.
  • The matrix has gaps. The signal tiers include a network heartbeat, yet neither the combined logic nor the matrix has a column for it, and of the three Phase 2 conditions only storage appears. That is an incompleteness in the design document itself.
  • Two rows carry identical inputs. "Controller network cut" and "controller cut yet heartbeat arriving" are written with the same values, so the table cannot express what separates them.
  • This is internal material. Product names, customers, addresses and accounts are not used.

Closing#

One line carries this part. Put two questions of different kinds into one verdict and you get both of them wrong. Split, the path by which a storage fault read as a compute fault closed, and seven of eight holding stopped looking like a strange result.
