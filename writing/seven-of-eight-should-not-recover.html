Seven of Eight Node HA Scenarios Should Not Recover
A switch died, healthy compute nodes were judged down, and recovery ran in bulk.

In March 2026 I redesigned instance-HA failure handling for an OpenStack-based private cloud product. The incident is one sentence. An L2/L3 switch failed, compute nodes that were running perfectly well were judged dead, and recovery ran at scale.

Recovery here means a Nova evacuate — bringing the same VM up on another node. If the original is still alive when the copy attaches to the same volume, both write to it. This is the case where automatic recovery costs more than the failure.

Detection had not failed. The compute nodes were still saying “I am alive”. What had failed was that nobody had decided whose word to believe. So instead of making detection sharper, I decided first what each signal is entitled to testify to. Judged against that, exactly one of eight scenarios was safe to recover.

Who this is for#

  • You run automatic recovery that restarts VMs elsewhere when a node dies
  • You have written "detection was inaccurate" as a root cause
  • You have to decide when recovery should not run

The observer's isolation was read as the subject's failure#

Flatten a switch failure into "the network went down" and this incident is impossible to understand. The product runs several networks with different jobs, and during the failure each of them was in a different state.

When controllers cannot reach each other, quorum collapses, and some controller decides on its own that a compute node is dead. Meanwhile MGMT was up, so that compute node's agent heartbeat was arriving normally the whole time.

Two contradictory statements existed in the system simultaneously. The compute node was saying "I am alive." An isolated controller concluded "it is dead." The existing logic took the second one.

Call that a detection failure and the prescription comes out wrong. Detection did not fail — the heartbeat arrived. What failed was that nobody had decided whose word counts.

Not accuracy — entitlement#

Four signals were given a confidence grade and, more importantly, a role.

The four signals, their confidence, and what each can testify to.
signalconfidencewhat it can testify to
agent heartbeathighestthe compute node's actual state
controller quorumhighwhether the controller cluster can agree at all
network heartbeatmediumconnectivity between controller and compute
external reachability probelowwhether the controller is isolated

The last row is the whole design. The external probe only checks reachability outward from the controller. It never verifies the compute node. Judge a compute node's liveness with it and you read the observer's isolation as the subject's failure. That is precisely what happened.

So the principle was written down: only the compute node can say whether the compute node is alive. Every other signal either corroborates that statement, or explains why the statement did not arrive.

"Is it broken" and "is it safe to act" are different questions#

The old judgement mixed two kinds of condition: has a failure actually occurred, and is it safe to run recovery right now. Put both in one decision and they contaminate each other.

They were split.

[Phase 1 — failure detection]
1. Check quorum
   Controller quorum lost → the judgement cannot be trusted → HOLD

2. Check agent heartbeat
   TTL healthy (within 30s) → compute is alive → HOLD

3. TTL exceeded → additional checks
   external probe result / nova-compute service state / storage session state
   → if the judgement still cannot be trusted → HOLD (notify an operator)

[Phase 2 — execution readiness]
1. Storage unreachable → HOLD  (the evacuated VM could not attach anyway)
2. Message queue unhealthy → HOLD  (the command would not arrive)
3. Nova API unhealthy → HOLD  (the call itself would fail)
4. All clear → fence

The default is HOLD. When it cannot be sure, it does nothing.

The split immediately removed one class of misjudgement: reading a storage-path failure as a compute failure. Storage conditions live in Phase 2, so they never pollute detection. Losing sight of storage is not evidence that the compute node died; it is evidence that now is not the time to recover.

Seven of eight#

Eight scenarios that can actually occur were then judged one at a time.

The bottom row is the incident. Its action is now HOLD.

Seven of eight comes out of an asymmetry in cost. Skip a recovery and the service stays down while a human gets time to intervene. Run a recovery wrongly and the original and the copy write to the same volume, which cannot be undone. When the two mistakes are not worth the same, the decision boundary should not sit in the middle.

The obvious objection: "if seven of eight hold, doesn't real recovery get slower?" It does. Slower is the price this design chose to pay. In exchange, HOLD is not a state where nothing happens — it raises an operator alert. Automation gives up the decision and hands it to a person; it does not drop it.

No fencing, no recovery — and the five seconds#

Even in the one scenario where recovery is allowed, you have to confirm the original is definitely powered off before moving anything. Skip that and you get this.

Compute-01 → VM-A still running   → writes /dev/vdb   (original attachment held)
Compute-02 → VM-A evacuated       → writes /dev/vdb   (new attachment)

Two writers on one block device corrupts the filesystem — and how badly depends on the storage type.

scroll sideways for the rest

Concurrent-write risk by storage type.
storagerisk
iSCSISCSI-3 PR exists, but new access arriving before the original attachment is torn down can still collide
LVMno SCSI PR. Concurrent writes carry a high risk of VG/LV metadata corruption
NFSfile-lock based, so consistency cannot be guaranteed under concurrent mount and write

Hence the principle: no fencing, no recovery. Four stages — detect, verify, fence, recover. The fencing stage on its own reads:

1. IPMI chassis power off
2. wait at least 5s               ← do not query immediately
3. IPMI power status → must read off
4. confirm residual storage attachments are cleared (varies by type)
5. run the recovery

Step 2 exists for a plain reason. Query the power state right after cutting it and it is not off yet. Without the wait, the check reads "not off" and is taken as a fencing failure — or waved through optimistically. Five seconds is the floor; the ceiling is a separate fencing timeout.

And one precondition invalidates the entire procedure. Fencing goes over IPMI, so if the BMC sits on the same physical switch as MGMT, the switch failure takes IPMI down with it. Fencing becomes impossible at exactly the moment fencing is needed.

Whether fencing survives a switch failure, by BMC network topology.
topologyduring a switch failureresult
BMC and MGMT on the same physical switchMGMT and IPMI cut togetherfencing impossible
BMC separated by VLAN onlythe switch dies and the VLANs on it go with itfencing unreliable
BMC on a dedicated physical switchMGMT cut, IPMI survivesfencing possible

A VLAN is not enough. When the switch itself dies, every VLAN on it disappears. At the time of the incident there was no BMC network at all. So this was written not as a section of the design but as a precondition: without it, even the one recoverable cell of the matrix cannot be executed.

A DB lock is not distributed consensus#

With the decision procedure settled, the remaining question was who executes it and where. Galera was already in house, so there was momentum behind putting a DB lock (ShedLock) on top of it. Three approaches were compared on the same axes.

The first row decided it. A DB lock is not distributed consensus. A lock reduces duplicate execution, but under a network partition it does not stop both sides from each taking their own lock. The entire point of this work was preventing split-brain; an option that cannot prevent it structurally does not achieve the goal, however cheap it is. It stayed on the table as a stopgap.

The primary recommendation was Pacemaker + Corosync, and not because of detection time. STONITH is built in, so "no fencing, no recovery" is enforced by the structure rather than by everyone remembering it. etcd was the fallback if the operational cost proved too high.

That has its own objection: "Pacemaker freezes the minority side of a partition — doesn't the service stop?" It does. That is an intended safe failure. Stopping and calling a human beats moving without certainty, which is the posture of the whole design, so the execution layer was chosen with the same posture.

What this does not claim#

  • The deliverable was a design document; another engineer took the implementation. So there is no “this shipped and misjudgements fell by N” measurement here. What there is is a decision procedure, and the result of running every scenario through it. I do not name the product, its version, the customer, or ticket numbers.
  • Not a claim that I implemented it. My scope ended at the design document; another engineer took the implementation.
  • There is no after-measurement. I do not have a number for how many misjudgements this removed. What exists is a verdict for eight scenarios, not a record of those verdicts being confirmed in the field.
  • The logic that misjudged was not mine. The existing recovery logic misjudged; the decision procedure came afterwards.
  • The "at least 5s" in the fencing procedure is also not a measurement. It is the floor the design recommends; the distribution of how long power actually takes to drop on this hardware was never measured.
  • ~5s / ~10s / ~30s are general properties of each approach, not measurements taken in this environment. The rest of that comparison is likewise a reading of documentation and standards, not a benchmark.
  • The recovery time objective was an estimate. The design carries a staged calculation, but it was never measured and remained pending team agreement, which is why no such number appears in this article.
  • Eight is not every case. They are the combinations observed or foreseeable at design time; anything else falls through to the default, which is HOLD — the second reason the default is HOLD.

Wrapping up#

  • Do not read the observer's isolation as the subject's failure. Only the compute node can testify that the compute node is alive.
  • "Is this a failure?" and "is it safe to act now?" are different questions. Put them in one verdict and they contaminate each other.
  • No fencing, no recovery. You may start the copy only after the original is definitely off.
  • The default is HOLD. That puts a person where the automation was, which is not the same as doing nothing.

In a high-availability system the hard part is not the code that performs recovery; it is the judgement that declines to. And that judgement does not come from sharper detection. It comes from first deciding which signal is entitled to testify to what.
