The Bugs That Return Exit Code 0

Writing · Aug 2026

Over one week of work on a Kubernetes GPU control plane I found ten defects. Not one of them failed a test, crashed a process, or returned a non-zero exit code. Every single one was found by reading a result that looked fine.

This post is about that class of bug, and about the three habits that turned out to catch them. All the numbers below are measured on a local kind cluster with simulated GPU capacity — I say what that does and does not prove at the end.

The one that would have gone on a résumé

I built a chaos experiment for FR-002: delete the pod behind a model backend, and measure how long the gateway takes to recover. It printed this:

first error   49.1ms after the delete
recovered   3079.8ms after the delete
gateway 5xx: 9      client failures: 9

Nine and nine. I wrote it up as the headline result — every failure the client experienced appears in the gateway's own counters — because that agreement is the thing that actually matters. An on-call engineer sees the counters, not the client. A gateway whose metrics stay clean through an outage its users felt is a worse problem than the outage.

It was a coincidence.

gpuaas_gateway_requests_total is cumulative. The harness read the value after the run and compared that absolute number against one run's client failures. They happened to match once. I only found out because I had written "this experiment is n=1" in a validity table and then went back to close that gap:

run 1:  counter = 15
run 2:  counter = 23
run 3:  counter = 31      ← climbing, while every run saw 9 failures

The comparison had never been a comparison. Two corrections followed. The harness now records the counter before and after and compares the delta. And a client failure with curl code 000 — no HTTP response at all, its own timeout or a refused connection — is excluded from what the gateway must account for, because demanding that a proxy count a request that never reached it is an impossible standard. That exclusion was the whole of the residual discrepancy.

Three corrected runs, agreeing exactly:

The lesson is not "check your metrics". It is that a single run cannot test an agreement between two observers, because coincidence and correctness look identical at n=1.

Habit 1 — put the instrument's resolution in the artifact

The same experiment claimed a precision it did not have. The record said:

"samplingIntervalMs": 100        ← a constant, written by hand
"clientView": { "sampled": 3 }   ← 3 samples across 5.3 seconds

A failing request blocks for its timeout. The timeout was 5 seconds. So the sampling interval widens exactly when things break — 100ms while healthy, seconds while broken. The resolution is worst precisely where the measurement matters.

Now the harness measures its own interval every run and writes it down. Any latency at or under that interval is reported as a bound rather than a number:

"samplingIntervalMs": 419.4,
"latenciesMs": { "killToRecovery": 1294.6 }   ← ± one sample, stated

A sibling experiment (FR-004, node degradation) had the same defect from the opposite direction — there the resolution was recorded, and the record caught a half-finished fix on its own:

"harnessResolutionMs": 95.9,
"readyToUntaint": 37.9        ← smaller than the resolution that produced it

Nothing failed. The document simply contradicted itself in a way a reader could see, because the judgement criterion sat next to the measurement. Had the harness reported only latencies, 37.9ms would have looked like the best number in the run.

Measure the instrument every run and put the number in the artifact. A constant cannot contradict the data beside it.

Habit 2 — assert the reason, not just the outcome

I built an admission webhook and wanted to know whether the apiserver was really calling it, so I installed the real manifest into envtest and mutated it three ways.

mutationwhat went red
drop UPDATE from operationsonly the edit test — the edit was stored
point resources at another kindrejection tests: "the webhook was not consulted"
misspell clientConfig.pathcorrected a prediction of mine

I predicted the third would leave the rejection tests passing. Because failurePolicy is Fail, a 404 from a wrong path becomes a rejection — so a completely broken webhook still refuses writes, and a suite made only of rejection cases would score it full marks.

It did not pass. The tests assert why a write was refused, not merely that it was, and a 404 does not mention spec.image:

rejected for something other than the image:
  failed calling webhook "vmltrainingjob.kb.io": the server could not find the requested resource

Asserting the reason turned out to be a tighter net than the control case I had built for exactly this purpose.

The end-to-end admission tests

The same webhook could make objects undeletable

Worth including because it is my own defect, and because of how it fails. The validator refuses to intercept DELETE, and its comment says why: a webhook able to refuse one could strand an object nobody can remove.

The reasoning was right. The guard was on the wrong verb. A finalizer comes off with an ordinary UPDATE, so an object whose spec the validator rejects — an empty image on something created before the rule existed — could never complete the update that ends its deletion.

And it is silent. kubectl delete succeeds; it only stamps a timestamp. The object then sits in Terminating with no error anywhere until somebody notices it never went away.

Habit 3 — ask what the test environment cannot see

The controller's scalability had never been measured. Before writing a benchmark I asked why, and the answer was the actual cause: the test suite built its reconciler with an uncached client, while production hands it the manager's cached one.

Whether a List consults an index or walks the store, and how that grows with object count, are properties of the cache alone. To a read-through client those questions do not even exist. It was not that scalability had never been measured — it could not have been.

A benchmark standing up its own informer cache found the lookup was O(N) on the path every job takes on the way in:

workloadsbeforeafter
100116,602 ns/op1,292 ns/op
500485,338 ns/op1,423 ns/op
20001,644,429 ns/op1,094 ns/op

With MaxConcurrentReconciles at its default of 1 for every reconciler, a per-item cost proportional to namespace size drains the queue in O(N²).

The fix folds both claims a Workload can carry — the job-uid label and its owner references — into one field index, so a single indexed List replaces a full label walk plus a full namespace list.

The ratio is weaker evidence than the ordering

A 1503× speedup only says "something got faster" — a warm cache says that too. What it cannot explain is this: before the fix a miss cost about 20× a hit; after it, a miss is cheaper.

A scan walks the whole store either way, so a miss can never come in under a hit. An index can: the miss returns nothing to copy while the hit deep-copies the one object it matched. The inversion is what proves the index is consulted.

Evidence for a performance fix should be a change in shape, not a ratio.

What the dashboard is for

The operator and gateway export seventeen metrics. They had never been scraped — and pointing a Prometheus at them found that the operator was serving none of them.

A kustomize overlay I had written patched the manager's args with a strategic merge. containers[].args is a list of plain strings with no merge key, so a strategic merge replaces it. The patch deleted --metrics-bind-address.

Everything looked healthy: kustomize built, apply succeeded, the Deployment rolled out, the webhook worked, and a live webhook verification passed 6/6 — none of which touch the metrics port.

Two panels were wrong on first render, and both are worth naming. The error stat read 2.26 — increase() extrapolates across scrape boundaries, so counting discrete events with it yields fractions, and a displayed value that cannot be true undermines every other number on the page. And the failed-jobs stat read No data where the answer was zero; those are different facts, and only one of them is good news.

A dashboard fails quietly by design: a panel querying a metric that does not exist renders an empty graph, and empty reads as no traffic — the most reassuring thing a dashboard can say. So the repository checks panels two ways: every expression must parse as PromQL, and every metric it names must exist in the Go source. Only the second catches a rename.

Ten defects, ten exit codes of zero. Nine were caught by reading a result directly — adding numbers up, comparing names to names, reading a log, asking git show HEAD:<path>. Exactly one was caught by tooling: the run record that contradicted itself, because the resolution was stored beside the measurements.

That ratio is the actual finding. Tooling caught one in ten. The other nine needed somebody to look at the answer and ask whether it could be true.

What this does and does not establish

Every number here was measured on a three-node kind cluster against simulated nvidia.com/gpu capacity. No GPU in this project is real.

FR-004 detection 34.6–36.9smeasured — but it is Kubernetes' number, not the platform's
Controller reaction to a degraded nodenot measured — below the harness resolution, bound only

The chaos runs measure control-plane reaction, not device behaviour. The backend is a stub, not vLLM. And two of the ten defects above were found by external code review, which is its own argument for having one.
