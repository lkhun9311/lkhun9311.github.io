Adding Threads Made the Tail Longer

Sep 2026

Scope. In May 2026 I fixed the volume list screen of an OpenStack-based private cloud management console. I do not name the product, its version, or any customer. Every number below was measured with JMeter in an internal test environment, not against production traffic. The load profile is identical across all six configurations — 50 concurrent users, 2-minute ramp-up, 10-minute duration, 2–5s think time. Code is quoted from the real source with internal identifiers removed.

The screen degraded linearly as volumes accumulated and eventually died on a 10-minute timeout. The cause was a loop calling an external API once per volume, sequentially, and the prescription looked obvious. Run it in parallel.

Running it in parallel made it slower. Holding the cache setting fixed and switching sequential to parallel took p99 from 42.6s to 79.0s. This is about what that one cell told me, and about the test design that made the cell visible at all.

Six rows#

Land every fix at once, measure before and after, and one fact survives: it got faster. Which change bought how much of that is gone. So I split the configuration into six steps and measured each one under identical conditions.

Units are milliseconds. The 600,017 in row ① is not a measurement — it is the 10-minute timeout ceiling, and 83.3% of that configuration's requests never finished. The latency of a request that never finished is not "600 seconds"; it is unknown, and that cell has to be read that way.

③ being worse than ② is what catches the eye first: 42.6s against 129.9s. But those two rows are not controls for each other — ② is a 5s cache and sequential, ③ is no cache and parallel, so two variables change at once. Nothing about parallelism alone can be separated out of that difference.

The pair that holds the cache fixed is ② and ④. Both run a 5s cache; only sequential versus parallel differs.

p99 rose from 42.6s to 79.0s. More threads, a tail 1.85 times longer. That is the whole of what this experiment can say about parallelism on its own, and the direction is not in doubt — it was harmful.

Why ③ is worse than ②#

The parallel code looked like this.

final Map<String, VolumeGroup> groupCache = new ConcurrentHashMap<>();

final List<VolumeDto> dtos = volumes.stream()
    .map(volume -> CompletableFuture.supplyAsync(() -> {

        // many threads enter this block at once
        final VolumeGroup group = groupCache.computeIfAbsent(
            volume.getGroupId(),
            gid -> client.groups().get(gid)   // ← external I/O inside the lock
        );
        ...
    }, executor))
    .map(CompletableFuture::join)
    .collect(Collectors.toList());

It is easy to read ConcurrentHashMap and conclude this is safe. It is safe. The question is not safety but what the safety is bought with.

computeIfAbsent runs the mapping function while holding the bin that the key hashes to. If the mapping function reads a map and returns, that window is nanoseconds. Here it performs a network round trip inside it.

So: if M volumes belong to the same group, M threads from the executor arrive at computeIfAbsent with the same key. One makes the external call; the other M−1 queue behind that bin. What used to be a queue in sequential code is still a queue in parallel code, and now it pins pool threads while it waits. The gain is nothing; the added cost is context switching and pool exhaustion.

That is why ③ is worse than ②. In ②, the 5-second cache kept the number of external calls low. In ③, with no cache, every request had to pass through the held bin.

One term. Documents often call this a "segment lock". Segments are Java 7 vocabulary. Since Java 8, ConcurrentHashMap has no segments and locks at bin granularity. The lock got narrower; the fact that the bin is held for as long as the mapping function runs did not change. A narrower lock is not a licence to do I/O inside it.

The fix is to stop hand-rolling the lock. Caffeine's LoadingCache guarantees that on a miss the loader runs exactly once per key while the other callers wait for its result. Same "call it once" guarantee, except the waiters are not holding a bin of the map.

The second defect: absence was never cached#

Another path on the same screen had a second hand-written cache.

public static List<Message> messages(final String resourceId) {
    CacheManager manager = CacheManager.getInstance().init(Message.class, 10);
    final List<Message> cached = manager.list(Message.class);

    if (cached == null || cached.isEmpty()) {              // ← many threads pass this at once
        client.messages().list(...)
              .forEach(r -> manager.set(Message.class, r.getResourceUuid(), r));
    }
    ...
}

Two defects, stacked.

One. When N parallel threads clear the isEmpty() check together, all N call the external API. An ordinary cache stampede.

Two. If the lookup returns zero rows, forEach never runs, so nothing is written to the cache. The next request sees an empty cache and calls again. Absence was never cached. And on this path zero rows was the common answer — meaning the cache did nothing at all in the most frequent case.

The prescription is the same. Caffeine caches an empty list as a value like any other, so the data structure distinguishes "the answer is nothing" from "nobody has asked yet". The hand-written cache collapsed both into one isEmpty().

The two defects differ in kind. The first is correct but slow. The second makes you believe there is a cache. The second survived longer for an obvious reason: there was a cache in the code, and nobody ever counted whether it was being filled.

Which fix actually mattered#

Read the six rows as adjacent pairs and each change separates out.

The last step was the largest as a ratio — 6.9s to 23ms, about 300x. In absolute terms ④→⑤ is larger (a fall of roughly 72.1s against roughly 6.84s). Both are true, and which one you call "largest" is decided by the scale you pick. Either way it was the last change added, so a before-and-after would have credited it to the four ahead of it.

Why is ⑤→⑥ that large? Up to ⑤, a request that finds an expired entry waits for it to be refilled. Caffeine's refresh keeps serving the previous value at expiry and reloads in the background. What the last step removed was not lookup cost but time spent waiting for a refresh — and that was most of the tail.

What a before-and-after would have reported#

Measure only ① and ⑥ and the report writes itself. "Applying caching and parallelism reduced the error rate from 83.3% to 0% and p99 from 10 minutes to 23ms."

Every number in that sentence is true. The implication that parallelism contributed is false. On its own it was harmful — with the cache held fixed, parallel was still worse than sequential, so this experiment shows no positive contribution from parallelism at all. Not knowing that, the obvious next move — "let's parallelise this other screen too" — walks straight back into the same trap.

The table also did diagnostic work. Parallelising with the cache held fixed being worse says the bottleneck is not CPU or throughput but a serialisation point. That is what sent me looking for a lock, and the external call inside computeIfAbsent is what came back. The table pointed at the code.

Two objections worth answering up front.

"Why not just enlarge the thread pool?" — When the bottleneck is a lock, more threads only add more waiters. ② ↔ ④ is exactly that experiment: at the same cache setting, parallel was slower than sequential.

"A 4ms median is just a cache hit, isn't it?" — Yes. That is why the median is not read alone. On the same row p99 is 23ms and Apdex is 1.000. Apdex weighs satisfied, tolerating and frustrated counts, so it reads the distribution rather than the middle — though the printed 1.000 does not by itself prove the whole sample (see the caveats).

What this does not claim#

  • Not that parallelism is bad. Parallelising code that does I/O inside a lock is bad. But none of these six configurations removes that condition while staying parallel, so whether parallelism pays once it is removed is not something this experiment shows. ③→④ changes only the cache and does not answer it.
  • Not a production measurement. Synthetic load in an internal test environment. Real user distribution, data volume and network differ.
  • ② and ③ are not controls for each other. Cache and execution mode change together, so their difference (42.6s → 129.9s) cannot be attributed to either. The only evidence this article uses for parallelism alone is ② → ④, with the cache held fixed.
  • An Apdex of 1.000 does not prove the whole sample was inside the satisfied threshold. If the tool rounds to three decimal places, a small number of tolerating samples still displays as 1.000. The unrounded value was not checked.
  • One run per configuration. There is no repeated measurement and therefore no variance estimate, so where two adjacent configurations differ narrowly I do not lean on the difference. The only differences this article argues from are the multiple-fold ones, like ②→④.
  • The 600s in ① is not a latency. It is the timeout ceiling. Quoting it as a p99 would be reporting something that was never measured.
  • Apdex uses the tool's default threshold, not one derived from a service level objective.

What is left is one line. If you changed several things, which one changed the outcome has to be measured separately. And when you do measure it, occasionally the change you were proudest of turns out to have been harmful on its own.
