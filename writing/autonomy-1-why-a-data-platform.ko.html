자율주행 데이터 플랫폼 01. 로컬 GPU 없이 시작한 자율주행 프로젝트는 왜 데이터 플랫폼이 됐을까

혼자 하는 자율주행 프로젝트를 시작하면서 처음 만든 것은 디렉터리 목록이었습니다. scene-platform, dataset-engine, evaluation-engine, simulation/isaac, robot-runtime까지 최상위 디렉터리가 열두 개였습니다. 센서 로그를 모으는 일부터 시뮬레이터와 실차 런타임까지, 자율주행 회사의 조직도를 그대로 옮긴 모양이었습니다.

그 목록을 줄여야 한다는 것은 알고 있었습니다. 어려웠던 것은 무엇을 기준으로 줄이느냐였습니다. 처음에는 하드웨어를 기준으로 삼았습니다. 이 머신에는 NVIDIA GPU가 없으니 GPU가 필요한 디렉터리는 지우면 된다고 생각했습니다.

방향은 이틀 동안 여러 번 바뀌었고 바뀔 때마다 무엇이 뒤집혔는지 문서로 남겼습니다. 그 기록에는 제가 틀린 자리가 날짜와 함께 남아 있어서 결과만이 아니라 판단이 어디서 흔들렸는지까지 따라갈 수 있습니다.

처음 기준이 흔들린 것은 같은 날 다른 저장소의 실행 로그를 열었을 때였습니다. GPU 서빙 실험을 하던 저장소에 AWS EKS 위의 GPU 노드그룹이 이미 있었고 그날 오전 세 시간 동안 유료 실험 16회가 그 위에서 끝나 있었습니다. 「GPU가 없다」는 이 머신 이야기였지, 제가 쓸 수 있는 컴퓨트 이야기가 아니었습니다.

이 글의 예상 독자#

  • 혼자 하는 사이드 프로젝트의 범위를 어떤 기준으로 줄일지 고민하는 분
  • 자율주행 · 로보틱스 쪽 포트폴리오를 데이터 플랫폼으로 잡을지 망설이는 분
  • Iceberg 같은 테이블 포맷이 해 주는 일과 직접 만들 일을 가르려는 분

처음 적은 제약#

먼저 로컬 머신을 쟀습니다. 명령을 하나씩 돌려 값을 적었습니다.

항목값명령
GPUNVIDIA 없음(AMD 내장 그래픽)lspci
CPU32코어nproc
RAM59 GiBfree -g
디스크 여유1.2 TiBdf -h
ROS 2없음ls /opt/ros

이 표를 근거로 첫 판은 「GPU가 없어 착수할 수 없는 디렉터리」를 골라냈습니다. 열두 개 가운데 네 개였습니다.

AWS 경로를 넣고 다시 셌습니다#

다른 저장소의 Terraform을 열어 보니 GPU 노드그룹 세 종류가 desired_size = 0인 Spot으로 정의돼 있었습니다. 서울 리전 g5.xlarge(A10G) Spot은 코드 주석 기준 시간당 0.357~0.424달러였습니다. 월 예산은 30달러로 잡혀 있었고 실제 지출이 80%에 닿거나 예상 지출이 100%를 넘으면 알림이 오도록 돼 있었습니다.

이 경로를 쓸 수 있다고 놓고 열두 개를 다시 나누니 결과가 달라졌습니다. GPU 때문에 아예 못 하는 디렉터리는 하나도 없었습니다. 디렉터리마다 필요한 일을 적고 로컬 CPU, AWS GPU, 실물 장비 가운데 어디서 되는지를 표로 갈랐습니다. 실물 로봇이 없어서 막히는 것이 둘(robot-runtime의 실차 검증, demos/sim-to-real)이었고 나머지는 로컬 CPU로 하거나 AWS 비용을 내면 됐습니다.

첫 판의 「네 개 불가」에는 범주 오류도 섞여 있었습니다. robot-runtime 전체를 불가로 적었는데 codex가 로그 재생, 인터페이스 계약, 오프라인 인지는 실물 없이도 된다고 짚었습니다. 「지금 할 가치가 없다」와 「착수할 수 없다」를 같은 칸에 넣어 범위를 줄이는 근거를 부풀린 셈입니다.

남은 제약은 시간과 예산이었습니다. 개인 작업에 쓸 수 있는 시간은 일주일에 8시간이었고 그 8시간도 이미 지원 준비와 앞선 프로젝트 마무리에 나뉘어 있었습니다. GPU를 쓰는 디렉터리는 월 30달러 예산을 앞선 프로젝트와 나눠 써야 했습니다.

열두 개를 한꺼번에 열지 않았습니다#

제약이 시간이라면 디렉터리 열두 개를 동시에 여는 것이 가장 큰 위험이었습니다. 검토는 세 단계로 했습니다. Fable이 판정 초안을 쓰고 codex가 그 초안을 공격하고 갈린 자리는 제가 코드와 원시 자료로 다시 확인했습니다. 다른 점에서는 여러 번 갈렸지만 이 점은 세 단계 모두 같았습니다.

빈 디렉터리를 미리 만들어 두는 것도 버렸습니다. 디렉터리를 만들면 그 안을 채울 일정이 생기는데 주 8시간으로는 열두 곳의 일정을 지킬 수 없었습니다. 채우지 못한 폴더는 레포를 여는 사람에게 지키지 못한 계획으로 보입니다. 지금 레포에는 「디렉터리는 산출물이 생길 때 나타난다」는 규칙이 있고 실제로 있는 것은 data-platform/ 하나입니다.

로보틱스와 데이터 플랫폼 사이#

다음 질문은 남길 하나를 무엇으로 하느냐였습니다. 첫 판정은 로보틱스 쪽이었습니다. 첫 산출물로 카메라와 라이다의 시각 차이(skew) p99와 일부러 넣은 결함을 얼마나 잡는지를 제안했습니다.

이 판정은 제가 정정한 사실 세 가지 때문에 폐기됐습니다. 첫째, 이 프로젝트로 보여 주려는 일은 로봇 연구가 아니라 AI 학습 데이터를 공급하는 플랫폼이었습니다. 둘째, GPU는 AWS로 쓸 수 있었습니다. 셋째, 제가 「연구자 수준의 글」을 표현의 기준으로 적은 것을 첫 판정은 연구 진로 목표로 읽었습니다. 데이터 플랫폼에서 먼저 보여 줘야 할 것은 테이블, 품질 검사, 재현 가능한 출고입니다. 그래서 skew p99는 첫 산출물의 자리에서 내려와 센서 품질 검사 가운데 하나가 됐습니다.

같은 정정이 AWS 자산의 위치도 바꿨습니다. 로보틱스 기준에서 EKS는 쓸 일 없는 GPU 장비였습니다. 데이터 플랫폼 기준에서는 Terraform으로 EKS와 예산 가드를 실제로 운영했다는 운영 증거였습니다. 성능을 재는 장비로는 쓰지 않고 배포와 권한 경로를 한 번 증명하는 데 씁니다.

Iceberg가 해 주는 것과 제가 만들어야 하는 것#

데이터 플랫폼으로 정한 뒤에 가장 오래 다툰 것은 「무엇을 직접 만드나」였습니다.

Fable 판정은 버전 관리, 슬라이스, 카탈로그를 직접 만들면 안 된다고 했습니다. Iceberg가 Snapshot과 Time Travel을 이미 주므로 다시 만들면 같은 기능을 두 벌 유지하게 되고 레포를 읽는 사람에게는 Iceberg를 모르고 만든 것으로 보인다는 이유였습니다. codex는 이 판정이 경계를 뭉갰다고 공격했습니다. Fable 자신도 같은 기능을 pipelines/, quality/라는 다른 이름으로 다시 만들고 있었다는 것이 근거였습니다.

Iceberg가 주는 것여전히 직접 만드는 것
Snapshot 원자 커밋 · Time Travel · Branch · Tag여러 센서와 테이블을 하나의 단위로 묶어 공개하는 일
스키마 · 파티션 진화센서별 필드 모델과 원본 정규화
SQL 조건으로 행 고르기센서 묶음 · 보정값 버전 · 빠진 프레임 정책 · 파일 존재를 함께 지키는 dataset slice
없음품질 Gate · 오케스트레이션 · 파일 수명 관리

저는 codex 쪽 판정을 따랐습니다. Snapshot이나 Time Travel을 다시 만들 이유는 없습니다. 그러나 오른쪽 열의 일은 Iceberg가 해 주지 않고 그 일을 Iceberg의 기능 위에 올리는 것이 이 프로젝트가 실제로 만드는 부분입니다. 첫 줄의 「여러 테이블을 하나의 단위로 묶어 공개하는 일」이 다음 편의 Release 계약이 됩니다.

남은 모양#

남은 것은 하나의 약속입니다. 큐레이터가 조건, 품질 정책, 시점으로 데이터 묶음을 지정하면 Release id 하나를 받습니다. 그 id를 언제 어느 머신의 Loader에 넘겨도 같은 행과 같은 bytes를 받거나, 바뀐 객체의 이름을 댄 거부를 받습니다. 이 약속을 중심에 둔 것은 학습 데이터가 조용히 달라지는 실패가 가장 늦게 발견되기 때문입니다. 데이터가 바뀐 채로 학습이 끝나면 그 차이는 모델 성능의 차이로만 보이고 원인을 데이터에서 찾을 단서가 남지 않습니다. 로드를 거부하면 적어도 사람이 그 자리에서 알게 됩니다. 다섯 개의 마일스톤은 이 약속의 성질을 하나씩 증명하도록 나눴습니다.

AWS가 공개한 자율주행 데이터 프레임워크(ADDF, 2022-06-24)도 원본, 카탈로그, 계보(lineage), 메타데이터, 장면 검색을 서로 다른 저장소에 나눕니다. 원본은 S3, 카탈로그는 Glue, 계보는 Neptune, 주행 메타데이터는 DynamoDB, 장면 검색은 OpenSearch에 두고 MWAA가 작업을 조율합니다. 층을 나누는 방식은 이 프로젝트와 같습니다. 그런데 나뉜 층을 한 시점의 묶음으로 고정해 다시 꺼내는 규칙, 즉 Release id 수준의 재현 계약은 그 글에서 찾지 못했습니다. 이 프로젝트가 가장 많은 시간을 쓰는 곳이 그 계약입니다.

이 글이 주장하지 않는 것#

  • 아직 구현하지 않았습니다. 이 글의 숫자는 개발 머신을 잰 값, 다른 저장소의 실행 기록(16회, 약 세 시간), Terraform 코드의 가격 주석과 예산 설정입니다. 이 플랫폼의 성능은 하나도 재지 않았습니다.
  • 「GPU 때문에 막히는 디렉터리 0개」는 열두 개 목록을 기준으로 한 판정입니다. 각 디렉터리를 실제로 AWS에서 돌려 본 것은 아닙니다.
  • 방향을 바꾼 근거 가운데 일부는 모델(Fable, codex)의 판정이고 판정이 갈린 자리는 제가 코드와 원시 자료로 다시 확인한 쪽을 따랐습니다. 최종 방향은 제가 정했습니다.

마치며#

그 뒤로는 제약을 적을 때마다 확인한 명령이나 파일을 옆에 붙였습니다. 범위를 줄이는 근거가 틀리면 줄인 범위도 같이 틀리기 때문입니다. 다음 편은 Release id 계약이 정확히 무엇을 고정하는지 다룹니다.

읽어 주셔서 감사합니다.
