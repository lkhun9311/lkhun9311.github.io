モニタリング画面の初期ロードがプロジェクトの数だけ認証していました
そのファクトリから Client を得ることが、そのまま Keystone への認証でした。

2026年9月

社内クラウド管理コンソールの Backend を作っています。モニタリング画面が遅い、という報告を 受けました。時系列グラフを描く画面なので、遅いのはクエリだろうと思いました。違いました。

初期ロードがプロジェクト 1 つごとに Client を作り直していて、使っていた serviceClient() は呼ぶたびに Keystone へ認証します。プロジェクトが N 個なら 認証も N 回、しかも順番にです。おまけにその場所に Cache があるのに、誰も読んで いませんでした。

直したのは Client を 1 つ、ループの外で作って使い回したことだけです。認証 N 回が 1 回に なります。ところがどれだけ速くなったかは分かりません。測っていませんし、普段使う負荷 シナリオではこの区間にトラフィックが流れません。なぜ測れなかったのかが、この記事の半分です。

想定読者#

  • クラウド SDK に getClient() のような便利関数を用意して使っている方
  • ループの中で Client を取るコードを見たことがある方
  • 画面が遅いとき、まずクエリを開く方

どんな画面#

複数プロジェクトのリソース使用量を 1 画面で見るモニタリングタブです。2 つが同時に動きます。

  • 初期ロードは REST で 1 回、プロジェクトごとにクォータと使用量を集めます。
  • その後はサーバーが 15 秒ごとに値を計算し、開いているすべての画面へ送ります。 接続を開いたままサーバーが送る方式なので SSE(Server-Sent Events)と呼びます。 ここで接続者数と無関係なのは 計算の回数で、作った値を直列化して各接続へ 書き出す費用は接続数だけ増えます。

まずクエリを開きたくなります#

「時系列グラフが遅い」と聞くと、まず手が伸びる場所があります。クエリです。式を整えて結果を Cache し、そのうえで負荷ツールでユーザーを増やして確かめる。 順番として自然ですが、ここでは遅い区間がそちらではありませんでした。

時系列の取得は 15 秒に 1 回です。しかも開いている画面の数と関係なく 1 回です。 頻度だけで「安い」とは判定できません。ただ記録の上で 先に見る区間として挙げられていたのはここではありませんでした。

実行時間の長い関数が、そのままユーザーの待つ区間とは限りません。 クエリは目につきやすいので、先に標的になります。

原因: Client を得ることが、そのまま認証です#

初期ロード側のコードはこうなっていました。

for (String projectId : projects) {
    // 反復ごとに client を取り直す
    var quota = ClientUtil.serviceClient()
                          .compute().quotaSets().getDetail(projectId);
    ...
}

読んでも何も問題が無いように見えます。便利関数を呼んで使うだけです。 その関数が何をするかが、名前に書かれていません。

このファクトリでは、Client を得ることが認証することです。 serviceClient() は設定ファイルのアカウントで Keystone につないでトークンを受け取り、 認証済みの Client を返します。

SDK 一般がそうだという話ではありません。同じライブラリにも、すでに持っている トークンから Client を作る道が別にあります。認証しているのは こちら側のファクトリの実装 であり、その事実が関数名に出ていなかった、というのがこの記事の話です。

そして これは社内文書 2 件で確認したことです。serviceClient() の 実装そのものはこの記事に載せておらず、リポジトリに残っているのも実装ではなく、それを説明する文書です。

するとループはこう回ります。

  • プロジェクト 1 個 → 認証の往復 1 回 + そのプロジェクトへの取得が数回
  • プロジェクト N 個 → 認証の往復 N 回 + 取得が N × 数回
  • しかも 順番に回ります。前が終わらないと次が始まりません

画面に見えるのはグラフなのに、それを描く前に 認証だけ N 回していました。 プロジェクトが増えれば 順次認証の回数もその分だけ線形に増えます。 それが応答時間をちょうどその分だけ延ばす、とまでは言いません。 認証 1 回がどれだけか、毎回同じかを測っていません。

そして Cache は読まれていませんでした#

同じ経路にクォータの Cache がすでに入っていました。ところが 読むコードがありませんでした。 詰めるだけで、毎回 live 呼び出しをしていました。

「Cache を入れた」と「Cache を読む」は別の仕事です。 読まれない Cache は無いより悪い。あると信じさせるからです。

前の ③編が「Cache があるのに、その Cache のせいで 遅かった」だとすれば、こちらは 「Cache があるのに誰も見ていなかった」です。

修正: 認証をループの外に出しました#

// 認証 1 回。ループの外で作る
final var client = ClientUtil.serviceClient(
        Config.newConfig()
              .withConnectionTimeout(...)
              .withReadTimeout(...));

for (String projectId : projects) {
    var quota = client.compute().quotaSets().getDetail(projectId);   // トークン再利用
    var net   = client.networking().quotas().detail(projectId);
    ...
}

変えたのは serviceClient() を呼ぶ場所 1 つです。 ループの中にあったものを外へ出しました。

正確にします。認証が無くなったのではなく、リクエスト 1 件あたり N 回が 1 回になった のです。Client はこのメソッドの中で作られるので、次のリクエストはまた 1 回認証します。

そして その「1 回」にも条件が付きます。ループが回っている間にトークンが期限切れになれば、 次の呼び出しは拒否されます。そのときライブラリが自分で認証し直して再試行するかは 使うバージョンとコネクタ次第で、この記事は確認していません。 トークンの有効期間がこのループの時間よりずっと長いので、表に出なかっただけです。

リクエストの間 Client を持ち続ければ認証をさらに減らせます。 ただし そちらのほうが難しいです。この系統の Client は現在のセッションを Thread に紐づける構造なので、1 つを複数のリクエスト Thread で分け合うとセッションが混ざったり 空になったりします。トークンの期限もそこからは自分で扱うことになります。 この修正はそこまで行っていません。

Timeout を この Client にだけ掛けたのも意図的です。全体の設定に掛けると、 正常に長くかかる他の呼び出しまで切れます。遅い画面を直そうとして正常な機能を切るのが、 よくある次の事故です。

2 つは別のものを制限します。Connection Timeout は 接続を張るのにかかる時間を、 Read Timeout は 送ってから応答を待つ時間を切ります。そしてこの Client にだけ掛けても この Client が行う認証・取得にはすべて掛かります。防げるのは、他の Client へ設定が 広がることだけです。これはそうすると決めた 意図で、全体に掛けたとき実際に何が 切れるのかを確かめた記録はありません。

ところが前後を測っていません#

ここからが、この記事が前の 3 編と違うところです。

社内の記録に残る数字は 2 つで、互いに食い違います。一方は「N プロジェクトなら 応答 5〜10 秒」、もう一方は「初期ロードが数秒から数十秒」と書かれています。 どちらもどう測った値かが書かれておらず、直したあとの値はそもそもありません。

ですからこの記事は 「何倍速くなった」と書けません。書けるのは、コードから確かめられる ところまでです。

横にスクロールすると残りが見えます

この記事が言えることと言えないこと。
言えること言えないこと
認証の往復が N 回から 1 回になるそれで何秒減ったか
認証 1 回分の費用を N−1 回払わずに済む認証 1 回が何 ms か
認証側がプロジェクト数に比例することは無くなる初期ロード全体がどれだけ緩やかになるか

左は コードを読めば出るもの、右は 測って初めて出る ものです。今回は左しかありません。初期ロードがプロジェクト数に比例すること自体はそのまま です。プロジェクトごとの取得には手を付けていません。比例が消えたのは認証の側だけです。

負荷ツールは、シナリオが送った経路しか測りません#

「では測ればいい」が次の問いです。ところがこの画面では、 よく書かれるシナリオだと遅い区間が試験に入りません。

負荷ツールを立ち上げて同時ユーザーを増やすのが普通のやり方です。ところがこの画面で ユーザーが待つ重い区間は 初期ロード 1 回で、その後は 15 秒ごとにサーバーが 1 回計算して、開いているすべての画面へ同じ値を送る構造です。

ユーザーを 10 人に増やしても Tick ごとの計算は 1 回のままです。 接続を持ち続けるシナリオなら、グラフは「ユーザーを増やしても平気」と出ます。 それはアーキテクチャの性質であって、遅い経路を踏んだという意味ではありません。

ツールのせいではありません。ユーザー 10 人がそれぞれ画面を開けば、初期ロードも 10 回回ります。つまり負荷ツールがその経路を踏めないのではなく、 接続を保って push を受ける側でシナリオを書くと、その経路がシナリオに入らないという 話です。負荷試験の結果は シナリオが実際に送ったリクエストについてだけ有効です。

きちんと測るには 軸を変える必要があります。同時ユーザーではなく プロジェクト数 N を増やしながら初期ロード 1 件を測るのです。 そう測ろうと記録には書いてあり、実際にそう測った記録はありません。 この記事が数値なしで終わる理由です。

限界: この記事が主張しないこと#

  • 前後の実測値がありません。「5〜10 秒」と「数秒から数十秒」は社内記録の 2 つの文で、 方法が書かれていません。直したあとの値はありません。この記事のどの文も 速度の改善幅を主張しません。
  • 認証 1 回がどれだけかを知りません。ですから「N−1 回分を払わずに済む」が 何秒なのかも分かりません。
  • Client を得ることが認証だというのは社内文書 2 件で確認しました。 serviceClient() の実装自体はリポジトリになく、この記事にも載せていません。 使っているライブラリのバージョンやコネクタも確認できていません。
  • プロジェクトごとの取得はそのままです。無くしたのは認証の側で、取得は今も プロジェクトの数だけ回ります。そこまで減らすには別の修正が要ります。
  • 負荷ツールが役に立たないという話ではありません。軸が合わなければ役に立たない、 という話です。前の ①編では同じ道具で 6 通りの構成を切り分けました。

おわりに#

  • 名前が費用を隠します。serviceClient() はただのように見えて ネットワークの往復です。ループの中で Client を取るコードは、いつも一度疑う価値があります。
  • 「Cache を入れた」と「Cache を読む」は別の仕事です。
  • 負荷試験の結果は、シナリオが実際に送ったリクエストについてだけ有効です。 軸が合わなければ平らなグラフが出て、そのグラフは踏まなかった経路について何も言いません。
  • 直したのに測れなかったなら、測れなかったと書きます。コードで確かなことと 測って初めて分かることを分けておけば、少なくとも次の人は何を測ればよいか分かります。

最後に 1 行だけ残すなら、これです。 測る前に「ユーザーは何を待っているのか」と「このシナリオはその経路へリクエストを送るのか」を 先に問うべきです。今回は遅い区間を見つけて直しておきながら、その区間を通るシナリオを 書かなかったので、前後を比べられませんでした。

次回はその 2 つめの問いを正面から扱います。構成を 6 段階に分け、同じ条件で それぞれ測った試験の話です (⑤編)。
