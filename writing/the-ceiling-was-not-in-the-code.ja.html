スループットの上限はコードになかった
S3 のために入った ライブラリの既定値 5 — ソーシャル投票プラットフォームのコンテンツ検閲経路

こんにちは。ソーシャル投票プラットフォームを作っています。前回の記事でトランザクション境界を 直し、負荷試験ハーネスを立てて数値を作りました。 そのハーネスがすぐに次の問いを投げてきました — 「投稿作成のスループットは、なぜ 6.27 req/s から上がらないのか」。

書き込みスレッドを4倍にしても、DB コネクションプールを3倍にしても、その数字は動きませんでした。 犯人は私が入れた覚えも、選んだ覚えも、名前を見た覚えもないライブラリの既定値でした。

この記事の想定読者#

  • Spring Boot の RestClient や RestTemplate で外部 API を呼んでいる方
  • スループットがある数字で止まっていて、スレッドも DB プールも増やしたのに動かない方
  • 「自分が入れていないライブラリが、自分のサービスの挙動を決めているのでは?」が気になる方

どんな内容ですか?#

  • コンテンツ検閲経路のスループットが 6.27 req/s で止まっていました。書き込みスレッドを 4倍にしても、DB プールを3倍にしても同じでした。
  • 原因は S3 を使うために入れた AWS SDK が連れてきた HTTP クライアントの既定値 「対象ホストあたりコネクション5本」でした。
  • このライブラリはランタイムのクラスパスにしかありません。コードのどこにも名前が出ないので、 読んでも見つからず、測ってはじめて出てきます。
  • 直し方は上限をなくすことではなく、決めることでした。上限を消してもスループットは同じだけ 上がりますが、それは誰も選んでいない 5 を 誰も選んでいない無限大に 替えるだけです。
  • 結果は外部呼び出しの同時実行 10 → 32、投稿作成 p50 2,592 → 805ms、 スループット 6.27 → 19.89 req/s(3.17倍)、エラー率 0% でした。

コードは非公開リポジトリにあります。まだリリース前なのでリポジトリを開けていません。 そのため各セクションには GitHub リンクの代わりにファイルパスとシンボル名を書いてあります。

⚠️ 先にお伝えすることがあります。この記事の数値はすべてローカルのハーネスで 測ったものです。負荷ツール・アプリケーション・外部 API のスタブ・PostgreSQL が すべて同じマシンで CPU を分け合っています。ですから 絶対スループットには意味がなく、比較にだけ意味があります。外部呼び出しの 800ms は スタブに設定した値であって実際の遅延分布ではなく、条件ごとに1回の実行です。

どの経路の話ですか?#

事業化を目指して作っているソーシャル投票プラットフォームです。ユーザーが質問を投稿すると 他の人が匿名で投票し、その結果のチャートをアプリの外へ共有します。Kotlin と Spring Boot で作った単一の モノリスで、データベースはマネージドの PostgreSQL 一つです。

投稿はモデレーションゲートを通らないと公開されません。ゲートは四層あり、そのうち ③ 有害分類と④ 攻撃判定の二層が外部 API を呼びます。ゲートは fail-closed なので、この呼び出しが失敗すると投稿は 公開されません。

図が語っていないことを一つ添えると、③ と ④ は同じホストへ出ます。この事実が後で 「ホストあたり5」という既定値と出会って問題になります。

最初は DB がボトルネックだと思っていました#

ハーネスが最初に出した数値はこうでした。書き込み16スレッド、DB コネクションプール10、外部スタブの遅延 800ms。

指標値
投稿作成スループット6.27 req/s
投稿作成 p502,592 ms
フィード取得 p504 ms
エラー率0%

→ 表は横にスクロールできます

まず浮かんだ仮説はありふれたものでした。

書き込みが16なのに DB コネクションプールは10だから、コネクション待ちで遅いのでは。 あるいは INSERT 自体が重いのでは。だとしたら書き込みをキューに逃がすか、Redis を足すべきでは。

三つとも外れでした。そして外れだと分かったのは推論ではなく、ハーネスが教えてくれたからです。

結論から申し上げると#

ボトルネックは DB でも INSERT でもアプリケーションスレッドでもありませんでした。 外へ出る HTTP 呼び出しの同時実行が10で縛られていました。

そしてその10は、こうやって出来ていました。

S3 を使うために入れた AWS SDK
  → software.amazon.awssdk:apache5-client
     → org.apache.httpcomponents.client5:httpclient5      ← 推移的依存
        → Spring の RestClient がクラスパスからこれを選ぶ
           → コネクションプールの既定値: 対象ホストあたり5
              → 同じホストを見る RestClient 2つ × 5 = 同時10

この連鎖で私が選んだのは一行目だけです。ファイルアップロードのために S3 を足しただけなのに、 それが連れてきた HTTP クライアントを通じてコンテンツ検閲のスループット上限を決めていました。

書き込みは重くありませんでした#

「書き込みは重いのか」はハーネスがそのまま答えられる問いでした。外部スタブの遅延を 0ms に 置いて他の条件をそのままにすれば、残るのはアプリケーションと DB の純粋な書き込みコストだけです。

条件投稿作成 p50投稿作成スループット
外部遅延 800ms2,592 ms6.27 req/s
外部遅延 0ms8 ms1,398 req/s

→ 表は横にスクロールできます

INSERT の経路そのものは8ミリ秒です。毎秒1,398件を受けます。書き込みはこのシステムの問題では ありませんでしたし、したがって書き込みをキューに逃がす設計は壊れていないところを直す作業に なります。

⚠️ この測定は最初、間違っていました。遅延0を要求したのに、 前の実行の 800ms スタブがポートに生きたまま残っていました。ハーネスには「スタブは本当に その遅延で応答しているか」を見る往復検査があったのですが、条件が 往復時間 < 要求遅延 × 0.8 だったので、要求遅延が0なら常に偽になります。 検査が空虚に通過したわけです。そのせいで 800ms の実行を 0ms の実行として記録し、 そこから結論を出していました。

直し方は時間ではなく身元を見ることでした。スタブに自分の設定値を報告させ、それを要求値と 突き合わせます。

$ curl -s localhost:18080/__stub/health
{"ok": true, "delay_ms": 800, "jitter_ms": 0, "max_in_flight": 10}
#            ↑ 要求した値と違えば実行を中止する

そのうえでわざと違うスタブを立てて回し、実行が実際に止まることを確認してから測り直しました。 このリポジトリで最も多い欠陥は「失敗したのに通過に見える検査」なので、検査を入れたらわざと 失敗させてみる、というのを規則にしています。

何を変えても 10 から動きませんでした#

次にスタブに計測を入れました。リクエストが入るときに数え、出るときに引いて、 同時に処理中の外部呼び出しの最大値を記録させます。この数字ひとつが残り全部を説明します。

書き込みスレッドDB プール外部呼び出しの最大同時実行投稿スループット投稿 p50
1610106.27 req/s2,592 ms
1630106.27 req/s2,595 ms
3230106.26 req/s5,119 ms

→ 表は横にスクロールできます

表の読み方はこうです。書き込みを4倍にしても、DB プールを3倍にしても同時実行は10から動きません。 伸びるのは応答時間だけです(2,592 → 5,119ms)。これは典型的な待ち行列の兆候です — 仕事が増えたのではなく、列が長くなっただけです。

スタブが犯人である可能性は別に消しました。同じスタブをアプリ抜きで32ワーカー・20秒叩くと 同時32 · 40 req/s を出します。ですから10はスタブの限界ではなく、 アプリが外へ出る道の限界です。

ここで算数が合います。投稿1件が呼び出し2つを出すので、同時10は同時に検閲中の投稿5件です。 呼び出し1回が 800ms なので 5 ÷ 0.8秒 = 約 6.3 req/s。観測された 6.27 と一致します。

スレッドダンプがどこで止まっているか教えてくれました#

「アプリのどこかに10がある」ところまでは来たものの、それがどこかはコードを読んでも見つかりませんでした。 私のコードには10も5も書かれていないからです。

そこで負荷がかかった状態でスレッドダンプを取りました。Tomcat ワーカー16のうち 5つはソケット入出力中(RUNNABLE)、11は park でした。park 側のスタックが 答えでした。

at org.apache.hc.core5.pool.StrictConnPool$1.get(StrictConnPool.java:183)
at org.apache.hc.client5.http.impl.io.PoolingHttpClientConnectionManager$3.get(...)
at org.apache.hc.client5.http.impl.classic.InternalExecRuntime.acquireEndpoint(...)

Apache HttpClient 5 のコネクションプールで待っていました。私はこのライブラリを入れた 覚えがありませんでした。

連鎖をさかのぼると S3 に着きます#

依存ツリーを出すと、連鎖はこうでした。

図が語っていないことを一つ。httpclient5 はランタイムのクラスパスにしかありません。 コンパイルのクラスパスにないので、自分のコードでは名前すら書けません。実際、先に設定コードを書こうとして Unresolved reference 'hc' で止まりました。

ですからこの層は読んでも見つかりません。コード検索でもレビューでも出てきません。 測ってはじめて出てきます。

一行の設定で確認しました#

仮説が正しいかは一行で確認できました。Spring にApache ではなく JDK クライアントを使えと 指定し、他の条件はすべてそのままにします。

806ms はもう外部呼び出しそのものです。手前にあった待ちが消えました。仮説は当たっていました。

ただし、このままにしてはいけません#

ここで止めたい誘惑がありました。一行で 3.17 倍ですから。ところが jdk クライアントにはホストあたりの上限がありません。

つまりこの一行がしたことは、誰も選んでいない 5 を誰も選んでいない無限大に替えただけです。 この記事がずっと言ってきたことと正反対です。

上限がなければ、負荷が集中したとき外部 API へ無制限の同時呼び出しが出ます。それは 相手のサービスへの負荷であり私の費用です。流入制御は上限をなくすことではなく、 意図して決めることです。

付け加えると、このリポジトリは同じ形の欠陥をすでに一度経験しています。Tomcat スレッド200とコネクションプールが どちらもフレームワークの既定値で、その二つが作った並行性の方針は方針ではありませんでした。 アウトバウンドにも同じことがあり、今回は誰もその層を見ていませんでした。

そこで上限を決めました#

Private repo

選んだ方法は二つです。

  1. httpclient5 を明示的な依存に格上げします。すでにランタイムで使っていた ライブラリを名前で書くということで、そうしてはじめて設定コードが書けます。
  2. コネクションプールを一つだけ作り、すべての RestClient で共有します。 クライアントごとに自分のプールを持つと「ホストあたり N」が実際には「クライアント数 × N」になります。 それが5が10になっていた理由です。
@Configuration
class OutboundHttpConfig {
    @Bean
    fun outboundConnectionManager(
        @Value("\${oxy.http.outbound.max-per-route:50}") maxPerRoute: Int,
        @Value("\${oxy.http.outbound.max-total:100}") maxTotal: Int,
        // Spring が付けてくれていたタイムアウトをここで付け直す — 同じプロパティキーを読む。
        @Value("\${spring.http.client.connect-timeout:3s}") connectTimeout: Duration,
        @Value("\${spring.http.client.read-timeout:10s}") readTimeout: Duration,
    ): PoolingHttpClientConnectionManager = ...

    @Bean
    fun outboundHttpCustomizer(cm: PoolingHttpClientConnectionManager): RestClientCustomizer {
        // ファクトリも一つだけ作り、すべてのビルダーが同じプールを使うようにする。
        val factory = HttpComponentsClientHttpRequestFactory(
            HttpClients.custom().setConnectionManager(cm).build())
        return RestClientCustomizer { builder -> builder.requestFactory(factory) }
    }
}

50 という数字の根拠もコメントに書きました。投稿1件が呼び出し2つを出すので50は 同時に検閲中の投稿25件にあたり、外部呼び出しが 800ms なら毎秒およそ31件まで受けます。 いま立てているどのトラフィック想定よりも大きく、しかし無限ではありません。

もう一度測りました。条件は前と同一です。

⚠️ 32 は新しい上限ではありません。書いた上限は50なのに観測された最大同時実行は32です。 32 は負荷の形であって上限ではありません — 書き込みスレッド16が投稿1件あたり呼び出し2つを 出すので 16 × 2 = 32 です。つまりこの実行で天井はアウトバウンドのプールから離れており、 いまスループットを決めているのは流入の並行度です。50 が実際に効くかは書き込みスレッドを25以上に上げないと 見えませんが、測っていません。

そして factory=jdk(19.89 req/s)とこの処方(19.89 req/s)はスループットが同じです。 二つを分けるのは性能ではなく、上限が書かれているかどうかです。

最初の実装はタイムアウトを消してしまいました#

Private repo

最初の実装は requestFactory を丸ごと入れ替えました。すると Spring の自動設定が付けてくれていた spring.http.client.* のタイムアウトも一緒に消えました。

これは静かに通り過ぎうる種類の事故です。タイムアウトがなくても正常な応答は正常に返ってきます。 問題は応答が返らないサーバーに出会ったときだけ現れます。

幸い、このリポジトリにはそれを狙うテストがすでにありました。 「応答のないサーバーにぶら下がらない」というガードが40秒で失敗しました。 そのガードがなければ、無限待ちが静かに戻ってきていたはずです。

直し方は値を複製しないことでした。同じプロパティキーを読みます。複製すれば、いつか片方だけが 変わる日が来ます。

設定はそれ自体では何も失敗させません#

Private repo

この修正には他と違う性質が一つありました。成果物が設定値だということです。ロジックを壊せば そのロジックを狙うテストが赤くなりますが、設定は消しても何も失敗しません。ただ静かに既定値へ 戻るだけです。

そしてその「静かに戻った既定値」こそが、この記事全体の原因でした。ですから値が 実際に付いたかを断言するテストを二つ入れました。

// ① 既定値(5)ではなく、こちらが与えた値が付かなければならない。
assertThat(manager.defaultMaxPerRoute).isEqualTo(37)
assertThat(manager.maxTotal).isEqualTo(91)
// ルート別の取得も同じ値であること — 食い違えば実際の上限が変わる。
assertThat(manager.getMaxPerRoute(route)).isEqualTo(37)

// ② クライアントごとにプールを持つと「ホストあたり N」が「クライアント数 × N」になる。
//    それが 5 が 10 になっていた理由なので、同じファクトリを共有しているかを断言する。
assertThat(factories[0]).isSameAs(factories[1])

この断言が本当に狙っているかは ミューテーションで確認しました。 setMaxConnPerRoute を消すと一つ目が5を見て赤くなり、ファクトリをビルダーごとに作り直すと 二つ目が赤くなります。どちらも実際に確認しました。

「Redis やキューを使えばいいのでは?」#

この作業中に実際に受けた質問です。アーキテクチャを変えて解くべきではないか、という話でした。ハーネスが あったので答えを選ぶ前に測る順序で進められました。

候補いまのボトルネック(外部同時10)に触れるか判定
Redis キャッシュ(フィード · 統計)✗ 読み取りは p50 4ms ですでに速い根拠なし
Redis キャッシュ(検閲判定)△ 同じ本文が繰り返されるときだけ。ユーザー投稿はたいてい一意まず重複率を測る
キューイング(Redis · Kafka)✗ キューは待ちを移すだけで外部上限は上げないそれ自体では無効
書き込みをキューへ✗ 書き込みは 8ms直すものがない
アウトバウンドの同時実行を明示✓ 天井を直接上げる最優先

→ 表は横にスクロールできます

キューイングについてだけもう一つ書きます。検閲をキューに逃がすことは実際に何かを変えます。 ただし変わるのは性能ではなくプロダクトの約束です。

ゲートは fail-closed なので、検閲前に投稿が見えてはいけません。ですから取りうる形は 「先に公開して後から検閲」ではなく「検閲が終わるまで公開されない非同期ジョブ」です。 遅延をなくすのではなくリクエストスレッドから切り離すだけで、アウトバウンドの 上限はそのままです。代わりに状態表示・再試行・重複防止・失敗通知がすべて新しく必要になります。

そこでいつその設計が正当になるかを先に書いておきました。あとで「感覚」で導入しないためです — 上限を意図的に上げたあとでも投稿作成 p95 が目標を超えるか、外部 API の p99 が自前のタイムアウトに近づいたら、 そのとき非同期にします。

この記事が主張しないこと#

  • 本番の数値ではありません。負荷ツール・アプリ・スタブ・DB が一台で CPU を分け合っています。 絶対スループットに意味はなく、比較にだけ意味があります。
  • 800ms はスタブに設定した値です。実際の外部 API の遅延分布ではありません。実際の利得は その分布次第です。
  • 条件ごとに1回の実行です。繰り返して分散を見ていません。
  • 3.17倍はこの条件に付随する数字です。外部呼び出しの遅延と流入の並行度が変われば同じ倍率には なりません。
  • max-per-route = 50 は実トラフィックで測った値ではありません。 「誰も選んでいない5」を「根拠を書いた50」に替えたもので、実測ができたら決め直します。
  • 50 が実際に効くところは見ていません。この負荷では流入が先に32で縛られます。
  • 障害は起きていません。リリース前の点検で出たもので、運用でこの上限に当たった記録は ありません。
  • AWS SDK や Apache HttpClient を責める記事ではありません。ライブラリは自分の既定値を 持つ自由があります。問題はその既定値が私のサービスの方針になっていて、誰も知らなかったという 点にあります。
  • まだマージしていません。セキュリティゲートに触れる経路なので、リポジトリの規約どおり 書面レビューが先です。

おわりに#

まとめるとこうです。

  • スループットがある数字に張り付いて動かないなら、まずその数字を作った層を探します。 スレッドや DB プールを増やすのはその次です。
  • 私が選んでいないライブラリが私のサービスの並行性の方針を決めていました。その層は ランタイムのクラスパスにしかないので、読んでも見つからず、測ってはじめて出てきます。
  • 上限をなくすことと決めることは違います。スループットは同じだけ上がりますが、 一方には数字が書かれていて、もう一方にはありません。
  • 設定で直したものは消しても何も失敗しません。だからこそ値が付いたということ自体を 断言する必要があります。

最後に一行だけ残すなら、これです。 誰も選んでいない既定値も、方針のように振る舞います。 ただしそれは誰も責任を負わない方針で、たいていは測るまで存在にすら気づきません。
