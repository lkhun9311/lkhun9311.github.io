Instance HA ②: 信号ごとに証言できる範囲が違います
検知をより精緻にする代わりに、どの信号が何を言う資格を持つかを先に決めました。Instance HA 障害対応設計の連作、その二編目です。

①編で見たのは、Controller が自分の孤立を Compute の死として読んだという事実でした。この話を聞くと たいてい同じ処方が先に出てきます。検知をより精緻にしようというものです。私も最初はそちらを考えました。

ところがその方向はこの事故には効きません。観測者が孤立しているときは、何をより精密に見ても その観測を信じられないからです。精度を上げることと資格を問うことは別の仕事です。

そこで設計の最初の決定は、検知器に手を入れることではなく信号ごとに何を言う資格があるかを 決めることになりました。この編はその等級表と、最下位に置いた EXT Probe のパラメータ六つに それぞれ根拠を付けた過程です。

想定読者#

  • 障害判定に複数の信号を混ぜて使う仕組みを設計している方
  • 外部への到達性チェックでノードの生死を判定している構成をお使いの方
  • Timeout や再試行回数のような値に根拠を残したい方
  • ①編を読んで、それで何を変えたのかが気になる方

検知をより精緻にするのは答えではありませんでした#

よくある処方は検知の間隔を縮めるか検査項目を増やすことです。どちらも観測の解像度を上げます。 ところが①編の事故で間違っていたのは解像度ではなく観測者の自己認識でした。孤立した Controller はいくら頻繁に突いても、届かないという同じ答えを受け取り続けます。

ここで問いを変えました。何をより多く見るかではなく、いま見ているもののうち誰が何を言えるのかです。 この問いは答えが変わります。信号ごとに観測地点が違い、観測地点が違えば証言できる対象も違うからです。

信号を四つの等級に並べました#

横にスクロールすると残りが見えます

四つの信号等級と各信号の役割。
信号等級言えること
Agent HeartBeatHighestCompute Node の実際の状態
Controller QuorumHighController cluster の合意状態
Network HeartBeatMediumController と Compute のあいだの接続
EXT ProbeLowController が孤立しているかどうか

順序の根拠は観測地点です。Agent HeartBeat は Compute の上で動き、そのノード自身が送る信号なので 対象の状態を直接語ります。反対に EXT Probe は Controller から外へ出ていく検査なので、Compute に 一度も触れていません。

EXT Probe は Compute を見ていません#

この一文がこの編の核心です。EXT Probe は Controller から外部アドレスへの到達性だけを 確認します。それで Compute の稼働を判定すると、①編で見た誤認がそのまま再現されます。 観測者の孤立を対象の障害として読むことになります。

そこで EXT Probe を廃止せず役割を変えて残しました。この信号は「あのノードは 死んだか」には答えず、「いま自分は判断してよい立場か」に答えます。同じ検査をそのまま置いて問いだけを 変えた形です。

横にスクロールすると残りが見えます

同じ信号を二つの問いに使った場合。
問いEXT Probe の答え妥当か
あの Compute は死んだか届かない妥当ではありません
自分は孤立しているか届かない妥当です

六つの値を決めました#

役割が決まると値が残ります。どれくらいの頻度で突き、何回失敗したら判断に上げるかです。六つを決め、 それぞれになぜその値なのかを添えました。

横にスクロールすると残りが見えます

EXT Probe のパラメータ六つと根拠。
パラメータ値根拠
probe の方向Controller から外へController の外部到達性の確認であって Compute の直接検証ではありません
probe 間隔10 秒HeartBeat の周期に合わせました
連続失敗回数3 回揺らぎによる 1〜2 回の失敗を判断に上げません
判断 TTL30 秒間隔 10 秒かける 3 回です
EXT アドレス最小数3 個以上2 個構成では同時障害の可能性が残ります
判断 threshold3 個中 2 個の失敗1 個の失敗はそのアドレス固有の障害かもしれません

なぜ十秒でなぜ三回か#

三つの値は独立していません。間隔と回数を決めれば TTL は掛け算で付いてきます。ですから復旧を早く 始めたければどちらかを削ることになり、その分だけ一度の揺らぎで判断が立つ側に傾きます。 縮める方法とその代償を一緒に書いておいた理由です。

アドレスを三つ以上置き、そのうち二つが失敗して初めてパーティションと見るのも同じ形です。一つだけ 見るとそのアドレス側の障害と自分の孤立を区別できず、二つでは両方が同時に死ぬ場合が残ります。設計の 中身は数字そのものではなく、その数字で何を区別しようとしたかにあります。

限界：この記事が主張しないこと#

  • ⚠️ この連作の成果物は設計書です。実装は別のメンバーが引き継いでおり、これらの値が運用でどう 調整されたかはこの記事の範囲ではありません。
  • 六つの値は提案値であって実測で調整した値ではありません。負荷をかけて測って選んだのではなく、 区別したい状況から逆にたどって決めました。
  • 等級表はこの製品の信号構成から出たものです。Agent のない環境では最上段が空くので、同じ表を そのまま移せません。
  • 社内資料のため製品名・顧客名・アドレス・アカウントは書いていません。

おわりに#

この編の結論は一行です。検知の精度を上げることと信号の資格を決めることは別の仕事です。 孤立した観測者は精密に見ても外し、資格を決めておけば自分が判断する立場ではないと自分で気づけます。

次の編はこの等級を実際の判定に移す話です。「本当に障害か」と「いま実行してよいか」を二段階に分け、 八つのシナリオを判定した結果へ続きます。③編へ進みます。
