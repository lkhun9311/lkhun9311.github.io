Splitting One Card Meets a Latency Target the Shared Engine Never Does
Before finding that out, I paid for a ladder whose answer was already decided.

Two tenants share one GPU. I measured which arrangement holds a latency target to a higher offered load: one engine serving both, or an engine each.

Half of this post is about my own mistake. The criterion, the readings and the stopping rule were all correct, and I still paid for an experiment whose answer was already decided, because I put the ladder somewhere it could not be climbed. That was knowable before renting anything.

One caveat first. What follows are pass and fail results at four sampled arrival rates, not a proof of a maximum sustainable rate. Neither arrangement's maximum was located. The rest of the caveats are gathered under "What this does not claim".

Who this is for

  • Anyone weighing up letting several tenants share one GPU
  • Anyone who designs performance experiments and is never sure what to buy to get an answer
  • Anyone who builds their own measurement tools

The setup

A small language model (Qwen2.5-3B) served from one NVIDIA A10G, taking two kinds of customer at once. The premium tenant sends short prompts often and needs its first token quickly. The contending tenant sends a 40,000-character prompt now and then, and each one holds the GPU for a long time.

The criterion was fixed to one number. The premium time-to-first-token p99 at or under 139.0 ms. That is exactly twice the isolated baseline of 69.5 ms measured with no contender, and it was written down before the experiment started.

I assumed a fixed workload could measure capacity

An earlier run gave both arrangements exactly the same request trace. All three arms finished every request, losing none. Comparing throughput gave 589.3 / 586.9 / 584.0 tok/s, and I nearly wrote "separation costs 0.9% of capacity".

It cannot. If all three arms completed the same fixed work, the numerator is a constant.

The result, up front

Put the ladder below the load the earlier run used, and this is what comes out.

The shared engine misses the target even with premium lowered to 1.16 req/s. The contender offered and completed 139 of 139 requests in every cell, and the two rungs that landed near the target were bought a second time on a different card. They moved 2.1 ms and 0.3 ms.

I put the ladder where it could not be climbed

A ladder works like this. Start at a low load, climb a rung at a time, and stop at the first rung where both arrangements miss the target. The rung below it is what each one sustained.

I put the bottom rung at 9.22 req/s, the load the earlier run used. And that earlier run had measured 1,892 ms and 1,007 ms at exactly that load. The target is 139 ms.

I had quoted those numbers in the second paragraph of my own pre-registration and still did not see it. The criterion, the readings and the stopping rule were all correct. What was wrong was the search direction, and a search direction is part of a design. Re-confirming a number I already had cost about $0.35.

The verdict was right and the runner misread its exit code

This part hurts more. At the first rung the verdict command said, entirely correctly, "both arrangements missed the target, stop here", and exited 10. The runner read that as 0.

# wrong
if "$BIN" ladder-verdict ... ; then
  ...
  continue
fi
verdict_code=$?          # this is the IF STATEMENT's status, not the command's

In bash, $? after an if is the status of the if statement, not of the condition. When the condition fails and there is no else, an if returns 0. So a correct stop was reported as a rung that could not be scored, and a paid session ended there.

# right — capture the status beside the command
verdict_code=0
"$BIN" ladder-verdict ... || verdict_code=$?
if [ "$verdict_code" -eq 0 ]; then ...

No rehearsal could have caught it. The GPU-free rehearsal answers in milliseconds with a stub engine, so it never breaches the target, so the stopping branch never executes. I had pinned the verdict command's exit code 10 in a test. I had not pinned the script's reading of it.

There is now a rehearsal that wedges a thin shim in front of the verdict command and drives the real runner down that branch. And before fixing it, I restored the defect and watched the test go red.

Why lowering the load does not rescue the shared engine

Because the tail is not made of premium queueing behind premium. At 4.61 req/s under the shared engine, 651 premium requests went over 139 ms, and 649 of them (99.7%) were sent while a contending request was still waiting for its own first token.

What the p99 was hiding

Because the criterion is a p99, it does not show how large a miss is. Counting the evidence I had already bought:

Split arrangement p99 and the number of premium requests over 139 ms, by offered rate.
offered premiumsplit p99requests over 139 ms
1.16 req/s123.8 ms1 of 585 (0.17%)
2.31 req/s130.4 ms5 of 1,164 (0.43%)
4.61 req/s143.2 ms40 of 2,327 (1.72%)
9.22 req/s1,013.2 ms823 of 4,655 (17.68%)

The miss at 4.61 is forty requests. That fraction rises monotonically across all four points, and unlike a p99, which is one observation and can move, a count over thousands of requests cannot move much unless the distribution does. The actual cliff is between 4.61 and 9.22, from 1.7% to 17.7%, and I did not measure there.

It is not free

The split loses none of the contender's work. It makes it wait.

Completion times under both arrangements at 2.31 requests per second.

premium completion median1.089 s1.987 s
contender completion median1.316 s4.654 s
contender completion p994.050 s16.344 s

Premium trades its median for its tail, and the contender pays most of the bill. A platform that turns this on is choosing that, and owes the tenant it charges an account of it.

What this does not claim

  • A maximum sustainable rate for either arrangement. Neither was located. The table is pass and fail at four sampled loads, not a proof that nothing between or above them qualifies.
  • Anything about windows shorter than 505 seconds. The run that passes at 2.31 req/s has a p99 of 141.7 ms over its own final 101 seconds.
  • Anything about a different contender arrival pattern. The contender's count is held at 139 per rung; its schedule is not, so comparisons across rungs mix a rate change with a different contention schedule.
  • That the topology rather than the batch cap moved the result. Splitting also halves the per-engine sequence cap, from 64 to 32, and no arm separates the two.
  • That 139 ms means anything commercially. It is twice a baseline, not a customer requirement.
  • Anything about another card, another model, or MIG. One A10G, one model, one prompt mix.

Closing

  • An experiment whose fixed workload is completed in full cannot measure capacity. The numerator is a constant, so any amount of headroom produces the same number.
  • The search direction is part of the design. With the criterion, the readings and the stopping rule all correct, starting where the answer cannot be does not produce one. And that was knowable before renting.
  • Pinning a guard and pinning the code that reads it are different jobs. Exit code 10 was held by a test. That the runner read it with $? after an if was not.
  • There is a result. Under this contending load the split holds 139 ms up to 2.31 req/s and the shared engine holds it at no rate measured, at the price of quadrupling the contender's tail.

If you build your own measurement tools, break them on purpose and check that something goes red. Every expensive defect in this project had the same shape: a guard that exists, is correct where it is written, and is not consulted where it matters.
