On a social polling service I build alone, editing a design document was set up to kick off an outside review automatically. Result files piled up in a folder. I believed it was working.

I rebuilt the string that gets handed to that review. It was cut through the middle of a character. The review tool rejects an argument like that before it ever reaches a model.

I was cutting the document with head -c 60000. That command counts bytes, not characters. In a Korean document the 60,000th byte can land inside a three-byte character. And when it failed that way, nothing anywhere said so.

Who this is for#

  • Anyone who set up an automated check and then reassured themselves by looking at the output folder
  • Anyone who types 2>/dev/null out of habit
  • Anyone piping Korean or Japanese documents into a tool

Editing a design doc was supposed to trigger a review#

It is a solo project, so there is nobody to review the design. I set it up so that editing a design document makes an outside tool read it and pull out the five most serious problems. The result is saved under a timestamped filename.

"Editing" is narrower than it sounds. The hook only fires for one particular editing tool. Change the file from a shell or through some other path and it never runs at all. That comes back later.

FILE="${1:-docs/DESIGN.md}"
OUT=".reviews/design-$(date +%Y%m%d-%H%M%S)-$$.md"   # the $$ was added later

DOC=$(head -c 60000 "$FILE")
PROMPT="Review this design document ruthlessly. ...

DOC ($FILE):
$DOC"

codex exec --sandbox read-only "$PROMPT" > "$OUT" 2>/dev/null
exit 0

head -c 60000 was there because handing over the whole document might make the argument too long. 2>/dev/null and exit 0 were there so a failed review would not block the edit.

The defect this article is about lives in those eight lines. Every one of them went in for a plausible reason. Except the last one, which is outside the code. It comes later.

The cut landed inside a character#

head -c counts bytes. For ASCII a character is one byte, so the two coincide; a modern Hangul syllable is three bytes. (Korean prose also mixes in one-byte digits and punctuation, and there are four-byte characters and emoji built from several pieces.)

I measured every revision that survives#

"A character can be split" and "it was split then" are different statements. So I pulled out every revision of this document that survives as a commit and checked two things: whether the whole original is valid, and whether the first 60,000 bytes are. If the original was already broken, the cut is not to blame.

blob=$(git rev-parse "$commit:docs/DESIGN.md")

git cat-file -p "$blob" | iconv -f UTF-8 -t UTF-8 > /dev/null                # whole original
git cat-file -p "$blob" | head -c 60000 | iconv -f UTF-8 -t UTF-8 > /dev/null # first 60,000

All six originals are valid. So the breakage in the right-hand column comes from the cut. All four commits over 60,000 bytes are affected, five counting the working copy. I was about to write "it catches about half the time" and deleted it after measuring.

This table proves exactly this much: "cutting this blob with this command produces invalid UTF-8". Not that the hook actually received that blob, nor how it ended if it did. There were more intermediate states between commits and they are not preserved. I do not know how many.

So what this article can say is "among what can still be measured, I found no counterexample". "It went unread for weeks" is an inference drawn from that, not a proof.

The program that rejected it was not the one I thought#

I ran a string containing a split character as an argument, in the same form the hook used at the time.

$ codex exec --sandbox read-only "$(cat broken.txt)"

exit code: 2
stdout: 0 bytes
stderr: error: invalid UTF-8 was detected in one or more arguments
        Usage: codex exec [OPTIONS] [PROMPT]

It never reaches a model. The rejection happens while the arguments are being checked. So not one character of review comes back.

And here I got it wrong once more. The fixed hook has a timeout in front, and having measured in that form I had written down an exit code of 125. Measuring again:

$ codex exec ... "<broken argument>"              → 2
$ timeout 60 codex exec ... "<broken argument>"   → 125

$ timeout 60 cat  "<broken argument>"             → 125
$ timeout 60 echo "<broken argument>"             → 125

The last two lines are the answer. It has nothing to do with codex. The timeout on this machine is not the GNU one but the Rust rewrite (uutils coreutils 0.8.0), and it rejects invalid UTF-8 in its own arguments before doing anything. codex never starts.

The two programs print a first line that does not differ by a character, because both use the same Rust argument-parsing library. What differs is the second line and the exit code.

The hook before the fix had no timeout. So the value at the time would have been 2. The 125 is a value I produced while measuring now, and I nearly wrote it down as what happened back then.

The outcome is the same either way: not one character of review comes back. But I had the wrong idea about who did the rejecting. "The tool rejects the document" and "the wrapper around the tool rejects the argument" are different stories, and they get fixed in different places.

Three different things erased one signal each#

The failure itself is loud. The exit code is not zero and the message is plain. That it never reached me is down to three things I put in. They are not layers over the same thing. Failure leaves three signals and a different thing erased each one.

The first is the nastiest. > creates and empties the file before the command starts. So a file appears even when the tool emits nothing. Normally "there is no result file" would be the signal that something failed, and that signal never appears.

It is not that all three are required to hide it. Remove only 2>/dev/null and the reason survives; remove only exit 0 and the caller receives a non-zero value.

So there is a fourth, and it is outside the code. This hook is invoked automatically after an edit, and I never once looked at where its output went or who received its exit code. I only looked at the folder. I am the one who put the three in, and I am the one who did not look.

Meanwhile the folder kept filling up#

Opening the results folder, files were accumulating. So I believed it was running. Counted, it looks like this.

The table is counted; the meaning is not. Whether a zero-byte file means "called and failed" cannot be known, because stderr was being discarded. Failing to find the executable would look the same. And an absent file is not evidence that nothing was called.

And laid out like this, the odd spots stand out. The zero-byte files do, and so does a gap of more than two weeks. The reason I did not see them is that I never laid them out like this. I checked, now and then, only that the file count was going up. Not the sizes, not the gaps between dates.

The zero-byte file from 13 July is not explained by the cause in this article. The document was under 60,000 bytes then, so there was nothing to cut. The reason that one failed, I do not know.

In early August reviews with content kept coming. There were two design documents then, and the newer one was 31,965 bytes — under 60,000, so nothing to cut. The content of those reviews was about that newer document too. The output does not record a filename, so that is a guess from reading the content, and which review looked at which document cannot be told from the output.

So the folder looked even healthier. Every edit to the shorter document appeared to add another neat result.

Dropping one byte let it through#

The fix is one pipe: a conversion that drops invalid bytes.

DOC=$(head -c 60000 "$FILE" | iconv -f UTF-8 -t UTF-8 -c)

I ran the same document with and without it, side by side. The tool is codex-cli 0.153.4, run without timeout, as the hook was before the fix.

[without iconv]
  slice of 60,000 bytes → exit code 2 · stdout 0 bytes

[through iconv]
  slice of 59,999 bytes → exit code 0 · answered with the document's title, correctly

The difference is one byte. Drop the one fragment of a split character and the tool reads the document and answers.

Those numbers are the size of the slice, not the size of the argument that actually went over. Instructions and a filename go in front, and command substitution strips every trailing newline. So even a document under 60,000 bytes is not byte-for-byte identical inside the variable.

-c does not only drop the tail. It drops invalid bytes anywhere in the input, so corruption in the middle of a document is quietly deleted too. Here that is what I want; in general it is not.

And the iconv on this machine (GNU libc 2.43) prints a diagnostic and ends with 1 while dropping the tail. That is not a warning, it is ending in failure. The hook does not look at that status. Had the script been running under set -e, it would have died before ever calling the tool.

What I fixed and what I did not#

DOC=$(head -c 60000 "$FILE" | iconv -f UTF-8 -t UTF-8 -c)   # drop invalid bytes

ERR=".reviews/.last-design-err"                             # do not discard stderr
timeout 240 codex exec -m "$MODEL" --sandbox read-only "$PROMPT" < /dev/null > "$OUT" 2>"$ERR"
STATUS=$?

if [ "$STATUS" -ne 0 ] || [ ! -s "$OUT" ]; then
  rm -f "$OUT"                                              # leave no zero-byte file
  echo "[codex] design review FAILED (exit=$STATUS) — cause: $(tail -2 "$ERR" | tr '\n' ' ')"
fi
  • Only valid bytes survive the cut. The limit stays; only the fragment goes.
  • The tool's stderr goes to a log file. The failure message carries the last two lines of that log, bringing the reason to the screen. Only that one line's stderr goes to the log. The diagnostic from the iconv in front still leaks out.
  • A failure deletes the zero-byte file, so it cannot be mistaken for "reviewed".
  • < /dev/null was added. This hook runs behind the edit, so if the tool ever sat waiting on standard input, it could hang without anyone noticing. The instruction goes in as an argument, so it does not normally wait. This guards the case where an inherited input is still open.

Even this fixed version does not report failure properly. The failure branch ends with echo, so the script exits zero again. To a caller that does not watch the output it is still a success. Of the three things above, the third is still unfixed.

And names collide. The error log is a single file, so overlapping runs overwrite each other and the wrong cause gets attached. The result filename is a second-resolution timestamp, so two runs in the same second each truncate and write, mixing or corrupting it. The process id is now in the name, which covers the result side only; the log side is still open.

The result file still does not say which document was read. The filename is only a timestamp.

"A review ran" and "this document was reviewed" are different statements, and the folder only shows the first. Writing this article, I never did work out which documents August's reviews had looked at from the output alone.

I wrote the same defect down wrong three times#

This is the uncomfortable part. The day I first found this, I wrote the following into my rules document.

Measured: the design review hook has never once succeeded (zero design-* files in the results folder).

Both halves are wrong. That day the folder already held 38 design-* files, of which 5 were zero bytes. Counting only the committed ones gives 34; the other four had not been committed yet. I wrote "measured" and never counted. Then I copied that sentence into the hook's own comment.

This is the same shape as the defect I was fixing. I wrote down something unverified as if it were verified, and believed it was verified because it was written down. No checker catches this kind, so it survives until someone reads it again.

The right shape is this. Not "it never worked" but "for the document past 60,000 bytes, every revision that can still be measured is affected". And in the meantime other result files were still accumulating. A far less visible shape, and that is why it lasted longer.

I also no longer know what I was looking at when I wrote "zero". I may simply not have looked, or looked at a different folder. That there is no record of checking is all that can be verified now.

And the third one I made while writing this article. I put the exit code down as 125, and that was a value timeout produced. The hook before the fix had no timeout. So I nearly wrote a value made under my own hand just now down as something that happened back then.

All three are the same shape. The place I measured and the place I claimed were different. I moved "measuring here and now gives this" over into "that is what happened there and then". Exactly the mistake this article is about, and I made it once more in the middle of writing it up.

Limits: what this article does not claim#

  • What this article actually measured is “what happens when the documents that survive today are cut by that command”. What the hook received back then, and how it ended, is not recorded. The gap is inference, and the body keeps marking which is which.
  • The cause of the five zero-byte files is unconfirmed. stderr was being discarded, so the reasons from that time are gone. What the reproduction shows is one path that produces the same shape, not the cause of those five. The one from 13 July is not explained by that path.
  • "Unread for weeks" is not proved. What is proved is "every measurable revision is cut inside a character, and the tool rejects such an argument". The intermediate states in between are not preserved.
  • Why there were no reviews at all in mid-August is also unknown. The hook only fires for Edit and Write, so another path would not trigger it, but there is no record of what I used then.
  • This does not mean other documents always break. If the 60,000th byte lands between characters it does not. I simply found no such revision in this document.
  • Whether the fixed hook holds up over time is still unknown. There are four successful results since the fix, and I checked that failures are visible by deliberately breaking it once.

Closing#

  • Feed Korean into a tool that cuts by bytes and it can be cut inside a character. And that only starts once the document passes the limit. Below it there is nothing to cut and everything is fine.
  • > creates the file before the command. A file remains even on failure, and a file present reads to a person as "it worked".
  • Failure leaves several pieces of evidence, and there can be several covers. If the result, the message and the exit code are each covered by a different thing, fixing one changes nothing you can see.
  • "A check ran" and "this was checked" are different statements. If the output does not record what it looked at, you only get the first.

Writing down that you fixed a check and counting what that check actually did are different jobs. I did the first and looked at the folder.
