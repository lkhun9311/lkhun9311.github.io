When a Live Host Is Judged Dead, Recovery Becomes the Incident
A switch failure cut only the controllers from each other, and a healthy Compute node was judged dead — firing mass VM evacuation. Instead of sharpening detection, this is the failure-response design that re-decided which signal to trust.

Instance HA is the feature that, when a Compute host dies, evacuates the VMs on it to a healthy host and brings them back up. Automatic recovery. But the moment this feature is most dangerous is when it judges a host dead that isn't. Then the system forcibly moves VMs that are running fine and, with bad luck, corrupts data. Recovery becomes the incident.

This post walks through the failure-response design I wrote — after that incident actually happened — to keep it from recurring, in the order of situation, cause, and resolution. It ends with the complete architecture laid out as a table and a diagram.

First, the scope. This post is a write-up from the perspective of the target architecture I designed. After living through the incident, it draws the finished form against the question "what should the structure be" — where detect → judge → fence → recover form one safe chain. Implementation was carried on by the team, and exactly when each piece lands in the product is not this post's focus. The recovery time (RTO) below is a step-by-step estimate, not a measurement. Customer names, server addresses, hostnames, and accounts are not written here.

Who this is for#

  • Anyone designing or operating a system that auto-recovers dead nodes (Instance HA, the Masakari family)
  • Anyone who has seen automation make an incident worse under a network partition
  • Anyone who has to decide which signal declares "the node is dead," and how much to trust it
  • Anyone curious why Split-Brain and fencing must come before "fast recovery"

The day recovery became the incident#

The event summarizes in one line. During an L2/L3 switch failure, a leader controller judged a live Compute node dead and fired unnecessary Instance HA (Nova Evacuate) en masse. Healthy VMs were moved to other hosts at once, and in the worst case an evacuated copy could attach to the same volume while the original was still alive — corrupting the filesystem.

What matters here isn't "recovery was late" but "a recovery that should not have run, ran." A failure in this direction is far harder to undo.

Why a live server looked dead#

The crux is this. When a switch dies, each network ends up in a different state. One being cut does not mean all are cut.

Per-network state during an L2/L3 switch failure.
NetworkPurposeState on failure
MGMTController ↔ Compute management trafficalive
DATAVM data trafficcut
ControllerController ↔ Controller trafficcut
BMCFencing (power control)absent ← this was the problem

When controller-to-controller traffic is cut, the cluster's quorum collapses. Then some controllers judge, on their own, that "the Compute is dead." Yet MGMT was alive, so that Compute's Agent HeartBeat was being received normally. The node judged dead was, in fact, calmly reporting its own health.

My not being able to reach a node can mean the node is dead, or it can mean the path between me and that node is cut. Those are entirely different situations that look identical from the outside. The root of the incident was mistaking the observer's isolation for the target's failure.

I ranked the signals, not the detection#

The common prescription is "make detection more precise." But however high you push observation accuracy, when the observer is isolated, nothing it sees can be trusted. So instead of accuracy, I decided whose word to believe — ranking each signal by trust.

The four signal-trust tiers.
SignalTrustRole
Agent HeartBeatHighestThe Compute node reports its actual state directly
Controller QuorumHighThe controller cluster's consensus state
Network HeartBeatMediumController ↔ Compute connectivity
EXT Network ProbeLowJudges the controller's own network partition

The point is the bottom row. The EXT probe does not directly verify Compute state. It only checks reachability from controller to the outside, so judging whether Compute is up from it lands you straight in "the observer's isolation read as the target's failure." That is exactly what the incident was.

Next, I split a conflated judgment in two. "Is it really a failure" and "is it safe to act right now" are different questions — bundled together, they were contaminating each other.

Separating Phase 1 Failure Detection from Phase 2 Execution Readiness.
Phase 1 — Failure Detection (is it really a failure)Phase 2 — Execution Readiness (is it safe to act now)
Check quorum — if lost, the judgment can't be trusted → HoldStorage reachable — can the VM reach its storage

One aim of this split was to keep a storage-path failure from being misjudged as a "Compute failure" (by design). Putting storage in Phase 2 keeps it from contaminating the Phase 1 failure judgment.

The default is Hold — seven of eight stop#

Using the two phases, I judged eight failure scenarios. The result was Fencing for one, HOLD for seven. In this design, only one of eight cases was one where "actually running recovery" was allowed.

Run recovery wrongly and data breaks; hold and a human gets time to step in. An asymmetric cost set the verdict. So the default is to do nothing when you can't be sure, and a HOLD comes with an operator alert.

Confirm the power is off before you move#

Even when you've judged recovery to be allowed, there's something you must do before moving: confirm the original server's power is definitively off. Without this, Split-Brain happens.

Compute-01 → VM-A still running  → write /dev/vdb   (original attachment kept)
Compute-02 → VM-A evacuated      → write /dev/vdb   (new attachment)
        → concurrent write → filesystem corruption → data loss

So I set the principle as "no fencing = no recovery." If power-off (fencing) can't be confirmed, don't recover. The risk differs by storage type.

Scroll sideways to see the rest

Split-Brain corruption risk by storage type.
StorageCorruption risk
iSCSISCSI-3 PR exists, but a collision is possible if new access happens before the original attachment is cleaned up
LVMNo SCSI PR. High risk of VG/LV metadata corruption on concurrent write
NFSFile-lock based, so no consistency guarantee on concurrent mount/write

Fencing is done via IPMI power control. But there's a precondition. If the BMC (power control) network sits on the same physical switch as MGMT, IPMI is cut along with it when the switch dies. Then the very means to cut power is gone, and fencing is impossible. VLAN separation alone isn't enough — when a switch dies wholesale, the VLANs on it vanish too. So I pinned a dedicated physical switch for the BMC as a precondition. At the time of the incident, the BMC network was absent.

The recovery procedure splits into four stages: Detect → Verify → Fence → Recover. Within Fence there's a small but important order.

1. ipmitool chassis power off        (via the dedicated BMC switch)
2. wait at least 5s                  (time for power to actually drop; no immediate query)
3. ipmitool chassis power status  →  must confirm off
4. extra storage check               (varies by type)
5. run Nova Evacuate

Step 2 is the point. Query the state right after cutting power and it's not off yet. Check without waiting and "not off" gets read, so a perfectly good fencing is misjudged as a failure — or, going the optimistic way, you move the VMs of a server that never went down. Sending the command and confirming its result are different things, and inserting a wait between them is nearly the whole procedure.

A lock is not distributed consensus#

How to control "who runs recovery" also had to be decided. We already had Galera in house, so there was a pull to use its DB lock. I took apart three options against the same criteria.

The point is that a DB lock is not distributed consensus. A lock reduces double execution, but it doesn't stop both sides from each grabbing a lock under a partition. When the goal is Split-Brain prevention and you can't prevent it structurally, you don't meet the goal. So I recommended Pacemaker + Corosync first (~5s detection, and built-in STONITH so "no fencing = no recovery" is enforced by structure), with etcd as the fallback if that's hard to adopt.

The complete architecture — four layers, one chain#

Pulling the judgments so far together, this design is four layers linked in order: detect → judge/consensus → fence → recover. What matters is not the list of components but the order. Fail to pass an earlier layer and you don't advance, and the irreversible action (evacuation) sits only at the very end.

Scroll sideways to see the rest

The four layers of the complete architecture, with components and roles.
LayerComponentsRole
DetectAgent HeartBeat · multiple networks · BMC stategather "suspicion" of failure — distinct from a confirmed death
Judge · consensussignal-trust tiers · Quorum · Phase 1/2is it really a failure, and does this node hold the decision
Fencingconfirm IPMI power-off (STONITH)fail-closed guarantee that the original can no longer write
RecoverRecoveryMethod · evacuate/live-migration · StateCheckerselect targets and re-place them on a safe host

Rendered as close to code as possible (just the gist), the chain looks like this.

if (!quorum())                 return HOLD;   // the observer itself can't reach consensus
if (agentHeartbeat.isFresh())  return HOLD;   // Compute directly reports it's alive
if (extProbe.failed())         return HOLD;   // suspect my isolation — not the target's failure
if (!phase2.ready())           return HOLD;   // Storage · MQ · Nova API not ready
fence(host); confirmPowerOff();               // fail-closed confirm the original can't write
evacuate(targets);                            // only here do we finally move

In this chain, detection, the existing decision logic, and much of recovery already exist in code — the self-health gate (an isolated observer hands recovery off), target selection by metadata keys (HA_Enabled · HA_Disabled), and host selection by RecoveryMethod are those places. The safety axis of this chain — fencing and consensus (STONITH · Pacemaker/Corosync) — is the design's target, not a claim that it is active. Without that axis, however precise the rest is, it can't structurally prevent Split-Brain under a partition. That's why the design places this axis in the middle of the chain.

Limits: what this post does not claim#

  • This post is a write-up of the target architecture. My part was the 17-page failure-response design; implementation was carried on by the team. The chain above is not a confirmation that "it works this way" but a blueprint of "it should work this way."
  • Let me be clear about the residual risk. Until the safety axis, fencing, is actually turned on, Split-Brain prevention under a partition is not structurally guaranteed. So automatic recovery should not be treated as an unconditionally safe feature. The completion conditions are: confirm fencing success · stop recovery when the BMC is unreachable · fail-closed on quorum loss. And for that axis to stand, a precondition like a dedicated physical switch for the BMC must be in place first.
  • RTO ~100–160s is not a measurement. It's a per-stage estimate, and even the design doc marks it "needs team agreement."
  • What misjudged was the existing recovery logic, and I designed the decision system that followed to prevent recurrence. It was not logic I built that misjudged.
  • Product names, versions, customer, server addresses, hostnames, and accounts are not written. Network layout and parameters are generalized only as far as explaining the decision logic requires.

Closing#

One sentence stayed with me through this design. The quality of automatic recovery is decided less by how well it recovers than by how precisely it declines to. So I didn't go the route of sharpening detection; I ranked the signals, split judgment from execution, and set the default to Hold. That's why a design that stops seven of eight came out.

I expect the rebuttal: "if you hold seven, isn't recovery late on a real failure?" It is late. But a recovery run wrongly can't be undone. When Split-Brain corrupts the filesystem, it's not one VM but a whole volume. An asymmetric cost set the whole tone of this design. The moment automation is most dangerous is when it's most confident — this incident keeps reminding me of that.
