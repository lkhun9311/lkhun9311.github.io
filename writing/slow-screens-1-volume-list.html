A Volume List Went From a Ten-Minute Timeout to 23 ms
A hand-rolled cache was holding one key locked while it waited on an external API. An internal cloud admin console. Slow Screens, part one

Hello. I write the backend of an internal cloud admin console. Its volume list screen was running past ten minutes and timing out. It failed about five times in six.

After fixing it I split the work into six configurations and measured each one under the same load. That table is the whole article. It shows which change bought how much, and which change made something worse.

Who this is for#

  • You have parallelised a slow list query with CompletableFuture.
  • You have hand-rolled a cache on top of ConcurrentHashMap.computeIfAbsent.
  • You have thought “can’t we just grow the thread pool?”

What this is about#

  • Six configurations, measured one at a time. Measure only “before and after” and you never learn which change did the work.
  • Holding the cache fixed and switching sequential to parallel made the median 21x faster and P99 1.9x slower. Neither “faster” nor “slower” is the answer.
  • The largest drop in seconds came from adding one cache: a 579.0 s average became 13.1 s. The final 23 ms came from putting Caffeine’s refresh behaviour on top of that.
  • The hand-rolled cache had a defect. It never stored an empty answer, so it asked again every time there was nothing to find.

⚠️ The claim that parallelising can make things slower has its own article. That one holds the cache fixed and compares sequential against parallel. This one looks at all six configurations.

This is an internal product, so the code here is not the code that shipped. Product names, customers and internal addresses are gone; the structure and the numbers stay. Class names are generalised only as far as the story needs.

⚠️ One thing up front. The numbers below were measured with JMeter in an isolated test environment, not taken from production. The “ten minutes” is the load test’s own timeout ceiling, not a wait any real user sat through.

The screen#

An administrator opens it to see every volume in the system. For each volume, beyond the name and size, the screen also shows which project owns it, which volume group it belongs to and whether it has a recent error message. All three come from different APIs.

So one render of the list costs this many calls.

To render N volumes
  project lookup        N calls
  volume group lookup   N calls
  error message lookup  N calls
= 3N external API calls

More volumes, linearly slower. In the test environment this screen ran past ten minutes and timed out, with an error rate of 83.3%.

The guess: I thought sequential calls were the problem#

Those 3N calls were being made one after another, so the diagnosis looked easy.

It is slow because the calls are sequential. Go parallel and it drops a lot, maybe not by a factor of N, but a lot.

I built one task per volume with CompletableFuture.supplyAsync and handed them to an executor. To cut the repeated lookups I put a cache in front, a plain ConcurrentHashMap, since the same group id only needs fetching once.

The result: six configurations, measured separately#

In one line, this is it.

Measure only “before and after” and you never learn which change did the work. Measuring six configurations in turn showed that parallelising moves the median and the tail in opposite directions.

Here is the table first. The load was identical in all six runs. The median is the middle value once requests are sorted by response time; P99 is the line 1% of requests fall beyond on the slow side. Parallelising made the median 21x faster and the tail 1.9x slower. “It got slower” is not a sentence that describes this distribution.

Requests in the middle got faster. In exchange, the slowest 1% were pushed past 79 seconds. P99 does not mean “one user in a hundred waited 79 seconds”. It is the line 1% of requests fall beyond once you sort them slowest first. One user issues many requests, so it does not convert directly into a headcount.

Apdex rose from 0.014 to 0.526 as well. Apdex is the share of requests finishing within 0.5 s and within 1.5 s, not something derived from the median. It rose because more requests landed inside those bands. Read the mean alone and you get “1.13x slower”, one line that erases both directions at once.

Which configuration bought how much depends on which metric you ask. By the mean, the largest drop in seconds is 1 → 2: 579.0 s became 13.1 s, a saving of 565.9 s, and all that changed was adding one cache. The largest drop as a ratio is 5 → 6, which took 1.0 s to 5.3 ms. Both sentences are mean-based. Measured by the median the ranking changes.

⚠️ What inside configuration 5 bought what cannot be separated from this record. The source says only addMoreInfo() optimized. That it was a bundle of changes inside the function that builds one volume is as far as I could verify.

Cause 1: the network wait happened inside a lock#

Here is the shape of the problem.

final Map<String, VolumeGroup> groupCache = new ConcurrentHashMap<>();

final List<VolumeDto> dtos = volumes.stream()
    .map(v -> CompletableFuture.supplyAsync(() -> {

        // ← several threads enter this block at once
        final VolumeGroup group = groupCache.computeIfAbsent(
            v.getGroupId(),
            gid -> client.groups().get(gid)   // external I/O, called inside the lock
        );
        ...
    }, executor))
    .map(CompletableFuture::join)
    .collect(Collectors.toList());

N volumes means N tasks in the executor. If M of them share a group id, M threads enter computeIfAbsent on the same key at the same time. One of them makes the external round trip; the other M−1 wait right there.

And while they wait, those threads are still holding executor seats. So tasks for other volumes queue behind them.

⚠️ This causal story comes from reading the code, not from what the test proved. What the six configurations show is “hold the cache fixed, go parallel, it got worse” and no further. Whether that came from lock contention, thread switching cost, or a limit on the external API side, this test cannot separate. Separating them would need a parallel arm with the lock removed, and I did not run one.

Cause 2: an empty result was never cached#

The hand-rolled cache had one more defect, on the path that reads error messages. ⚠️ This one was written up on a sibling screen of the same product (project volumes), and I include it here because the structure is identical. The six-configuration table above is the admin volume screen.

List<Message> messages = manager.list(Message.class);

// if empty, the external API is called again every time
if (messages == null || messages.isEmpty()) {
    client.messages().list(...)
          .forEach(r -> manager.set(Message.class, r.getResourceUuid(), r));
}

Two problems overlap here.

  • Zero rows means nothing is stored, because forEach never runs. When a query returns nothing, that answer never reaches the cache, so the next request calls the external API again. ⚠️ The source does not record how often the result was empty. That the structure behaves this way is as far as I verified.
  • There is a gap between the check and the store. If several threads pass isEmpty() at once, all of them call the external API.

A cache that will not store “nothing” is not a cache for that answer.

Why: a ConcurrentHashMap still makes threads queue#

ConcurrentHashMap does not lock the whole map, which makes it easy to read “we used a concurrent data structure, so we are fine”. But computeIfAbsent locks the bin that key lives in and then runs the mapping function.

The same key is blocked completely, and for exactly as long as the mapping function takes. Even a different key is blocked too if its hash lands in the same bin.

If the mapping function is a memory computation, that is microseconds. Here it was a network round trip. Not milliseconds, but tens to hundreds of them.

⚠️ The internal document calls this a “segment lock”, which is not accurate. Segments are the Java 7 implementation; since Java 8 ConcurrentHashMap locks per bin. Use the wrong name and the next person goes looking in the wrong place.

The fix: not better locking, but removing the reason to lock#

⚠️ One thing first. computeIfAbsent also runs the mapping function once per key and makes the rest wait. Switching to Caffeine’s LoadingCache does not remove the queue. The difference is not whether threads queue but whether they queue holding the map’s lock, and that difference alone does not turn ten minutes into 23 ms. (If the mapping function returns null, nothing is stored and the next call computes again. Looking up a deleted group is one such path.)

So what this screen actually got was not better locking, but removing the reason to lock. The hand-rolled cache and its synchronized blocks came out and Caffeine went in. One loader per key is guaranteed, so there is no separate lock to write against a stampede.

What configuration 6 added is a refresh policy. Instead of dropping a stale value and making the next caller repopulate it, it hands back the old value and reloads behind them. ⚠️ That behaviour only appears once a value is there. The first request for a key waits for the loader to finish.

Five things actually changed on this screen.

  • The hand-rolled cache became Caffeine. What CacheManager and synchronized blocks were doing is now the library’s job.
  • Refreshing moved to the background. With refreshAfterWrite(5s), a list query returns the value it has immediately and the reload happens behind it.
  • The cache is filled at startup. An ApplicationReadyEvent triggers CompletableFuture.runAsync. It does not block startup. Which makes it not a device that removes the cold start but one that lowers the odds of meeting it. A request arriving before warming finishes still loads for itself, and the same holds if warming fails. ⚠️ The design document describes this step as “synchronous warming”, but the code says runAsync. I wrote down the code, not the document.
  • Creating or deleting a volume invalidates the cache, without leaving it empty. The existing value stays while a fresh read happens behind it and swaps in atomically.
  • The path that edits a volume group was not invalidating the volume cache. It cleared its own cache and left the volume DTO cache alone. That path now invalidates both.

Freshness: invalidating a cache slows down whoever comes next#

Add a cache and when to drop it comes with it. Creating or deleting a volume changes the list, so it has to be invalidated. But the query right after an invalidation goes out to the external API, and it is not the person who deleted something who pays that cost. It is whoever arrives next.

So it keeps the existing value and refills behind it. That is a trade between showing a briefly stale value and making one person slow. The five seconds has a reason behind it: the screen re-fetches the list every five seconds, so the team agreed that staying fresh within that cycle was enough.

That said, “five seconds” is not a ceiling. The volume list carries only refreshAfterWrite(5s) and no expiry. The reload starts when someone asks for the value again after those five seconds have passed, and that person receives the old value. If nobody asks, nothing refreshes. If the reload fails, the old value stays. Which means there is no fixed ceiling on how stale the value can get. Adding an expiry creates one, and at that moment you are back at the first paragraph of this section. Someone pays the cost.

Objection: “why not just add threads?”#

It is the first prescription anyone reaches for, and here it is wrong.

What blocks is not the thread count but a single key. More threads only means more of them standing in front of that key. Configurations 2 and 4 part company exactly there: going parallel made the median 21x faster and P99 1.9x slower. The queue did not get shorter, the distribution got wider. ⚠️ I did not measure the order in which requests finished. That two percentiles moved in opposite directions is everything this test says.

Growing the executor fails for the same reason. The queue does not shorten; the people queuing simply take up more seats.

Limits: what this article does not claim#

  • These are not production numbers. They were measured with JMeter in an isolated test environment. The “ten minutes” is the load test’s timeout ceiling, not a wait any user sat through.
  • This is not an argument that parallelism is bad. I suspect the network call inside a lock is why parallelism hurt in this code, and once that lock was gone parallelism pays. But the basis for that suspicion is the code, not this test.
  • It also did not have to be Caffeine. The property needed is “one loader per key”, not a particular library. You can write it yourself. Writing it myself is what caused this article.
  • I do not attribute all four screens to one cause. Each had slightly different secondary causes, and only the first one is written up in detail here.
  • The 23 ms is the aggregate P99 over all 7,658 samples, not a figure filtered to cache hits. What the source explains as a cache hit is the 4 ms median.
  • Configurations 5 and 6 cannot be attributed change by change. The source records 5 only as addMoreInfo() optimized, and several edits went in together.
  • This test cannot say why parallel got worse. The lock-contention explanation comes from reading the code.

Closing#

To gather it up.

  • Parallelising can make things slower, when it manufactures contention that was not there before.
  • A computeIfAbsent mapping function should be short and simple. The Java documentation says so. Put I/O inside it and that key stays locked for the whole round trip.
  • “Nothing” is a value too. A cache that will not store zero rows is not a cache for as long as the answer is zero rows.
  • Using a concurrent data structure and having no contention are different claims.

If one line survives, this one: measure only “before and after” and you never learn which change did the work. Only after measuring the six configurations separately could I see that parallelism has a harmful stretch in this code.
