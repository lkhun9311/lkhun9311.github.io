Instance HA ⑥: 復旧時間は一つの数字では書けませんでした
復旧時間を一つの数字で書こうとしてやめました。三つの段階に分け、サービス種別ごとに可否を書き添えてはじめて、合意できる値になりました。

⑤編までで判定と手順と構成が 決まりました。残る問いは一つです。この設計で復旧すると、どれだけかかるのかです。

設計書には「約100秒」と書いてあります。この編は、その数字がどう出てきて、なぜそのまま渡しては いけないのかという話です。

最初は一つの数字で書こうとしました。書いてみると、その数字を受け取った人にできることが ありませんでした。十分かどうかを判断する手がかりが、数字の中になかったからです。

この記事の想定読者#

  • 復旧目標時間をチームで合意する必要がある方
  • RTO の数字はあるが、それで足りるのか言いにくい方
  • 検知を短くしようという提案を受けて、代償を量る必要がある方
  • ①編から読んで、この設計がどこまで届いたのか気になる方

最初は一つの数字で書こうとしました#

一つの数字で書くと、二つのことができません。短くしようという話が出たときにどこを削るか指せず、 十分かという問いにも答えられません。どちらの答えも、数字ではなくその中の組み立てが 持っています。

そこで二方向に分けました。時間の側では段階ごとに、人の側ではサービス種別ごとに分けました。 前者はどこを削るかを教え、後者は削る必要があるのかを教えます。

三つの段階に分けて試算しました#

復旧は三つの段階を通ります。死んだと判定するまで、電源を落として確認するまで、ほかのホストで 立ち上げ直すまでです。

横にスクロールすると残りが見えます

復旧時間の段階ごとの試算。
段階所要一番大きい変数
検知 (TTL 30秒)約30秒TTL と判定の周期
IPMI Fencing5〜10秒電源確認までの待ち
Nova Evacuate と VM 起動60〜120秒イメージの大きさと Storage 種別
合計 (現設計)約100〜160秒右の三つの積み上げ

一番長い区間は検知ではなく立ち上げ直すほうで、幅も一番広いです。検知を半分に しても（30秒→15秒）合計は9〜15パーセントほどしか縮みません（下限100秒基準で15パーセント、上限160秒基準で9パーセント）。 削る場所を探すには、まず段階を分ける必要があります。

ここまでは試算です。あとで実際に測った記録が残っています。

実測は試算より短く出ます。試算が段階ごとに上限を取ったから です。同じ表から復旧方式が二つに分かれることも見えます。Compute のサービスが生きていれば live migration へ、通信が切れていれば evacuate へ進みます。

100秒は一台を復旧するときの数字でした#

ここまでの試算はすべて一台を復旧するときの数字です。ノードが落ちると、その上に 載っていた Instance が一度に対象になります。一台ではなく二十台です。

一度に復旧すると共用の保管所の側でエラーが急増しました。同じ 10G の網で五個目から エラーが増え始め、十個を同時に実行したときは二個しか成功しませんでした。

そこで同時に実行する最大数を設定として置き、一台の移送が終わってから次を始めるように 変えました。一度に投げるほうがむしろ遅いのです。失敗した分をやり直すことに なるからです。

横にスクロールすると残りが見えます

同時復旧のために変わった設定と、その理由。
変わったものどう変えたかなぜ
同時復旧の最大数設定した数を超えないよう制限する共用の保管所が同時の要求を受け切れない
次の復旧を始める時点一台の移送が終わってから次を始める一度に投げると失敗分をやり直すことになり、かえって伸びる
検知周期の最小値20秒から10秒へ下げた前半は縮められる。後半はこの値では縮まらない
復旧の総時間一台基準の数値に待ち行列の長さを掛けるノードに載った Instance の数が実際の RTO を決める

これが前の節の試算を読み直させます。100秒は待ち行列の先頭に立つ一台の 数字です。最後尾の Instance にとって RTO は、前に何台いるかで決まります。検知周期を20秒から 10秒へ下げても、この区間は縮みません。

同じ100秒がサービスごとに違います#

時間を分けても、十分かという問いにはまだ答えられません。その答えは設計ではなくサービスが 持っています。

横にスクロールすると残りが見えます

サービス種別ごとの許容基準。
サービス種別判定根拠
Stateless API サービス許容再試行で吸収でき、状態が残りません
DB 基盤のサービス危険Downtime のあいだのデータ整合性を別に見る必要があります

同じ試算値なのに判定が三つに分かれます。NFV はこの設計を手直しして届く値では なく、アーキテクチャを変えるべき場所です。 その判断は開発者が一人で下せるものではありません。

設計書に「RTO 目標、チーム合意が必要」と書いた理由がこれです。数字を合意事項として挙げたので あって、目標を決めてしまったわけではありません。

縮めることはできますが代償があります#

短くする方法そのものはあります。検知の区間は外部 Probe の TTL が決めるので、再試行の回数を 減らせば30秒が15秒になります。

# 現設計: 5秒間隔で六回外すと死んだとみなします
probe_interval=5s
probe_retry=6      # 30s TTL

# 短縮案: 三回に減らすと TTL が15秒になります
probe_retry=3      # 15s TTL

# 代償: 一瞬の遅れを死と読む余地も一緒に広がります

ただし②編で見たとおり、その TTL は一瞬の遅れと本当の停止を分ける値でもあります。短く取るほど、 遅れを死と読む余地が広がります。縮むのは復旧時間で、広がるのは誤判定の可能性です。

だから短縮案を書くときに代償も一緒に書きました。短くできるとだけ言えば、受け取った人は決められ ません。

設計書がどこまで届いたか#

この連作の成果物は設計書です。実装はほかのチームメンバーが引き継ぎ、私はそこに参加していません。 ですからこの設計が参照されたかを言うには、私の言葉ではなくほかの人の文書を見る必要があります。

同じ時期に出た別の検討文書が、この設計書を引用しています。その文書の結論は「観測地点が壊れて いるときは復旧を実行すべきでない」というもので、これは設計書の保留ロジックと Phase 分離と同じ 内容です。

限界: この記事が主張しないこと#

  • ⚠️ 約100秒から160秒は試算値であって実測ではありません。段階ごとの既知の所要を 足した値で、設計書にもチーム合意が必要な項目として書かれています。
  • 私はこの値を達成したことがありません。設計段階で試算し、種別ごとの基準を提案したところまでが 私の範囲です。
  • サービス種別の三つは判断を助ける区分であって、すべてのサービスがこの三つのどれかに入るという 意味ではありません。
  • 後続の文書が設計書を引用したことまでは文書で確かめました。二つの文書の前後関係と作成の履歴は 確かめられていないので、それ以上は書きません。
  • 社内資料なので、製品名と顧客名とアドレスとアカウントとホスト名と課題番号と作成者名は書いて いません。

おわりに#

この連作を貫くものは一つです。判断の根拠を一つの数字や一つの信号に寄せてしまうと、それが 間違っていたときに抜け道がありません。既存の復旧ロジックが観測地点を一つ信じて生きている ノードを死んだと見たのが①編で、そのあとはすべて根拠を分ける話でした。

信号を証言できる範囲で分け、障害かどうかと今実行してよいかを分け、命令と確認を分け、合意と Fencing を分け、最後に時間を段階とサービスに分けました。

⑦編は移すと決めたあとの話です。装置を要求する Instance をどこへ送るかを決める部分へ続きます。
