②編で信号ごとに証言できる範囲を 決めました。ところが等級を付けるだけでは判定が立ちません。等級の高い信号が正常だと言うとき、何を してよいかが残るからです。

設計書を書きながら最も長く向き合ったのがこの場所でした。従来の判定には性格の違う二つの 問いが一塊に溶け込んでいました。「本当に障害か」と「今復旧を実行してよいか」です。二つは 答える時点も根拠も違うのに、一行で判定されていました。

この編はその二つを Phase 1 と Phase 2 に分けた話です。分けたうえで同じ基準で障害シナリオ八つを 判定したところ、復旧してよいものは一つでした。

想定読者#

  • 自動復旧の判定条件を設計あるいは改修している方
  • Storage やメッセージキューの障害がノード障害として読まれる場面を見たことがある方
  • 判定ロジックを表とコードのどちらで残すか迷っている方
  • ②編を読んで、等級が実際の判定にどう移るのかが気になる方

一つの判定に二つの問いが混ざっていました#

混ざっていると何が問題かは一つの場合で表れます。Compute は正常なのに Storage へ届かない状況です。 以前の判定はこれを障害信号として受け取り復旧対象に上げていました。ところがStorage へ届かない 状態で VM を移すと、移った先でもディスクを書けません。

そこで二つの問いを分けました。前半は対象の生死だけを見て、後半は実行可否だけを見ます。この分離が 生んだ効果が一つあります。Storage の条件を後ろへ移したことでStorage 障害が障害判定を汚染する 経路が閉じました。

Phase 2 は今実行してよいかだけを見ます#

横にスクロールすると残りが見えます

Phase 2 の条件と目的。
条件なぜ見るか
Storage へ到達可能移った VM がディスクを書けなければなりません
RabbitMQ が正常復旧コマンドが伝わらなければなりません

三つの条件は対象の生死とは無関係です。すべて復旧を実行できる状態かを問います。 一つでも欠ければ障害が確定していても実行しません。

順序をコードで固定しました#

表だけで置くと読む人ごとに順序が変わります。そこで設計書には判定の順序を擬似コードで書きました。 抜け道が一つだけだということがこのコードの要点です。

[Phase 1 - 障害か]
1. Quorum 確認
   Quorum 喪失 -> 判断を信頼できない -> Hold

2. Agent HeartBeat 確認
   TTL 以内で正常 -> Compute は正常 -> Hold

3. TTL 超過なら追加検証
   EXT Probe の結果 - nova-compute の状態 - Storage session
   確信が持てなければ -> Hold (運用者へ通知)

[Phase 2 - 今実行してよいか]
1. Storage へ到達不可 -> Hold
2. RabbitMQ が異常     -> Hold
3. Nova API が異常     -> Hold
4. すべて正常          -> Fencing を実行

八つのうち七つは止まります#

この基準で障害シナリオ八つを判定しました。結果はFencing 1 件と Hold 7 件でした。

横にスクロールすると残りが見えます

八つのシナリオの判定。
シナリオPhase 1 の結果処置
Compute が実際に crash障害確定Phase 2 へ進み Fencing
Controller ネットワーク断判断不可Hold
DATA ネットワーク断Partition の疑いHold
MGMT ネットワーク断判断不可Hold
Storage 経路の障害Compute は正常Hold (Phase 2 で停止)
EXT のみ不達Compute は正常Hold
HeartBeat 超過で EXT も失敗Partition の疑いHold のうえ追加判断
Controller 断だが HeartBeat は受信判断不可Hold (単独判定の禁止)

七つが Hold だということは七つが間違いだという意味ではありません。今ある信号では 復旧してよいと言う根拠が足りないという意味です。誤って実行した復旧は取り消せず、保留は人が介入する 時間を残します。

限界：この記事が主張しないこと#

  • ⚠️ この連作の成果物は設計書です。実装は別のメンバーが引き継いでいます。「誤判がなくなった」では なく、誤判の経路を塞ぐ設計を提案したということです。
  • 判定表には空欄があります。信号の等級には Network HeartBeat があるのに統合ロジックにも判定表にも その列がなく、Phase 2 の三条件のうち表には Storage しか出てきません。設計書自体の未完成です。
  • 表の二行は入力値が同じです。Controller ネットワーク断と、Controller 断だが HeartBeat を受信する 場合が同じ値で書かれており、何が二つを分けるのかを表が語れていません。
  • 社内資料のため製品名・顧客名・アドレス・アカウントは書いていません。

おわりに#

この編の結論は一行です。一つの判定に性格の違う二つの問いを入れると、どちらも外します。 分けたことで Storage 障害が Compute 障害として読まれる経路が閉じ、八つのうち七つが止まることが奇妙な 結果ではなく当然の結果になりました。

次の編はその一つが通ったあとの話です。移す前に元のホストの電源を確認する手順へ続きます。④編へ進みます。
