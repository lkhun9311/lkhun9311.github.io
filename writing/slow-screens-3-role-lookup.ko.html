프로젝트 역할 조회가 1,409ms → 1ms로 줄었습니다
못 찾은 프로젝트 id마다 전체 목록을 다시 부르고 있었습니다.

2026년 9월

사내 Cloud 관리 Console의 Backend를 만들고 있습니다. 이용자 한 명을 열면 아래쪽에 그 사람이 어느 프로젝트에서 어떤 역할인지가 표로 나옵니다. 그 표가 1초를 넘겨 로딩만 돌고 있었습니다.

역할 자체는 우리 DB에 있는데 프로젝트 이름은 OpenStack 쪽, 정확히는 이용자와 프로젝트를 맡는 Keystone에 있습니다. 그래서 역할 한 줄마다 프로젝트를 한 번씩 찾아야 하고 그 찾는 자리에는 이미 Cache가 있었습니다. ①편에 나온 그 CacheManager이고 보관 기간은 10분이었습니다.

그러니까 이 글은 ‘Cache를 넣었더니 빨라졌다’가 아닙니다. Cache가 있는데 그 Cache 때문에 느렸던 이야기입니다.

조회 한 건마다 찾았는지 못 찾았는지와 걸린 시간을 이미 찍고 있었습니다. 고치기 전 실행의 로그를 열어 보니 역할 14줄 가운데 여덟 줄은 0ms였고 나머지 여섯 줄이 각각 230ms 안팎이었습니다. 그 여섯을 더했더니 1,409ms, 그 실행에서 타이머가 찍은 총계와 같았습니다. 그때 물음이 바뀌었습니다. ‘Cache가 왜 안 도와주나’가 아니라 ‘못 찾은 줄 하나가 왜 235ms인가’입니다.

이 글의 예상 독자#

  • Cache를 넣었는데 기대만큼 안 빨라진 화면을 보신 분
  • 못 찾았을 때 무엇을 다시 불러올지 정해 본 적이 있는 분
  • 없는 것을 찾는 조회가 있는 줄 모르고 지나쳐 보신 분

역할 한 줄이 프로젝트 이름에 닿기까지#

로그가 이미 찍고 있던 것#

그 로그를 그대로 옮기면 이렇습니다. logger 이름과 project id는 가렸고 밀리초는 원본입니다.

[Miss] projectId=project-A   elapsed  247 ms
[Miss] projectId=project-B   elapsed  235 ms
[Hit ] projectId=project-C   elapsed    0 ms
[Hit ] projectId=project-D   elapsed    0 ms
[Miss] projectId=project-E   elapsed  238 ms
[Miss] projectId=project-F   elapsed  228 ms
[Miss] projectId=project-G   elapsed  233 ms
[Hit ] projectId=project-H   elapsed    0 ms
[Hit ] projectId=project-I   elapsed    0 ms
[Hit ] projectId=project-D   elapsed    0 ms
[Miss] projectId=project-J   elapsed  228 ms
[Hit ] projectId=project-D   elapsed    0 ms
[Hit ] projectId=project-H   elapsed    0 ms
[Hit ] projectId=project-K   elapsed    0 ms
[Result] Total elapsed time: 1409 ms

247 + 235 + 238 + 228 + 233 + 228 = 1,409

못 찾은 여섯 줄만으로 총계가 채워집니다. 찾은 여덟 줄이 각각 정확히 0이었다는 뜻은 아닙니다. DTO를 만들고 거르고 정렬하는 비용은 각 줄의 구간 밖에 있고 1ms 아래면 이 해상도에서는 이렇게 보입니다.

원인: miss 1건이 전체 목록을 다시 불렀습니다#

프로젝트를 찾는 코드가 이렇게 생겼습니다.

public static Project project(final String projectId) {
    CacheManager manager = CacheManager.getInstance().init(Project.class, 10);
    final Project project = manager.get(Project.class, projectId);

    if (project == null) {                       // ← 키 1개가 없다
        client.identity().projects().list()      // ← 전체 목록을 다시 받아
              .forEach(r -> manager.set(Project.class, r.getId(), r));
        return manager.get(Project.class, projectId);   // ← 다시 찾아본다
    }
    return project;
}

읽으면 그럴듯합니다. 없으면 채워 넣고 다시 본다. Cache를 처음 쓸 때 자연스럽게 나오는 모양이고 실제로 처음 한 번은 이게 맞습니다.

문제는 ‘채워 넣어도 없는 키’가 있을 때입니다.

그 6건은 채워 넣어도 없었습니다#

역할 표는 우리 DB에 있고 프로젝트는 OpenStack에 있습니다. OpenStack 쪽에서 프로젝트를 지워도 우리 역할 표의 그 줄은 그대로 남습니다. 그 줄이 가리키는 projectId는 이제 어디에도 없습니다.

그러면 위 코드가 이렇게 돕니다.

  1. Cache에서 찾는다 → 없다
  2. 전체 목록을 다시 받는다 → 235ms
  3. 다시 찾는다 → 여전히 없다. 지워진 프로젝트니까요
  4. 다음 줄에서 또 없는 id를 만난다 → 1번으로

없는 id를 만날 때마다 프로젝트 전체 목록을 새로 받았습니다. 새로 받아도 그 6개 id는 목록에 없으므로 다음 줄에서도 똑같이 받습니다.

못 찾은 6줄은 제가 가진 3번의 실행에서 모두 같은 6개 id였습니다. 고치기 전 1회와 고친 뒤 2회이고 날짜도 하루 차이가 납니다. 우연히 비어 있던 것이 아니라 채워질 수 없는 자리로 보입니다. 3회는 3회입니다. 그 이상 돌려 보지 않았습니다.

수정: 키로 찾지 말고 목록을 걸렀습니다#

고친 것은 찾는 방식 하나입니다.

// 전: 키 1개를 cache에 묻는다. 없으면 외부 API를 부른다
var project = CacheBox.project(roleAssignment.getProjectId());

// 후: 목록을 cache에서 받아 그 안에서 거른다. 없으면 없는 채로 끝
var project = CacheBox.projects().stream()
        .filter(p -> p.getId().equalsIgnoreCase(roleAssignment.getProjectId()))
        .findFirst();

projects()도 외부 API를 부를 때가 있습니다. 다른 것은 ‘그 id가 없다’가 더 이상 외부 API를 부르는 조건이 아니라는 것입니다.

정확히는 이렇습니다. projects()는 Cache에서 목록을 받아 오는데 이때 만료된 항목을 하나씩 걸러 냅니다. 그렇게 걸러 낸 결과가 완전히 비었을 때만 외부 API를 부릅니다.

여기에 함정이 하나 있습니다. 일부만 만료되면 부르지 않습니다. 살아남은 항목이 하나라도 있으면 그 불완전한 목록을 그대로 돌려주고 그 사이에 빠진 프로젝트는 있는데도 ‘못 찾음’이 됩니다. 이번 실행에서는 항목들이 한꺼번에 채워져 한꺼번에 만료되므로 드러나지 않았습니다. 드러나지 않았다는 것이지 없다는 뜻은 아닙니다.

로그가 그대로 보여 줍니다. Cache가 만료된 상태에서 한 번 돌리면,

[Miss] projectId=project-A   elapsed  246 ms   ← 목록을 받아 오는 호출
[Miss] projectId=project-B   elapsed    0 ms
[Hit ] projectId=project-C   elapsed    0 ms
…
[Miss] projectId=project-J   elapsed    0 ms
[Result] Total elapsed time: 250 ms

miss는 여전히 6번입니다. 그런데 그중 5번이 0ms입니다. Cache가 유효한 상태에서는 첫 번째도 0ms가 되고 총계가 1ms가 됩니다.

가로로 스크롤하면 나머지가 보입니다

역할 조회 1건의 상태별 구간 총계.
상태역할 줄못 찾음못 찾은 1줄의 시간구간 총계
고치기 전146228~247ms1,409ms
고친 뒤 · Cache 만료146첫 1건만 246ms250ms
고친 뒤 · Cache 유효1460ms1ms

가운데 칸이 세 줄 다 6입니다. 못 찾는 횟수를 줄인 적이 없습니다. 바뀐 것은 오른쪽 두 칸입니다. 세 줄 모두 1회 관측입니다. 반복해서 분포를 본 값이 아닙니다.

대신 잃은 것: 새 프로젝트가 늦게 보입니다#

고치기 전 코드에는 안 쓰이던 쓸모가 하나 있었습니다. 모르는 id를 만나면 목록을 다시 받았으니, 방금 만든 프로젝트가 곧바로 보였습니다. 느린 대신 최신이었던 것입니다.

고친 뒤에는 모르는 id를 만나도 아무것도 안 합니다. 그래서 새 프로젝트는 Cache가 다시 채워질 때까지 안 보입니다.

그 ‘다시 채워질 때’가 10분이라고 못 박을 수는 없습니다. 보관 기간은 목록 단위가 아니라 항목마다 기록된 저장 시각에 걸립니다. 그리고 project()는 지워지지 않고 남아 있어서 다른 화면에서 그 함수가 한 번 돌면 항목들이 통째로 다시 채워집니다. 그러면 시각이 갱신되어 더 늦게 보일 수도, 마침 그 순간에 채워져 더 빨리 보일 수도 있습니다. 말할 수 있는 것은 다른 곳에서 채우지 않는다면 마지막 항목이 만료된 뒤 첫 조회에 반영된다는 것까지입니다.

지연을 없앤 것이 아니라 지연과 최신성을 맞바꾼 것입니다. 이 화면은 사람이 눈으로 읽는 목록이라 10분을 받아들일 수 있었습니다. 그 판단이 안 되는 화면도 있습니다.

그리고 원인은 그대로 남았습니다#

느린 것의 직접 원인은 못 찾을 때마다 전체 목록을 다시 부르던 조회 방식이었고 그 방식을 6번이나 밟게 만든 데이터 조건이 없는 프로젝트를 가리키는 역할 줄 6개였습니다. 둘은 다른 것입니다.

제가 고친 것은 앞의 것입니다. 뒤의 것은 지금도 그대로 있습니다. 그 줄들이 비싸지 않게 됐을 뿐 없어지지는 않았습니다. OpenStack에서 프로젝트가 지워질 때 우리 역할 표도 같이 정리되게 하는 것이 원래 할 일이고 그건 이 작업에 들어 있지 않았습니다.

한계: 이 글이 주장하지 않는 것#

  • 측정이 System.currentTimeMillis()와 log.info입니다. currentTimeMillis()는 단조 시계가 아니라 시스템 시각이 바뀌면 값도 흔들립니다. 그리고 각 줄의 구간 안에 로그 출력 1회가 들어가 있고 그 뒤의 로그 1회는 빠져 있습니다. 0ms는 ‘1ms 미만’이라는 뜻이지 ‘비용이 없다’가 아닙니다. 제대로 하려면 System.nanoTime()이나 timer metric으로 재고 외부 API 호출 횟수는 따로 세어야 합니다.
  • 1회 실행입니다. 세 상태를 각각 한 번씩 돌린 로그이고 반복해서 분포를 본 것이 아닙니다. 235ms라는 값도 그 6건의 평균일 뿐입니다.
  • 왜 목록 1회가 235ms인지는 파고들지 않았습니다. 네트워크인지 Keystone 쪽 처리인지 프로젝트 개수 때문인지 가르지 않았습니다.
  • 프로젝트가 몇 개였는지 기록에 없습니다. 그래서 ‘목록이 커서 느리다’인지 ‘호출 자체가 비싸다’인지도 이 로그로는 모릅니다.
  • 고친 코드도 완전하지 않습니다. projects()를 역할 1줄마다 한 번씩 부릅니다. Cache가 따뜻할 때는 0ms라 드러나지 않지만 줄이 아주 많아지면 목록을 반복해서 훑는 비용이 남습니다. 반복문 밖으로 한 번만 꺼내는 것이 낫습니다.
  • 이 Cache는 ①편의 문제를 그대로 안고 있습니다. projects()에 잠금이 없어서 Cache가 비는 순간 요청이 여럿 들어오면 각자 외부 API를 부릅니다. ⚠️ 코드를 읽고 하는 말이고 이 로그로 확인한 것은 아닙니다. 이용자 1명을 연 실행이라 동시 요청이 없었습니다.
  • 운영 통계가 아닙니다. 테스트 환경에서 이용자 1명을 연 로그입니다.
  • 1,409ms는 화면 응답 시간이 아닙니다. 타이머가 DB 조회가 끝난 뒤에 시작해서 역할 줄을 DTO로 바꾸는 구간만 잽니다. DB 조회와 직렬화·전송은 그 바깥이라 사용자가 기다린 시간은 이보다 깁니다.
  • 로그의 [Hit]·[Miss]는 Cache 안을 잰 이름이 아닙니다. CacheBox를 부른 결과로 프로젝트가 돌아왔는지만 보고 붙였습니다. Cache에서 제대로 읽었는데 그 id가 목록에 없어서 [Miss]가 되기도 합니다. 본문에서는 ‘찾음 · 못 찾음’으로 불렀습니다.
  • 줄별 밀리초는 사내 문서에 붙어 있는 로그 갈무리를 보고 손으로 옮긴 값입니다. 문서 본문에 숫자로 적혀 있는 것은 총계(1,409ms · 250ms · 1ms) 쪽입니다.

마치며#

Cache가 있다는 것과 빠르다는 것은 다릅니다. 찾은 줄이 전부 0ms인데도 구간이 1,409ms였고 원인은 못 찾았을 때 무엇을 하느냐 쪽에 있었습니다. ‘없으면 전부 다시 받는다’는 처음 한 번에는 맞고 채워도 안 생기는 id 앞에서는 가장 나쁜 선택입니다.

줄일 수 있는 것은 두 가지였습니다. 못 찾는 횟수와, 못 찾았을 때 드는 시간. 이번에 줄인 것은 뒤쪽이고 앞쪽은 그대로 남아 있습니다. 대신 잃은 것은 10분어치의 최신성입니다.

그리고 이 일은 이미 찍히고 있던 로그를 더해 보기만 하면 되는 일이었습니다. 그 여섯 줄을 더하기 전까지 저는 ‘Cache가 왜 안 듣지’를 들여다보고 있었습니다.
