A Performance Review That Found No Case to Change Anything
A cache where there is little to save buys staleness and complexity instead. An internal cloud admin console. Slow Screens, part seven

Hello. I write the backend of an internal cloud admin console. A report came in that monitoring was slow, so I reviewed three screens.

The conclusion was “I could not find a case for changing anything.” This part is about a review that decided to do nothing. ⚠️ That is a different sentence from “there was nothing to fix”, and the article keeps that distinction throughout.

⚠️ This conclusion turned out to be wrong. Measuring first data on the same screen again gave 6.8 seconds, and adding a cache in the very place this article declined to put one brought it to 23 ms. What I had failed to measure is written up in “The Screen I Said Not to Fix Took 6.8 Seconds”. The text below stays as it was written.

Who this is for#

  • You get a report that something is slow and have to decide where to look first.
  • A load test came back looking good and you were not quite convinced.
  • You have to decide whether to add another cache.

What this is about#

  • I reviewed three screens and found no case for a new optimisation. One slow spot was already fixed in part four, and for the rest nothing came up that would justify a change. ⚠️ That is not the same sentence as “there was nothing to fix”.
  • No further cache went in. Where one would have gone there was little to save, and putting a cache there buys staleness and complexity instead.
  • One setting that looked excessive was left alone deliberately. The query window was wider than needed, and narrowing it made the graph flicker.
  • ⚠️ And I never ran a load test. I judged from the code that the usual scenario would produce a flat graph on this architecture, and did not confirm it by running one.
  • A review that ends in “do nothing” is hard to check afterwards. Nothing was done, so there is nothing to compare. That part is in here too.

This is an internal product, so neither the code nor the screens are reproduced as they are. Product names, customers and internal addresses are gone; only the structure and the configured values stay.

What was reviewed#

There are three monitoring screens: dashboard, physical resources and virtual resources. All three read values from a time-series store and draw graphs.

“It is slow” arrives without distinguishing between them. So the first job was working out which stretch of which screen was slow.

Dashboard and physical resources: already filled in the background#

These two do not go out when a request arrives. There is a place inside the backend that holds values in advance (a cache) and they read from it. That place fills itself in the background every 60 seconds. A held value is discarded after five minutes.

So the request path does not wait. Going outside happens at a time unrelated to any request.

Turning “go outside on every request” into “fill it in advance in the background” takes the waiting out of request handling. For these two, that change was already done.

Before that it was a loop that slept. Code that slept briefly inside a loop and checked again; earlier work had already removed it. This review looked at the state after that.

So no further cache went in#

The remaining candidate was the value computed every 15 seconds. “Why not cache that too?” is the natural next thought.

But that computation runs once every 15 seconds. And however many screens are open, it runs once. One result is built and the same value goes to every open screen. On the read side it pulls six measurements from the time-series store in a single query.

The left column has one row, and that row runs once per 15 seconds. ⚠️ This is not a measurement of “cheap”. Looking at the frequency and the structure, I judged there was little to save. How many milliseconds that computation takes, or how much CPU it uses, was never measured. As part four says, frequency alone does not settle cost.

Put a cache where there is little to save and you get more to handle than you gain. A cache is a tool for making expensive things cheap. Here I could not find evidence that it was expensive, so none went in.

An excessive-looking setting, left deliberately#

Something caught my eye during the review. Drawing the graph read the last 180 seconds. On a screen that refreshes every 15 seconds, 180 is twelve times wider.

I started narrowing it and stopped. Narrowing makes the graph flicker. If collection runs a beat late or misses once, the window holds no points at all, and the graph briefly shows “no data” before coming back.

A wide window keeps the graph from emptying when a value briefly does not arrive. ⚠️ The cost of keeping it wide was not measured. I saw the flicker when it was narrowed; what a wide window costs, I do not know. The internal record only says “excessive but cheap”.

I left it. A value that looks excessive is sometimes preventing something, and this was one of those.

No load test was run#

Normally you turn on a load tool here. I did not. The reason is written out in part four; here it is two lines.

A scenario that holds connections open and only adds users exercises the stretch that computes once every 15 seconds. That computation runs once regardless of how many are connected, so adding users does not move its count. ⚠️ What is independent is the computation count; writing the result out to each connection grows with the number of connections. And a scenario where each user opens the screen afresh runs the initial load that many times too.

⚠️ This is a prediction. I judged from the structure of the code that it would come out that way, and did not confirm it by running anything.

The axis that would mean something is not concurrent users but the number of projects, and the record says so. ⚠️ It says so and nothing was measured.

A review that ends in “do nothing” is hard to check#

This is the most uncomfortable part of the article.

Fix something and you can compare before and after. Skip it and there is nothing to compare. Whether nothing happened because no cache went in, or whether something better was missed by not adding one, this review cannot tell.

So what was done was looking at the same thing twice, separately. The record says only “two independent reviews, conclusions converged”. ⚠️ Who asked what, and when, is not recorded; what survives is that it was looked at twice and the conclusion was the same.

Even so this is a review, not a measurement. Looking twice and agreeing does not make it right. If it is wrong, it is wrong the same way twice.

Limits: what this article does not claim#

  • There is no record of a load test being run. “Flat however many users you add” is a prediction from reading the code, not an observation. No sentence in this article cites a load-test result.
  • “Little to save” is not a measured figure. The basis is frequency and structure — once per 15 seconds, independent of viewer count. How many milliseconds that computation takes, I do not know.
  • “A wide window is not much more expensive” is not measured either. The flicker on narrowing is something I saw; the cost of keeping it wide was never measured.
  • This is a judgement made at one point in time. With more resources or more screens the same review could reach a different conclusion.
  • I cannot prove that not adding a cache was better than adding one. Nothing was done, so there is nothing to compare it against. This article carries that limit.

Closing#

Pulling the seven parts so far together.

  • “It is slow” does not point at a stretch. Working out which stretch of which screen comes first, and that work is half of it.
  • A cache is a tool for making expensive things cheap. Put one where there is little to save and you keep the staleness and the complexity; leave one unread and it is worse than none.
  • What was not measured gets written down as not measured. Two of these seven parts have no before-and-after figures, and each says so in its own text.
  • Deciding not to change something still needs a reason. And that decision is harder to check afterwards than one that changed something.

If one line survives, this one: half of performance work is not finding what to fix but ruling out what does not need fixing. That is what this review actually did.
