The Monitoring Screen I Said Not to Fix Took 6.8 Seconds
I measured a boundary users were not waiting on. An internal cloud admin console. Unified Monitoring, part one

I build the backend of an internal cloud admin console.

In part seven I reviewed three monitoring screens and wrote that I could not find a case for changing anything. That article also contains this sentence. “I decided not to add more cache. The place I was going to add it was already a cheap path, and a cache there buys staleness and complexity.”

First data on that screen took 6.8 seconds. And the fix was a cache in exactly that place. It became 23 ms.

This is the story of why that judgement was wrong, and of what I had failed to measure. Four parts after this one go screen by screen.

Who this is for#

  • Anyone whose load test looks good while users keep saying the screen is slow
  • Anyone pushing first data over SSE or WebSocket
  • Anyone who has written off a path as “already cheap” and moved on

What is in here#

  • An article I published reached the wrong conclusion. I wrote that there was no case for a change, and first data on the same screen was 6.8 seconds.
  • What was wrong was not the arithmetic but where I measured. I measured the REST response. The user was waiting for the first SSE data event.
  • “The time-series store is cheap because it runs once every 15 seconds” was true only of the periodic refresh. The same computation also ran synchronously on every new connection.
  • I fixed the three screens one at a time, then merged three caches into one. Medians went from 6,776 ms, 3,938 ms and 1,436 ms to about 23 ms each.

This is an internal product, so the code and the screens are not reproduced literally. Product names, customers and internal addresses are out; the structure and the configured values stay.

⚠️ One thing up front. These numbers are 30 runs by a single user, not production statistics. And between the review in part seven (August) and this measurement (September) someone else's improvement landed as well. I did not separate their contribution from mine. It is in “what this article does not claim” below.

Which screens?#

Unified monitoring has three screens. Dashboard, physical nodes, virtual resources. All three take structure over REST and live values over SSE.

The last line of part seven was “I did not run a load test. I judged it from the code and never confirmed it by running one.” The limit it wrote down for itself is the one that came true.

⚠️ One thing needs separating. “Cheap because it runs once every 15 seconds” is not a false statement by itself. The periodic refresh really is independent of the number of users and really does run once per tick. What was wrong was treating that one sentence as an account of the whole screen.

Where I measured was not where users waited#

The screen finished loading on this condition.

1. take structure information over REST        about 20 ms
2. EventSource connects
3. a connection event arrives
4. the first data event arrives                ← 6.8 seconds to here
5. the front end drops the loading layer

An ordinary HTTP sampler stops at 3 and calls it a success. What the user waited for was 4.

So I wrote a small probe that attaches to the SSE stream, closes the connection on the first data frame and records the elapsed time. Percentiles and Apdex came out of those values.

The virtual resources row is the SSE side. That screen also had a REST path at about 2,627 ms, and both had to be fixed before it got faster. That is part four.

The fix is one line#

I took the computation off the request path. A background worker builds a completed snapshot every 15 seconds, and a new connection is handed the last completed value immediately. If a refresh fails, the previous value stays.

The name for it is serve-stale: hand over the last value even if it is old. It is a trade, accepting staleness to remove latency, and how far that trade is allowed to go differs per screen. That is what the next four parts are about.

The four parts that follow#

  • Part two, the dashboard. How I found the boundary users actually wait on and how the probe was built. From 6,776 ms to 10 ms.
  • Part three, physical nodes. Moving the same pattern raised one question. When the metric query returns an empty list, may that be published as a healthy zero?
  • Part four, virtual resources. Two bottlenecks, REST and SSE, so fixing one left the screen where it was.
  • Part five, the shared cache. Merging three caches into one turned things that separation had been protecting by accident into explicit contracts.

What this article does not claim#

  • These are not production statistics. Thirty runs by a single user, with no concurrency and no long-run distribution.
  • I could not separate the contributions. Between the review in part seven (August) and this measurement (September), someone else's improvement also landed. How much of the “before” figure belongs to it was never measured apart.
  • Part seven was not wrong throughout. One of the things it decided to leave alone, a query window that looks too wide, is still right to leave alone. What was wrong is the judgement about cache and the basis behind it.
  • serve-stale is not always the answer. It holds only where an old value may be shown. Drawing that line per screen is the subject of parts three and five.
  • 23 ms is not a constant. It is the cost of reading a snapshot from memory and serialising it, and it moves with the size of the data.

Wrapping up#

  • “Already cheap” needs to say cheap for which path. The periodic refresh was cheap and the connection path was not. Taking one sentence to cover both was the mistake.
  • Check that where the tool says success is where the user stopped waiting. If those differ, the space between them is invisible to everyone.
  • A decision not to act is harder to check than a change. I wrote that in part seven and then never built the instrument that would have checked it.

If one line survives, this one. “No case for a change” has to be written differently from “I did not measure.” Part seven is an article that works hard to keep those apart, and it failed to keep them apart in the one place that counted.
