A Teardown Destroyed 96 Resources and Two of Its Seven Lines Never Asked
The load balancer and interface queries sit behind a check for the VPC, so once the VPC was gone both printed the empty value they started with.

As a personal project I build a Kubernetes control plane that lets several people share a small pool of GPUs. One AWS account holds a Terraform root that stands an entire EKS cluster up and takes it down again, and a GitHub Actions workflow tears it down every night.

That workflow had succeeded every single time. There was nothing to remove. A successful teardown and a teardown with no work to do had been piling up in the same shade of green.

So I spent a day actually standing it up and taking it down. Ninety-six resources appeared, and the destroy took thirteen minutes and thirty-five seconds. After querying the resource IDs I had recorded, one at a time, to confirm they were gone, I went back and reread the list the workflow prints at the end, and stopped on two lines. Of the seven, two had never asked AWS anything, and they reported absence in exactly the same words as the other five.

Who this is for#

  • You build a path that stands a whole cluster up with Terraform and tears it down again
  • You treat the "no residue" line at the end of a cleanup job as evidence
  • You have tried to tell a check that passed from a check that never ran

What the system is#

It is a control plane for about one lab's worth of GPUs. The cluster does not stay up. Terraform builds it when it is needed and destroys it afterwards. Standing it up creates a VPC and eight subnets, an EKS cluster, four node groups, a NAT gateway and an elastic IP, ninety-six resources in one apply.

Taking it down is the workflow's job. It deletes the Argo CD applications first, destroys the cluster state with Terraform, and finally asks the account whether anything survived. That last step is what this article is about.

I thought the teardown path was already proven#

The teardown workflow had been running nightly for months without a failure. Read as a list of runs, that looks like a proven path.

For all of those months the account had no cluster in it. Every run had confirmed that there was nothing to remove and then exited successfully. The code that removes things had never removed anything. So I built one.

The short version#

The removal worked. Terraform reported ninety-six resources destroyed. Separately from that count, I queried the resource IDs I had recorded beforehand. EKS returned ResourceNotFoundException, the elastic IP and the VPC and the volume and all five interfaces returned NotFound, the machine was terminated and the NAT gateway was deleted. The state object shrank from 106,851 bytes to 1,361. I did not re-query all ninety-six one by one.

Seven lines all printed none#

Once the destroy finishes, the workflow queries the account for what is left and prints an inventory. This is what this run printed.

VPC:               <none>
EC2 instances:     <none>
EBS volumes:       <none>
NAT gateways:      <none>
Unassociated EIPs: <none>
Load balancers:    <none>
Network ifaces:    <none>
no residue

Seven lines, all of them none. Reading that, you conclude seven things were asked about and seven things were absent. That is how I read it too.

The last two were never queries#

This check is written to look up load balancers and network interfaces using the VPC ID it found earlier. The code says so.

LB=""
ENI=""
if [ -n "$VPC" ]; then
  LB=$(q elb aws elbv2 describe-load-balancers ...)
  ENI=$(q eni aws ec2 describe-network-interfaces ...)
fi

If the VPC is already gone, $VPC is an empty string and neither query runs. LB and ENI keep the empty value assigned at the top, and the print helper renders an empty value as <none>. "I asked AWS and there was nothing" and "I did not ask" come out identical, character for character.

The five interface IDs I had recorded were confirmed gone because I queried them myself, one by one. That confirms those five, not that no interface remained. As for load balancers, this cycle never created one. Neither fact came from the output above.

I had fixed the other half of the same file that morning#

Earlier the same day I had fixed the other half of this check. The queries ran under set +e and only their captured output was read, so an expired credential returned an empty string and that empty string read as absence.

The fix records the exit status of each query, appends the failures to a list, and fails the job at the end if that list is not empty.

if [ -n "$FAILED" ]; then
  echo "::error::residue verification did not complete: these queries failed:$FAILED"
  echo "This is NOT a report of no residue -- nothing above says whether anything is still billing."
  exit 1
fi

So one check held the same defect in two shapes. The morning fix was about a failed query reading as absence, and what I found in the evening was a skipped query reading as absence. I had fixed one of them and believed I had read the file.

A warning that named a cause it could not know#

During the destroy, the two steps that delete Argo CD in order were skipped. The log said this.

##[warning]Kubernetes API is not reachable from this runner.
          The cluster endpoint is private and this runner is outside the VPC.

That explanation is wrong for this run. The public half of the endpoint was open. It was open to exactly one address, mine, which does not include a GitHub-hosted runner.

In the code, the probe turns every non-zero exit of kubectl get --raw /readyz into a single failure and discards the error. That cannot separate a CIDR refusal from an authentication failure, a DNS failure or an API that is not ready yet. Naming one of them sends the reader after the wrong thing. It now reports the symptom and lists the possible causes.

What the check never looks at#

Even with those two lines fixed, the question this check can answer is narrow. It reads one region, finds machines and volumes and NAT gateways by tag, finds the VPC by name tag, and counts only elastic IPs that are unassociated.

An elastic IP left behind while it is still associated is not something this check can find. On this cycle the elastic IP was associated with the NAT gateway while the cluster was alive, and its removal was confirmed by the query I ran against its allocation ID rather than by the workflow.

What this article does not claim#

  • ⚠️ This does not say the teardown path is validated. This cycle used the smallest cluster the root can build, with no load balancer, no Argo CD, no GPU node and no PVC, so none of the hard cases this workflow was written for were exercised.
  • I have still never seen the residue check fail. It passed again here, and a record of successes alone cannot tell me whether the queries actually ran.
  • This does not say the bill went to zero. What ended is this cluster's usage. The state bucket, the KMS key and two ECR repositories are still there, and no amount was read from billing data.
  • ⚠️ Nor does it say the nightly cron does the same job unattended. This destroy was dispatched by hand and watched.

Closing#

  • "I asked and there is nothing" is not "I did not ask." When both print the same text, the reader has no way to tell them apart.
  • The initial value of a skipped query looks like a result. Print a variable that is only filled inside a condition and the fact that the condition was false disappears from the output.
  • One file can hold the same defect in more than one shape. Fixing one of them and considering the file read was my mistake here.
  • Do not name a cause you cannot distinguish. A warning that states one sends the reader in that direction.
