Instance HA ①: 生きているノードを死んだと判定しました
スイッチが一つ死んだだけでネットワークごとに状態が分かれ、Controller は自分の孤立を Compute の死として読みました。Instance HA 障害対応設計の連作、その一編目です。

この製品の Instance HA は、Compute ホストが死んだときにその上の VM を生きている別のホストへ 退避させて立ち上げ直す機能です。自動復旧です。この機能が最も危うくなる瞬間は 死んでいないホストを死んだと判定するときです。そのときシステムは正常に動いている VM を強制的に move し、運が悪ければデータを壊します。

2026 年 3 月にそれが実際に起こりました。L2/L3 スイッチが死にましたが、切れたのは Compute では なく Controller 同士の通信でした。その状態で Leader Controller が生きている Compute を障害と 判定し、Nova Evacuate を大量に実行しました。私は事故を自分で調査してはいません。整理された事実を受け取り、再発を防ぐための判定体系を設計しました。

この記事は連作の一編目で、①編は原因までを扱います。ネットワークが四本に分かれて 別々の状態になった経緯、Controller が自分の孤立を対象の死として読んだ理由、誤って実行した復旧が どこまで行き得たかです。信号に等級を付ける話と Phase を分ける話は次の編にあります。

想定読者#

  • 死んだノードを自動復旧する仕組みを設計または運用している方
  • ネットワーク分断で自動化がかえって事故を大きくする場面を見たことがある方
  • 「ノードが死んだ」をどの信号で判定するかを決める立場の方
  • Split-Brain がなぜ速い復旧より先に来るのかが気になる方

復旧が事故になった日#

事件は一行で要約できます。L2/L3 スイッチ障害のとき Leader Controller が生きている Compute を障害と誤判し、不要な Instance HA を大量に実行しました。正常な VM を別のホストで 建て直す evacuate が同時多発で起き、原本がまだ生きているのに再構築された側が同じボリュームに付くと、 最悪の場合ファイルシステムが壊れ得る状況でした。

横にスクロールすると残りが見えます

項目内容

ここで大切なのは「復旧が遅れた」ではなく「やってはいけない復旧をした」という 点です。この方向の失敗は取り消すほうがずっと難しくなります。

一つのスイッチに四本がぶら下がっていました#

核心はこれです。スイッチが死ぬとネットワークごとに状態が変わります。一本が 切れたからといって全部が切れたわけではありません。このファームには枝が四本ありました。障害が起きたとき運命が分かれたのは三本で、四本目の BMC は最初から敷かれていませんでした。

横にスクロールすると残りが見えます

四つのネットワークの用途と障害時の状態。
ネットワーク用途障害時
MGMTController と Compute の管理通信正常
DATAVM のデータトラフィック遮断
ControllerController 同士の通信遮断
BMCFencing の経路不在

Controller 同士の通信が切れると、Controller は互いの状態を合意できなくなります。まともな Quorum なら多数を失って孤立した側は判断を止めるべきなのに、このときは孤立した側が止まらず単独で判定を下しました。 ところが MGMT は生きていたので、その Compute の Agent HeartBeat は正常に受信されて いました。死んだと判定されたノードが、実は自分の状態をきちんと報告し続けていました。

届かないことと死んだことを分けられませんでした#

「あのノードに届かない」は二つのことを意味し得ます。あのノードが死んだという意味かもしれませんし、 自分とあのノードの間の経路が切れたという意味かもしれません。二つはまったく違う状況 なのに、外から見ると同じに見えます。

事故の根は観測者の孤立を対象の障害として誤認したことでした。判定が観測者自身の ネットワーク健全性を入力に使っていなかったため、遠隔ノードの死と観測経路の断絶をついに区別できません でした。何をより精緻に見るかではなく、誰の言葉を信じるかの問題でした。

同じ構造の事件がもう一つありました#

この事故だけではありませんでした。Controller を三つ置く構成で、そのうち一部が障害や断絶に 遭ったとき、障害が起きたそのノードがリーダーに選ばれて復旧が全ノードと VM へ 広がった件が別にありました。

切れた場所は違います。一方はスイッチが死んで枝が切れ、もう一方は Controller どうしの通信が切れました。それなのに観測者が見た画面は同じで、実際の Compute も両方とも 生きていました。

だから二つを一文にまとめられます。Compute 自体の障害ではなく観測地点の障害なのに、その観測地点が 自分の状態を判定に入れていなかったのです。ここからこの連作の最初の原則が出ます。自分が判断できる 状態かを先に見て、それが壊れていれば復旧を行いません。

走るべきでなかった復旧がボリュームを壊します#

誤判が高くつく理由はその次にあります。原本の VM がまだ生きてディスクに書いているのに、再構築された 側が別のホストで同じボリュームに付き、両側が同時に書けてしまうと、壊れるのは VM 一台ではなく ボリューム全体になり得ます。

横にスクロールすると残りが見えます

Storage 種別ごとの同時書き込みリスク。
Storage同時書き込みが起きると
iSCSISCSI-3 PR はありますが、原本の接続整理前に新規接続が来ると衝突し得ます
LVMSCSI PR 非対応のため VG と LV のメタデータ損傷リスクが高くなります
NFSFile Lock 基盤のため同時 mount と write では一貫性を保証できません

だからこの設計は「速く復旧する」ではなく「確信できなければ止める」を既定に します。非対称なコストが判定を決めました。

何を復旧するかは二層で決まっていました#

設計を始めるとき、一つはすでに製品にありました。復旧対象を選ぶ軸がホスト制御属性と Instance メタデータの二層だということです。2024 年 9 月にこの機能を検証しながら三つの値をすべて確認して いました。

ホスト属性が HA_Enabled ならメタデータに HA_Enabled の印がある Instance だけが対象になり、HA_Disabled なら逆に HA_Disabled の印を持たないものが すべて対象になり（メタデータが無い Instance も対象に含まれます）、NONE なら メタデータに関係なくすべてが対象になります。つまり opt-in と opt-out と全体をホスト単位で選べる 構造です。

そのとき対象リストだけでなく除外リストが意図どおり埋まるかも一緒に見ました。復旧機能で危ないのは 復旧されないことよりも復旧されてはいけないものが復旧されることだからです。2026 年の 設計で八つのシナリオのうち七つを保留にすると決めたとき、「復旧するかしないか」を判断する地点が製品に すでにあるという前提をここから持ってきました。

おわりに#

この編で言いたいことは一つです。自動復旧が危うくなる場所は復旧が遅いときではなく、 観測者が自分の状態を知らないまま対象を判定するときです。スイッチが一つ死んだだけなのに枝ごとに運命が分かれました。残った枝はそのノードが生きていると伝えていました。それでも判定を下したのは、切れた枝を持つ側でした。

次の編はそれで何を違えて設計したかです。検知をより精緻にする代わりに、信号ごとに証言できる範囲を 決めた設計の話へ続きます。②編へ進みます。
