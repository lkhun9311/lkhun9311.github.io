生きているサーバーを死んだと判定すると、復旧が事故になります
スイッチ障害でコントローラー同士だけが切れたのに、健全な Compute を死んだと判定して VM を大量に退避させた事故がありました。検知を精緻にする代わりに、どの信号を信じるかから決め直した障害対応設計です。

Instance HA は、Compute ホストが死ぬとその上の VM を生きている別のホストへ退避（evacuate）させ、 再び起動する機能です。自動復旧ですね。ところがこの機能が最も危険になる瞬間は、死んでいない ホストを死んだと判定するときです。そのときシステムは、問題なく動いている VM を強制的に移し、 運が悪ければデータを壊します。復旧がそのまま事故になります。

この記事は、実際にその事故が起きたときに再発を防ぐため、私が単独で作成した障害対応 設計を、現状・原因・解決の順にまとめたものです。最後に、その完成アーキテクチャを表と図で 置きました。

先に範囲を明かしておきます。この記事は私が設計した目標アーキテクチャの観点での まとめです。事故を経て「どういう構造であるべきか」を基準に、検知 → 判定 → Fencing → 復旧が一本の 安全な鎖としてつながる完成形を描きます。実装はチームが引き継ぎましたし、各要素が 製品にいつ入るかはこの記事の焦点ではありません。後に出てくる復旧時間（RTO）は、実測ではなく段階別の 見積りです。顧客名・サーバーアドレス・ホスト名・アカウントといった識別情報は書いていません。

想定読者#

  • 死んだノードを自動復旧するシステム（Instance HA、Masakari 系）を設計・運用している方
  • ネットワーク分断（partition）で自動化がかえって事故を大きくする場面を経験した方
  • 「ノードが死んだ」をどの信号で判定するか、その信号をどこまで信じるかを決める必要がある方
  • Split-Brain と Fencing がなぜ「速い復旧」より先に来るべきか気になる方

現状：復旧が事故になった日#

事件は一行で要約できます。L2/L3 スイッチ障害のとき、リーダーのコントローラーが生きている Compute ノードを死んだと誤判定し、不要な Instance HA（Nova Evacuate）を大量に実行しました。 健全な VM が一斉に別ホストへ移り、最悪の場合、元が生きているまま退避先が同じボリュームに接続して ファイルシステムが壊れかねない状況でした。

横にスクロールすると残りが見えます

事件の要約：状況・結果・影響・潜在リスク。
項目内容
状況L2/L3 スイッチ障害のとき、リーダーのコントローラーが Compute ノードを障害と誤判定
結果不要な Instance HA が発火（= Nova Evacuate）
影響誤った退避（Evacuate）が同時多発
潜在リスクFalse Positive HA → Split-Brain → ストレージ破損

ここで重要なのは「復旧が遅れた」ではなく「やってはいけない復旧をやった」という 点です。この方向の失敗は、元に戻すのがはるかに難しいのです。

なぜ生きているサーバーが死んで見えたか#

核心はこれです。スイッチが死ぬと、ネットワークごとに状態が変わります。一つが 切れたからといって、全部が切れたわけではありません。

横にスクロールすると残りが見えます

L2/L3 スイッチ障害時のネットワーク別状態。
ネットワーク用途障害時の状態
MGMTController ↔ Compute 管理通信正常
DATAVM データトラフィック遮断
ControllerController ↔ Controller 通信遮断
BMCFencing（電源制御）不在 ← これが問題だった

コントローラー間の通信が切れると、クラスタのQuorum が崩壊します。すると一部の コントローラーが単独で「Compute が死んだ」と判断してしまいます。ところが実際には MGMT は生きていて、その Compute の Agent HeartBeat は正常に受信され続けていました。 死んだと判定されたノードは、実は自分の状態をきちんと報告していたのです。

私があるノードに届かないというのは、そのノードが死んだという意味かもしれないし、 私とそのノードの間の経路が切れたという意味かもしれません。二つはまったく違う状況 なのに、外から見ると同じに見えます。事故の根は、観測者の孤立を対象の障害と誤認 したことでした。

検知ではなく、信号に資格を付けた#

よくある処方は「検知をもっと精緻に」です。ところが観測精度をいくら上げても、観測者が 孤立しているときは何を見ても信じられません。そこで精度ではなく、誰の言葉を 信じるかを決めました。信号ごとに信頼度の等級を付けたのです。

横にスクロールすると残りが見えます

信号信頼度の4等級。
Signal信頼度役割
Agent HeartBeatHighestCompute ノードの実際の状態を、そのノードが直接報告
Controller QuorumHighコントローラークラスタの合意状態
Network HeartBeatMediumController ↔ Compute の接続確認
EXT Network ProbeLowコントローラー自身のネットワーク分断（partition）判定

核心は最下段です。EXT Probe は Compute 状態を直接検証しません。 コントローラー → 外部方向の到達性だけを確認するので、それで Compute の稼働可否を判定すると、すぐに 「観測者の孤立を対象の障害と」誤認します。事故がまさにそれでした。

次に、混ざっていた判断を二つに分けました。「本当に障害か」と「いま安全に実行してよいか」は 別の問いなのに、一つにまとまっていて互いを汚染していました。

横にスクロールすると残りが見えます

Phase 1 Failure Detection と Phase 2 Execution Readiness の分離。
Phase 1: Failure Detection（本当に障害か）Phase 2: Execution Readiness（いま実行してよいか）
Quorum 確認。失っていれば判断は信頼できない → HoldStorage reachable。VM がストレージに到達できるか
Agent HeartBeat TTL（30秒以内）正常 → Compute 正常 → HoldRabbitMQ healthy。復旧コマンドを伝えられるか
TTL 超過時のみ追加検証（EXT probe · nova-compute · storage session）Nova API healthy。API を呼べるか

この分離の狙いの一つ: ストレージ経路の障害を「Compute 障害」と 誤判定しないようにすることです（設計基準）。Storage を Phase 2 に置くと、Phase 1 の障害判定を 汚染しないからです。

既定は Hold: 8つのうち7つは止まる#

二つの Phase を基準に、障害シナリオ8種を判定しました。結果はFencing 1件、HOLD 7件。 つまりこの設計で「実際に復旧を実行してよい」ケースは、8つのうち1つだけでした。

復旧を誤って実行すればデータが壊れ、保留すれば人が介入する時間が生まれます。 非対称なコストが判定を決めました。だから確信できないなら何もしないのが既定で、HOLD は オペレーターへの通知を伴います。

動かす前に電源を確認する#

復旧してよいと判定したとしても、動かす前に必ずやることがあります。元サーバーの電源が 確実に落ちたかを確認すること。これがないと Split-Brain が起きます。

Compute-01 → VM-A still running  → write /dev/vdb   (元の接続を維持)
Compute-02 → VM-A evacuated      → write /dev/vdb   (新規 attach)
        → 同時 write → filesystem corruption → データ破損

そこで原則を「no fencing = no recovery」としました。電源遮断（Fencing）を確認 できなければ復旧しません。リスクはストレージ種別ごとに違います。

横にスクロールすると残りが見えます

ストレージ種別ごとの Split-Brain 破損リスク。
Storage破損リスク
iSCSISCSI-3 PR はあるが、元の接続を整理する前に新規アクセスすると衝突しうる
LVMSCSI PR 非対応。同時 write で VG/LV メタデータ破損リスクが高い
NFSFile Lock ベースなので、同時 mount/write では一貫性保証ができない

Fencing は IPMI 電源制御で行います。ただし前提条件が一つ付きます。BMC（電源制御用） ネットワークが MGMT と同じ物理スイッチにあると、スイッチが死ぬとき IPMI も一緒に切れます。 すると電源を落とす手段そのものが失われ、Fencing が不可能になります。VLAN 分離だけでは足りません。 スイッチが丸ごと死ぬと、その上の VLAN も全部消えるからです。そこでBMC 専用の物理スイッチ を前提条件として明記しました。事故当時、BMC ネットワークは不在でした。

復旧手順は四段階に分けました。Detect → Verify → Fence → Recover。このうち Fence 段階に、小さいが重要な順序があります。

1. ipmitool chassis power off        （BMC 専用物理スイッチ経由）
2. 最低 5 秒待つ                     （電源が実際に落ちる時間、即時照会禁止）
3. ipmitool chassis power status  →  必ず off を確認
4. Storage の追加確認                （種別ごとに異なる）
5. Nova Evacuate 実行

2 番が核心です。電源を落とした直後に状態を照会すると、まだ off ではありません。 待たずに確認すると「off でない」と読まれ、問題のない Fencing を失敗と誤判定したり、逆に楽観的に進んで、 落ちてもいないサーバーの VM を移してしまいます。命令を送ることと、その結果を確認することは 別の作業で、その間に待機を入れることがこの手順のすべてと言ってもよいくらいです。

ロックは分散合意ではない#

「誰が復旧を実行するか」を制御する方式も決める必要がありました。社内にはすでに Galera があり、その DB Lock を使おうという流れがありました。三つの方式を同じ基準で分解しました。

核心はDB Lock が分散合意ではないという点です。ロックは重複 実行を減らしますが、分断状況で両側がそれぞれロックを取るのを止められません。目的が Split-Brain 防止 なのに、それを構造的に防げなければ目的を達成できません。そこでPacemaker + Corosync を第一 候補に（検知 ~5秒 + STONITH 内蔵で「no fencing = no recovery」を構造が強制）、導入が難しければ etcdを次善策として推奨しました。

復旧はどれくらいかかるか（見積り）#

復旧体系を設計すると「どれくらいかかるか」が必ず付いてきます。単一の数字ではなく段階別に分解しました。 改めて強調しますが、これは実測ではなく設計の見積りで、チームの合意が必要な値です。

RTO は技術ではなくサービス要求が決める値です。だから一つの数字を 「達成した」と言う代わりに、段階別の分解と種別ごとの許容基準、そして TTL を 15 秒に縮める短縮オプションと その代償（Jitter 誤判定リスクの増加）を一緒に残しました。縮められるとだけ言っても、判断の助けになりません から。

完成アーキテクチャ: 四つの層が一本の鎖に#

ここまでの判断を一つにまとめると、この設計は四つの層が順に連なった鎖です。 検知 → 判定・合意 → Fencing → 復旧。重要なのは構成要素のリストではなく順序 です。前の層を通過できなければ次の層へ進まず、元に戻せない動作（退避）は鎖の最後にだけあります。

横にスクロールすると残りが見えます

完成アーキテクチャの四つの層と、構成要素・役割。
層構成要素役割
検知Agent HeartBeat · 複数ネットワーク · BMC 状態障害の「疑い」を集める。死亡の確定と区別
判定 · 合意信号信頼度4等級 · Quorum · Phase 1/2本当に障害か、そしてこのノードが決定権を持つか
FencingIPMI 電源遮断の確認（STONITH）元がもう書けないことをFail-closed で保証
復旧RecoveryMethod · evacuate/live-migration · StateChecker対象を選別して安全なホストへ再配置

鎖をできるだけコードに近づけて書くと（要旨だけ）、こういう形です。

if (!quorum())                 return HOLD;   // 観測者自身が合意できない
if (agentHeartbeat.isFresh())  return HOLD;   // Compute が生きていると直接報告
if (extProbe.failed())         return HOLD;   // 自分の孤立を疑う — 対象の障害ではない
if (!phase2.ready())           return HOLD;   // Storage · MQ · Nova API 未準備
fence(host); confirmPowerOff();               // 元が書けないことを fail-closed で確認
evacuate(targets);                            // ここまで来て初めて移す

この鎖のうち、検知・既存の判定ロジック・復旧の多くはすでにコードにあります。自己状態の点検 ゲート（孤立した観測者は復旧を譲る）、メタデータキー（HA_Enabled · HA_Disabled） による対象選別、RecoveryMethod によるホスト選定がその場所です。そしてこの鎖の 安全軸である Fencing と合意（STONITH · Pacemaker/Corosync）は設計が目指す目標であり、有効化 済みという意味ではありません。この軸がなければ、残りがどれほど精緻でも、分断時に Split-Brain を 構造的に防げません。だから設計はこの軸を鎖の真ん中に置きました。

限界：この記事が主張しないこと#

  • この記事は目標アーキテクチャのまとめです。私の担当は17ページの障害対応設計書で、 実装はチームが引き継ぎました。上の鎖は「こう動く」の完成確認ではなく、「こう動くべき」の設計図です。
  • 残るリスクを明確にしておきます。安全軸である Fencing が実際に有効化される前は、 分断時の Split-Brain 防止が構造的に保証されません。だから自動復旧を無条件に安全な機能と見なしては いけません。完成条件は、Fencing 成功の確認 · BMC 不通時の復旧中断 · Quorum 喪失時の Fail-closed です。 そしてこの軸が立つには、BMC 専用の物理スイッチのような前提が先に整っている必要が あります。
  • RTO ~100–160秒は実測ではありません。段階別の見積りで、設計書にも「チーム合意が 必要」と書かれています。
  • 誤判定したのは既存の復旧ロジックで、その後に再発を防ぐ判定体系を私が設計しました。 私が作ったロジックが誤判定したのではありません。
  • 製品名 · バージョン · 顧客 · サーバーアドレス · ホスト名 · アカウントは書いていません。ネットワーク構成や パラメータは、判定ロジックを説明するのに必要なぶんだけ一般化しました。

おわりに#

この設計を通してずっと反芻した一文があります。自動復旧の品質は、どれだけうまく復旧するか より、どれだけ正確にしないかで決まる。だから検知を精緻にする方向へは行かず、信号に資格を付け、 判定と実行を分け、既定を Hold にしました。8つのうち7つを止める設計になった理由です。

「7つを保留したら、本当の障害のとき復旧が遅れないか」という反問を予想します。遅れます。ですが誤って 実行した復旧は元に戻せません。Split-Brain でファイルシステムが壊れると、VM 一つではなくボリューム全体 です。非対称なコストがこの設計全体の基調を決めました。自動化が最も危険になる瞬間は自信満々のときだと、 この事故が長く思い出させてくれました。
