スナップショットスケジューラが毎回失敗しても画面は STARTED でした
FAILED という状態値はあり、それを書くコードがありませんでした。

2026年9月

OpenStack ベースのプライベートクラウドポータルのスナップショットスケジューラを担当しました。 決めた時刻ごとにボリュームと Instance のスナップショットを取っておく機能です。プロジェクトの スナップショットクォータが満杯になると、その時刻ごとに作成要求が 413 で拒否されます。

ところがスケジュールの状態はずっと STARTED でした。スナップショットは一枚も 作られないのに、画面は正常に見えます。失敗の理由はバッチログにしか残りませんでした。確かめると FAILED という状態値はすでに Enum にあり、その値を書くコードがどこにもありませんでした。

原因を追ううちに、もっと大きいものが出てきました。クォータが満杯で作成が失敗する、まさにその 状況で、コードが前のスナップショットを先に消してから新しいものを作っていました。

この記事の想定読者#

  • 周期ジョブの失敗を画面や通知に上げるコードを書いている方
  • バックアップやスナップショットのように、前のものを消して新しく作る保持ポリシーを扱う方
  • クォータや上限を検査するコードがどの範囲を見ているか、確かめたことのない方

失敗が画面まで届きませんでした#

バッチは作成を呼び、例外が出たらログに書いて投げ直します。それだけです。その上で例外を受けて 状態を変える場所がありませんでした。だから実行は失敗し、状態はそのままです。

ここで一度間違えました。最初はこれを「FAILED 状態を追加しなければならない」と書きました。 コードを開くとその値はすでにありました。無かったのはその値を設定するロジックです。似て見えて 直す場所が違います。前者は Enum を直す仕事で、後者は失敗経路をつなぐ仕事です。

失敗経路がもう一つありました。ボリュームが付いていない Instance は、失敗しても 何も言わずに戻ります。ログも残りません。例外を投げる経路だけ直すと、こちらは そのまま残ります。

検査が他人のプロジェクトを見ていました#

スケジュールを登録するときにクォータを検査するコードがありました。その検査が二つを誤って 見ていました。

一つは上限です。プロジェクトごとの上限ではなく、クォータクラスの既定値を読んでいました。 プロジェクトが別に上げておいた上限は無視されます。

もう一つは使用量です。対象プロジェクトを渡さずにスナップショット一覧を呼びました。すると クライアントが認証したスコープのプロジェクトの一覧が返ります。つまり検査は、他人のプロジェクトの スナップショット数を他人の既定上限と比べていました。

二方向に同時に誤っていました。スコープのプロジェクトにスナップショットが多ければ正当な登録が 拒まれ、対象プロジェクトがすでに満杯でも登録は通ります。そして修正の経路はそもそも検査を していませんでした。

クォータが満杯のときが最も危険でした#

保持ポリシーがあります。何枚までを残し、あふれたら古いものを消します。Instance にボリュームが 付いている経路は、その削除を作成より先に行っていました。

作成が成功すれば何の問題もありません。作成が失敗すると、最後のバックアップまで消えます。 そして作成が最も失敗しやすいのはクォータが満杯のときです。このチケットが直そうとしていた まさにその状況が、バックアップを全滅させる条件でした。

クォータゲートでは直せません。ゲートはクォータのせいで失敗するものを先に止めるだけで、作成は API エラー・Timeout・状態の失敗でも失敗します。順序の問題は順序で直すしかありません。

そこで「新しい写しが active として確定するまでは、最後の写しを消さない」をコードで強制しました。 待ち関数が active かどうかを返すようにし、確定でなければ削除経路に届く前に戻ります。

レビューがここでもう一つ穴を見つけました。確定失敗で戻ると、作られたイメージが DB の行なしで 残ります。保持ポリシーは行を数えるので回収できません。直しながら新しく作った漏れでした。未確定の イメージを失敗経路ごとに消すようにして、「完全な新しいスナップショットでなければ何も残さない」に 合わせました。

登録・実行・画面を一組で合わせました#

一か所だけ直すと別の場所がずれます。三つの時点をまとめて決めました。

  • 登録・修正: 対象プロジェクトの実際の使用量で検査します。足りなければ警告し進行は許しますが、 一枚も作れない状態なら止めます。照会自体が失敗したら開けておきます。検査ができなかったからと 登録を止めると、検査の障害が機能の障害になります。
  • 実行: 作成の直前にもう一度クォータを見ます。足りなければ作成も削除もせずに失敗で終えます。
  • 画面: 一覧と詳細に FAILED を出し、次の実行が成功したら STARTED に戻します。

失敗の理由と時刻は、あえてスケジュールの行に入れませんでした。一行に最後の失敗だけを残すと、 その前に何があったかは結局ログにしかありません。理由は実行単位の履歴として別に扱うことにし、 後続チケットに回しました。

TIMEOUT を中立に置く案を廃止しました#

最初の設計は Timeout を罰しないようにしていました。まだ作成中かもしれないので失敗と数えない、 という考えです。

レビューが二つを指摘しました。一つは成功との取り違えです。中立に置くと画面は正常に見えるのに スナップショットは確定していません。この記事が直そうとしていたまさにその形です。もう一つは孤児です。 確定していないものをそのままにすると、回収する主体がいません。

そこで確定していないものはすべて片づけて失敗として伝えるようにしました。かわりに待ち時間を サイズに比例させ、その値を設定テーブルから実行時に読むようにしました。再起動なしで調整できて はじめて、「もう少し待てばよかったのに失敗と記録される」を運用で直せます。

この記事が主張しないこと#

  • 製品名・バージョン・顧客名・チケット番号・サーバーアドレスは書きません。コードの引用も クラス名なしで動作だけ書きました。
  • 運用でこの欠陥によってバックアップが実際に消えたことがあるかは分かりません。コード経路として ありうるというところまでが確認したことで、事故記録を照会したわけではありません。
  • 「毎回の実行が全種類 413 で失敗する」は誇張でした。Instance 本体のスナップショットは イメージサービスを使うのでボリュームのクォータとは無関係です。チケットのその一文をそのまま 受けず、経路ごとに分けました。
  • 検証はコンパイルと単体テスト、そして登録警告と FAILED 表示をブラウザで確認したところまでです。 負荷や長期運用での挙動は測っていません。
  • 残したものがあります。Timeout の時点で作成中だったスナップショットの完全な回収は、まだ ベストエフォートです。名前ベースのジョブキーのせいでスケジュール名を変えると新旧のジョブが 一緒に発火する問題も、別チケットに残しました。

おわりに#

  • 状態値があることと、その値が書かれることは別です。FAILED は最初からあり、誰も書きませんでした。 Enum を数えてもこれは見つかりません。
  • 上限を検査するコードは、どのプロジェクトの上限をどのプロジェクトの使用量と比べるのかを 書いておく必要があります。両方誤っていてもコンパイルは通ります。
  • 消してから作る順序は、作成が失敗する日にだけ現れます。そしてその日はたいてい、すでに ほかの何かが壊れている日です。
  • 失敗を中立に置く設計は、画面で成功と区別できません。区別できないものは無いのと同じです。

周期ジョブは誰も見ていないときに回ります。失敗がどこまで届くのかをコードに書いておかなければ、 失敗はログファイルの中で終わります。
