I Wrote a Generator So Six Runs Would Share One Condition
The declared load conditions were pinned as constants; which run was which configuration lived outside the tool. An internal cloud admin console. Slow Screens, part eight

Hello. I work on the backend of an internal cloud admin console. In part one I took a single volume list screen and measured it under six configurations. ⚠️ The six do not stack neatly on top of each other; there is a place where a cache is added and then taken away again. Three more screens were measured under the same conditions (part five).

To see what each configuration contributed, everything but the thing you are looking at has to match. This article is about the tool that took on the "keep the load conditions the same" half of that, and about what that tool did not do.

Who this is for#

  • Anyone who has set up a load test by filling in a GUI and pressing run
  • Anyone measuring the same thing repeatedly without being sure the runs match
  • Anyone who wrote an automation script and then moved on at "well, it runs"

What this is about#

  • I moved the load conditions into constants in code and generated the JMX from them. Those values were never touched between runs, so the declared load conditions are identical across all six. ⚠️ That does not mean the environment was.
  • I made the ten measurement targets runnable one at a time, so the tool would not hit the other APIs alongside.
  • I left the result format as CSV. That format has no column for a response body.
  • ⚠️ And yet, with no result files at all, the run script printed "done" and exited zero. I reproduced it to check.
  • ⚠️ And which run was which code configuration is nowhere in the reports. That pairing was being done by a document outside the harness.

Six configurations mean six runs#

Measuring only before and after tells you nothing about which change did the work. So the code configuration was split into six and each one was measured. No cache and sequential, cache only, parallel only, cache and parallel, then the logic optimisation, and finally refreshAfterWrite.

That is the table in part one, and the story of the one step where going parallel made the tail longer is part five.

To measure configurations separately, everything but the thing you are looking at has to match. Change one thing, hold the rest still. That is what makes a comparison a comparison.

⚠️ The six do not each differ from the next by exactly one thing; there are places where two things moved together. That is why part five picks two rows that hold the cache constant and compares those. Measuring all six is what makes that choice available. Measuring only before and after does not.

⚠️ Filling the values in by hand is not wrong in itself. If you write down what you entered each time and keep that note with the result, the comparison holds. The problem is not the hand, it is the missing note. I chose to remove the hand rather than add the note.

I moved the conditions into constants#

The load conditions went to the top of a python file as constants, and the .jmx that JMeter reads is generated from them.

THREADS        = 50    # 50 concurrent users
RAMP_UP        = 120   # seconds to bring them all in
DURATION       = 600   # how long the test runs (seconds, 10 min)
THINK_TIME_MIN = 2000  # think time, lower bound (ms)
THINK_TIME_MAX = 5000  # think time, upper bound (ms)
GROUP          = "01"  # "all" | "volume" | "snapshot" | "01"~"10"

What changed is where the conditions live. They used to live in a person's hands and on a screen; now they live in a file. A file can be read, and compared.

⚠️ Only in the sense that it now has that shape. This harness does not keep a copy of that file per run. To actually compare runs you would have to put it under version control or copy it into the run folder, and I did neither.

Across the six configurations these constants were never changed. What changed was the server-side code. That is the basis on which part one and part five can say the load conditions were the same in all six.

⚠️ And that is as far as "the same" goes. What matched is the declared load conditions, not the whole setting the test sat in. How much data had piled up, how warm the JVM was, what else was running on that machine at the time — all of that is outside these constants. Please read "the same conditions" in the earlier parts with that scope.

And which report belongs to which configuration is paired up by a document written at the time. ⚠️ What the harness leaves behind is not linked together. If that document cannot be opened, the output of this tool alone cannot answer it. (Deployment records and commit times leave some room to reconstruct it. That is not something the harness did for me.)

Measuring one thing at a time was the point#

The targets were ten read APIs on the volume and snapshot side. ⚠️ Which ones, and their paths, are internal API surface and are not written here.

GROUP is the handle on this harness. "01" runs that one, "volume" runs the five on the volume side, "all" runs everything.

When one screen is slow, you have to pull out just what that screen calls so that this tool is not hammering the other APIs at the same time.

⚠️ That does not mean load from other people or other processes on the machine is gone. Only that the harness is not adding it.

⚠️ And "alone" is not "independent". The resource ids that go into the requests are pulled from a CSV file, and the config that reads that file sits once, at the top of the test plan, with sharing set to all and wrap-around on when it reaches the end. That means one cursor shared across every thread. With the groups running one after another, each group picks up where the previous one stopped.

It may not stop at the cursor. If the server was not restarted in between, whatever is left in its cache and however warm the JVM is carry over too. ⚠️ There is no record of what was done to the server between runs. What is certain reaches as far as the CSV cursor.

"all" does not mean at the same time#

Rereading the generated JMX, something caught my eye. These values are in the test plan, and in every thread group.

<!-- test plan -->
<boolProp name="TestPlan.serialize_threadgroups">true</boolProp>

<!-- per group (the generator stamps out ten from one template) -->
<boolProp name="LoopController.continue_forever">true</boolProp>
<intProp  name="LoopController.loops">-1</intProp>
<boolProp name="ThreadGroup.scheduler">true</boolProp>
<stringProp name="ThreadGroup.duration">600</stringProp>

With the first line true, the thread groups run one at a time, in order. The four below mean the loop count is unlimited and the time is 600 seconds. ⚠️ Two of them say the same thing twice: -1 already means forever, so continue_forever being on as well changes nothing.

Had the loop count not been -1, the group would stop at whichever of count and time it reached first. Here the count is never reached, so the path by which it ends normally is that 600 seconds. ⚠️ It can of course end sooner if something stops it from outside or an error policy fires.

So "all" is not a test that loads ten things at once. It is measuring one at a time, ten times over. ⚠️ As the previous section said, the cursor and the cache and the JVM carry across, so the ten are not independent of each other.

⚠️ There is no record that it ever took 100 minutes. What I verified is that the configuration says so. Whether any run ever went through "all" to the end is not written down anywhere.

⚠️ And it is 100 minutes as configured, not exactly 100 minutes. JMeter checks the time between requests; it does not cut off a request in flight. If the last request sits waiting for a response, that group ends past its 600 seconds. On a screen with a ten-minute timeout, like the one in part one, that overshoot is not small.

Deciding what not to save was the design#

JMeter lets you choose what to write to file for each sample. What actually decided it here was the format.

<xml>false</xml>                    <!-- results as CSV, not XML -->
<time>true</time>
<latency>true</latency>
<code>true</code>
<message>true</message>             <!-- the response message -->
<assertions>true</assertions>
<saveAssertionResultsFailureMessage>true</saveAssertionResultsFailureMessage>
<responseData>false</responseData>

False on the first line means results accumulate one CSV line at a time. And CSV has no column that can hold a response body at all. That is why a test running 50 threads for ten minutes did not pile up bodies.

The two items in the last left-hand cell matter. The Read timed out in part one is a response message, not an assertion failure message. They are different columns and both are on. With only one of them, that screen does not appear.

⚠️ The test plan also carries <responseData>false</responseData>. In CSV that line does nothing, because the format already cannot hold a body. It looks like it is holding something back, and the thing holding it back is the format. I found this out while writing this article.

⚠️ And "saving bodies makes it slower" is a claim to make carefully. JMeter receives the whole response and fixes the sample's timing before it hands the result to whatever writes it out. The time spent writing to file is not simply added to that sample's response time. What can be said is that it uses more CPU and disk on the machine generating the load, and that this can shake the result through throughput. How much it shakes it was never measured.

Reports pile up per run, the raw data does not#

Comparison is the point, so earlier runs have to survive. Each execution creates a folder named by the clock, and under it a separate report per measurement target.

⚠️ To be exact about why the targets get separate folders: it is not that a combined report hides them. A combined report does give you per-label rows. They are split so that the same target from two runs sits side by side — open two folders in the same place and there it is.

But the raw data does not survive. The run script deletes the previous result files as it starts. Reports pile up per run; the raw files disappear the moment the next run begins. If you later want to re-aggregate at a different percentile, there is nothing to work from. I nearly titled this section "runs are preserved". What is preserved is the reports.

It finished successfully with nothing produced#

This is the reason I am writing the article. The part that builds the reports looks like this.

for jtl in jmeter/results/*.jtl; do
  [ -f "$jtl" ] || continue
  "$JMETER_BIN" -g "$jtl" -o "$REPORT_BASE/$(basename "$jtl" .jtl)" 2>/dev/null
done

While writing this I ran a minimal version again, with no result files at all.

$ bash run-min.sh
 test finished — generating HTML reports...
 reports are in: jmeter/report/20260908_151437/
exit code: 0

reports produced: 0

It prints "test finished", tells you where the reports are, and exits zero. What it produced is one empty folder.

The reason is that in a default bash, when nothing matches, the loop variable gets the pattern itself rather than a filename.

jtl = [jmeter/results/*.jtl]
not a file → continue

⚠️ It depends on shell settings. When nothing matches, with nullglob on the loop simply runs zero times. The outcome is the same — no reports built, and it still reaches the completion message. The only one that ends differently is failglob, which fails before entering the loop.

[ -f "$jtl" ] || continue filters that pattern out. It also filters out "nothing was produced".

By exit code and completion message alone, "it never ran" and "it went fine" are indistinguishable. Open the folder and they differ. But whatever runs this automatically does not open the folder. In a tool whose purpose is comparison, that is not a small defect.

There is a second problem on the same line: 2>/dev/null. I set up a failing report generation and compared the two.

[stderr discarded]
exit code: 1

[stderr kept]
ERROR: Data exporter ... cannot generate report: empty file
exit code: 1

Both do end in failure. set -e is on and this is not one of the positions that get a pass, so a failure kills it. Being inside a loop has nothing to do with it.

The positions that do get a pass are elsewhere: the condition of an if or a while, a command that is not the last in an && or || list, a command prefixed with !, and a non-final member of a pipeline. It is not "what it is inside", it is "which position".

What differs is whether it dies silently or leaves a reason. In the reproduction that message came out on stderr only, so the first case left nothing at all on screen.

If I wrote it again I would do this: check the count against the expected count, confirm the report actually appeared, and send stderr to a log file instead of throwing it away.

made=0
for jtl in jmeter/results/*.jtl; do
  [ -f "$jtl" ] || continue
  dir="$REPORT_BASE/$(basename "$jtl" .jtl)"            # a folder per target
  "$JMETER_BIN" -g "$jtl" -o "$dir" 2>>"$REPORT_BASE/report.err" || {
    echo "[ERROR] report failed: $jtl — see $REPORT_BASE/report.err" >&2; exit 1; }
  [ -s "$dir/index.html" ] || { echo "[ERROR] report is empty: $dir" >&2; exit 1; }
  made=$((made + 1))
done
[ "$made" -eq "$EXPECTED" ] || {                        # 1 · 5 · 10, depending on GROUP
  echo "[ERROR] $made reports — expected $EXPECTED" >&2; exit 1; }

Four things changed.

  • dir is computed inside the loop. Set once outside, the second report meets a non-empty folder and fails. JMeter requires that folder to be empty.
  • Not -gt 0 but -eq "$EXPECTED". Expect ten, get one, and -gt 0 still passes. That is the dangerous case.
  • JMeter returning zero does not mean a report exists, so it also checks whether index.html is non-empty.
  • stderr goes to a log inside the run folder. The file the message points at has to actually exist.

⚠️ This is still not enough. Things it does not catch:

  • Matching counts pass. One expected target missing and one stray result file present still totals the same. It should compare the list of names.
  • A one-byte index.html passes. A report is many files and this looks at one of them.
  • Dying on the tenth leaves the first nine. That folder looks like a completed run. Better to write a marker when everything finishes, or build into a temporary folder and rename at the end.
  • The log the message points at may not exist. If the run folder is not writable, sending stderr to report.err fails in the first place.

⚠️ And this corrected form is not what is in the internal repository. I cannot reach that code now, so what is written here is how I would write it again.

I checked it with a fake executable standing in for JMeter — twenty lines that refuse when the -o target is non-empty and otherwise create one index.html. With that I ran five cases: normal, zero results, fewer than expected, a zero return with an empty report, and a folder collision. All five stopped where they were meant to. ⚠️ That is not a check against real JMeter; it is a check of the script's decision logic only.

Nothing says which run was which configuration#

This is the broken pink line in the earlier diagram. Put together:

  • The load conditions do not move. They are pinned as constants and were not touched across the six. The generated JMX carries the same values.
  • What changed was the server-side code, and that is outside the harness. This tool does not know what it is measuring.
  • Run folders are told apart only by the clock. Nothing says "this folder is no cache, sequential".

What this harness did is keep the conditions from drifting. What it did not do is mark which configuration a result belongs to. That second part was being done by memory and by a separate document.

⚠️ "There is no condition at all in the report" would not be accurate. A JMeter report has start and end times, a graph of active threads over time, and per-label statistics. You can read the thread count off the chart. What is missing is the JMX and the constants used, and the name of the run.

The fix is not hard: put the generated JMX, the constants, and a name for the run into the run folder alongside the results. ⚠️ Even then it is not proof that this JMX is what actually ran. What shrinks is "how much you have to ask a person later", not down to zero.

The test had to stay authenticated for ten minutes#

A load test has to run ten minutes without a break. If authentication expires partway and rejections start coming back, the numbers from that point on are not response times, they are how fast you get turned away.

So before writing the test I had to read what keeps this screen logged in. ⚠️ What that was is not written here.

The authentication had to be understood before the tool could be built. Without it the obstacle is not writing the script, it is getting through ten minutes.

⚠️ And ten minutes is the case where GROUP is a single target. "all" is a 100-minute affair as configured, and whether authentication is obtained once and reused or obtained again per group over that stretch, I do not know. The test plan alone does not say, and there is no record of it being run that way.

⚠️ How to feed credentials to a load tool is something I have never properly solved. The reason it is not covered here is that I have no answer worth showing, and what was put in that place is not going in this article.

Limits: what this article does not claim#

  • "Doing it by hand makes the conditions drift" was never measured. There is no record of the values diverging between runs, and none of them matching either. Not being able to check is what made me build the tool.
  • This harness does not pin every condition. What it pins is the calling side. The volume of data, how warm the JVM was, whatever else was on that machine at that hour — all outside the constants. If the six runs happened at different times, that difference is still sitting inside the results.
  • I did not look at the PowerShell side. The harness also has a Windows runner, and how the empty-result case, the error stream and the exit code behave there is unverified. The defects in this article apply to the bash side.
  • There is no record of "all" actually running for 100 minutes. The configuration says so; that is the extent of it, and that 100 is a nominal figure.
  • The corrected script is a proposal. It is not in the internal code; it is a form checked in a separate environment.
  • No general claim about tool choice. JMeter was picked because the reports come with it and it was already in use. If you want scenarios written as code, something else fits.

Closing#

This series has been about fixing a number of slow screens. Part seven was a decision not to fix; this one is the instrument written in order to be able to say something was fixed.

  • Conditions in a file are easier to check afterwards. You can do it by hand and write it down, but then a person has to remember to write it down. This harness removed the remembering.
  • Pinning the conditions and naming the results are different jobs. Which folder was which configuration was still written by a person.
  • A script that prints "done" may have produced nothing. Without checking against an expected count, the exit code does not tell them apart.
  • Throw stderr away and it dies without a reason. The death itself shows in the exit code; where and why does not.

If one line survives, it is this. Building an instrument steadies the conditions you measure under, but whether the instrument did its job is a separate thing to look at. I looked four months after I started using it, and the way I looked was running it once with no result files.

Eight parts, and that is the end of the series. Thank you for reading.
