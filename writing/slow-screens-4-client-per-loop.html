A Monitoring Screen's Initial Load Authenticated Once Per Project
Getting a client from that factory was the same thing as authenticating to Keystone.#AdminConsole#SlowScreens④

I write the backend of an internal cloud admin console. A report came in that the monitoring screen was slow. It draws time-series graphs, so the slow part looked like it would be the query. It was not.

The initial load was building a new client for every project, and the serviceClient() we were using authenticates against Keystone on every call. N projects means N authentications, in order. And there was a cache sitting right there that nobody was reading.

The fix was one client, built outside the loop and reused. N authentications become one. How much faster it got, though, I do not know. I did not measure it, and the load scenario we normally run does not send traffic through this stretch at all. Why I could not measure it is half of this article.

Who this is for#

  • You keep a convenience function like getClient() around a cloud SDK.
  • You have seen code that gets a client inside a loop.
  • Your first move on a slow screen is to open the query.

The screen#

A monitoring tab that shows resource usage across several projects on one screen. Two things run at once.

  • The initial load is one REST request that collects quota and usage per project.
  • After that the server computes values every 15 seconds and pushes them to every open screen. Holding the connection open and sending from the server is called SSE (Server-Sent Events). What is independent of the number of viewers is the computation; serialising the result and writing it to each connection grows with the number of connections.

The query is what you want to open first#

Hearing “the time-series graph is slow”, there is one place your hand goes first: the query. Tune the expression, cache the result, then turn on a load tool and ramp up users to confirm. The order feels natural, and here the slow stretch was not on that side.

The time-series query runs once every 15 seconds, and once regardless of how many screens are open. Frequency alone does not make it cheap. What it does mean is that the record never pointed here as the place to look first.

A function that runs a long time is not automatically the stretch the user is waiting on. Queries are visible, so they get targeted first.

The cause: getting a client is authenticating#

The initial-load code looked like this.

for (String projectId : projects) {
    // a new client on every iteration
    var quota = ClientUtil.serviceClient()
                          .compute().quotaSets().getDetail(projectId);
    ...
}

Nothing looks wrong reading it. It calls a convenience function and uses the result. What that function does is not in its name.

In this factory, getting a client is authenticating. serviceClient() connects to Keystone with the account from the config file, takes a token, and hands back a client that is already authenticated.

This is not a claim about SDKs in general. The same library has another route that builds a client from a token you already hold. What authenticates here is our own factory's implementation, and the article is about that fact not being visible in the function's name.

And this comes from two internal documents. The implementation of serviceClient() is not reproduced here, and what survives in the archive is not that implementation but the documents describing it.

Which makes the loop run like this.

  • one project → one authentication round trip plus a few queries for it
  • N projects → N authentication round trips plus N × a few queries
  • and it runs in order. Each one has to finish before the next starts

What the screen shows is a graph, and before drawing it the code was authenticating N times. More projects means proportionally more sequential authentications. I will not go as far as saying response time grows by exactly that much. How long one authentication takes, and whether it is the same every time, was never measured.

And nothing was reading the cache#

There was already a quota cache on the same path. Nothing read it. It was being filled while every request still went out live.

“We added a cache” and “we read the cache” are different things. A cache nothing reads is worse than none, because it makes people believe there is one.

If part three was “there was a cache and the cache was why it was slow”, this one is “there was a cache and nobody looked at it”.

The fix: authentication moved out of the loop#

// one authentication. built outside the loop
final var client = ClientUtil.serviceClient(
        Config.newConfig()
              .withConnectionTimeout(...)
              .withReadTimeout(...));

for (String projectId : projects) {
    var quota = client.compute().quotaSets().getDetail(projectId);   // token reused
    var net   = client.networking().quotas().detail(projectId);
    ...
}

What changed is one place where serviceClient() is called. It moved from inside the loop to outside it.

To be precise: authentication did not disappear, it went from N per request to one per request. The client is built inside this method, so the next request authenticates again.

And even that “once” has conditions. If the token expires while the loop is running, the next call is refused. Whether the library re-authenticates and retries on its own depends on the version and connector in use, and I did not check. The token's lifetime is simply far longer than this loop takes, so it never showed.

Holding the client between requests would cut authentication further. That side is harder. Clients in this family tie the current session to a thread, so sharing one across request threads can leave the session mixed up or missing. Token expiry becomes yours to handle from that point too. This fix did not go there.

Scoping the timeouts to this client only was deliberate too. Put them in the global configuration and legitimately long calls elsewhere get cut as well. Fixing a slow screen and breaking a working feature is a common next incident.

The two limit different things. A connection timeout caps establishing the connection; a read timeout caps waiting for a response after sending. And scoping them to this client still applies them to every authentication and query this client makes. What scoping prevents is the setting spreading to other clients. This is the stated intent; there is no record of anyone checking what actually breaks when it is set globally.

And I never measured before and after#

This is where the article parts company with the previous three.

The internal record holds two numbers and they disagree. One says “5 to 10 seconds with N projects”; the other says “the initial load takes seconds to tens of seconds”. Neither says how it was measured, and there is no figure at all from after the fix.

So this article cannot say “it got N times faster”. What it can say is what the code shows.

A load test only measures the path its scenario sends#

“Then measure it” is the next question. But on this screen, the scenario people usually write leaves the slow stretch out of the test.

Turning on a load tool and ramping up concurrent users is the usual move. But the heavy stretch a user waits on here is the one initial load, and after that the structure is the server computing once every 15 seconds and pushing the same values to every open screen.

Take it to ten users and the computation is still once per tick. With a scenario that holds connections open, the graph reads “it scales perfectly”. That is a property of the architecture, not evidence that the slow path was exercised.

This is not the tool's fault. Ten users each opening the screen would run the initial load ten times. The load tool can reach that path perfectly well; a scenario written to hold a connection and receive pushes simply does not include it. Load-test results are valid only for the requests the scenario actually sent.

Measuring it properly means changing the axis: raising the number of projects N and timing one initial load at each step, instead of raising concurrent users. That is written down in the record as the thing to do, and there is no record of anyone doing it. That is why this article ends without a number.

Limits: what this article does not claim#

  • There are no before-and-after measurements. “5 to 10 seconds” and “seconds to tens of seconds” are two sentences from the internal record with no method attached, and there is no post-fix figure. No sentence in this article claims an improvement factor.
  • I do not know what one authentication costs. So “N−1 fewer of them” does not convert into seconds either.
  • That getting a client authenticates comes from two internal documents. The implementation of serviceClient() is not in the archive and is not reproduced here, and I could not confirm the library version or connector in use.
  • The per-project queries are unchanged. What went away is on the authentication side; the queries still run once per project. Reducing those needs a different change.
  • This is not an argument that load tools are useless. It is an argument that they are useless with the wrong axis. Part one used the same kind of tool to separate six configurations.

Closing#

  • A name can hide a cost. serviceClient() looks free and is a network round trip. Code that gets a client inside a loop is always worth one look.
  • “We added a cache” and “we read the cache” are different things.
  • Load-test results are valid only for the requests the scenario actually sent. With the wrong axis you get a flat graph, and that graph says nothing about the path it never took.
  • If you fixed it and could not measure it, write that. Separating what the code makes certain from what only measurement can settle at least tells the next person what to measure.

Before measuring, ask what the user is waiting on and whether this scenario sends a request down that path. This time I found the slow stretch and fixed it, then never wrote a scenario that went through it, so there is nothing to compare.
