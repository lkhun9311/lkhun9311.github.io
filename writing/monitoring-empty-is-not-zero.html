An Empty List Could Mean Zero Nodes or a Failed Query
Empty because nothing is there and empty because nothing could be fetched arrive in the same shape. An internal cloud admin console. Unified Monitoring, part three

I build the backend of an internal cloud admin console. In part two the dashboard computation moved off the request path. Carrying the same pattern to the physical nodes screen looked like a copy job.

It stopped at one question. When the metric query returns an empty list, may that be published as “zero nodes”?

It may not. The list can be empty because there really is nothing, or because collection failed. Without separating those, the moment something breaks a healthy screen gets overwritten with zero.

Who this is for#

  • Anyone building a screen that serves the last known good value
  • Anyone deciding whether “the result was empty” means healthy or failed
  • Anyone choosing which of a false zero, a blank screen or an endless spinner to avoid during an outage

What is in here#

  • The same serve-stale pattern moved across, but what “empty” means differed per screen.
  • Empty results were split five ways. Only two are published as new values; the rest keep the last good one.
  • The value and the collection status travel separately. That is what makes “showing the last value, and the current collection failed” expressible.
  • The median went from 3,938 ms to 23 ms.

This is an internal product, so the code and the screens are not reproduced literally. Product names, customers and internal addresses are out; the structure and the decision rules stay.

⚠️ This part includes something I did not get right at first. In the physical nodes implementation the five branches were not complete. “Fetch succeeded but the result was empty” could still be read as healthy, and it took the shared cache work in part five to lift it into a common judgement.

Physical nodes have a property the dashboard does not. “How many are there right now” is itself the content of the screen. So “empty result” reads directly as “zero”.

“Empty” had five meanings#

A new collection coming back empty was not published unconditionally. I looked at whether the infrastructure structure could be read, whether the metric fetch succeeded, and how the expected number of targets compared with the number of matched samples.

if the infrastructure could not be read:   INFRA_UNAVAILABLE
else if the metric fetch failed:           FETCH_FAILED
else if matched samples > 0:               FRESH
else if expected targets == 0:             EMPTY_VALID
else:                                      NO_VALID_METRICS

Split like that, the rule is short. FRESH and EMPTY_VALID publish as new values. The other three leave the last good value alone and update only the degraded flag and the failure time.

Separating the generation of the value from the outcome of the last attempt is the point. It lets old data avoid posing as new data without blanking the screen.

Arrival order is data too#

Right after a connection, the cached value goes out, and a new broadcast can land almost at the same time. Asynchronous listeners have no guaranteed ordering, so an older response can arrive after a newer broadcast. Then the screen moves backwards.

Using an HH:mm:ss string as the chart key is not enough here. Two generations can be made within the same second, and a process restart can move the clock backwards. The display time, the ordering generation and the monotonic time used for scheduling are kept as three separate values.

The value and its trustworthiness are drawn separately#

While the last good value is on screen, a user must not read it as current. So the payload carries these four separately.

  • The data and the time that data was made
  • The status and time of the last collection attempt
  • A degraded flag saying the previous value is being carried
  • A generation for ordering within the life of the connection

When the degraded flag is set, the front end keeps the existing value and shows that it is old. Only when the flag is clear and the result is empty does it draw a real zero. Without that split you cannot avoid at least one of “render an outage as zero” or “hide a genuine zero behind an old value”.

What this article does not claim#

  • These are not production statistics. It is a sequential harness measuring first-data latency, not a concurrency load test.
  • This part's contribution was not measured on its own. The “after” column includes the shared cache from part five.
  • I do not claim the five branches were complete from the start. At the time of the physical nodes work, “fetch succeeded and the result was empty” could still be read as healthy, and part five is where it became a common judgement.
  • last-known-good is not always right. Hiding the age of the data buys availability by lying for longer.

Wrapping up#

  • “Empty” is not an observation, it is a value that needs interpreting. Empty because nothing is there and empty because nothing could be fetched arrive in the same data structure.
  • An honest screen needs the value and the collection status kept apart. “Here is the last value, and the current collection failed” is not sayable once they are merged.
  • Judging recency by arrival order makes the screen move backwards. Creation order has to ride along with the value.

If one line survives, this one. What a monitoring screen has to decide is not the latest number, but which of a false zero, a blank screen and an endless spinner it will avoid when observation fails.
