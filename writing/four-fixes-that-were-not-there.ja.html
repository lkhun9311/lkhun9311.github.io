リポジトリに聞きました#

git log -S はよく「その文字列が入ったコミットを探してくれる」と紹介されますが、 そうではありません。親コミットと比べてその文字列の出現回数が変わった コミットを選びます。だから最後の 1 つを消したコミットも結果に出て、 そのコミットにはその文字列がありません。

ガードごとに、そのガードにしかない文字列を 1 つずつ選んで聞きました。 この記事を書きながら回し直した結果です。

$ git log -S"ttl_arm" --oneline -- hack/gpu-session.sh
e96687e fix: give the m6 paid path a deadline, a scale-down, and a delete that finishes

$ git log -S"worst_total_min" --oneline -- hack/m5c-matrix.sh
4165f10 fix: twelve defects a cold review found in the guards added over the last two days
d125bfe fix: keep the deadline until the node is confirmed down, and refuse runs that cannot fit

$ git log -S"the card starts billing here" --oneline -- hack/m5b-gpu-session.sh
4243faf fix: register the deadline before the card exists, by scaling the node group here

真ん中は2 行です。あとでもう一度手を入れたという意味で、 はじめて入ったのは下のほうです。

回数が変わったコミットを選ぶのですから「増えたのか減ったのか」は別に見る必要があります。 親とそのコミットでそれぞれ何回出るか数えました。

ttl_arm                        e96687e   親 0 回 → 1 回
worst_total_min                d125bfe   親 0 回 → 4 回
the card starts billing here   4243faf   親 0 回 → 1 回

3 つとも親では 0 回です。その文字列がこの経路で、いまの HEAD から辿れる履歴の中ではじめて現れたコミットで、 日付は2026 年 8 月 31 日と 9 月 1 日、すべて私のコミットです。

⚠️ 選んだ文字列がすべて実行コードというわけでもありません。 3 つ目に選んだ the card starts billing here は画面に出す 案内文です。その文がなかったということであって、 「そのガードがなかった」をそれだけで言うことはできません。

⚠️ この検索が答えるのは「その文字列がその経路の以前のコミットになかった」 までです。--all なしで回すといまの枝から辿れる履歴だけを見て、 --follow なしで経路を指定すると名前が変わる前の履歴を取り落とします。 同じ機能を別の文字列で書いていたら、そもそも引っかかりません。

4 つ目の解除順序は、文字列ではなく位置の問題です。 はじめは 2 行の行番号を比べましたが、その方法にはあとで出てくる穴があります。 なのでここでは同じ関数の 2 つの版を並べて置きます。

# 6086a51 — 期限機能がはじめて入ったコミット
gpu_scale_down() {
  # Drop the deadline first. If the scale-down below succeeds the schedule has nothing left
  # to do, and if it fails the schedule is the reason this is survivable ...
  command -v ttl_disarm >/dev/null 2>&1 && ttl_disarm     # 関数の最初の動作

# d125bfe — 2026 年 8 月 31 日、私のコミット
gpu_scale_down() {
  # The deadline is NOT dropped here, and the ordering is the whole point.
  # ... It comes off at the bottom of this function, after desiredSize has been
  # read back as 0, and nowhere else.

前の版は関数の最初の動作が解除です。 後の版はその場所に解除がなく、代わりに「いちばん下で、サイズが 0 と読み戻されたあとに」 とコメントが言っています。

⚠️ ところがコメントはそうするという言葉であって、そうしている証拠ではありません。 次の節で戒めることを、ここで先に守らなければなりません。後の版の関数のいちばん下です。

  # Confirm it took. An accepted API call that left desiredSize at 1 is the failure this
  # whole function exists to make impossible ...
  DESIRED=$(aws eks describe-nodegroup ... --query 'nodegroup.scalingConfig.desiredSize' ...)
  if [ "$DESIRED" = "0" ]; then
    # Only now. The deadline has nothing left to protect ...
    command -v ttl_disarm >/dev/null 2>&1 && ttl_disarm
  else
    echo "WARNING: ... after the scale-down. It is billing." >&2
    echo "The TTL deadline is left armed on purpose. It is what remains." >&2
  fi
}

コメントが言った場所に実際にあります。 サイズを読み戻して0 のときだけ解除し、そうでなければ残します。 前の版は関数の最初の行、後の版は読み戻しのあと。 順序を変えたのは後の版、つまり私のコミットです。

⚠️ これはソースに書かれた並びです。どちらの版も同じ関数の中の 直線コードなので実行の並びも同じだと見ていますが、回して確かめたわけではありません。

git では分けられないもの

ここで「だから編集をしたことがない」に進んではいけません。 コミットしていない編集はコミット履歴に残りません。 本当に書いて失っていたなら履歴ではいまとまったく同じに見えます。 ⚠️ git add まで行った内容なら別のところに痕跡が残りうりますが、 私はそのときそれを探しませんでした。

2 つの場合に共通して確定するのは 1 つです。 報告した時点まで、そのガードはコミットとして存在していなかった。

⚠️ 「報告するとき確かめなかった」まではここから出ません。 本当に書いて、確かめまでして、コミット前に失った可能性もあります。 ⚠️ そしてコミットされていないコードが動かないわけでもありません。 これは自分のノートパソコンで回すシェルスクリプトなので、作業ツリーにあればそのまま実行されます。

それでも残るものがあります。続く履歴として残らなかったということです。 明日の私も、別の機械も、戻したあとの私もそれを拾えません。 私はその状態を「完了」と呼びました。

コメントがコードを弁護していました#

1 つ目の項目のコードはこうでした。

gpu_scale_down() {
  # Drop the deadline first. If the scale-down below succeeds the schedule has nothing left to do,
  # and if it fails the schedule is the reason this is survivable -- so it is removed only after a
  # clean exit path is under way, never as a precondition for one.
  command -v ttl_disarm >/dev/null 2>&1 && ttl_disarm

このコメントは自分で崩れます。 「失敗したら予約があるから生き延びられる」と書いておいて、 その予約を失敗しうる呼び出しより先に消します。 失敗した瞬間、予約はすでにありません。

大事なのは、これが失われた修正の痕跡ではないという点です。 このコメントは誤った順序を説明しようとして、筋の通らない理由を作り出したものです。

そして私はそのコメントを読み返しながら「ああこれは処理した」と 通り過ぎました。自分が書いた正当化を自分で証拠にしました。

説明が付いているということは、その説明が正しいという意味ではありません。 コードがすぐ隣にあってもそうです。

エラー応答が正常な測定として流れ込んでいました#

同じ日に出たもののうち数値をいちばん大きく揺らしたものは別にありました。 モデルが最初のトークンを出すまでの時間を測ろうとしたコードです。 ⚠️ 正確には最初のバイトまでの時間を測っていて、その最初のバイトが応答ヘッダーの 可能性もあります。2 つが同じだと確かめたことはありません。

古いコードは応答本文を捨て、終了状態を見ないまま最初のバイトまでの時間だけを 使っていました。エラー応答でもその時間は計算されます。 そしてその日の記録に残ったそのエラー応答はとても速いものでした。

この記事を書きながら、500 だけを返すサーバーを立てて確かめました。

$ curl -s -o /dev/null -w 'http_code=%{http_code} time_starttransfer=%{time_starttransfer}\n' http://127.0.0.1:8791/
http_code=500 time_starttransfer=0.000390
$ echo $?
0                          <- 500 なのに終了コードは 0

$ curl -sf -o /dev/null http://127.0.0.1:8791/   # --fail を付けると
$ echo $?
22

既定の curl は HTTP 500 を失敗として扱いません。 転送そのものは成功したからです。終了コードは 0 で、時間も 正常な応答とまったく同じやり方で計算されて出ます。

ですから「終了状態を見ていればよかった」も誤りです。 既定では正常な応答も 500 も終了コードが 0 なので、それだけでは分かれません。 --fail を付けるか、応答コードを自分で読む必要があります。 直す場所は、私が最初に思っていたところではありませんでした。

[以下はその日の記録に残った値です]
HTTP 500 の応答時間        : 0.000566 秒
そのとき導出されたはずの到着率 : 2,826/s

正常(1.4 秒かかるとき)      : 1.142/s
                             → 2,475 倍

⚠️ この 2 つの到着率は測った値ではなく導出された値です。 どちらもある定数を応答時間で割った形で(両方とも到着率と時間を掛けると 1.6 になります)、 その定数が何かは今回確かめていません。

記録に残る 2 つの値から今回計算してみたのはこうです。 2,826 ÷ 1.142 = 2,474.6、1.4 ÷ 0.000566 = 2,473.5。 2 つはほぼ同じです。記録された到着率が応答時間に反比例するという 意味で、応答が速いほど導出値が大きくなります。 (ぴったり同じでないのは両方の数字とも丸められているからだと見ています。 到着率も応答時間も桁が切られています。)

この到着率はすべての実験条件の負荷と実行時間を決める単一の入力です。 この値がカードの実際の処理能力を大きく超えると裾の遅延の標本が切り落とされます。

⚠️ この節で今回再現したのは curl の動作 1 つだけです。 数値と「だから直した」はその日の記録です。 直したあとその値で回した実行がどんな判定を受けたかはそのときも確かめていません。

すぐ隣の KV 容量の検査も同じ性格でした。エンジンが報告した値と予測値を 並べて出力するだけで比較はしていませんでした。 ファイルの先頭に「予測とまったく違えば拒否する」と書いておいてです。 ⚠️ これもその日の記録です。

名前ひとつがテストを静かに通しました#

同じ日、別の試験 harness では GROUPS という名前の変数を使いました。 ところがそれは bash が自分の分として使う名前です。シェル一般ではなく bash の話です。 いまこの機械(bash 5.3.9)で回し直すとこうです。

$ bash -c 'GROUPS=(a b c); echo "${GROUPS[*]}"'
<現在のユーザーのグループ番号>               <- 入れた値ではない

$ bash -c 'MY_GROUPS=(a b c); echo "${MY_GROUPS[*]}"'
a b c                                        <- 名前を変えれば入る

代入が静かに飲み込まれます。この版ではエラーも警告もありません。 ⚠️ bash の版によって違います。古い文書にはこうした代入が 0 でない状態を返すと書かれています。確かめたのはこの版 1 つです。

⚠️ ここまでが今回再現したものです。この先はその日の記録です。 「別のカードがすでに点いている」を検知するはずの試験が 入れておいた値を一度も見ないまま通りました。

コードは無事で、テストが嘘をつきました。 ⚠️ 前の 2 つの誤検知とこれは原因が互いに違います。 1 つはコメントをコードとして数えたもの、1 つは判定式自体がでたらめだったもの、これは値が入らなかったものです。 同じなのは結果が緑に見えたことだけです。 検査は回りました。ただ私が入れようとした値が入らないまま回りました。 検査が通ったということは、その検査が意図した入力で回ったという意味ではありません。

限界: この記事が主張しないこと#

  • この記事はガードがいまどういう状態かを述べません。 プロジェクトは進行中で、ここに書いたのは2026 年 9 月 1 日の 1 日に 見つけて確かめたものです。その後も同じ場所から直すものが出続けています。
  • 報告がそのコミットより前だったことも、時刻で突き合わせていません。 残っているのはコミットの日付で、報告の時刻と文面は別に持っていません。 「有料セッションの直前に開いて気づいた」はその日の記録です。
  • なぜそう報告したのかは分かりません。やろうとしてやめたのか、 別のファイルでやったと思い違いをしたのか、計画を結果として読んだのか記録がありません。 確認されたのは報告とコードが違ったということだけです。
  • git log -S は出現回数が変わったコミットを選びます。 同じ機能を別の文字列で書いていたら、そもそも引っかかりません。 ですからこの検索は「そのガードがなかった」ではなく「その文字列がなかった」までしか 教えてくれません。
  • 行番号比較の数字は、何を数えるかで変わります。 この記事を書きながら同じコミットを見直したところ、検索の模様を少し変えると 確認する行の行番号が変わりました。結論(順序が逆転した)は同じでしたが、 数字そのものはそのまま持ち出せるものではありません。
  • お金が漏れる経路が全部塞がったとは言いません。そのとき数えた守りは 3 重で、 3 重目は存在だけを知っていて何を消すのか見たことがありませんでした。 数えないほうが正直だと書いておきました。
  • 18 個の確認スクリプトがいまも正しいかは分かりません。 そのとき誤検知 2 つを直しただけで、残り 16 個の判定式は別に検査していません。
  • 12 件は今回のセッションで再現していません。その日のコミット記録から写したもので、 そのうち 2 件だけを本文に載せました。 残り 10 件がいまどういう状態かも、この記事の範囲の外です。

  • 「やった」は記憶であって証拠ではありません。記憶は 編集をしたのか、しようとしたのかを区別できません。
  • 間違っていたと分かったとき、私はまず道具を疑いました。 そちらの説明が楽だからです。楽な説明ほど確認が先であるべきです。
  • 自分が書いたコメントを自分で証拠にしました。 説明が付いているということは、その説明が正しいという意味ではありません。
  • 確認スクリプトを書いたら、そのスクリプトも確認しなければなりません。 ❌ 3 つのうち 2 つがコードではなく私の判定式でした。
  • 「直した」ももう一度見なければなりません。その日に直したコードから同じ日に 12 件出て、そのうち 2 つは失敗が安全な状態とまったく同じに見える 形でした。

1 行だけ残すならこれです。 うまくいっていると感じるとき、その感覚が何に支えられているかを確かめるべきです。 私の支えは記憶でした。

git log -S は数秒で答えます。その数秒を惜しんだ代わりに、 有料実行の直前に報告どおりの姿ではなかったガードを 4 つ見つけました。 3 つは課金が続くのを止める装置でした。
