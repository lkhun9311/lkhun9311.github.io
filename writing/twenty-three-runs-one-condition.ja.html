①編でゲートを四つ立て、拒否経路を一つずつ 発火させました。道具が信頼できるようになったあとで状態を表にまとめたら、予想していなかった欄が 一つ出てきました。

溜まっていた実測23件がすべて同じ条件でした。先取りが起きない条件だけが23回で、 先取りを尊重する条件と無視する条件はそれぞれ0件でした。

この実験の道具は、まさにその二つを比べるために作ったものです。私は道具が信頼できるように なったことと、結果があることを同じものとして見ていました。

この記事の想定読者#

  • AとBを比べるために実験の道具を作って使っている方
  • ガードを通すことに時間を使い、肝心の比較を後回しにしている方
  • キューの方針が資源を回収するとき、何が利益で何が代償かを見たい方
  • ①編を読んで、ゲートを立てたあとに何をしたのか気になる方

積み上がった23件がすべて同じ条件でした#

ゲートを一つずつ通しているあいだ、その通過が視野を狭めました。毎回どこかが緑に変わるので 前に進んでいる感じがしたのに、比較は一度もしていませんでした。

同じ表から二つ目の空欄も出ました。五つのゲートのうち拒否経路を実物で確かめたのは三つだけで、 残る二つはコードをわざと壊す方法でしか拒否を証明していませんでした。

権限から動詞を一つだけ外しました#

観測の連続性ゲートは「監視を立てられなければ投入しない」を強制します。この拒否を実物で見るには 監視が失敗する必要があります。そこで実行に必要な権限をすべて与えたうえで、 一つのリソースの監視権限だけを外した身元を作りました。

# 溜まっていた実測がどの条件だったか
arms exercised: {'no-preemption': 23}

# 一つのストリームで動詞を一つだけ外した身元
jobs   list  -> yes      workloads  watch -> yes
jobs   watch -> NO   <-  pods       watch -> yes
jobs   get   -> yes      nodes      patch -> yes

# 結果: 何も投入する前に拒否
ERROR: setup-failed: the stream ended before it ever established a watch (403)
ledger: 0 events

外したのが正確に一つの動詞かを先に確かめたことが大事でした。権限を広く削ると実行がもっと早い 段階で失敗し、そうなるとこのゲートではなく別のものを実証してしまいます。

結果は正確でした。実行は何も投入する前に拒否し、成果物に403の原文が残りました。残る一つの ゲートはファイルに欠陥を入れて確かめたのですが、そのとき通ってしまい、その話は 別の記事に書きました。

三つの条件を初めて並べて走らせました#

拒否経路を閉じたあと、三つの条件を初めて並べて走らせました。三つの実行は同じフィクスチャで、 所有者は同じ時刻に現れます。

横にスクロールすると残りが見えます

三つの条件を初めて並べて走らせた結果。
項目先取りなし先取り + 尊重先取り + 無視
先取りの発生011
借り手の停止の仕方該当なし信号を受けて終了最後まで実行
所有者が再び上がるまで23秒3秒19秒
帰属する廃棄040.7 GPU秒0
帰属しない占有0059.3 GPU秒
道具の警告該当なし該当なし先取りが無効だったと表示

先取りの利益はほとんどすべて作業が終了信号を尊重するかどうかに かかっています。所有者の待ちが23秒から3秒に縮むのが利益ですが、借り手が信号を無視すると 19秒なので、取り戻せたのは4秒だけです。

そして無視する条件は両方を失います。遅延の利益がほとんどないうえに、借り手の完了した作業が 認められず最初からやり直しになります。道具がこれを自分で指摘して警告に出しました。

五回ずつ回して方向を固めました#

一回ずつでは方向しか言えないので、同じコミットで条件ごとに五回ずつ、合わせて十五回回しました。 解釈の規則は結果を見る前に決めて書いておきました。あとから基準を決めればそれは当てはめです。

横にスクロールすると残りが見えます

条件ごとに五回ずつ、合わせて十五回回した結果。
条件回数所有者の待ちの平均最小と最大無効な先取り
先取りなし523.40秒23.37 〜 23.47該当なし
先取り + 尊重52.79秒2.33 〜 3.490 / 5
先取り + 無視519.42秒19.35 〜 19.545 / 5

一番の収穫はゲートの偽陽性が十五件のうち0件だったことです。 それまで正常な実行は五、六回しかなく、まれに出る偽陽性はまだ見ていないだけという可能性がありました。

クォータを得るのと装置を得るのは別です#

事前に書いておいた規則の一つが発動しました。無視する条件の19秒は測る値ではなく計算される値 でした。五回とも19.35秒から19.54秒のあいだでした。

横にスクロールすると残りが見えます

無視する条件の所要を段階に分けたもの。
段階先取りなし先取り + 尊重先取り + 無視
所有者がクォータ確保22.46秒0.12秒0.11秒
借り手が停止20.45秒0.16秒18.60秒
所有者が再び上がる23.40秒2.79秒19.42秒

無視する条件の所有者は0.11秒でクォータを得ます。ところが 再び上がるのは19.42秒です。その差のすべてが、借り手が残りのサービスを使い切るまで待った時間です。

そこで文を直しました。「無視する条件は20秒のうち4秒だけ回収する」と書こうとしたのですが、 実際には「クォータはすぐ得るが装置は得られない」です。取り戻した4秒はサービスが戻ったのではなく 入場の手続きを飛ばしただけで、残りは借り手の残り時間が決めます。

限界: この記事が主張しないこと#

  • ⚠️ 19秒は強制終了が決めた値ではなく、借り手の残りのサービス時間が決めた下限です。もっと長い 作業なら猶予の締切で切られます。
  • 条件ごとに五回でも統計ではありません。ばらつきが小さいのは精密だからではなくフィクスチャが 決定論的だからで、一台のマシンで一日のうちに回したものです。
  • 元の記録の最後の節には「条件ごとに一回では方向しか言えない」がまだ残っています。十五回の節が あとから付いたときに古い行を消さなかったようです。この記事は十五回のほうを採り、その食い違いを ここに書いておきます。
  • 尊重する条件の40.7 GPU秒は無駄にした時間ではなく捨てられた進捗です。尊重しても進捗の廃棄は そのまま起きます。
  • これらの実行は kind クラスタと偽のデバイスプラグインの上で回りました。実デバイスではありません。

おわりに#

この編の結論は一行です。道具が信頼できるようになったことと、比較が終わったことは別です。 ゲートが一つずつ緑に変わるあいだ、この道具が存在する理由である比較は0件でした。

そして数字を得たあとは、それが測る値なのか計算される値なのかを分ける必要があります。19秒は測る値の ように見えましたが、借り手の残り時間が決めていました。
