A Dialog That Would Not Open Had Two Causes

Hello. I build an internal cloud admin console. On the volume list screen, clicking “create volume” left a spinner instead of opening the dialog.

A button that does nothing reads as a front-end problem. Half right. There was one cause on each side.

Who this is for#

  • You have put a periodic refresh (polling) on a list screen.
  • You prefetch what a dialog is likely to need before it opens.
  • You have had to work out which side a symptom actually came from.

What this is about#

  • The dialog failed to open because two things overlapped: fetching everything up front and re-fetching every five seconds.
  • The list query took over ten seconds while the screen re-fetched it every five. The next one goes out before the previous one is done.
  • DevTools showed four requests still (pending).
  • The fix was pausing the refresh while a dialog is open and fetching only what the user selected, when they select it.
  • ⚠️ But “requests piled up” is more than I verified. What the screenshot shows is that four requests had not finished at that moment, and I never timed how long the dialog took to open, before or after.
  • And those five seconds shaped a backend decision. They are the five in part one's refreshAfterWrite(5s).

This is an internal product, so neither the screens nor the code are reproduced as they are. Product names, customers and internal addresses are gone; only the structure stays. No screenshot containing the product UI is used, and the DevTools panel appears cropped, with the request names masked.

The screen#

A screen listing volumes with a “create volume” button above it. Two things run together.

  • The list re-fetches itself every five seconds. These resources change state, so the screen keeps itself current without anyone doing anything. That periodic re-fetch is called polling.
  • Pressing the button opens a create dialog with a field for choosing a volume source.

The symptom: clicking does not open it#

Press the button and the dialog starts to appear and then just spins. No error. Sometimes it eventually opens, sometimes it does not.

Open DevTools and the answer is sitting there.

(pending) means not finished yet. Where it is waiting does not appear on this screen. It could be queued inside the browser, or sent and waiting on a response.

So the click was handled. The dialog had started to open and was stuck waiting for what it needed.

⚠️ That is as far as the screenshot goes. Which of these is the periodic refresh and which belongs to the dialog, when each started, and where each spent its time — this screen cannot separate any of that. The two causes below come from the code and the internal record, not from this one capture.

Cause 1: fetching everything up front#

Opening the dialog fetched four things: the volume list, the volume snapshot list, the image list, and the volume type list. ⚠️ The first three were called one after another and the volume type separately. They did not all go out side by side.

But opening the dialog does not need all four. Choosing “volume” as the source needs the volume list; choosing “image” needs the image list. Before anything is chosen, none of the volume, snapshot or image lists is needed.

Fetching something because it might be needed later is called over-fetching. It looks like a win — it will be fast later — except when the dialog never opens to reach that “later”.

Cause 2: the five-second refresh kept running#

This is the middle of the article.

The list screen re-fetches the entire volume list every five seconds. And that refresh kept running while the dialog was open. Nothing told it to stop.

And that full list query took over ten seconds. So the next one goes out while the previous one is still running.

Call something that takes ten seconds every five seconds and they overlap. The next one goes out before the previous finishes, so two of the same request are in flight at once.

⚠️ One step past that and the evidence runs out. For “requests pile up without bound” you need two more things, and neither is confirmed by this record.

  • The refresh has to run on a fixed clock. An implementation that waits five seconds after the previous one finishes, or skips while one is in flight, never overlaps. What the record has is the call site of usePolling, not what is inside it.
  • The overlapping requests have to queue somewhere. If they simply go out alongside each other, the number in flight settles around two and stops growing. The browser's limit on connections to one host could be that place, and I did not check.

So what this article can say is that they overlap. The internal record called it “accumulation”, and I read it that way at the time. Looking again, that word claims more than was verified.

And at the same moment the dialog's own requests go out too — cause one. ⚠️ There is no direct evidence that they waited behind the refresh requests. The screenshot shows neither when each request started nor where it spent its time.

⚠️ Browsers also cap how many connections they open to one host. A long queue could run into that cap, but this article did not check. What it checked is that four requests were still (pending).

The fix: pause while open, fetch on selection#

Two separate causes, so two fixes.

One. Pause the refresh while a dialog is open.

// stop polling if any dialog is open
const isAnyDialogOpen = Object.values(openDialogs).some(Boolean);

usePolling({
  callback: () => refetchVolumes(),
  pollingCondition: isLoadingDataExist && !isAnyDialogOpen,
});

⚠️ What this condition prevents is the next refresh going out. It does not cancel a request already in flight. And whether openDialogs becomes true right after the click or only once the data has arrived is not something the call site alone can tell you.

Two. Fetch on selection instead of up front. Picking “snapshot” as the volume source fetches the snapshot list then, and only then. Anything already fetched is not fetched again.

const loadSourceData = async (sourceValue: string) => {
  if (sourceValue === 'volume' && volumeSelectItems.length === 0) {
    // when 'volume' is picked, the volume list only
  } else if (sourceValue === 'snapshot' && snapshotSelectItems.length === 0) {
    // when 'snapshot' is picked, the snapshot list only
  }
  ...
};

Fetching when it is needed is called lazy loading. ⚠️ Depending on the choice it is not always exactly one request: picking “image” or “empty volume” also needs the volume type list, so one more goes out.

A bonus: the options show even when a list fails#

One more thing turned up while fixing this. The source-type options themselves were being built from an API response. So when that call failed, there was nothing to choose from at all.

The options are fixed: volume, snapshot, image, empty volume. That is not something to ask a server for. It became a constant array.

Fetch an unchanging value from a server and a failed call takes the screen with it. Now a failed list still leaves the options visible, and the failure shows up only on that one item.

Those five seconds shaped a backend decision#

The same day, the backend had to pick a refresh interval for the volume list cache — the refreshAfterWrite(5s) from part one.

Those five seconds came from here. The screen re-fetches the list every five seconds, so the trigger for refreshing the cache was lined up with that interval. The team agreed on it.

⚠️ That does not mean “fresh within five seconds”. As part one says, refreshAfterWrite is not a ceiling but the condition that starts a refresh, and if nobody asks, nothing refreshes. What was decided here was what to line the interval up with, not a ceiling on staleness.

The front end's refresh interval set what the backend lined its own refresh up against. These were not two numbers chosen independently — one was the reason for the other.

So which side needed fixing#

“Isn't the backend taking ten seconds the problem?” is the obvious question. It is. And fixing only that would not have been enough.

Limits: what this article does not claim#

  • I never timed how long the dialog took to open, before or after. What the record has is the sentence “it opens right away on click”, which is something someone watched. I cannot say it went from N seconds to M.
  • “Over ten seconds” is the source's sentence. How it was measured is not recorded.
  • The four pending requests are a single observation. That is how it was at that instant, not that it was four every time.
  • Pausing the refresh has a cost. While the dialog is open the list behind it goes stale, so leaving it open a long time can make things jump when it closes. ⚠️ The source does not record that cost, and I did not measure it either.
  • Whether it hit a connection limit, I do not know. A long queue could run into the browser's cap on connections to one host, and I did not check.
  • The front-end fix did not fix the backend. The slow list query was fixed separately in part one. This article sits on top of that and only covers why the dialog would not open.

Closing#

To gather it up.

  • Pick an interval with the slowest response in view. Call something that takes ten seconds every five and the same request overlaps itself.
  • Polling needs a condition to stop on. If the screen is not in front of anyone, or a dialog is open, it does not have to run.
  • Prefetching is not free, and unchanging options should not be asked of a server. The first adds requests at the same moment; the second takes the screen down with the server.
  • One side's number becomes the other side's reason. The front end's five seconds is what the backend cache lined its refresh up against.

If one line survives, this one: a symptom appearing in one place does not put the cause there. The dialog failed to open in the front end, and half the reason it failed was in the backend.
