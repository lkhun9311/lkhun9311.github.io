スレッドを増やしたらテールが伸びた

範囲. 2026年5月、OpenStack ベースのプライベートクラウド管理コンソールの ボリューム一覧画面を改善した記録である。製品名・バージョン・顧客名は書かない。以下の数値は すべて社内試験環境で JMeter により測定した値であり、本番トラフィックではない。負荷条件は 6 構成すべて同一である — 同時ユーザー 50 名 · ランプアップ 2 分 · 継続 10 分 · シンクタイム 2〜5 秒。コードは実際の ソースから引用し、社内固有の識別子は削除した。

この画面はボリュームが増えるほど線形に遅くなり、最終的に 10 分のタイムアウトで落ちた。原因はボリューム 1 件ごとに外部 API を逐次で呼ぶループであり、処方は自明に見えた。並列にすればよい。

並列にしたらさらに遅くなった。キャッシュ設定を固定したまま逐次を並列に変えると p99 が 42.6 秒から 79.0 秒になった。この記事は、その 1 マスが何を教えたか、そして その 1 マスを見えるようにした試験設計についてである。

6 行#

対策をまとめて入れて前後を測ると、「速くなった」という事実だけが残る。何がどれだけ寄与したかは分から ない。そこで構成を 6 段階に分け、同じ条件でそれぞれ測定した。

単位はミリ秒である。① の 600,017ms は測定値ではなく、10 分のタイムアウト上限に張り付いた値 だ。この構成ではリクエストの 83.3% が完了していない。完了しなかったリクエストの遅延は「600 秒」ではなく 不明が正しく、表のそのマスはそう読まなければならない。

③ が ② より悪いことがまず目に留まる。42.6 秒に対して 129.9 秒だ。ところが この 2 行は互いの対照群ではない — ② はキャッシュ 5 秒で逐次、③ はキャッシュなしで並列なので 2 つの変数が同時に変わる。この差から並列化の効果だけを取り出すことはできない。

キャッシュを固定した対は② と ④である。どちらもキャッシュ 5 秒で、逐次か並列かだけが違う。

p99 は 42.6 秒から 79.0 秒に上がった。スレッドを増やしたのにテールが 1.85 倍になった。 これがこの実験で並列化単独の効果として言えるすべてであり、向きははっきりしている — 有害だった。

なぜ ③ は ② より悪いのか#

並列化したコードはこうなっていた。

final Map<String, VolumeGroup> groupCache = new ConcurrentHashMap<>();

final List<VolumeDto> dtos = volumes.stream()
    .map(volume -> CompletableFuture.supplyAsync(() -> {

        // 複数のスレッドが同時にこのブロックへ入る
        final VolumeGroup group = groupCache.computeIfAbsent(
            volume.getGroupId(),
            gid -> client.groups().get(gid)   // ← ロックの中で外部 I/O を呼んでいる
        );
        ...
    }, executor))
    .map(CompletableFuture::join)
    .collect(Collectors.toList());

ConcurrentHashMap を使っているのだから安全だ、と読みたくなる。安全ではある。問題は安全性 ではなく、その安全性を何で買っているかである。

computeIfAbsent は、マッピング関数をそのキーが属するビンをロックしたまま 実行する。マッピング関数がマップを読んで返るだけの計算なら、その区間はナノ秒である。ここではその場で ネットワーク往復を行っている。

結果としてこうなる。同じグループに属するボリュームが M 件あれば、executor に投入された M 個のスレッドが 同じキーで computeIfAbsent に入る。1 つが外部呼び出しを行っている間、残りの M−1 個はそのビンの前に並ぶ。逐次コードで並んでいたものが 並列コードでも並び、しかもその間スレッドプールの枠を占有している。得たものは無く、増えた のはコンテキストスイッチとプール枯渇だけである。

だから ③ は ② より悪い。② は 5 秒キャッシュのおかげで外部呼び出しの回数自体が少なく、③ はキャッシュが 無いためすべてのリクエストがロックされた場所を通らなければならなかった。

用語をひとつ. この構造を「セグメントロック」と呼ぶ文書をよく見る。セグメント はJava 7 時代の用語である。Java 8 以降の ConcurrentHashMap はセグメントを廃し、 ビン(bin)単位でロックする。ロックの範囲が狭くなっただけで、マッピング関数が走る間その 場所がロックされるという事実は変わらない。ロック範囲が狭くなったことは、 ロックの中で I/O をしてよいという意味ではない。

直し方は、ロックを自前で扱うのをやめることである。Caffeine の LoadingCache は、キャッシュ ミス時にキーごとにローダーをちょうど 1 回だけ実行し、他の呼び出し側はその結果を待つ。同じ 「1 回だけ呼ぶ」保証でありながら、待つ側がマップのビンを掴んでいない。

2 つ目の欠陥: 「無い」をキャッシュしていなかった#

同じ画面の別経路には、自前のキャッシュがもう 1 つあった。

public static List<Message> messages(final String resourceId) {
    CacheManager manager = CacheManager.getInstance().init(Message.class, 10);
    final List<Message> cached = manager.list(Message.class);

    if (cached == null || cached.isEmpty()) {              // ← ここを複数が同時に通過する
        client.messages().list(...)
              .forEach(r -> manager.set(Message.class, r.getResourceUuid(), r));
    }
    ...
}

欠陥が二重になっている。

ひとつ。並列化された N 個のスレッドが isEmpty() の判定を同時に通過すると、 N 個すべてが外部 API を呼ぶ。よくあるキャッシュスタンピードである。

ふたつ。取得結果が 0 件だと forEach が一度も回らない。すると キャッシュには何も保存されない。次のリクエストもキャッシュが空だと判断してまた呼ぶ。 「無い」という答えをキャッシュしていないのだ。そしてこの経路では 0 件がよくある答えだった — つまり 最も頻度の高いケースでキャッシュがまったく機能していなかった。

ここでも処方は同じである。Caffeine はローダーが空リストを返してもその空リストを値として キャッシュする。「値が無い」と「まだ訊いていない」をデータ構造が区別してくれる。自前のキャッシュは その 2 つを同じ isEmpty() で潰していた。

この 2 つの欠陥は性質が違う。1 つ目は正しいが遅い欠陥であり、2 つ目は キャッシュがあると信じ込ませる欠陥である。2 つ目のほうが長く生き延びた理由は明白だ — コードにキャッシュがあり、そのキャッシュが埋まっているかを誰も数えなかった。

なぜ ⑤→⑥ がこれほど大きいのか。⑤ までは、期限切れのキャッシュを読もうとしたリクエストが 新しく埋まるまで待つ。Caffeine の refresh は期限切れの時点で既存の値を返し続けながら、 バックグラウンドで更新する。つまり最後の段が消したのは取得コストではなく 更新を待つ時間であり、それがテール遅延の大部分だった。

前後だけを測っていたら何を誤って報告したか#

① と ⑥ だけを測っていたら、報告書はこう書かれただろう。「キャッシュと並列化を適用し、エラー率 83.3% を 0% に、p99 を 10 分から 23ms に改善した。」

すべての数値が真である。そして並列化が寄与したという含意は偽である。並列化は単独では 有害だった。キャッシュを固定しても並列は逐次より悪かったので、この実験は並列化の正の寄与を示していない。それを知らないまま他の画面に「ここも並列化しよう」と 処方していたら、同じ罠に再び入っていた。

実際、この表は診断の根拠にもなった。キャッシュを固定したまま並列化が悪化するということは、 ボトルネックが CPU やスループットではなく直列化点であるという意味であり、だからコードの中にロックを探し、 computeIfAbsent の中の外部呼び出しが出てきた。表がコードを指した。

予想される反論を 2 つ先に書いておく。

「スレッドプールを大きくすればよいのでは?」 — ボトルネックがロックなら、スレッドを 増やしても待つ側が増えるだけである。②↔④ がまさにその実験だ。同じキャッシュ設定で、逐次より並列のほうが 遅かった。

「中央値 4ms はキャッシュヒットだから当然では?」 — その通り。だから中央値だけを見ない。 同じ行の p99 が 23ms で、Apdex が 1.000 である。Apdex は満足・許容・不満を重み付けして数えるので、 中央ではなく分布全体を読む — ただし表示された 1.000 が標本全体を証明するわけではない(後述の留保)。

この記事が主張しないこと#

  • 並列化が悪いという主張ではない。ロックの中で I/O を行うコードを並列化すると悪い。 ただしこの 6 構成の中にその条件を外した並列構成が無いので、外したときに並列化が 値を持つかどうかはこの実験が示していない。③→④ はキャッシュだけが変わった対であり、その答えではない。
  • 本番の測定ではない。社内試験環境での合成負荷である。実際のユーザー分布・データ規模・ ネットワークは異なる。
  • ② と ③ は互いの対照群ではない。キャッシュと実行方式が同時に変わるため、その差 (42.6 秒 → 129.9 秒)をどちらの効果にも帰属できない。この記事が並列化単独の根拠に使うのは、キャッシュを 固定した ②→④ だけである。
  • Apdex 1.000 は標本全体が満足しきい値の内側にあることの証明ではない。ツールの表示が 小数第 3 位で丸められるなら、少数の tolerating 標本があっても 1.000 に見える。丸め前の値は確認していない。
  • 構成ごとに 1 回ずつしか測っていない。反復測定による分散が無いので、隣接する 2 構成の 差が小さいときはその差を根拠にしていない。この記事が根拠に使うのは ②→④ のような 倍単位の差だけである。
  • ① の 600 秒は遅延ではない。タイムアウト上限である。① の p99 を「600 秒」として 引用すると、測定できなかったものを測定したふりをすることになる。
  • Apdex のしきい値はツールの既定値をそのまま使った。サービス水準目標から定義した値では ない。

残る 1 行はこれである。直したものが複数あるなら、何が直したのかは別々に測らないと出てこない。 そしてそう測ると、ときどき、良くなったと信じていた対策が単独では有害だったと分かる。
