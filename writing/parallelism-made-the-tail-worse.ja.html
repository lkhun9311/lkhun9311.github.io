ボリューム一覧を並列にしたら P99 が 2 倍悪化しました
computeIfAbsent の中で外部 API を呼ぶと、その Bin が固定されます。

OpenStack ベースのプライベートクラウド管理コンソールのボリューム一覧画面は、ボリュームが 増えるほど線形に遅くなり、最終的に 10 分の Timeout で落ちました。原因はボリューム 1 件ごとに 外部 API を逐次で呼ぶループであり、処方は自明に見えました。並列にすればよいはずでした。

並列にしたら、さらに遅くなりました。Cache 設定を固定したまま逐次を並列に 変えると、P99 が 42.6 秒から 79.0 秒になりました。

遅くなった理由は、computeIfAbsent のマッピング関数の中で外部 API を呼んで いたことでした。その場所が施錠されたままネットワークの往復を待つので、同じキーを使う Thread は 並列コードでも一列に並びます。得たものはなく、Thread Pool の占有とコンテキストスイッチだけが 増えました。その 1 マスが見えたのは、修正を一度に入れず構成を 6 段階に分けて同じ条件で 別々に測ったからです。この記事はその 6 行と、それを見えるようにした試験設計の話です。

想定読者#

  • 対策をまとめて入れて、前後だけを測ったことがある方
  • 逐次のループを並列にすれば速くなると考えている方
  • computeIfAbsent の中で外部 API を呼ぶコードを見たことがある方

6 行#

対策をまとめて入れて前後を測ると、「速くなった」という事実だけが残ります。何がどれだけ寄与したかは分から ない。そこで構成を 6 段階に分け、同じ条件でそれぞれ測定しました。

単位はミリ秒です。① の 600,017ms は測定値ではなく、10 分の Timeout 上限に張り付いた値 です。この構成ではリクエストの 83.3% が完了していません。完了しなかったリクエストの遅延は「600 秒」ではなく 不明が正しく、表のそのマスはそう読まなければなりません。

③ が ② より悪いことがまず目に留まります。42.6 秒に対して 129.9 秒です。ところが この 2 行は互いの対照群ではない。 ② は Cache 5 秒で逐次、③ は Cache なしで並列なので 2 つの変数が同時に変わります。この差から並列化の効果だけを取り出すことはできません。

Cache を固定した対は② と ④です。どちらも Cache 5 秒で、逐次か並列かだけが違います。

P99 は 42.6 秒から 79.0 秒に上がりました。Thread を増やしたのにテールが 1.85 倍になりました。 これがこの実験で並列化単独の効果として言えるすべてであり、向きははっきりしています。有害でした。

なぜ ③ は ② より悪いのか#

並列化したコードはこうなっていました。

final Map<String, VolumeGroup> groupCache = new ConcurrentHashMap<>();

final List<VolumeDto> dtos = volumes.stream()
    .map(volume -> CompletableFuture.supplyAsync(() -> {

        // 複数の thread が同時にこのブロックへ入る
        final VolumeGroup group = groupCache.computeIfAbsent(
            volume.getGroupId(),
            gid -> client.groups().get(gid)   // ← lock の中で外部 I/O を呼んでいる
        );
        ...
    }, executor))
    .map(CompletableFuture::join)
    .collect(Collectors.toList());

ConcurrentHashMap を使っているのだから安全だ、と読みたくなります。安全ではあります。問題は安全性 ではなく、その安全性を何で買っているかです。

computeIfAbsent は、マッピング関数をそのキーが属するビンを Lock したまま 実行します。マッピング関数がマップを読んで返るだけの計算なら、その区間はナノ秒です。ここではその場で ネットワーク往復を行っています。

結果としてこうなります。同じグループに属するボリュームが M 件あれば、Executor に投入された M 個の Thread が 同じキーで computeIfAbsent に入ります。1 つが外部呼び出しを行っている間、残りの M−1 個はそのビンの前に並びます。逐次コードで並んでいたものが 並列コードでも並び、しかもその間 Thread Pool の枠を占有しています。得たものは無く、増えた のはコンテキストスイッチと Pool 枯渇だけです。

だから ③ は ② より悪いです。② は 5 秒 Cache のおかげで外部呼び出しの回数自体が少なく、③ は Cache が 無いためすべてのリクエストが Lock された場所を通らなければなりませんでした。

用語をひとつ. この構造を「セグメント Lock 」と呼ぶ文書をよく見ます。セグメント はJava 7 時代の用語です。Java 8 以降の ConcurrentHashMap はセグメントを廃し、 ビン(Bin)単位で Lock します。 Lock の範囲が狭くなっただけで、マッピング関数が走る間その 場所が Lock されるという事実は変わりません。 Lock 範囲が狭くなったことは、 Lock の中で I/O をしてよいという意味ではありません。

直し方は、 Lock を自前で扱うのをやめることです。Caffeine の LoadingCache は、 Cache ミス時にキーごとにローダーをちょうど 1 回だけ実行し、他の呼び出し側はその結果を待ちます。同じ 「1 回だけ呼ぶ」保証でありながら、待つ側がマップのビンを掴んでいません。

2 つ目の欠陥: 「無い」を Cache していませんでした#

同じ画面の別経路には、自前の Cache がもう 1 つありました。

public static List<Message> messages(final String resourceId) {
    CacheManager manager = CacheManager.getInstance().init(Message.class, 10);
    final List<Message> cached = manager.list(Message.class);

    if (cached == null || cached.isEmpty()) {              // ← ここを複数が同時に通過する
        client.messages().list(...)
              .forEach(r -> manager.set(Message.class, r.getResourceUuid(), r));
    }
    ...
}

欠陥が二重になっています。

ひとつ。並列化された N 個の Thread が isEmpty() の判定を同時に通過すると、 N 個すべてが外部 API を呼びます。よくある Cache スタンピードです。

ふたつ。取得結果が 0 件だと forEach が一度も回りません。すると Cache には何も保存されません。次のリクエストも Cache が空だと判断してまた呼びます。 「無い」という答えを Cache していないのです。そしてこの経路では 0 件がよくある答えでした。つまり 最も頻度の高いケースで Cache がまったく機能していませんでした。

ここでも処方は同じです。Caffeine はローダーが空リストを返してもその空リストを値として Cache する。「値が無い」と「まだ訊いていない」をデータ構造が区別してくれます。自前の Cache は その 2 つを同じ isEmpty() で潰していました。

この 2 つの欠陥は性質が違います。1 つ目は正しいが遅い欠陥であり、2 つ目は Cache があると信じ込ませる欠陥です。2 つ目のほうが長く生き延びた理由は明白です。 コードに Cache があり、その Cache が埋まっているかを誰も数えませんでした。

前後だけを測っていたら何を誤って報告したか#

① と ⑥ だけを測っていたら、報告書はこう書かれただろいます。「 Cache と並列化を適用し、エラー率 83.3% を 0% に、P99 を 10 分から 23ms に改善した。」

すべての数値が真です。そして並列化が寄与したという含意は偽です。並列化は単独では 有害でした。 Cache を固定しても並列は逐次より悪かったので、この実験は並列化の正の寄与を示していません。それを知らないまま他の画面に「ここも並列化しよう」と 処方していたら、同じ罠に再び入っていました。

実際、この表は診断の根拠にもなりました。 Cache を固定したまま並列化が悪化するということは、 ボトルネックが CPU やスループットではなく直列化点であるという意味であり、だからコードの中に Lock を探し、 computeIfAbsent の中の外部呼び出しが出てきました。表がコードを指しました。

予想される反論を 2 つ先に書いておきます。

「 Thread Pool を大きくすればよいのでは?」。ボトルネックが Lock なら、 Thread を 増やしても待つ側が増えるだけです。②↔④ がまさにその実験です。同じ Cache 設定で、逐次より並列のほうが 遅かったです。

「中央値 4ms は Cache ヒットだから当然では?」。その通りです。だから中央値だけを見ません。 同じ行の P99 が 23ms で、Apdex が 1.000 です。Apdex は満足・許容・不満を重み付けして数えるので、 中央ではなく分布全体を読みます。ただし表示された 1.000 が標本全体を証明するわけではない(後述の留保)。

この記事が主張しないこと#

  • 製品名・バージョン・顧客名は書きません。以下の数値はすべて社内試験環境で JMeter により測定した値であり、本番トラフィックではありません。負荷条件は 6 構成すべて同一です。同時ユーザー 50 名 · ランプアップ 2 分 · 継続 10 分 · シンクタイム 2〜5 秒です。コードは実際のソースから引用し、社内固有の識別子は削除しました。
  • 並列化が悪いという主張ではありません。Lock の中で I/O を行うコードを並列化すると悪いです。 ただしこの 6 構成の中にその条件を外した並列構成が無いので、外したときに並列化が 値を持つかどうかはこの実験が示していません。③→④ は Cache だけが変わった対であり、その答えではありません。
  • 本番の測定ではありません。社内試験環境での合成負荷です。実際のユーザー分布・データ規模・ ネットワークは異なります。
  • ② と ③ は互いの対照群ではありません。Cache と実行方式が同時に変わるため、その差 (42.6 秒 → 129.9 秒)をどちらの効果にも帰属できません。この記事が並列化単独の根拠に使うのは、 Cache を 固定した ②→④ だけです。
  • Apdex 1.000 は標本全体が満足しきい値の内側にあることの証明ではありません。ツールの表示が 小数第 3 位で丸められるなら、少数の tolerating 標本があっても 1.000 に見えます。丸め前の値は確認していません。
  • 構成ごとに 1 回ずつしか測っていません。反復測定による分散が無いので、隣接する 2 構成の 差が小さいときはその差を根拠にしていません。この記事が根拠に使うのは ②→④ のような 倍単位の差だけです。
  • ① の 600 秒は遅延ではありません。Timeout 上限です。① の P99 を「600 秒」として 引用すると、測定できなかったものを測定したふりをすることになります。
  • Apdex のしきい値はツールの既定値をそのまま使いました。サービス水準目標から定義した値では ない。

おわりに#

  • 対策をまとめて入れると「速くなった」しか残りません。何がどれだけ効いたかは、 構成を分けてそれぞれ測らないと出てきません。
  • Lock を握ったままネットワーク往復をすると、並列化は待ち行列を増やすだけです。 Thread を増やしても同じ Bin の前の列が伸びるだけです。
  • 「値が無い」と「まだ訊いていない」をデータ構造が区別できないと、Cache は空の結果を 答えとして固めてしまいます。
  • 表がコードを指しました。Cache を固定したまま並列の方が悪いということは、ボトルネックが スループットではなく直列化点だという意味であり、そこから Lock を探しに行きました。

直したものが複数あるなら、何が直したのかは別々に測らないと出てきません。 そしてそう測ると、ときどき、良くなったと信じていた対策が単独では有害だったと分かります。
