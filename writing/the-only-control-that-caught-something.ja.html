コストの誤りを捕まえた統制は、予算アラート1つだけだった

2026年9月

範囲. 個人プロジェクトである Kubernetes ネイティブ GPU コントロールプレーンのために 作った AWS ラボアカウントの、コストとアカウント運用の記録である。金額の出所は混在している — $14.56 と $0.40 は請求・集計から出た値、 約 $8 は私の見積り、$0.05・$0.18 は課金時間 × 時間単価の計算値である。 いずれにせよ個人ラボの規模であって本番ではない。アカウント ID・ポリシー ID は書かない。

GPU を借りて実験する個人プロジェクトで一番怖いのは、実験が外れることではなく 点けたものを忘れることである。だから統制を何層か作った — サービスコントロールポリシー、 TTL のスケールダウン予約、月次予算、一時的な apply と destroy。

1 か月回してみると、リハーサルはポリシーの欠陥を捕まえ、TTL は発火を証明した。ところが コストそのものの誤りを捕まえたのはそのうち 1 つだけだった。そしてその 1 つはコードに 無かった。

80% は早期警告ではない#

月次予算の上限は 30 ドルにした。通知のしきい値として既定で付くのは予算の 80% である。ところがこの プロジェクトの支出は3 時間のバーストで到着する。有料 GPU セッションは半日で始まって終わり、 月単位のしきい値はそのセッションが既に終わった後にしか何も言わない。

そこで早期警告を 10% に置いた。30 ドルの予算なら 3 ドル、おおよそ有料セッション 1 回分だ。 そうすればその月の最初のセッションがいくら使ったかを報告し、次のセッションはまだ考え直せる。

しきい値を選ぶ基準は「何パーセントが妥当か」ではなく、「これが鳴ったとき、まだ変えられる決定が 残っているか」である。この支出の形では 80% はその条件を満たさない。

見積りから丸ごと抜けていた項目#

2026-09-03、3 回目の有料セッションの後にそのアラートが鳴った。

アラートが報告したその月の累計$14.56

差額を追うと NAT ゲートウェイのデータ処理料金だった。インスタンス時間と EKS の料金は 数えていたが、バイトが NAT を通る費用は見積りに存在すらしていなかった。

なぜ見えなかったかは明確だ。私の見積りは自分が点けたものの一覧だった。GPU インスタンス、 EKS コントロールプレーン、NAT ゲートウェイ — 時間単価があるものだ。ところが NAT は時間料金と 処理したバイトあたりの料金を別に取り、コンテナイメージを引くたびにその行が伸びる。 点けたものを数える一覧は、点けたものが何をしているかを数えない。

そして Terraform がそれを消すところだった#

そのアラートは 2026-08-31 にコンソールで手作業で作り、設定には書かなかった。

数日後、イメージのミラーリポジトリを追加しようと plan を回したところ、この通知ブロックが 設定には無くアカウントには有る状態で現れた。そのまま apply していれば、 無関係な変更の副作用として、静かに消えていた。

消えるところだったのが、よりによってこのアカウントでこれまで唯一コストの誤りを捕まえた統制 だった。

これはこのプロジェクトが繰り返し作り出す形である。値が片方にしか無く、両者を比べるものが何も 無い。コンソールで急いで作ったものはコードに無く、コードを真実とみなすツールはコードに無いものを 削除対象として見る。だからアラートを Terraform に移す際、なぜこのブロックが存在するのかと、一度 消えるところだったという事実をコメントとして併記した。次にこのブロックを消そうとする人が読めるように。

同じ 15.6GB を無料で運ぶ方法#

NAT の行が見えた途端、次の実験の形が変わった。

2026-09-04 の問いは vLLM のスケジューラ設定に関するものだった。ゲートウェイも Kubernetes も要らず、 インスタンス 1 台で足りる。すると 1 つの事実がコストの大部分を分ける。

デフォルトサブネットのインスタンスはパブリック IP でインターネットゲートウェイを通じて 通信し、インバウンド転送は無料である。

それまでの有料実行は、コンテナイメージとモデルの重み — コールドなノード 1 台あたり 約 15.6GB — を GB あたり $0.059 の NAT でダウンロードしていた。 (最初の 3 セッションの NAT データ処理の請求は合計約 92GB・$5.43 である。1 セッション 15.6GB を 3 回ではその総量を説明できず、私はその差を突き合わせていない。)パブリックサブネットのインスタンス 1 台に 移すとその行は消え、その日の実験は約 $0.40 で終わった。

変えたのはアルゴリズムではなくバイトが通る経路である。そしてその経路が見えるように なったのは、アラートが請求書を項目別に読ませたからだ。

わざと失敗したリハーサル、20 分 5 セント#

最初の有料 GPU セッションの前に、GPU を点けないリハーサルを回した。クラスタを apply して すぐ destroy する。目的は性能ではなく手順が最後まで通るかである。

apply が失敗した。原因は前日に私が付けたサービスコントロールポリシーだった。

Error: creating EC2 Launch Template: UnauthorizedOperation
  ec2:CreateLaunchTemplate ... explicit deny in a service control policy

問題の文はインスタンスタイプを許可リストで制限しようとするものだった。

{
  "Effect": "Deny",
  "Action": ["ec2:CreateLaunchTemplate", "ec2:CreateLaunchTemplateVersion"],
  "Condition": { "StringNotLike": { "ec2:InstanceType": ["t3.*", "g4dn.*", "g5.*"] } }
}

ここに 2 つが重なった。

1 つ。IAM の否定条件演算子はキーが無ければ真になる。StringNotLike は 「この値がリストと異なれば」だけでなく、キーがそもそも無い場合にも満たされる。

2 つ。EKS マネージドノードグループはインスタンスタイプをノードグループに持ち、起動テンプレートには 入れない。そのため ec2:InstanceType キーが不在だった。

2 つが重なって、この文はインスタンスファミリーを制限したのではなくサービスを丸ごと遮断した。 許可リストに g5.* と書いてあるのに g5 のノードグループを作れなかった。

これをリハーサルで踏んだ値はこうだ。

このポリシー欠陥に有料 GPU セッションで初めて出会っていたら、カードを点けたまま デバッグしていた。リハーサルの価値は成功したことではなく、失敗を安い場所で踏んだことにある。

鳴るか確かめていなかった警報#

同じ週に、GPU ノードを一定時間後に 0 へ下げる予約を作り、「これでバックストップができた」と書いた。

翌日その文の根拠をたどると根拠が無かった。確認したのは予約が ENABLED と 表示されることだけだ。それは AWS がその予約を受理したという意味であって、時間になったら 実際に呼び出しを出すという意味ではない。ロールの引き受けが通るのか、ポリシーがその呼び出しを 許すのか、ペイロードがどんな形か — 何も確認していなかった。

ところが本当に確認するには GPU を借りて時間が経つのを待つ必要がある。 支出を抑えるための仕組みを検証するために支出することになる。

抜け道は失敗の位置にあった。知りたいのは呼び出しが出るかであって、呼び出しが成功するか ではない。ならば対象は存在しなくてよい。

存在しないクラスタとノードグループの名前を入れて 2 分後に予約した。リトライ 0 回、完了後は自動削除。

1 つ目の証拠は予約が消えたことである。自動削除は呼び出しが実行された後にしか起きない。 発火しなかった予約はそのまま残る。

2 つ目は監査ログだった。

プリンシパル : assumed-role/gpu-platform-ttl-scaledown/...
リクエスト   : {"scalingConfig": {"minSize": 0, "desiredSize": 0}, ...}
エラー       : ResourceNotFoundException

ロールが引き受けられ、ポリシーが呼び出しを通し、ペイロードはスクリプトが書いたものと同じだった。 失敗したのは対象だけで、その対象は金を使わないためにわざと存在しない名前にしたものだ。 費用は 0 ドルだった。

確認された範囲を正確に書けばこうなる — 予約が時刻どおりにロールを引き受け、その形の呼び出しを 出すまでである。実際のノードグループがその呼び出しで 0 に下がることは、この実験が示したことではない。

入口がルート 1 つしか無かった#

組織を作って 2 日目、クレジットの支援ケースを開こうと管理アカウントにログインしたところ、ルートの MFA が 合わなかった。その数分間、自分が構成した管理経路では組織管理・SCP・Identity Center に触る 方法が無かった。

正確に書くと、AWS には登録済みのメールと電話で本人確認する代替認証経路があり、私はそれを 知っていた。ただしその経路が動くかは確認していない — 結局ログインに成功して使う機会が 無かったからだ。試していない非常経路は、あるものとして数えにくい。

構成が間違っていたからではない。自分が作った入口が 1 つしか無かったからだ。 Identity Center を立てる際、権限セットをラボアカウントにだけ割り当てていた。

管理アカウントに割り当てなかったのは判断ではなく漏れだった。「管理アカウントにはワークロードを置かないから そこですることは無い」と考えていたが、組織・SCP・Identity Center を管理する仕事がまさにそこで 起きる。ワークロードが無いアカウントは、アクセス経路が要らないアカウントではない。

直すのに 3 分。気づくのに 2 日かかり、気づいた契機はMFA がたまたま合わなかったことだった。

この記事が主張しないこと#

  • TTL が実際にコスト事故を防いだという主張ではない。確認されたのは予約が時刻どおりに 呼び出しを出すところまでで、対象はわざと存在しない名前だった。そしてその統制の範囲は ノードグループを 0 に下げることであって、アカウント全体の支出を止めることではない。
  • $0.05・$0.18 は請求書の項目ではない。課金時間に時間単価を掛けた計算値である。 $14.56 と $0.40 は請求・集計から出た値だが、この記事はいずれも請求台帳と別途突き合わせては いない。
  • SCP の欠陥は条件を補って直したのではない。その呼び出しではその条件キーで インスタンスファミリーを制限できないため、その文自体を削除した。
  • SCP の欠陥はこの組織構成でのものである。条件キーの不在が否定演算子を真にすることは 一般的だが、どのキーが不在になるかはサービスと呼び出し経路によって違う。
  • 規模は個人ラボである。ここで統制が有用だった理由の半分は、支出が小さく単一項目の 誤差が目立ったからだ。
  • 予算アラートは発見的統制である。支出を止めるのではなく報告するだけだ。この記事が言うのは それが強力だということではなく、何層かのうち実際に何かを捕まえたのがそれ 1 つだったという 観測である。

残る 1 行はこれである。統制を作ったことと、その統制が発火するのを確認したことは別の仕事であり、 ほとんどの統制は後者をしないまま一覧に載る。そして私の一覧でコストの誤りを捕まえたのは最も単純なもの — 私の見積りと実際の請求を並べてくれたアラート — だった。
