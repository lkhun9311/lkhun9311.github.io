個人プロジェクト#GPUaaS コントロールプレーン

AWS GPU ラボのコスト誤りを捕まえたのは予算アラートだけでした
ほかの三つは発火を証明したか、つながれていただけで、コストを捕まえたことはありません。

個人プロジェクトとして Kubernetes ネイティブ GPU コントロールプレーン を作っていて、 そのために GPU を借りる AWS ラボアカウントを使っています。ここで一番怖いのは実験が 外れることではなく、点けたものを忘れることです。

だから統制を 4 層作りました。サービスコントロールポリシー、TTL のスケールダウン予約、 月次予算アラーム、一時的な apply と destroy です。1 か月回してみると、リハーサルは ポリシーの欠陥を捕まえ、TTL は発火を証明しました。ところがコストそのものの誤りを 捕まえたのは 4 つのうち 1 つ、予算アラームだけでした。私の見積りから丸ごと 抜けていた項目が請求書にあり、アラームが見積りと請求を並べてくれたので見えました。

そしてそのアラームを、Terraform が黙って消すところでした。状態ファイルの外で作った 資源なので、次の apply の計画に削除として載っていたのです。

想定読者#

  • 個人のカードでクラウドの GPU を借りて実験している方
  • 予算アラート・ポリシー・予約停止などの安全装置を何層か掛けている方
  • その安全装置が実際に鳴るかはまだ確かめていない方

80% は早期警告ではありません#

月次予算の上限は 30 ドルにしました。通知のしきい値として既定で付くのは予算の 80% です。ところがこの プロジェクトの支出は3 時間のバーストで到着します。有料 GPU セッションは半日で始まって終わり、 月単位のしきい値はそのセッションが既に終わった後にしか何も言いません。

そこで早期警告を 10% に置きました。30 ドルの予算なら 3 ドル、おおよそ有料セッション 1 回分です。 そうすればその月の最初のセッションがいくら使ったかを報告し、次のセッションはまだ考え直せます。

しきい値を選ぶ基準は「何パーセントが妥当か」ではなく、「これが鳴ったとき、まだ変えられる決定が 残っているか」です。この支出の形では 80% はその条件を満たしません。

見積りから丸ごと抜けていた項目#

2026-09-03、3 回目の有料セッションの後にそのアラートが鳴りました。

横にスクロールすると続きが見えます

アラートが報告した月次累計と、私の見積りの差。
金額
アラートが報告したその月の累計$14.56
私が持っていた概算約 $8

差額を追うと NAT ゲートウェイのデータ処理料金でした。インスタンス時間と EKS の料金は 数えていたが、バイトが NAT を通る費用は見積りに存在すらしていませんでした。

なぜ見えなかったかは明確です。私の見積りは自分が点けたものの一覧でした。GPU インスタンス、 EKS コントロールプレーン、NAT ゲートウェイ — 時間単価があるものです。ところが NAT は時間料金と 処理したバイトあたりの料金を別に取り、コンテナイメージを引くたびにその行が伸びます。 点けたものを数える一覧は、点けたものが何をしているかを数えません。

そして Terraform がそれを消すところでした#

そのアラートは 2026-08-31 にコンソールで手作業で作り、設定には書きませんでした。

数日後、イメージのミラーリポジトリを追加しようと plan を回したところ、この通知ブロックが 設定には無くアカウントには有る状態で現れました。そのまま apply していれば、 無関係な変更の副作用として、静かに消えていました。

消えるところだったのが、よりによってこのアカウントでこれまで唯一コストの誤りを捕まえた統制 でした。

これはこのプロジェクトが繰り返し作り出す形です。値が片方にしか無く、両者を比べるものが何も ありません。コンソールで急いで作ったものはコードに無く、コードを真実とみなすツールはコードに無いものを 削除対象として見ます。だからアラートを Terraform に移す際、なぜこのブロックが存在するのかと、一度 消えるところだったという事実をコメントとして併記しました。次にこのブロックを消そうとする人が読めるように。

同じ 15.6GB を無料で運ぶ方法#

NAT の行が見えた途端、次の実験の形が変わりました。

2026-09-04 の問いは vLLM のスケジューラ設定に関するものでした。ゲートウェイも Kubernetes も要らず、 インスタンス 1 台で足ります。すると 1 つの事実がコストの大部分を分けます。

デフォルトサブネットのインスタンスはパブリック IP でインターネットゲートウェイを通じて 通信し、インバウンド転送は無料です。

それまでの有料実行は、コンテナイメージとモデルの重み — コールドなノード 1 台あたり 約 15.6GB — を GB あたり $0.059 の NAT でダウンロードしていました。 (最初の 3 セッションの NAT データ処理の請求は合計約 92GB・$5.43 です。1 セッション 15.6GB を 3 回ではその総量を説明できず、私はその差を突き合わせていません。)パブリックサブネットのインスタンス 1 台に 移すとその行は消え、その日の実験は約 $0.40 で終わりました。

変えたのはアルゴリズムではなくバイトが通る経路です。そしてその経路が見えるように なったのは、アラートが請求書を項目別に読ませたからです。

わざと失敗したリハーサル、20 分 5 セント#

最初の有料 GPU セッションの前に、GPU を点けないリハーサルを回しました。クラスタを apply して すぐ destroy します。目的は性能ではなく手順が最後まで通るかです。

apply が失敗しました。原因は前日に私が付けたサービスコントロールポリシーでした。

Error: creating EC2 Launch Template: UnauthorizedOperation
  ec2:CreateLaunchTemplate ... explicit deny in a service control policy

問題の文はインスタンスタイプを許可リストで制限しようとするものでした。

{
  "Effect": "Deny",
  "Action": ["ec2:CreateLaunchTemplate", "ec2:CreateLaunchTemplateVersion"],
  "Condition": { "StringNotLike": { "ec2:InstanceType": ["t3.*", "g4dn.*", "g5.*"] } }
}

ここに 2 つが重なりました。

1 つ。IAM の否定条件演算子はキーが無ければ真になります。StringNotLike は 「この値がリストと異なれば」だけでなく、キーがそもそも無い場合にも満たされます。

2 つ。EKS マネージドノードグループはインスタンスタイプをノードグループに持ち、起動テンプレートには 入れません。そのため ec2:InstanceType キーが不在でした。

2 つが重なって、この文はインスタンスファミリーを制限したのではなくサービスを丸ごと遮断しました。 許可リストに g5.* と書いてあるのに g5 のノードグループを作れませんでした。

これをリハーサルで踏んだ値はこうです。

横にスクロールすると続きが見えます

2 回のリハーサルの結果と残留物。
回結果後片付け残留物
1 回目apply 失敗(SCP が拒否)destroy 85 個0

このポリシー欠陥に有料 GPU セッションで初めて出会っていたら、カードを点けたまま デバッグしていました。リハーサルの価値は成功したことではなく、失敗を安い場所で踏んだことにあります。

鳴るか確かめていなかった警報#

同じ週に、GPU ノードを一定時間後に 0 へ下げる予約を作り、「これでバックストップができた」と書きました。

翌日その文の根拠をたどると根拠がありませんでした。確認したのは予約が ENABLED と 表示されることだけです。それは AWS がその予約を受理したという意味であって、時間になったら 実際に呼び出しを出すという意味ではありません。ロールの引き受けが通るのか、ポリシーがその呼び出しを 許すのか、ペイロードがどんな形か — 何も確認していませんでした。

ところが本当に確認するには GPU を借りて時間が経つのを待つ必要があります。 支出を抑えるための仕組みを検証するために支出することになります。

抜け道は失敗の位置にありました。知りたいのは呼び出しが出るかであって、呼び出しが成功するか ではありません。ならば対象は存在しなくてよいです。

存在しないクラスタとノードグループの名前を入れて 2 分後に予約しました。リトライ 0 回、完了後は自動削除。

1 つ目の証拠は予約が消えたことです。自動削除は呼び出しが実行された後にしか起きません。 発火しなかった予約はそのまま残ります。

2 つ目は監査ログでした。

プリンシパル : assumed-role/gpu-platform-ttl-scaledown/...
リクエスト   : {"scalingConfig": {"minSize": 0, "desiredSize": 0}, ...}
エラー       : ResourceNotFoundException

ロールが引き受けられ、ポリシーが呼び出しを通し、ペイロードはスクリプトが書いたものと同じでした。 失敗したのは対象だけで、その対象は金を使わないためにわざと存在しない名前にしたものです。 費用は 0 ドルでした。

確認された範囲を正確に書けばこうなる — 予約が時刻どおりにロールを引き受け、その形の呼び出しを 出すまでです。実際のノードグループがその呼び出しで 0 に下がることは、この実験が示したことではありません。

入口がルート 1 つしかありませんでした#

組織を作って 2 日目、クレジットの支援ケースを開こうと管理アカウントにログインしたところ、ルートの MFA が 合いませんでした。その数分間、自分が構成した管理経路では組織管理・SCP・Identity Center に触る 方法がありませんでした。

正確に書くと、AWS には登録済みのメールと電話で本人確認する代替認証経路があり、私はそれを 知っていました。ただしその経路が動くかは確認していない — 結局ログインに成功して使う機会が 無かったからです。試していない非常経路は、あるものとして数えにくいです。

構成が間違っていたからではありません。自分が作った入口が 1 つしか無かったからです。 Identity Center を立てる際、権限セットをラボアカウントにだけ割り当てていました。

管理アカウントに割り当てなかったのは判断ではなく漏れでした。「管理アカウントにはワークロードを置かないから そこですることは無い」と考えていたが、組織・SCP・Identity Center を管理する仕事がまさにそこで 起きます。ワークロードが無いアカウントは、統制が要らないアカウントではありません。

直すのに 3 分。気づくのに 2 日かかり、気づいた契機はMFA がたまたま合わなかったことでした。

この記事が主張しないこと#

  • 金額の出所は混在しています。$14.56 と $0.40 は請求・集計から出た値、約 $8 は私の見積り、$0.05・$0.18 は課金時間 × 時間単価の計算値です。いずれにせよ個人ラボの規模であって本番ではありません。アカウント ID・ポリシー ID は書きません。
  • TTL が実際にコスト事故を防いだという主張ではありません。確認されたのは予約が時刻どおりに 呼び出しを出すところまでで、対象はわざと存在しない名前でした。そしてその統制の範囲は ノードグループを 0 に下げることであって、アカウント全体の支出を止めることではありません。
  • $0.05・$0.18 は請求書の項目ではありません。課金時間に時間単価を掛けた計算値です。 $14.56 と $0.40 は請求・集計から出た値だが、この記事はいずれも請求台帳と別途突き合わせては いない。
  • SCP の欠陥は条件を補って直したのではありません。その呼び出しではその条件キーで インスタンスファミリーを制限できないため、その文自体を削除しました。
  • SCP の欠陥はこの組織構成でのものです。条件キーの不在が否定演算子を真にすることは 一般的だが、どのキーが不在になるかはサービスと呼び出し経路によって違います。
  • 規模は個人ラボです。ここで統制が有用だった理由の半分は、支出が小さく単一項目の 誤差が目立ったからです。
  • 予算アラートは発見的統制です。支出を止めるのではなく報告するだけです。この記事が言うのは それが強力だということではなく、何層かのうち実際に何かを捕まえたのがそれ 1 つだったという 観測です。

おわりに#

  • 80% は早期警告ではありません。残り 20% で変えられる決定があって初めて警告になります。
  • 見積りから抜けた項目は、見積りを読み直しても出てきません。請求と並べると出てきます。
  • state ファイルの外で作った資源は、次の plan の削除一覧にあります。
  • 統制を作ったことと、それが鳴るのを確認したことは別の仕事です。 ほとんどは後者をしないまま一覧に載ります。

統制を作ったことと、その統制が発火するのを確認したことは別の仕事であり、 ほとんどの統制は後者をしないまま一覧に載ります。そして私の一覧でコストの誤りを捕まえたのは最も単純なもの — 私の見積りと実際の請求を並べてくれたアラート — でした。
