モニタリングの Cache 三つをまとめたら互いの値を消しました
分かれていたとき偶然守られていた規則を、すべてコードに書く必要がありました。

2026年9月

社内クラウド管理コンソールの Backend を作っています。④編までで三つの画面をそれぞれ 直しました。最初のデータはどれも速くなったのに、同じ源を画面ごとに別々に収集していました。 ノードのメトリックはダッシュボードと物理ノードが重ねて読み、Instance のメトリックは ダッシュボードと仮想リソースが重ねて読んでいました。

Cache 三つを一つにまとめれば、その重複はなくなります。データ構造三つを一つにするだけに 見えました。実際の作業はそれよりずっと大きなものでした。別々だったから偶然 守られていたことが、すべて明示すべき契約になったからです。

まとめた途端に回帰が一つ出ました。片方の画面だけ開いておくと、もう片方の画面の最後の値が Cache から消え、再入場が 5,115ms でした。この記事はその契約を一つずつ書きます。部分失敗を 項目ごとに引き継ぐこと、可変 DTO を共有しないこと、そして障害を空の値として確定しないこと です。

この記事の想定読者#

  • 似た Cache をいくつか一つにまとめようとしている方
  • 複数の消費者が同じ源をそれぞれ読んでいる構造をお持ちの方
  • 「オブジェクト数を減らすリファクタリング」で始めて、契約を書き直すことになった方

統合前の構造が持っていた三つ#

一つ目、重複収集。三画面の 15 秒周期が重なると、同じノードと Instance を 何度も読みます。画面が増えるほど源の負荷が消費者の数に比例します。

二つ目、可変 DTO の共有。構造 Cache が返したオブジェクトを、画面ごとに その場でメトリックで埋めていました。ある Thread が値を変えているあいだに別の Thread が直列化すると、一つの Payload に別々の時点が混ざります。 原子的な参照でポインタを入れ替えても、中のオブジェクトが共有かつ可変なら不変スナップショットでは ありません。

三つ目、障害を空の値として確定すること。インフラの取得やメトリックの取得が 失敗したのに、空のリストを新しい正常スナップショットとして公開すると、最後の正常な画面が 0 で 塗り替えられます。③編と④編で画面ごとに出会った問題です。

部分的な失敗は項目ごとに引き継ぎます#

ダッシュボードはノードと Instance の結果を合わせて見せます。 Instance のメトリックだけ失敗したからといって成功したノードまで前の世代に戻すと、 依存先一つの障害が画面全体を古くします。逆に空の Instance 一覧を新しい値として受け取ると、 実際の VM 数を 0 で塗り替えます。

そこで③編の五つの分岐を共通の判定に引き上げ、項目ごとに適用しました。

FRESH              新しいデータと新しい世代で公開
EMPTY_VALID        対象が 0 なので正常な空データとして公開
INFRA_UNAVAILABLE  前のデータを引き継ぎ + 劣化表示
FETCH_FAILED       前のデータを引き継ぎ + 劣化表示
NO_VALID_METRICS   前のデータを引き継ぎ + 劣化表示

まとめた直後に回帰が出ました#

統合後にいちばん目立ったのはページを移ってから戻ったときでした。

単一 Producer はいま購読されている経路だけを計算してマップ一つで公開し、 公開のときに前のマップをまるごと入れ替えていました。物理ノードの画面だけ開いた状態で 更新が回ると、最新の世代にはノードだけが残ります。 前のダッシュボードの値は Cache から消えます。

そのあとダッシュボードに接続すると、すぐ送る値が無いので 収集を一周待ちます。測ると約 5,115msで、 すぐにもう一度接続すると 16ms でした。

分離された Cache が黙って持っていた契約はこれでした。 「別の経路の更新が自分の最後の値を消さない。」 まとめたことでその契約が消え、誰もそれを書き残していませんでした。

latestGeneration       今回の収集に含まれた経路の集合
lastPageByPath[経路]   各経路の最後に成功した payload

公開(世代):
    latestGeneration を入れ替える
    含まれた経路だけを lastPageByPath にマージする

接続(経路):
    lastPageByPath[経路] をすぐに送る
    その経路が latestGeneration に無ければ更新を要求する

遅い消費者を収集から切り離しました#

SSE の送信は遅いクライアントで詰まることがあります。収集の Lock を配信が終わるまで握っていると、 一つのクライアントのネットワークが次の収集を遅らせます。 そこで新しい世代を公開した直後に収集トークンを手放し、送信は別のコンポーネントに渡しました。

ところが通常の実行キューにセッションごとの処理を入れると、小さな Pool では 前のセッションだけが繰り返し受け入れられ、後ろのセッションが拒否され続ける飢餓が 起こりえました。送信器は準備 Deque と常駐 Worker を使います。

  • セッションごとに待ちの Payload はいちばん大きい世代を一つだけ持ちます。
  • セッションはキューに一度だけ入ります。
  • Worker が一度送ったあと新しい待ちがあれば末尾に入れ直します。
  • すでに送った世代以下の値は捨てます。
  • 終了したセッションは送信の直前にもう一度確認します。

同期送信そのものが消えたわけではありません。 同時に詰まったセッションの数が Worker の数を超えれば、送信は依然として遅れます。 非同期 I/O や遅いセッションの先制的な追い出しは別の課題として残しました。

統合の結果#

ダッシュボード約 6,776ms約 23ms約 8,607ms約 55ms

三つともエラー率 0%、Apdex 1.000 です。REST の取得も数十 ms 以内を保ち、 先の改善が戻っていないことを確認しました。 ただし仮想リソースを測り直した時点では一部のメトリックが無い環境でした。 データがある条件での直接比較は④編の個別測定を基準にしています。

共有状態をまとめるときに確認すること#

Cache の統合はオブジェクト数を減らすリファクタリングではありません。 次の問いに答える必要があります。

  • いま購読していない消費者の最後の値は保たれるか
  • ある源の失敗が別の源の成功を戻すか
  • 空の値は正常な 0 か、判断不能か
  • Payload の中のオブジェクトまで世代ごとに不変か
  • 新しい値と古い値が逆転して送られうるか
  • 遅い消費者がProducer を止めるか
  • プロセスが複数ならProducer も複数か

この記事が主張しないこと#

  • 運用統計ではありません。単一利用者の逐次測定です。
  • 仮想リソースの最終値は直接比較ではありません。測り直しの時点で一部の メトリックが無い環境だったため、④編の個別測定を基準にしています。
  • 遅い消費者の問題を解決したとは言いません。収集から切り離しただけで、 同時に詰まったセッションが Worker の数を超えれば送信は依然として遅れます。
  • Producer が複数の場合は扱っていません。上の問いの最後の項目が そのまま残っています。

おわりに#

五編から残ったものを書いておきます。

  • 「直す根拠がない」と「測っていない」は違います。 測った場所が、利用者が待っていた場所と違いました。
  • 「先に作っておいて渡す」は、誰が作って誰が公開するかを決めてはじめて一行になります。
  • 「空」は観測ではなく、解釈が要る値です。
  • 画面の遅延は、遅く終わるゲートが決めます。
  • 別々だったから守られていたことは、まとめるときに契約として書かなければなりません。

共有状態は一か所に集めたから単純になるのではありません。暗黙だった契約をすべて表に出して はじめて管理できます。

重複収集をなくして得た性能より、これらの意味をコードとテストに書き残したことの ほうが長く残る結果だと思います。五編お読みいただきありがとうございました。
