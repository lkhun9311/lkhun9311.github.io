스레드를 늘렸더니 꼬리가 길어졌다

Writing · 2026년 9월 · 9분

범위. 2026년 5월, OpenStack 기반 프라이빗 클라우드 관리 콘솔의 볼륨 목록 화면을 고친 기록이다. 제품명·버전·고객사는 쓰지 않는다. 아래 숫자는 전부 사내 시험 환경에서 JMeter 로 잰 값이고, 프로덕션 트래픽이 아니다. 부하 조건은 여섯 구성 모두 동일하다 — 동시 사용자 50명 · Ramp-Up 2분 · 지속 10분 · Think Time 2~5초. 코드는 실제 코드를 인용하되 사내 식별자는 지웠다.

화면은 볼륨이 늘수록 선형으로 느려지다가 결국 10분 Timeout 으로 죽었다. 원인은 볼륨 하나마다 외부 API 를 순차로 부르는 루프였고, 처방은 뻔해 보였다. 병렬로 돌리면 된다.

병렬로 돌리자 더 느려졌다. 캐시 설정을 고정한 채 순차를 병렬로 바꾸니 P99 가 42.6초에서 79.0초가 됐다. 이 글은 그 한 칸이 무엇을 알려줬는지, 그리고 그 한 칸을 볼 수 있게 만든 시험 설계에 대한 것이다.

  • 여섯 줄

여섯 줄#

조치를 한꺼번에 넣고 전후를 재면 "빨라졌다"는 사실 하나만 남는다. 무엇이 얼마나 기여했는지는 모른다. 그래서 구성을 여섯 단계로 나눠 같은 조건으로 각각 쟀다.

가로로 스크롤하면 나머지가 보입니다

단위는 밀리초다. ①의 600,017ms 는 측정값이 아니라 10분 Timeout 상한에 붙은 값이다 — 그 구성은 요청의 83.3%가 끝나지 못했다. 끝나지 못한 요청의 지연은 "600초"가 아니라 모른다가 정답이고, 표의 그 칸은 그렇게 읽어야 한다.

③이 ②보다 나쁘다는 게 먼저 눈에 걸린다. 42.6초 대 129.9초다. 그런데 이 두 줄은 서로의 대조군이 아니다 — ②는 캐시 5초에 순차이고 ③은 캐시 없음에 병렬이라 두 변수가 동시에 바뀐다. 이 차이에서 병렬화의 효과만 떼어낼 수 없다.

캐시를 고정한 쌍은 ②와 ④다. 둘 다 캐시 5초이고, 순차냐 병렬이냐만 다르다.

P99 가 42.6초에서 79.0초로 올랐다. 스레드를 늘렸는데 꼬리가 1.85배가 됐다. 이것이 이 실험에서 병렬화 단독의 효과로 말할 수 있는 전부이고, 방향은 분명하다 — 해로웠다.

왜 ③이 ②보다 나쁜가#

병렬화한 코드는 이렇게 생겼다.

final Map<String, VolumeGroup> groupCache = new ConcurrentHashMap<>();

final List<VolumeDto> dtos = volumes.stream()
    .map(volume -> CompletableFuture.supplyAsync(() -> {

        // 여러 스레드가 동시에 이 블록에 들어온다
        final VolumeGroup group = groupCache.computeIfAbsent(
            volume.getGroupId(),
            gid -> client.groups().get(gid)   // ← 외부 I/O 를 락 안에서 부른다
        );
        ...
    }, executor))
    .map(CompletableFuture::join)
    .collect(Collectors.toList());

ConcurrentHashMap 을 썼으니 안전하다고 생각하기 쉽다. 안전한 것은 맞다. 문제는 안전성이 아니라 그 안전성을 무엇으로 사는가다.

computeIfAbsent 는 매핑 함수를 해당 키가 속한 버킷을 잠근 채 실행한다. 매핑 함수가 맵을 읽고 끝나는 계산이면 그 구간은 나노초 단위다. 여기서는 그 자리에서 네트워크 왕복을 한다.

그러면 이런 일이 벌어진다. 같은 그룹에 속한 볼륨이 M 개면, executor 에 제출된 M 개의 스레드가 같은 키로 computeIfAbsent 에 들어온다. 하나가 외부 호출을 하는 동안 나머지 M−1 개는 그 버킷 앞에 줄을 선다. 순차 코드에서는 한 줄로 서서 기다리던 것이 병렬 코드에서도 한 줄로 서고, 스레드 풀 자리는 그동안 묶여 있다. 얻은 것은 없고 컨텍스트 스위칭과 풀 고갈만 늘었다.

그래서 ③은 ②보다 나쁘다. ②는 5초 캐시 덕분에 외부 호출 횟수 자체가 적었고, ③은 캐시가 없어 모든 요청이 그 잠긴 자리를 통과해야 했다.

용어 하나. 이 구조를 "세그먼트 락"이라고 부르는 문서를 자주 본다. 세그먼트는 Java 7 시절 용어다. Java 8 이후 ConcurrentHashMap 은 세그먼트를 없애고 버킷(bin) 단위로 잠근다. 잠김의 범위가 더 좁아졌을 뿐, 매핑 함수가 도는 동안 그 자리가 잠긴다는 사실은 그대로다. 락 범위가 좁아진 것이 락 안에서 I/O 를 해도 된다는 뜻은 아니다.

고치는 방법은 락을 직접 다루는 걸 그만두는 것이다. Caffeine 의 LoadingCache 는 캐시 미스에서 키마다 로더를 정확히 한 번만 실행하고 나머지 호출자는 그 결과를 기다린다. 같은 "한 번만 부른다"를 보장하면서, 기다리는 쪽이 맵의 버킷을 붙들고 있지 않는다.

두 번째 결함: "없음"을 캐시하지 않았다#

같은 화면의 다른 경로에는 직접 만든 캐시가 하나 더 있었다.

public static List<Message> messages(final String resourceId) {
    CacheManager manager = CacheManager.getInstance().init(Message.class, 10);
    final List<Message> cached = manager.list(Message.class);

    if (cached == null || cached.isEmpty()) {              // ← 여기를 여럿이 동시에 통과한다
        client.messages().list(...)
              .forEach(r -> manager.set(Message.class, r.getResourceUuid(), r));
    }
    ...
}

결함이 두 겹이다.

하나. 병렬화된 N 개 스레드가 isEmpty() 검사를 동시에 통과하면 N 개가 전부 외부 API 를 부른다. 흔한 cache stampede 다.

둘. 조회 결과가 0건이면 forEach 가 한 번도 돌지 않는다. 그러면 캐시에 아무것도 저장되지 않는다. 다음 요청도 캐시를 비어 있다고 보고 또 부른다. "없음"이라는 답을 캐시하지 않은 것이다. 그리고 이 경로에서는 0건이 흔한 답이었다 — 즉 가장 빈번한 경우에 캐시가 전혀 작동하지 않았다.

여기서도 처방은 같다. Caffeine 은 로더가 빈 리스트를 돌려줘도 그 빈 리스트를 값으로 캐시한다. "값이 없다"와 "아직 안 물어봤다"를 자료구조가 구분해 준다. 직접 만든 캐시는 그 둘을 같은 isEmpty() 로 뭉갰다.

이 두 결함은 성질이 다르다. 첫째는 정확성은 맞는데 느린 결함이고, 둘째는 캐시가 있다고 믿게 만드는 결함이다. 둘째가 더 오래 살아남았던 이유는 명백하다 — 코드에 캐시가 있었고, 아무도 그 캐시가 채워지는지 세어 보지 않았다.

고친 것 중 무엇이 실제로 컸는가#

여섯 줄을 인접한 쌍으로 읽으면 각 조치의 기여가 분리된다.

마지막 한 단계가 배수로는 가장 컸다 — 6.9초에서 23ms 로 약 300배다. 절대량으로는 ④→⑤ 가 더 크다(약 72.1초 감소 대 약 6.84초). 둘 다 참이고, 어느 쪽을 "가장 컸다"고 부를지는 척도가 정한다. 다만 어느 척도로 보든 그 단계는 맨 마지막에 넣은 것이라, 전후만 쟀다면 앞선 네 조치의 공으로 돌아갔을 것이다.

⑤→⑥ 이 왜 그렇게 큰가. ⑤까지는 만료된 캐시를 읽으려는 요청이 새로 채워질 때까지 기다린다. Caffeine 의 refresh 는 만료 시점에 기존 값을 계속 돌려주면서 백그라운드에서 갱신한다. 즉 마지막 단계가 없앤 것은 조회 비용이 아니라 갱신을 기다리는 시간이었고, 그 시간이 꼬리 지연의 대부분이었다.

같은 처방을 나머지 세 화면에도 적용했다. 네 화면 모두 같은 부하 조건에서 잰 값이다.

전후만 쟀다면 무엇을 잘못 보고했을까#

①과 ⑥만 쟀다면 보고서는 이렇게 나왔을 것이다. "캐시와 병렬화를 적용해 오류율 83.3%를 0%로, P99 를 10분에서 23ms 로 개선했다."

모든 숫자가 참이다. 그리고 병렬화가 기여했다는 함의는 거짓이다. 병렬화는 단독으로는 해로웠다. 캐시를 고정해도 병렬이 순차보다 나빴으므로, 이 실험은 병렬화의 양의 기여를 보이지 않는다. 그 사실을 모른 채 다른 화면에 "여기도 병렬화하자"를 처방했다면 같은 함정에 다시 들어갔을 것이다.

실제로 이 표는 진단 근거로도 쓰였다. 캐시를 고정한 채 병렬화가 악화라는 것은 병목이 CPU 나 처리량이 아니라 직렬화 지점이라는 뜻이고, 그래서 코드에서 락을 찾았고 computeIfAbsent 안의 외부 호출이 나왔다. 표가 코드를 가리켰다.

예상되는 반문 두 가지를 미리 적어 둔다.

"그냥 스레드 풀을 키우면 되지 않나?" — 병목이 락이면 스레드를 늘려도 대기자만 늘어난다. ②↔④ 가 정확히 그 실험이다. 같은 캐시 설정에서 순차보다 병렬이 느렸다.

"Median 4ms 는 캐시 히트라 당연한 것 아닌가?" — 맞다. 그래서 Median 만 보지 않는다. 같은 줄의 P99 가 23ms 이고 Apdex 가 1.000 이다. Apdex 는 만족·용인·불만족을 가중해 세는 값이라 중앙값이 아니라 분포 전체를 본다 — 다만 1.000 이라는 표기가 표본 전체를 증명하지는 않는다(아래 유보).

이 글이 주장하지 않는 것#

  • 병렬화가 나쁘다는 주장이 아니다. 락 안에서 I/O 를 하는 코드를 병렬화하면 나쁘다. 다만 이 여섯 구성 안에 그 조건을 없앤 병렬 구성이 없으므로, 없앴을 때 병렬화가 값을 하는지는 이 실험이 보이지 않는다. ③→④ 는 캐시만 바뀐 쌍이라 그 답이 아니다.
  • 프로덕션 측정이 아니다. 사내 시험 환경에서 합성 부하로 잰 값이다. 실제 사용자 분포·데이터 규모·네트워크는 다르다.
  • ②와 ③은 서로의 대조군이 아니다. 캐시와 실행 방식이 동시에 바뀌므로 그 차이(42.6초 → 129.9초)에서 어느 쪽 효과인지 나눌 수 없다. 이 글이 병렬화 단독의 근거로 쓰는 것은 캐시를 고정한 ②→④ 뿐이다.
  • Apdex 1.000 은 표본 전체가 만족 임계 안이라는 증명이 아니다. 도구 표기가 소수 셋째 자리 반올림이면 소수의 tolerating 표본이 있어도 1.000 으로 보인다. 반올림 전 원시값은 확인하지 않았다.
  • 구성마다 한 번씩만 쟀다. 반복 측정으로 분산을 낸 것이 아니라서, 인접한 두 구성의 차이가 작을 때는 그 차이를 근거로 삼지 않았다. 이 글이 근거로 쓰는 것은 ②→④ 처럼 배 단위의 차이뿐이다.
  • ①의 600초는 지연이 아니다. Timeout 상한이다. ①의 P99 를 "600초"로 인용하면 측정하지 못한 것을 측정한 척하는 것이 된다.
  • Apdex 임계는 도구 기본값을 그대로 썼다. 서비스 수준 목표를 별도로 정의해 맞춘 값이 아니다.

남는 한 줄은 이것이다. 고친 것이 여러 개면, 무엇이 고쳤는지는 따로 재야 나온다. 그리고 그렇게 재면 가끔, 좋아졌다고 믿었던 조치가 혼자서는 해로웠다는 게 나온다.
