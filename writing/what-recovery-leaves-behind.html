Instance HA ⑧: Recovery Succeeded and It Still Was Not Over
Resource allocations and service states survive a successful move. Leave them and the next recovery is the one that fails.

In part seven we settled where to send it. It was sent, the instance came back up, and the screen reported recovery complete.

Then the next recovery failed. The reason given was that there was no valid host to move to, and the nodes had room.

I assumed the capacity calculation was wrong. It was not. The earlier recovery had left an allocation behind on the node the instance departed from.

Who this is for#

  • Anyone whose automatic recovery went strange from the second run onward
  • Anyone writing down the restore procedure that follows a successful recovery
  • Anyone keeping per-node state on shared storage
  • Anyone who read part seven and wondered what is left after the send

I thought moving it was the end#

A successful recovery means the instance came back up on another node. That verdict is correct. It is simply not the point where cleanup finished.

The four sit on different layers. A resource count, a service state, a file and a process cannot be cleared in one action, and each is checked somewhere else.

An allocation stays where it left#

The first row took the longest. The instance was running on the new node while the node it left still held an allocation for that same instance.

There is a path that clears this automatically. It does not run when the node returns through a network reconnection. So a separate cleanup went in for the moment a node comes back, and it clears only the allocation on the departed side.

One thing needs care here. The allocation on the side that is actually running must not be touched. So the target is narrowed to instances running elsewhere that still hold an allocation on the returning node.

A shared state file gets overwritten#

The second long one was a node that came back but whose service would not start. The log said the identifier this node holds is not its own.

The cause was the shared storage. Several nodes share one directory, and inside it a file that has to differ per node existed only once. Depending on the order the nodes start, whichever came up first overwrites it.

The fix was to take that file off the shared path and let each node keep its own. What is good to share and what must not be shared were sitting in one directory.

Both failures had the same root#

Two messages came back when recovery failed. One said the instance files on shared storage were in an invalid state; the other said there was no valid host to move to.

In both cases the surface message and the real cause differed. An allocation left by the earlier failure was the common root. It stays invisible while you change settings and retry.

Restoring is not automatic#

Last comes restoring. Recovery switches off the failed node's compute service. That is correct, so nothing gets scheduled there again, but bringing the node back does not switch it on.

# What to check after the screen says recovery finished

  1. compute service state
     switch it back on. Recovery switched it off and will not switch it back

  2. per-node state value
     confirm the node uses its own value rather than a shared path

  3. agent state
     restart it if it was disconnected for a long time

  4. allocation where the instance left
     confirm the same instance is not held in two places

Has the agent come backAfter a long disconnection it needs restarting
Is the departed allocation emptyIf not, the next recovery fails

The four are in order. The state file has to be right before the service is switched on, and the allocation is checked last so that the first three are reflected.

Limits: what this post does not claim#

  • ⚠️ What this series comes from is a design document. This part is read out of the build and the test records; I did not change that code.
  • The four leftovers are what was observed in this environment. It does not follow that the same list appears in another setup.
  • The allocation cleanup runs on a best-effort basis. It is skipped when the resource count service is unavailable.
  • The shared state file problem only appears in setups that use shared storage.
  • This came from internal material, so product names, customers, addresses, accounts, hostnames and paths are left out.

Wrapping up#

The conclusion is one line. The verdict that recovery succeeded and the moment cleanup finished are two different points. Leave the gap and the next recovery fails in its place.

And none of the leftovers appear on screen. Only the success shows, and the rest returns later wearing a different face. That is why the restore steps are worth writing down.
