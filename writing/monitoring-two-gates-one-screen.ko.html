REST와 SSE 중 한쪽만 고치니 화면은 그대로였습니다
화면이 끝나는 시각은 둘 중 늦게 끝나는 쪽이 정합니다.사내 Cloud 관리 Console · 통합 모니터링 연작 ④

사내 Cloud 관리 Console의 Backend를 만들고 있습니다. ③편까지 화면 두 개를 고쳤습니다. 세 번째인 가상자원 화면은 앞의 둘과 달랐습니다.

이 화면에는 서로 따로 시작하는 데이터 경로가 둘 있습니다. REST가 프로젝트별 할당량과 사용량을 만들고 SSE가 가상서버 메트릭을 보냅니다. 개선 전 REST는 약 2.6초, SSE 첫 데이터는 약 1.4초였습니다.

그래서 한쪽만 고치면 화면은 안 빨라집니다. 화면이 끝나는 시각은 둘의 합이 아니라 늦게 끝나는 쪽이기 때문입니다. 이 식을 먼저 적어 두고 시작했습니다.

고친 뒤에 숨어 있던 것이 하나 드러났습니다. SSE가 24ms가 되자 REST보다 먼저 도착해서 화면이 비었습니다. 느린 쪽이 순서를 지켜 주고 있었던 것입니다.

이 글의 예상 독자#

  • 화면 하나가 여러 요청으로 채워지는 구조를 가진 분
  • 목록을 돌면서 항목마다 외부 API를 부르는 코드를 가진 분
  • 「한쪽을 빠르게 했는데 화면은 그대로」를 겪어 보신 분

완료 조건을 식으로 적었습니다#

화면 완료 = max(REST 사용량, SSE 첫 메트릭, 작은 설정 요청)

REST만 고치면 SSE의 1.4초가 남고 SSE만 고치면 REST의 2.6초가 남습니다. 이 화면의 성능 작업은 단일 병목 최적화가 아니라 서로 다른 두 게이트를 없애는 일이었습니다.

첫째 게이트, 프로젝트 수만큼 도는 호출#

REST 경로는 프로젝트 목록을 돌면서 각 프로젝트의 컴퓨트와 네트워크 또는 스토리지 할당량을 차례로 조회했습니다. 프로젝트가 N개면 외부 호출이 약 2N개가 됩니다. 클라이언트를 만들 때마다 인증까지 하는 경로라면 비용은 더 커집니다.

먼저 떠오르는 해법은 병렬화입니다. 그런데 제한 없는 병렬 호출은 인증 서비스와 외부 API와 애플리케이션 Thread Pool에 순간 부하를 몰아넣습니다. 중앙값은 줄어도 p99와 오류율이 나빠질 수 있고 요청이 몰리면 사용자 수만큼 같은 팬아웃이 복제됩니다.

고른 방법은 팬아웃을 사용자 요청에서 떼어 내는 것이었습니다.

백그라운드 사용량 로더
    현재 프로젝트 목록을 읽는다
    프로젝트마다 필요한 할당량 값을 가져온다
    일관된 사용량 스냅샷 하나를 발행한다

REST 요청
    마지막 완성 스냅샷을 돌려준다

여기서 리뷰 지적이 하나 나왔습니다. 구조 Cache가 저하돼 빈 프로젝트 목록을 돌려줬을 때 로더가 그것을 정상 성공으로 받으면 0/0 사용량이 새 정상값으로 저장됩니다. ③편에서 본 것과 같은 모양입니다.

고친 방법은 구조 정보가 없을 때 예외를 내는 것이었습니다. 실패는 기존 값을 지키지만 빈 목록의 성공은 기존 값을 0으로 덮습니다. serve-stale에서는 실패를 정확히 실패로 표현해야 Cache가 마지막 정상값을 지킵니다.

REST 중앙값은 약 2,627ms에서 5~12ms가 됐고 p99는 약 3,005ms에서 10~20ms대가 됐습니다.

둘째 게이트, 그리고 빨라져서 드러난 것#

SSE 쪽은 앞의 두 화면과 같았습니다. 접속할 때 메트릭을 새로 수집해 첫 데이터를 보냈고 15초 Worker가 미리 만들어 두고 접속에는 즉시 재생하는 구조로 바꿨습니다. 중앙값은 약 1,436ms에서 24ms가 됐습니다.

그런데 여기서 회귀 후보가 하나 나왔습니다.

기존 화면은 REST가 먼저 도착한다는 암묵적 순서에 기대고 있었습니다. 이전 상태가 비어 있으면 SSE 병합 함수가 일찍 반환했고 느렸던 REST가 우연히 그 상태를 먼저 채워 줬습니다. SSE를 수십 ms로 줄이면 순서가 뒤집혀 다음 15초 방송까지 화면이 빕니다.

그래서 안전장치를 셋 뒀습니다. 접속 응답과 주기 방송이 역전될 수 있으므로 만든 시각으로 오래된 프레임을 버리고 프로세스 재기동으로 시각 기준이 되감기면 새 스트림을 받아들이도록 재기준화하고 SSE가 REST보다 먼저 도착해도 첫 프레임으로 프로젝트와 VM 목록을 초기화하게 했습니다.

리뷰에서 남긴 한계#

  • 화면별 Cache가 여전히 다른 화면과 같은 가변 구조 DTO를 공유했습니다. 한 화면이 제자리에서 갱신하는 동안 다른 화면이 직렬화하면 세대가 섞일 수 있습니다.
  • 인프라가 저하됐을 때 SSE가 빈 스냅샷을 정상으로 발행하는 문제는 세 화면에 공통이었습니다. 한 화면에만 예외를 붙이면 같은 원천을 화면마다 다르게 해석합니다.
  • 프로젝트 집합이 바뀔 때의 계약이 없었습니다. 프런트엔드가 기존 프로젝트에 메트릭만 합치면 나중에 추가된 프로젝트가 새로고침 전까지 안 보이고 삭제된 것이 남습니다.

앞의 둘을 다음 편의 공유 Cache 작업으로 넘겼습니다.

이 글이 주장하지 않는 것#

  • 수치는 단일 사용자 순차 측정입니다. 동시 사용자 부하 테스트가 아니라서 「몇 명까지 되는가」로 읽지 않았습니다.
  • 사내 제품이라 코드와 화면을 그대로 옮기지 않았습니다. 제품명·고객사·내부 주소는 빼고 구조와 수치만 남겼습니다.
  • 운영 통계가 아닙니다. 단일 사용자 순차 측정입니다.
  • 병렬화가 나쁘다는 말이 아닙니다. 제한 없는 병렬화를 안 골랐을 뿐이고 골랐을 때 p99가 어떻게 됐을지는 재지 않았습니다.
  • 순서 의존이 운영에서 터졌다고 말하지 않습니다. 개선 중에 발견해서 막았고 사용자가 빈 화면을 본 기록은 없습니다.
  • 프로젝트 집합 계약은 아직 없습니다. 남은 과제로 적어 둡니다.

마치며#

  • 화면 성능은 눈에 띄는 API 하나의 시간이 아닙니다. 병렬 경로 중 마지막으로 끝나야 하는 게이트가 사용자 지연을 정합니다.
  • N+1의 가장 좋은 결과는 N개를 빨리 끝내는 것이 아닙니다. 사용자 요청과 그 N개 사이의 동기 결합을 끊는 것입니다.
  • 느린 것이 순서를 지켜 주고 있었을 수 있습니다. 빨라지면 그 우연이 사라집니다.

각 경로를 따로 재고 전체 완료식을 같이 적어 둬야, 한쪽만 빨라진 것을 완료로 착각하지 않습니다.

다음 편이 마지막입니다. 세 화면의 Cache를 하나로 합치자 따로 있어서 우연히 지켜지던 것들이 계약으로 드러났습니다. 읽어 주셔서 감사합니다.
