Instance HA ⑦: A GPU Instance Only Goes to a Host That Has the Device
Recovery evacuation names its target host outright, so no scheduler steps in. That is why the filtering has to happen before anything is sent.

Everything up to part four was about whether to move at all. This part starts after that decision. Where does it go?

When an instance is created normally, a scheduler finds a host that matches the conditions. The evacuation used in recovery names its target host outright. Nothing picks for you.

I did not think this mattered at first. Look at free memory, CPU and disk and send it, I assumed. But send an instance that needs a GPU to a host without one and it fails a long way down the line.

Who this is for#

  • Anyone running instances that use GPU or PCI devices
  • Anyone reworking the part of automatic recovery that decides where to send things
  • Anyone weighing an early filter against a late failure
  • Anyone who read part four and wondered what happens after the decision to move

No scheduler steps into recovery#

The difference is one line. An ordinary create takes conditions and lets the scheduler find candidates. Recovery evacuation tells it which host to use.

Pick wrongly and it fails later. That failure is slow and the cause is muddy. Filter before sending and it ends early and clearly as "no suitable host", while the other instances keep recovering.

Reading what the instance asks for#

First, read what the instance asks for. The demands live in the flavor's extra entries and come in two kinds: an amount and a trait.

What gets pulled out of the flavor's extra entries.
Example entryWhat is taken
resources:VGPU=1One special resource demand
resources:VCPU=4Excluded. A standard resource, counted separately
trait:…=requiredA required trait. Not consumed, so never deducted
pci_passthrough:alias=…Not counted as a demand, only logged

The three standard resources are excluded because every host has them and they are already counted as free capacity. What is left is the device family.

Which ways of asking can be filtered in advance.
How the flavor asksFiltered in advanceWhy
By resource classYesIt shows up directly in the provider inventory
By required traitYes, at host levelJudged on the union across the tree
By the legacy aliasNoThe alias cannot be resolved to a resource class, so it is logged and passed on

The third row is the one that cannot be closed here. A legacy alias cannot be resolved to a resource class, so it is logged and the final judgement happens when the evacuation actually runs.

Counting what the host actually holds#

With the demand read, count what the host holds. Something trips you here. The device hangs off a provider below the host rather than on the host itself.

So the root named after the host is found, every provider rooted there is gathered into one tree, inventory is summed into availability, and traits are collected as the union across the tree.

Placing only when both conditions hold#

Placement fills hosts starting with the largest instance. For an instance to land on a host, both conditions have to hold.

# Read from the instance
  entries starting with resources: minus the three standard ones  -> required amounts
  entries starting with trait: whose value is required            -> required traits

# No special demand at all? Stop here. The provider is never queried

# Count on the host
  sum inventory across the tree   -> available = total - reserved - used
  union traits across the tree    -> traits held

# Place
  standard fits AND amounts fit AND all required traits held -> confirm and deduct
  nothing takes it -> that instance is recorded as failed

Once confirmed, both standard and special resources are deducted so that too much does not pile onto one host. Traits are not consumed, so they are not deducted.

If there is no special demand at all, the provider is never queried. In an environment without devices this behaves exactly like the previous calculation.

Wrong twice in the same place#

This logic was wrong twice, and both times it was wrong quietly. Neither showed up as a failure; both showed up as a bad placement.

Scroll sideways to see the rest

Two things that went wrong in the same logic.
What was wrongSymptomHow it was fixed
Re-fetching instead of using the embedded entryThe lookup by name failed, the demand came back empty, and a GPU instance was read as an ordinary oneUse the embedded entry first and look up only when it is empty
Checking only whether headroom is exactly zero, then breakingA full first host skipped every later host with room. Negative headroom slipped throughTreat zero or less as full and keep evaluating the next host

The second one is the nastier. Checking only whether headroom is exactly zero and then breaking means that, under a priority ordering, a full first host skips every later host with room. And headroom that went negative through overcommit is not zero, so it passed.

Limits: what this post does not claim#

  • ⚠️ Devices asked for through the legacy alias cannot be filtered in advance. The alias does not resolve to a resource class, so it is logged and passed on, and the final call happens at send time.
  • Trait matching is per host. It does not do the finer matching where a resource and a trait must sit on the same provider. It only rules out hosts that are plainly impossible.
  • If the provider service is unavailable, a warning is logged and placement falls back to standard resources alone. Device filtering does not run in that case.
  • Availability and demands are cached for one recovery run only. If state changes mid-run, the first reading is what that cycle uses.
  • This came from internal material, so product names, customers, addresses, accounts and hostnames are left out.

Wrapping up#

The conclusion is one line. On a path where nothing picks for you, you have to filter before you send. Carry over the habits of a path that has a scheduler and the failure arrives late.

And the value of filtering early is not in the success rate but in the shape of the failure. Ending as "no suitable host" lets every other instance carry on recovering.

Part eight is about what remains after the send. A successful move is not the same as a finished cleanup.
