テストでは常に緑だった Operator が EKS で6回落ちました
Kueue CRD をテスト環境の3つは入れていて、GitOps デプロイだけが入れていませんでした。

初めての有料 GPU セッションを控えた夜でした。その前の2日間でコスト統制と測定の妥当性にかかわる欠陥を30件あまり直し、 1つずつ欠陥を注入して確かめました。Operator のイメージは ECR に上げ、Runbook も書きました。準備は終わったと 思っていました。

その夜、GPU を1枚も点けないまま EKS クラスタを立ててプラットフォームを載せてみました。テストでは常に緑だった Operator が、EKS では起動した途端に落ちました。この記事は、その原因がなぜテストでは一度も現れえなかったのかという 話です。

先に留保をひとつ置きます。この記事が確かめたのは原因であって修正ではありません。足りない CRD を手で入れて Operator が生き返るところまでは見ましたが、同じことを GitOps が自分でこなす経路はその夜一度も動いていません。 残りの留保は「この記事が主張しないこと」にまとめました。

この記事の想定読者

  • Kubernetes Operator を作り、envtest・kind・e2e でテストしている方
  • Argo CD のような GitOps ツールで CRD をデプロイしている方
  • 高くつく実行を前に、何を先に立ててみるべきか決めようとしている方

どんな構成ですか

個人プロジェクトとして作っている GPUaaS プラットフォームのコントロールプレーンです。ユーザーが MLTrainingJob を作ると、Operator がそれを Kueue(Kubernetes で作業を並べ、クォータに合わせて受け入れる スケジューラ)に渡します。スケジューラに仕事を渡すことがこの Operator の本業です。

デプロイは2段に分かれています。Terraform が EKS と周辺のリソースを作り、その上で Argo CD が root Application 1つから残りをすべて載せます(app-of-apps)。

最初は準備が終わったと思っていました

人が見守らないまま有料セッションを回してよいか codex に尋ねました。codex は反対し、根拠は3つでした。

1つ目に、実行は無人のワークフローではありませんでした。セッションスクリプトはエンジンを起動した後に Port Forward を 張って待ちます。測定は別のシェルで人が回す必要があり、終わればセッションも人が終了させる必要がありました。

2つ目に、自動復旧がありませんでした。Spot が中断されたり Port Forward が切れたりすると測定は止まり、再開しません。 その間セッションのシェルは待ち続けるので、何もしないまま TTL まで課金されます。

3つ目に、6.2時間という計画は安全な窓ではありませんでした。372分は想定の処理速度から出た値で、カードが遅いと スクリプトは期限を最大420分まで延ばします。反対側の境界は、クラスタを丸ごと消す夜間の片付けワークフロー destroy.yml です。cron の予定時刻は 03:00 UTC(KST の正午)ですが定時の保証はなく、このリポジトリには実際の 発火が 03:53 から 14:57 UTC までぶれた記録があります。両側とも動くのに、私は片側しか計算していませんでした。

そして最も重い指摘が続きました。最大のリスクはコストではなく、初めて通る区間で起きた運用上の失敗が人なしでは 復旧せず、セッション全体が無効になることだという指摘です。最も安い緩和策は、その夜クラスタと Argo CD までを 立ててみて消すことでした。

ここで「初めて」の範囲をはっきりさせておきます。クラスタそのものは初めてではありませんでした。8月31日に CI で terraform apply を回し、リソース96個を作って消した記録があります。初めてだったのはその上にプラットフォームを 載せること、つまり Argo CD のブートストラップと root Application の適用と Operator の起動でした。その区間は kind でしか 回したことがありませんでした。最初に記録したときは私も「初の実クラスタ」と書いていて、レビューで同じディレクトリの 記録を指摘されて直しました。

結論から申し上げます

クラスタはリソース96個で立ち上がり、root Application を適用すると子の Application ができました。cert-manager は Healthy になりました。ECR の Operator イメージはダイジェスト指定で 34MB を1.7秒で取得し、Webhook の証明書も 発行されました。

そして Operator が6回落ちました。

Failed to create controller {"controller": "mltrainingjob",
  "error": "index workloads by job ref: no matches for kind \"Workload\"
            in version \"kueue.x-k8s.io/v1beta1\""}

Kueue CRD がクラスタにありませんでした。Operator をテストしていた3つの環境はそれぞれこの CRD を入れていて、 GitOps のデプロイ経路だけ誰も入れていませんでした。CRD 4つを手で入れて Pod を消すと、Operator は Available になりました。

3つの環境が CRD を入れていたため、テストではこの失敗が起こりえませんでした

Kueue CRD をどこから得ているかを環境ごとに書くと、こうなります。

環境ごとの Kueue CRD の入手方法。
環境Kueue CRD をどう得るか
test/e2eManager のデプロイ前に installKueueCRDs()
admission テストスイートenvtest の CRDDirectoryPaths で同じファイル
kind の経路手で apply
GitOps / EKS誰もしない

Operator は起動時に kueue.x-k8s.io/v1beta1 の Workload にフィールドインデックスを作ります。CRD がなければ それはハードな失敗です。私はこの動作が正しいと考えています。スケジューラに仕事を渡すことが本業の Operator が スケジューラを黙って飛ばすより、起動を拒むほうがましです。

問題は、そのハードな失敗がテストでは起こりえなかったことです。3つの環境がすべて CRD を入れていたからです。 Operator はテストでは常に緑で、実際のデプロイ経路に初めて出会った瞬間に落ちました。

同じ形が cert-manager にもありました。ハードな依存で、それを必要とするファイルにそう書かれているのに、誰も 入れていませんでした。違いは、cert-manager はコメントを読んで見つけ、Kueue CRD は立ててみて初めて出てきたことです。 3つの環境が CRD を入れるという事実はそれぞれのファイルに書かれていましたが、GitOps だけが入れないという事実は どのファイルにも書かれていませんでした。ないものはファイルを読んでも見えません。

手で入れて復旧し、セッションのゲートがその状態を通しました

稼働中のクラスタに CRD 4つを入れて Pod を消しました。

$ kubectl apply --server-side -f test/crd/kueue
$ kubectl delete pod -l control-plane=controller-manager
→ controller-manager   1/1   AVAILABLE 1

--server-side を使ったのには理由があります。Workload CRD が last-applied-configuration アノテーションの上限(262,144バイト)を超えるからです。クライアント側の適用だと4つのうち3つが入り、1つが拒否されます。 その結果はサイズ制限というより部分的なインストールのように読めます。

続いてセッションスクリプトの Operator ゲートを実際のクラスタに向けて回し、通過するところまで見ました。このゲートは 前日に名前だけを確かめるものから Available Replica を要求するものへ直したものです。その修正がなければ CrashLoopBackOff 状態の Operator を通してカードを点けていたはずです。

テスト Fixture をデプロイの原本にして、元に戻しました

最初は新しい Application が test/crd/kueue を指すようにしました。コピーを作らないための判断でしたが、 レビューで覆りました。コピー同士の Drift を避けた代わりに、テスト Fixture が本番の desired state に なったからです。Fixture を整理することがそのまま本番の変更になる構造です。Drift の種類を変えただけで、なくしては いませんでした。

そこで定義を config/kueue-crds/ に移し、テスト3か所がそちらを読むようにしました。コピーは相変わらず1つだけで、 今はその1つを出荷する側が持っています。

prune が有効だと、CRD ファイルを1つ動かした瞬間にデータも消えます

さらに悪いことがありました。その Application では prune: true と cascade Finalizer が有効でした。

CRD を消すことはスキーマだけを消すことではありません。その CRD に属するインスタンスがすべて削除の対象になります。

プラットフォーム自身の CRD を載せる Application も最初から同じ設定でした。どちらも prune を切りました。 selfHeal は残しました。人が手で消した定義を復元するのは安全な方向で、selfHeal はファイルが移動した からといって定義を消しはしないからです。

原因は確かめ、修正は確かめていません

その夜にしたことを順に並べると、境界が見えます。

しかも Argo CD のすべての Application は targetRevision: main を見ています。修正は dev ブランチにありました。そのまま新しいクラスタを立てると main の config/argocd にはその Application が ないので、同じ CrashLoopBackOff がまた起きます。そのため main への昇格は選択ではなく修正の 一部でした。

仮説を確かめたことと修正を確かめたことは違います。私は前者をして、後者をしたと書くところでした。

昇格は同じ夜に行いました。修正コミット3つを含む dev が PR #63 で9月2日 02:26(KST)に main へ 入りました。main の kueue-crds Application は config/kueue-crds を指し、sync-wave が -2 なので sync-wave 0 の Operator より先に同期されるように書かれています。書かれているというところまでで、 新しいクラスタでその順に動いた姿ではありません。

削除するほうを選びました

GPU Node Group が3つとも0台であることを確かめてクラスタを消しました。リソース96個がすべて削除され、EKS・EC2・NAT・ EIP・EBS・VPC・予約がすべて0になりました。

コストコンソールはその時点で0ドルを示していましたが、それは集計の遅れです。クラスタが立っていた時間は約40分で 1時間あたり0.263ドルなので、およそ0.18ドルで、そこにイメージを取得した NAT のデータ料金が少し 加わります。GPU は一度も点けていないので、そちらは本当に0です。

一晩置いておく選択肢もありました。そうすれば朝に20分を節約できます。しかし1時間あたり0.263ドルがかかり続け、さらに 悪いことに夜間の片付けワークフローと次のセッションが重なります。6.2時間のセッションを予定時刻(03:00 UTC、KST の正午)の 4時間前に始めると、途中でクラスタが丸ごと消えます。セッションスクリプトは予定時刻まで2時間を切っていれば拒否しますが、 4時間なら通します。作り直すには20分と0.09ドルがかかります。

この記事が主張しないこと

  • GitOps で修正が動くことは示していません。CRD を手で入れて生き返らせたところまでしか見ていません。 Application が自分で CRD を載せる経路と、main への昇格後の新しいクラスタは、この記事の根拠の中では一度も 実行されていません。その後 EKS にクラスタを立てた記録はありますが、Kueue CRD がどの経路で入ったかを書いた箇所は ありません。
  • 「6回」を何で数えたかは分かりません。コンテナの再起動回数なのか、日誌に方法が書かれていません。 同じ日の日誌は「6回」とだけ書いており、その夜の kubectl の出力や再起動回数の記録は残っていません。
  • GPU 側の経路については何も分かりません。GPU ノードが実際に立ち上がること、NVIDIA ドライバが付くこと、 Device Plugin が nvidia.com/gpu を広告すること、DCGM が指標を出すこと、16GB のエンジンイメージと重みが NAT を 通って降りてくることは、その夜1つも通っていません。
  • 繰り返しはありません。クラスタの作成、Argo CD のブートストラップ、root の適用はそれぞれ1回ずつ回りました。
  • 正確なコストではありません。0.18ドルは稼働時間と時間単価から計算した値で、NAT のデータ料金は入れていません。 請求書とは突き合わせていません。
  • Finalizer があるときの削除のタイミングは分かりません。prune がインスタンスを消すという方向だけを書き、実際に 消してはいません。
  • ファイルを読んで欠陥を見つける方法が役に立たないとは言えません。前の2日間の30件あまりはすべて読んで見つけ、 実際に有料セッションを台無しにするものでした。今回の欠陥がその方法では出てこなかったというだけです。

おわりに

  • テスト環境が代わりに入れてくれる依存は、テストが確かめません。3つの環境が Kueue CRD を入れている間、 Operator の起動失敗の分岐は一度も実行されませんでした。
  • あるものは読めて、ないものは読めません。3つの環境のインストールコードはファイルにあり、GitOps に インストールがないという事実はどのファイルにもありませんでした。だから立ててみて初めて出てきました。
  • CRD を GitOps で載せるときは、まず prune を見ます。ファイル名が1つ変わるだけで、定義と一緒に インスタンスが削除の対象になります。
  • 原因を確かめたことと修正を確かめたことは違います。手で直したクラスタが生き返ったのは仮説の確認です。 デプロイ経路が同じことをこなすかは、別に回してみる必要があります。

Operator をテストしているなら、テスト環境が代わりに入れてくれるものの一覧と実際のデプロイマニフェストを一度 並べてみることをおすすめします。ないものはファイルを1つ読んでも見えません。
