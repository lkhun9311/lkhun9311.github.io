A Go Benchmark Harness Opened 884 TCP Connections for 884 Rejections
It closed 429 responses without reading their bodies, so no connection was ever reused.

On 15 August 2026 I pushed a branch, the push hook ran codex and Claude reviews, and ten findings came back. Two of them were defects in the measuring instrument itself. This post is about one of those.

The finding was short: the benchmark harness's Send returned without reading the body of a non-200 response. A comment in the same file cited a measurement, 431 → 6, as evidence that the connection pool worked. I opened that evidence, and the trace it had measured contained not a single rejection.

One caveat first. What this post measured is the number of TCP connections the server accepted. How much the new handshakes inflated the latency the harness reports was not measured. The rest of the caveats are gathered under "What this does not claim".

Who this is for

  • Anyone building a load generator or benchmark harness on Go's net/http client
  • Anyone measuring a system that returns many rejections such as 429 (rate limiting, admission control)
  • Anyone who writes measured values into code comments or documents as evidence

The setup

The GPUaaS platform I am building as a personal project has a gateway that takes LLM requests, and inside it an admission guard. The guard reads the request body, picks a backend, and stands in front of the proxy to vLLM. The guard protects capacity by rejecting. A request the guard declines comes back as a 429.

The benchmark harness replays one request trace identically against the guard switched off, a fixed cap that ignores load, and a guard that watches KV cache pressure, and compares the premium requests' TTFT p99.

The connection counts in this post were taken with ConnState on the server the harness connects to, not at the guard.

I thought the connection pool was already verified

The comment in the same file as Send stated the pool's effect as a number: counting accepted connections with ConnState on the server side gave 431 before the pool and 6 after. It was measured on 8 August on kind, with the harness connected directly to a stub server without the gateway, replaying an 884-request trace in legacy and pooled (hack/m5b-gateway-path-evidence.log). The tests were passing too. There was a number, a method and green tests, so I read it as verified.

When I opened the record behind that number, every arm had zero 429s. done == total: every request sent was completed. 431 → 6 was measured on a trace with no rejections at all, and it had never covered the path the review pointed at.

The result, up front

With the same method (counting ConnState on the server side), I measured again on a trace where all 884 requests are rejected, at concurrency 20. The request count matches the 431 → 6 trace, but the commit message records them as different traces.

The pooled mode real runs use was opening one connection per request. With the pool on, it could not be told apart from legacy. It was even higher than the "before" value of 431 on the rejection-free trace. After changing the code to read and drain the body of non-200 responses, it became 22, a fortyfold difference from before the fix.

The measurement conditions go alongside.

That all 884 were rejections comes from the fix commit d450877: its message, and the code comment the same commit added, describe this trace as "an 884-rejection trace".

The mode names predate this fix. The three modes were created on 8 August in commit 651140c, and the log that measured 431 → 6 already ran under those three names. Before the fix, the only place that drained a body was readStream, which reads 200 responses, and non-200 responses were returned undrained. So on a rejection-only trace drain-only had no response to drain either and came out at the same 884 as legacy.

A body closed unread does not return its connection to the pool

If Close() is called before a response body has been read to the end, Go's HTTP transport cannot reuse that connection. The next request then starts again from the TCP handshake.

These are the parts of Send that handle non-200 responses, before and after the fix. Both are the code from that day's commits, with the comments removed from the "after" side. In both, resp.Body.Close() is already deferred earlier in the function.

// before: d450877^
if resp.StatusCode != http.StatusOK {
	kind := "http"
	if resp.StatusCode == http.StatusTooManyRequests {
		kind = "rejected"
	}
	return SendResult{HTTPStatus: resp.StatusCode, ErrorKind: kind}
}

// after: d450877
if resp.StatusCode != http.StatusOK {
	if h.drain {
		drainForReuse(resp.Body)
	}
	kind := "http"
	if resp.StatusCode == http.StatusTooManyRequests {
		kind = "rejected"
	}
	return SendResult{HTTPStatus: resp.StatusCode, ErrorKind: kind}
}

drainForReuse reads and discards up to 8 KB of the body. If it does not reach the end within that, only that one connection gives up on reuse.

The problem is that this handshake cost arises on the instrument's side, not the side being measured, and it lands inside the latency the harness reports. Even the latency of a request the guard rejected carries the time the instrument spent opening a new connection.

Rejection is not the exception but this harness's busiest path

In this harness a 429 is not an exceptional case. The admission guard protects capacity by rejecting, and a run that actually exercises the guard sends most of its requests down this path.

So the more a run's guard rejects, the more requests this defect touches. Conversely, the evidence that showed the pool working came from a trace in which the guard never rejected anything.

Why drain-only exists

In the table drain-only is 357. This mode exists to separate the body-draining fix from the pool settings, so each one's effect on the connection count can be seen. Writing only "884 → 22" as one lump leaves no record of which side removed how much.

The three modes are defined in SenderConnForMode in internal/bench/httpsender.go. legacy sets no transport of its own, so it uses Go's defaults (two idle connections per host), and does not drain bodies. drain-only turns on body draining on the same default transport. pooled derives the per-host idle connection cap from the trace (arrival rate × request timeout, no more than the trace length and no less than 2), removes the overall idle cap, and turns on body draining.

So drain-only and pooled drain bodies the same way and differ only in the idle connection cap. The record does not say what pooled's cap was on this trace or how many times it was measured, so I do not attribute the gap between 357 and 22 to the cap item by item.

I wrote the evidence's scope into the comment

Correcting the number alone lets the same thing happen again, because someone may quote 431 → 6 next time. So I put this sentence into the comment on drainForReuse (commit d450877).

Read that trace's scope before quoting those numbers: every arm in it recorded ZERO rejections, so they describe the all-200 path only.

431 → 6 was evidence I had written. I did not re-measure that number itself this time. The problem was reading it as evidence for a different path.

431 → 6 also appears outside the code comment. The evidence document hack/m5b-gateway-path.md, committed on 8 August, says "431 connections down to 6, a factor of 72". The 15 August fix did not touch that document and it has not changed since, so the only places that state the scope are the code comment and the commit message. The published site (lkhun9311.github.io) does not carry this number.

Four defects found that day had the same shape

Lay the four defects found that day side by side and they reduce to one sentence: the evidence did not cover the path it was meant to measure.

All four defects had tests, and the tests were passing. What was missing was not a test but the habit of checking that the scope a test covers matches the scope it claims.

A short note on the third row. Even when the read-back rejected the record, reportRun printed the whole result and ledger to stdout and then wrote "do not quote the above" to stderr. It was asking the reader to unsee what a shell redirect had already captured. I changed it so that, instead of printing and then disowning, a failed validation sends everything to stderr. On a run that failed validation, stdout became 929 bytes with 0 event lines and stderr 2,696 bytes with 13 event lines.

The first row came from earlier work the same day. watchstream.go had code and tests that take a baseline List and continue a watch from its resourceVersion, but nothing in production code called that function (startWatchStream). What actually ran was collector.watch, which starts a watch from "now" with no baseline List.

What this does not claim

  • How much latency was inflated. That the handshake lands inside the reported latency is a prediction from how the mechanism works, and latency before and after the fix was not measured side by side.
  • A repetition count. The message of commit d450877 holds a single set of before and after values per mode, and neither the code comment from the same commit nor the two journals give a repetition count. The raw log of that run is not in the repository and no session record survives.
  • That latency numbers already reported are wrong. This post's evidence does not say which of the numbers produced while this defect existed came from rejection-heavy runs.
  • That 22 is the right value. It is a count under one condition, concurrency 20. Other concurrency levels and other rejection ratios were not measured.
  • Raw data from the rejection-trace run. That all 884 were rejections, and the six values in the table, come from the commit message and the code comment. The raw log of that run, the trace file and the configuration of the server that returned the rejections are not in the repository.
  • That this is independent of the Go version. The transport's reuse conditions were not checked per Go version.

Closing

  • A trace with only 200 responses cannot measure connection reuse on the rejection path. 431 → 6 was measured on a trace with zero rejections.
  • A Go client reuses a connection only if it reads a non-200 response body to the end before closing. Unread, the pooled mode opened 884 connections for 884 requests. After the fix to read them, it opened 22.
  • For an instrument that measures an admission guard, rejection is the main path. The more a run's guard rejects, the more requests the instrument's defect touches.
  • When you write a number down as evidence, write the scope of the trace that measured it next to it.

If you have written evidence numbers into a measurement tool, open them once and check whether the input that produced them contained the path you are measuring now. Passing tests and a correct number can still never have looked at the same path.
