429 응답의 Body를 읽지 않고 닫아서 Connection을 한 번도 다시 쓰지 못했습니다.

2026년 8월 15일에 브랜치를 올리자 푸시 훅이 codex와 Claude 리뷰를 돌렸고 지적 10건이 나왔습니다. 그중 두 건이 측정 도구 자체의 결함이었습니다. 이 글은 그 가운데 하나를 다룹니다.

지적은 짧았습니다. 벤치 Harness의 Send가 200이 아닌 응답의 Body를 읽지 않고 반환한다는 것이었습니다. 같은 파일의 주석에는 Connection Pool이 효과가 있다는 근거로 431 → 6이라는 측정값이 적혀 있었습니다. 저는 그 근거를 열어 봤고 근거가 잰 트레이스에는 거부 응답이 한 건도 없었습니다.

먼저 유보 하나. 이 글이 잰 것은 서버가 받아들인 TCP Connection의 개수입니다. 새로 생긴 Handshake가 Harness가 보고하는 지연을 얼마나 부풀렸는지는 재지 않았습니다. 나머지 유보는 「이 글이 주장하지 않는 것」에 모아 두었습니다.

이 글의 예상 독자

  • Go net/http 클라이언트로 부하 생성기나 벤치 Harness를 만드시는 분
  • 429 같은 거부 응답이 많이 나오는 시스템(Rate Limit, 입장 제어)을 재시는 분
  • 코드 주석이나 문서에 측정값을 근거로 적어 두시는 분

어떤 서비스인가요?

개인 프로젝트로 만들고 있는 GPUaaS 플랫폼에는 LLM 요청을 받는 Gateway가 있고 그 안에 입장 가드가 있습니다. 가드는 요청 Body를 읽고 보낼 Backend를 정한 뒤 vLLM으로 프록시하기 전에 섭니다. 가드는 거부해서 용량을 지킵니다. 가드가 받지 않기로 한 요청은 429로 돌아옵니다.

벤치 Harness는 요청 트레이스 하나를 가드를 끈 설정, 부하를 보지 않는 고정 상한, KV Cache 압력을 보는 가드에 똑같이 재생하고 Premium 요청의 TTFT p99를 비교합니다.

이 글의 Connection 수는 가드가 아니라 Harness가 붙은 서버 쪽에서 ConnState로 셌습니다.

처음엔 Connection Pool이 이미 검증된 줄 알았습니다

Send와 같은 파일의 주석은 Pool의 효과를 숫자로 말하고 있었습니다. 서버 쪽에서 ConnState로 받아들인 Connection을 세어 보니 Pool을 넣기 전 431개, 넣은 뒤 6개였다는 기록입니다. 8월 8일 kind에서 Harness를 Gateway 없이 Stub 서버에 바로 붙이고 요청 884건짜리 트레이스를 legacy와 pooled로 재생해 잰 값입니다 (hack/m5b-gateway-path-evidence.log). 테스트도 통과하고 있었습니다. 숫자가 있고 방법이 있고 테스트가 초록이니 검증된 것으로 읽었습니다.

그 숫자를 만든 기록을 열어 보니 모든 Arm에서 429가 0건이었습니다. done == total, 즉 보낸 요청이 전부 완료됐습니다. 431 → 6은 거부가 한 번도 없는 트레이스에서 잰 값이었고 리뷰가 지적한 경로를 덮은 적이 없었습니다.

결론부터 말씀드리자면

같은 방법(서버 쪽 ConnState 계수)으로 요청 884건이 전부 거부되는 트레이스를 동시 20으로 다시 쟀습니다. 요청 수는 431 → 6의 트레이스와 같지만 커밋 메시지는 둘을 다른 트레이스로 적었습니다.

요청 884건이 전부 거부되는 트레이스에서 모드별로 서버가 받아들인 Connection 수, 수정 전과 후.
모드수정 전수정 후
legacy884884
drain-only884357
pooled (실제 런이 쓰는 모드)88422

실제 런이 쓰는 pooled 모드가 요청 하나에 Connection 하나를 열고 있었습니다. Pool을 켰는데도 legacy와 구별되지 않았습니다. 거부가 없는 트레이스의 ‘고치기 전’ 값 431보다도 많았습니다. 200이 아닌 응답의 Body를 읽어 비우도록 고치자 22개가 됐습니다. 고치기 전과 40배 차이입니다.

884건이 전부 거부 응답이었다는 것은 수정 커밋 d450877의 메시지와 같은 커밋이 넣은 코드 주석이 이 트레이스를 ‘an 884-rejection trace’라고 적은 데서 가져왔습니다.

모드 이름은 이 수정보다 먼저 있었습니다. 세 모드는 8월 8일 커밋 651140c에서 생겼고 431 → 6을 잰 로그도 이미 세 이름으로 돌았습니다. 수정 전 코드에서 Body를 비우는 곳은 200 응답을 읽는 readStream뿐이었고 200이 아닌 응답은 비우지 않고 반환했습니다. 그래서 거부만 나오는 트레이스에서는 drain-only도 비울 응답이 없어 legacy와 같은 884가 됐습니다.

Body를 읽지 않고 닫으면 Connection이 Pool에 돌아가지 않습니다

Go의 HTTP Transport는 응답 Body를 끝까지 읽지 않은 채 Close()가 불리면 그 Connection을 다시 쓰지 못합니다. 그러면 다음 요청은 TCP Handshake부터 새로 합니다.

수정 전후의 Send에서 200이 아닌 응답을 다루는 부분입니다. 둘 다 그날 커밋의 코드이고 수정 후 쪽의 주석은 뺐습니다. resp.Body.Close()는 두 코드 모두 이 앞에서 defer로 걸려 있습니다.

// before: d450877^
if resp.StatusCode != http.StatusOK {
	kind := "http"
	if resp.StatusCode == http.StatusTooManyRequests {
		kind = "rejected"
	}
	return SendResult{HTTPStatus: resp.StatusCode, ErrorKind: kind}
}

// after: d450877
if resp.StatusCode != http.StatusOK {
	if h.drain {
		drainForReuse(resp.Body)
	}
	kind := "http"
	if resp.StatusCode == http.StatusTooManyRequests {
		kind = "rejected"
	}
	return SendResult{HTTPStatus: resp.StatusCode, ErrorKind: kind}
}

drainForReuse는 Body를 최대 8KB까지 읽어 버립니다. 그 안에 끝에 닿지 못하면 그 Connection 하나만 재사용을 포기합니다.

문제는 이 Handshake 비용이 측정 대상이 아니라 측정 도구 쪽에서 생긴다는 점입니다. 그리고 그 비용은 Harness가 보고하는 지연 안에 들어갑니다. 가드가 거부한 요청의 지연에도 도구가 Connection을 새로 여는 시간이 섞입니다.

거부는 예외가 아니라 이 Harness가 가장 많이 지나는 경로입니다

이 Harness에서 429는 예외 상황이 아닙니다. 입장 가드는 거부함으로써 용량을 지키고 가드를 실제로 행사하는 런은 대부분 이 경로를 지납니다.

그래서 이 결함은 가드가 거부를 많이 하는 런일수록 더 많은 요청에 걸립니다. 반대로 Pool의 효과를 보여 준 근거는 가드가 한 번도 거부하지 않은 트레이스에서 나왔습니다.

drain-only가 따로 있는 이유

표에서 drain-only는 357개입니다. 이 모드는 Body를 읽어 비우는 수정과 Pool 설정을 따로 떼어서 각각이 Connection 수를 얼마나 줄이는지 보려고 둔 것입니다. 한 덩어리로 ‘884 → 22’만 적으면 어느 쪽이 얼마를 줄였는지가 남지 않습니다.

세 모드의 정의는 internal/bench/httpsender.go의 SenderConnForMode에 있습니다. legacy는 Transport를 따로 두지 않아 Go 기본값(Host당 유휴 Connection 2개)을 쓰고 Body를 비우지 않습니다. drain-only는 같은 기본 Transport에 Body 비우기만 켭니다. pooled는 Host당 유휴 Connection 상한을 트레이스에서 도출하고(도착률 × 요청 Timeout, 트레이스 길이를 넘지 않고 2 아래로 내려가지 않음) 전체 유휴 상한을 없앤 뒤 Body 비우기를 켭니다.

그래서 drain-only와 pooled는 Body 비우기가 같고 유휴 Connection 상한만 다릅니다. 이 트레이스에서 pooled의 상한이 몇이었는지와 몇 번 쟀는지는 기록에 없으므로 357과 22의 차이를 상한 하나하나에 나누어 붙이지는 않습니다.

주석에 증거의 범위를 적었습니다

숫자를 고치는 것만으로는 같은 일이 되풀이됩니다. 다음에 누군가 431 → 6을 다시 인용할 수 있기 때문입니다. 그래서 drainForReuse의 주석에 이 문장을 넣었습니다(커밋 d450877).

Read that trace's scope before quoting those numbers: every arm in it recorded ZERO rejections, so they describe the all-200 path only.

(‘이 숫자를 인용하기 전에 그 트레이스의 범위를 읽어라. 그 안의 모든 Arm이 거부 0건이었으므로 이 숫자는 전부 200인 경로만 말한다.’)

431 → 6은 제가 적은 증거였습니다. 이번에 그 숫자 자체를 다시 재지는 않았습니다. 문제는 그 숫자를 다른 경로의 근거로 읽은 데 있었습니다.

431 → 6은 코드 주석 밖에도 실려 있습니다. 8월 8일에 커밋한 증거 문서 hack/m5b-gateway-path.md가 ‘431 connections down to 6, a factor of 72’라고 적었습니다. 8월 15일 수정은 이 문서를 건드리지 않았고 그 뒤로도 바뀌지 않아서 범위를 적은 곳은 코드 주석과 커밋 메시지뿐입니다. 발행한 글(lkhun9311.github.io)에는 이 숫자가 없습니다.

같은 날 나온 결함 넷이 같은 모양이었습니다

그날 찾은 결함 넷을 나란히 놓으면 한 문장으로 줄어듭니다. 증거가 측정하려는 경로를 덮지 않았습니다.

같은 날 찾은 결함 넷과 각 증거가 덮은 범위와 덮지 않은 범위.
결함증거가 덮은 것덮지 않은 것
watchstream 호출자 없음컴포넌트 단위 테스트프로덕션 배선
decodeRunRecord가 뒤에 붙은 데이터를 무시알 수 없는 필드와 스키마문서 뒤의 바이트
reportRun이 거부한 결과를 stdout에 출력종료 코드이미 캡처된 stdout
HTTP 송신이 200이 아닌 응답을 안 읽음200 트레이스 431 → 6429 경로(884 → 884)

네 결함 모두 테스트가 있었고 통과하고 있었습니다. 없던 것은 테스트가 아니라 테스트가 덮는 범위와 주장하는 범위가 같은지 확인하는 습관이었습니다.

셋째 줄도 짧게 적어 둡니다. reportRun은 되읽기가 레코드를 거부해도 결과와 원장을 전부 stdout에 출력한 뒤 stderr에 ‘위의 것은 인용하지 말라’고 적고 있었습니다. 셸 리다이렉트가 이미 가져간 것을 독자에게 못 본 척하라고 요구한 셈입니다. 출력을 막지 않고 검증에 실패하면 전부 stderr로 보내게 바꿨습니다. 검증에 실패한 실행에서 stdout은 929바이트에 이벤트 0줄, stderr는 2,696바이트에 이벤트 13줄이 됐습니다.

첫째 줄은 같은 날 앞선 작업에서 나온 결함입니다. watchstream.go에는 기준 List를 받고 그 resourceVersion에서 watch를 이어 가는 코드와 테스트가 있었지만 프로덕션 코드에 그 함수(startWatchStream)를 부르는 곳이 없었습니다. 실제로 돈 것은 기준 List 없이 ‘지금’부터 watch를 거는 collector.watch였습니다.

이 글이 주장하지 않는 것

  • 지연이 얼마나 부풀었는지. Handshake가 보고된 지연 안에 들어간다는 것은 동작 원리에서 나온 예측이고 수정 전후의 지연을 나란히 재지 않았습니다.
  • 반복 횟수. 커밋 d450877의 메시지에는 모드별 수정 전·후 값이 한 벌만 있고 같은 커밋의 코드 주석과 일지 둘에도 반복 횟수가 없습니다. 그 런의 원시 로그는 저장소에 없고 세션 기록도 남아 있지 않습니다.
  • 이미 보고한 지연 숫자가 틀렸다는 것. 이 결함이 있던 동안 낸 숫자 가운데 어느 것이 거부가 많은 런이었는지는 이 글의 근거가 말하지 않습니다.
  • 22개가 알맞은 값이라는 것. 동시 20 한 조건에서 센 개수입니다. 다른 동시성이나 다른 거부 비율에서는 재지 않았습니다.
  • 거부 트레이스 런의 원자료. 884건이 전부 거부였다는 것과 표의 여섯 값은 커밋 메시지와 코드 주석에서 가져왔습니다. 그 런의 원시 로그, 트레이스 파일, 거부를 돌려준 서버의 설정은 저장소에 없습니다.
  • Go 버전과 무관하다는 것. Transport의 재사용 조건을 Go 버전별로 확인하지 않았습니다.

마치며

  • 200 응답만 있는 트레이스로는 거부 경로의 Connection 재사용을 잴 수 없습니다. 431 → 6은 거부가 0건인 트레이스에서 잰 숫자였습니다.
  • Go 클라이언트는 200이 아닌 응답의 Body도 끝까지 읽고 닫아야 Connection을 다시 씁니다. 읽지 않았을 때 pooled 모드는 요청 884건에 Connection 884개를 열었습니다. 읽게 고친 뒤 22개가 됐습니다.
  • 입장 가드를 재는 도구에서 거부는 본 경로입니다. 가드가 거부를 많이 하는 런일수록 도구의 결함이 더 많은 요청에 걸립니다.
  • 숫자를 근거로 적을 때는 그 숫자를 잰 트레이스의 범위를 옆에 같이 적습니다.

측정 도구에 근거 숫자를 적어 두셨다면 그 숫자를 잰 입력에 지금 재려는 경로가 들어 있었는지 한 번 열어 보시길 권합니다. 통과하는 테스트와 맞는 숫자가 있어도 둘이 같은 경로를 본 적이 없을 수 있습니다.

읽어 주셔서 감사합니다.
