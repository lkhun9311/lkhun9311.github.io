社内クラウド管理コンソールの Backend を作っています。前回の⑦編でモニタリング画面 3 つを レビューし、「直すべきだと言える根拠が見つからなかった」と書きました。その記事にはこんな文も あります。「Cache をこれ以上足さないことにしました。足そうとしていた場所はすでに安い経路で、 そこに Cache を入れると古さと複雑さだけが増えます。」

その画面の最初のデータは 6.8 秒でした。そして直した方法は、まさにその場所に Cache を 入れることでした。23ms になりました。

間違っていたのは計算ではなく、測った場所でした。私は REST の応答時間を 測り、ユーザーは SSE の最初の data を待っていました。「InfluxDB は 15 秒に一度だからすでに 安い」という根拠も、周期更新についてだけ正しかったのです。接続が新しく開くたびに、同じ計算が 同期でもう一度回っていました。続く 4 編で画面ごとに詳しく扱います。

この記事の想定読者#

  • 負荷試験の結果は良いのに、利用者はずっと遅いと言う画面をお持ちの方
  • SSE や WebSocket で最初のデータを押し出す画面を作っている方
  • 「ここはすでに安い」と判断して通り過ぎた経路がある方

どの画面ですか?#

統合モニタリングには画面が 3 つあります。ダッシュボード · 物理ノード · 仮想リソース。 三つとも構造情報は REST で受け取り、リアルタイムの値は SSE で受け取ります。

公開した記事が間違っていました#

まず何を書いたのかをそのまま並べます。

横にスクロールすると残りが見えます

⑦編の判断と今回の測定の対照。
⑦編に書いたこと今回測ったこと
結論直すべきだと言える根拠が見つからなかった最初のデータの中央値 6,776ms
Cacheこれ以上足さない。すでに安い経路だその場所に入れて 23ms
根拠15 秒に 1 回計算して全員に配る定期更新は正しい。接続ごとにもう一度回る
測定負荷試験を走らせていないSSE の最初の data までを直接測った

⑦編の最後の行は「負荷試験を走らせていません。コードを見て判断し、 実際に走らせて確かめてはいません。」でした。自分で書いておいた限界がそのまま実現しました。

一つだけ切り分けておきます。「15 秒に 1 回だから安い」はそれ自体が誤りではありません。 定期更新は実際に利用者数と無関係で、Tick ごとに 1 回です。間違っていたのは その一文で画面全体を説明できると見たことです。

測った場所と待っていた場所が違いました#

画面がローディングを終える条件はこうでした。

1. REST で構造情報を受け取る                約 20ms
2. EventSource が接続する
3. connection イベントを受け取る
4. 最初の data イベントを受け取る           ← ここまで 6.8 秒
5. フロントエンドがローディング層を外す

一般的な HTTP サンプラーは1〜3 までを見て成功として終わります。 利用者が待っていたのは 4 でした。

そこで SSE につないで最初の data フレームで接続を閉じ、経過時間を残す 小さな計測器を作りました。その値からパーセンタイルと Apdex を出し直しました。

仮想リソースは SSE 側の値です。この画面は REST も約 2,627ms あり、 両方を直してはじめて速くなりました。④編の主題です。

直した方法は一行です#

リクエスト経路から計算を外しました。後ろで回る Worker が 15 秒ごとに完成したスナップショットを作り、 新しい接続には最後に完成した値をすぐに送ります。更新が失敗したら 前の値をそのまま残します。

名前は serve-stale です。古い値でもすぐに渡すという意味で、 古さを受け入れる代わりに遅延をなくす取引です。 その取引が画面ごとにどこまで許されるのかが、続く 4 編の内容です。

続く四編#

  • ②編 ダッシュボード。利用者が待つ境界をどう見つけ、 計測器をどう作ったか。6,776ms から 10ms まで。
  • ③編 物理ノード。同じパターンを移そうとして出会った問いが一つ。 メトリックが空のリストで返ったとき、それを正常な 0 台として発行してよいのか。
  • ④編 仮想リソース。ボトルネックが REST と SSE の二つあり、 片方だけ直しても画面はそのままでした。
  • ⑤編 共有 Cache。三画面の Cache を一つにまとめると、 別々だったから偶然守られていたことが契約として表に出ました。

この記事が主張しないこと#

  • 運用統計ではありません。単一利用者 30 回の測定で、 同時利用者や長期の分布は見ていません。
  • 改善の寄与を切り分けられていません。⑦編のレビュー（8 月）と今回の測定（9 月）の あいだに、別の人の改善がもう一つ入っています。before の値にその寄与がどれだけ含まれるかを 分けて測っていません。
  • ⑦編が丸ごと間違いだという話ではありません。あの記事が「直さない」と決めたうちの 一つ、広すぎるように見える照会窓は今もそのままでよいと考えています。間違っていたのは Cache についての判断と、その根拠です。
  • serve-stale がいつでも答えだという話でもありません。古い値を見せてよい画面でだけ 成り立ちます。その境界を画面ごとに引くのが③編と⑤編の主題です。
  • 23ms は定数ではありません。メモリからスナップショットを読んで直列化する費用で、 データ規模が変わればこの値も変わります。

おわりに#

  • 「すでに安い」という判断には、どの経路について安いのかが付いていなければなりません。 定期更新は安く、接続経路はそうではありませんでした。一文で両方を説明できると見たのが誤りでした。
  • ツールが成功と書く地点が、利用者が待ち終えた地点と同じかを確かめる必要があります。 違えば、そのあいだは誰にも見えません。
  • やらないと決めたことは、直したことより検算が難しいです。 ⑦編にそう書いておきながら、検算する道具を作りませんでした。

「直す根拠がない」は「測っていない」と区別して書かなければなりません。 ⑦編はその二つを分けようと努めた記事なのに、いちばん分けるべき場所で分けられませんでした。
