풀러는 두 고갈 중 하나만 고친다

Writing · 2026년 9월 · 7분

다른 언어 English · 日本語

범위. 개인 프로젝트(Kotlin · Spring Boot · 관리형 Postgres, 모놀리스)의 출시 전 구조 점검 기록이다. 장애가 난 적은 없고, 부하 시험으로 잰 수치도 없다. 아래에 나오는 "최대 10초"는 외부 호출에 설정한 read timeout이지 요청마다 실제로 그만큼 쥐고 있었다고 측정한 값이 아니다. 개선은 코드 성질의 변화로 설명되는 것이고, 이 글은 실측치를 주장하지 않는다.

점검의 출발 가설은 흔한 것이었다 — 커넥션이 마를 위험이 있으니 풀러(RDS Proxy·PgBouncer 류)를 넣으면 되지 않나.

답은 이 코드베이스에서는 아니오였고, 그 이유는 제품 문서가 아니라 트랜잭션 풀링의 정의에서 나왔다.

목차

  • 증상은 하나, 원인은 둘
  • 왜 풀러가 B 를 못 고치나
  • 그래서 순서가 있다
  • 아무도 고르지 않은 두 숫자
  • 풀러를 쓸 수 있는 코드인지 먼저 확인했다
  • 스레드와 커넥션은 다른 자원이다
  • 가드를 결과가 아니라 원인에 걸었다
  • 이 글이 주장하지 않는 것

증상은 하나, 원인은 둘#

커넥션이 마르면 보이는 것은 대체로 하나다. 풀 대기 타임아웃, 서로 무관한 API 들이 동시에 느려짐, 그리고 로그의 Connection is not available, request timed out.

그런데 그 뒤의 원인은 두 종류다.

A — 커넥션이 많아서. 앱 인스턴스가 늘어나면 인스턴스 수 × 풀 크기만큼 커넥션이 열린다. Postgres 는 커넥션마다 백엔드 프로세스를 만들고, 유휴여도 메모리를 쓴다. 실제로 쿼리를 돌리는 것은 그중 일부인데 나머지는 열려만 있다.

이게 풀러가 존재하는 이유다. 앱 커넥션 수천 개를 백엔드 커넥션 수십 개로 접어 준다.

B — 트랜잭션이 오래 열려 있어서.

BEGIN → SELECT → [ 외부 HTTP 호출 ] → INSERT → COMMIT
                  ↑ 커넥션을 쥔 채로 쿼리를 하나도 안 한다

동시 요청이 풀 크기를 넘으면 마른다. 여기서 커넥션 개수는 문제가 아니다 — 점유 시간이 문제다.

그리고 마르는 것은 그 경로만이 아니다. 투표도 피드도 차트 조회도 같은 풀에서 커넥션을 받으므로 함께 멈춘다. 이 앱에서 특히 아픈 것은 타이밍이었다 — 성장 엔진이 "결과 차트를 공유하는 것"이라, 공유가 터지는 날이 곧 마르는 날이다.

왜 풀러가 B 를 못 고치나#

"앱 커넥션 수천 개를 DB 커넥션 수십 개로 접는다"는 그림은 맞다. 문제는 언제 접히는가이고, 그건 트랜잭션 풀링의 정의에 이미 들어 있다.

멀티플렉싱은 트랜잭션 사이에서 일어난다. 트랜잭션이 열려 있는 동안에는 그 백엔드 커넥션이 그 클라이언트에 고정(pin)된다. 당연하다 — 트랜잭션은 상태이고, 중간에 다른 세션에 빌려주면 격리가 깨진다.

그래서 이렇게 된다 — 트랜잭션이 10초 열려 있으면 백엔드 커넥션도 10초 고정되고, 접힘 비율은 1:1 이 되며, 프록시의 이득은 0 에 가까워진다.

풀러는 짧은 트랜잭션이 많을 때 값을 하는 도구다. B 를 앓는 상태에서 사면 돈을 쓰고도 아무것도 나아지지 않는데, 더 나쁜 것은 그다음이다 — "이제 대비했다"고 믿게 된다. 그 믿음이 다음 점검을 막는다.

그래서 순서가 있다#

해법은 하나가 아니라 층이고, 층에는 순서가 있다.

가로로 스크롤하면 나머지가 보입니다

커넥션 고갈에 대한 다섯 층의 해법과 각각의 성격.
층무엇성격
①트랜잭션을 짧게 — 외부 호출을 밖으로유일하게 근본적. 나머지 전부의 전제
②유입 제어 — 스레드·풀 상한을 의도적으로실패를 빠르고 예측 가능하게
③풀러①이 끝나야 효과가 있다
④읽기 분리·캐시커넥션을 덜 쓰게 만드는 유일한 층
⑤비동기 오프로드(outbox)요청당 DB 작업 자체를 줄임

그래서 코드부터 고쳤다. 외부 모더레이션 호출을 트랜잭션 밖으로 빼는 작업을 쓰기 경로 세 곳에 했다. 그중 하나는 더 나빴다 — 폴 부착 경로는 for update 로 행까지 잠근 채 외부 호출을 하고 있었다. 커넥션과 행 락, 두 자원을 동시에 쥔 것이다.

결론을 한 줄로 적으면 이렇다. 코드 수정은 풀러의 대안이 아니라 전제조건이었다. 고치고 나니 이제 풀러가 값을 할 수 있는 상태가 됐다.

아무도 고르지 않은 두 숫자#

②에 함정이 하나 있다. 블로킹 JDBC 에서는 커넥션 풀이 사실상 동시성 상한이다. 스레드가 아무리 많아도 커넥션을 못 받으면 일을 못 한다.

이 서비스는 톰캣 스레드가 기본값 200, 커넥션 풀이 그보다 열 배 작았다. 그러면 나머지 요청들은 커넥션을 기다리다 타임아웃 뒤에 실패한다. 방향은 맞다 — 빨리 실패해야 나머지가 산다. 문제는 다른 데 있었다.

두 값 다 아무도 고른 것이 아니었다. 하나는 프레임워크 기본값이고 하나는 그냥 그렇게 돼 있었다. 유입 제어라는 것은 상한을 두는 것이 아니라 그 상한을 의도적으로 정하는 것이고, 기본값 두 개가 만들어 낸 동시성 정책은 정책이 아니다.

풀러를 쓸 수 있는 코드인지 먼저 확인했다#

③으로 넘어가기 전에 확인할 것이 하나 더 있다. 트랜잭션 풀링에는 핀(pin)을 유발하는 패턴이 있고, 그게 있으면 풀러가 무력해진다.

  • 세션 스코프 advisory lock (pg_advisory_lock)
  • 임시 테이블
  • SET · set search_path
  • 서버 프리페어드 스테이트먼트(풀러와 버전에 따라)

네 가지 다 없었다. advisory lock 은 세 군데에서 쓰는데 전부 xact 스코프였다 — 트랜잭션 종료 시 자동으로 풀리므로 트랜잭션 풀링에 그대로 얹힌다.

이건 운이었다. 그리고 운이라는 것을 적어 두는 편이 낫다 — 세션 스코프 락을 한 군데만 썼어도 그 경로가 풀러를 무력화했을 것이고, 그 사실은 풀러를 도입한 뒤에야 알게 됐을 것이다. 도구를 사기 전에 그 도구가 이 코드에서 작동하는지를 먼저 보는 절차가 이 점검에서 얻은 것 중 제일 재사용 가능한 부분이다.

스레드와 커넥션은 다른 자원이다#

여기서 자주 나오는 처방이 하나 더 있다 — 비동기로 바꾸면 되지 않나.

WebFlux 나 코루틴으로 바꾸면 스레드는 아낀다. 그런데 커넥션은 그대로 잡는다. JDBC 는 블로킹이고, 트랜잭션이 열려 있는 한 커넥션은 반납되지 않는다.

문제의 축이 커넥션인데 스레드를 아끼는 처방을 가져오면 축이 어긋난다. R2DBC 라면 이야기가 다르지만, 그건 데이터 접근 계층을 전면 재작성하는 일이다.

풀을 키우는 처방도 같은 종류다. 완화는 되지만 수리는 아니고, 풀 크기 × 인스턴스 수 ≤ DB 커넥션 상한에 먼저 걸린다. 그리고 근본 원인 — 느린 외부 호출이 커넥션을 쥔다 — 은 그대로 남는다.

가드를 결과가 아니라 원인에 걸었다#

이 수정에는 특유의 취약함이 있다. @Transactional 한 줄이면 되돌아간다. 그리고 되돌려도 기능은 멀쩡하다 — 테스트도 통과하고 화면도 정상이다. 증상은 부하가 걸리는 날에만 나온다.

그래서 회귀 방어를 결과가 아니라 원인에 걸었다. 외부 클라이언트 자리에 spy 를 앉혀, 호출이 일어나는 그 시점에 트랜잭션이 활성인지를 단언한다.

// 외부 호출 자리의 spy 가 호출 시점의 상태를 본다
whenever(moderationClient.screen(any())).thenAnswer {
    assertThat(TransactionSynchronizationManager.isActualTransactionActive())
        .isFalse()   // ← 이 호출은 트랜잭션 밖이어야 한다
    ...
}

이 가드는 "응답이 빠른가"를 묻지 않는다. "외부 호출이 트랜잭션 안에 있는가"를 묻는다. 그게 실제 원인이고, 되돌리기가 일어나는 자리다.

그리고 가드가 정말 겨누고 있는지는 뮤테이션으로 확인했다 — 경로마다 각각 red 를 봤다. 가드 하나가 세 경로를 다 지킨다고 믿는 것과, 세 경로에서 각각 빨강을 본 것은 다른 일이다.

이 글이 주장하지 않는 것#

  • 성능 수치가 없다. 부하 시험을 하지 않았고, "몇 배 빨라졌다"고 말할 근거가 없다. 바뀐 것은 코드의 성질 — 트랜잭션이 외부 호출을 기다리지 않게 된 것 — 이고, 그것이 지연이나 처리량으로 얼마가 되는지는 재지 않았다.
  • "최대 10초"는 설정값이다. 외부 호출에 건 read timeout 이고, 요청마다 실제로 그만큼 점유했다고 측정한 값이 아니다.
  • 장애가 난 적은 없다. 출시 전 구조 점검에서 나온 것이고, 이 경로가 실제로 마르는 것을 관측한 기록은 없다.
  • 풀러가 쓸모없다는 주장이 아니다. A 형 고갈에는 정확히 맞는 도구다. 이 글이 말하는 것은 B 를 앓는 상태에서는 접힘 비율이 1:1 이라 값을 못 한다는 것뿐이다.
  • 벤더별 커넥션 상한 수치는 쓰지 않았다. 확인하지 않은 값이다.
  • 핀 유발 패턴 목록이 완전하지 않을 수 있다. 풀러와 버전에 따라 다르고, 여기서는 이 코드에 그 넷이 없다는 것만 확인했다.

남는 한 줄은 이것이다. 증상이 같다고 원인이 같지 않고, 도구는 원인 하나에만 맞는다. 그리고 잘못 고른 도구의 진짜 비용은 돈이 아니라, 대비했다는 믿음이다.
