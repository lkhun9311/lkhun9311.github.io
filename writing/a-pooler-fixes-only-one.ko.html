RDS Proxy로는 못 고치는 커넥션 고갈
트랜잭션 안에서 외부 API를 호출하고 있었습니다. 출시 전 소셜 투표 플랫폼 점검

안녕하세요. 소셜 투표 플랫폼을 만들고 있습니다. 출시 전에 아키텍처를 점검하다가 “트래픽이 늘면 DB 커넥션이 부족해질 텐데 connection pooler를 하나 붙이면 되지 않을까”라는 아주 흔한 가설에서 출발했는데 결론은 “이 코드베이스에서는 아니오”였습니다.

왜 아니오였는지 그리고 그 판단을 무엇을 근거로 내렸는지 공유하려고 합니다.

이 글의 예상 독자#

  • Spring Boot로 서비스를 만들고 있는데 connection pool 설정을 아직 직접 건드려 본 적이 없는 분
  • “커넥션이 부족하면 RDS Proxy 같은 걸 붙이면 되지 않나?”라고 생각해 보신 분
  • 트랜잭션 안에서 외부 API를 호출하는 코드를 보신 적이 있거나, 지금 그렇게 쓰고 계신 분

무슨 내용인가요?#

  • 커넥션 고갈에는 원인이 두 가지 있고 connection pooler는 그중 하나만 고칩니다.
  • 왜 못 고치는지는 제품 문서가 아니라 transaction pooling이라는 방식의 정의에서 나옵니다.
  • 그래서 도구를 도입하기 전에 이 코드에서 그 도구가 동작하는지부터 확인했습니다.
  • 수정이 @Transactional 한 줄로 되돌아갈 수 있는 종류라 회귀 방어를 결과가 아니라 원인에 걸었습니다.

코드는 비공개 저장소에 있습니다. 아직 출시 전이라 저장소를 열어 두지 않았습니다. 그래서 절마다 GitHub 링크 대신 파일 경로와 심볼 이름을 적어 뒀습니다. 패키지 이름과 환경변수 이름은 원본 기록에서 이미 익명화된 것을 그대로 씁니다.

⚠️ 미리 말씀드릴 것이 있습니다. 이 글의 수치는 로컬 harness로 잰 것이지 운영 수치가 아닙니다. 외부 호출 지연은 stub에 설정한 값입니다. 장애가 난 적도 없습니다. 아래에 나오는 “최대 10초”는 외부 호출에 설정해 둔 read timeout 값이지 요청마다 실제로 그만큼 붙잡고 있었다고 측정한 값이 아닙니다.

어떤 서비스인가요?#

사업화를 목표로 만들고 있는 소셜 투표 플랫폼입니다. 사용자가 질문을 올리면 다른 사람들이 투표하고 그 결과 차트를 앱 밖으로 공유하는 서비스입니다. Kotlin과 Spring Boot로 만든 단일 monolith이고 데이터베이스는 관리형 PostgreSQL 하나를 씁니다. 아직 출시 전입니다.

구조를 그림으로 보면 이렇습니다.

외부 모더레이션 API는 유해한 내용을 걸러 주는 외부 서비스입니다. 글이나 댓글을 쓸 때마다 한 번씩 호출하고 이 호출에는 read timeout이 10초로 설정돼 있습니다. 그리고 이 호출이 데이터베이스 트랜잭션 안에서 일어나고 있었습니다.

# application.yml
read-timeout: ${APP_HTTP_READ_TIMEOUT:10s}

이 숫자를 기억해 주세요. 이 글의 나머지가 전부 여기서 나옵니다.

가설: connection pooler를 붙이면 될 줄 알았습니다#

점검의 출발점은 흔한 가설이었습니다.

트래픽이 늘면 DB 커넥션이 부족해질 텐데 RDS Proxy나 PgBouncer 같은 connection pooler를 앞에 세우면 되지 않을까?

connection pooler는 애플리케이션이 여는 커넥션 수천 개를 DB 커넥션 수십 개로 묶어 주는 미들웨어입니다. 소개 그림만 보면 정확히 제게 필요한 물건처럼 보였습니다.

그런데 이 판단을 내리기 전에 확인해야 할 것이 있었습니다. “내가 겪을 커넥션 부족이 정말 이 도구가 고치는 종류의 부족인가”입니다.

결론: pooler는 두 원인 중 하나만 고칩니다#

아니었습니다. 한 줄로 줄이면 이렇습니다.

커넥션 고갈에는 커넥션 개수 때문에 생기는 것과 커넥션을 오래 붙잡고 있어서 생기는 것이 있습니다. 증상은 같고 처방은 다릅니다. connection pooler는 앞쪽만 고칩니다.

그리고 이 결론의 근거는 RDS Proxy나 PgBouncer의 제품 문서가 아니라 transaction pooling이라는 방식의 정의 자체에서 나왔습니다. 아래에서 차례로 보겠습니다.

먼저 증상부터 보겠습니다. connection pool이 고갈되면 겉으로 드러나는 모습은 대체로 하나입니다. pool에서 커넥션을 기다리다 타임아웃이 나고 서로 아무 상관 없는 API 들이 동시에 느려집니다. 로그에는 이런 줄이 찍힙니다.

Connection is not available, request timed out after 30000ms

여기까지는 두 원인이 똑같이 생겼습니다. 그래서 증상만 보고 도구를 고르면 틀립니다.

원인 ①: 커넥션 개수가 많아서#

첫 번째는 커넥션 개수 자체가 문제인 경우입니다.

앱 instance 100대 × pool 크기 20 = 커넥션 2,000개
그런데 실제로 지금 쿼리를 실행 중인 건 50개
나머지 1,950개는 그냥 열려만 있습니다

PostgreSQL은 커넥션 하나마다 백엔드 프로세스를 하나씩 만들고 그 커넥션이 아무 일도 안 하고 있어도 메모리를 씁니다. 그래서 instance를 늘릴수록 DB 쪽이 먼저 한계에 부딪힙니다.

이것이 connection pooler가 존재하는 이유입니다. 앱 커넥션 2,000개를 백엔드 커넥션 50개로 묶어 주니까요. 원인 ① 쪽 고갈에는 정확히 맞는 도구입니다.

원인 ②: 커넥션을 오래 붙잡고 있어서#

두 번째는 커넥션 개수가 아니라 붙잡고 있는 시간이 문제인 경우입니다. 그리고 제 코드가 이쪽이었습니다.

// CommentService.kt (수정 전)
@Transactional
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    val user = activeUserGuard.requireActive(userId)                 // DB
    val postWithAuthor = postQueryRepository.findActiveById(postId)  // DB
    // ...
    moderationGate.screenComment(body)   // ← 외부 HTTP 호출. read timeout 10초
    // ...
    val comment = commentRepository.insert(...)                      // DB
}

@Transactional 이 메서드 전체에 걸려 있으니 이 메서드가 도는 동안 커넥션 하나가 계속 점유됩니다. 그런데 그 구간 한가운데에 쿼리를 하나도 실행하지 않으면서 최대 10초를 기다리는 외부 호출이 들어 있습니다.

동시에 글을 쓰는 요청이 pool 크기를 넘으면 그 시점부터 커넥션이 없습니다. 여기서 커넥션 개수를 늘려도 근본 원인은 그대로입니다. 느린 외부 호출이 커넥션을 붙잡고 있다는 사실은 변하지 않으니까요.

그리고 멈추는 건 글쓰기 경로만이 아닙니다.

투표도, 피드 조회도, 결과 차트 조회도 같은 connection pool에서 커넥션을 받습니다. 그래서 글쓰기 경로가 pool을 다 쓰면 서비스 전체가 함께 느려집니다.

이 앱에서 특히 아팠던 건 타이밍이었습니다. 이 서비스의 성장 엔진이 “투표 결과 차트를 공유하는 것”이라서 공유가 잘 터지는 날이 곧 서비스가 멈추는 날이 됩니다.

이유: transaction pooling의 정의 때문입니다#

여기가 이 글의 본론입니다.

“앱 커넥션 수천 개를 DB 커넥션 수십 개로 묶어 준다”는 설명은 맞습니다. 문제는 언제 묶이는가이고 그 답이 transaction pooling의 정의에 이미 들어 있습니다.

커넥션을 다시 쓰는 일은 트랜잭션과 트랜잭션 사이에서만 일어납니다. 트랜잭션이 열려 있는 동안에는 그 백엔드 커넥션이 그 클라이언트에 묶입니다(pin).

당연한 이야기이기도 합니다. 트랜잭션은 상태이고 열려 있는 중간에 다른 세션에 빌려주면 격리가 깨지니까요.

그래서 이렇게 됩니다.

트랜잭션이 10초 열려 있음
  → 백엔드 커넥션도 10초 묶임
  → 앱 커넥션 1개당 DB 커넥션 1개
  → connection pooler가 줄여 주는 게 없음

connection pooler는 짧은 트랜잭션이 많을 때 값을 하는 도구입니다. 원인 ②인 상태에서 도입하면 돈을 쓰고도 아무것도 나아지지 않습니다. 사실 더 나쁜 건 그다음입니다. “이제 대비했다”고 믿게 됩니다. 그 믿음이 다음 점검을 막습니다.

순서: 트랜잭션을 짧게 만드는 것이 먼저입니다#

해법은 하나가 아니라 여러 층이고 층에는 순서가 있습니다.

가로로 스크롤하면 나머지가 보입니다

커넥션 고갈에 대한 다섯 층의 해법과 각각의 성격.
층무엇을어떤 성격인가
①트랜잭션을 짧게. 외부 호출을 트랜잭션 밖으로유일하게 근본적입니다. 나머지 전부의 전제입니다
②유입 제어. 동시 처리 상한을 의도적으로 정하기실패를 빠르고 예측 가능하게 만듭니다
③connection pooler①이 끝나야 효과가 있습니다
④읽기 분리·캐시커넥션을 덜 쓰게 만드는 유일한 층입니다
⑤비동기 오프로드(outbox)요청당 DB 작업 자체를 줄입니다

순서가 이 표의 요점입니다. ①이 안 되어 있으면 ②③④⑤는 완화일 뿐 수리가 아닙니다.

connection pooler는 ③입니다. ①을 안 하고 ③부터 가면 효과가 없다는 게 앞 절의 내용이었습니다.

수정 ①: 외부 호출을 트랜잭션 밖으로#

그래서 ①부터 했습니다. 트랜잭션 경계를 쓰기 구간으로 좁히는 작업입니다. Spring에서 @Transactional 은 프록시 기반이라 같은 클래스 안에서 자기 메서드를 부르면 안 걸립니다. 그래서 이미 코드베이스에 있던 TransactionTemplate 패턴을 그대로 재사용했습니다. 새 메커니즘을 들이지 않았다는 점이 중요합니다.

// 수정 후: 메서드에 @Transactional이 없습니다
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    // ① 검증 (읽기. 각각 짧게 커넥션을 쓰고 반납합니다)
    val user = activeUserGuard.requireActive(userId)
    val postWithAuthor = postQueryRepository.findActiveById(postId) ?: throw ...

    // ② 외부 호출. 트랜잭션 밖입니다. 여기서 10초를 써도 커넥션을 잡지 않습니다
    moderationGate.screenComment(body)

    // ③ 쓰기만 원자적으로 묶습니다
    val written = writeTx.execute {
        val identity = postAliasRepository.ensureIdentity(...)
        val comment = commentRepository.insert(...)
        Triple(comment, identity?.alias, ...)
    }!!
}

여기서 “트랜잭션을 쪼개면 경합이 늘어나지 않나요?”라는 질문이 나올 수 있는데 경합 창은 넓어지지 않았습니다. 수정 전에도 모더레이션 호출이 읽기와 쓰기 사이에 있었고 그 경로는 게시글 행에 락을 걸지 않고 있었기 때문입니다 (for update 가 없었습니다). 트랜잭션 안에 있다고 해서 다른 세션의 변경을 막아 주지는 않습니다. 읽기에서 쓰기까지의 거리는 동일합니다.

같은 작업을 쓰기 경로 세 곳(글 · 댓글 · 투표 첨부)에 했습니다. 그중 하나는 상태가 더 나빴습니다. 투표 첨부 경로는 for update 로 행까지 잠근 채 외부 호출을 하고 있었습니다. 커넥션과 행 락, 두 자원을 동시에 쥐고 있었던 겁니다.

글과 댓글 두 경로를 먼저 고치고 투표 첨부는 검열에 넣는 입력이 잠근 행에서 나오는 탓에 staleness(값이 낡았는지) 재확인이 필요해서 의도적으로 미뤘다가 나흘 뒤에 고쳤습니다.

결론을 한 줄로 적으면 이렇습니다. 코드 수정은 connection pooler의 대안이 아니라 전제조건이었습니다. 고치고 나니 이제 connection pooler가 값을 할 수 있는 상태가 됐습니다.

설정: 아무도 고르지 않은 두 숫자#

②(유입 제어)에도 함정이 하나 있었습니다. 블로킹 JDBC 에서는 connection pool이 사실상 동시성 상한입니다. 스레드가 아무리 많아도 커넥션을 못 받으면 일을 못 하니까요.

그런데 설정을 열어 보니 이랬습니다.

# application.yml (발견 당시)
spring:
  datasource:
    url: ${DB_URL:...}
    username: ${DB_USER:...}
    password: ${DB_PASSWORD:...}
    # 끝. hikari 블록 자체가 없습니다

톰캣 스레드는 기본값 200, connection pool은 설정이 한 줄도 없어서 Spring Boot 기본값이 그대로 서비스 용량이 되어 있었습니다. 이러면 나머지 요청들은 커넥션을 기다리다 타임아웃 뒤에 실패합니다.

방향 자체는 맞습니다. 빨리 실패해야 나머지가 삽니다. 문제는 다른 데 있었습니다. 두 값 다 아무도 고른 것이 아니었습니다. 둘 다 프레임워크 기본값이고 나쁜 것은 숫자 자체가 아니라 그 숫자가 어디에도 적혀 있지 않다는 것이었습니다.

그래서 명시했습니다.

hikari:
  maximum-pool-size: ${DB_POOL_MAX:20}
  connection-timeout: ${DB_POOL_TIMEOUT_MS:5000}   # 30초 기본값은 너무 깁니다. 빨리 실패해야 나머지가 삽니다
  max-lifetime: ${DB_POOL_MAX_LIFETIME_MS:1200000}

다만 pool을 키운 것은 수리가 아니라 완화입니다. 그리고 키우는 데에도 상한이 있습니다.

pool 크기 × 최대 instance 수 ≤ DB 커넥션 상한

앱은 자기 instance가 몇 대인지 모르기 때문에 이 불변식을 코드로 강제할 수 없습니다. IaC 주석이 유일한 방어라 거기에 못박아 뒀습니다.

유입 제어라는 것은 상한을 두는 것이 아니라 그 상한을 의도적으로 정하는 것입니다. 기본값 두 개가 만들어 낸 동시성 정책은 정책이 아닙니다.

사전 점검: 이 코드가 pooler를 쓸 수 있나#

③으로 넘어가기 전에 확인할 것이 하나 더 있었습니다. transaction pooling에는 핀(pin)을 유발하는 패턴이 있고 코드에 그게 있으면 connection pooler가 무력해집니다. 핀이 걸리면 그 커넥션은 트랜잭션이 끝나도 그 클라이언트에 계속 묶여 있게 됩니다.

  • 세션 스코프 advisory lock (pg_advisory_lock)
  • 임시 테이블
  • SET · set search_path
  • 서버 프리페어드 스테이트먼트 (pooler와 버전에 따라 다릅니다)

직접 확인해 봤습니다.

$ grep -rn "pg_advisory_lock" src/main/kotlin/      # (없음)
$ grep -rn "advisory_xact" src/main/kotlin/
ReportRepository.kt      pg_advisory_xact_lock(...)
AuthAuditPurge.kt        pg_try_advisory_xact_lock(...)
VoteRepository.kt        pg_advisory_xact_lock(...)

네 가지 다 없었습니다. advisory lock은 세 군데에서 쓰는데 전부 xact 스코프였습니다. 트랜잭션이 끝날 때 자동으로 풀리기 때문에 transaction pooling에 그대로 얹힙니다.

이 셋이 xact 스코프인 것이 의도였는지 우연이었는지는 기록으로 가릴 수 없습니다. 확실한 것은 세션 스코프 락을 한 군데만 썼어도 그 경로가 connection pooler를 무력화했을 것이고 그 사실은 도입한 뒤에야 알게 됐으리라는 겁니다.

도구를 도입하기 전에, 그 도구가 이 코드에서 실제로 동작하는지 먼저 확인하는 절차. 이 점검에서 얻은 것 중 다른 프로젝트로 가장 잘 옮겨지는 부분이 이거였습니다.

반론: “비동기로 바꾸면 되지 않나요?”#

이 이야기를 하면 자주 나오는 처방이 하나 더 있습니다.

WebFlux나 코루틴으로 바꾸면 스레드는 아낍니다. 그런데 커넥션은 그대로 잡습니다. JDBC는 블로킹이고 트랜잭션이 열려 있는 한 커넥션은 반납되지 않기 때문입니다.

스레드와 커넥션은 다른 자원입니다. 문제의 축이 커넥션인데 스레드를 아끼는 처방을 가져오면 축이 어긋납니다. R2DBC 라면 이야기가 다르지만, 그건 데이터 접근 계층을 전면 재작성하는 일입니다.

pool을 키우는 처방도 같은 종류입니다. 완화는 되지만 수리는 아니고 앞서 본 pool 크기 × instance 수 ≤ DB 커넥션 상한에 먼저 걸립니다. 그리고 근본 원인은 그대로 남습니다. 느린 외부 호출이 커넥션을 붙잡는다는 것 말입니다.

가드: 되돌리기 쉬운 수정이라 원인에 걸었습니다#

이 수정에는 특유의 취약함이 있습니다. @Transactional 한 줄이면 원래대로 돌아갑니다. 그리고 되돌려도 기능은 멀쩡합니다. 테스트도 통과하고 화면도 정상입니다. 증상은 부하가 걸리는 날에만 나옵니다.

“커넥션을 오래 안 잡는다”는 것은 직접 관측하기가 어렵습니다. 그래서 결과 대신 원인을 단언했습니다. 실제 HTTP 클라이언트가 앉는 인터페이스 자리에 spy를 앉히고 호출이 일어나는 그 시점에 트랜잭션이 활성인지를 기록합니다.

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

// 단언
assertThat(probe.sawTransaction).isNotEmpty()         // ① 호출이 실제로 일어났나
assertThat(probe.sawTransaction).containsOnly(false)  // ② 그 호출은 트랜잭션 밖이었나

①이 없으면 ②가 공허하게 통과합니다. 게이트가 통째로 빠져서 호출이 0건이면 containsOnly 는 빈 리스트에 대해 참이기 때문입니다. “~가 아니다”를 검사하는 단언에는 항상 “호출이 있기는 했나”를 같이 붙여야 합니다.

그리고 이 가드가 정말 겨누고 있는지는 mutation으로 확인했습니다. 코드를 일부러 되돌려 놓고 테스트를 돌려서 빨간불이 나는지 보는 방법입니다.

# 댓글 경로에 @Transactional 복원
ModerationOutsideTransactionTest > the moderation call does not hold a database transaction() FAILED

# 글 경로에 @Transactional 복원
ModerationOutsideTransactionTest > creating a post also screens outside a transaction() FAILED

글과 댓글 경로에서는 해당 가드만 빨간불이 됐습니다. 그런데 투표 첨부 경로는 달랐습니다. mutation이 처음엔 초록불이었습니다. staleness 가드가 겨누는 조건이 테스트 안에서 만들어지지 않았기 때문이고 spy의 onScreen 훅으로 검열 구간에 행을 바꿔 조건을 만든 뒤에야 빨간불을 봤습니다.

여기서 배운 것이 이 글에서 제일 옮길 만한 것입니다. mutation이 초록불이면 코드가 안전한 게 아니라 가드가 겨누고 있지 않은 것입니다.

측정: 세 주 뒤에 실제로 재 봤습니다#

이 글은 원래 “수치가 없습니다”로 끝날 예정이었습니다. 그런데 그 문장을 쓰고 나니 수치를 만들 도구가 없다는 뜻이라는 게 분명해져서 세 주 뒤에 JMeter harness를 만들어 재 봤습니다.

핵심은 한 변수만 바꾸는 것이었습니다. arm A는 현재 코드, arm B는 @Transactional 한 줄만 되돌린 코드입니다. pool 크기·스레드 수·외부 호출 지연·데이터는 전부 같습니다. 외부 호출 지연은 앱에 심지 않고 로컬 stub을 세워 base-url 을 그쪽으로 돌렸습니다. 앱에 「느리게 도는 모드」를 넣으면 그게 언젠가 운영에서 켜집니다.

고친 경로(글 생성)는 두 arm 이 거의 같습니다. 벌어지는 곳은 글쓰기와 아무 상관 없는 피드 조회뿐입니다.

읽는 법은 이렇습니다. 쓰기 경로는 두 arm이 같습니다(2,577 대 2,584ms). 외부 호출 1.6초가 어느 쪽이든 지배하기 때문입니다. 그래서 쓰기만 재면 이 수정의 효과가 보이지 않습니다.

효과는 글쓰기와 아무 상관 없는 피드 조회에 나타납니다. arm B 에서는 쓰기 16개가 각각 1.6초씩 커넥션을 붙잡아 pool 10개를 전부 소진하고 4ms로 끝나던 조회가 6초가 됩니다. 오류가 아니라 대기라서 오류율은 0% 인 채로 서비스가 느려집니다. 이게 이 결함이 조용한 이유입니다.

그리고 처음 돌린 실행은 차이가 거의 없었습니다(p95 5ms 대 8ms). 쓰기 8개로는 pool 10개가 고갈되지 않기 때문입니다. pool이 마르지 않으면 이 현상은 나타나지 않습니다. 이 수치는 조건에 딸린 값이지 상수가 아닙니다.

수정 ②: 재고 나니 하나 더 보였습니다#

수치가 생기니 다음 질문이 자동으로 나왔습니다. 글 생성 p50이 왜 stub 지연의 정확히 두 배인가. 게이트를 열어 보니 외부 분류기를 순차로 부르고 있었습니다.

③ 유해분류와 ④ 저격판정은 같은 입력을 보는 독립 검사입니다. 앞의 결과가 뒤의 입력이 되지 않으니 순서가 필요 없습니다.

가상 스레드(Java 21)로 ④ 를 띄우고 ③ 을 호출 스레드에서 돌립니다. 고정 크기 pool을 두지 않은 것이 요점입니다. pool 크기는 곧 새 동시성 상한이고 이 글이 내내 이야기한 「아무도 고르지 않은 상한」을 모더레이션 경로에 다시 만들게 됩니다.

동작은 그대로여야 합니다. 병렬화는 성능 변경이지 동작 변경이 아닙니다. 그래서 둘 다 끝날 때까지 기다리고(먼저 던졌다고 남은 호출을 버려두면 비용은 나가고 결과는 아무도 안 봅니다), 예외는 ③ 이 ④ 보다 우선합니다(순차와 같은 응답).

⚠️ 대가가 있습니다. 순차일 때는 ③ 이 막으면 ④ 를 아예 안 불렀습니다. 이제는 ③ 이 막아도 ④ 가 돌아 게시글당 약 $0.0002가 더 나갑니다. 지연을 절반으로 줄이는 대가로 이걸 받는 거래입니다.

외부 대기를 반으로 줄였으니 글 생성만 두 배가 되는 것이 맞습니다. 피드 조회가 그대로인 것은 건드리지 않은 경로이기 때문입니다.

정확히 2배입니다. 800ms 두 번을 더하던 것이 겹쳐서 한 번이 됐으니 예상대로이고 피드 조회는 4ms 그대로입니다. 건드리지 않은 경로는 안 움직여야 맞습니다.

그런데 처음엔 개선이 안 보였습니다

먼저 쓰기 16으로 돌렸더니 p50이 2,577ms 대 2,598ms로 차이가 없었습니다. 병렬화가 안 먹은 줄 알았습니다.

원인은 코드가 아니라 측정 조건이었습니다. 쓰기 16에서는 부하기·앱·stub·DB가 한 기계의 CPU를 나눠 쓰며 이미 포화라 처리량이 두 쪽 모두 6.26 req/s라는 같은 천장에 걸려 있었습니다. 외부 호출이 그 시점엔 병목이 아니었으므로 그걸 절반으로 줄여도 총 처리량이 변하지 않습니다.

확인은 이 순서로 했습니다. ①stub이 병목인지 직접 쟀습니다. 동시 32건이 0.81초에 끝나니 아닙니다. ②소스와 jar 시각을 대조해 병렬 코드가 빌드에 들어간 것을 봤습니다. ③단건 요청을 쟀더니 0.817초였고 병렬화는 동작하고 있었습니다. ④포화되지 않는 쓰기 4에서 다시 재니 2배가 그대로 나왔습니다.

남는 교훈은 이겁니다. 포화된 시스템에서는 병목이 아닌 것을 고쳐도 숫자가 안 움직입니다. 개선이 안 보이면 코드를 의심하기 전에 무엇이 천장을 만들고 있는지부터 재야 합니다.

새 규칙에는 새 가드를

이 변경은 예외 우선순위라는 규칙을 새로 만듭니다. 순차일 때는 ③ 이 던지면 ④ 를 안 불렀으니 우선순위라는 것 자체가 없었습니다.

그래서 일부러 뒤집어 봤더니 기존 테스트 8건이 전부 통과했습니다. 규칙을 만들면 그걸 지키는 단언도 만들어야 합니다. 2건을 추가하고 mutation 3종으로 확인했습니다. ExecutionException 언랩 제거, 우선순위 뒤집기, ③ 이 막으면 ④ 건너뛰기. 셋 다 빨간불이 납니다.

한계: 이 글이 주장하지 않는 것#

  • 운영 수치가 아닙니다. 잰 것은 로컬 harness이고 부하기와 앱이 같은 기계에서 CPU를 나눠 씁니다. 절대 처리량은 의미가 없고 비교만 의미가 있습니다. 외부 호출 800ms는 stub에 설정한 값이지 실제 지연 분포가 아닙니다.
  • arm 당 1회 실행입니다. 반복 실행으로 분산을 보지 않았습니다.
  • 1,512배는 조건에 딸린 숫자입니다. 쓰기 동시성이 pool 크기를 넘을 때 나타납니다. 쓰기 8 · pool 10 에서는 p95가 5ms 대 8ms였습니다.
  • “최대 10초”는 설정값입니다. 외부 호출에 걸어 둔 read timeout 이고 요청마다 실제로 그만큼 점유했다고 측정한 값이 아닙니다.
  • 장애가 난 적은 없습니다. 출시 전 구조 점검에서 나온 것이고 이 경로가 실제로 고갈되는 것을 관측한 기록은 없습니다.
  • connection pooler가 쓸모없다는 이야기가 아닙니다. 원인 ① 쪽 고갈에는 정확히 맞는 도구입니다. 이 글이 말하는 것은 원인 ②인 상태에서는 앱 커넥션 1개당 DB 커넥션 1개가 되어 값을 못 한다는 것뿐입니다.
  • 벤더별 커넥션 상한 수치는 쓰지 않았습니다. 확인하지 않은 값입니다.
  • 핀 유발 패턴 목록이 완전하지 않을 수 있습니다. pooler와 버전에 따라 다르고 여기서는 이 코드에 그 넷이 없다는 것만 확인했습니다.

마치며#

정리하면 이렇습니다.

  • 커넥션 고갈의 원인은 개수와 점유 시간 두 가지이고 증상이 같아서 헷갈립니다.
  • connection pooler는 개수 문제를 고치는 도구입니다. 점유 시간 문제에서는 앱 커넥션 1개당 DB 커넥션 1개가 되어 줄여 줄 것이 없습니다. 이건 제품의 한계가 아니라 transaction pooling이라는 방식의 정의에서 나옵니다.
  • 순서: 트랜잭션을 짧게 만드는 것이 먼저입니다. 트랜잭션을 짧게 만드는 것이 나머지 전부의 전제입니다.
  • 도구를 도입하기 전에 이 코드에서 그 도구가 동작하는지 확인하는 절차를 넣으면 도입하고 나서 알게 될 일을 미리 알 수 있습니다.

마지막으로 한 줄만 남긴다면 이겁니다. 증상이 같다고 원인이 같은 것은 아니고 도구는 원인 하나에만 맞습니다. 그리고 잘못 고른 도구의 진짜 비용은 돈이 아니라 “이제 대비했다”는 믿음입니다.
