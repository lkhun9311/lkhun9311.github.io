RDS Proxy를 붙이면 될 줄 알았습니다
트랜잭션 안의 외부 API 호출과 커넥션 고갈

Writing · 2026년 9월 · 12분

다른 언어 English · 日本語

안녕하세요. 개인 프로젝트로 소셜 투표 앱을 만들고 있습니다. 출시 전에 아키텍처를 점검하다가 “트래픽이 늘면 DB 커넥션이 부족해질 텐데, 커넥션 풀러를 하나 붙이면 되지 않을까”라는 아주 흔한 가설에서 출발했는데, 결론은 “이 코드베이스에서는 아니오”였습니다.

왜 아니오였는지, 그리고 그 판단을 무엇을 근거로 내렸는지 공유하려고 합니다.

이 글의 예상 독자#

  • Spring Boot 로 서비스를 만들고 있는데, 커넥션 풀 설정을 아직 직접 건드려 본 적이 없는 분
  • “커넥션이 부족하면 RDS Proxy 같은 걸 붙이면 되지 않나?”라고 생각해 보신 분
  • 트랜잭션 안에서 외부 API 를 호출하는 코드를 보신 적이 있거나, 지금 그렇게 쓰고 계신 분

무슨 내용인가요?#

  • 커넥션 고갈에는 원인이 두 가지 있고, 커넥션 풀러는 그중 하나만 고칩니다.
  • 왜 못 고치는지는 제품 문서가 아니라 트랜잭션 풀링이라는 방식의 정의에서 나옵니다.
  • 그래서 도구를 도입하기 전에 이 코드에서 그 도구가 동작하는지부터 확인했습니다.
  • 수정이 @Transactional 한 줄로 되돌아갈 수 있는 종류라, 회귀 방어를 결과가 아니라 원인에 걸었습니다.

⚠️ 미리 말씀드릴 것이 있습니다. 이 글에는 부하 테스트로 측정한 수치가 없습니다. 장애가 난 적도 없습니다. 아래에 나오는 “최대 10초”는 외부 호출에 설정해 둔 read timeout 값이지, 요청마다 실제로 그만큼 붙잡고 있었다고 측정한 값이 아닙니다. 개선은 코드 성질의 변화로 설명되는 것이고, 이 글은 실측치를 주장하지 않습니다.

어떤 서비스인가요?#

개인 프로젝트로 만들고 있는 소셜 투표 앱입니다. 사용자가 질문을 올리면 다른 사람들이 투표하고, 그 결과 차트를 앱 밖으로 공유하는 서비스입니다. Kotlin 과 Spring Boot 로 만든 단일 모놀리스이고, 데이터베이스는 관리형 PostgreSQL 하나를 씁니다. 아직 출시 전입니다.

구조를 그림으로 보면 이렇습니다.

여기서 눈여겨보실 곳은 아래쪽 분홍색 상자입니다. 글이나 댓글을 쓸 때마다 외부 모더레이션 API(유해한 내용을 걸러 주는 외부 서비스)를 한 번씩 호출합니다. 그리고 이 호출에는 read timeout 이 10초로 설정돼 있습니다.

# application.yml
read-timeout: ${OXY_HTTP_READ_TIMEOUT:10s}

이 숫자를 기억해 주세요. 이 글의 나머지가 전부 여기서 나옵니다.

처음엔 커넥션 풀러를 붙이면 될 줄 알았습니다#

점검의 출발점은 흔한 가설이었습니다.

트래픽이 늘면 DB 커넥션이 부족해질 텐데, RDS Proxy 나 PgBouncer 같은 커넥션 풀러(connection pooler)를 앞에 세우면 되지 않을까?

커넥션 풀러는 애플리케이션이 여는 커넥션 수천 개를 DB 커넥션 수십 개로 묶어 주는 미들웨어입니다. 소개 그림만 보면 정확히 저희에게 필요한 물건처럼 보였습니다.

그런데 이 판단을 내리기 전에 확인해야 할 것이 있었습니다. “우리가 겪을 커넥션 부족이 정말 이 도구가 고치는 종류의 부족인가”입니다.

결론부터 말씀드리자면#

아니었습니다. 한 줄로 줄이면 이렇습니다.

커넥션 고갈에는 커넥션 개수 때문에 생기는 것과 커넥션을 오래 붙잡고 있어서 생기는 것이 있습니다. 증상은 같고 처방은 다릅니다. 커넥션 풀러는 앞쪽만 고칩니다.

그리고 이 결론의 근거는 RDS Proxy 나 PgBouncer 의 제품 문서가 아니라, 트랜잭션 풀링(transaction pooling)이라는 방식의 정의 자체에서 나왔습니다. 아래에서 차례로 보겠습니다.

먼저 증상부터 보겠습니다. 커넥션 풀이 고갈되면 겉으로 드러나는 모습은 대체로 하나입니다. 풀에서 커넥션을 기다리다 타임아웃이 나고, 서로 아무 상관 없는 API 들이 동시에 느려집니다. 로그에는 이런 줄이 찍힙니다.

Connection is not available, request timed out after 30000ms

여기까지는 두 원인이 똑같이 생겼습니다. 그래서 증상만 보고 도구를 고르면 틀립니다.

원인 A — 커넥션이 많아서#

첫 번째는 커넥션 개수 자체가 문제인 경우입니다.

앱 인스턴스 100대 × 풀 크기 20 = 커넥션 2,000개
그런데 실제로 지금 쿼리를 실행 중인 건 50개
나머지 1,950개는 그냥 열려만 있습니다

PostgreSQL 은 커넥션 하나마다 백엔드 프로세스를 하나씩 만들고, 그 커넥션이 아무 일도 안 하고 있어도 메모리를 씁니다. 그래서 인스턴스를 늘릴수록 DB 쪽이 먼저 한계에 부딪힙니다.

이것이 커넥션 풀러가 존재하는 이유입니다. 앱 커넥션 2,000개를 백엔드 커넥션 50개로 묶어 주니까요. A 형 고갈에는 정확히 맞는 도구입니다.

원인 B — 커넥션을 오래 붙잡고 있어서#

두 번째는 커넥션 개수가 아니라 붙잡고 있는 시간이 문제인 경우입니다. 그리고 저희 코드가 이쪽이었습니다.

// CommentService.kt — 수정 전
@Transactional
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    val user = activeUserGuard.requireActive(userId)                 // DB
    val postWithAuthor = postQueryRepository.findActiveById(postId)  // DB
    // ...
    moderationGate.screenComment(body)   // ← 외부 HTTP 호출. read timeout 10초
    // ...
    val comment = commentRepository.insert(...)                      // DB
}

@Transactional 이 메서드 전체에 걸려 있으니, 이 메서드가 도는 동안 커넥션 하나가 계속 점유됩니다. 그런데 그 구간 한가운데에 쿼리를 하나도 실행하지 않으면서 최대 10초를 기다리는 외부 호출이 들어 있습니다.

동시에 글을 쓰는 요청이 풀 크기를 넘으면, 그 시점부터 커넥션이 없습니다. 여기서 커넥션 개수를 늘려도 근본 원인은 그대로입니다. 느린 외부 호출이 커넥션을 붙잡고 있다는 사실은 변하지 않으니까요.

그리고 멈추는 건 글쓰기 경로만이 아닙니다.

투표도, 피드 조회도, 결과 차트 조회도 같은 커넥션 풀에서 커넥션을 받습니다. 그래서 글쓰기 경로가 풀을 다 쓰면 서비스 전체가 함께 느려집니다.

이 앱에서 특히 아팠던 건 타이밍이었습니다. 이 서비스의 성장 엔진이 “투표 결과 차트를 공유하는 것”이라서, 공유가 잘 터지는 날이 곧 서비스가 멈추는 날이 됩니다.

왜 커넥션 풀러가 B를 못 고치나요?#

여기가 이 글의 본론입니다.

“앱 커넥션 수천 개를 DB 커넥션 수십 개로 묶어 준다”는 설명은 맞습니다. 문제는 언제 묶이는가이고, 그 답이 트랜잭션 풀링의 정의에 이미 들어 있습니다.

커넥션을 다시 쓰는 일은 트랜잭션과 트랜잭션 사이에서만 일어납니다. 트랜잭션이 열려 있는 동안에는 그 백엔드 커넥션이 그 클라이언트에 묶입니다(pin).

당연한 이야기이기도 합니다. 트랜잭션은 상태이고, 열려 있는 중간에 다른 세션에 빌려주면 격리가 깨지니까요.

그래서 이렇게 됩니다.

트랜잭션이 10초 열려 있음
  → 백엔드 커넥션도 10초 묶임
  → 앱 커넥션 1개당 DB 커넥션 1개
  → 커넥션 풀러가 줄여 주는 게 없음

커넥션 풀러는 짧은 트랜잭션이 많을 때 값을 하는 도구입니다. B 를 앓는 상태에서 도입하면 돈을 쓰고도 아무것도 나아지지 않는데, 사실 더 나쁜 건 그다음입니다 — “이제 대비했다”고 믿게 됩니다. 그 믿음이 다음 점검을 막습니다.

그래서 순서가 있습니다#

해법은 하나가 아니라 여러 층이고, 층에는 순서가 있습니다.

가로로 스크롤하면 나머지가 보입니다

커넥션 고갈에 대한 다섯 층의 해법과 각각의 성격.
층무엇을어떤 성격인가
①트랜잭션을 짧게 — 외부 호출을 트랜잭션 밖으로유일하게 근본적입니다. 나머지 전부의 전제입니다
②유입 제어 — 동시 처리 상한을 의도적으로 정하기실패를 빠르고 예측 가능하게 만듭니다
③커넥션 풀러①이 끝나야 효과가 있습니다
④읽기 분리·캐시커넥션을 덜 쓰게 만드는 유일한 층입니다
⑤비동기 오프로드(outbox)요청당 DB 작업 자체를 줄입니다

커넥션 풀러는 ③입니다. ①을 안 하고 ③부터 가면 효과가 없다는 게 앞 절의 내용이었습니다.

코드부터 고쳤습니다#

그래서 ①부터 했습니다. 트랜잭션 경계를 쓰기 구간으로 좁히는 작업입니다. Spring 에서 @Transactional 은 프록시 기반이라 같은 클래스 안에서 자기 메서드를 부르면 안 걸립니다. 그래서 이미 코드베이스에 있던 TransactionTemplate 패턴을 그대로 재사용했습니다. 새 메커니즘을 들이지 않았다는 점이 중요합니다.

// 수정 후 — 메서드에 @Transactional 이 없습니다
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    // ① 검증 (읽기. 각각 짧게 커넥션을 쓰고 반납합니다)
    val user = activeUserGuard.requireActive(userId)
    val postWithAuthor = postQueryRepository.findActiveById(postId) ?: throw ...

    // ② 외부 호출 — 트랜잭션 밖입니다. 여기서 10초를 써도 커넥션을 잡지 않습니다
    moderationGate.screenComment(body)

    // ③ 쓰기만 원자적으로 묶습니다
    val written = writeTx.execute {
        val identity = postAliasRepository.ensureIdentity(...)
        val comment = commentRepository.insert(...)
        Triple(comment, identity?.alias, ...)
    }!!
}

여기서 “트랜잭션을 쪼개면 경합이 늘어나지 않나요?”라는 질문이 나올 수 있는데, 경합 창은 넓어지지 않았습니다. 수정 전에도 모더레이션 호출이 읽기와 쓰기 사이에 있었고, 그 경로는 게시글 행에 락을 걸지 않고 있었기 때문입니다 (for update 가 없었습니다). 트랜잭션 안에 있다고 해서 다른 세션의 변경을 막아 주지는 않습니다. 읽기에서 쓰기까지의 거리는 동일합니다.

같은 작업을 쓰기 경로 세 곳(글 · 댓글 · 투표 첨부)에 했습니다. 그중 하나는 상태가 더 나빴습니다 — 투표 첨부 경로는 for update 로 행까지 잠근 채 외부 호출을 하고 있었습니다. 커넥션과 행 락, 두 자원을 동시에 쥐고 있었던 겁니다.

글과 댓글 두 경로를 먼저 고치고, 투표 첨부는 검열에 넣는 입력이 잠근 행에서 나오는 탓에 staleness(값이 낡았는지) 재확인이 필요해서 의도적으로 미뤘다가 나흘 뒤에 고쳤습니다.

결론을 한 줄로 적으면 이렇습니다. 코드 수정은 커넥션 풀러의 대안이 아니라 전제조건이었습니다. 고치고 나니 이제 커넥션 풀러가 값을 할 수 있는 상태가 됐습니다.

아무도 고르지 않은 두 숫자#

②(유입 제어)에도 함정이 하나 있었습니다. 블로킹 JDBC 에서는 커넥션 풀이 사실상 동시성 상한입니다. 스레드가 아무리 많아도 커넥션을 못 받으면 일을 못 하니까요.

그런데 저희 설정을 열어 보니 이랬습니다.

# application.yml — 발견 당시
spring:
  datasource:
    url: ${DB_URL:...}
    username: ${DB_USER:...}
    password: ${DB_PASSWORD:...}
    # 끝. hikari 블록 자체가 없습니다

톰캣 스레드는 기본값 200, 커넥션 풀은 설정이 한 줄도 없어서 Spring Boot 기본값이 그대로 서비스 용량이 되어 있었습니다. 이러면 나머지 요청들은 커넥션을 기다리다 타임아웃 뒤에 실패합니다.

방향 자체는 맞습니다. 빨리 실패해야 나머지가 삽니다. 문제는 다른 데 있었습니다 — 두 값 다 아무도 고른 것이 아니었습니다. 둘 다 프레임워크 기본값이고, 나쁜 것은 숫자 자체가 아니라 그 숫자가 어디에도 적혀 있지 않다는 것이었습니다.

그래서 명시했습니다.

hikari:
  maximum-pool-size: ${DB_POOL_MAX:20}
  connection-timeout: ${DB_POOL_TIMEOUT_MS:5000}   # 30초 기본값은 너무 깁니다 — 빨리 실패해야 나머지가 삽니다
  max-lifetime: ${DB_POOL_MAX_LIFETIME_MS:1200000}

다만 풀을 키운 것은 수리가 아니라 완화입니다. 그리고 키우는 데에도 상한이 있습니다.

풀 크기 × 최대 인스턴스 수 ≤ DB 커넥션 상한

앱은 자기 인스턴스가 몇 대인지 모르기 때문에 이 불변식을 코드로 강제할 수 없습니다. IaC 주석이 유일한 방어라 거기에 못박아 뒀습니다.

유입 제어라는 것은 상한을 두는 것이 아니라 그 상한을 의도적으로 정하는 것입니다. 기본값 두 개가 만들어 낸 동시성 정책은 정책이 아닙니다.

커넥션 풀러를 쓸 수 있는 코드인지 먼저 확인했습니다#

③으로 넘어가기 전에 확인할 것이 하나 더 있었습니다. 트랜잭션 풀링에는 핀(pin)을 유발하는 패턴이 있고, 코드에 그게 있으면 커넥션 풀러가 무력해집니다. 핀이 걸리면 그 커넥션은 트랜잭션이 끝나도 그 클라이언트에 계속 묶여 있게 됩니다.

  • 세션 스코프 advisory lock (pg_advisory_lock)
  • 임시 테이블
  • SET · set search_path
  • 서버 프리페어드 스테이트먼트 (풀러와 버전에 따라 다릅니다)

직접 확인해 봤습니다.

$ grep -rn "pg_advisory_lock" src/main/kotlin/      # (없음)
$ grep -rn "advisory_xact" src/main/kotlin/
ReportRepository.kt      pg_advisory_xact_lock(...)
AuthAuditPurge.kt        pg_try_advisory_xact_lock(...)
VoteRepository.kt        pg_advisory_xact_lock(...)

네 가지 다 없었습니다. advisory lock 은 세 군데에서 쓰는데 전부 xact 스코프였습니다. 트랜잭션이 끝날 때 자동으로 풀리기 때문에 트랜잭션 풀링에 그대로 얹힙니다.

이 셋이 xact 스코프인 것이 의도였는지 우연이었는지는 기록으로 가릴 수 없습니다. 확실한 것은 세션 스코프 락을 한 군데만 썼어도 그 경로가 커넥션 풀러를 무력화했을 것이고, 그 사실은 도입한 뒤에야 알게 됐으리라는 겁니다.

도구를 도입하기 전에, 그 도구가 이 코드에서 실제로 동작하는지 먼저 확인하는 절차. 이 점검에서 얻은 것 중 다른 프로젝트로 가장 잘 옮겨지는 부분이 이거였습니다.

“비동기로 바꾸면 되지 않나요?”#

이 이야기를 하면 자주 나오는 처방이 하나 더 있습니다.

WebFlux 나 코루틴으로 바꾸면 스레드는 아낍니다. 그런데 커넥션은 그대로 잡습니다. JDBC 는 블로킹이고, 트랜잭션이 열려 있는 한 커넥션은 반납되지 않기 때문입니다.

스레드와 커넥션은 다른 자원입니다. 문제의 축이 커넥션인데 스레드를 아끼는 처방을 가져오면 축이 어긋납니다. R2DBC 라면 이야기가 다르지만, 그건 데이터 접근 계층을 전면 재작성하는 일입니다.

풀을 키우는 처방도 같은 종류입니다. 완화는 되지만 수리는 아니고, 앞서 본 풀 크기 × 인스턴스 수 ≤ DB 커넥션 상한에 먼저 걸립니다. 그리고 근본 원인 — 느린 외부 호출이 커넥션을 붙잡는다 — 은 그대로 남습니다.

되돌리기 쉬운 수정이라, 가드를 원인에 걸었습니다#

이 수정에는 특유의 취약함이 있습니다. @Transactional 한 줄이면 원래대로 돌아갑니다. 그리고 되돌려도 기능은 멀쩡합니다 — 테스트도 통과하고 화면도 정상입니다. 증상은 부하가 걸리는 날에만 나옵니다.

“커넥션을 오래 안 잡는다”는 것은 직접 관측하기가 어렵습니다. 그래서 결과 대신 원인을 단언했습니다. 실제 HTTP 클라이언트가 앉는 인터페이스 자리에 spy 를 앉히고, 호출이 일어나는 그 시점에 트랜잭션이 활성인지를 기록합니다.

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

// 단언
assertThat(probe.sawTransaction).isNotEmpty()         // ① 호출이 실제로 일어났나
assertThat(probe.sawTransaction).containsOnly(false)  // ② 그 호출은 트랜잭션 밖이었나

①이 없으면 ②가 공허하게 통과합니다. 게이트가 통째로 빠져서 호출이 0건이면 containsOnly 는 빈 리스트에 대해 참이기 때문입니다. “~가 아니다”를 검사하는 단언에는 항상 “호출이 있기는 했나”를 같이 붙여야 합니다.

그리고 이 가드가 정말 겨누고 있는지는 뮤테이션으로 확인했습니다. 코드를 일부러 되돌려 놓고 테스트를 돌려서, 빨간불이 나는지 보는 방법입니다.

# 댓글 경로에 @Transactional 복원
ModerationOutsideTransactionTest > the moderation call does not hold a database transaction() FAILED

# 글 경로에 @Transactional 복원
ModerationOutsideTransactionTest > creating a post also screens outside a transaction() FAILED

글과 댓글 경로에서는 해당 가드만 빨간불이 됐습니다. 그런데 투표 첨부 경로는 달랐습니다 — 뮤테이션이 처음엔 초록불이었습니다. staleness 가드가 겨누는 조건이 테스트 안에서 만들어지지 않았기 때문이고, spy 의 onScreen 훅으로 검열 구간에 행을 바꿔 조건을 만든 뒤에야 빨간불을 봤습니다.

여기서 배운 것이 이 글에서 제일 옮길 만한 것입니다. 뮤테이션이 초록불이면 코드가 안전한 게 아니라, 가드가 겨누고 있지 않은 것입니다.

이 글이 주장하지 않는 것#

  • 성능 수치가 없습니다. 부하 테스트를 하지 않았고, “몇 배 빨라졌다”고 말할 근거가 없습니다. 바뀐 것은 코드의 성질(트랜잭션이 외부 호출을 기다리지 않게 된 것)이고, 그것이 지연이나 처리량으로 얼마가 되는지는 재지 않았습니다.
  • “최대 10초”는 설정값입니다. 외부 호출에 걸어 둔 read timeout 이고, 요청마다 실제로 그만큼 점유했다고 측정한 값이 아닙니다.
  • 장애가 난 적은 없습니다. 출시 전 구조 점검에서 나온 것이고, 이 경로가 실제로 고갈되는 것을 관측한 기록은 없습니다.
  • 커넥션 풀러가 쓸모없다는 이야기가 아닙니다. A 형 고갈에는 정확히 맞는 도구입니다. 이 글이 말하는 것은 B 를 앓는 상태에서는 앱 커넥션 1개당 DB 커넥션 1개가 되어 값을 못 한다는 것뿐입니다.
  • 벤더별 커넥션 상한 수치는 쓰지 않았습니다. 확인하지 않은 값입니다.
  • 핀 유발 패턴 목록이 완전하지 않을 수 있습니다. 풀러와 버전에 따라 다르고, 여기서는 이 코드에 그 넷이 없다는 것만 확인했습니다.

마치며#

정리하면 이렇습니다.

  • 커넥션 고갈의 원인은 개수와 점유 시간 두 가지이고, 증상이 같아서 헷갈립니다.
  • 커넥션 풀러는 개수 문제를 고치는 도구입니다. 점유 시간 문제에서는 앱 커넥션 1개당 DB 커넥션 1개가 되어 줄여 줄 것이 없습니다. 이건 제품의 한계가 아니라 트랜잭션 풀링이라는 방식의 정의에서 나옵니다.
  • 그래서 순서가 있습니다. 트랜잭션을 짧게 만드는 것이 나머지 전부의 전제입니다.
  • 도구를 도입하기 전에 이 코드에서 그 도구가 동작하는지 확인하는 절차를 넣으면, 도입하고 나서 알게 될 일을 미리 알 수 있습니다.

마지막으로 한 줄만 남긴다면 이겁니다. 증상이 같다고 원인이 같은 것은 아니고, 도구는 원인 하나에만 맞습니다. 그리고 잘못 고른 도구의 진짜 비용은 돈이 아니라, “이제 대비했다”는 믿음입니다.
