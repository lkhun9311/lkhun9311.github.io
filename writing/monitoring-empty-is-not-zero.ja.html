空のリストを 0 台として公開してはいけませんでした
対象が無くて空なのと、取れなくて空なのが同じ形で届きます。社内クラウド管理コンソール · 連載「統合モニタリング」③

社内クラウド管理コンソールの backend を作っています。 ②編でダッシュボードの計算を リクエスト経路の外に移しました。同じパターンを物理ノード画面にそのまま移せばよさそうでした。

移す途中で問いが一つ出て止まりました。 メトリックのクエリが空のリストを返したとき、それを「ノード 0 台」として公開してよいのか。

いけません。本当に対象が無くて空のこともあれば、収集が失敗して空のこともあります。 二つを分けないと、障害が起きた瞬間に正常だった画面を 0 台で塗りつぶします。

この記事の想定読者#

  • 最後の正常値を見せる画面（last-known-good）を作ろうとしている方
  • 「結果が空だった」を正常とするか失敗とするか決める必要がある方
  • 障害時に偽の 0 · 空の画面 · 終わらないローディングのどれを避けるか選ぶ方

どんな内容ですか?#

  • 同じ serve-stale のパターンを移しましたが、「空」の意味が画面ごとに違いました。
  • 空の結果を五つに分けました。二つだけを新しい値として公開し、 残りは最後の正常値を保ちます。
  • 値と収集の状態を別々に載せて送ります。それではじめて 「最後の値は見せるが、いまの収集は失敗した」という画面が作れます。
  • 中央値 3,938ms が 23ms になりました。

社内製品なので、コードや画面をそのまま載せていません。製品名・顧客名・内部アドレスは外し、 構造と判定の規則だけを残しています。

⚠️ この編には、最初にできていなかったことが入っています。 物理ノードの実装では、この五つの分岐が完全ではありませんでした。 「取得は成功したが結果が空」を正常と見る余地が残っており、それを ⑤編の共有 cache の作業でようやく共通の判定に引き上げました。

同じパターン、違う問い#

構造はダッシュボードと同じです。後ろで回る worker が 15 秒ごとに完成スナップショットを作り、 新しい接続には最後の値をすぐに送ります。改善前の最初のデータはこうでした。

ダッシュボードより計算の範囲は小さいのに、利用者が見る遅延はやはり秒単位でした。

物理ノードにはダッシュボードに無い性質があります。 「いま何台か」そのものが画面の中身です。だから「空の結果」がそのまま「0 台」と読まれます。

「空」には意味が五つありました#

新しく収集したものが空でも、無条件には公開しませんでした。インフラの構造が読めたか、 メトリックの取得が成功したか、期待する対象の数とマッチした標本の数がいくつかを 一緒に見ました。

if インフラの構造が読めなかった:   INFRA_UNAVAILABLE
else if メトリックの取得に失敗:    FETCH_FAILED
else if マッチした標本 > 0:        FRESH
else if 期待する対象の数 == 0:     EMPTY_VALID
else:                              NO_VALID_METRICS

分けてしまえば規則は短いです。FRESH と EMPTY_VALID は新しい値として 公開します。残りの三つは最後の正常値をそのままにして、劣化状態と失敗時刻だけを 更新します。

値の世代と最後の試行の結果を分けておくのが要点です。 古いデータを新しいデータのふりをさせずに、画面も空にしないで済みます。

到着の順序もデータです#

接続の直後に cache された値が出て、ほぼ同時に新しい配信が届くことがあります。 非同期リスナーの実行順序は保証されないので、より古い応答が新しい配信より遅く 届くことがあります。すると画面が巻き戻ります。

ここで HH:mm:ss の文字列をチャートのキーに使うだけでは足りません。 同じ秒に二つの世代が作られることがあり、プロセスが再起動すると時計が巻き戻ることも あります。表示用の時刻、並べ替え用の世代番号、実行間隔用の単調増加時間を 別々の値として持ちました。

値と信頼度を別々に描きます#

最後の正常値を見せているあいだ、利用者がそれを最新だと誤解してはいけません。 そこで payload にこの四つを別々に載せました。

  • データとそのデータが作られた時刻
  • 最後の収集試行の状態と時刻
  • 前の値を引き継いでいるかを示す劣化表示
  • 接続の寿命の中で順序を判定する世代番号

フロントエンドは劣化表示が立っていれば既存の値を保ち、古いことも一緒に見せます。 劣化表示が立っておらず結果が空のときだけ、本当の 0 台として描きます。 この区別が無いと、「障害を 0 として表示する」か「正常な 0 を過去の値で隠す」の どちらかは必ず起きます。

この記事が主張しないこと#

  • 運用統計ではありません。最初のデータの遅延を見る逐次 harness であって、 同時利用者の負荷試験ではありません。
  • この編の寄与だけを測っていません。表の「改善後」には⑤編の共有 cache が 一緒に入っています。
  • この五つの分岐が最初から完全だったとは言いません。 物理ノードの時点では「取得成功かつ結果が空」を正常と見る余地が残っており、 ⑤編でようやく共通の判定に引き上げました。
  • last-known-good が常に正しいという話でもありません。 データの古さを隠せば、可用性と引き換えに長く嘘をつくことになります。

おわりに#

  • 「空」は観測ではなく、解釈が要る値です。 対象が無くて空なのと、取れなくて空なのは同じデータ構造で届きます。
  • 値と収集状態を分けてはじめて正直な画面になります。 「最後の値は見せるが、いまの収集は失敗した」は、二つを混ぜたら書けない文です。
  • 到着順で最新を判定すると画面が巻き戻ります。 作った順を値に載せる必要があります。

最後に一行だけ残すなら、これです。 モニタリング画面が決めるべきなのは最新の数字ではなく、観測が失敗したときに 偽の 0 と空の画面と終わらないローディングのどれを避けるかです。
