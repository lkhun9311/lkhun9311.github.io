Thirteen Write-Ups, and Two Results That Came Out Backwards
A parallel version that measured slower, and a review that found nothing to fix on a 6.8-second screen.

Thirteen write-ups about backend work on an internal cloud admin console for an OpenStack-based private cloud: eight parts on slow screens and five on unifying the monitoring path. The single most useful thing in them is not any one fix.

It is that two results came out the opposite way round from what I expected, and neither was caught by reading the code.

Four screens each looked like a slow query, and none of them was. The causes were a lock held across a network round trip, a saturated swap with 1,021 rows still marked deleted, a cache that was written and never read, and authentication repeated once per project. The run was split into six configurations measured one at a time, which is the only reason one of the fixes could be identified as harmful on its own.

Who this is for#

  • You own a control-plane screen that fans out to several infrastructure APIs
  • You are about to report "we made it N times faster" and have to say which change did it
  • You have concluded a review with "nothing worth changing here"

None of them was the query#

The screens all render lists or time-series, so the query is the first suspect every time. In four consecutive cases it was the wrong one.

The pattern is not "queries are fine". It is that a screen's latency lives wherever the request waits, and a query is only one of the places it can wait. Three of the four above were waiting on something the database never saw.

Six runs, not two#

Four changes went into the volume list. Measuring before and after would have produced one true and useless sentence: p99 went from a ten-minute timeout to 23 ms.

So the run was split into six configurations under one declared load profile, with the generator producing the plan from constants rather than from a form filled in by hand. Adjacent rows then differ by one variable, and a pair can be read.

That is what made the next section possible. A harmful change is invisible inside a win unless something isolates it.

Two results came out backwards#

The first is the parallel version. Replacing a sequential loop with parallel calls is the obvious prescription, and with the cache configuration held fixed it moved p99 from 42.6 s to 79.0 s. The external call sat inside computeIfAbsent, so the Bin stayed locked for the whole round trip and the threads queued in front of it instead of working.

The second is worse, because it was a conclusion rather than a change. A performance review looked at three monitoring screens and found no case for adding a cache. The reasoning was sound for the path it examined: a periodic refresh every fifteen seconds is already cheap. It was the wrong path. The boundary a user waits on is the first data after connecting, and measuring that one gave 6.8 s.

The correction sits on top of the original article rather than replacing it, because deleting the wrong conclusion would delete the evidence of how it was reached.

What unifying the monitoring path added#

Fixing the three screens one at a time left them each fast and each collecting the same source separately. Merging the three caches into one removed the duplicate collection and immediately produced a regression: opening one screen erased another's last value, and re-entry measured 5,115 ms.

The rules that separation had been keeping by accident all had to be written down. Two of them are worth carrying to any shared cache:

  • A partial failure is carried per item. One source failing must not roll back the items that succeeded.
  • An Empty List Could Mean Zero Nodes or a Failed Query Nothing there and nothing fetched arrive in the same shape, and publishing the second as the first turns an outage into a confident report of zero nodes.

What this does not claim#

  • Product names, versions and customers are not written here. Every number was measured in an internal test environment under a declared load profile, mostly single-user sequential for the monitoring work. They are not a capacity statement.
  • These are test-environment numbers. Synthetic load in an isolated environment under a declared profile. Real user distributions, data volumes and networks differ.
  • Each configuration was measured once. No repetition, no variance, so only multiple-fold differences are used as evidence anywhere in the series.
  • Parallelism is not the problem. Parallelising code that holds a lock across I/O is. None of the six configurations removed that condition, so the series cannot say what parallelism is worth once it is gone.
  • The monitoring measurements are single-user sequential. They say nothing about how many concurrent users the screens hold.
  • Nothing here is anonymised code. Snippets are quoted with internal identifiers removed; screens and product names are not reproduced.

Wrapping up#

  • Measure the boundary the user waits on. A review can be internally correct and still be about the wrong path, and that failure looks exactly like a finished review.
  • Ship four changes, learn one fact. Splitting a run into configurations is what turns "it got faster" into "this one did it, and that one hurt".
  • A slow list is rarely a slow query. Look for where the request waits: a lock held across I/O, an authentication inside a loop, a cache written and never read.
  • Separation keeps contracts by accident. Merging caches is not a refactor; it is the moment those contracts have to be written down.

The two results that came out backwards are the only two that taught me anything transferable, and both of them needed a run that was designed to be able to disagree with me.
