I Fired Every Refusal Path in a GPU Experiment Harness for Real
Only after four gates were standing could I call this tool's numbers evidence.

Numbers out of an experiment tool are worth something only under one condition. The cluster has to be proven clean when the run starts and clean when it ends.

This harness could not produce that proof. Every non-preview run was being refused, and the reason was that the validity gates were unimplemented. A lot of care had gone into teardown, and teardown was not where the bottleneck was.

At first I thought the observation continuity gate was largely built. The file was there and so were its tests. That judgement was wrong, and I wrote about that in the previous post. This one is the record of what came after: four gates put up, and each refusal path fired for real.

Who this is for#

  • Anyone who builds their own experiment or benchmark tooling
  • Anyone with guards in place who wants to know what those guards actually catch
  • Anyone separating a property of the system from an artifact of the instrument
  • Anyone who needs a boundary between runs in a cluster-based experiment

There were numbers, but no evidence#

There are four gates. Was observation unbroken, did the environment qualify at the start, did that qualification hold for the whole run, and did the evidence for all of it reach the record?

After fixing observation continuity I measured the size of the distortion. The same trace ran on the same cluster through the old collector and the new one.

The exit was guarded and the entrance was not#

Teardown proves that nothing is left behind when a run ends. Nothing was looking at the start.

Labels and taints only block future placement; they do not evict what is already there. A terminating GPU Pod left by an earlier run's stuck teardown still holds a device, and a taint cannot see it. So a check went in right after the worker is held and before the first create: capacity, foreign consumers, node readiness, with the observation written into the record.

The capacity requirement is derived from the fixture. Hard-coding it means the check drifts silently when the fixture changes. I first derived it from the sum of the quotas, and review pointed out that the largest single request is also a bound. A job lands whole on one node, so a three-device request cannot run on a two-device node however generous the total is. It now takes the maximum of the two bounds and records which one bound it.

Two checkpoints leave the middle open#

Exclusivity was checked at exactly two moments, hold and release. If a third party lifts the taint in between, admits other work, and puts it back before release, both checks pass. The schedule that was measured is contaminated anyway.

So I lifted the taint mid-run and put it back exactly as it was. The check at release passed cleanly, and only continuous observation caught the one violation. The record says the installed values diverged across four node versions, and the run was invalidated.

One place on the evidence side was empty too. Entry and persistence both wrote their own evidence into the record; only observation continuity did not. Without per-stream baselines, establishment times and end reasons, an auditor holding the stored record cannot tell complete observation from truncated observation. So the verdict is derived from fields rather than from free text. A verdict that parses a sentence misses when one reason overwrites another; a verdict derived from the evidence does not.

Making the contrast itself a qualification#

What this lab measures is reclamation. One arm is a workload that honours the termination signal and the other ignores it, and the difference is a single shell command. If the cluster fails to deliver the signal properly the two arms collapse into one, and the numbers still look fine.

# Honours the signal: leaves as soon as it arrives
sh -c "trap 'exit 143' TERM; sleep D & wait"

# Ignores it: stays until the grace period runs out
sh -c "sleep D"

# Qualification. The two lines must end differently for the contrast to hold here
#   honours  1024ms  exit 143 (TERM)
#   ignores 31138ms  exit 137 (KILL)

The point is that the contrast itself became a qualification. Watching only for the honouring arm to leave quickly means a runtime that kills everything immediately passes for the wrong reason. The ignoring arm holding out until the grace deadline has to be seen as well.

And this runs once per combination rather than as a ritual before every run. The same image, cluster, runtime and harness give the same answer.

The most valuable output of this work was not code but a taxonomy of defects. The same shapes kept arriving.

The last row came up most often. A fake client hid reality five times, and one of those meant a conditional delete guard had never executed once.

Limits: what this post does not claim#

  • ⚠️ Having gates up is not the same as being able to trust this tool. A gate speaks only within what it looks at.
  • The latency figures come from one run each on one cluster. They were not repeated, so they are not a distribution.
  • The termination canary probes Pods it creates itself. The other path the experiment's workload takes is not exercised by it, and the record says so on its own.
  • The nine shapes come from this one piece of work and are not a general frequency ranking.
  • These runs were on a kind cluster with a fake device plugin. Not real devices.

Wrapping up#

The conclusion is one line. Validating a guard by reading it tells you nothing about what that guard actually catches. Cutting one verb out of a role and injecting a defect into a file made the refusals fire, and that is when the holes in the guards themselves showed up.

And once the tool is fixed, the size of the fix has to be measured. Put a row inside the same run that should not move, and that row becomes the control.

Part two is about running the comparison for the first time with that fixed tool.
