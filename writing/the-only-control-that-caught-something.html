The Only Control That Has Ever Caught a Cost Error

Scope. Cost and account operations on the AWS lab account behind a personal project, a Kubernetes-native GPU control plane. The figures come from mixed sources — $14.56 and $0.40 come from billing and accounting, the ~$8 is my own estimate, and $0.05 and $0.18 are billed time multiplied by the hourly rate. Either way this is personal-lab scale, not production. Account and policy identifiers are omitted.

On a personal project that rents GPUs, the frightening failure is not a wrong experiment. It is leaving something switched on. So I built several layers of control: a service control policy, a TTL scale-down schedule, a monthly budget, ephemeral apply and destroy.

After a month of running it, the rehearsal had caught a policy defect and the TTL had proved it fires. But exactly one of them had ever caught an error in the cost itself. And that one was not in the code.

80% is not an early warning#

The monthly budget ceiling is thirty dollars. The threshold a budget notification defaults to is 80% of that. But this project's spend arrives in three-hour bursts. A paid GPU session starts and finishes within an afternoon, and a month-scale threshold says something only after that session is already over.

So the early warning sits at 10%. On a thirty dollar budget that fires at three dollars, roughly the price of one paid session. Then the first session of a month reports what it cost while the next one can still be reconsidered.

The question when choosing a threshold is not "what percentage is reasonable" but "when this fires, is there still a decision left to change?" At this spend shape, 80% does not satisfy that.

Chasing the gap led to NAT gateway data-processing charges. I had been counting instance hours and the EKS charge, but the cost of bytes crossing the NAT was not in my estimate at all.

Why it was invisible is clear enough. My estimate was a list of what I had switched on — the GPU instance, the EKS control plane, the NAT gateway — things with an hourly rate. But a NAT gateway bills an hourly rate and a rate per byte processed, and that second line grows every time an image is pulled. A list of what you switched on does not count what the things you switched on are doing.

And Terraform nearly deleted it#

That alert was created by hand in the console on 2026-08-31 and never written into the configuration.

Days later, running a plan before adding image mirror repositories, the notification block showed up as absent from the configuration and present in the account. Applying that plan would have removed it silently, as a side effect of an unrelated change.

What was about to be deleted happened to be the only control that has ever caught a cost error in this account.

This is a shape the project keeps producing: a value living in one place and not the other, with nothing comparing them. Something made quickly in a console is not in the code, and a tool that treats the code as the truth sees anything absent from it as something to remove. So when the alert was moved into Terraform, the reason it exists and the fact that it was nearly deleted went in as a comment beside it — for whoever next considers removing that block.

Moving the same 15.6GB for free#

Once the NAT line was visible, the shape of the next experiment changed.

The question on 2026-09-04 was about vLLM scheduler settings. No gateway, no Kubernetes — one instance is enough. And then a single fact decides most of the cost.

An instance in a default subnet talks through the internet gateway on a public IP, and inbound transfer is free.

Until then paid runs had been pulling container images and model weights — about 15.6GB for one cold node — across a NAT at $0.059 per GB. (The NAT data-processing charge for the first three sessions came to roughly 92GB and $5.43 in total. Three runs of 15.6GB does not account for that, and I did not reconcile the gap.) Moving to one instance in a public subnet removed that line entirely, and that day's experiment finished at about $0.40.

What changed was not an algorithm but the path the bytes take. And that path only became visible because an alert forced me to read the bill by line item.

The rehearsal that failed, twenty minutes and five cents#

Before the first paid GPU session I ran a rehearsal with no GPU switched on: apply the cluster and immediately destroy it. The point was not performance but whether the procedure reaches the end.

The apply failed, on a service control policy I had attached the day before.

Error: creating EC2 Launch Template: UnauthorizedOperation
  ec2:CreateLaunchTemplate ... explicit deny in a service control policy

The offending statement was meant to restrict instance types to an allow list.

{
  "Effect": "Deny",
  "Action": ["ec2:CreateLaunchTemplate", "ec2:CreateLaunchTemplateVersion"],
  "Condition": { "StringNotLike": { "ec2:InstanceType": ["t3.*", "g4dn.*", "g5.*"] } }
}

Two things stacked.

One. A negated IAM condition operator is true when the key is absent. StringNotLike does not only mean "this value differs from the list"; it is also satisfied when the key is not there at all.

Two. An EKS managed node group carries the instance type on the node group, not in the launch template. So ec2:InstanceType was absent.

Together, the statement did not restrict instance families — it blocked the service. g5.* was in the allow list and a g5 node group still could not be created.

Had that policy defect first appeared during a paid GPU session, I would have been debugging it with the card running. The value of a rehearsal is not that it succeeded; it is that the failure happened somewhere cheap.

The alarm nobody had heard ring#

The same week I created a schedule that scales GPU nodes to zero after a fixed interval, and wrote down "there is a backstop now".

The next day I traced what that sentence rested on and found nothing. All I had checked was that the schedule read ENABLED. That means AWS accepted it — not that it emits a call when the time comes. Whether the role assumption works, whether the policy permits the call, what shape the payload has: none of it verified.

But verifying it properly means renting a GPU and waiting for the interval to pass. Spending money to verify the thing that exists to control spending.

The way out was in where the failure lands. What I want to know is whether a call goes out, not whether it succeeds. Which means the target does not have to exist.

I scheduled it two minutes out against a cluster and node group name that do not exist, with zero retries and delete-on-completion.

The first piece of evidence was the schedule disappearing. Delete-on-completion happens only after the call has run; a schedule that never fired stays.

The second was the audit log.

principal : assumed-role/gpu-platform-ttl-scaledown/...
request   : {"scalingConfig": {"minSize": 0, "desiredSize": 0}, ...}
error     : ResourceNotFoundException

The role was assumed, the policy let the call through, and the payload matched what the script writes. The only thing that failed was the target, and the target was deliberately a name that does not exist so that nothing would be spent. The cost was zero dollars.

Stating the verified boundary exactly: the schedule assumes its role on time and emits a call of that shape. That a real node group then goes to zero is not something this experiment showed.

The only way in was root#

Two days after creating the organisation, signing in to the management account to open a credits support case, root MFA did not match. For those few minutes there was no way through the administrative path I had built to the organisation, the SCPs, or Identity Center.

To be exact: AWS does have an alternative verification path using the registered email and phone, and I knew it existed. But I never confirmed that it works — the sign-in eventually succeeded, so it was never needed. An emergency path you have not tested is hard to count as one you have.

Not because the configuration was wrong. Because the way in I had built was exactly one. Setting up Identity Center, I assigned the permission set to the lab account only.

Not assigning the management account was an omission rather than a decision. I had thought "no workloads live there, so there is nothing to do there" — but managing the organisation, the SCPs and Identity Center is exactly what happens there. An account with no workloads is not an account that needs no access.

Fixing it took three minutes. Noticing took two days, and what made me notice was an MFA code happening not to match.

What this does not claim#

  • Not a claim that the TTL prevented a cost incident. What was verified is that the schedule emits a call on time; the target was deliberately a name that does not exist. And the control's scope is scaling a node group to zero, not capping account-wide spend.
  • $0.05 and $0.18 are not bill line items. They are billed time multiplied by the hourly rate. $14.56 and $0.40 come from billing and accounting, but this article did not reconcile either against the billing ledger separately.
  • The SCP defect was not fixed by patching the condition. That call cannot be restricted to instance families through that condition key, so the statement itself was removed.
  • The SCP defect is specific to this organisation's setup. That an absent condition key satisfies a negated operator is general; which key is absent depends on the service and the call path.
  • This is personal-lab scale. Half the reason the controls were useful here is that the spend is small enough for a single line item's error to stand out.
  • A budget alert is a detective control. It does not prevent spend; it reports it. The claim here is not that it is powerful, but the observation that of several layers, it was the one that caught something.

What is left is one line. Building a control and confirming that the control fires are different pieces of work, and most controls get onto the list without the second one. And the one on my list that caught a cost error was the simplest — an alert that put my estimate and the real bill side by side.
