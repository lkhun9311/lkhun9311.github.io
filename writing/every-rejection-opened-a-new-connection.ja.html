Go ベンチ Harness が拒否応答884件に TCP Connection を884本開きました
429 応答の Body を読まずに閉じたため、Connection を一度も再利用できませんでした。

2026年8月15日にブランチを上げると、プッシュフックが codex と Claude のレビューを回し、指摘が10件出ました。そのうち2件が 測定ツールそのものの欠陥でした。この記事はそのうちの1つを扱います。

指摘は短いものでした。ベンチ Harness の Send が、200 以外の応答の Body を読まずに返しているというものです。 同じファイルのコメントには、Connection Pool に効果がある根拠として 431 → 6 という測定値が書かれていました。 私はその根拠を開いてみましたが、根拠が測ったトレースには拒否応答が1件もありませんでした。

先に留保をひとつ置きます。この記事が測ったのはサーバーが受け付けた TCP Connection の本数です。新たに生じた Handshake が Harness の報告する遅延をどれだけ膨らませたかは測っていません。残りの留保は「この記事が主張しないこと」に まとめました。

この記事の想定読者

  • Go の net/http クライアントで負荷生成器やベンチ Harness を作っている方
  • 429 のような拒否応答が多く出るシステム(Rate Limit、入場制御)を測っている方
  • コードコメントや文書に測定値を根拠として書いている方

どんな構成ですか

個人プロジェクトとして作っている GPUaaS プラットフォームには LLM の要求を受ける Gateway があり、その中に入場ガードが あります。ガードは要求の Body を読んで送り先の Backend を決め、vLLM へプロキシする手前に立ちます。ガードは 拒否することで容量を守ります。ガードが受け付けないと決めた要求は 429 で返ります。

ベンチ Harness は1つの要求トレースを、ガードを切った設定、負荷を見ない固定上限、KV Cache の圧力を見るガードに まったく同じように再生し、Premium 要求の TTFT p99 を比べます。

この記事の Connection 数は、ガードではなく Harness がつながったサーバー側で ConnState を使って数えました。

最初は Connection Pool がすでに検証済みだと思っていました

Send と同じファイルのコメントは、Pool の効果を数字で語っていました。サーバー側で ConnState を使って 受け付けた Connection を数えると、Pool を入れる前が431本、入れた後が6本だったという記録です。8月8日に kind で Harness を Gateway なしで Stub サーバーに直接つなぎ、要求884件のトレースを legacy と pooled で再生して測った値です (hack/m5b-gateway-path-evidence.log)。テストも通っていました。数字があり、方法があり、テストが緑なので、 検証済みだと読みました。

その数字を出した記録を開いてみると、すべての Arm で 429 が0件でした。done == total、つまり送った要求が すべて完了していました。431 → 6 は拒否が一度もないトレースで測った値で、レビューが指摘した経路を覆ったことは ありませんでした。

結論から申し上げます

同じ方法(サーバー側の ConnState による計数)で、要求884件がすべて拒否されるトレースを同時実行数20で測り直しました。 要求数は 431 → 6 のトレースと同じですが、コミットメッセージは2つを別のトレースとして記しています。

要求884件がすべて拒否されるトレースで、モードごとにサーバーが受け付けた Connection 数の修正前と修正後。
モード修正前修正後
legacy884884
drain-only884357
pooled(実際のランが使うモード)88422

実際のランが使う pooled モードが、要求1件ごとに Connection を1本開いていました。Pool を有効にしていても legacy と区別がつきませんでした。拒否のないトレースの「直す前」の値431よりも多かったのです。200 以外の応答の Body を読み切るように直すと22本になりました。直す前との差は40倍です。

測定条件もあわせて書きます。

884件がすべて拒否応答だったことは、修正コミット d450877 のメッセージと、同じコミットが入れたコードコメントが このトレースを「an 884-rejection trace」と書いていることから取りました。

モード名はこの修正より前からありました。3つのモードは8月8日のコミット 651140c で生まれ、431 → 6 を 測ったログもすでに3つの名前で回っていました。修正前のコードで Body を読み切る場所は 200 応答を読む readStream だけで、200 以外の応答は読み切らずに返していました。そのため拒否だけが出るトレースでは drain-only も読み切る応答が なく、legacy と同じ884になりました。

Body を読まずに閉じると Connection は Pool に戻りません

Go の HTTP Transport は、応答の Body を最後まで読まないまま Close() が呼ばれると、その Connection を再利用 できません。すると次の要求は TCP Handshake からやり直します。

修正前後の Send で 200 以外の応答を扱う部分です。どちらもその日のコミットのコードで、修正後のほうはコメントを 除きました。resp.Body.Close() はどちらのコードでもこの手前で defer されています。

// before: d450877^
if resp.StatusCode != http.StatusOK {
	kind := "http"
	if resp.StatusCode == http.StatusTooManyRequests {
		kind = "rejected"
	}
	return SendResult{HTTPStatus: resp.StatusCode, ErrorKind: kind}
}

// after: d450877
if resp.StatusCode != http.StatusOK {
	if h.drain {
		drainForReuse(resp.Body)
	}
	kind := "http"
	if resp.StatusCode == http.StatusTooManyRequests {
		kind = "rejected"
	}
	return SendResult{HTTPStatus: resp.StatusCode, ErrorKind: kind}
}

drainForReuse は Body を最大 8KB まで読んで捨てます。その範囲で終わりに届かなければ、その Connection 1本だけが 再利用をあきらめます。

問題は、この Handshake のコストが測定対象ではなく測定ツールの側で生じることです。そしてそのコストは Harness が 報告する遅延の中に入ります。ガードが拒否した要求の遅延にも、ツールが Connection を新しく開く時間が混ざります。

拒否は例外ではなく、この Harness が最も多く通る経路です

この Harness にとって 429 は例外的な状況ではありません。入場ガードは拒否することで容量を守り、ガードを実際に働かせる ランはほとんどがこの経路を通ります。

そのためこの欠陥は、ガードが多く拒否するランほど多くの要求にかかります。反対に、Pool の効果を示した根拠は、ガードが 一度も拒否しなかったトレースから出ていました。

drain-only が別にある理由

表で drain-only は357本です。このモードは、Body を読み切る修正と Pool の設定を切り離し、それぞれが Connection 数を どれだけ減らすかを見るために置いたものです。ひとまとめに「884 → 22」とだけ書くと、どちらがどれだけ減らしたかが 残りません。

3つのモードの定義は internal/bench/httpsender.go の SenderConnForMode にあります。legacy は Transport を別に持たず Go の既定値(Host あたりのアイドル Connection 2本)を使い、Body を読み切りません。drain-only は 同じ既定の Transport で Body の読み切りだけを有効にします。pooled は Host あたりのアイドル Connection の上限を トレースから導き(到着率 × 要求の Timeout、トレースの長さを超えず2を下回らない)、全体のアイドル上限をなくしたうえで Body の読み切りを有効にします。

そのため drain-only と pooled は Body の読み切りが同じで、アイドル Connection の上限だけが違います。この トレースで pooled の上限がいくつだったか、何回測ったかは記録にないので、357と22の差を上限の1つ1つに割り振る ことはしません。

コメントに証拠の範囲を書きました

数字を直すだけでは同じことが繰り返されます。次に誰かが 431 → 6 をまた引用するかもしれないからです。そこで drainForReuse のコメントにこの文を入れました(コミット d450877)。

Read that trace's scope before quoting those numbers: every arm in it recorded ZERO rejections, so they describe the all-200 path only.

(「この数字を引用する前に、そのトレースの範囲を読め。その中のすべての Arm が拒否0件だったので、この数字はすべてが 200 の経路についてしか語らない。」)

431 → 6 は私が書いた証拠でした。今回その数字自体を測り直してはいません。問題はその数字を別の経路の 根拠として読んだことにありました。

431 → 6 はコードコメントの外にも載っています。8月8日にコミットした証拠文書 hack/m5b-gateway-path.md が 「431 connections down to 6, a factor of 72」と書いています。8月15日の修正はこの文書に触れておらず、その後も変わって いないので、範囲を書いた場所はコードコメントとコミットメッセージだけです。公開した記事(lkhun9311.github.io) にはこの数字はありません。

同じ日に出た欠陥4件が同じ形でした

その日に見つけた欠陥4件を並べると、1文にまとまります。証拠が、測ろうとした経路を覆っていませんでした。

4件の欠陥にはどれもテストがあり、通っていました。欠けていたのはテストではなく、テストが覆う範囲と主張する範囲が 同じかを確かめる習慣でした。

3行目も短く書いておきます。reportRun は読み戻しがレコードを拒否しても、結果と台帳をすべて stdout に出力したあとで stderr に「上のものは引用するな」と書いていました。シェルのリダイレクトがすでに持っていったものを、読み手に見なかった ことにしてくれと求めていたわけです。出力してから取り消すのではなく、検証に失敗したらすべてを stderr に送るように変えました。 検証に失敗した実行で、stdout は929バイトでイベント0行、stderr は2,696バイトでイベント13行になりました。

1行目は同じ日の先の作業で出た欠陥です。watchstream.go には基準の List を受け取り、その resourceVersion から watch を 続けるコードとテストがありましたが、本番コードにその関数(startWatchStream)を呼ぶ場所がありませんでした。実際に 動いていたのは、基準の List なしに「今」から watch をかける collector.watch でした。

この記事が主張しないこと

  • 遅延がどれだけ膨らんだかは測っていません。Handshake が報告された遅延に入るというのは動作原理からの予測で、 修正前後の遅延を並べて測ってはいません。
  • 繰り返し回数は分かりません。コミット d450877 のメッセージにはモードごとの修正前・後の値が1組だけあり、 同じコミットのコードコメントと日誌2つにも繰り返し回数はありません。そのランの生ログはリポジトリになく、セッションの記録も 残っていません。
  • すでに報告した遅延の数字が誤っているとは言えません。この欠陥があった間に出した数字のうち、どれが拒否の多いランだったかは この記事の根拠からは分かりません。
  • 22本が適切な値だとは言えません。同時実行数20という1つの条件で数えた本数です。別の同時実行数や別の拒否率では測って いません。
  • 拒否トレースのランの生データはありません。884件がすべて拒否だったことと表の6つの値は、コミットメッセージとコード コメントから取りました。そのランの生ログ、トレースファイル、拒否を返したサーバーの設定はリポジトリにありません。
  • Go のバージョンに依存しないとは言えません。Transport の再利用条件を Go のバージョンごとに確かめてはいません。

おわりに

  • 200 応答しかないトレースでは、拒否経路の Connection 再利用は測れません。431 → 6 は拒否が0件の トレースで測った数字でした。
  • Go のクライアントは、200 以外の応答の Body も最後まで読んで閉じてはじめて Connection を再利用します。読まな かったとき、pooled モードは要求884件に Connection を884本開きました。読むように直した後は22本になりました。
  • 入場ガードを測るツールにとって、拒否は本来の経路です。ガードが多く拒否するランほど、ツールの欠陥がより多くの要求に かかります。
  • 数字を根拠として書くときは、その数字を測ったトレースの範囲を横に一緒に書きます。

測定ツールに根拠の数字を書いているなら、その数字を測った入力に今測ろうとしている経路が入っていたかを一度開いて 確かめることをおすすめします。通るテストと合っている数字があっても、2つが同じ経路を見たことはないかもしれません。
