스케줄을 지워도 실행 이력은 지우지 않았습니다
현재 설정과 과거 실행 증거의 수명을 분리해 삭제 뒤에도 당시 동작을 설명할 수 있게 했습니다.

2026년 9월

스냅샷 실행 이력 설계 연작의 한 편입니다. 이번 주제는, 스케줄이 사라진 뒤에도 실행의 증거는 남아야 한다는 것입니다. 전체 개요와 글 순서를 먼저 볼 수 있습니다.

Scheduler 하나를 지운 뒤 그 Scheduler가 지난주에 왜 실패했는지 물었습니다. 초기 설계에서는 답할 수 없었습니다. 부모 행을 지우면 외래키 cascade와 애플리케이션 삭제가 실행 이력까지 함께 지웠기 때문입니다.

처음에는 그것을 정합성으로 봤습니다. 화면의 진입점이 사라지면 이력은 도달할 수 없는 orphan이 되고 orphan을 남기지 않는 것이 깔끔해 보였습니다. 하지만 실행 이력은 현재 설정의 부속물이 아니라 과거 실행의 증거였습니다. 부모의 수명에 묶는 순간 증거가 운영 편의보다 먼저 사라졌습니다.

리뷰 뒤 저는 설계를 뒤집었습니다. 실행 시작 시 설정과 프로젝트를 캡처하고 이력 테이블에는 의도적으로 외래키를 두지 않았습니다. 이 글은 실행 결과 모델 다음으로, 변경·삭제되는 현재 상태와 보존해야 할 실행 기록을 어떻게 분리했는지 다룹니다.

이 글의 예상 독자#

  • Job 이력의 부모가 수정되거나 삭제될 수 있는 시스템을 설계하시는 분
  • FK cascade와 감사 기록 보존 사이에서 선택해야 하는 분
  • 비정규화 JSON과 권한 검사의 장단점을 실제 구현 단위로 보고 싶은 분

처음에는 함께 지우는 것이 정합성이라고 생각했습니다#

초기 테이블은 schedule_id로 Scheduler를 참조하고 ON DELETE CASCADE를 걸었습니다. 서비스도 삭제 전에 deleteByScheduleId를 호출했습니다. 이력 저장 시에는 Scheduler를 다시 읽어 프로젝트를 채우고 이미 삭제됐으면 기록을 건너뛰었습니다.

이 설계는 orphan을 만들지 않지만 삭제와 실행이 경합하면 결과가 타이밍에 따라 달라집니다. 삭제가 먼저 보이면 실행은 끝났어도 이력이 생기지 않습니다. 기록이 먼저 들어가도 뒤의 cascade가 지웁니다. 어느 쪽이 먼저 잠금을 잡았는지가 감사 기록의 존재를 결정했습니다.

삭제 경로는 하나가 아니라 셋이었습니다#

외래키만 제거하면 끝날 것 같았지만 실제 코드에는 세 겹의 삭제가 있었습니다. DDL의 cascade, Scheduler 서비스의 Repository 직접 호출, 별도 History Service의 bulk delete였습니다. 하나라도 남으면 환경이나 호출 경로에 따라 이력이 다시 사라집니다.

현재 상태 대신 실행 시점 설정을 저장했습니다#

부모를 없애면 과거 행의 무엇으로 실행했는가도 잃습니다. Scheduler 이름, 대상, 주기, 보관 개수는 모두 현재 행에 있었습니다. 따라서 FK만 끊으면 이력은 남아도 해석할 수 없는 ID 모음이 됩니다.

실행을 시작해 Scheduler DTO를 읽은 직후 전용 SnapshotScheduleHistorySnapshot으로 설정을 복사했습니다. API DTO 자체를 JSON으로 넣지 않고 필드를 따로 선언했습니다. API 필드가 바뀔 때 과거 JSON의 의미까지 따라 바뀌지 않게 하려는 선택입니다.

가로로 넘겨 표 전체를 볼 수 있습니다.

식별과 대상name, type, target, instance_id, volume_id삭제 뒤 실행 대상 복원현재 대상 재조회

SnapshotScheduleDto schedule = scheduleService.get(scheduleId);
capturedProjectId = schedule.getProjectId();
capturedScheduleSnapshot = SnapshotScheduleHistorySnapshot.from(schedule);

// 이후 실행 중 수정·삭제돼도 시작 시점 값으로 기록
scheduleService.recordRun(run.toBuilder()
    .projectId(capturedProjectId)
    .scheduleSnapshot(capturedScheduleSnapshot)
    .build());

스냅샷을 캡처해 놓고도 저장 서비스가 Scheduler를 다시 읽으면 삭제 경합이 돌아옵니다. 그래서 SnapshotScheduleRunRecord가 프로젝트와 설정 스냅샷을 함께 전달합니다. 저장 서비스는 현재 Scheduler 존재 여부를 묻지 않고 받은 실행 사실을 append합니다.

부모가 없어도 소유권을 검사해야 합니다#

삭제 후 조회를 허용하면서 새 문제가 생겼습니다. 예전에는 Scheduler 행의 project_id로 다른 프로젝트 접근을 막았습니다. 부모가 사라지면 단순히 관리자만 허용하거나, 반대로 소유권 검사를 건너뛰기 쉽습니다.

조회 서비스는 Scheduler가 있으면 현재 프로젝트를 사용하고 없으면 같은 schedule_id의 가장 최근 이력에서 non-null 프로젝트를 찾습니다. 그 값으로 프로젝트 일치 또는 시스템 관리자 여부를 검사한 뒤에만 페이지를 반환합니다. OpenStack 대상 이름 조회 없이 DB 값만 쓰므로 외부 장애 중에도 로컬 이력은 열립니다.

JSON 비정규화가 만든 새 계약#

  • 얻은 것: 부모가 삭제돼도 실행 당시 설정과 소유 프로젝트가 남습니다.
  • 지불한 것: 실행마다 설정을 복사하고 JSON key를 장기 계약으로 관리해야 합니다.
  • 남은 것: 보존된 이력을 찾는 별도 검색 화면과 보존 기간 정책은 다음 문제입니다.

마치며#

현재 상태는 바뀌고 지워집니다. 실행 이력은 그 상태로 이미 무엇을 했는지 남기는 증거입니다. 둘의 수명이 다르면 FK cascade로 함께 묶는 것이 정합성이 아니라 정보 손실이 됩니다.

이력을 오래 살게 하는 일은 FK 하나를 빼는 작업이 아니었습니다. 삭제 경로를 모두 걷어내고 실행 시점 값을 쓰기 경로로 전달하고 부모가 없는 조회의 권한까지 다시 세워야 했습니다.

다음 글에서는 bootable Volume 둘 가운데 실제 Root를 판별하면서 Nova microversion과 SDK session 경계까지 따라간 과정을 다룹니다.
