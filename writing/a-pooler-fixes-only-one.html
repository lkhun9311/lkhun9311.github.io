A Pooler Fixes Only One of the Two Exhaustions

Writing · September 2026 · 8 min read

Other languages 한국어 · 日本語

Scope. This is a record of a pre-launch structural review of a personal project (Kotlin · Spring Boot · managed Postgres, a monolith). Nothing ever broke in production, and there are no load-test numbers. The "up to 10 seconds" below is a configured read timeout on an outbound call, not a measurement that each request actually held a connection that long. The improvement is explained by a change in the properties of the code; this article claims no measured figures.

The review started from a common hypothesis — connections could run dry, so shouldn't we put a pooler (RDS Proxy, PgBouncer and the like) in front?

The answer was not in this codebase, and the reason came from the definition of transaction pooling rather than from any vendor document.

One symptom, two causes#

When connections run dry, what you see is mostly one thing. Pool-wait timeouts, unrelated APIs slowing down together, and Connection is not available, request timed out in the log.

Behind that single symptom there are two causes.

A — too many connections. As app instances multiply, you open instances × pool size connections. Postgres forks a backend process per connection, and an idle one still costs memory. Only some of them are running queries; the rest are just open.

This is why poolers exist. They fold thousands of client connections into dozens of backend ones.

B — transactions stay open too long.

BEGIN → SELECT → [ outbound HTTP call ] → INSERT → COMMIT
                  ↑ holds the connection and runs no query at all

Once concurrent requests exceed the pool size, it runs dry. Here the number of connections is not the problem — hold time is.

And it is not only that path that dries up. Voting, the feed and chart reads all draw from the same pool, so they stall together. What made this particularly sharp in this app was the timing — the growth engine is sharing the result chart, so the day sharing spikes is the day the pool runs dry.

Why a pooler cannot fix B#

The picture of "thousands of client connections folded into dozens of DB connections" is correct. The question is when the folding happens, and that is already contained in the definition of transaction pooling.

Multiplexing happens between transactions. While a transaction is open, the backend connection is pinned to that client. It has to be — a transaction is state, and lending it out mid-flight would break isolation.

Which gives you this — if a transaction stays open for 10 seconds, the backend connection is pinned for 10 seconds, the folding ratio becomes 1:1, and the proxy's benefit approaches zero.

A pooler earns its keep when there are many short transactions. Buying one while suffering from B spends money and changes nothing, and the worse part comes next — you come to believe you are now covered. That belief is what stops the next review.

So there is an order#

The remedy is not one thing but layers, and the layers have an order.

Five layers of remedy for connection exhaustion and what each one is.
LayerWhatNature
①Shorten the transaction — move the outbound call outside itThe only fundamental one. The premise of every other layer
②Admission control — thread and pool caps chosen deliberatelyMakes failure fast and predictable
③PoolerOnly works once ① is done
④Read splitting and cachingThe only layer that makes you use fewer connections
⑤Async offload (outbox)Reduces DB work per request itself

So the code got fixed first. Moving the outbound moderation call out of the transaction was done on three write paths. One of them was worse than the rest — the poll-attachment path was making the outbound call while holding a row lock via for update. It held two resources at once: the connection and the row lock. The post and comment paths went first; the poll path takes its screening input from the locked row, so it needed a staleness re-check and was deliberately deferred, then fixed four days later.

The conclusion in one line: the code change was not an alternative to the pooler, it was its precondition. Once it was fixed, the system was finally in a state where a pooler could earn its keep.

Two numbers nobody chose#

There is a trap in ②. With blocking JDBC, the connection pool is effectively the concurrency cap. However many threads you have, they cannot work without a connection.

This service ran Tomcat threads at the default 200, and the connection pool had no configuration at all — the framework default was the service's capacity. So the remaining requests wait for a connection and fail after a timeout. The direction is right — failing fast is what keeps the rest alive. The problem was elsewhere.

Neither number had been chosen by anyone. Both were framework defaults, and what was bad was not the numbers themselves but that they were written down nowhere. Admission control is not about having a cap, it is about deciding that cap deliberately, and a concurrency policy produced by two defaults is not a policy.

Whether the code could take a pooler at all#

Before moving on to ③ there was one more thing to check. Transaction pooling has pin-inducing patterns, and where they exist the pooler is powerless.

  • Session-scoped advisory locks (pg_advisory_lock)
  • Temporary tables
  • SET · set search_path
  • Server-side prepared statements (depending on the pooler and version)

None of the four were present. Advisory locks are used in three places, and all three are xact-scoped — they release at transaction end, so they ride on transaction pooling as-is.

Whether all three being xact-scoped was deliberate or accidental is not something the record can settle. What is certain is that a single session-scoped lock anywhere would have made that path defeat the pooler, and that fact would only have surfaced after the pooler was already in place. The procedure of checking whether a tool works in this code before buying it is the most reusable thing this review produced.

Threads and connections are different resources#

There is another remedy that comes up often here — why not just go async?

Switching to WebFlux or coroutines saves threads. It still holds the connection. JDBC is blocking, and as long as the transaction is open the connection is not returned.

When the axis of the problem is connections and you bring a remedy that saves threads, the axes do not line up. R2DBC would be a different story, but that is a full rewrite of the data access layer.

Growing the pool is the same kind of move. It relieves, it does not repair, and it hits pool size × instances ≤ DB connection limit first. The root cause — a slow outbound call holding a connection — stays exactly where it was.

The guard went on the cause, not the effect#

This fix has a fragility of its own. One line of @Transactional undoes it. And once undone, the feature still works — the tests pass and the screens are fine. The symptom shows up only on a day with load.

So the regression guard went on the cause rather than the effect. A spy sits where the outbound client goes and asserts whether a transaction is active at the moment of the call.

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

assertThat(probe.sawTransaction).isNotEmpty()         // ① did the call actually happen
assertThat(probe.sawTransaction).containsOnly(false)  // ② was it outside the transaction

Without ①, ② passes vacuously. If the gate falls out entirely and there are zero calls, containsOnly is true of an empty list. A negative assertion always needs "and the case was not empty" attached to it.

This guard does not ask "is the response fast". It asks "is the outbound call inside a transaction". That is the actual cause, and the place where the revert happens.

Whether the guard is really aiming at anything was checked by mutation — I restored @Transactional and actually ran it. On the post and comment paths only the matching guard went red. The poll-attachment path was different — the mutation came back green at first. The condition its staleness guard aims at was never constructed inside the test, and red only appeared after an onScreen hook on the spy changed the row during the screening window to build that condition.

That is the most portable thing in this article. A green mutation does not mean the code is safe; it means the guard is not aiming.

What this article does not claim#

  • There are no performance numbers. No load test was run, and there is no basis to say "it got N times faster". What changed is a property of the code — the transaction no longer waits on an outbound call — and how much that is worth in latency or throughput was never measured.
  • "Up to 10 seconds" is a configured value. It is the read timeout set on the outbound call, not a measurement that each request actually held that long.
  • Nothing ever broke. This came out of a pre-launch structural review, and there is no record of observing this path actually run dry.
  • This is not a claim that poolers are useless. For type-A exhaustion a pooler is exactly the right tool. All this article says is that while you are suffering from B the folding ratio is 1:1, so it cannot earn its keep.
  • No per-vendor connection limits are quoted. Those are values I did not verify.
  • The list of pin-inducing patterns may not be complete. It varies by pooler and version; all that was established here is that those four are absent from this code.

The line that remains is this. The same symptom does not mean the same cause, and a tool fits exactly one cause. And the real cost of the wrong tool is not the money — it is the belief that you are covered.
