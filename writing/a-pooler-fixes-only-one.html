The Connection Exhaustion RDS Proxy Cannot Fix
I was calling an external API inside the transaction — a pre-launch review of a social polling platform

Commercial projectWriting · September 2026 · 14 min read

I am building a social polling platform. While reviewing the architecture before launch I started from a very ordinary hypothesis — “traffic will grow, database connections will run short, so why not put a connection pooler in front?” — and the answer turned out to be “not in this codebase.”

This is why it was no, and what I based that judgement on.

Who this is for#

  • You are building a service on Spring Boot and have never touched the connection pool settings directly.
  • You have thought “if connections run short, can't we just put something like RDS Proxy in front?”
  • You have seen code that calls an external API inside a transaction — or you are writing it right now.

What is in here#

  • Connection exhaustion has two causes, and a pooler fixes one of them.
  • Why it cannot fix the other comes from the definition of transaction pooling, not from a vendor document.
  • So before adopting the tool I checked whether the tool works in this code.
  • The fix is the kind that one line of @Transactional undoes, so the regression guard went on the cause rather than the effect.

The code is in a private repository. The app has not launched, so the repository is not open. Each section therefore carries the file path and the symbol name rather than a GitHub link. Package and environment-variable names are the anonymised ones from the original notes.

⚠️ One thing up front. There are no load-test numbers in this article, and nothing ever broke in production. The “up to 10 seconds” below is a configured read timeout on the outbound call, not a measurement that each request actually held a connection that long. The improvement is explained by a change in the properties of the code; this article claims no measured figures.

What is the service?#

A social polling platform I am building toward commercial launch. A user posts a question, other people vote on it, and the result chart gets shared outside the app. It is a single monolith in Kotlin and Spring Boot with one managed PostgreSQL behind it. It has not launched yet.

The shape of it:

The external moderation API is a third-party service that screens harmful content. Every post and comment calls it once, and that call has a read timeout of 10 seconds. And it was happening inside a database transaction.

# application.yml
read-timeout: ${APP_HTTP_READ_TIMEOUT:10s}

Hold on to that number. The rest of this article comes out of it.

At first I thought a pooler would do it#

The review started from a common hypothesis.

Traffic will grow and database connections will run short, so why not put a connection pooler — RDS Proxy, PgBouncer and the like — in front?

A connection pooler is middleware that folds thousands of application connections into dozens of database connections. From the marketing diagram alone it looked like exactly what I needed.

But there was something to establish before that decision: is the connection shortage I am going to hit the kind this tool fixes?

The conclusion first#

It was not. In one line:

Connection exhaustion comes in two kinds — one caused by the number of connections, one caused by holding connections too long. The symptom is the same and the remedy is not. A pooler fixes the first one.

And the basis for that conclusion was not the product documentation for RDS Proxy or PgBouncer but the definition of transaction pooling itself. I will get there.

Start with the symptom. When a connection pool runs dry, what surfaces is mostly one thing: requests wait for a connection and time out, and APIs with nothing to do with each other slow down together. The log carries this line.

Connection is not available, request timed out after 30000ms

Both causes look identical up to here. Which is why picking a tool from the symptom gets it wrong.

Cause A — too many connections#

The first is when the count itself is the problem.

100 app instances × pool size 20 = 2,000 connections
but only 50 are actually running a query right now
the other 1,950 are simply open

PostgreSQL forks one backend process per connection, and an idle one still costs memory. So the more instances you add, the sooner the database side hits its ceiling.

This is why poolers exist. They fold 2,000 app connections into 50 backend ones. For type-A exhaustion a pooler is exactly the right tool.

Cause B — connections held too long#

Private services/api/…/comment/CommentService.kt create

The second is when the problem is not the number of connections but how long each one is held. My code was this kind.

// CommentService.kt — before
@Transactional
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    val user = activeUserGuard.requireActive(userId)                 // DB
    val postWithAuthor = postQueryRepository.findActiveById(postId)  // DB
    // ...
    moderationGate.screenComment(body)   // ← outbound HTTP. read timeout 10s
    // ...
    val comment = commentRepository.insert(...)                      // DB
}

@Transactional is on the whole method, so a connection stays held for as long as the method runs. And sitting in the middle of that span is an outbound call that waits up to ten seconds while running no query at all.

Once concurrent writes exceed the pool size, there are no connections left. Raising the count does not touch the root cause here — a slow outbound call is still holding a connection.

And it is not only the write path that stops.

Voting, feed reads and result-chart reads all take connections from the same pool. So when the write path consumes it, the whole service slows down together.

What made this particularly sharp was the timing. This service's growth engine is “sharing the result chart”, which means the day sharing spikes is the day the service stalls.

Why can't a pooler fix B?#

This is the heart of it.

“Thousands of app connections folded into dozens of database connections” is an accurate description. The question is when the folding happens, and the answer is already contained in the definition of transaction pooling.

Reusing a connection happens only between transactions. While a transaction is open, that backend connection is pinned to that client.

Which is not surprising. A transaction is state, and lending it out mid-flight would break isolation.

Which gives you this.

transaction open for 10s
  → backend connection pinned for 10s
  → 1 app connection costs 1 database connection
  → the pooler folds nothing

A pooler earns its keep when there are many short transactions. Adopting one while suffering from B spends money and changes nothing — and the worse part comes next: you come to believe you are covered. That belief is what stops the next review.

So there is an order#

The remedy is not one thing but several layers, and the layers have an order.

Scroll sideways to see the rest

Five layers of remedy for connection exhaustion and what each one is.
LayerWhatWhat kind of thing it is
①Shorten the transaction — move the outbound call outside itThe only fundamental one. The premise of every other layer
②Admission control — decide the concurrency cap deliberatelyMakes failure fast and predictable
③Connection poolerOnly works once ① is done
④Read splitting and cachingThe only layer that makes you use fewer connections
⑤Async offload (outbox)Reduces the DB work per request itself

A pooler is ③. Going straight to ③ without ① is what the previous section was about.

The code went first#

Private services/api/…/comment/CommentService.kt create · services/api/…/post/PostService.kt createPost · addPoll

So ① came first: narrowing the transaction boundary to the write. In Spring, @Transactional is proxy-based and does not apply to self-invocation, so I reused the TransactionTemplate pattern that was already in the codebase. Introducing no new mechanism mattered here.

// after — no @Transactional on the method
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    // ① validation (reads. each borrows a connection briefly and returns it)
    val user = activeUserGuard.requireActive(userId)
    val postWithAuthor = postQueryRepository.findActiveById(postId) ?: throw ...

    // ② the outbound call — outside the transaction. ten seconds here holds no connection
    moderationGate.screenComment(body)

    // ③ only the write is atomic
    val written = writeTx.execute {
        val identity = postAliasRepository.ensureIdentity(...)
        val comment = commentRepository.insert(...)
        Triple(comment, identity?.alias, ...)
    }!!
}

The obvious question is “doesn't splitting the transaction widen the race window?” — it did not widen. The moderation call already sat between the read and the write before the change, and that path was not locking the post row (there was no for update). Being inside a transaction did not stop other sessions from changing it. The distance from read to write is identical.

The same work was done on three write paths (post, comment, poll attachment). One of them was in worse shape — the poll-attachment path was making the outbound call while holding a row lock via for update, holding two resources at once: the connection and the row lock.

The post and comment paths went first. The poll path takes its screening input from the locked row, so it needed a staleness re-check and was deliberately deferred, then fixed four days later.

The conclusion in one line: the code change was not an alternative to the pooler, it was its precondition. Once it was done, the system was finally in a state where a pooler could earn its keep.

Two numbers nobody chose#

Private services/api/src/main/resources/application.yml spring.datasource.hikari

Layer ② had a trap of its own. With blocking JDBC the connection pool is effectively the concurrency cap. However many threads there are, they cannot work without a connection.

Opening the configuration, this is what was there.

# application.yml — as found
spring:
  datasource:
    url: ${DB_URL:...}
    username: ${DB_USER:...}
    password: ${DB_PASSWORD:...}
    # that's it. no hikari block at all

Tomcat threads sat at the default of 200, and the connection pool had no configuration at all, so the Spring Boot default was the service's capacity. The remaining requests wait for a connection and fail after a timeout.

The direction is right — failing fast is what keeps the rest alive. The problem was elsewhere: neither number had been chosen by anyone. Both were framework defaults, and what was bad was not the numbers but that they were written down nowhere.

So they were made explicit.

hikari:
  maximum-pool-size: ${DB_POOL_MAX:20}
  connection-timeout: ${DB_POOL_TIMEOUT_MS:5000}   # the 30s default is too long — failing fast keeps the rest alive
  max-lifetime: ${DB_POOL_MAX_LIFETIME_MS:1200000}

That said, growing the pool is relief, not repair, and there is a ceiling on growing it.

pool size × max instances ≤ database connection limit

The app does not know how many instances of itself are running, so this invariant cannot be enforced in code. An IaC comment is the only defence, so that is where it was pinned.

Admission control is not about having a cap, it is about deciding that cap deliberately. A concurrency policy produced by two defaults is not a policy.

I checked whether the code could take a pooler at all#

Private services/api/…/vote/VoteRepository.kt pg_advisory_xact_lock

Before moving to ③ there was one more thing to establish. Transaction pooling has pin-inducing patterns, and where the code has them the pooler is powerless — a pinned connection stays bound to that client even after the transaction ends.

  • Session-scoped advisory locks (pg_advisory_lock)
  • Temporary tables
  • SET · set search_path
  • Server-side prepared statements (varies by pooler and version)

So I went and looked.

$ grep -rn "pg_advisory_lock" src/main/kotlin/      # (none)
$ grep -rn "advisory_xact" src/main/kotlin/
ReportRepository.kt      pg_advisory_xact_lock(...)
AuthAuditPurge.kt        pg_try_advisory_xact_lock(...)
VoteRepository.kt        pg_advisory_xact_lock(...)

None of the four were present. Advisory locks are used in three places and all three are xact-scoped, releasing at transaction end, so they ride on transaction pooling as-is.

Whether all three being xact-scoped was deliberate or accidental is not something the record can settle. What is certain is that a single session-scoped lock anywhere would have made that path defeat the pooler, and that fact would only have surfaced after the pooler was already in place.

A procedure for checking that a tool actually works in this code before adopting it. Of everything this review produced, that is the part that transfers best to another project.

“Why not just go async?”#

There is one more remedy that comes up whenever this is discussed.

Switching to WebFlux or coroutines saves threads. It still holds the connection, because JDBC is blocking and a connection is not returned while the transaction is open.

Threads and connections are different resources. When the axis of the problem is connections and the remedy saves threads, the axes do not line up. R2DBC would be a different story, but that is a full rewrite of the data access layer.

Growing the pool is the same kind of move. It relieves, it does not repair, and it hits pool size × instances ≤ database connection limit first. The root cause — a slow outbound call holding a connection — stays exactly where it was.

The fix is easy to undo, so the guard went on the cause#

Private services/api/src/test/…/ModerationOutsideTransactionTest.kt TransactionProbe

This fix has a fragility of its own. One line of @Transactional puts it back. And once undone, the feature still works — the tests pass and the screens are fine. The symptom only shows up on a day with load.

“The connection is not held for long” is hard to observe directly. So instead of the effect I asserted the cause. A spy sits where the real HTTP client's interface goes and records whether a transaction is active at the moment of the call.

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

// the assertions
assertThat(probe.sawTransaction).isNotEmpty()         // ① did the call actually happen
assertThat(probe.sawTransaction).containsOnly(false)  // ② was it outside the transaction

Without ①, ② passes vacuously. If the gate falls out entirely and there are zero calls, containsOnly is true of an empty list. An assertion that checks “X is not the case” always needs “and there was an X to check” next to it.

Whether the guard is really aiming at anything was checked by mutation — putting the code back on purpose and running the tests to see whether they go red.

# @Transactional restored on the comment path
ModerationOutsideTransactionTest > the moderation call does not hold a database transaction() FAILED

# @Transactional restored on the post path
ModerationOutsideTransactionTest > creating a post also screens outside a transaction() FAILED

On the post and comment paths only the matching guard went red. The poll-attachment path was different — the mutation came back green at first. The condition its staleness guard aims at was never constructed inside the test, and red only appeared after an onScreen hook on the spy changed the row during the screening window to build that condition.

That is the most portable thing in this article. A green mutation does not mean the code is safe; it means the guard is not aiming.

What this article does not claim#

  • There are no performance numbers. No load test was run, and there is no basis to say “it got N times faster”. What changed is a property of the code — the transaction no longer waits on an outbound call — and how much that is worth in latency or throughput was never measured.
  • “Up to 10 seconds” is a configured value. It is the read timeout set on the outbound call, not a measurement that each request actually held that long.
  • Nothing ever broke. This came out of a pre-launch structural review, and there is no record of observing this path actually run dry.
  • This is not a claim that poolers are useless. For type-A exhaustion a pooler is exactly the right tool. All this article says is that while you are suffering from B, one app connection costs one database connection, so it cannot earn its keep.
  • No per-vendor connection limits are quoted. Those are values I did not verify.
  • The list of pin-inducing patterns may not be complete. It varies by pooler and version; all that was established here is that those four are absent from this code.

Wrapping up#

To pull it together:

  • Connection exhaustion has two causes — count and hold time — and they are easy to confuse because the symptom is identical.
  • A pooler is the tool for the count problem. Against the hold-time problem, one app connection costs one database connection and there is nothing left to fold. That is not a product limitation but the definition of transaction pooling.
  • So there is an order. Shortening the transaction is the premise of everything else.
  • Adding a step that checks whether a tool works in this code before adopting it tells you beforehand what you would otherwise learn afterwards.

If one line survives, this one. The same symptom does not mean the same cause, and a tool fits exactly one cause. And the real cost of the wrong tool is not the money — it is the belief that you are covered.
