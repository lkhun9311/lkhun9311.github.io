개인 프로젝트#GPUaaS Control Plane

AWS 자원 96개를 지운 Teardown이 「잔여 없음」을 찍었는데 두 줄은 조회하지 않았습니다
VPC가 이미 없으면 Load Balancer와 Network Interface 질의는 실행되지 않고 빈 초기값이 그대로 출력됩니다.

개인 프로젝트로 GPU를 나눠 쓰는 Kubernetes Control Plane을 만들고 있습니다. AWS 계정 하나에 EKS 클러스터를 통째로 세웠다가 지우는 Terraform 루트가 있고 밤마다 그것을 지우는 GitHub Actions 워크플로가 돌고 있습니다.

그 워크플로는 여태 매번 성공했습니다. 지울 것이 없었기 때문입니다. 성공한 정리와 할 일이 없던 정리가 같은 초록색으로 쌓여 있었습니다.

그래서 하루를 들여 진짜로 세웠다가 지웠습니다. 자원 96개가 생겼고 지우는 데 13분 35초가 걸렸습니다. 기록해 둔 자원 ID를 하나씩 조회해 없어진 것을 확인하고 나서 워크플로가 마지막에 찍은 목록을 다시 읽다가 두 줄에서 멈췄습니다. 일곱 줄 가운데 두 줄은 AWS에 물어본 적이 없는데 나머지 다섯 줄과 똑같은 글자로 없음을 찍고 있었습니다.

이 글의 예상 독자#

  • Terraform으로 클러스터를 통째로 세웠다 지우는 경로를 만드시는 분
  • 정리 작업 끝에 찍히는 「잔여 없음」을 근거로 삼고 계신 분
  • 검사가 통과한 것인지 실행되지 않은 것인지를 구분해 보신 분

어떤 서비스인가요?#

연구실 하나 규모의 GPU를 여러 사람이 나눠 쓰게 하는 Control Plane입니다. 클러스터는 상시로 띄워 두지 않습니다. 필요할 때 Terraform으로 세우고 쓰고 나면 지웁니다. 세우면 VPC와 서브넷 여덟 개, EKS 클러스터, 노드그룹 넷, NAT와 EIP까지 자원 96개가 한 번에 생깁니다.

지우는 쪽은 워크플로가 맡습니다. Argo CD 애플리케이션을 먼저 지우고 Terraform으로 클러스터를 지운 다음 마지막에 남은 것이 있는지 계정에 물어봅니다. 그 마지막 단계가 이 글의 주인공입니다.

처음엔 정리 경로가 검증된 줄 알았습니다#

정리 워크플로는 몇 달째 밤마다 돌고 있었고 실패한 적이 없었습니다. 실행 기록만 보면 검증이 끝난 경로로 읽힙니다.

그런데 그 기간 동안 이 계정에는 클러스터가 없었습니다. 워크플로는 매번 「지울 것이 없다」를 확인하고 성공으로 끝난 것입니다. 지우는 코드가 실제로 지워 본 적은 한 번도 없었습니다. 그래서 세웠습니다.

결론부터 말씀드리자면#

지우는 일 자체는 됐습니다. Terraform은 96개를 지웠다고 보고했습니다. 그 집계와 별개로 제가 미리 기록해 둔 자원 ID를 조회했습니다. EKS는 ResourceNotFoundException, EIP와 VPC와 EBS와 ENI 다섯 개는 전부 NotFound, EC2는 terminated, NAT는 deleted였습니다. 상태 파일은 106,851바이트에서 1,361바이트로 줄었습니다. 96개를 하나씩 다시 조회한 것은 아닙니다.

일곱 줄이 전부 없음으로 찍혔습니다#

파괴가 끝난 뒤 워크플로가 계정에 무엇이 남았는지 조회해서 목록을 찍습니다. 이번 실행의 출력입니다.

VPC:               <none>
EC2 instances:     <none>
EBS volumes:       <none>
NAT gateways:      <none>
Unassociated EIPs: <none>
Load balancers:    <none>
Network ifaces:    <none>
no residue

일곱 줄이 나란히 없음입니다. 이걸 보면 일곱 가지를 전부 물어봤고 전부 없더라로 읽게 됩니다. 저도 그렇게 읽었습니다.

뒤의 두 줄은 조회한 적이 없습니다#

이 검사는 Load Balancer와 Network Interface를 앞서 찾은 VPC ID를 기준으로 조회하도록 쓰여 있습니다. 코드가 이렇게 돼 있습니다.

LB=""
ENI=""
if [ -n "$VPC" ]; then
  LB=$(q elb aws elbv2 describe-load-balancers ...)
  ENI=$(q eni aws ec2 describe-network-interfaces ...)
fi

VPC가 이미 지워졌으면 $VPC는 빈 문자열이고 두 질의는 실행되지 않습니다. LB와 ENI는 맨 위에서 넣어 둔 빈 초기값 그대로 남고 출력 함수는 빈 값을 <none>으로 찍습니다. 「AWS에 물어봤더니 없더라」와 「묻지 않았다」가 한 글자도 다르지 않게 나옵니다.

기록해 둔 ENI ID 다섯 개가 없어진 것은 제가 따로 하나씩 조회해서 확인했습니다. 그것은 그 다섯 개에 대한 확인이지 남은 ENI가 하나도 없다는 확인은 아닙니다. Load Balancer는 이번 구성에서 아예 만들지 않았습니다. 어느 쪽도 저 출력이 알려 준 것이 아닙니다.

같은 파일의 다른 절반을 그날 아침에 고쳤습니다#

같은 날 아침에 저는 이 검사의 다른 절반을 고쳤습니다. 조회를 set +e 아래에서 돌리고 결과 문자열만 받아 쓰고 있어서 자격증명이 만료돼도 빈 문자열이 돌아오고 그게 없음으로 읽히던 자리였습니다.

고친 방식은 질의마다 종료 코드를 보고 실패하면 따로 기록해 두었다가 마지막에 그 목록이 비어 있지 않으면 작업을 실패시키는 것입니다.

if [ -n "$FAILED" ]; then
  echo "::error::residue verification did not complete: these queries failed:$FAILED"
  echo "This is NOT a report of no residue -- nothing above says whether anything is still billing."
  exit 1
fi

한 검사 안에 같은 결함이 두 가지 모양으로 있었던 셈입니다. 아침에 고친 것은 실패한 조회가 없음으로 읽히는 것이었고 저녁에 본 것은 실행되지 않은 조회가 없음으로 읽히는 것이었습니다. 저는 한쪽을 고치고 그 파일을 다 봤다고 생각했습니다.

알 수 없는 원인을 지목한 경고#

파괴 도중에 Argo CD를 순서대로 지우는 단계 둘이 건너뛰어졌습니다. 로그는 이렇게 말했습니다.

##[warning]Kubernetes API is not reachable from this runner.
          The cluster endpoint is private and this runner is outside the VPC.

이 실행에서 그 설명은 틀렸습니다. Endpoint의 공개 쪽은 열려 있었고 다만 허용 대역이 제 주소 하나뿐이라 GitHub 호스팅 러너가 거기 들어 있지 않았을 뿐입니다.

코드를 보니 접속 확인은 kubectl get --raw /readyz의 모든 비정상 종료를 하나의 실패로 바꾸고 오류 내용을 버립니다. 그러면 대역 거부와 인증 실패와 DNS 실패와 준비 미완료를 구분할 수 없습니다. 구분할 수 없는데 원인을 하나 지목하면 읽는 사람을 엉뚱한 곳으로 보냅니다. 증상만 말하고 가능한 원인을 나열하도록 고쳤습니다.

이 검사가 애초에 안 보는 것들#

두 줄을 고치더라도 이 검사가 답할 수 있는 범위는 좁습니다. 한 리전만 보고 EC2와 EBS와 NAT는 태그로 찾고 VPC는 이름 태그로 찾습니다. EIP는 연결되지 않은 것만 셉니다.

연결된 채 남은 EIP는 이 검사가 찾지 못합니다. 이번 EIP는 살아 있는 동안 NAT에 연결돼 있었습니다. 없어진 것은 제가 allocation ID를 조회해서 확인했고 그 확인은 워크플로가 아니라 제가 따로 한 것입니다.

이 글이 주장하지 않는 것#

  • ⚠️ 정리 경로가 검증됐다는 말이 아닙니다. 이번 한 바퀴는 가장 작은 클러스터였고 Load Balancer도 Argo CD도 GPU 노드도 PVC도 없었습니다. 이 워크플로가 대비하고 있던 어려운 경우는 하나도 시험되지 않았습니다.
  • 잔여 검사가 실패하는 것은 여전히 본 적이 없습니다. 이번에도 통과했고 성공 기록만으로는 그 검사가 실제로 조회를 했는지 판단할 수 없습니다.
  • 돈이 0이 됐다는 말이 아닙니다. 끝난 것은 이 클러스터의 사용량입니다. 상태 버킷과 KMS 키와 ECR 저장소 둘은 그대로 있고 금액은 청구 자료에서 읽지 않았습니다.
  • ⚠️ 밤마다 도는 cron이 무인으로 같은 일을 해내는지도 확인하지 않았습니다. 이번 파괴는 손으로 띄워서 지켜본 것입니다.

마치며#

  • 「물어봤더니 없다」와 「묻지 않았다」는 다릅니다. 둘이 같은 글자로 나오면 읽는 쪽에서 가를 방법이 없습니다.
  • 건너뛴 조회의 초기값은 결과처럼 보입니다. 조건 안에서만 채워지는 변수를 그대로 출력하면 조건이 거짓이던 사실이 출력에서 사라집니다.
  • 한 파일 안에 같은 결함이 여러 모양으로 있을 수 있습니다. 한쪽을 고치고 그 파일을 다 봤다고 여긴 것이 이번의 제 실수였습니다.
  • 구분할 수 없는 것을 지목하지 않습니다. 원인을 하나로 적은 경고는 읽는 사람을 그쪽으로 보냅니다.
