모니터링 Cache 세 개를 합치자 서로의 값을 지웠습니다
따로 있을 때 우연히 지켜지던 규칙을 전부 코드로 적어야 했습니다.

2026년 9월

목차

  • 이 글의 예상 독자
  • 통합 전 구조가 가진 셋
  • 부분 실패는 항목별로 이어 씁니다
  • 합치자마자 회귀가 나왔습니다
  • 느린 소비자를 수집에서 떼어 냈습니다
  • 통합 결과
  • 공유 상태를 합칠 때 확인할 것
  • 이 글이 주장하지 않는 것
  • 마치며

사내 Cloud 관리 Console의 Backend를 만들고 있습니다. ④편까지 화면 셋을 각각 고쳤습니다. 첫 데이터는 다 빨라졌는데 같은 원천을 화면마다 따로 수집하고 있었습니다. 노드 메트릭은 대시보드와 물리 노드가 겹쳐 읽었고 Instance 메트릭은 대시보드와 가상자원이 겹쳐 읽었습니다.

Cache 셋을 하나로 합치면 그 중복이 없어집니다. 자료구조 셋을 하나로 바꾸는 일이라 작아 보였습니다.

실제 작업은 그보다 훨씬 컸습니다. 따로 있어서 우연히 지켜지던 것들이 전부 명시할 계약이 됐기 때문입니다. 합치자마자 회귀가 하나 나왔습니다. 한 화면만 열어 두면 다른 화면의 마지막 값이 Cache에서 사라졌고 재진입이 5,115ms였습니다.

이 글은 그 계약들을 하나씩 적습니다. 부분 실패를 항목별로 이어 쓰는 것, 가변 DTO를 공유하지 않는 것, 그리고 장애를 빈 값으로 확정하지 않는 것입니다.

이 글의 예상 독자#

  • 비슷한 Cache 여러 개를 하나로 합치려는 분
  • 여러 소비자가 같은 원천을 각각 읽고 있는 구조를 가진 분
  • ‘객체 수를 줄이는 리팩터링’으로 시작했다가 계약을 다시 쓰게 된 분

통합 전 구조가 가진 셋#

첫째, 중복 수집. 세 화면의 15s 주기가 겹치면 같은 노드와 Instance를 여러 번 읽습니다. 화면이 늘수록 원천 부하가 소비자 수에 비례합니다.

둘째, 가변 DTO 공유. 구조 Cache가 돌려준 객체를 화면마다 제자리에서 메트릭으로 채웠습니다. 한 Thread가 값을 바꾸는 동안 다른 Thread가 직렬화하면 한 Payload 안에 서로 다른 시점이 섞입니다. 원자 참조로 포인터를 바꿔도 안의 객체가 공유·가변이면 불변 스냅샷이 아닙니다.

셋째, 장애를 빈 값으로 확정. 인프라 조회나 메트릭 가져오기가 실패했는데 빈 목록을 새 정상 스냅샷으로 발행하면 마지막 정상 화면이 0으로 덮입니다. ③편과 ④편에서 화면마다 따로 만난 문제입니다.

부분 실패는 항목별로 이어 씁니다#

대시보드는 노드와 Instance 결과를 합쳐서 보여 줍니다. Instance 메트릭만 실패했다고 성공한 노드까지 이전 세대로 되돌리면 의존성 하나의 장애가 화면 전체를 늙게 만듭니다. 반대로 빈 Instance 목록을 새 값으로 받으면 실제 VM 수를 0으로 덮습니다.

그래서 ③편의 다섯 갈래를 공통 판정으로 끌어올리고 항목마다 따로 적용했습니다.

FRESH              새 데이터와 새 세대로 발행
EMPTY_VALID        대상이 0이므로 정상 빈 데이터로 발행
INFRA_UNAVAILABLE  이전 데이터 이어 씀 + 저하 표시
FETCH_FAILED       이전 데이터 이어 씀 + 저하 표시
NO_VALID_METRICS   이전 데이터 이어 씀 + 저하 표시

합치자마자 회귀가 나왔습니다#

통합 후 가장 눈에 띈 것은 페이지를 옮겼다가 돌아왔을 때였습니다.

단일 Producer는 지금 구독 중인 경로만 계산해 맵 하나로 발행했고 발행할 때 이전 맵을 통째로 교체했습니다. 물리 노드 화면만 열어 둔 채 갱신이 돌면 최신 세대에는 노드만 남습니다. 이전 대시보드 값은 Cache에서 사라집니다.

그다음 대시보드에 접속하면 즉시 보낼 값이 없어 수집 한 사이클을 기다립니다. 재 보니 약 5,115ms였고 바로 다시 접속하면 16ms였습니다.

분리된 Cache가 말없이 갖고 있던 계약은 이것이었습니다. ‘다른 경로의 갱신이 내 마지막 값을 지우지 않는다.’ 합치면서 그 계약이 사라졌고 아무도 그것을 적어 둔 적이 없었습니다.

latestGeneration      이번 수집에 포함된 경로 집합
lastPageByPath[경로]  각 경로의 마지막 성공 payload

발행(세대):
    latestGeneration 을 교체한다
    포함된 경로만 lastPageByPath 에 병합한다

접속(경로):
    lastPageByPath[경로] 를 즉시 보낸다
    그 경로가 latestGeneration 에 없으면 갱신을 요청한다

느린 소비자를 수집에서 떼어 냈습니다#

SSE의 전송은 느린 클라이언트에서 막힐 수 있습니다. 수집 Lock을 방송이 끝날 때까지 쥐고 있으면 한 클라이언트의 네트워크가 다음 수집을 늦춥니다. 그래서 새 세대를 발행한 직후 수집 토큰을 놓고 전송은 별도 컴포넌트에 넘겼습니다.

그런데 일반 실행기 큐에 세션별 작업을 넣으면 작은 Pool에서 앞 세션만 반복 수락되고 뒤 세션은 계속 거부되는 기아가 생길 수 있었습니다. 전송기는 준비 Deque와 상주 Worker를 씁니다.

  • 세션마다 대기 Payload는 가장 큰 세대 하나만 둡니다.
  • 세션은 큐에 한 번만 들어갑니다.
  • Worker가 한 번 보낸 뒤 새 대기가 있으면 뒤에 다시 넣습니다.
  • 이미 보낸 세대 이하의 값은 버립니다.
  • 종료된 세션은 전송 직전에 다시 확인합니다.

동기 전송 자체가 사라진 것은 아닙니다. 동시에 막힌 세션 수가 Worker 수를 넘으면 전송은 여전히 늦어집니다. 비동기 I/O나 느린 세션 선제 축출은 따로 남겨 둔 과제입니다.

공유 상태를 합칠 때 확인할 것#

Cache 통합은 객체 수를 줄이는 리팩터링이 아닙니다. 이 질문들에 답해야 합니다.

  • 지금 구독 중이 아닌 소비자의 마지막 값은 보존되는가
  • 한 원천의 실패가 다른 원천의 성공을 되돌리는가
  • 빈 값은 정상적인 0인가, 판단 불가인가
  • Payload 안의 객체까지 세대별로 불변인가
  • 새 값과 오래된 값이 역전되어 전송될 수 있는가
  • 느린 소비자가 Producer를 막는가
  • 프로세스가 여러 대라면 Producer도 여러 개인가

이 글이 주장하지 않는 것#

  • 사내 제품이라 코드와 화면을 그대로 옮기지 않았습니다. 제품명·고객사·내부 주소는 빼고 구조와 계약만 남겼습니다.
  • 운영 통계가 아닙니다. 단일 사용자 순차 측정입니다.
  • 가상자원의 최종값은 직접 비교가 아닙니다. 재측정 당시 일부 메트릭이 없는 환경이라 ④편의 개별 측정을 기준으로 삼았습니다.
  • 느린 소비자 문제를 해결했다고 말하지 않습니다. 수집에서 떼어 냈을 뿐이고 동시에 막힌 세션이 Worker 수를 넘으면 전송은 여전히 늦어집니다.
  • Producer가 여러 대일 때는 다루지 않았습니다. 위 질문 목록의 마지막 항목이 그대로 남아 있습니다.

마치며#

다섯 편에서 남은 것을 적어 둡니다.

  • ‘고칠 근거가 없다’와 ‘안 재 봤다’는 다릅니다. 잰 자리가 사용자가 기다린 자리와 달랐습니다.
  • ‘미리 만들어 두고 준다’는 누가 만들고 누가 게시하는지를 정해야 한 줄이 됩니다.
  • ‘비었다’는 관측이 아니라 해석이 필요한 값입니다.
  • 화면의 지연은 늦게 끝나는 게이트가 정합니다.
  • 따로 있어서 지켜지던 것은 합칠 때 계약으로 적어야 합니다.

공유 상태는 한 곳에 모았다고 단순해지지 않습니다. 암묵적이던 계약을 전부 드러냈을 때 비로소 관리할 수 있습니다.

중복 수집을 없애 얻은 성능보다 이 의미들을 코드와 테스트로 적어 둔 것이 더 오래갈 결과라고 생각합니다. 다섯 편 읽어 주셔서 감사합니다.
