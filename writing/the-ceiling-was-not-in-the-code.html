The Throughput Ceiling Was Not in the Code
A default of five from a library S3 pulled in — the moderation path of a social polling platform

I am building a social polling platform. In the previous article I moved an external call out of a database transaction and stood up a load-test harness to put numbers on it. The harness immediately asked the next question — why does post creation stop at 6.27 req/s?

Four times the write threads did nothing. Three times the database pool did nothing. The culprit was a default inside a library I never added, never chose, and had never seen the name of.

Who this is for#

  • Anyone calling an external API from Spring Boot through RestClient or RestTemplate
  • Anyone whose throughput sits on one number and will not move, even after raising threads and the database pool
  • Anyone who has wondered “is a library I never added deciding how my service behaves?”

What is in here#

  • Throughput on the content moderation path sat at 6.27 req/s. Four times the write threads, three times the database pool — no change.
  • The cause was the HTTP client the AWS SDK pulled in when I added S3, and its default of five connections per target host.
  • That library is only on the runtime classpath. Its name appears nowhere in my code, so reading could not find it — only measuring could.
  • The fix was setting the limit, not removing it. Removing it raises throughput by exactly the same amount, but it only swaps a five nobody chose for an infinity nobody chose.
  • Result: outbound concurrency 10 → 32, post creation p50 2,592 → 805 ms, throughput 6.27 → 19.89 req/s (3.17×), errors 0%.

The code is in a private repository. The product has not launched, so the repository is not open yet. Each section therefore carries a file path and a symbol name instead of a GitHub link.

⚠️ One thing up front. Every number here comes from a local harness. The load generator, the application, the external-API stub and PostgreSQL all share one machine's CPU. Absolute throughput is meaningless; only the comparison means anything. The 800 ms external latency is a value I configured in the stub, not a real latency distribution, and each condition was run once.

Which path is this about?#

A social polling platform I am building toward commercial launch. Someone posts a question, other people vote anonymously, and the resulting chart gets shared outside the app. It is a single Kotlin and Spring Boot monolith on one managed PostgreSQL database.

A post has to clear the moderation gate before it is published. The gate has four layers, and two of them — ③ harmful-content classification and ④ targeted-harassment classification — call an external API. The gate is fail-closed: if those calls fail, the post is not published.

One thing the diagram does not say: ③ and ④ go to the same host. Later, that fact meets a default that reads “five per host,” and the two together are the whole problem.

At first I thought the database was the bottleneck#

The harness's first numbers looked like this. Sixteen write threads, a database pool of ten, an 800 ms external stub.

The first hypothesis was the ordinary one.

There are sixteen writers and only ten database connections, so they must be queueing for a connection. Or the INSERT itself is heavy. Should the writes go through a queue? Should I add Redis?

All three were wrong. And I did not reason my way to that — the harness told me.

The conclusion first#

The bottleneck was not the database, not the INSERT, and not application threads. Outbound HTTP concurrency was pinned at ten.

And the ten was assembled like this.

AWS SDK, added so I could use S3
  → software.amazon.awssdk:apache5-client
     → org.apache.httpcomponents.client5:httpclient5      ← transitive
        → Spring's RestClient picks it up off the classpath
           → connection pool default: 5 per target host
              → 2 RestClients on the same host × 5 = 10 concurrent

The only line in that chain I chose is the first one. I added S3 to upload files, and by way of the HTTP client it dragged along, it was setting the throughput ceiling of content moderation.

Writes were not heavy#

“Are writes heavy?” is a question the harness answers directly. Set the stub's latency to 0 ms, hold everything else constant, and what is left is the pure application and database cost of a write.

ConditionPost creation p50Post creation throughput
External latency 800 ms2,592 ms6.27 req/s
External latency 0 ms8 ms1,398 req/s

The INSERT path costs eight milliseconds and takes 1,398 requests a second. Writes are not this system's problem, which means moving writes onto a queue would be repairing something that is not broken.

⚠️ This measurement was wrong the first time. I asked for zero latency, but the previous run's 800 ms stub was still alive on the port. The harness had a round-trip check for “is the stub really answering with that latency,” and its condition was round trip < requested latency × 0.8 — which is always false when the requested latency is zero. The check passed vacuously, so I recorded an 800 ms run as a 0 ms run and drew a conclusion from it.

The fix was to check identity rather than timing. The stub now reports its own configuration, and the run compares that against what was asked for.

$ curl -s localhost:18080/__stub/health
{"ok": true, "delay_ms": 800, "jitter_ms": 0, "max_in_flight": 10}
#            ↑ if this differs from the requested value, abort the run

Then I deliberately started the wrong stub and confirmed the run actually stops. The most frequent defect class in this repository is “a check that failed but looked like it passed,” so breaking a new check on purpose is a standing rule here.

Nothing I changed moved it off ten#

Next I instrumented the stub: count on the way in, decrement on the way out, and record the peak number of external calls in flight. That single number explains everything else.

Here is how to read the table. Four times the writers and three times the pool leave concurrency at ten. The only thing that grows is latency (2,592 → 5,119 ms), which is the classic queueing signal — no extra work, just a longer line.

I ruled out the stub separately. Hit the same stub with 32 workers for twenty seconds, without the application in the way, and it delivers 32 concurrent · 40 req/s. So the ten is not the stub's limit; it is the limit of the application's way out.

And the arithmetic closes. One post makes two calls, so ten in flight is five posts being moderated at once. Each call takes 800 ms, so 5 ÷ 0.8 s ≈ 6.3 req/s — the 6.27 that was measured.

A thread dump showed where it was stopping#

“There is a ten somewhere in the application” was as far as reading got me, because neither ten nor five appears anywhere in my code.

So I took a thread dump under load. Of sixteen Tomcat workers, five were RUNNABLE in socket I/O and eleven were parked. The parked stack was the answer.

at org.apache.hc.core5.pool.StrictConnPool$1.get(StrictConnPool.java:183)
at org.apache.hc.client5.http.impl.io.PoolingHttpClientConnectionManager$3.get(...)
at org.apache.hc.client5.http.impl.classic.InternalExecRuntime.acquireEndpoint(...)

They were waiting on Apache HttpClient 5's connection pool. I had no memory of adding that library.

Follow the chain back and you arrive at S3#

The dependency tree laid the chain out.

Here is what the diagram does not say. httpclient5 is on the runtime classpath only. It is absent from the compile classpath, so I cannot even name it in my own code. I found this out by trying to write the configuration first and hitting Unresolved reference 'hc'.

Which is why this layer cannot be found by reading. Not by code search, not by review. Only by measuring.

But it must not stay like that#

There was a temptation to stop there — one line, 3.17×. Except that the JDK client has no per-host limit at all.

So what that line actually did was swap a five nobody chose for an infinity nobody chose. That is the exact opposite of what this article has been about.

With no limit, a burst sends unbounded concurrent calls at the external API. That is load on somebody else's service and my bill. Admission control is not the absence of a limit; it is a limit somebody decided on.

Worth adding: this repository has already had the same shape of defect once. Tomcat's 200 threads and the connection pool were both framework defaults, and the concurrency policy those two produced was not a policy. The same thing was true on the outbound side, and this time nobody was looking at that layer at all.

So I set the limit#

Two decisions.

  1. Promote httpclient5 to an explicit dependency. It is a library the application already used at runtime; declaring it by name is what makes configuration code possible at all.
  2. Build one connection pool and let every RestClient share it. When each client holds its own pool, “N per host” is really “number of clients × N.” That is exactly how five had become ten.
@Configuration
class OutboundHttpConfig {
    @Bean
    fun outboundConnectionManager(
        @Value("\${oxy.http.outbound.max-per-route:50}") maxPerRoute: Int,
        @Value("\${oxy.http.outbound.max-total:100}") maxTotal: Int,
        // Re-attach the timeouts Spring used to supply — by reading the same property keys.
        @Value("\${spring.http.client.connect-timeout:3s}") connectTimeout: Duration,
        @Value("\${spring.http.client.read-timeout:10s}") readTimeout: Duration,
    ): PoolingHttpClientConnectionManager = ...

    @Bean
    fun outboundHttpCustomizer(cm: PoolingHttpClientConnectionManager): RestClientCustomizer {
        // One factory too, so every builder ends up on the same pool.
        val factory = HttpComponentsClientHttpRequestFactory(
            HttpClients.custom().setConnectionManager(cm).build())
        return RestClientCustomizer { builder -> builder.requestFactory(factory) }
    }
}

The reasoning behind 50 is written into the comment. One post makes two calls, so fifty is twenty-five posts under moderation at once; at 800 ms per call that accepts roughly thirty-one posts a second. Larger than any traffic assumption I currently hold, and not infinite.

⚠️ The 32 is not a new limit. The written limit is fifty; the observed peak is thirty-two. Thirty-two is the shape of the load, not a ceiling — sixteen write threads making two calls per post is 16 × 2 = 32. In other words the ceiling has left the outbound pool, and what sets throughput now is inbound concurrency. Whether fifty ever binds would take twenty-five or more write threads to see, and I did not measure that.

Also worth stating plainly: factory=jdk (19.89 req/s) and this fix (19.89 req/s) have the same throughput. What separates them is not performance. It is whether a number is written down.

My first attempt threw the timeouts away#

My first attempt replaced the whole requestFactory. Doing that also removed the spring.http.client.* timeouts that autoconfiguration had been applying.

This is the kind of accident that can pass quietly. Without a timeout, normal responses still come back normally. It only shows up when you meet a server that never answers.

Fortunately a test aimed at exactly that already existed. The guard — “does not hang on a server that never responds” — failed after forty seconds. Without it, an unbounded wait would have quietly returned.

The repair was to avoid duplicating the values: read the same property keys. Duplicate them and a day comes when only one side is updated.

Configuration does not fail anything by itself#

This change had one property that sets it apart from most: the deliverable is a setting. Break a piece of logic and the test aimed at that logic goes red. Delete a setting and nothing fails at all — it just falls back to the default, quietly.

And that quiet fallback to a default is the cause of this entire article. So I added two tests that assert the values actually took effect.

// ① The value must be ours, not the default of 5.
assertThat(manager.defaultMaxPerRoute).isEqualTo(37)
assertThat(manager.maxTotal).isEqualTo(91)
// Per-route lookup must agree — if they diverge, the effective limit differs.
assertThat(manager.getMaxPerRoute(route)).isEqualTo(37)

// ② A pool per client turns "N per host" into "clients × N".
//    That is how 5 became 10, so assert the factory is shared.
assertThat(factories[0]).isSameAs(factories[1])

Whether those assertions actually aim at anything I checked with mutation testing. Remove setMaxConnPerRoute and the first one sees 5 and goes red; build a new factory per builder and the second goes red. I ran both.

“Why not Redis, or a queue?”#

This is a question I actually got while doing the work — shouldn't this be solved by changing the architecture? Because the harness existed, I could measure before choosing.

One more note on queueing. Moving moderation onto a queue does change something. What it changes, though, is not performance but the product's promise.

The gate is fail-closed, so a post must not be visible before it is screened. The only available shape is therefore not “publish now, screen later” but “an asynchronous job that does not publish until screening finishes.” That does not remove the latency; it detaches it from the request thread, and the outbound limit is unchanged. In exchange, status display, retries, deduplication and failure notification all become new work.

So I wrote down when that design becomes justified, ahead of time, to avoid adopting it later on a feeling: if post creation p95 still misses the target after the limit has been deliberately raised, or if the external API's p99 approaches our own timeout, then it goes asynchronous.

What this article does not claim#

  • These are not production numbers. The load generator, the application, the stub and the database share one machine's CPU. Absolute throughput is meaningless; only the comparison means anything.
  • 800 ms is a value configured in the stub, not the real API's latency distribution. The real gain depends on that distribution.
  • Each condition was run once. I did not repeat runs to see variance.
  • 3.17× belongs to these conditions. Change the external latency or the inbound concurrency and the ratio changes with it.
  • max-per-route = 50 was not measured against real traffic. It swaps “a five nobody chose” for “a fifty with a stated reason,” and it gets set again when real numbers exist.
  • I never observed 50 binding. Under this load, inbound concurrency caps first at thirty-two.
  • There was no incident. This came out of a pre-launch review; nothing in production has ever hit this limit.
  • This is not a complaint about the AWS SDK or Apache HttpClient. A library is entitled to its own defaults. The problem is that its default had become my service's policy and nobody knew.
  • It is not merged yet. The path touches the security gate, so the repository's rules require a written review first.

Wrapping up#

To summarise.

  • When throughput sticks to a number, find the layer that produced that number first. Raising threads and database pools comes after.
  • A library I never chose was setting my service's concurrency policy. It lives on the runtime classpath only, so reading cannot find it — measuring can.
  • Removing a limit and setting one are different acts. Throughput rises the same either way, but one of them has a number written down and the other does not.
  • A fix made of configuration fails nothing when deleted. So the fact that the value took effect is itself what has to be asserted.

If one line survives, let it be this. A default nobody chose still behaves like a policy. It is just a policy nobody owns — and usually one you do not know exists until you measure.
