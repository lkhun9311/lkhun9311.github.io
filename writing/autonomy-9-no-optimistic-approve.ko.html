개인 프로젝트#Driving Data Studio

자율주행 데이터 플랫폼 09. 운영 콘솔은 승인 버튼을 눌러도 왜 바로 「승인됨」을 띄우지 않을까

2026년 10월

목차

  • 이 글의 예상 독자
  • 승인 한 번의 흐름
  • AWS 콘솔의 문법을 빌렸습니다
  • 실행과 검증은 CI/CD 화면에서 빌렸습니다
  • 화면이 상태를 앞지르지 않게 하는 다른 자리
  • 이 글이 주장하지 않는 것
  • 마치며

이 플랫폼에서 사람이 맡는 일은 하나입니다. Release 후보를 보고 승인하거나 거부하는 큐레이터의 일입니다. 큐레이터가 쓰는 화면을 Driving Data Studio라는 이름의 운영 콘솔로 만들고 있습니다. 로그를 보고 품질 검사 결과를 보고 Release를 만들고 승인하는 화면입니다.

화면 설계에서 가장 먼저 부딪힌 것은 버튼 하나였습니다. 큐레이터가 「승인」을 누르면 화면은 언제 「승인됨」을 띄워야 할까요. 웹 화면의 흔한 답은 「바로」입니다. 서버 응답을 기다리지 않고 화면을 먼저 바꾸는 낙관적 갱신(optimistic UI)이 반응이 빠르다고 느끼게 합니다.

이 플랫폼에서는 그 답이 맞지 않습니다. 승인은 요청을 받은 순간 끝나지 않습니다. 서버는 승인 요청을 기록한 뒤, 고정한 파일의 Checksum을 다시 확인하고 Iceberg Snapshot에 Tag를 겁니다. 그 확인이 실패하면 Release는 승인되지 않고 막힘(blocked) 상태로 갑니다.

화면을 먼저 「승인됨」으로 바꾸면 확인이 실패한 Release를 큐레이터는 승인된 것으로 보고 그 id를 학습 작업에 넘길 수 있습니다. Loader는 막힌 Release를 거부하므로 데이터가 잘못 나가지는 않지만 큐레이터는 학습 작업이 실패한 뒤에야 승인이 안 됐다는 것을 압니다.

이 글의 예상 독자#

  • 계약 상태를 다루는 운영 화면을 설계하는 분
  • 낙관적 갱신(Optimistic UI)을 어디까지 써도 되는지 고민하는 분
  • AWS 콘솔 · CI/CD 도구의 화면 문법을 사내 도구에 가져오려는 분

승인 한 번의 흐름#

그래서 화면의 상태 배지는 세 단계로 움직입니다. 요청이 접수되면 「승인 처리 중」을 띄우고 「승인됨」과 「막힘」 같은 결과 상태는 그 결과를 알리는 이벤트가 도착한 뒤에만 띄웁니다.

[승인] 클릭 → POST /releases/rel_…:approve
  → Postgres: status=approving + outbox 1행 (한 Transaction) → 202 {command_id}
  → 화면: 「◷ 승인 처리 중」
  → Debezium → release.events(approving) → release-service: 재확인 · tag · checksum 고정
  → outbox → release.events(approved) → console-gateway SSE
  → 화면: 「✓ 승인됨」 + 알림 바 + 모니터 기록
  (실패 시) release.events(blocked, 사유) → 빨간 알림 바 + 사유 + 추적 링크

API는 승인 요청을 받으면 처리 결과가 아니라 202 Accepted와 명령 id를 돌려줍니다. 화면은 「승인 처리 중」을 띄우고 기다립니다. GET /commands/{id}로 명령 상태를 따로 물어볼 수 있고 결과는 release.events 이벤트가 SSE로 화면까지 밀어 줍니다.

이 규칙은 연결이 끊긴 상황에도 이어집니다. SSE 연결이 끊긴 동안에는 승인, 거부 같은 변경 버튼을 막습니다. 그동안 화면이 보여 주는 Release 상태는 낡았을 수 있습니다. 낡은 화면에서 누른 요청은 서버가 If-Match version 검사로 거절하지만 큐레이터는 거절 응답을 받고 나서야 그 사실을 압니다. 버튼을 미리 막아 두면 그 왕복이 생기지 않습니다. 이미 보낸 명령의 상태는 연결이 끊겨도 GET /commands/{id}로 볼 수 있습니다. 다시 연결되면 먼저 조회로 화면을 맞추는데 조회 응답에는 그 상태가 반영한 마지막 이벤트 번호가 들어 있고 화면은 그 번호 다음 이벤트부터 이어 받습니다.

AWS 콘솔의 문법을 빌렸습니다#

화면 형태는 몇 번 바뀌었습니다. 처음에는 Open WebUI 채팅을 주 화면으로 두고 플랫폼을 대화로 다루게 했는데 ChatGPT 화면처럼 보였습니다. 큐레이터의 일은 대화보다 「목록에서 Release를 고르고 → 상세를 보고 → 승인하거나 거부한다」의 반복에 가깝습니다. 그 반복은 클라우드 콘솔이 리소스를 다루는 방식과 같아서 여러 시안을 나란히 놓고 AWS 콘솔 형태를 골랐습니다. 어두운 콘솔 시안도 그렸지만 표와 상태 배지가 많은 화면에서는 밝은 쪽이 읽기 쉬웠습니다. AWS 콘솔이 쓰는 디자인 시스템 Cloudscape가 Apache-2.0으로 공개돼 있어, 상세 화면의 탭 구성, 빈 상태, 삭제 확인 같은 규칙을 그대로 가져올 수 있었습니다.

Cloudscape에서 가져온 규칙 가운데 이 프로젝트에 맞게 다시 정한 것이 셋입니다.

  • 측면 메뉴에는 구조만, 상단 바에는 도구만. 검색, 알림, 도움말, 설정, 계정, 그리고 화면 아래에 CLI 서랍을 여는 버튼은 상단 바에 둡니다. 측면 메뉴는 데이터(Logs), 품질(Gates, Quarantine), 출고(Releases), 운영(Events) 네 묶음과 맨 위 대시보드로 이뤄집니다.
  • 메뉴는 그 페이지가 동작하는 날 나타납니다. 「준비 중」으로 흐리게 둔 메뉴는 두지 않습니다. 흐린 메뉴는 큐레이터가 눌러 볼 때마다 아직 없다는 것만 확인하게 하고 일정이 밀리면 그 자리가 지키지 못한 약속으로 남습니다. 그래서 첫 단계(M1: 테이블, 품질 검사, Release)에는 위의 여섯 메뉴만 있고 장면 검색 메뉴는 검색 기능을 만드는 마지막 단계(M5)에 나타납니다.
  • 화면 = API = CLI. 화면의 리소스 이름(Releases)은 API 경로(/releases)와 CLI 명령(dp release)과 같습니다. 모든 화면의 CLI 서랍에 지금 보는 작업과 같은 dp 명령을 옵션까지 채워 보여 줍니다. 화면에서 고른 Release를 학습 스크립트로 옮길 때 이름을 바꿔 적을 일이 없게 하려는 것입니다. 같은 데이터가 나온다는 보장은 이 규칙이 아니라 Release의 Manifest가 맡습니다.

실행과 검증은 CI/CD 화면에서 빌렸습니다#

Release를 만들고 검증하는 과정은 빌드 파이프라인과 모양이 비슷합니다. 그래서 세 도구의 화면 문법을 빌렸습니다.

화면빌린 곳보여 주는 것
실행 상세GitHub Actions의 작업 그래프와 단계 로그수집 → 정규화 → 검사 → 고정 단계가 어디서 멈췄는지, 그 단계의 로그
단계 격자Jenkins의 stage view실행 여러 개를 가로로 놓고 같은 단계끼리 비교
리소스 트리Argo CD의 리소스 트리Release · Manifest · 파일 · Tag를 나무로 그리고 동기화 축과 건강 축 두 가지로 색칠

리소스 트리의 두 축은 Argo CD에서 가져왔습니다. Argo CD는 git이 원하는 상태와 클러스터를 비교합니다. 이 콘솔의 동기화 축은 승인 때 고정한 Manifest를 원하는 상태로 두고 저장소의 실제 bytes와 비교해 「일치, 불일치」로 칠합니다. 건강 축은 그 리소스의 처리 상태를 「정상, 막힘, 진행 중, 없음」으로 칠합니다. 예를 들어 승인 전에는 Tag가 아직 없으므로 「없음」이고 필수 검사가 미완료면 그 Gate는 「막힘」입니다. 파일 하나의 Hash가 다르면 동기화 축에서 그 파일부터 Release까지 이어지는 경로가 빨갛게 칠해집니다.

화면이 상태를 앞지르지 않게 하는 다른 자리#

승인 버튼과 같은 원칙이 세 군데에 더 걸려 있습니다.

화면에는 AI 어시스턴트가 들어갑니다. 하단에 접혀 있다가 오른쪽 패널, 전체 화면 채팅으로 펼쳐집니다. 어시스턴트가 스스로 부를 수 있는 것은 조회 API뿐입니다. 무언가를 바꾸자는 제안은 정확한 API와 dp 명령이 적힌 확인 카드로 나오고 큐레이터가 카드의 버튼을 누르면 콘솔이 큐레이터의 권한으로 그 요청을 보냅니다. 어시스턴트의 답은 상태의 근거가 되지 않습니다. 어시스턴트가 「승인됐다」고 말해도 상태 배지는 이벤트가 와야 바뀝니다.

로그인은 Google과 GitHub OAuth만 둡니다. 허용 목록에 있는 계정만 들어오고 역할(관리자, 큐레이터, 보기 전용)은 API가 검사합니다. 화면에서 보기 전용 사용자의 승인 버튼을 숨겨도, 누군가 API를 직접 호출하면 화면은 그 요청을 막을 수 없기 때문입니다.

언어는 한국어, English, 日本語를 고를 수 있고 ID, CLI, 로그 원문, 리소스 이름은 번역하지 않습니다. rel_01J8XQ7…이나 Releases가 언어마다 달라지면 화면과 CLI와 API가 같은 것을 가리킨다는 규칙이 깨집니다.

이름도 같은 이유로 하나만 씁니다. 콘솔의 이름은 네 번 바뀌었습니다. Autonomy Console이라는 이름으로 시작해, 형제 프로젝트 Retrieval Studio와 짝을 맞춰 Autonomy Studio, 자율주행 전용임을 드러내려고 AV Data Studio로 갔습니다. 「AV」는 업계 안에서는 autonomous vehicle의 약자로 통하지만 업계 밖 영어에서는 audio-visual로 읽히고 한국어와 일본어에서는 성인 영상의 뜻이 먼저 떠오릅니다. 그래서 일본어 화면에서만 Driving Data Studio로 바꿔 봤지만 이름이 둘이면 문서와 스크린숏마다 둘이 같은 제품이라고 설명해야 했습니다. 지금은 세 언어 모두 Driving Data Studio 하나를 쓰고 약자 DDS는 ROS 2의 통신 미들웨어와 겹쳐 쓰지 않습니다.

이 글이 주장하지 않는 것#

  • 화면은 아직 목업입니다. 디자인 캔버스에 그린 화면이고 React와 Cloudscape로 구현하지 않았습니다. 목업의 Release 수, 처리량, 시간은 설명용 예시입니다.
  • 목업 가운데 Log 뷰어의 이미지, 라이다, 지도, 카메라별 시각 차는 Argoverse 2 val 로그를 일회용 스크립트로 렌더링한 실제 데이터입니다. 플랫폼이 만든 화면은 아닙니다.
  • 「낙관적 갱신을 쓰지 않으면 느리게 느껴진다」는 비용은 재지 않았습니다. 승인처럼 드문 작업에서는 기다림을 받아들이기로 정한 것이고 목록 필터처럼 계약과 무관한 조작은 즉시 반영합니다.

마치며#

아직 정하지 않은 것은 「승인 처리 중」이 길어질 때입니다. 재확인이 몇 분 걸리는 동안 큐레이터가 화면을 떠났다가 돌아오면 무엇을 보여 줄지, 언제 「처리 지연」으로 바꿀지는 실제 재확인 시간을 재고 정합니다. 연작은 여기까지이고 이 설계를 구현하면서 실제로 잰 값이 생기면 그때 측정 글을 따로 씁니다.

읽어 주셔서 감사합니다.
