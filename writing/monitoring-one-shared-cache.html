Merging Three Monitoring Caches Made Them Erase Each Other
Rules that separation had been keeping by accident all had to be written down.

I build the backend of an internal cloud admin console. By part four all three screens were fixed individually. First data was fast everywhere, and each screen was still collecting the same source separately. Node metrics were read twice, by the dashboard and by physical nodes. Instance metrics were read twice, by the dashboard and by virtual resources.

Merging the three caches into one removes that duplication. It looked small: three data structures becoming one. The actual work was much larger, because everything that separation had been protecting by accident became a contract that had to be written down.

A regression showed up the moment they merged. Leave one screen open and the other screen's last value vanished from the cache; re-entering took 5,115 ms. This part writes those contracts down one at a time: carrying partial failure per item, not sharing a mutable DTO, and not letting a failure settle as an empty value.

Who this is for#

  • Anyone about to merge several similar caches into one
  • Anyone whose several consumers each read the same source
  • Anyone who started with “a refactor to reduce object count” and ended up rewriting contracts

Three problems in the structure before merging#

First, duplicate collection. When the three screens' 15 second cycles overlap, the same nodes and instances are read several times. As screens are added, load on the source grows in proportion to the number of consumers.

Second, a shared mutable DTO. Each screen filled the object returned by the structure cache with metrics in place. If one thread mutates while another serialises, two different moments end up in one payload. Swapping the pointer atomically does not help: if the objects inside are shared and mutable, it is not an immutable snapshot.

Third, treating an outage as an empty value. When an infrastructure read or a metric fetch failed and an empty list went out as the new healthy snapshot, the last good screen was overwritten with zero. Parts three and four met this problem screen by screen.

Partial failure is carried per item#

The dashboard shows node and instance results combined. Rolling successfully collected nodes back to an earlier generation because the instance metric failed lets one dependency's outage age the whole screen. Accepting an empty instance list as a new value overwrites the real VM count with zero.

So the five branches from part three were lifted into a common judgement and applied per item.

FRESH              publish new data with a new generation
EMPTY_VALID        the target count is zero, so publish the empty data as healthy
INFRA_UNAVAILABLE  carry the previous data + degraded
FETCH_FAILED       carry the previous data + degraded
NO_VALID_METRICS   carry the previous data + degraded

Merging produced a regression immediately#

The most visible thing after merging was leaving a page and coming back.

The single producer computed only the paths currently subscribed and published them as one map, replacing the previous map wholesale. With only the physical nodes screen open, a refresh leaves only nodes in the newest generation. The previous dashboard value disappears from the cache.

Connecting to the dashboard after that leaves nothing to send at once, so it waits a full collection cycle. Measured, that was about 5,115 ms, and connecting again right away was 16 ms.

The contract the separated caches had been keeping silently was this. “A refresh on another path does not erase my last value.” Merging removed that contract, and nobody had ever written it down.

latestGeneration       the set of paths included in this collection
lastPageByPath[path]   the last successful payload for each path

publish(generation):
    replace latestGeneration
    merge only the included paths into lastPageByPath

onConnect(path):
    send lastPageByPath[path] immediately
    if the path is absent from latestGeneration:
        request a refresh

Slow consumers were separated from collection#

An SSE send can block on a slow client. Holding the collection lock until the broadcast finishes lets one client's network delay the next collection. So the collection token is released right after the new generation is published, and sending was handed to a separate component.

Putting per-session tasks on an ordinary executor queue can starve them: in a small pool the leading sessions are accepted repeatedly while the trailing ones keep getting rejected. The sender uses a ready deque and resident workers.

  • Each session keeps only the highest pending generation.
  • A session enters the queue once.
  • After a worker sends, a new pending item puts the session back at the tail.
  • Anything at or below an already-sent generation is dropped.
  • A closed session is re-checked immediately before sending.

The synchronous send itself did not go away. When the number of simultaneously blocked sessions exceeds the number of workers, sending is still delayed. Asynchronous I/O and pre-emptive eviction of slow sessions remain as separate work.

What to check when merging shared state#

Cache consolidation is not a refactor to reduce object count. These questions need answers.

  • Is the last value preserved for a consumer that is not currently subscribed?
  • Does one source's failure roll back another source's success?
  • Is an empty value a healthy zero or an undecidable one?
  • Are the objects inside the payload immutable per generation?
  • Can a new value and an old one be sent out of order?
  • Does a slow consumer block the producer?
  • With several processes, are there several producers?

What this article does not claim#

  • These are not production statistics. Sequential single-user measurements.
  • The final figure for virtual resources is not a direct comparison. Some metrics were absent at re-measurement, so part four's per-screen measurement is the reference.
  • I do not claim the slow consumer problem is solved. It was separated from collection; sending is still delayed once blocked sessions outnumber workers.
  • Several producers were not addressed. The last question in the list above is still open.

Wrapping up#

Five parts, and what is left of them.

  • “No case for a change” is a different sentence from “I did not measure.” Where I measured was not where users waited.
  • “Build it ahead and serve it” becomes one line only once you decide who builds and who publishes.
  • “Empty” is not an observation, it is a value that needs interpreting.
  • The gate that finishes last sets the screen's delay.
  • What separation was protecting has to be written down as a contract when you merge.

Shared state does not get simpler by being gathered in one place. It becomes manageable only once every implicit contract has been made explicit.

More durable than the performance won by removing duplicate collection is having written these meanings into the code and the tests. Thank you for reading all five parts.
