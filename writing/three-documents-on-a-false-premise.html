Three Documents I Wrote Rested on a False Premise

Scope. In July 2026 I prepared an upgrade of a customer's live OpenStack-based private cloud portal to a release 2,255 commits ahead of the one they were running. I do not name the product, the version numbers, the customer, or ticket IDs. What I actually did was the isolated reproduction and the procedure and runbooks — this is not a record of me performing the production cutover. The numbers come from mixed sources — the migration results (3 of 3, 0 failures) are from the isolated container; the commit counts, the release comparison and the 48-table column check are repository and schema surveys; the startup failure is local troubleshooting.

The shape of the job: two breaking changes — the authentication model changed and reset every user's password, and two database schemas were merged into one. It is a production database, so there is no zero-downtime path and a rollback route is mandatory. And the official migration guide was written against a version one step above the one in the field.

The natural way to write a procedure here is to read the documents and reason. That is how I wrote three of them. And the premise of all three was wrong. I did not learn that by reasoning more carefully. I learned it by standing the old version up in an isolated environment and running the part that could be reproduced end to end — and, in the middle of that, by reading the guide again, properly this time.

Are they even the same?#

A reproduction needs a starting point. But the field had received two copies of the old release build, downloaded more than five months apart (2025-10-31 and 2026-04-15, 166 days). Before choosing which one to treat as the baseline, I checked whether they were the same thing.

diff -rq  <release A>  <release B>      # no differences (exit 0)
find . -type f -exec md5sum {} \;       # every file matches on both sides

The contents were identical; the only difference was file mtime — the moment each was downloaded. Either one could serve as the baseline, so I recorded that and moved on.

The step looks trivial and gets expensive to have skipped. If the reproduction later fails, you can no longer tell "is my script wrong, or was the starting point different?" The first condition of a reproduction is that the starting point is pinned, and that is something you check rather than assume.

I did not trust date order#

Next was identifying the delta: which patches the old baseline already contains and which it does not. I checked the baseline schema for marker tables, one at a time.

One thing caught here. The baseline had the October patch but not the July and August ones before it.

So the baseline is not a snapshot cut at some date. It is a curation — somebody picked what that line needed. Which means the policy "sort by date and apply everything after the cut" guarantees nothing. You either re-apply something already in, or skip something that should have gone first.

I concluded that the exact list, ordering and idempotency of the delta had to be established by reproduction, not by inference. That is the direct reason the reproduction script exists.

The survey also closed an item an earlier document had left open as "needs checking". The old release build's patch folder did not contain the intermediate-version migration SQL at all — so that migration was not included, it had to be part of the delta, and being the earliest by date it had to be applied first.

The method itself was different#

Then I read the official migration guide properly. And met this sentence.

This guide is not sequential patch application. It rebuilds a new database and migrates the data across.

All three documents I had written assumed "apply the patches in order". I had been building a delta list, deciding an ordering, reasoning about idempotency. That whole body of work was the procedure for a different method.

The delta survey did not become worthless — knowing which patches are in the baseline still matters for a rebuild-and-migrate. What became worthless was the conclusion that applying patches in order gets you there.

I did not delete the three documents. I annotated each with the correction. Delete them and the reasoning disappears with them, and the next person at that fork reasons their way to the same place. Leave them and the document carries "this premise was wrong, for this reason".

The lesson is not "read the guide first". The guide was there from the beginning and I did look at it — more precisely, I skimmed it. The sentence about the method was in the overview, not in the procedure list, and I had gone straight to the procedure list. What you went to a document for and what the document is trying to tell you are not always the same thing.

The part I made deliberately imprecise#

The reproduction became a one-shot script. Bring up a database on an isolated port, build the old version, back it up, rebuild the new version, migrate the data, update the version marker, verify.

start isolated DB
  → build old version (both schemas) + plant test data
  → back up
  → rebuild new version
  → migrate data
  → update VERSION
  → verify

In the migration step I made a deliberately imprecise choice. The guide specifies the column mapping in a table, and I did not have that table at the time. So the script copies only the intersection of columns present in both the source and target, with INSERT IGNORE.

This is not a correct migration. That was the point. The script's job is not to move data correctly; it is to expose which tables break. It absorbs schema drift and keeps going, and the tables that fail land in the log — so the failure log becomes a candidate list of schema gaps. Not a complete one — tables absent from the target are skipped, and INSERT IGNORE absorbs missing columns and coercion warnings without calling them failures. What surfaces is what breaks, not everything that differs.

To see whether data really moved, something recognisable has to move. I planted three kinds of test data first, each proving a different thing.

I did not hide what could not be reproduced#

The local environment has no OpenStack and no identity CLI. So everything entangled with the authentication change — creating the account and role tables, converting user identifiers from UUIDs to names, checking service accounts — could not be reproduced.

Two options. Drop those steps from the script and write "end-to-end success", or keep them and say they did not run.

The script logs an explicit SKIP or WARN at each of those steps. Then whoever reads the run log sees what was verified and what was not on the same screen. When an unverified stretch disappears from the log, the next person reads it as verified.

This is the same class of problem as Ten Bugs, Zero Failed Tests. Verification that cannot distinguish "did not run" from "passed" is worse than none — because it makes you believe there is some.

And one of them did blow up#

During preparation I fast-forwarded the customisation branch to the remote tip. Thirty-nine commits arrived at once, and the application exited on startup. Tomcat context initialisation failed constructing a cache bean and the process died with exit 1.

No enum constant ConfigureKey.FEATURE_SETTINGS
  ↑
BlocklistCache → RequestUrlServiceImpl → ConfigureServiceImpl.list → configures findAll

I walked the call path back from the stack trace to the enum conversion, then found the commit in the history: a feature had been rolled back, and that commit removed the enum constant, the patch SQL and the seed row together.

The code dropped the enum. But the existing database still had a row carrying that value. On boot the ORM tries to map that row onto the enum, fails, and a failed context load means the application cannot start at all.

What matters is what comes next. This class of defect surfaces one per restart — clear the first mine and the next one appears. So I compared three local databases against the code's enum constants exhaustively, established that this was the only stale key remaining, and only then deleted it.

The value of the incident is not the one-line DELETE. Tracing it exposed three defects in the field deployment procedure.

"Isn't a fresh install easier?" — I answered by counting#

A reasonable suggestion came up during preparation. If migrating is this involved, wouldn't a fresh install be simpler? It was plausible — this site had exactly one custom account, which makes the most tedious part of a migration trivial.

The way to answer was to count what gets deleted first.

What gets deleted is accumulated billing and metering history, plus audit and activity logs. Both are impossible to recompute: the source events are gone, so the only path back is migrating them from a backup. Meanwhile the actual VMs, volumes and networks are owned by OpenStack rather than by this portal, and the portal resynchronises them from the API, so they were never at risk in the first place.

That left "but migrating is hard". I answered that by measuring. For every table that had to be preserved, I compared the old and new columns through information_schema.

Zero columns added or dropped across 48 tables. An identical column set makes an INSERT ... SELECT path plausible — but this compared the set of column names and nothing else. Whether types, lengths, ordering, nullability, defaults, keys, foreign keys and triggers match is a question this comparison does not answer. The one confirmed difference is that the billing and metering tables change which schema they live in.

A vague worry — "migrating is hard" — was settled by one number, and the direction was decided: migrate, do not reinstall.

Nothing in that section is technically impressive; it is a few information_schema queries. The point is working out which part of a disagreement is countable. "Migration is hard" is not countable. "How many columns changed" is.

What this does not claim#

  • Not a claim that I completed the production migration. What I did was verify the reproducible part of the path and prepare the field procedure and installation runbooks. Not the whole path — the authentication stretch was not reproduced, as below.
  • Zero migration failures means "the script counted zero tables as failed", in an isolated environment. It does not mean the migration was correct or lossless. I noted in the document that reproducing against a real field dump would be the accurate test, and that was left as follow-up work. It was not done.
  • Copying the intersection of columns is not a correct migration method. It was built that way as a smoke test; a correct column mapping has to follow the guide's table.
  • The authentication stretch is unverified. No identity CLI locally, so it could not be reproduced, and the script leaves SKIP/WARN in its place.
  • Zero column change means no columns were added or dropped, and is a fact about those two versions. It does not mean types, lengths, ordering, nullability, defaults, keys, foreign keys and triggers are identical, and how far the comparison went was not established from the sources behind this article. Nor does it claim this product's history tables never change.

What is left is one line. Exactly one thing here was learned from the documents alone — that the method is a rebuild and a migration rather than sequential patching. And even that was missed on the first pass, and only surfaced from reading the overview rather than the procedure list. Everything else — that the two release copies were identical, that the baseline was a curation rather than a date cut, that the procedure pointed at a file that did not exist — came out of actually checking something. The one exception is the method, which came from reading the guide properly — and even that was missed on the first skim. A production database is the most expensive place to try something for the first time.
