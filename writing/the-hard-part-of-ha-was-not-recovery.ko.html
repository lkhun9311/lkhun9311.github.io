회사 업무#IaaS 백엔드

살아 있는 서버를 죽었다고 판정하면, 복구가 사고가 됩니다
스위치 장애로 컨트롤러끼리만 끊겼는데 멀쩡한 Compute를 장애로 오판해 VM을 대량 대피시킨 사고가 있었습니다. 감지를 더 정교하게 만드는 대신, 어느 신호를 믿을지부터 다시 정한 장애 대응 설계입니다.

2026년 9월

Instance HA는 Compute 호스트가 죽으면 그 위의 VM을 살아 있는 다른 호스트로 대피(evacuate)시켜 다시 띄우는 기능입니다. 자동 복구죠. 그런데 이 기능이 가장 위험해지는 순간은 죽지 않은 호스트를 죽었다고 판정할 때입니다. 그때 시스템은 멀쩡히 돌고 있는 VM을 강제로 옮기고 운이 나쁘면 데이터를 깹니다. 복구가 곧 사고가 됩니다.

이 글은 실제로 그 사고가 났을 때, 재발을 막기 위해 제가 단독으로 작성한 장애 대응 설계를 현황 · 원인 · 해결 순서로 정리한 것입니다. 마지막에는 감지 · 판정 · Fencing · 복구가 하나의 안전한 사슬로 이어지는 완성 아키텍처를 표와 그림으로 두었습니다.

먼저 범위를 밝혀 둡니다. 이 글은 제가 설계한 목표 아키텍처 관점의 정리입니다. 사고를 겪고 나서 「어떤 구조여야 하는가」를 기준으로, 감지 → 판정 → Fencing → 복구가 하나의 안전한 사슬로 이어지는 완성형을 그립니다. 구현은 팀이 이어받았고 세부 제품 반영 시점은 이 글의 초점이 아닙니다. 뒤에 나오는 복구 시간(RTO)은 실측이 아니라 단계별 산정치입니다. 고객사 · 서버 주소 · 호스트명 · 계정 같은 식별 정보는 쓰지 않았습니다.

이 글의 예상 독자#

  • 죽은 노드를 자동 복구하는 시스템(Instance HA, Masakari 계열)을 설계하거나 운영하시는 분
  • 네트워크 분단(partition)에서 자동화가 오히려 사고를 키우는 경우를 겪어 보신 분
  • 「노드가 죽었다」를 어느 신호로 판정할지, 그 신호를 얼마나 믿을지 정해야 하는 분
  • Split-Brain과 Fencing이 왜 「빠른 복구」보다 먼저 와야 하는지 궁금한 분

현황: 복구가 사고가 된 날#

사건은 한 줄로 요약됩니다. L2/L3 스위치 장애 때 Leader Controller가 살아 있는 Compute Node를 장애로 오판해, 불필요한 Instance HA(Nova Evacuate)를 대량으로 실행했습니다. 멀쩡한 VM들이 동시에 다른 호스트로 옮겨졌고 최악의 경우 원본이 살아 있는 채 복제본이 같은 볼륨에 붙어 파일시스템이 깨질 수 있는 상황이었습니다.

왜 살아 있는 서버를 죽었다고 봤나#

핵심은 이겁니다. 스위치가 죽으면 네트워크마다 상태가 달라집니다. 하나가 끊겼다고 전부 끊긴 게 아닙니다.

Controller 간 통신이 끊기면 클러스터의 Quorum이 붕괴합니다. 그러면 일부 Controller가 단독으로 「Compute가 죽었다」고 판단해 버립니다. 그런데 정작 MGMT는 살아 있어서 그 Compute의 Agent HeartBeat는 정상적으로 수신되고 있었습니다. 죽었다고 판정된 노드가 사실은 자기 상태를 또박또박 보고하고 있었던 겁니다.

내가 어떤 노드에 닿지 못한다는 건, 그 노드가 죽었다는 뜻일 수도 있고 나와 그 노드 사이의 길이 끊겼다는 뜻일 수도 있습니다. 둘은 완전히 다른 상황인데 밖에서 보면 똑같아 보입니다. 사고의 뿌리는 관측자의 고립을 대상의 장애로 오인한 것이었습니다.

감지가 아니라 신호에 자격을 매겼다#

흔한 처방은 「감지를 더 정교하게」입니다. 그런데 관측 정확도를 아무리 올려도, 관측자가 고립됐을 때는 무엇을 봐도 못 믿습니다. 그래서 정확도가 아니라 누구의 말을 믿을지를 정했습니다. 신호마다 신뢰도 등급을 매긴 겁니다.

핵심은 맨 아랫줄입니다. EXT Probe는 Compute 상태를 직접 검증하지 않습니다. Controller → 외부 방향의 도달성만 확인하므로 그것으로 Compute의 가동 여부를 판정하면 곧바로 「관측자의 고립을 대상의 장애로」 오인하게 됩니다. 사고가 정확히 그것이었습니다.

그다음 섞여 있던 판단을 둘로 갈랐습니다. 「정말 장애인가」와 「지금 안전하게 실행해도 되는가」는 다른 질문인데, 하나로 묶여 있어서 서로를 오염시키고 있었습니다.

기본값은 Hold: 여덟 중 일곱은 멈춘다#

복구를 잘못 실행하면 데이터가 깨지고 보류하면 사람이 개입할 시간이 생깁니다. 비대칭적인 비용이 판정을 정했습니다. 그래서 확신할 수 없으면 아무것도 하지 않는 것이 기본값이고 HOLD는 운영자 알림을 동반합니다.

옮기기 전에 전원을 확인한다#

복구를 해도 된다고 판정했다 해도, 옮기기 전에 반드시 해야 하는 일이 있습니다. 원본 서버의 전원이 확실히 내려갔는지 확인하는 것. 이게 없으면 Split-Brain이 납니다.

Compute-01 → VM-A still running  → write /dev/vdb   (원본 연결 유지)
Compute-02 → VM-A evacuated      → write /dev/vdb   (신규 attach)
        → 동시 write → filesystem corruption → 데이터 손상

그래서 원칙을 「no fencing = no recovery」로 세웠습니다. 전원 차단(Fencing)을 확인하지 못하면 복구하지 않습니다. 위험도는 스토리지 유형마다 다릅니다.

가로로 스크롤하면 나머지가 보입니다

스토리지 유형별 Split-Brain 손상 위험.

iSCSISCSI-3 PR이 있으나, 원본 연결 정리 전 신규 접근 시 충돌 가능
LVMSCSI PR 미지원. 동시 write 시 VG/LV 메타데이터 손상 위험 높음
NFSFile Lock 기반이라 동시 mount/write 시 일관성 보장 불가

Fencing은 IPMI 전원 제어로 합니다. 그런데 여기 전제 조건이 하나 붙습니다. BMC(전원 제어용) 네트워크가 MGMT와 같은 물리 스위치에 있으면 스위치가 죽을 때 IPMI도 같이 끊깁니다. 그러면 전원을 내릴 수단 자체가 사라져 Fencing이 불가능합니다. VLAN 분리만으로는 부족합니다. 스위치가 통째로 죽으면 그 위 VLAN도 전부 사라지니까요. 그래서 BMC 전용 물리 스위치를 전제 조건으로 못 박았습니다. 사고 당시 BMC 네트워크는 부재였습니다.

복구 절차는 네 단계로 갈랐습니다. Detect → Verify → Fence → Recover. 이 중 Fence 단계에 작지만 중요한 순서가 있습니다.

1. ipmitool chassis power off        (BMC 전용 물리 스위치 경로)
2. 최소 5초 대기                     (전원이 실제로 내려갈 시간, 즉시 조회 금지)
3. ipmitool chassis power status  →  반드시 off 확인
4. Storage 추가 확인                 (유형별로 상이)
5. Nova Evacuate 실행

2번이 핵심입니다. 전원을 내린 직후 상태를 조회하면 아직 off가 아닙니다. 대기 없이 확인하면 「off 아님」으로 읽혀 멀쩡한 Fencing을 실패로 오판하거나, 반대로 낙관적으로 넘어가 내려가지도 않은 서버의 VM을 옮깁니다. 명령을 보내는 것과 그 결과를 확인하는 것은 다른 일이고 그 사이에 대기를 넣는 것이 이 절차의 전부라고 해도 됩니다.

잠금은 분산 합의가 아니다#

「누가 복구를 실행할지」를 통제하는 방식도 정해야 했습니다. 사내에는 이미 Galera가 있어서 그 DB Lock을 쓰자는 흐름이 있었습니다. 세 방식을 같은 기준으로 뜯어봤습니다.

핵심은 DB Lock이 분산 합의가 아니라는 점입니다. 잠금은 중복 실행을 줄이지만 분단 상황에서 양쪽이 각자 Lock을 잡는 것을 막지 못합니다. 목적이 Split-Brain 방지인데 그걸 구조적으로 못 막으면 목적을 달성하지 못합니다. 그래서 Pacemaker + Corosync를 1순위로(감지 ~5초 + STONITH 내장으로 「no fencing = no recovery」를 구조가 강제), 도입이 어려우면 etcd를 차선으로 권고했습니다.

복구는 얼마나 걸리나 (산정치)#

복구 체계를 설계하면 「얼마나 걸리냐」가 반드시 따라옵니다. 단일 숫자 대신 단계별로 분해했습니다. 다시 강조하지만 이건 실측이 아니라 설계 산정치이고 팀 합의가 필요한 값입니다.

RTO는 기술이 아니라 서비스 요구가 정하는 값입니다. 그래서 숫자 하나를 「달성했다」고 말하는 대신, 단계별 분해와 유형별 허용 기준, 그리고 TTL을 15초로 줄이는 단축 옵션과 그 대가(Jitter 오판 위험 증가)를 함께 남겼습니다. 줄일 수 있다는 말만 하면 결정을 도울 수 없으니까요.

완성 아키텍처: 네 층이 하나의 사슬로#

지금까지의 판단을 하나로 모으면 이 설계는 네 층이 순서대로 이어진 사슬입니다. 감지 → 판정·합의 → Fencing → 복구. 중요한 건 구성요소의 목록이 아니라 순서입니다. 앞 층을 통과하지 못하면 뒤 층으로 넘어가지 않고 되돌릴 수 없는 동작(대피)은 사슬의 맨 끝에만 있습니다.

사슬을 코드에 가장 가깝게 옮기면 이런 모양입니다(요지만).

if (!quorum())                 return HOLD;   // 관측자 자신이 합의 불가
if (agentHeartbeat.isFresh())  return HOLD;   // Compute 가 살아 있다고 직접 보고
if (extProbe.failed())         return HOLD;   // 나의 고립 의심 — 대상 장애 아님
if (!phase2.ready())           return HOLD;   // Storage · MQ · Nova API 미준비
fence(host); confirmPowerOff();               // 원본 쓰기 불능을 fail-closed 로 확인
evacuate(targets);                            // 여기까지 와야 비로소 옮긴다

이 사슬에서 감지, 기존 판정 로직, 복구의 상당 부분은 이미 코드에 있습니다. 자기 상태 점검 게이트(고립된 관측자는 복구를 넘김), 메타데이터 키(HA_Enabled · HA_Disabled) 기반 대상 선별, RecoveryMethod로 호스트를 고르는 부분이 그 자리입니다. 그리고 이 사슬의 안전 축인 Fencing과 합의(STONITH · Pacemaker/Corosync)는 설계가 지향하는 목표입니다. 이 축이 없으면 나머지가 아무리 정교해도 네트워크 분단에서 Split-Brain을 구조적으로 막지 못합니다. 그래서 설계는 이 축을 사슬의 가운데에 두었습니다.

한계: 이 글이 주장하지 않는 것#

  • 이 글은 목표 아키텍처의 정리입니다. 제 몫은 17쪽 장애 대응 설계서였고 구현은 팀이 이어받았습니다. 위 사슬은 「이렇게 동작한다」의 완성 확인이 아니라 「이렇게 동작해야 한다」의 설계도입니다.
  • 남는 위험을 분명히 해 둡니다. 안전 축인 Fencing이 실제로 켜지기 전까지는, 네트워크 분단에서 Split-Brain 방지가 구조적으로 보장되지 않습니다. 그래서 자동 복구를 무조건 안전한 기능으로 봐서는 안 됩니다. 완성 조건은 Fencing 성공 확인 · BMC 불통 시 복구 중단 · Quorum 상실 시 Fail-closed입니다. 그리고 이 축이 서려면 BMC 전용 물리 스위치 같은 전제가 먼저 갖춰져야 합니다.
  • RTO ~100–160초는 실측이 아닙니다. 단계별 산정치이고 설계서에도 「팀 합의 필요」로 적혀 있습니다.
  • 오판한 것은 기존 복구 로직이고 그 뒤 재발을 막는 판정 체계를 제가 설계했습니다. 제가 만든 로직이 오판한 것이 아닙니다.
  • 제품명 · 버전 · 고객사 · 서버 주소 · 호스트명 · 계정은 쓰지 않았습니다. 네트워크 구성과 파라미터는 판정 로직을 설명하는 데 필요한 만큼만 일반화했습니다.

마치며#

이 설계를 하며 계속 되새긴 문장이 있습니다. ‘자동 복구의 품질은 얼마나 잘 복구하느냐보다, 얼마나 정확하게 하지 않느냐에서 갈린다.’ 그래서 감지를 더 정교하게 만드는 쪽으로 가지 않고 신호에 자격을 매기고 판정과 실행을 나누고 기본값을 Hold로 두었습니다. 여덟 중 일곱을 멈추는 설계가 나온 이유입니다.

「7개를 보류하면 진짜 장애 때 복구가 늦지 않느냐」는 반문을 예상합니다. 늦습니다. 대신 잘못 실행한 복구는 되돌릴 수 없습니다. Split-Brain으로 파일시스템이 깨지면 VM 하나가 아니라 볼륨 전체가 손상됩니다. 비대칭적인 비용이 이 설계 전체의 기조를 정했습니다. 자동화가 가장 위험해지는 순간은 자신만만할 때라는 걸, 이 사건이 오래 상기시켜 주었습니다.
