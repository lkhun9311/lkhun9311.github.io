head -c が文字を割って設計レビューが走りませんでした
バイトで切ると文字の途中で切れ、ツールはその引数を拒否します。

ひとりで作っているソーシャル投票プラットフォームで、設計文書を直すと 外部レビューが自動で回るようにしていました。結果ファイルはフォルダに 溜まっていきました。私はうまく回っていると信じていました。

そのレビューに渡す文字列をいま作り直してみました。 文字の真ん中で切れていました。レビューツールはそういう引数を受け取ると、 モデルに届く前に拒否します。

文書を head -c 60000 で切って渡していました。このコマンドは文字ではなく バイトを数えます。日本語や韓国語の文書では、3 バイトの文字の真ん中が 60,000 バイト目に なりえます。そしてそう失敗しても、どこにも印が出ませんでした。

この記事の想定読者#

  • 自動チェックを仕掛けて、結果フォルダだけ見て安心したことがある方
  • スクリプトで 2>/dev/null を癖のように書く方
  • 韓国語・日本語の文書をツールに流すパイプラインを扱う方

設計文書を直すとレビューが回るようにしていました#

ひとりで作るプロジェクトなので設計を見てくれる人がいません。そこで設計文書を直すと 外部ツールがそれを読んでいちばん深刻な問題 5 つを挙げるようにしました。 結果は時刻を付けたファイルで残ります。

「直すと」の範囲が狭いです。このフックは特定の編集ツールを使うときだけ 掛かります。シェルで直したり別の経路で書いたりするとそもそも呼ばれません。 あとでまた出てきます。

FILE="${1:-docs/DESIGN.md}"
OUT=".reviews/design-$(date +%Y%m%d-%H%M%S)-$$.md"   # $$ は後から付けた

DOC=$(head -c 60000 "$FILE")
PROMPT="この設計文書を容赦なくレビューせよ。...

DOC ($FILE):
$DOC"

codex exec --sandbox read-only "$PROMPT" > "$OUT" 2>/dev/null
exit 0

文書全体を渡すと引数が長くなりすぎるかと思って head -c 60000 で先頭だけ切りました。 2>/dev/null と exit 0 は レビューが失敗しても編集作業は止めないように入れました。

この 8 行にこの記事が扱う欠陥が入っています。 どれももっともらしい理由で入れたものです。 ただし最後の一つはコードの外にあります。あとで出てきます。

切る位置が文字の中でした#

head -c はバイトを数えます。ASCII は 1 文字が 1 バイトなので 両者は一致しますが、いま使うハングル音節は 1 文字が 3 バイトです。 (韓国語の文にも数字や記号のような 1 バイト文字が混ざり、4 バイトの文字や複数の断片でできた 絵文字もあります。)

残っているリビジョンを全部測りました#

「文字が割れうる」と「そのとき割れた」は別の話です。そこでこの文書の コミットとして残っているリビジョンを一つずつ取り出して2 つ見ました。 原本全体が有効か、そして先頭 60,000 バイトが有効かです。 原本がすでに壊れていたなら切った位置のせいではないからです。

blob=$(git rev-parse "$commit:docs/DESIGN.md")

git cat-file -p "$blob" | iconv -f UTF-8 -t UTF-8 > /dev/null                # 原本全体
git cat-file -p "$blob" | head -c 60000 | iconv -f UTF-8 -t UTF-8 > /dev/null # 先頭 60,000

横にスクロールすると残りが見えます

リビジョン大きさ原本全体先頭 60,000 バイト
7 月 17 日51,927 バイト有効切るものがない
8 月 2 日75,281 バイト有効文字の中で切れる
8 月 16 日111,834 バイト有効文字の中で切れる

8 月 26 日115,891 バイト有効文字の中で切れる
作業ツリー(いま)130,939 バイト有効文字の中で切れる

原本は 6 つとも有効です。ですから右の欄の壊れは 切った位置で生じたものです。6 万バイトを超えたコミット 4 つが全部 該当し、いま作業中のものを入れると 5 つです。 「半分くらい引っかかる」と書きかけて測ってから消しました。

この表が証明するのはここまでです。 「この Blob をこのコマンドで切ると有効でない UTF-8 になる」。 当時フックがその Blob を実際に受け取ったか、受け取ってどう終わったかではありません。 コミットのあいだに中間状態がもっとあったはずですが、それは残っていません。 いくつだったかも分かりません。

ですからこの記事が言えるのは「測れるものからは反例が見つからなかった」までです。 「何週間も一度も読まれなかった」はその観測から出た推論であって証明ではありません。

拒否したのは私が思っていたプログラムではありませんでした#

割れた文字が入った文字列を引数として渡すとどうなるか回してみました。 当時フックが使っていた形のままです。

$ codex exec --sandbox read-only "$(cat broken.txt)"

終了コード: 2
stdout: 0 バイト
stderr: error: invalid UTF-8 was detected in one or more arguments
        Usage: codex exec [OPTIONS] [PROMPT]

モデルまで行きません。引数を検査する段階で拒否します。 ですからレビュー結果が一文字も出ません。

ところがここで私はもう一度間違えました。 直したフックには timeout を付けてあり、その形で測って 終了コードが 125 だと書いていました。測り直すとこうです。

$ codex exec ... "<壊れた引数>"              → 2
$ timeout 60 codex exec ... "<壊れた引数>"   → 125

$ timeout 60 cat  "<壊れた引数>"             → 125
$ timeout 60 echo "<壊れた引数>"             → 125

下の 2 行が答えです。codex とは何の関係もありません。 この機械の timeout は GNU 版ではなく Rust で書き直された版 (uutils coreutils 0.8.0)で、自分の引数に有効でない UTF-8 があると 自分で拒否します。だから codex は起動すらしません。

2 つのプログラムが一文字も違わない 1 行目を出します。 どちらも同じ Rust の引数処理ライブラリを使っているからです。 違うのは2 行目と終了コードだけです。

横にスクロールすると残りが見えます

壊れた引数を拒否する 2 つのプログラムの違い。
拒否したもの1 行目2 行目終了コード
codexinvalid UTF-8 …Usage: codex exec …2
Timeoutinvalid UTF-8 …For more information …125

直す前のフックには timeout がありませんでした。 ですから当時出たはずの値は 2 です。125 は いま私が測りながら作った値で、それを当時起きたこととして書くところでした。

結果はどちらでも同じです。レビューが一文字も出ません。 しかし誰が拒否したのかを私は取り違えていました。 「ツールが文書を拒否する」と「ツールを呼ぶ殻が引数を拒否する」は別の話で、 直す場所も違います。

別々のものが失敗の信号を一つずつ消しました#

失敗そのものは騒々しいです。終了コードも 0 ではなく、メッセージもはっきりしています。 それが私まで届かなかったのは、私が入れた 3 つのせいです。 重ねて塞いだのではありません。失敗が残す信号が 3 つあって、 別々のものが一つずつ消しました。

1 つ目がいちばん厄介です。> はコマンドが始まる前に ファイルを作って空にします。ですからツールが何も出さなくてもファイルはできます。 本来なら「結果ファイルが無い」が失敗の信号のはずなのに、その信号ができません。

3 つ揃わないと見えないわけではありません。 2>/dev/null だけ外しても理由は残り、 exit 0 だけ外しても呼んだ側は 0 でない値を受け取ります。

だから4 つ目があります。これはコードの外です。 このフックは編集のあとに自動で呼ばれるのに、私はその出力がどこへ行くのかも、 終了コードを誰が受け取るのかも一度も見ませんでした。フォルダだけ見ました。 3 つを入れたのも私で、見なかったのも私です。

そのあいだフォルダは埋まっていました#

レビュー結果のフォルダを開くとファイルが増えていました。だから回っていると信じました。 数えるとこうです。

横にスクロールすると残りが見えます

設計レビュー結果ファイルの時期ごとの状態。
時期結果ファイル
7 月初 ~ 8 月 8 日中身のあるファイル 28 個
7 月 13 日 · 8 月 12~13 日0 バイトのファイル 5 個

この表は数えたもので、意味は数えたものではありません。 0 バイトのファイルが「呼んだが失敗」なのかは当時 stderr を捨てていたので分かりません。 ツールが見つからなくても同じ形になります。ファイルが無いことも「呼ばれなかった」の証拠ではありません。

そしてこう並べて見ると、おかしい所が目につきます。 0 バイトのファイルもそうですし、2 週間を超える空白もそうです。私が見なかったのは こう並べて見なかったからです。ファイルが増えることだけを ときどき確かめていました。大きさも日付の間隔も見ていません。

7 月 13 日の 0 バイトはこの記事の原因では説明されません。 そのとき文書は 6 万バイトより短く、切るものがありませんでした。 その失敗の原因は分かりません。

8 月初には中身のあるレビューが出続けました。そのとき設計文書が2 つあり、 新しく書いていたほうは31,965 バイトでした。6 万より短いので切るものがありません。 そのレビューの中身もその新しい文書のほうの話でした。 成果物にファイル名が書かれていないので中身を読んで推測したものであり、 どのレビューがどの文書を見たのかは成果物からは区別できません。

だからフォルダはもっと健康に見えました。 短いほうの文書を直すたびに、結果がきちんと積まれているように見えたのですから。

1 バイト捨てたら通りました#

直し方はパイプ 1 つです。有効でないバイトを捨てる変換を挟みます。

DOC=$(head -c 60000 "$FILE" | iconv -f UTF-8 -t UTF-8 -c)

同じ文書である場合と無い場合を並べて回しました。 ツールは codex-cli 0.153.4 で、直す前のフックと同じく timeout 無しで回しました。

[iconv 無し]
  切り取った断片 60,000 バイト → 終了コード 2 · stdout 0 バイト

[iconv を通して]
  切り取った断片 59,999 バイト → 終了コード 0 · 文書の題を正確に答えた

違いは 1 バイトです。割れた文字の断片 1 つを捨てると ツールが文書を読んで答えました。

上の数字は切り取った断片の大きさであって、実際に渡った引数の大きさでは ありません。前に指示文とファイル名が付き、コマンド置換は末尾に付いた改行を全部消します。 ですから 6 万より短い文書でも変数の中身が原本とバイト単位で同じではありません。

-c は末尾だけ捨てるのではありません。 入力のどこにあっても有効でないバイトを全部捨てます。ですから文書の途中が壊れていても 静かに消して進みます。ここではそれが望む動作ですが一般的にはそうではありません。

そしてこの環境の iconv(GNU libc 2.43)は末尾を捨てながら 診断文を出して 1 で終わります。警告ではなく失敗で終わることです。 いまのフックはその状態を見ていません。set -e の掛かったスクリプトだったら ツールを呼ぶ前に死んでいたはずです。

直したものとまだ直せていないもの#

DOC=$(head -c 60000 "$FILE" | iconv -f UTF-8 -t UTF-8 -c)   # 有効でないバイトを捨てる

ERR=".reviews/.last-design-err"                             # stderr を捨てない
timeout 240 codex exec -m "$MODEL" --sandbox read-only "$PROMPT" < /dev/null > "$OUT" 2>"$ERR"
STATUS=$?

if [ "$STATUS" -ne 0 ] || [ ! -s "$OUT" ]; then
  rm -f "$OUT"                                              # 0 バイトのファイルを残さない
  echo "[codex] design review FAILED (exit=$STATUS) — 原因: $(tail -2 "$ERR" | tr '\n' ' ')"
fi
  • 切ったあと有効なバイトだけ残します。上限はそのままで断片だけ捨てます。
  • ツールの stderr をログファイルへ送ります。失敗メッセージにそのログの最後の 2 行を付けて理由を画面まで持ってきます。 ログへ行くのはその 1 行の stderr だけです。前の iconv が出す 診断文はいまも外に漏れます。
  • 失敗したら 0 バイトのファイルを消します。「レビュー済み」と誤解されるのを防ぎます。
  • < /dev/null を付けました。このフックは裏で回るので、 ツールが標準入力を掴んで待つ状況になるとぶら下がっても誰も気づきません。 指示は引数で渡しているので本来は待ちません。引き継いだ入力が開いている場合を防ぐ仕掛けです。

ところがこの直した版も失敗をきちんと伝えません。 失敗分岐の最後が echo なのでスクリプトはまた 0 で終わります。 画面を見ない呼び出し側にはいまも成功です。前に挙げた 3 つのうち 3 つ目をまだ直せていません。

そして名前が重なります。エラーログはファイル 1 つだけなのでフックが重なって 回ると互いに上書きして、見当違いの失敗理由が付きます。結果ファイルの名前も秒単位の時刻 なので同じ秒に 2 つ回るとそれぞれがファイルを空にして書き、混ざるか壊れます。 いまは名前にプロセス番号を付けて結果側だけ塞いであり、ログ側はまだです。

結果ファイルにどの文書を読んだのかがいまも書かれていません。 ファイル名は時刻だけです。

「レビューが回った」と「この文書がレビューされた」は別の話なのに、 フォルダは前者しか見せません。この記事を書きながら、8 月のレビューがどの文書を見たものかを 成果物だけでは最後まで突き止められませんでした。

同じ欠陥を三度書き間違えました#

いちばん居心地の悪い部分です。この欠陥を最初に見つけた日、私は規則の文書にこう書きました。

実測: 設計レビューのフックは一度も成功したことがなかった (結果フォルダに design-* が 0 個)。

どちらも間違いです。その日すでに結果フォルダには design-* が 38 個あり、そのうち 0 バイトは5 個でした。 コミット済みのものだけ数えると 34 個で、残りの 4 個はまだコミット前でした。 「実測」と書いておいて数えていませんでした。 そしてその文をそのままフックのコードのコメントにも複写してありました。

これは私が直そうとしていた欠陥と同じ形です。 確認していないことを確認したかのように書き、書いてあるから確認済みだと信じました。 チェッカーが捕まえてくれる種類ではないので読み返すまで残ります。

正しい形はこうです。「一度も成功しなかった」ではなく「6 万バイトを超えたその文書は、 測れるリビジョンが全部引っかかる」です。そのあいだも別の結果ファイルは 積まれていました。ずっと見えにくい形で、だからもっと長く続きました。

そのとき「0 個」と書いたのがどこを見て書いたのかも、いまは分かりません。 単に見なかったのかもしれませんし、別のフォルダを見たのかもしれません。 確認した記録が無いということが、いま確認できる全部です。

そして3 つ目はこの記事を書きながら出しました。 終了コードを 125 と書きましたが、それは timeout が出した値でした。 直す前のフックにはその timeout がありませんでした。 つまりいま私の手元で作られた値を、当時起きたこととして書くところでした。

3 つとも同じ形です。測った場所と主張する場所が違いました。 「いまここで測るとこうだ」を「そのときそこでそうだった」に移して書きました。 この記事が扱う欠陥とまったく同じ間違いで、 私はそれを書いている途中にもう一度やりました。

限界: この記事が主張しないこと#

  • この記事が実際に測ったのは「いま残っている文書をそのコマンドで切るとどうなるか」です。当時フックが何を受け取ってどう終わったかは記録がありません。そのあいだは推論で、本文で区別し続けました。
  • 0 バイトのファイル 5 件の原因は確認できていません。当時 stderr を捨てていたので そのときの失敗理由が残っていません。再現で示したのは 同じ形を作る 1 つの経路であって、その 5 件の原因ではありません。 うち 7 月 13 日のものはその経路では説明されません。
  • 「何週間も読まれなかった」を証明できません。証明したのは 「測れるリビジョンは全部切れた位置が文字の中で、そういう引数をツールが拒否する」 までです。そのあいだの中間状態は残っていません。
  • 8 月中旬にレビューが全く無かった理由も分かりません。フックは特定の編集ツール にしか掛からないので別の方法で直せば掛かりませんが、 そのとき何で直したのか記録がありません。
  • 他の文書でも必ず引っかかるという意味ではありません。60,000 バイト目が 文字と文字のあいだに落ちれば引っかかりません。 この文書でそういうリビジョンが見つからなかっただけです。
  • 直したフックが長く回り続けるかはまだ分かりません。直したあとの成功記録が 4 件で、 失敗が見えるかはわざと失敗させて 1 度確かめました。

おわりに#

  • バイトで切るツールに韓国語を入れると文字の中で切れうります。 そしてそれは文書が上限を超えたあとからだけ起きます。 超える前は切るものがないので無事です。
  • > はコマンドより先にファイルを作ります。 失敗してもファイルが残り、ファイルがあれば人は「できた」と読みます。
  • 失敗の証拠は複数あり、覆いも複数あります。 結果・メッセージ・終了コードをそれぞれ別のものが塞いでいると、1 つ直しても見えません。
  • 「検証が回った」と「これが検証された」は別の話です。 成果物に何を見たか書かれていなければ、前者しか分かりません。

チェックを直したと書くことと、そのチェックが何をしたか数えることは別の仕事です。 私は前者だけやって、フォルダだけ見ていました。
