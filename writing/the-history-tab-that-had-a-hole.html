The Run History Tab Had a Path That Left No History
A run that looks like it never ran leaves not one row behind.

An earlier article fixed a snapshot scheduler whose failures never reached the screen. The failure reason and time were deliberately kept out of the schedule row and pushed to a follow-up. One row holds only the last failure, so everything before it still lives in the log.

So a history was built: one row per run. Success, partial success or failure, with the reason, shown newest first on a tab of the detail screen.

Reviewing it afterwards turned up a path that leaves no history row at all. The screen built to make failures visible had a hole in it.

Who this is for#

  • Anyone attaching a run history to a scheduled job
  • Anyone classifying failure reasons out of exception messages
  • Anyone deciding how to count succeeded and total on a job that can partly succeed

One row per run#

An append-only table, one row written by the batch per run. Three results: everything confirmed is a success, several targets with only some confirmed is a partial success, none at all is a failure.

The reason is split in two. One is a reason code, the other a description a person reads. The code lets the screen translate; the description keeps what differed between two failures that share a code.

Writing the history is best effort. Failing to write it must not flip the verdict on the backup itself. Once the recorder can change what it records, the record stops being evidence.

The screen built to show failures had a hole#

The batch first checks whether the target exists. If not, it stops the scheduler and returns. The code above it that writes history is only called when a run actually ran. So this path looks like no run happened, and not one row is written.

A schedule stopping because its target was deleted is correct behaviour. The problem is that nothing on the screen says so. The schedule is stopped and the reason is nowhere.

This defect runs directly against the point of the feature. The history tab exists to lift onto a screen what used to live only in the log, and the tab could not see this path.

Absent and unreadable were not separated#

Looking harder at the same place turned up what was behind it. The function that checks whether the target exists was swallowing lookup exceptions and returning “it does not exist”.

So one transient lookup error stops the schedule forever. And, as just seen, nothing records that. Put the two defects together and you get “backups stopped one day and nobody knows”.

The fix added a third answer. Present, absent, or check-failed: absent writes history and stops; check-failed writes history and does not stop, and looks again next cycle.

Moving to three answers took only a few lines. The hard part was noticing that two were not enough. A function named for whether something exists does not invite a third answer.

The reason did not come from the message#

The easy way to decide a reason is to classify the exception message. Contains “quota”, call it quota; contains “not found”, call it target missing. That was the first plan and it was dropped.

The counterexample arrived immediately. Looking up the role of the snapshot service user fails with a message that also contains “not found”. Read as target missing, the screen says “the target volume does not exist” when in fact a permission is unset. The operator goes looking for a volume that was never the problem.

So reasons are attached where the failure happens. The quota code at the place the quota check failed, the timeout code at the place the wait ran out. Only failures with no per-target tally at all, like a setup step, are classified by exception type.

Counting only successes makes the count contradict itself#

An instance with several volumes attached has several targets, so the row carries succeeded and total. It reads like 2/3.

There was a trap. Successes are counted first and failures later, so counting a few successes and then leaving through an exception gives succeeded 1, total 1. The screen reads “1/1 partial success”: everything succeeded, and it is called partial.

The fix adds the one uncounted failure to the total. It is one addition, and without it the screen states a sentence that contradicts itself.

Review rejected two hypotheses. Could the save and cleanup code that runs after a confirmed success mark a success as partial? Those methods swallow their exceptions internally, so no. Could counting instances and volumes together double-count? The total matched the target count exactly. Both were checked against the code and both were wrong.

The description was rewritten six times#

After the feature worked, the description on the screen was rewritten six times. The first one read “target volume a7c21f3e…: volume snapshot available timeout”.

Three things wrong. An identifier first pushes what a person reads to the back; the description repeated what the reason column already said; and English words came through untranslated.

The last version matches the words the quota screen uses: “volume snapshots short (1 needed / 0 available)”. When two screens call the same thing by different names, the operator has to work out whether it is the same thing first.

The count got an explanation too. The 3 in 2/3 is how many snapshots this run set out to make, and has nothing to do with the retention count. Left as a bare number it reads as “2 of the 3 kept copies survived”.

What this article does not claim#

  • No product name, version, customer, ticket number or server address, and no screenshots.
  • Whether this history hole ever left a schedule stopped and unnoticed in production is unknown. What was confirmed is that the code path allows it.
  • Verification goes as far as 19 batch unit tests, 3 controller slice tests, and opening the tab locally. The instance cases were checked on screen by inserting synthetic history rows rather than running real backups; the batch logic produces those reasons by the same table, but that path was not run end to end.
  • An adversarial review was attached and timed out twice on the size of the file, so no final summary came back. Its interim conclusion matched what is written here.
  • Something is left. The integration path at the execute level is heavy to mock and is not covered yet.

Wrapping up#

  • A feature built to make things visible has blind spots of its own. Attach a history and then count the paths that leave no history.
  • Check what an existence function returns when it could not look. Falling into “absent” turns a transient error into a permanent stop.
  • An exception message is written for a person. Branch on it and the day the wording changes, it drifts silently.
  • A screen that counts partial success has to say what the denominator is. A bare number lets the reader invent one.

Lifting failures onto a screen is wider than counting them. It is not done until you have looked for runs that look like they never ran.
