GPUaaS Input Length: One Character Still Cost 30 Tokens

There is an experiment that measures how much worse one tenant's tail latency gets when two tenants share a single GPU. I made that experiment declarable as a Kubernetes CRD, and the CRD writes prompt length in tokens: inputTokens: 256.

The Harness that generates the load takes characters: --premium-prompt-chars 200. What joined the two was ceil(chars/4), the estimate that roughly four characters make one token. Measured against the real tokenizer, that estimate puts 50 tokens against a measured 68 at 200 characters, and 10,000 against 7,695 at 40,000. The direction of the error flips.

So there was no way to invert "the character length that gives 256 tokens", and nothing to do but measure it and write it down. Two things turned up while measuring. One character still costs 30 tokens, and there are 21 places in one window where adding a character makes the token count go down.

Who this is for

  • Anyone who has specified an LLM serving load by prompt length
  • Anyone carrying a measurement protocol from a Kubernetes CRD into a runner
  • Anyone who has put "about four characters per token" into code

Two units that do not convert

  • The CRD registers the experiment's protocol. Once created, its spec never changes.
  • The Trace Generator builds prompts by character length, cut from one corpus.
  • The arrow joining those two units is what this article is about.

At first I thought the estimate would do

ceil(chars/4) was already in the code. It is what the Gateway uses to estimate a request's input tokens. Run backwards it gives 256 * 4 = 1024 characters, and passing that looked like it would do.

How well that estimate holds had already been measured in this repository.

On short prompts the estimate counts too few; on long ones it counts too many. No single correction factor fixes both. Tune it to 1.36x at 200 characters and it is off by 1.8x at 40,000.

The answer first

There is no function from characters to tokens. It has to be measured into a table, and the search for it cannot be a binary search.

With even one decrease, a binary search steps over an answer that exists. So the estimate is used only to narrow the window, and inside the window every length is swept.

One character costs 30 tokens

Character counts from 1 to 10 and the token count each produced.
characters12345678910
tokens30313131313131323231

One character, 30 tokens. Those 30 are the Chat Template, not the prompt. What goes to the Engine is not a prompt string but one request wrapped in roles, separators and a generation marker, so a single character of content still pays 30 tokens for the envelope.

And what was 32 tokens at 9 characters falls to 31 at 10. One character more, one token fewer.

The reason is Byte Pair Encoding. The tokenizer merges character pairs that often occur together, and cutting the string one character longer changes which pairs merge at the boundary. If a place that used to split into three tokens merges into two, the total falls even though a character was added after it.

There were 21 such places in that window: 9 chars 32 tokens → 10 chars 31, 21 chars 34 → 22 chars 33, 37 chars 37 → 38 chars 36, 44 chars 38 → 45 chars 37.

Several lengths give the same token count

Sweeping 301 lengths around 256 tokens produced 57 distinct token counts. On average 5.28 lengths give the same count. The most crowded count had nine.

These are the lengths that give 256 tokens.

1174  1175  1178  1179  1180  1181  1182  1185

One of the eight has to be chosen. The smallest, because at the same token count it moves the fewest bytes and it is the one choice that needs no further argument. It does one more thing in operation: widen the window and measure again, and the same rule picks the same value, so rebuilding the table does not move it.

Whether that rule is actually enforced was checked by breaking it. The recorded value was changed to 1175, also a length on the list but not the smallest, and two tests went red, the calibration one and the plan one.

Counted inside the Engine, not by importing a tokenizer

This repository already carried a decision not to import a tokenizer, and the reason is written down.

"Ask the Engine; do not import a tokenizer. The Engine is the authority. What its tokenizer and chat template do IS the number the criterion means. Putting a tokenizer here creates a second copy of a decision that lives in the served model, and the moment either moves they diverge."

That objection is right, so the counting happened inside the serving Image itself: digest-pinned vllm/vllm-openai@sha256:0a51ea…, which carries transformers 5.15.0 and tokenizers 0.22.2. The CPU Image was measured to hold the same versions. Not a copy of the implementation, the same one.

The model weights were never downloaded; 3.7 GB adds nothing to counting tokens. Only the four tokenizer files were fetched, and Qwen2.5's 0.5B, 3B and 7B were measured to carry those four byte for byte identical. Their repository revisions are three different strings. The revision alone could not say this; the per-file hashes did.

The table records what it was measured against

A table of values alone cannot be reproduced by the next person. These are what was recorded beside it.

The corpus hash was missing at first. The table's own first comment said it recorded the corpus and it did not, which means the corpus could change while two copies of the table still agreed with each other and every count in them was void. An external review caught it. Changing one character then turned the calibration test red with every count in it is stale.

Freezing it cut the comparison to the earlier table

After building the table its values went into the execution contract. The registration had frozen five things: the arrival rate, three weights, and the replay duration. Prompt length was not among them.

What that absence meant took two paid runs to learn. Two runs of the same study, the same seed 11, the same arrival schedule and the same corpus hash produced numbers that cannot be compared to each other.

What two runs satisfying the same registration actually sent. The three units differ.
what was sent2026-09-132026-10-01

the estimate ceil(chars/4)50 tokens294 tokens
what the Engine counted68 tokens256tokens
request Timeout30,000ms60,000ms

The third row is what this article's table did. In the 2026-10-01 run the Engine counted all 46,549 premium requests at 256 tokens. The declaration was inputTokens: 256, so declaration and execution agreed for the first time.

The 2026-09-13 run predates this table and used the generator's default of 200 characters. The Engine reads that length as 68 tokens, a number that corresponds to no inputTokens declaration at all.

So the isolated baseline moved between the two runs. Same card, same Engine, and the victim's tail latency is 69.5 ms against 174 ms. When each request carries a different amount of prefill the baseline moves with it, and a ratio against one run's baseline cannot be read beside the other's.

The frozen tuple went from five entries to nine: the two prompt lengths, the request Timeout, the two output caps, and the identifiers in the table above. Timeout is in there because it decides which requests get cut off. Freeze the lengths and leave the Timeout out, and the next comparison repeats this.

I misread the measurement once

The first measurement gave 2 tokens for both 11 characters and 200. It looked like a broken tokenizer.

It was not broken. In transformers 5.15.0, apply_chat_template(tokenize=True) returns a BatchEncoding rather than a list, and len() counts its two keys. The token count is the length of ['input_ids'].

A control was what revealed it. Encoding plain text with no template grows with length: 11 characters 2 tokens, 200 characters 25, 2,000 characters 250. With the template applied it is 31, 54 and 279. When the first grows and the second does not, the reading is wrong.

Had those numbers gone into the table, a table claiming every length is 2 tokens would have been committed.

What this does not claim

  • ⚠️ It says nothing about any other model's tokenizer. One was measured: Qwen2.5. The same repository holds a comparison with Phi-3 where one 40,000-character prompt read as 5,029 tokens under Qwen2.5 and 10,004 under Phi-3. Twice the count.
  • It does not establish that the character length chosen here equals what the Engine counts. The Engine is the authority, and a separate tool asks it again at run time. If the two disagree, the Engine is right and the table is stale.
  • "Smallest" means smallest within the window that was swept. A shorter length may exist outside it; that was not checked.
  • It does not claim the non-monotonicity appears at the same density everywhere. Three windows gave 21, 21 and 30 decreases; the ranges between them were not measured.
  • This table does not fill the CRD's status. It is one piece of carrying the measurement protocol into the runner; nothing yet writes a result back to the CRD.
  • It does not claim this calibration explains the earlier result. Between the two runs the prompt length, the request Timeout and the repetition count all changed, and no measurement separates the three. Nothing here licenses reading the tail ratio's move from 27.2 to 23.0 as an effect of the length correction.

Wrapping up

  • The estimate narrowed the window and was never the answer. A line fitted to three points had residuals under 1.1 tokens, and acceptance still required the measured count to match exactly.
  • The search method was chosen after checking monotonicity. Using a binary search without checking would have reported no answer where one exists.
  • Rather than importing a tokenizer, the counting ran inside the serving Image. The library versions were measured to match, which is what licenses calling it the same implementation rather than a copy.
  • What the table was measured against is recorded beside its values: the revision, the per-file hashes, the template hash, the corpus hash and the Image digest: five identifiers.

Where two layers meet in different units, asking whether a conversion function exists turned out to be worth more than looking for one.
