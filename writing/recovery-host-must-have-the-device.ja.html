Instance HA ⑦: GPU Instance は装置を持つホストにだけ行きます
復旧の evacuate は対象ホストを強制で指定するので、スケジューラが入りません。だから送る前に絞る必要がありました。

④編までは移してよいかを扱いました。 この編は移すと決めたあとの問いです。どこへ送るかです。

普段 Instance を作るときは、スケジューラが条件に合うホストを選んでくれます。ところが復旧で使う evacuate は対象ホストを強制で指定します。選んでくれる側がいません。

最初はこれが問題になると思っていませんでした。残りのメモリと CPU とディスクだけ見て送ればよいと 考えていたのですが、GPU を要求する Instance を装置のないホストへ送ると、かなりあとで失敗します。

この記事の想定読者#

  • GPU や PCI の装置を使う Instance を運用で扱っている方
  • 自動復旧のうち、どこへ送るかを決める部分に手を入れる方
  • 先に絞ることと、あとで失敗することの違いが気になる方
  • ④編を読んで、移すと決めたあとに何をするのか気になる方

復旧にはスケジューラが入りません#

違いは一行です。普段の作成は条件を渡せばスケジューラが候補を探してくれます。復旧の evacuate は すでに決まったホストへ送れと指示します。

だから選び間違えるとあとで失敗します。その失敗は遅く、原因もぼやけます。送る前に絞れば 「合うホストなし」として早くはっきり終わり、ほかの Instance の復旧はそのまま進みます。

Instance が何を要求するかを読みます#

まず Instance が何を要求するかを読みます。要求は flavor の追加項目にあり、種類が二つです。 一つは数量で、もう一つは特性です。

横にスクロールすると残りが見えます

flavor の追加項目から何を取り出すか。
追加項目の例取り出す結果
resources:VGPU=1特殊資源の要求が一つ
resources:VCPU=4除外。標準資源なので別に計算
trait:…=required必須の特性。消費されないので差し引かない
pci_passthrough:alias=…要求量として数えず記録だけ残す

標準資源の三つを除く理由は、その三つがどのホストにもあり、すでに残り容量として 別に計算しているからです。除いて残るのが装置の系統です。

横にスクロールすると残りが見えます

指定の仕方ごとに事前に絞れるか。
flavor の指定方法事前の絞り込み根拠
resource class で指定できる提供者の在庫にそのまま現れます
必須の特性で指定できる。ホスト単位ツリー全体の和集合で判定します
古い方式の別名で指定できない別名を resource class に解けないので記録だけ残して渡します

三行目がここでは閉じられない箇所です。古い方式の別名は resource class に解けません。だから記録だけ残し、最終の判定は実際に送る時点で行われます。

ホストが実際に持つものを数えます#

要求を読んだら、ホストが何を持っているかを数えます。ここで一度つまずきます。 装置はホスト自身ではなく、その下に付いた提供者に載っています。

そこでホスト名と同じ root を探し、その root を根に持つ提供者を全部集めて一つのツリーとして見ます。 在庫を合算して可用量を出し、特性はツリー全体の和集合として集めます。

二つの条件を両方満たすときだけ配置します#

配置は大きい Instance から順に詰めます。一つの Instance が一つのホストに入るには、二つの条件を 両方満たす必要があります。

# Instance 側から読むもの
  resources: で始まる項目から標準資源の三つを除いた残り  -> 要求する数量
  trait: で始まり値が required のもの                  -> 必須の特性

# 特殊な要求が一つもなければここで終わり。提供者への照会はしない

# ホスト側で数えるもの
  ツリーの全提供者の在庫を合算  -> 可用量 = 総量 - 予約 - 使用
  ツリーの全特性を和集合に      -> 保有する特性

# 配置
  標準資源を満たす AND 数量を満たす AND 必須の特性を全部持つ -> 確定して差し引く
  どのホストにも入らなければ、その Instance は失敗として記録

確定したら標準資源と特殊資源を両方差し引きます。同じホストに偏って載るのを防ぐためです。特性は 消費されないので差し引きません。

特殊な要求が一つもなければ、提供者への照会をまったくしません。装置を使わない 環境では、これまでの計算とまったく同じに動きます。

同じ場所で二度間違えました#

この処理で二度間違えました。二度とも静かに間違えました。失敗としてではなく、誤った配置として 現れました。

横にスクロールすると残りが見えます

同じ処理で二度間違えた箇所。
間違えたこと症状直し方
埋め込み項目ではなく再照会名前で照会して失敗し、要求が空になって GPU Instance を普通の VM と見なした埋め込みで来たものを先に使い、空のときだけ照会する
余裕がちょうど零かだけ見て繰り返しを中断前のホストが満杯だと、うしろの余裕があるホストを全部飛ばす。負の余裕も通す零以下で満杯と判定し、次のホストを評価し続ける

二つ目のほうが厄介です。余裕がちょうど零かだけ見て繰り返しを止めると、優先順位の並びで 前のホストが満杯のときに、うしろの余裕があるホストを全部飛ばします。しかも 超過割り当てで負になった余裕は零ではないので、そのまま通ってしまいます。

限界: この記事が主張しないこと#

  • ⚠️ 古い方式の別名で指定された装置は事前に絞れません。別名を resource class に解けないため 記録だけ残して渡し、最終の判定は送る時点で行われます。
  • 特性の判定はホスト単位です。資源と特性がちょうど同じ提供者になければならない細かい突き合わせは しません。明らかに不可能なホストを先に外す程度です。
  • 提供者のサービスが使えないときは警告を残し、標準資源だけで配置します。この場合は装置の 絞り込みが働きません。
  • 可用量と要求は復旧一回の範囲でだけ Cache します。実行の途中で状態が変わっても、その周期の中では 最初の値を使います。
  • 社内資料なので、製品名と顧客名とアドレスとアカウントとホスト名は書いていません。

おわりに#

この編の結論は一行です。選んでくれる側がいない経路では、送る前に自分で絞る必要があります。 スケジューラがある経路の習慣をそのまま持ち込むと、失敗が遅れて来ます。

そして先に絞ることの値打ちは、成功率ではなく失敗の形にあります。「合うホストなし」で 早く終われば、ほかの Instance の復旧はそのまま進みます。
