個人プロジェクト#GPUaaS コントロールプレーン

AWS リソース96個を消した Teardown が「残存なし」と出しましたが、2行は照会していません
VPC が既に無いと Load Balancer と Network Interface の照会は実行されず、初期値の空文字がそのまま出力されます。

個人プロジェクトとして、GPU を複数人で分け合うための Kubernetes Control Plane を作っています。 AWS アカウントひとつに EKS クラスタを丸ごと立てて消す Terraform ルートがあり、毎晩それを消す GitHub Actions のワークフローが回っています。

そのワークフローはこれまで毎回成功していました。消すものが無かったからです。 成功した片付けと、やることが無かった片付けが、同じ緑色で積み上がっていました。

そこで一日かけて実際に立てて消しました。リソースが96個できて、消すのに13分35秒かかりました。 記録しておいたリソース ID をひとつずつ照会して消えたことを確かめたあと、ワークフローが最後に出す 一覧を読み返して、2行のところで止まりました。七行のうち2行は AWS に尋ねたことが無いのに、 残りの五行とまったく同じ文字で「なし」と出ていました。

この記事の想定読者#

  • Terraform でクラスタを丸ごと立てて消す経路を作っている方
  • 片付けの最後に出る「残存なし」を根拠にしている方
  • 検査が通ったのか、実行されなかったのかを見分けようとしたことがある方

どんなサービスですか#

研究室ひとつぶんくらいの GPU を複数人で分け合うための Control Plane です。クラスタは常時 立てておきません。必要なときに Terraform で立て、使い終わったら消します。立てると VPC とサブネット 8個、EKS クラスタ、ノードグループ4つ、NAT と EIP までリソース96個が一度にできます。

消す側はワークフローが担当します。Argo CD のアプリケーションを先に消し、Terraform でクラスタを 消し、最後に残ったものがあるかアカウントに尋ねます。その最後の段階がこの記事の主役です。

最初は片付けの経路が検証済みだと思っていました#

片付けのワークフローは数か月ずっと毎晩回っていて、失敗したことがありませんでした。実行記録だけ見ると 検証の済んだ経路に読めます。

ところがその期間、このアカウントにはクラスタがありませんでした。ワークフローは毎回「消すものが無い」 ことを確かめて成功で終わっていたのです。消すコードが実際に消したことは一度もありませんでした。 だから立てました。

結論から申し上げます#

消すこと自体はできました。Terraform は96個を消したと報告しました。その集計とは別に、私が先に 記録しておいたリソース ID を照会しました。EKS は ResourceNotFoundException、EIP と VPC と EBS と ENI 5個はすべて NotFound、EC2 は terminated、NAT は deleted でした。状態ファイルは106,851バイトから1,361バイトに縮みました。96個を ひとつずつ照会し直したわけではありません。

七行すべてが「なし」で出ました#

破棄が終わると、ワークフローはアカウントに何が残っているかを照会して一覧を出します。 今回の実行の出力です。

VPC:               <none>
EC2 instances:     <none>
EBS volumes:       <none>
NAT gateways:      <none>
Unassociated EIPs: <none>
Load balancers:    <none>
Network ifaces:    <none>
no residue

七行が並んで「なし」です。これを見ると七つすべてを尋ねて、すべて無かったと読んで しまいます。私もそう読みました。

後ろの2行は照会したことがありません#

この検査は Load Balancer と Network Interface を、先に見つけた VPC ID を基準に照会するように 書かれています。コードはこうなっています。

LB=""
ENI=""
if [ -n "$VPC" ]; then
  LB=$(q elb aws elbv2 describe-load-balancers ...)
  ENI=$(q eni aws ec2 describe-network-interfaces ...)
fi

VPC が既に消えていれば $VPC は空文字で、二つの照会は実行されません。 LB と ENI は先頭で入れた初期値のまま残り、出力の関数は空の値を <none> として出します。「AWS に尋ねたら無かった」と「尋ねていない」が 一文字も違わずに出ます。

記録しておいた ENI の ID 5個が消えたことは、私が別にひとつずつ照会して確かめました。それはその 5個についての確認であって、ENI が一つも残っていないという確認ではありません。Load Balancer は今回の 構成では最初から作っていません。どちらもあの出力が教えてくれたわけではありません。

同じファイルのもう半分をその朝に直していました#

同じ日の朝、私はこの検査のもう半分を直していました。照会を set +e の下で回して結果の 文字列だけを受け取っていたので、認証情報が期限切れでも空文字が返り、それが「なし」として 読まれていた箇所です。

直し方は、照会ごとに終了コードを見て、失敗したものを別に記録しておき、最後にその一覧が空でなければ ジョブを失敗させることです。

if [ -n "$FAILED" ]; then
  echo "::error::residue verification did not complete: these queries failed:$FAILED"
  echo "This is NOT a report of no residue -- nothing above says whether anything is still billing."
  exit 1
fi

ひとつの検査の中に、同じ欠陥が二つの形であったわけです。朝に直したのは失敗した照会が 「なし」に読まれることで、夕方に見つけたのは実行されなかった照会が「なし」に読まれることでした。 私は片方を直して、そのファイルは見終えたつもりでいました。

分からない原因を名指しした警告#

破棄の途中で、Argo CD を順番に消す段階が二つ飛ばされました。ログはこう言っていました。

##[warning]Kubernetes API is not reachable from this runner.
          The cluster endpoint is private and this runner is outside the VPC.

この実行に関して、その説明は誤りです。エンドポイントの公開側は開いていました。 ただ許可した範囲が私のアドレスひとつだけで、そこに GitHub ホストのランナーが入っていなかっただけです。

コードを見ると、接続確認は kubectl get --raw /readyz のあらゆる異常終了をひとつの失敗に 変えて、エラーの中身を捨てます。それでは範囲拒否と認証失敗と DNS 失敗と準備未完了を区別できません。 区別できないのに原因をひとつ名指しすると、読む人を違う方向へ送ります。症状だけを述べ、あり得る原因を 並べるように直しました。

この検査がそもそも見ないもの#

その2行を直したとしても、この検査が答えられる範囲は狭いままです。ひとつのリージョンだけを見て、 EC2 と EBS と NAT はタグで探し、VPC は名前タグで探します。EIP は関連付けられていないものだけを 数えます。

関連付けられたまま残った EIP は、この検査では見つけられません。今回の EIP は生きている間 NAT に 関連付けられていました。消えたことは私が割り当て ID を照会して確かめたもので、ワークフローが 確かめたものではありません。

この記事が主張しないこと#

  • ⚠️ 片付けの経路が検証されたという話ではありません。今回の一周はいちばん小さいクラスタで、 Load Balancer も Argo CD も GPU ノードも PVC もありませんでした。このワークフローが備えていた 難しい場合はひとつも試されていません。
  • 残存検査が失敗するところは相変わらず見ていません。今回も通りましたが、成功の記録だけでは 照会が実際に行われたかどうかは判断できません。
  • 費用がゼロになったという話でもありません。終わったのはこのクラスタの使用量です。状態バケットと KMS キーと ECR リポジトリ2つはそのまま残っており、金額は請求データから読んでいません。
  • ⚠️ 毎晩の cron が無人で同じことをやり切るかも確かめていません。今回の破棄は手で起動して見守った ものです。

おわりに#

  • 「尋ねたら無かった」と「尋ねていない」は違います。同じ文字で出てしまうと、 読む側に見分ける方法がありません。
  • 飛ばされた照会の初期値は、結果のように見えます。条件の中でしか埋まらない変数を そのまま出すと、条件が偽だったという事実が出力から消えます。
  • ひとつのファイルに同じ欠陥が複数の形で潜んでいることがあります。片方を直してファイルを見終えた と思ったのが、今回の私の誤りでした。
  • 区別できないものを名指ししません。原因をひとつ書いた警告は、読む人をその方向へ送ります。
