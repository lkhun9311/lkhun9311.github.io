Four GPU Quota Defences Broke the Same Way
The tenant could write the very field each check read.

I build a Kubernetes-native GPU control plane as a personal project. I attacked the quota guard that enforces how many GPUs a tenant may hold, myself.

It broke four times. And every break had the same shape. The value the check read was a value the tenant could write.

There was no bug in the checking code. The check was right about what it read; what was wrong was reading that value as evidence about the tenant. That is why the four are collected in one place. The pattern is the finding, not any one of them.

Who this is for#

  • You build the side that enforces per-tenant resource limits on Kubernetes
  • You guarantee "this is blocked" with an admission webhook or a controller
  • You have had a check whose code was right and whose guarantee still broke

At first, nothing stopped it#

The design goes like this. Kueue's ClusterQueue is the single authority over a namespace's GPU budget, and the controller deliberately stops the namespace ResourceQuota from capping GPUs so the same device is not charged twice.

But Kueue only sees what enters its queues. So what stops a tenant from creating a Pod directly?

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: bypass-probe, namespace: serving}
spec:
  containers:
    - {name: c, image: busybox:1.36, command: ["sh","-c","sleep 30"],
       resources: {limits: {"nvidia.com/gpu": "2"}}}
EOF

pod/bypass-probe created
bypass-probe   Running   platform-worker2   2
$ kubectl -n serving get workloads
(none)

Created, scheduled, Running, holding two devices — and no Kueue Workload anywhere. Nothing admitted it and nothing is counting it.

"Multi-tenant GPU quota" was not a boundary but a convention the platform's own controller followed. A convention binds nobody who does not intend to follow it.

An ownerReference is a claim, not a fact#

So an admission webhook was written. The first rule was the natural one — admit a Pod whose controller is a Job in a queue. It passed ten unit specs and four live cases.

# create a real Job in a real queue
kubectl apply -f (Job "decoy", labels: {kueue.x-k8s.io/queue-name: gpu-premium})

# then claim that Job as your Pod's controller
kubectl apply -f (Pod, ownerReferences: [{kind: Job, name: decoy,
                        uid: <decoy's uid>, controller: true}],
                  limits: {"nvidia.com/gpu": "2"})

pod/forged-owner created
forged-owner   1/1   Running

ownerReferences is supplied by whoever creates the object, and Kubernetes does not check that the named owner had anything to do with it. Forging it needs one real Job's UID, which is readable in the same namespace.

Fix. Believe the reference only when the Job controller presents it by reading req.UserInfo.Username, a field in an admission request a tenant cannot write.

That has an implementation consequence. The typed Validator interface hands you only the object, and the object is exactly what cannot be trusted. So this had to drop to a raw admission.Handler and take the request itself. When a convenient abstraction hands you something that does not line up with the trust boundary, you cannot use that abstraction.

An exemption anyone can grant is not an exemption#

The same guard honoured a quota-exempt annotation on any Pod.

The annotation exists for a reason: infrastructure sometimes must hold a device outside any tenant's budget — a device plugin, for instance. But a tenant can annotate its own Pod. That makes it the bypass with one extra step.

Fix. Honour it only when the request comes from a kube-system service account — a set a tenant cannot join. And a Pod admitted through it emits a warning naming the annotation, so a device leaving the budget announces itself.

The reclaim guarantee is bounded by a number the victim chooses#

Quota reclaim works by preemption, preemption waits for termination, and termination waits for terminationGracePeriodSeconds — a value set by the Pod being preempted.

Measured directly:

Sweeping the parameter against a fixed 43 seconds of remaining work gives the model, and the knee lands where predicted — held = min(remaining, grace).

The same boundary was measured from the other side: an unresponsive workload defeats reclaim entirely while its remaining service fits inside grace, and is cut off at exactly grace once it does not.

Fix — and this one differs from the first two. The grace period genuinely belongs to the workload. Checkpointing before you die takes time, and that need is legitimate. So it could neither be replaced with something trusted nor restricted to a privileged set. Instead it was capped: 120 seconds for device holders.

Why not 30? A training step that checkpoints on SIGTERM needs longer, and refusing that pushes tenants to ignore SIGTERM — which the measurement shows is exactly the case that costs the owner most.

A reservation for Pods that can never exist#

The fourth turned up while testing the third, and it is the same shape again: refusing the Pod is too late.

Kueue admits a Job by looking at the Job. If that Job's Pods are then rejected, the Job keeps its admission. The Job controller retries, every Pod is refused, and the Workload sits admitted, holding quota.

t=20s    used=2  admitted=2  job.status.failed=0
t=240s   used=2  admitted=2  job.status.failed=0

backoffLimit cannot end it. An admission rejection is not a Pod failure, so failed never leaves 0 and the retry never stops. A tenant submitting such Jobs holds a budget indefinitely while running nothing.

Fix. Apply the rules that decide a Pod's fate to the template that would produce it, at the point where the reservation is made. A Job asking for devices is refused if its template's grace exceeds the cap, or if it carries no queue label.

The label is checked at the Job — that is where Kueue reads it, and refusing at the Pod would tell a user to fix a field their Pod does not have.

Re-attacked after deploying: both Jobs Forbidden, used unchanged at 1, and an ordinary queued Job with grace 90 still runs.

Why the four fixes take different forms#

Each guarantee was expressed in terms of a value the adversary supplies. Not a bug in the check — the checks were correct about what they read. The mistake was reading something the tenant writes and treating it as evidence about the tenant.

The most useful part of this is that the four repairs came out in four different shapes.

The four fixes and the form each took.
caseformwhat it did
① ownerReferencereplaceswapped the untrusted input for a trusted one — the requester is authenticated, the object is not
② exemption annotationrestrictnarrowed who may supply the input to a set the tenant cannot join
③ grace periodboundcould do neither, so it bounded the damage. The weakest of them and the honest one
④ Job reservationrelocatekept the rule and moved the check to where the commitment is made

③ is worth dwelling on. Reclaim is still not immediate, and no Kubernetes mechanism makes it so. A cap did not solve the problem; it made how bad it can get finite. Write a solution and a bound into the same column and the next reader takes it as solved.

④ says something different. The rule had been right all along; the moment it was applied was wrong. It was checking after the thing it existed to prevent had already happened. No amount of refining the rule removes that class of defect.

A claim in this document was false, and the guard was built on it#

The original write-up for this work contained a sentence: "Kueue's pod and deployment integrations are not enabled here, so only a Job can be governed and a serving Pod is invisible to Kueue however it is labelled."

That is wrong. Seventeen frameworks are enabled, including pod, deployment and statefulset. The conclusion came from reading the first twelve lines of a truncated grep, and it survived into the guard's design, its code comments, and the write-up.

What it changes is what the label means. A queue label is not a permission a tenant grants itself; it is a bill — a request to charge that queue's budget. Which makes "labelled, therefore admit" the same string check the guard existed to replace.

And that leads to the project's current state. The guard rejects serving Pods, because serving Pods are owned by a ReplicaSet and the guard accepts only a Job. So the serving namespace has been unlabelled again, and no namespace in this repository is currently governed by it.

The honest state is: the enforcement mechanism is built, tested against forgery, and cannot be turned on until serving genuinely has a quota to be charged against. The next step is not to weaken the guard; it is to put serving on the quota path.

What this does not claim#

  • The GPUs here are simulated, advertised by a fake device plugin. So the findings are about Kubernetes admission and trust boundaries, not about how devices behave.
  • Not a claim that this guard is protecting anything right now. As above, no namespace is currently governed by it.
  • The GPUs are simulated. A fake device plugin advertises nvidia.com/gpu, and "2 devices" are those fake devices. The findings are about admission and trust boundaries, not about how a real device is occupied.
  • 32s and 301s are observations in this cluster, and the model comes from a sweep against a fixed 43 seconds of remaining work. It does not follow that the same constants appear at other work lengths or other kubelet settings.
  • 120 seconds is not derived from measurement. It is a judgement between two failure modes — denying a checkpoint versus holding a device longer — and what the measurement supports is only the part that says ignoring SIGTERM costs the owner most.
  • Four is not all of them. Four is what attacking found; the surfaces nobody attacked are still there. That the first guard passed ten unit specs and four live cases is the reason to expect more: tests only try what you thought of.

Wrapping up#

  • An ownerReference is a claim, not a fact. The requester writes it, so it cannot be evidence of ownership.
  • An annotation anyone can attach is not an exemption. It becomes one only when the set that may grant it excludes the tenant.
  • If the victim picks how long reclamation takes, reclamation is not guaranteed. The guard has to set that ceiling.
  • Tests only try what I thought of. The first guard had already passed ten unit specs and four live cases; attacking it then produced four more findings.

When you write down a guarantee, write down which value it rests on, and write who supplies that value beside it. A guarantee built on a value the tenant writes ends at that field, however correct the check is.
