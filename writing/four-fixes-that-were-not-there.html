Hello. On a GPU control plane I build alone, just before renting a GPU with real money for the first time, I opened the files to finish off the remaining findings.

What I had reported as fixed did not look that way in the code. Not one of them — four.

⚠️ Scope first. This project is still in flight. What this article treats as finished is the discovery of that day and how I checked it, not the state the guards are in now. In fact twelve more came out of the code I fixed that day, and that is below too.

⚠️ And I separate what I measured from what only exists as a record. What I re-ran while writing this: three repository searches, two versions of one function, curl's exit code, and one shell variable. The two false positives among the eighteen checks, and the twelve findings, are that day's record and were not reproduced. I keep marking which is which.

Who this is for#

  • Anyone who has said "that one is handled" from memory
  • Anyone who wrote a verification script and never verified the script
  • Anyone deciding what to look at first before a run that costs money

What this is about#

  • Four things I had reported complete were not, in the commits, what I had reported. Two had the old ordering; for two the code was not there. Three of them stop billing from continuing.
  • My first explanation was "the edits were lost by accident", and I said it out loud twice before checking.
  • Asking the repository, all four first appear in my own commits of 31 August and 1 September 2026. ⚠️ That does not mean I never made the edits. git cannot tell those two apart.
  • The wrong ordering was defended by a comment I had written, and rereading it I took my own justification for evidence.
  • I wrote a script to count the other eighteen. Three came back ❌ — and two of those were my own test being wrong, not the code.
  • ⚠️ And twelve more came out of the code I fixed that day. "Fixed" was not the end.

My first explanation was "the edits were lost"#

I had reverted uncommitted changes at some point during the work. So "the edits were lost by accident" was plausible. I said it out loud twice, before checking.

That explanation was comfortable. I made the edit and a tool swallowed it sits better than I said I had done something I had not. I picked the comfortable one without checking.

I asked the repository#

git log -S is usually introduced as "it finds the commits containing that string", and that is not what it does. It selects commits where the number of occurrences of that string differs from the parent. So a commit that deleted the last one also comes back — and that commit does not contain the string.

For each guard I picked a string that only that guard had. These are the results from re-running it while writing this.

$ git log -S"ttl_arm" --oneline -- hack/gpu-session.sh
e96687e fix: give the m6 paid path a deadline, a scale-down, and a delete that finishes

$ git log -S"worst_total_min" --oneline -- hack/m5c-matrix.sh
4165f10 fix: twelve defects a cold review found in the guards added over the last two days
d125bfe fix: keep the deadline until the node is confirmed down, and refuse runs that cannot fit inside it

$ git log -S"the card starts billing here" --oneline -- hack/m5b-gpu-session.sh
4243faf fix: register the deadline before the card exists, by scaling the node group here

The middle one has two lines — it was touched again later, and the first appearance is the lower one.

Since it selects commits where the count changed, whether it went up or down has to be checked separately. I counted the occurrences in the parent and in the commit.

ttl_arm                        e96687e   parent 0 → 1
worst_total_min                d125bfe   parent 0 → 4
the card starts billing here   4243faf   parent 0 → 1

All three are zero in the parent. That is the commit where the string first appears, along this path, within the history reachable from the current HEAD, and the dates are 31 August and 1 September 2026, all my own commits.

⚠️ And the strings I picked are not all executable code. The third, the card starts billing here, is a message printed to the screen. That message was absent; "the guard was absent" does not follow from that alone.

⚠️ What this search answers is "that string was not in an earlier commit on that path" and no further. Without --all it only sees history reachable from the current branch, and without --follow a path restriction loses history from before a rename. If the same thing had been written with a different string, it would not be found at all.

The fourth one, the ordering, is not about a string but about position. I first compared line numbers, and that method has a hole that appears later. So here I put the two versions of the same function side by side.

# 6086a51 — the commit where the deadline feature first appeared
gpu_scale_down() {
  # Drop the deadline first. If the scale-down below succeeds the schedule has nothing left
  # to do, and if it fails the schedule is the reason this is survivable ...
  command -v ttl_disarm >/dev/null 2>&1 && ttl_disarm     # the function's first action

# d125bfe — 31 August 2026, my commit
gpu_scale_down() {
  # The deadline is NOT dropped here, and the ordering is the whole point.
  # ... It comes off at the bottom of this function, after desiredSize has been
  # read back as 0, and nowhere else.

In the first, the function's first action is the disarm. In the second it is not there, and instead a comment says "at the bottom, after the size has been read back as 0".

⚠️ But a comment is a statement of intent, not evidence of what happens. The thing the next section warns about has to be honoured here first. Here is the bottom of the second version.

  # Confirm it took. An accepted API call that left desiredSize at 1 is the failure this
  # whole function exists to make impossible ...
  DESIRED=$(aws eks describe-nodegroup ... --query 'nodegroup.scalingConfig.desiredSize' ...)
  if [ "$DESIRED" = "0" ]; then
    # Only now. The deadline has nothing left to protect ...
    command -v ttl_disarm >/dev/null 2>&1 && ttl_disarm
  else
    echo "WARNING: ... after the scale-down. It is billing." >&2
    echo "The TTL deadline is left armed on purpose. It is what remains." >&2
  fi
}

It really is where the comment said. It reads the size back and disarms only when it is 0; otherwise it leaves it. First version: the function's first line. Second: after the read-back. The one that changed the order is the second — my commit.

⚠️ This is the order written in the source. Both versions are straight-line code inside the same function so I take the execution order to match, but I did not run it to confirm.

What git cannot tell apart

This is where "so I never made the edit" must not follow. An uncommitted edit leaves nothing in the commit history. If I really wrote it and lost it, the history looks exactly as it does now. ⚠️ Content that reached git add can leave traces elsewhere, but I did not go looking for them at the time.

Exactly one thing is settled for both cases: up to the moment I reported, that guard was not present as a commit.

⚠️ "I did not check when I reported" does not follow from that. I might really have written it, checked it, and lost it before committing. ⚠️ And uncommitted code is not code that does not run: these are shell scripts I run on my own laptop, so whatever is in the working tree runs as it is.

What does remain is this: it was not left as durable history. Tomorrow's me, another machine, me-after-a-revert — none of them can pick it up. And I called that state "done".

A comment was defending the code#

The code for the first item looked like this.

gpu_scale_down() {
  # Drop the deadline first. If the scale-down below succeeds the schedule has nothing left to do,
  # and if it fails the schedule is the reason this is survivable -- so it is removed only after a
  # clean exit path is under way, never as a precondition for one.
  command -v ttl_disarm >/dev/null 2>&1 && ttl_disarm

The comment collapses on its own. It says "if it fails, the schedule is the reason this is survivable" — and then removes that schedule before the call that might fail. The moment it fails, the schedule is already gone.

What matters is that this is not the trace of a lost fix. This comment is a reason invented while trying to explain a wrong order.

And rereading it, I went "ah, that one is handled" and moved on. I took my own justification for evidence.

An explanation being attached does not mean the explanation is right, even with the code right beside it.

Error responses were flowing in as measurements#

The largest distortion of a number that day was elsewhere: the code meant to measure how long the model takes to produce its first token. ⚠️ Strictly it measured time to the first byte, and that first byte may be a response header. I have never confirmed the two are the same.

The old code discarded the response body and did not look at the exit status, keeping only the time to the first byte. That time is computed for an error response too. And the error response in that day's record was very fast.

While writing this I brought up a server that returns nothing but 500 and checked.

$ curl -s -o /dev/null -w 'http_code=%{http_code} time_starttransfer=%{time_starttransfer}\n' http://127.0.0.1:8791/
http_code=500 time_starttransfer=0.000390
$ echo $?
0                          <- a 500, and the exit code is 0

$ curl -sf -o /dev/null http://127.0.0.1:8791/   # with --fail
$ echo $?
22

Plain curl does not treat HTTP 500 as a failure. The transfer itself succeeded. The exit code is 0 and the time is computed exactly the way it is for a normal response.

So "I should have checked the exit status" is wrong too. By default a normal response and a 500 both exit 0, so that alone does not separate them. You need --fail, or to read the response code yourself. The place to fix was not where I first thought it was.

[the values below are from that day's record]
HTTP 500 response time      : 0.000566 s
arrival rate it would derive: 2,826/s

normal (when it takes 1.4 s): 1.142/s
                              → 2,475×

⚠️ These two arrival rates are derived values, not measurements. Both have the shape of some constant divided by the response time (rate times time gives 1.6 on both sides), and I did not check what that constant is.

What I calculated this time from the two recorded values: 2,826 ÷ 1.142 = 2,474.6 and 1.4 ÷ 0.000566 = 2,473.5. The two are nearly the same. That means the recorded rate is inversely proportional to the response time, and the faster the response, the larger the derived value. (They are not exactly equal, which looks like rounding on both numbers — the rates and the times are both given to limited digits.)

This arrival rate is the single input that sets the load and the run time of every experimental condition. If it greatly exceeds what the card can actually do, the tail-latency samples get truncated.

⚠️ The only thing reproduced in this section is curl's behaviour. The numbers, and "so I fixed it", are that day's record. What verdict a run at that value would have received was not checked then either.

The KV capacity check beside it had the same character: it printed the engine's reported value and the predicted one side by side and never compared them — with "refuse if it is nothing like the prediction" written at the top of the file. ⚠️ This is also that day's record.

I wrote a script to count the rest, and its test was wrong#

After fixing the four, I wrote a script that checks all eighteen remaining items at once to see whether they were really there. Three came back ❌.

Two of those were not the code but my own test being wrong.

Here is one. "Is the arming before the scale-up?" was compared by line number, and a comment on line 44 contained the string desiredSize=1. The test counted that comment as the scale-up.

The other was the test expression itself being nonsense. That day I did not just read the verdicts but compared against the files directly, and recorded that the two ❌ were false positives of the test, not defects in the implementation.

⚠️ What the third ❌ was is not in the record. I wrote down only that two were false positives and never wrote the remaining one. There is no way to know now. Even the record of checking the checker has a gap in it.

⚠️ The two false positives in this section and the desiredSize=1 comment story are that day's record and were not reproduced this time.

One name let a test pass in silence#

The same day, another test harness used a variable named GROUPS. That is a name bash keeps for itself. This is about bash, not shells in general. Re-running it on this machine (bash 5.3.9):

$ bash -c 'GROUPS=(a b c); echo "${GROUPS[*]}"'
<the current user's group ids>             <- not what was assigned

$ bash -c 'MY_GROUPS=(a b c); echo "${MY_GROUPS[*]}"'
a b c                                       <- with another name it goes in

The assignment is swallowed in silence. On this version there is no error and no warning. ⚠️ It differs by bash version. Older documentation says an assignment like this returns a non-zero status. I checked this one version.

⚠️ That is as far as this reproduction goes. What follows is that day's record. A test that was supposed to detect "another card is already running" passed without ever seeing the value I had put in.

The code was fine and the test lied. ⚠️ This and the two false positives above have different causes. One counted a comment as code, one had a nonsense test expression, this one never received its value. What they share is only that the result looked green. The check did run. It just ran without the value I meant to put in. A check passing does not mean it ran with the input you intended.

Twelve more came out of the code I had just fixed#

After fixing the four and counting the eighteen, I reviewed just those guards again the same day. Twelve came out. Most were inside code written moments earlier to fix the earlier findings.

The first put the listing call inside a command substitution and discarded stderr while never looking at the exit status. ⚠️ A command substitution does not destroy the exit status — the assignment inherits it and the caller did not look. According to the record, expired credentials, a permissions error and a network failure therefore all produced an empty list. ⚠️ That is the record; what the tool actually emits was not checked this time. An empty list is indistinguishable from "nothing else is running". A guard built for the moment something is wrong with the account passes at exactly that moment.

The second is the same. If it could not read the remaining deadline it returned 0. The moment authentication expires mid-session, exactly the moment to stop, the guard stops guarding — with the remote schedule still armed.

Limits: what this article does not claim#

  • This article says nothing about the state the guards are in now. The project is in flight, and what is written here is what I found and checked on one day, 1 September 2026. Things to fix keep coming out of the same places since.
  • I did not compare timestamps to show the report came before those commits. What I have is commit dates; I do not separately hold the time or wording of the report. "I found out when I opened it before the paid session" is that day's record.
  • I do not know why I reported it that way. Whether I started and stopped, confused it with another file, or read a plan as a result — there is no record. What is established is only that the report and the code differed.
  • git log -S selects commits where the occurrence count changed. If the same thing had been written with a different string it would not be found at all. So this search tells me "that string was absent", not "that guard was absent".
  • Numbers from a line-number comparison change with what you count. Rewriting this I looked at the same commits again, and changing the search pattern slightly changed the line number of the confirming line. The conclusion (the order was reversed) held, but the numbers are not something to carry over as they are.
  • I am not saying every money-leaking path is closed. The defence I counted then was three layers deep, and the third I only knew existed; I had never seen what it deletes. I wrote at the time that it was more honest not to count it.
  • I do not know whether the eighteen-item script is right today. I fixed two false positives then; the test expressions for the other sixteen were never checked.
  • The twelve were not reproduced in this session. They come from that day's commit record, and only two are carried into the text. What state the other ten are in is outside this article too.

Closing#

  • "I did it" is memory, not evidence. Memory does not separate having made an edit from having meant to.
  • When I learned I was wrong, I suspected the tool first. Because that explanation was comfortable. The more comfortable the explanation, the sooner it needs checking.
  • I took a comment I had written as evidence. An explanation being attached does not mean the explanation is right.
  • Write a verification script and the script needs verifying too. Two of the three ❌ were my test, not the code.
  • "Fixed" needs looking at once more. Twelve more came out of that day's fixes, and two of them were failures that looked exactly like the safe state.

If one line survives, it is this. When it feels like things are going well, check what that feeling rests on. Mine rested on memory.

git log -S answers in seconds. Saving those seconds, I found four guards that did not look the way I had reported, right before a paid run. Three were devices that stop billing from continuing.

⚠️ And after fixing those, twelve more came out of the same places. This is not a story about things being closed; it is a story about how to check. The project is still in flight.
