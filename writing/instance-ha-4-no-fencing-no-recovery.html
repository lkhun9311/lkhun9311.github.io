Instance HA ④: The Design Asked for Fencing and the Build Kills Processes
The design said not to move anything until the power was confirmed off. The build has no such check, and something else sits in its place.

In part three only one of eight scenarios passed through to recovery. A verdict is not permission to move anything.

The reason is the one from part one. If the original is still alive and writing to disk while a copy attaches to the same volume, the filesystem breaks. So the design made it a rule: nothing moves until the original's power is confirmed off.

I am rewriting this part after reading the rest of the material. The shipped build has no such confirmation. The rule belongs to the design document and never meant the product behaves that way, and the earlier version of this post did not say so.

Who this is for#

  • Anyone adding fencing to automatic recovery who needs the preconditions written down
  • Anyone whose design document and shipped build disagree, wondering what to write first
  • Anyone in an environment where power cannot be confirmed, looking at what replaces it
  • Anyone who read part three and wondered what happens after the verdict

The design said do not move without confirmation#

Recovery means starting a VM again on another host. If the original never died, two sides attach to the same volume. What breaks is not one VM but the whole volume.

The four stages of the recovery procedure.
StageWhat it does
DetectHeartbeat TTL expires and the phase one verdict completes
VerifyCheck that every phase two condition holds
FenceCut power and confirm it went down
RecoverRun the evacuation

The four stages exist to push the irreversible action to the very end. The first three can be stopped at any point and only the last one cannot be undone.

And if the path used to cut power dies with the failure, the rule cannot hold at all. That is why a dedicated physical switch became a precondition.

Five seconds between the command and the check#

This is the easiest place in the fence stage to get wrong. Query the state right after cutting power and it is not off yet. There is time between the command arriving and the power actually going down.

# Cut power over the dedicated BMC path
ipmitool chassis power off

# Wait at least five seconds. Query immediately and it is not off yet
sleep 5

# It has to read as off
ipmitool chassis power status

# Only after the per-storage cleanup checks
# does the evacuation run

Drop the wait and it fails in both directions. A fencing action that worked gets read as a failure and blocks recovery, or the run moves on optimistically and evacuates a machine that never went down. Five seconds is the floor; the ceiling is set separately.

Each storage type clears differently#

Power being off does not by itself make the volume safe to move. The connections the original held have to clear, and how they clear differs by storage type.

The four rows are not folded into one because they sit on different layers. A transport protocol, a volume layer and a management service do not share a single condition.

The build has no such confirmation#

That was the design. The build differs. The product today neither cuts power nor confirms it before recovering. Its evidence that the original is not alive comes from connectivity rather than from power state.

Lined up against the code, the design elements fall into three tiers. One tier is waiting to be adopted rather than rejected, which is why it is written that way. The power wait and retry settings are present as a commented skeleton.

The node kills its own VMs instead#

So what stops the original from carrying on writing? The node itself. An agent runs on each node, and when it decides it has failed, it kills the VM processes running on itself.

# What makes a node declare itself failed. Any one of these is enough
  no status request arrives from the control side for a set time
  the configured gateway does not answer a ping
  a TCP connection to the configured IP and port cannot be made
  a configured network interface is not up, or is a loopback

# Once that verdict holds for a set time
  find the VM processes on this node and kill them
  except any VM marked as being moved

There are four conditions and any one of them is enough. No status request from the control side, no answer from the gateway, no TCP connection to the configured address, or a network interface that is down.

But the kill can outrun a move. Killing a VM that is being relocated breaks the recovery. So move start and move end arrive as messages and an exempt list is kept separately.

This is not the same thing as cutting power. If the node reads its own state wrongly, the kill does not happen either. Power is confirmed from outside; this is decided from inside.

Limits: what this post does not claim#

  • ⚠️ What this series comes from is a design document. I designed the procedure and asked for the preconditions. I did not build the BMC network or run this procedure in production.
  • "Waiting to be adopted" is inferred from a commented skeleton and an upgrade in progress. It is not confirmed against a record of the decision.
  • Five seconds is a proposed value. It was not chosen by measuring how long power takes to drop on specific hardware.
  • The four storage rows are not an exclusive taxonomy. Two of them can appear in one setup.
  • This came from internal material, so product names, customers, addresses, accounts and hostnames are left out.

Wrapping up#

The conclusion is one line. Write what a design asked for and what a build does in the same sentence and the reader is misled. The earlier title did exactly that, which is why the title changed first.

One difference remains. Power is confirmed from outside; killing processes is decided from inside. If the observer misreads itself, the second method does not fire at all.
