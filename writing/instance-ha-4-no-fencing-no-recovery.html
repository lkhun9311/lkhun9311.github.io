Instance HA ④: We Do Not Recover Until the Power Is Confirmed Off
Sending the power-off command and confirming it took effect are different acts. That is why five seconds sit between them and why each storage type gets its own cleanup condition.

In part three, only one of eight scenarios proceeded to recovery. This part is what happens after that one passes. A verdict that recovery may run is not yet permission to move anything.

The reason is the one from part one. If the original is still alive and writing to its disk while a replica attaches to the same volume, the filesystem breaks. So the principle was set as nothing moves without confirmation that the original host's power is off.

Turning that principle into a procedure brings three things with it. The path for cutting power has to survive the failure, the command has to be separated from the confirmation, and leftover attachments have to be cleared differently per storage type.

Who this is for#

  • Anyone adding fencing to automatic recovery and working out the preconditions
  • Anyone deciding which network the IPMI or BMC path belongs on
  • Anyone wondering why leftover attachments are handled differently per storage type
  • Anyone who read part three and wants to know what follows a verdict

Why power comes before recovery#

Recovery means bringing a VM back up on another host. If the original did not actually die, two sides attach to the same volume. What breaks is not one VM but the whole volume.

So the principle became "no fencing, no recovery". Leave a path that proceeds without confirmation and that path eventually opens. Confirmation was made a gate rather than an option.

VLAN separation was not enough#

Power is cut over IPMI, so if that path dies along with the failure the principle cannot hold at all. Three wiring options were put side by side.

VLAN separation is logical separation, so it does not cover a switch dying outright. A dedicated physical switch was required as a precondition. At the time of the incident this farm had no BMC path at all.

Split into four stages#

The four stages of the recovery procedure.
StageWhat it does
DetectHeartbeat TTL expired and the Phase 1 verdict is complete
VerifyAll Phase 2 execution conditions are met
FenceCut power and confirm it went down
RecoverRun Nova Evacuate

The point of four stages is to push the irreversible act to the end. The first three can stop at any time and only the last cannot be undone.

Five seconds between command and confirmation#

This is the easiest place in the Fence stage to get wrong. Reading the status right after cutting power still reports not-off. There is time between the command arriving and the power actually going down.

# cut power over the dedicated BMC switch path
ipmitool chassis power off

# wait at least five seconds - an immediate read is not yet off
sleep 5

# the status must read off
ipmitool chassis power status

# only after the per-storage cleanup is confirmed
# does Nova Evacuate run

Drop the wait and it goes wrong in both directions. A fence that worked reads as failed and blocks recovery, or an optimistic read moves the VMs of a host that never went down. Five seconds is a lower bound on the power actually dropping, and the upper bound is set separately.

Each storage type clears differently#

Power being off does not by itself make the move safe. The attachments the original held have to be cleared, and how that is done differs by storage type.

The four lines are not collapsed into one because they sit at different layers. A transport protocol, a volume layer and a management service are mixed together, so no single condition covers them.

Limits: what this post does not claim#

  • ⚠️ What this series produced is a design document. I designed the procedure and required the precondition. I did not build the BMC network or run this procedure in production.
  • Five seconds is a proposed value. It was set as a lower bound to forbid an immediate read, not chosen by measuring how long power takes to drop on each model of hardware.
  • The four storage entries are not an exclusive taxonomy. Cinder manages the other three rather than sitting beside them, and two can appear together in one deployment.
  • This is internal material. Product names, customers, addresses and accounts are not used.

Closing#

One line carries this part. Sending a command and confirming its result are different acts. Separating them and putting a wait in between is nearly the whole of the Fence stage, and pinning down the BMC path that makes confirmation possible comes before even that.
