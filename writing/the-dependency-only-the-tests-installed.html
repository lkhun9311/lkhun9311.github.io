An Operator Green in Every Test Crashed Six Times on EKS
Three test environments installed the Kueue CRDs and the GitOps deployment was the only one that did not.

It was the night before my first paid GPU session. Over the previous two days I had fixed some thirty cost-control and measurement-validity defects and confirmed each one by injecting it. The operator image was in ECR and the runbook was written. I thought the preparation was done.

That night, without turning on a single GPU, I stood up an EKS cluster and brought the platform up on it. The operator that was always green in tests died on EKS as soon as it started. This post is about why that cause could never have appeared in a test.

One caveat first. What this post confirmed is the cause, not the fix. I saw the operator come back after installing the missing CRDs by hand, and the path where GitOps does the same thing by itself never ran that night. The rest of the caveats are gathered under "What this does not claim".

Who this is for

  • Anyone building a Kubernetes operator and testing it with envtest, kind or e2e
  • Anyone deploying CRDs with a GitOps tool such as Argo CD
  • Anyone deciding what to stand up first before an expensive run

The setup

This is the control plane of a GPUaaS platform I am building as a personal project. When a user creates an MLTrainingJob, the operator hands it to Kueue (a Kubernetes scheduler that queues work and admits it against quotas). Handing work to the scheduler is this operator's core job.

Deployment has two layers. Terraform creates EKS and the resources around it, and on top of that Argo CD brings up everything else from a single root Application (app-of-apps).

I thought the preparation was done

I asked codex whether the paid session could run with nobody watching. It said no, for three reasons.

First, the run was not an unattended workflow. The session script starts the engine, holds a port-forward and waits. The measurement had to be started by a person in a separate shell, and a person had to end the session afterwards.

Second, there was no automatic recovery. If the spot instance is interrupted or the port-forward drops, the measurement dies and does not restart. Meanwhile the session shell keeps waiting, billing up to its TTL while doing nothing.

Third, the 6.2-hour plan was not a safe window. The 372 minutes came from the expected processing rate, and if the card is slow the script extends the deadline up to 420 minutes. The boundary on the other side is the nightly cleanup workflow destroy.yml, which deletes the whole cluster. Its cron is scheduled for 03:00 UTC (noon KST), but there is no on-time guarantee, and this repository has a record of actual firings drifting from 03:53 to 14:57 UTC. Both ends move, and I had computed only one.

Then came the heaviest point. The biggest risk was not cost but an operational failure in a stage I had never run, one that would not recover without a person and would void the whole session. The cheapest mitigation was to stand up just the cluster and Argo CD that night and tear them down.

The scope of "never run" needs to be exact. The cluster itself was not new. On 31 August CI had run terraform apply, created 96 resources and destroyed them. What was new was putting the platform on top: the Argo CD bootstrap, applying the root Application and starting the operator. That stage had only run on kind. When I first wrote it down I also called it "the first real cluster", and corrected it after a review pointed to the record in the same directory.

The result, up front

The cluster came up with 96 resources, and applying the root Application created the child Applications. cert-manager went Healthy. The operator image in ECR was pulled by digest, 34 MB in 1.7 seconds, and the webhook certificate was issued.

And the operator died six times.

Failed to create controller {"controller": "mltrainingjob",
  "error": "index workloads by job ref: no matches for kind \"Workload\"
            in version \"kueue.x-k8s.io/v1beta1\""}

The Kueue CRDs were not in the cluster. The three environments that tested the operator each installed these CRDs, and the GitOps deployment path was the one place nobody installed them. After I installed the four CRDs by hand and deleted the Pod, the operator became Available.

Three environments installed the CRDs, so no test could hit this failure

Here is where each environment gets the Kueue CRDs.

How each environment obtains the Kueue CRDs.

test/e2einstallKueueCRDs() before deploying the manager
admission test suitethe same files through envtest's CRDDirectoryPaths

GitOps / EKSnobody

At start-up the operator builds a field index on the kueue.x-k8s.io/v1beta1 Workload. Without the CRD that is a hard failure. I think that behaviour is right. For an operator whose core job is handing work to a scheduler, refusing to start is better than silently skipping the scheduler.

The problem is that this hard failure could not happen in a test, because all three environments installed the CRDs. The operator was always green in tests and died the first time it met the real deployment path.

cert-manager had the same shape. It is a hard dependency, the file that needs it says so, and nobody installed it. The difference is that cert-manager was found by reading a comment and the Kueue CRDs only showed up by standing things up. That three environments install the CRDs was written in each of their files, but that GitOps alone does not install them was written in no file. Something that is absent cannot be seen by reading files.

A manual install revived it and the session gate passed that state

On the live cluster I installed the four CRDs and deleted the Pod.

$ kubectl apply --server-side -f test/crd/kueue
$ kubectl delete pod -l control-plane=controller-manager
→ controller-manager   1/1   AVAILABLE 1

There is a reason for --server-side. The Workload CRD exceeds the size limit of the last-applied-configuration annotation (262,144 bytes). With a client-side apply, three of the four go in and one is rejected, and that result reads less like a size limit than like a partial install.

Then I ran the session script's operator gate against the real cluster and watched it pass. The day before, that gate had been changed from checking only the name to requiring an Available replica. Without that change it would have passed an operator in CrashLoopBackOff and turned the card on.

I made a test fixture the deployment source, then reversed it

At first I pointed the new Application at test/crd/kueue. The idea was to avoid making a copy, and a review overturned it. Avoiding drift between copies came at the price of a test fixture becoming production's desired state. Tidying the fixture would itself be a production change. I had changed the kind of drift, not removed it.

So I moved the definitions to config/kueue-crds/ and made the three test locations read from there. There is still only one copy, and now the side that ships it owns it.

With prune on, moving one CRD file deletes the data with it

There was something worse. That Application had prune: true and a cascade finalizer enabled.

Deleting a CRD does not delete only a schema. Every instance belonging to that CRD becomes a deletion target.

The Application that installs the platform's own CRDs had had the same settings from the start. I turned prune off on both. I kept selfHeal: restoring a definition someone deleted by hand is the safe direction, and selfHeal does not delete a definition because a file moved.

The cause was confirmed and the fix was not

Laying out that night's steps in order shows the boundary.

On top of that, every Argo CD Application watches targetRevision: main. The fix was on the dev branch. Standing up a new cluster as things were, config/argocd on main would not contain that Application, so the same CrashLoopBackOff would happen again. Promoting to main was therefore not optional but part of the fix.

Confirming a hypothesis and confirming a fix are different things. I had done the first and nearly wrote that I had done the second.

The promotion happened the same night. dev, holding the three fix commits, went into main through PR #63 at 02:26 KST on 2 September. On main the kueue-crds Application points at config/kueue-crds with sync-wave -2, so it is written to sync before the operator at sync-wave 0. That is as far as "written" goes; it is not a sighting of that order running on a new cluster.

I chose to tear it down

I confirmed all three GPU node groups were at zero and deleted the cluster. All 96 resources were deleted, and EKS, EC2, NAT, EIP, EBS, VPC and reservations all went to zero.

The cost console showed $0 at that point, but that is aggregation lag. The cluster was up for about 40 minutes at $0.263 an hour, so roughly $0.18, plus a little NAT data charge for pulling images. No GPU was ever turned on, so that side really is zero.

Leaving it up overnight was an option. It would have saved 20 minutes in the morning. But $0.263 an hour keeps running, and worse, the nightly cleanup workflow would overlap the next session. Start a 6.2-hour session four hours before the scheduled time (03:00 UTC, noon KST) and the cluster disappears in the middle. The session script refuses to start when fewer than two hours remain before the scheduled time, but lets four hours through. Rebuilding costs 20 minutes and $0.09.

What this does not claim

  • That the fix works through GitOps. I only saw the manual install revive it. The path where the Application installs the CRDs by itself, and a new cluster after the promotion to main, never ran within this post's evidence. There are later records of clusters stood up on EKS, but none says by which path the Kueue CRDs got in.
  • How "six times" was counted. The journal does not say whether it is the container restart count. The journals from that day only say "six times", and no kubectl output or restart count from that night survives.
  • The GPU side. GPU nodes actually coming up, the NVIDIA driver attaching, the device plugin advertising nvidia.com/gpu, DCGM emitting metrics, and a 16 GB engine image and weights coming down through NAT: none of it ran that night.
  • Repetition. Cluster creation, the Argo CD bootstrap and the root apply each ran once.
  • An exact cost. $0.18 is computed from uptime and the hourly rate and leaves out the NAT data charge. It was not checked against the bill.
  • When deletion happens with finalizers present. I only described the direction in which prune deletes instances and did not actually delete any.
  • That finding defects by reading files is useless. The thirty or so from the previous two days were all found by reading, and they really would have ruined the paid session. This defect just did not come out that way.

Closing

  • A dependency the test environment installs for you is a dependency the tests do not check. While three environments installed the Kueue CRDs, the operator's start-up failure branch never ran.
  • What is present can be read, and what is absent cannot. The install code of the three environments was in files, and the absence of an install in GitOps was in no file. So it only surfaced by standing things up.
  • When GitOps ships CRDs, look at prune first. One renamed file makes the definitions and their instances deletion targets.
  • Confirming a cause and confirming a fix are different. A cluster repaired by hand coming back confirms a hypothesis. Whether the deployment path does the same has to be run separately.

If you test an operator, try laying the list of things your test environments install for you next to your real deployment manifests. Something absent cannot be seen by reading one file.

Thank you for reading.
