プーラーは二つの枯渇のうち一つしか直さない

Writing · 2026年9月 · 8分

他の言語 English · 한국어

範囲。個人プロジェクト（Kotlin · Spring Boot · マネージド Postgres、モノリス）の リリース前の構造点検の記録である。障害が起きたことはなく、負荷試験で測った数値も ない。以下に出てくる「最大10秒」は外部呼び出しに設定した read timeout であって、 リクエストごとに実際にそれだけ握っていたと測定した値ではない。改善はコードの性質の変化として説明される ものであり、この記事は実測値を主張しない。

点検の出発点はよくある仮説だった — コネクションが枯れる恐れがあるのだから、プーラー（RDS Proxy・ PgBouncer の類）を入れればいいのでは。

答えはこのコードベースでは否であり、その理由は製品ドキュメントではなく トランザクションプーリングの定義から出てきた。

症状は一つ、原因は二つ#

コネクションが枯れたときに見えるものはたいてい一つだ。プール待ちのタイムアウト、互いに無関係な API が 同時に遅くなること、そしてログの Connection is not available, request timed out。

ところがその背後の原因は二種類ある。

A — コネクションが多いから。アプリのインスタンスが増えれば、インスタンス数 × プール サイズだけコネクションが開く。Postgres はコネクションごとにバックエンドプロセスを作り、アイドルでも メモリを使う。実際にクエリを走らせているのはそのうちの一部で、残りは開いているだけだ。

これがプーラーの存在理由である。アプリのコネクション数千本を、バックエンドの コネクション数十本に畳んでくれる。

B — トランザクションが長く開いているから。

BEGIN → SELECT → [ 外部 HTTP 呼び出し ] → INSERT → COMMIT
                  ↑ コネクションを握ったままクエリを一本も出さない

同時リクエストがプールサイズを超えれば枯れる。ここではコネクションの本数は問題では ない — 占有時間が問題だ。

そして枯れるのはその経路だけではない。投票もフィードもチャート参照も同じプールから コネクションを受け取るので、一緒に止まる。このアプリで特に痛かったのはタイミングだった — 成長エンジンが 「結果チャートを共有すること」なので、共有が跳ねる日がそのまま枯れる日になる。

なぜプーラーは B を直せないのか#

「アプリのコネクション数千本を DB のコネクション数十本に畳む」という絵は正しい。問題は いつ畳まれるのかであり、それはトランザクションプーリングの定義にすでに含まれている。

多重化はトランザクションの間で起きる。トランザクションが開いている間、その バックエンドコネクションはそのクライアントに固定（pin）される。当然だ — トランザクション は状態であり、途中で他のセッションに貸せば分離が壊れる。

だからこうなる — トランザクションが10秒開いていればバックエンドコネクションも10秒固定され、 畳み比は 1:1 になり、プロキシの利得はゼロに近づく。

プーラーは短いトランザクションが多いときに価値を出す道具だ。B を患ったまま買えば金を 使っても何も良くならないが、もっと悪いのはその次である — 「これで備えた」と信じてしまう。 その信念が次の点検を止める。

だから順序がある#

解法は一つではなく層であり、層には順序がある。

横にスクロールすると残りが見えます

コネクション枯渇に対する五つの層の解法と、それぞれの性格。
層何を性格
①トランザクションを短く — 外部呼び出しを外へ唯一根本的。残り全部の前提
②流入制御 — スレッド・プールの上限を意図的に失敗を速く予測可能に
③プーラー①が終わって初めて効く
④読み取り分離・キャッシュコネクションを使わなくする唯一の層
⑤非同期オフロード（outbox）リクエストあたりの DB 作業そのものを減らす

だからコードから直した。外部モデレーション呼び出しをトランザクションの外に出す作業を 書き込み経路三か所に施した。そのうち一つはもっと悪かった — 投票添付の経路は for update で 行までロックしたまま外部呼び出しをしていた。コネクションと行ロック、二つの資源 を同時に握っていたのである。記事とコメントの二経路を先に直し、投票添付は検閲の入力がロックした行から 出てくるため staleness の再確認が必要で、意図的に後回しにして四日後に直した。

結論を一行で書けばこうだ。コード修正はプーラーの代替ではなく前提条件だった。 直してみて初めて、プーラーが価値を出せる状態になった。

誰も選んでいない二つの数字#

②に罠が一つある。ブロッキング JDBC ではコネクションプールが事実上の同時実行上限だ。 スレッドがいくら多くてもコネクションを受け取れなければ仕事はできない。

このサービスは Tomcat のスレッドがデフォルトの200で、コネクションプールは 設定が一行もなかった — フレームワークのデフォルトがそのままサービスの容量だった。すると 残りのリクエストはコネクションを待ってタイムアウト後に失敗する。方向は正しい — 速く失敗してこそ残りが生きる。問題は別のところにあった。

二つの値はどちらも誰かが選んだものではなかった。どちらもフレームワークのデフォルトで、 悪いのは数字そのものではなくその数字がどこにも書かれていないことだった。流入制御とは上限を 置くことではなくその上限を意図して決めることであり、デフォルト二つが作り出した同時実行 ポリシーはポリシーではない。

プーラーが効くコードかを先に確認した#

③に進む前に確認することがもう一つある。トランザクションプーリングにはピン（pin）を誘発する パターンがあり、それがあるとプーラーは無力になる。

  • セッションスコープの advisory lock（pg_advisory_lock）
  • 一時テーブル
  • SET · set search_path
  • サーバサイドのプリペアドステートメント（プーラーとバージョンによる）

四つともなかった。advisory lock は三か所で使っているがすべて xact スコープ だった — トランザクション終了時に自動で解放されるので、トランザクションプーリングにそのまま載る。

この三つが xact スコープだったのが意図なのか偶然なのかは、記録からは判定できない。確かな のはセッションスコープのロックを一か所でも使っていれば、その経路がプーラーを無力化していた はずで、その事実はプーラーを導入した後にしか分からなかっただろう、ということだ。道具を買う前に、その道具がこのコードで働くかを先に見る手続きが、 この点検で得たもののうち最も再利用可能な部分である。

スレッドとコネクションは別の資源だ#

ここでよく出てくる処方がもう一つある — 非同期にすればいいのでは。

WebFlux やコルーチンに変えればスレッドは節約できる。ところがコネクションは そのまま握る。JDBC はブロッキングであり、トランザクションが開いている限りコネクションは返却 されない。

問題の軸がコネクションなのにスレッドを節約する処方を持ってくると軸がずれる。 R2DBC なら話は別だが、それはデータアクセス層の全面書き換えである。

プールを大きくする処方も同種だ。緩和にはなるが修理ではなく、 プールサイズ × インスタンス数 ≤ DB コネクション上限に先に引っかかる。そして根本原因 — 遅い外部呼び出しがコネクションを握る — はそのまま残る。

ガードを結果ではなく原因に置いた#

この修正には固有の脆さがある。@Transactional 一行で元に戻る。 しかも戻しても機能は正常だ — テストも通るし画面も問題ない。症状は負荷がかかる日にしか 出ない。

だから回帰防御を結果ではなく原因に置いた。外部クライアントの位置に spy を座らせ、 呼び出しが起きるその時点でトランザクションが活性かどうかを断言する。

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

assertThat(probe.sawTransaction).isNotEmpty()         // ① 呼び出しが実際に起きたか
assertThat(probe.sawTransaction).containsOnly(false)  // ② その呼び出しはトランザクションの外だったか

①がなければ②は空虚に通過する。ゲートが丸ごと抜けて呼び出しが0件なら、 containsOnly は空リストに対して真だからだ。否定の表明には必ず 「空でない場合」を添える。

このガードは「応答が速いか」を問わない。「外部呼び出しがトランザクションの中にあるか」 を問う。それが実際の原因であり、巻き戻しが起きる場所だ。

そしてガードが本当に狙えているかはミューテーションで確認した — @Transactional を戻して 実際に走らせた。記事とコメントの経路では該当のガードだけが red になった。投票添付の経路は 違った — ミューテーションが最初はグリーンだった。staleness ガードが狙う条件がテストの中で 作られていなかったためで、spy の onScreen フックで検閲の区間に行を変えて条件を作ってはじめて red を見た。

ここで学んだことがこの記事で最も持ち出せるものだ。ミューテーションがグリーンならコードが安全 なのではなく、ガードが狙っていないのである。

この記事が主張しないこと#

  • 性能数値はない。負荷試験をしておらず、「何倍速くなった」と言う根拠がない。 変わったのはコードの性質 — トランザクションが外部呼び出しを待たなくなったこと — であり、 それが遅延やスループットでいくらになるかは測っていない。
  • 「最大10秒」は設定値だ。外部呼び出しにかけた read timeout であって、リクエスト ごとに実際にそれだけ占有したと測定した値ではない。
  • 障害が起きたことはない。リリース前の構造点検から出たものであり、この経路が実際に 枯れるのを観測した記録はない。
  • プーラーが無用だという主張ではない。A 型の枯渇にはまさに正しい道具だ。この記事が 言っているのはB を患った状態では畳み比が 1:1 なので価値を出せないということだけである。
  • ベンダー別のコネクション上限の数値は書いていない。確認していない値だからだ。
  • ピン誘発パターンの一覧は完全でないかもしれない。プーラーとバージョンによって 異なり、ここで確認したのはこのコードにその四つがないということだけである。

残る一行はこれだ。症状が同じでも原因は同じではなく、道具は原因一つにしか合わない。 そして誤って選んだ道具の本当の代償は金ではなく、備えたという信念である。
