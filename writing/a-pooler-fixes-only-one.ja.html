RDS Proxy では直せないコネクション枯渇
トランザクションの中で外部 API を呼び出していました — リリース前のソーシャル投票プラットフォーム点検

事業化プロジェクトWriting · 2026年9月 · 21分

ソーシャル投票プラットフォームを作っています。リリース前にアーキテクチャを点検していて、 「トラフィックが増えれば DB コネクションが足りなくなるだろうから、コネクションプーラーを一つ前に 立てればいいのでは」という、ごくありふれた仮説から出発しました。結論は 「このコードベースでは否」でした。

なぜ否だったのか、そしてその判断を何を根拠に下したのかを共有します。

この記事の想定読者#

  • Spring Boot でサービスを作っているが、コネクションプールの設定をまだ自分で触ったことがない方
  • 「コネクションが足りないなら RDS Proxy のようなものを足せばいいのでは?」と考えたことのある方
  • トランザクションの中で外部 API を呼び出すコードを見たことがある、あるいは今そう書いている方

どんな内容ですか?#

  • コネクション枯渇には原因が二つあり、コネクションプーラーはそのうち 一つだけを直します。
  • なぜ直せないのかは製品ドキュメントではなくトランザクションプーリングという方式の定義 から出てきます。
  • だから道具を導入する前にこのコードでその道具が動くのかを先に確認しました。
  • 修正が @Transactional 一行で戻ってしまう種類なので、回帰防御を 結果ではなく原因に置きました。

コードは非公開リポジトリにあります。まだリリース前なのでリポジトリを 公開していません。そのため各節には GitHub リンクではなくファイルパスとシンボル名を 書いています。パッケージ名と環境変数名は元の記録ですでに匿名化されているものをそのまま使っています。

⚠️ 先にお伝えすることがあります。この記事の数値はローカルのハーネスで 測ったもので、本番の数値ではありません。外部呼び出しの遅延はスタブに設定した値です。 障害が起きたこともありません。以下に出てくる「最大10秒」は外部呼び出しに 設定してある read timeout の値であって、リクエストごとに実際にそれだけ握っていたと 測定した値ではありません。

どんなサービスですか?#

事業化を目標に作っているソーシャル投票プラットフォームです。ユーザーが質問を投稿すると 他の人が投票し、その結果チャートをアプリの外へ共有するサービスです。Kotlin と Spring Boot で作った 単一のモノリスで、データベースはマネージド PostgreSQL を一つ使っています。まだリリース前です。

構成を図にするとこうなります。

外部モデレーション API は有害な内容をふるい落としてくれる外部サービスです。 投稿やコメントを書くたびに一回ずつ呼び出し、この呼び出しには read timeout が10秒で 設定されています。そしてこの呼び出しがデータベーストランザクションの中で起きていました。

# application.yml
read-timeout: ${APP_HTTP_READ_TIMEOUT:10s}

この数字を覚えておいてください。この記事の残りは全部ここから出てきます。

最初はプーラーを足せば済むと思っていました#

点検の出発点はありふれた仮説でした。

トラフィックが増えれば DB コネクションが足りなくなるだろうから、RDS Proxy や PgBouncer の ようなコネクションプーラー（connection pooler）を前に立てればいいのでは?

コネクションプーラーは、アプリケーションが開くコネクション数千本を DB コネクション数十本に まとめてくれるミドルウェアです。紹介図だけ見れば、まさに私に必要なものに 見えました。

ところがこの判断を下す前に確かめるべきことがありました。 「私がこれから迎えるコネクション不足は、本当にこの道具が直す種類の不足なのか」です。

結論から申し上げると#

違いました。一行にまとめるとこうです。

コネクション枯渇にはコネクションの本数が原因のものと コネクションを長く握っているのが原因のものがあります。 症状は同じで処方は違います。コネクションプーラーは前者だけを直します。

そしてこの結論の根拠は RDS Proxy や PgBouncer の製品ドキュメントではなく、 トランザクションプーリング（transaction pooling）という方式の定義そのものから 出てきました。順に見ていきます。

まず症状からです。コネクションプールが枯渇すると、表に出てくる姿はたいてい一つです。プールで コネクションを待ってタイムアウトし、互いに何の関係もない API が同時に遅くなります。ログにはこの行が 出ます。

Connection is not available, request timed out after 30000ms

ここまでは二つの原因がまったく同じ顔をしています。だから症状だけを見て道具を選ぶと外します。

原因 A — コネクションが多いから#

一つ目はコネクションの本数そのものが問題である場合です。

アプリ100台 × プールサイズ20 = コネクション2,000本
ところが今実際にクエリを実行しているのは50本
残りの1,950本はただ開いているだけです

PostgreSQL はコネクション一本ごとにバックエンドプロセスを一つ作り、そのコネクションが何もして いなくてもメモリを使います。だからインスタンスを増やすほど DB 側が先に限界にぶつかります。

これがコネクションプーラーの存在理由です。アプリのコネクション2,000本を バックエンドの50本にまとめてくれるのですから。A 型の枯渇にはまさに正しい道具です。

原因 B — コネクションを長く握っているから#

Private services/api/…/comment/CommentService.kt create

二つ目はコネクションの本数ではなく握っている時間が問題である 場合です。そして私のコードはこちらでした。

// CommentService.kt — 修正前
@Transactional
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    val user = activeUserGuard.requireActive(userId)                 // DB
    val postWithAuthor = postQueryRepository.findActiveById(postId)  // DB
    // ...
    moderationGate.screenComment(body)   // ← 外部 HTTP 呼び出し。read timeout 10秒
    // ...
    val comment = commentRepository.insert(...)                      // DB
}

@Transactional がメソッド全体に掛かっているので、このメソッドが回っている間ずっと コネクションが一本占有されます。ところがその区間の真ん中に、 クエリを一本も実行しないまま最大10秒待つ外部呼び出しが入っています。

同時に書き込むリクエストがプールサイズを超えると、その時点からコネクションがありません。ここで コネクションの本数を増やしても根本原因はそのままです。遅い外部呼び出しがコネクションを 握っているという事実は変わらないからです。

そして止まるのは書き込み経路だけではありません。

投票も、フィード参照も、結果チャート参照も同じコネクションプールから コネクションを受け取ります。だから書き込み経路がプールを使い切るとサービス全体が一緒に遅くなります。

このアプリで特に痛かったのはタイミングでした。このサービスの成長エンジンが 「投票結果チャートを共有すること」なので、共有がよく跳ねる日がそのままサービスが止まる日 になります。

なぜプーラーは B を直せないのですか?#

ここがこの記事の本題です。

「アプリのコネクション数千本を DB のコネクション数十本にまとめてくれる」という説明は正しいです。 問題はいつまとまるのかであり、その答えはトランザクションプーリングの定義にすでに 入っています。

コネクションを再利用することは、トランザクションとトランザクションの 間でしか起きません。トランザクションが開いている間は、そのバックエンドコネクションが そのクライアントに固定されます（pin）。

当然の話でもあります。トランザクションは状態であり、開いている途中で他のセッションに貸せば分離が 壊れるからです。

だからこうなります。

トランザクションが10秒開いている
  → バックエンドコネクションも10秒固定される
  → アプリのコネクション1本につき DB のコネクション1本
  → プーラーがまとめるものがない

コネクションプーラーは短いトランザクションが多いときに価値を出す道具です。B を 患ったまま導入すればお金を使っても何も良くならないのですが、実はもっと悪いのはその次です — 「これで備えた」と信じてしまいます。その信念が次の点検を止めます。

だから順序があります#

解法は一つではなくいくつもの層であり、層には順序があります。

横にスクロールすると残りが見えます

コネクション枯渇に対する五つの層の解法と、それぞれの性格。
層何をどういう性格か
①トランザクションを短く — 外部呼び出しをトランザクションの外へ唯一根本的です。残り全部の前提です
②流入制御 — 同時処理の上限を意図的に決める失敗を速く予測可能にします
③コネクションプーラー①が終わってはじめて効きます
④読み取り分離・キャッシュコネクションを使わなくする唯一の層です
⑤非同期オフロード（outbox）リクエストあたりの DB 作業そのものを減らします

コネクションプーラーは③です。①をやらずに③から行くと効かない、というのが前の節の内容でした。

コードから直しました#

Private services/api/…/comment/CommentService.kt create · services/api/…/post/PostService.kt createPost · addPoll

そこで①からやりました。トランザクションの境界を書き込みの区間まで狭める作業です。 Spring では @Transactional はプロキシベースなので、同じクラスの中で自分のメソッドを呼ぶと 掛かりません。そこで、すでにコードベースにあった TransactionTemplate のパターンを そのまま再利用しました。新しい仕組みを持ち込まなかった点が重要です。

// 修正後 — メソッドに @Transactional がありません
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    // ① 検証（読み取り。それぞれ短くコネクションを使って返します）
    val user = activeUserGuard.requireActive(userId)
    val postWithAuthor = postQueryRepository.findActiveById(postId) ?: throw ...

    // ② 外部呼び出し — トランザクションの外です。ここで10秒使ってもコネクションを掴みません
    moderationGate.screenComment(body)

    // ③ 書き込みだけを原子的にまとめます
    val written = writeTx.execute {
        val identity = postAliasRepository.ensureIdentity(...)
        val comment = commentRepository.insert(...)
        Triple(comment, identity?.alias, ...)
    }!!
}

ここで「トランザクションを割ったら競合が増えませんか?」という質問が出そうですが、 競合の窓は広がっていません。修正前もモデレーション呼び出しが読み取りと書き込みの 間にあり、その経路は投稿の行にロックを掛けていなかったからです(for update が ありませんでした)。トランザクションの中にあるからといって他のセッションの変更を防いでくれるわけでは ありません。読み取りから書き込みまでの距離は同じです。

同じ作業を書き込み経路三か所（投稿・コメント・投票添付）に施しました。そのうち一つは状態がもっと 悪く、投票添付の経路は for update で行までロックしたまま外部呼び出しを していました。コネクションと行ロック、二つの資源を同時に握っていたのです。

投稿とコメントの二経路を先に直し、投票添付は検閲に入れる入力がロックした行から出てくるため staleness（値が古くなっていないか）の再確認が必要で、意図的に後回しにして四日後に直しました。

結論を一行で書けばこうです。コード修正はコネクションプーラーの代替ではなく前提条件でした。 直してみてはじめて、プーラーが価値を出せる状態になりました。

誰も選んでいない二つの数字#

Private services/api/src/main/resources/application.yml spring.datasource.hikari

②（流入制御）にも罠が一つありました。ブロッキング JDBC ではコネクションプールが事実上の 同時実行上限です。スレッドがいくら多くてもコネクションを受け取れなければ仕事ができません。

ところが設定を開いてみるとこうでした。

# application.yml — 発見当時
spring:
  datasource:
    url: ${DB_URL:...}
    username: ${DB_USER:...}
    password: ${DB_PASSWORD:...}
    # 以上。hikari ブロック自体がありません

Tomcat のスレッドはデフォルトの200、コネクションプールは設定が一行も なくてSpring Boot のデフォルトがそのままサービスの容量になっていました。こうなると残りの リクエストはコネクションを待ってタイムアウト後に失敗します。

方向自体は正しいです。速く失敗してこそ残りが生きます。問題は別のところに ありました — 二つの値はどちらも誰かが選んだものではなかったのです。どちらも フレームワークのデフォルトで、悪いのは数字そのものではなくその数字がどこにも書かれていない ことでした。

そこで明記しました。

hikari:
  maximum-pool-size: ${DB_POOL_MAX:20}
  connection-timeout: ${DB_POOL_TIMEOUT_MS:5000}   # 30秒のデフォルトは長すぎます — 速く失敗してこそ残りが生きます
  max-lifetime: ${DB_POOL_MAX_LIFETIME_MS:1200000}

ただしプールを大きくしたのは修理ではなく緩和です。そして大きくするにも上限が あります。

プールサイズ × 最大インスタンス数 ≤ DB コネクション上限

アプリは自分のインスタンスが何台なのかを知らないので、この不変式をコードで強制できません。 IaC のコメントが唯一の防御なので、そこに書き留めておきました。

流入制御とは上限を置くことではなくその上限を意図的に決めることです。 デフォルト二つが作り出した同時実行ポリシーはポリシーではありません。

プーラーが使えるコードかを先に確認しました#

Private services/api/…/vote/VoteRepository.kt pg_advisory_xact_lock

③に進む前に確認することがもう一つありました。トランザクションプーリングには ピン（pin）を誘発するパターンがあり、コードにそれがあるとコネクションプーラーが 無力になります。ピンが掛かると、そのコネクションはトランザクションが終わってもそのクライアントに 固定されたままになります。

  • セッションスコープの advisory lock (pg_advisory_lock)
  • 一時テーブル
  • SET · set search_path
  • サーバサイドのプリペアドステートメント（プーラーとバージョンによって異なります）

直接確認してみました。

$ grep -rn "pg_advisory_lock" src/main/kotlin/      # (なし)
$ grep -rn "advisory_xact" src/main/kotlin/
ReportRepository.kt      pg_advisory_xact_lock(...)
AuthAuditPurge.kt        pg_try_advisory_xact_lock(...)
VoteRepository.kt        pg_advisory_xact_lock(...)

四つともありませんでした。advisory lock は三か所で使っていますがすべて xact スコープでした。トランザクションが終わるときに自動で解放されるので、 トランザクションプーリングにそのまま載ります。

この三つが xact スコープだったのが意図なのか偶然なのかは、記録からは判定できません。 確かなのはセッションスコープのロックを一か所でも使っていれば、その経路がコネクションプーラーを 無力化していたはずで、その事実は導入した後にしか分からなかっただろう、ということです。

道具を導入する前に、その道具がこのコードで実際に動くのかを先に確認する手続き。 この点検で得たもののうち、他のプロジェクトへ最もよく持ち出せる部分がこれでした。

「非同期にすればいいのでは?」#

この話をするとよく出てくる処方がもう一つあります。

WebFlux やコルーチンに変えればスレッドは節約できます。ところが コネクションはそのまま掴みます。JDBC はブロッキングであり、トランザクションが開いて いる限りコネクションは返却されないからです。

スレッドとコネクションは別の資源です。問題の軸がコネクションなのにスレッドを 節約する処方を持ってくると軸がずれます。R2DBC なら話は別ですが、それはデータアクセス層の全面 書き換えです。

プールを大きくする処方も同種です。緩和にはなりますが修理ではなく、先ほどの プールサイズ × インスタンス数 ≤ DB コネクション上限に先に引っかかります。そして根本原因 — 遅い外部呼び出しがコネクションを握る — はそのまま残ります。

戻しやすい修正なので、ガードを原因に置きました#

Private services/api/src/test/…/ModerationOutsideTransactionTest.kt TransactionProbe

この修正には固有の脆さがあります。@Transactional 一行で元に戻ります。 しかも戻しても機能は正常です — テストも通りますし画面も問題ありません。症状は負荷が かかる日にしか出ません。

「コネクションを長く握らない」ということは直接観測しにくいです。そこで結果の代わりに 原因を表明しました。実際の HTTP クライアントが座るインターフェースの位置に spy を 置き、呼び出しが起きるその時点でトランザクションが活性かどうかを記録します。

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

// 表明
assertThat(probe.sawTransaction).isNotEmpty()         // ① 呼び出しが実際に起きたか
assertThat(probe.sawTransaction).containsOnly(false)  // ② その呼び出しはトランザクションの外だったか

①がなければ②は空虚に通過します。ゲートが丸ごと抜けて呼び出しが0件なら、 containsOnly は空リストに対して真だからです。「〜ではない」を検査する表明には、 必ず「呼び出しがあったのか」を添えなければなりません。

そしてこのガードが本当に狙えているかはミューテーションで確認しました。コードを わざと戻しておいてテストを走らせ、赤信号が出るかを見る方法です。

# コメント経路に @Transactional を復元
ModerationOutsideTransactionTest > the moderation call does not hold a database transaction() FAILED

# 投稿経路に @Transactional を復元
ModerationOutsideTransactionTest > creating a post also screens outside a transaction() FAILED

投稿とコメントの経路では該当のガードだけが赤信号になりました。ところが投票添付の 経路は違いました — ミューテーションが最初はグリーンでした。staleness ガードが狙う 条件がテストの中で作られていなかったためで、spy の onScreen フックで検閲の区間に行を 変えて条件を作ってはじめて赤信号を見ました。

ここで学んだことがこの記事で一番持ち出せるものです。 ミューテーションがグリーンならコードが安全なのではなく、ガードが狙っていないのです。

三週間後に実際に測ってみました#

この記事はもともと「数値がありません」で終わる予定でした。ところがその一文を書いてみて、 それが数値を作る道具がないという意味だと分かったので、三週間後に JMeter の ハーネスを作って測りました。

要点は一つの変数だけを変えることでした。arm A は現在のコード、arm B は @Transactional 一行だけを戻したコードです。プールサイズ・スレッド数・外部呼び出しの 遅延・データはすべて同じです。遅延はアプリに仕込まずローカルのスタブを立てて base-url をそちらへ向けました — アプリに「遅く回るモード」を入れると、それはいつか 本番で有効になります。

読み方はこうです。書き込み経路は二つの arm で同じです（2,577 対 2,584ms）。 外部呼び出しの1.6秒がどちらでも支配するからです。つまり書き込みだけ測ってもこの修正の効果は 見えません。

効果は書き込みと何の関係もないフィード参照に現れます。arm B では書き込み16個が それぞれ1.6秒ずつコネクションを握ってプール10個を使い切り、4ms で終わっていた参照が6秒になります。 エラーではなく待機なのでエラー率は0%のままサービスが遅くなります。これがこの欠陥が 静かな理由です。

そして最初に回した実行では差がほとんどありませんでした（p95 5ms 対 8ms）。 書き込み8個ではプール10個が枯渇しないからです。プールが枯れなければこの現象は現れません — この数値は条件に付いた値であって定数ではありません。

③ 有害分類と ④ 狙撃判定は同じ入力を見る独立した検査です。前の結果が後の入力に ならないので、守るべき順序がありません。

仮想スレッド（Java 21）で ④ を走らせ、③ は呼び出しスレッドで回します。 固定サイズのプールを置かないことが要点です — プールサイズは新しい同時実行の上限で あり、この記事がずっと話してきた「誰も選んでいない上限」をモデレーション経路に作り直すことになります。

動作は同じでなければなりません。これは性能の変更であって動作の変更ではありません。 だから両方の完了を待ち（先に投げたからと残りを放置すれば費用は出て結果は誰も見ません）、例外は ③ が ④ より優先します（順次と同じ応答）。

⚠️ 代償があります。順次なら ③ が塞げば ④ を呼びませんでした。今は ③ が塞いでも ④ が回り、投稿あたり約 $0.0002 が余分に出ます。遅延を半分にする代わりの取引です。

ところが最初は改善が見えませんでした

最初は書き込み16で回して p50 が2,577ms 対 2,598ms、差がありませんでした。 並列化が効いていないのかと思いました。

原因はコードではなく測定条件でした。書き込み16では負荷生成器・アプリ・スタブ・DB が 一つの機械の CPU を分け合ってすでに飽和しており、スループットが両方とも 6.26 req/s という同じ天井に 当たっていました。その時点で外部呼び出しはボトルネックではなかったので、半分にしても 総スループットは変わりません。

確認の順序はこうです。①スタブがボトルネックかを直接測る — 同時32件が0.81秒で終わるので違います。 ②ソースと jar の時刻を照合し、並列コードがビルドに入っていることを見ます。③単発リクエスト を測ると0.817秒 — 並列化は効いていました。④飽和しない書き込み4で測り直すと、2倍がそのまま出ました。

残る教訓はこれです。飽和した系では、ボトルネックでないものを直しても数字は動きません。 改善が見えないときは、コードを疑う前に何が天井を作っているかを測るべきです。

新しい規則には新しいガードを

この変更は例外の優先順位という規則を新しく作ります。順次なら ③ が投げれば ④ を 呼ばなかったので、順序というもの自体がありませんでした。

わざと逆にしてみたら既存の8件が全部通過しました。規則を作ったらそれを守る表明も 作らなければなりません。2件を追加し、ミューテーション3種で確認しました — ExecutionException のアンラップ除去、優先順位の反転、③ が塞いだとき ④ を飛ばす。 三つとも赤になります。

この記事が主張しないこと#

  • 本番の数値ではありません。測ったのはローカルのハーネスで、負荷生成器と アプリが同じ機械で CPU を分け合っています。絶対スループットに意味はなく、比較にだけ意味があります。 外部呼び出しの800msはスタブに設定した値で、実際の遅延分布ではありません。
  • arm ごとに1回の実行です。繰り返して分散を見ていません。
  • 1,512倍は条件に付いた数字です。書き込みの同時実行がプールサイズを超えたときに 現れます。書き込み8・プール10ではp95が5ms対8msでした。
  • 「最大10秒」は設定値です。外部呼び出しに掛けた read timeout であって、 リクエストごとに実際にそれだけ占有したと測定した値ではありません。
  • 障害が起きたことはありません。リリース前の構造点検から出たものであり、この経路が 実際に枯渇するのを観測した記録はありません。
  • コネクションプーラーが無用だという話ではありません。A 型の枯渇にはまさに正しい 道具です。この記事が言っているのはB を患った状態ではアプリのコネクション1本につき DB の コネクション1本になり、価値を出せないということだけです。
  • ベンダー別のコネクション上限の数値は書いていません。確認していない値です。
  • ピン誘発パターンの一覧は完全でないかもしれません。プーラーとバージョンによって 異なり、ここで確認したのはこのコードにその四つがないということだけです。

おわりに#

まとめるとこうです。

  • コネクション枯渇の原因は本数と占有時間の二つで、症状が同じなので 紛らわしいです。
  • コネクションプーラーは本数の問題を直す道具です。占有時間の問題ではアプリのコネクション1本につき DB のコネクション1本になり、まとめるものがありません。これは製品の限界ではなく トランザクションプーリングという方式の定義から出てきます。
  • だから順序があります。トランザクションを短くすることが残り全部の前提です。
  • 道具を導入する前にこのコードでその道具が動くのかを確認する手続きを入れれば、 導入してから知ることになる事実を先に知ることができます。

最後に一行だけ残すならこれです。症状が同じでも原因が同じとは限らず、道具は原因一つにしか 合いません。そして誤って選んだ道具の本当の代償はお金ではなく、 「これで備えた」という信念です。
