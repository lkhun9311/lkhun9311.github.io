リリース前のソーシャル投票プラットフォームを一人で作っています。このサービスで投稿を一つ 書くと、サーバーはそれを DB に入れる前に外部Moderation API へ送り、有害な内容かどうかを 尋ねます。その呼び出しには Read Timeout が 10 秒で掛かっています。そしてその呼び出しが DB Transaction の中にありました。

この構造を見て最初に思ったのは、ごくありふれたことでした。「トラフィックが増えれば Connection が足りなくなるから、RDS Proxy のようなものを一つ前に立てよう。」 間違った考えでした。

Connection の枯渇には原因が二つあり、Connection Pooler はそのうち一つだけを直します。 なぜ直せないのかは製品の文書ではなく、Transaction Pooling という方式の定義から出てきます。 だから道具を導入する前に、このコードでその道具が動くのかを先に確かめました。

この記事の想定読者#

  • Spring Boot でサービスを作っているが、 Connection Pool の設定をまだ自分で触ったことがない方
  • 「 Connection が足りないなら RDS Proxy のようなものを足せばいいのでは?」と考えたことのある方
  • Transaction の中で外部 API を呼び出すコードを見たことがある、あるいは今そう書いている方

どんなサービスですか?#

事業化を目標に作っているソーシャル投票プラットフォームです。ユーザーが質問を投稿すると 他の人が投票し、その結果チャートをアプリの外へ共有するサービスです。Kotlin と Spring Boot で作った 単一の Monolith で、データベースはマネージド PostgreSQL を一つ使っています。まだリリース前です。

構成を図にするとこうなります。

先ほどの外部Moderation API が、有害な内容をふるい落とすそのサービスです。 投稿やコメントを書くたびに呼び出しますが、後で出てくるとおり実際には 投稿 1 件あたり 2 回です。

問題はこの呼び出しがあることではなく、どこにあるかでした。

# application.yml
read-timeout: ${APP_HTTP_READ_TIMEOUT:10s}

この 10 秒が記事の最後までついて回ります。ただし 後の測定は 10 秒ではなく 800ms の Stub で測ったものです。10 秒は「最悪でどこまで 握りうるか」を言う設定値です。

最初は Pooler を足せば済むと思っていました#

トラフィックが増えれば DB Connection が足りなくなるだろうから、RDS Proxy や PgBouncer の ようなConnection Pooler（Connection Pooler）を前に立てればいいのでは?

Connection Pooler は、アプリケーションが開く Connection 数千本を DB Connection 数十本に まとめてくれるミドルウェアです。紹介図だけ見れば、まさに私に必要なものに 見えました。

ところがこの判断を下す前に確かめるべきことがありました。 「私がこれから迎える Connection 不足は、本当にこの道具が直す種類の不足なのか」です。

症状は一つ、原因は二つでした#

違いました。道具を調べる代わりに自分の枯渇がどちらの種類かを先に見たら、 こう分かれました。

Connection 枯渇にはConnection の本数が原因のものと Connection を長く握っているのが原因のものがあります。 症状は同じで処方は違います。Connection Pooler は前者だけを直します。

そしてこの結論の根拠は RDS Proxy や PgBouncer の製品ドキュメントではなく、 Transaction Pooling（Transaction Pooling）という方式の定義そのものから 出てきました。

二つの原因は外から見るとまったく同じ顔をしています。 Connection Pool が枯渇すると、表に出てくる姿はたいてい一つです。 Pool で Connection を待って Timeout し、互いに何の関係もない API が同時に遅くなります。ログにはこの行が 出ます。

Connection is not available, request timed out after 30000ms

ここまでは二つの原因がまったく同じ顔をしています。だから症状だけを見て道具を選ぶと外します。

一つ目の原因は Connection の本数です#

アプリ100台 × pool サイズ20 = connection2,000本
ところが今実際にクエリを実行しているのは50本
残りの1,950本はただ開いているだけです

PostgreSQL は Connection 一本ごとに Backend プロセスを一つ作り、その Connection が何もして いなくてもメモリを使います。だから Instance を増やすほど DB 側が先に限界にぶつかります。

これが Connection Pooler の存在理由です。アプリの connection2,000本を Backend の50本にまとめてくれるのですから。A 型の枯渇にはまさに正しい道具です。

二つ目の原因は握っている時間です#

そして私のコードはこちらでした。

// CommentService.kt — 修正前
@Transactional
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    val user = activeUserGuard.requireActive(userId)                 // DB
    val postWithAuthor = postQueryRepository.findActiveById(postId)  // DB
    // ...
    moderationGate.screenComment(body)   // ← 外部 HTTP 呼び出し。read timeout 10秒
    // ...
    val comment = commentRepository.insert(...)                      // DB
}

@Transactional がメソッド全体に掛かっているので、このメソッドが回っている間ずっと Connection が一本占有されます。ところがその区間の真ん中に、 クエリを一本も実行しないまま最大10秒待つ外部呼び出しが入っています。

同時に書き込むリクエストが Pool サイズを超えると、その時点から Connection がありません。ここで Connection の本数を増やしても根本原因はそのままです。遅い外部呼び出しが Connection を 握っているという事実は変わらないからです。

そして止まるのは書き込み経路だけではありません。

投票も、フィード参照も、結果チャート参照も同じ Connection Poolから Connection を受け取ります。だから書き込み経路が Pool を使い切るとサービス全体が一緒に遅くなります。

このアプリで特に痛かったのはタイミングでした。このサービスの成長エンジンが 「投票結果チャートを共有すること」なので、共有がよく跳ねる日がそのままサービスが止まる日に なりえます。ただしまだリリース前で、そんな日が実際に来たことはありません。 観測した障害ではなく構造から出る予想です。

なぜ Pooler は二つ目を直せないのか#

では Pooler を足せばいいのでは。ここで製品ドキュメントではなく方式の定義を 見る必要があります。

「アプリの Connection 数千本を DB の Connection 数十本にまとめてくれる」という説明は正しいです。 問題はいつまとまるのかであり、その答えは Transaction Pooling の定義にすでに 入っています。

Connection を再利用することは、 Transaction と Transaction の 間でしか起きません。Transaction が開いている間は、その backendconnection が そのクライアントに固定されます（Pin）。

当然の話でもあります。 Transaction は状態であり、開いている途中で他のセッションに貸せば分離が 壊れるからです。

だからこうなります。

transaction が10秒開いている
  → backendconnection も10秒固定される
  → アプリの connection1本につき DB の connection1本
  → pooler がまとめるものがない

Connection Pooler は短い Transaction が多いときに価値を出す道具です。B を 患ったまま導入すればお金を使っても何も良くならないのですが、実はもっと悪いのはその次です — 「これで備えた」と信じてしまいます。その信念が次の点検を止めます。

直す順序はすでに決まっていました#

では何から手を付けるか。 Pooler が値を出すには Transaction が短くなければならないので、 順序はおのずと決まります。解法は一つではなくいくつもの層であり、層には順序があります。

横にスクロールすると残りが見えます

Connection 枯渇に対する五つの層の解法と、それぞれの性格。
層何をどういう性格か
①Transaction を短く — 外部呼び出しを Transaction の外へ唯一根本的です。残り全部の前提です
②流入制御 — 同時処理の上限を意図的に決める失敗を速く予測可能にします
③Connection Pooler①が終わってはじめて効きます
④読み取り分離・ CacheConnection を使わなくする唯一の層です
⑤非同期オフロード（Outbox）リクエストあたりの DB 作業そのものを減らします

Connection Pooler は③です。①をやらずに③から行くと効かない、というのが前の節の内容でした。

外部呼び出しを Transaction の外に出しました#

そこで①からやりました。 Transaction の境界を書き込みの区間まで狭める作業です。 Spring では @Transactional はプロキシベースなので、同じクラスの中で自分のメソッドを呼ぶと 掛かりません。そこで、すでにコードベースにあった TransactionTemplate のパターンを そのまま再利用しました。新しい仕組みを持ち込まなかった点が重要です。

// 修正後 — メソッドに @Transactional がありません
fun create(userId: UUID, postId: UUID, request: CreateCommentRequest): CommentResponse {
    // ① 検証（読み取り。それぞれ短く connection を使って返します）
    val user = activeUserGuard.requireActive(userId)
    val postWithAuthor = postQueryRepository.findActiveById(postId) ?: throw ...

    // ② 外部呼び出し — transaction の外です。ここで10秒使っても connection を掴みません
    moderationGate.screenComment(body)

    // ③ 書き込みだけを原子的にまとめます
    val written = writeTx.execute {
        val identity = postAliasRepository.ensureIdentity(...)
        val comment = commentRepository.insert(...)
        Triple(comment, identity?.alias, ...)
    }!!
}

ここで「 Transaction を割ったら競合が増えませんか?」という質問が出そうですが、 競合の窓は広がっていません。修正前もModeration呼び出しが読み取りと書き込みの 間にあり、その経路は投稿の行に Lock を掛けていなかったからです(for update が ありませんでした)。 Transaction の中にあるからといって他のセッションの変更を防いでくれるわけでは ありません。読み取りから書き込みまでの距離は同じです。

同じ作業を書き込み経路三か所（投稿・コメント・投票添付）に施しました。そのうち一つは状態がもっと 悪く、投票添付の経路は for update で行まで Lock したまま外部呼び出しを していました。 Connection と行 Lock 、二つの資源を同時に握っていたのです。

投稿とコメントの二経路を先に直し、投票添付は検閲に入れる入力がLock した行から出てくるため Staleness（値が古くなっていないか）の再確認が必要で、意図的に後回しにして同じ日のうちに直しました。

結論を一行で書けばこうです。コード修正は Connection Pooler の代替ではなく前提条件でした。 直してみてはじめて、 Pooler が価値を出せる状態になりました。

誰も選んでいない数字二つが容量を決めていました#

②（流入制御）にも罠が一つありました。ブロッキング JDBC では Connection Pool が事実上の 同時実行上限です。 Thread がいくら多くても Connection を受け取れなければ仕事ができません。

ところが設定を開いてみるとこうでした。

# application.yml — 発見当時
spring:
  datasource:
    url: ${DB_URL:...}
    username: ${DB_USER:...}
    password: ${DB_PASSWORD:...}
    # 以上。hikari ブロック自体がありません

Tomcat の Thread はデフォルトの200、 Connection Pool は設定が一行も なくてSpring Boot のデフォルトがそのままサービスの容量になっていました。こうなると残りの リクエストは Connection を待って Timeout 後に失敗します。

方向自体は正しいです。速く失敗してこそ残りが生きます。問題は別のところに ありました — 二つの値はどちらも誰かが選んだものではなかったのです。どちらも フレームワークのデフォルトで、悪いのは数字そのものではなくその数字がどこにも書かれていない ことでした。

そこで明記しました。

hikari:
  maximum-pool-size: ${DB_POOL_MAX:20}
 connection-timeout: ${DB_POOL_TIMEOUT_MS:5000}   # 30秒のデフォルトは長すぎます — 速く失敗してこそ残りが生きます
  max-lifetime: ${DB_POOL_MAX_LIFETIME_MS:1200000}

ただしPool を大きくしたのは修理ではなく緩和です。そして大きくするにも上限が あります。

pool サイズ × 最大 instance 数 ≤ DB connection 上限

アプリは自分の Instance が何台なのかを知らないので、この不変式をコードで強制できません。 IaC のコメントが唯一の防御なので、そこに書き留めておきました。

流入制御とは上限を置くことではなくその上限を意図的に決めることです。 デフォルト二つが作り出した同時実行ポリシーはポリシーではありません。

このコードは Pooler を使えるコードなのか#

① と ② を終えて、いよいよ ③ の番でした。ところが ③ には条件がもう一つ付いていました。 Transaction Pooling には ピン（Pin）を誘発するパターンがあり、コードにそれがあると Connection Pooler が 無力になります。ピンが掛かると、その Connection は Transaction が終わってもそのクライアントに 固定されたままになります。

  • セッションスコープの Advisory Lock (pg_advisory_lock)
  • 一時テーブル
  • SET · set search_path
  • サーバサイドのプリペアドステートメント（Pooler とバージョンによって異なります）

直接確認してみました。

$ grep -rn "pg_advisory_lock" src/main/kotlin/      # (なし)
$ grep -rn "advisory_xact" src/main/kotlin/
ReportRepository.kt      pg_advisory_xact_lock(...)
AuthAuditPurge.kt        pg_try_advisory_xact_lock(...)
VoteRepository.kt        pg_advisory_xact_lock(...)

四つともありませんでした。Advisory Lock は三か所で使っていますがすべて xact スコープでした。 Transaction が終わるときに自動で解放されるので、 Transaction Pooling にそのまま載ります。

この三つが xact スコープだったのが意図なのか偶然なのかは、記録からは判定できません。 確かなのはセッションスコープの Lock を一か所でも使っていれば、その経路が Connection Pooler を 無力化していたはずで、その事実は導入した後にしか分からなかっただろう、ということです。

道具を導入する前に、その道具がこのコードで実際に動くのかを先に確認する手続き。 この点検で得たもののうち、他のプロジェクトへ最もよく持ち出せる部分がこれでした。

「非同期にすればいいのでは?」#

この話をするとよく出てくる処方がもう一つあります。

WebFlux やコルーチンに変えればThread は節約できます。ところが Connection はそのまま掴みます。JDBC はブロッキングであり、 Transaction が開いて いる限り Connection は返却されないからです。

Thread と Connection は別の資源です。問題の軸が Connection なのに Thread を 節約する処方を持ってくると軸がずれます。R2DBC なら話は別ですが、それはデータアクセス層の全面 書き換えです。

Pool を大きくする処方も同種です。緩和にはなりますが修理ではなく、先ほどの pool サイズ × instance 数 ≤ DB connection 上限に先に引っかかります。そして根本原因 — 遅い外部呼び出しが Connection を握る — はそのまま残ります。

一行で戻る修正なので原因にガードを置きました#

この修正には固有の脆さがあります。@Transactional 一行で元に戻ります。 しかも戻しても機能は正常です — テストも通りますし画面も問題ありません。症状は負荷が かかる日にしか出ません。

「 Connection を長く握らない」ということは直接観測しにくいです。そこで結果の代わりに 原因を表明しました。実際の HTTP クライアントが座るインターフェースの位置に Spy を 置き、呼び出しが起きるその時点で Transaction が活性かどうかを記録します。

class TransactionProbe : ContentModerationApi {
    val sawTransaction = mutableListOf<Boolean>()
    override fun screen(text: String) {
        sawTransaction += TransactionSynchronizationManager.isActualTransactionActive()
    }
}

// 表明
assertThat(probe.sawTransaction).isNotEmpty()         // ① 呼び出しが実際に起きたか
assertThat(probe.sawTransaction).containsOnly(false)  // ② その呼び出しは transaction の外だったか

①がなければ②は空虚に通過します。ゲートが丸ごと抜けて呼び出しが0件なら、 containsOnly は空リストに対して真だからです。「〜ではない」を検査する表明には、 必ず「呼び出しがあったのか」を添えなければなりません。

そしてこのガードが本当に狙えているかはMutationで確認しました。コードを わざと戻しておいてテストを走らせ、赤信号が出るかを見る方法です。

# コメント経路に @Transactional を復元
ModerationOutsideTransactionTest > the moderation call does not hold a database transaction() FAILED

# 投稿経路に @Transactional を復元
ModerationOutsideTransactionTest > creating a post also screens outside a transaction() FAILED

投稿とコメントの経路では該当のガードだけが赤信号になりました。ところが投票添付の 経路は違いました — Mutation が最初はグリーンでした。Staleness ガードが狙う 条件がテストの中で作られていなかったためで、Spy の onScreen フックで検閲の区間に行を 変えて条件を作ってはじめて赤信号を見ました。

ここで学んだことがこの記事で一番持ち出せるものです。 Mutation がグリーンならコードが安全なのではなく、ガードが狙っていないのです。

三週間後に実際に測ってみました#

この記事はもともと「数値がありません」で終わる予定でした。ところがその一文を書いてみて、 それが数値を作る道具がないという意味だと分かったので、三週間後に JMeter の Harness を作って測りました。

要点は一つの変数だけを変えることでした。Arm A は現在のコード、Arm B は @Transactional 一行だけを戻したコードです。 Pool サイズ・ Thread 数・外部呼び出しの 遅延・データはすべて同じです。遅延はアプリに仕込まずローカルの Stubを立てて base-url をそちらへ向けました — アプリに「遅く回るモード」を入れると、それはいつか 本番で有効になります。

横にスクロールすると残りが見えます

Arm A と Arm B の応答時間・スループット比較。
指標Arm A — 外Arm B — 中に戻す倍率
フィード参照 p504 ms6,047 ms1,512×
フィード参照 p956 ms6,405 ms1,068×
フィード参照 スループット39.22 req/s1.35 req/s1/29
投稿作成 p502,577 ms2,584 ms1.00×
投稿作成 スループット6.26 req/s6.22 req/s0.99×
エラー率0%0%—

読み方はこうです。書き込み経路は二つの Arm で同じです（2,577 対 2,584ms）。 外部呼び出しの1.6秒がどちらでも支配するからです。つまり書き込みだけ測ってもこの修正の効果は 見えません。

効果は書き込みと何の関係もないフィード参照に現れます。Arm B では書き込み16個が それぞれ1.6秒ずつ Connection を握って pool10個を使い切り、4ms で終わっていた参照が6秒になります。 エラーではなく待機なのでエラー率は0%のままサービスが遅くなります。これがこの欠陥が 静かな理由です。

そして最初に回した実行では差がほとんどありませんでした（p95 5ms 対 8ms）。 書き込み8個では pool10個が枯渇しないからです。Pool が枯れなければこの現象は現れません — この数値は条件に付いた値であって定数ではありません。

測ったら次の問いが続いて出てきました#

この修正はまだマージしていません。セキュリティゲートに触れる変更なので 書面レビューが先です。以下の数値はブランチで測ったものです。

数値ができると次の問いが自動的に出ました — 投稿作成の p50 がなぜ Stub 遅延のちょうど 二倍なのか。ゲートを開けてみると、外部分類器を順次呼んでいました。

③ 有害分類と ④ 狙撃判定は同じ入力を見る独立した検査です。前の結果が後の入力に ならないので、守るべき順序がありません。

仮想 Thread（Java 21）で ④ を走らせ、③ は呼び出し Thread で回します。 固定サイズの Pool を置かないことが要点です。 Pool サイズは新しい同時実行の上限で あり、この記事がずっと話してきた「誰も選んでいない上限」をModeration経路に作り直すことになります。

ところがこの文を書いたとき、私はすでにその上限の中にいました。新しく作らな かっただけで、AWS SDK が連れてきた HTTP クライアントの「ホストあたり 5」がその経路にすでに 掛かっていました。それが分かったのは 3 週間後です。

応答は同じでなければなりません。ただし動作がまったく同じというわけでは ありません。③ が塞いでも ④ が回るので外部呼び出しの回数は増えます。 だから両方の完了を待ち（先に投げたからと残りを放置すれば費用は出て結果は誰も見ません）、例外は ③ が ④ より優先します（順次と同じ応答）。

代償があります。順次なら ③ が塞げば ④ を呼びませんでした。今は ③ が塞いでも ④ が回ります。増分は③ の遮断率 × ④ の単価で、遮断率が低いいまは投稿あたり 約 $0.0002 です。無条件の数値ではなく、遮断率が上がれば計算し直します。

ところが最初は改善が見えませんでした

最初は書き込み16で回して p50 が2,577ms 対 2,598ms、差がありませんでした。 並列化が効いていないのかと思いました。

原因はコードではなく測定条件でした。書き込み16では両方とも 6.26 req/s という同じ天井に当たっており、その時点で外部呼び出しはボトルネックでは なかったので、半分にしても総スループットは変わりません。

この段落は一度間違えました。最初はその天井を「負荷生成器・アプリ・ Stub ・DB が 一つの機械の CPU を分け合って飽和したもの」と書きました。ところが3週間後にその天井を追いかけると、 CPU ではなくアウトバウンド HTTP の同時実行上限でした。書き込みを32に上げても DB Pool を30にしても 6.26 から動かないという事実だけでは CPU の飽和と区別できません。どちらも 「動かない」を予測するからです。区別したのは二つです。Stub をアプリ抜きで直接叩くと 同時 32 件を 0.81 秒で受け、Stub に計測を入れると同時実行がちょうど 10 で 止まっていました。その追跡は 検閲経路のスループット上限は SDK の既定値でしたに別途書きました。 天井を「飽和」と呼んで原因を追わなかったことが、この記事の誤りです。

確認の順序はこうです。①Stub がボトルネックかを直接測る — 同時32件が0.81秒で終わるので違います。 ②ソースと jar の時刻を照合し、並列コードがビルドに入っていることを見ます。③単発リクエスト を測ると0.817秒 — 並列化は効いていました。④飽和しない書き込み4で測り直すと、2倍がそのまま出ました。

残る教訓はこれです。飽和した系では、ボトルネックでないものを直しても数字は動きません。 改善が見えないときは、コードを疑う前に何が天井を作っているかを測るべきです。

新しい規則には新しいガードを

この変更は例外の優先順位という規則を新しく作ります。順次なら ③ が投げれば ④ を 呼ばなかったので、順序というもの自体がありませんでした。

わざと逆にしてみたら既存の8件が全部通過しました。規則を作ったらそれを守る表明も 作らなければなりません。2件を追加し、 mutation3種で確認しました — ExecutionException のアンラップ除去、優先順位の反転、③ が塞いだとき ④ を飛ばす。 三つとも赤になります。

この記事が主張しないこと#

  • 本番の数値ではありません。測ったのはローカルの Harness で、負荷生成器と アプリが同じ機械で CPU を分け合っています。絶対スループットに意味はなく、比較にだけ意味があります。 外部呼び出しの800msは Stub に設定した値で、実際の遅延分布ではありません。
  • Arm ごとに1回の実行です。繰り返して分散を見ていません。
  • 1,512倍は条件に付いた数字です。書き込みの同時実行が Pool サイズを超えたときに 現れます。書き込み8・ pool10ではp95が5ms対8msでした。
  • 「最大10秒」は設定値です。外部呼び出しに掛けた Read Timeout であって、 リクエストごとに実際にそれだけ占有したと測定した値ではありません。
  • 障害が起きたことはありません。リリース前の構造点検から出たものであり、この経路が 実際に枯渇するのを観測した記録はありません。
  • Connection Pooler が無用だという話ではありません。A 型の枯渇にはまさに正しい 道具です。この記事が言っているのはB を患った状態ではアプリの connection1本につき DB の connection1本になり、価値を出せないということだけです。
  • ベンダー別の Connection 上限の数値は書いていません。確認していない値です。
  • ピン誘発パターンの一覧は完全でないかもしれません。Pooler とバージョンによって 異なり、ここで確認したのはこのコードにその四つがないということだけです。

おわりに#

  • Connection 枯渇の原因は本数と占有時間の二つで、症状が同じなので 紛らわしいです。
  • Connection Pooler は本数の問題を直す道具です。占有時間の問題ではアプリの connection1本につき DB の connection1本になり、まとめるものがありません。これは製品の限界ではなく Transaction Pooling という方式の定義から出てきます。
  • だから順序があります。Transaction を短くすることが残り全部の前提です。
  • 道具を導入する前にこのコードでその道具が動くのかを確認する手続きを入れれば、 導入してから知ることになる事実を先に知ることができます。

症状が同じでも原因が同じとは限らず、道具は原因一つにしか 合いません。そして誤って選んだ道具の本当の代償はお金ではなく、 「これで備えた」という信念です。
