2,255 コミットを飛ばす移行で手順書 3 本が誤っていました
パッチを順に当てると思っていましたが、実際は再構築と移行でした。

2026年7月、顧客現場で稼働している OpenStack ベースのプライベートクラウドポータルを、 2,255 コミット先のバージョンへ上げる準備をしました。認証方式が変わって 全ユーザーのパスワードが初期化され、スキーマ 2 つが 1 つに統合されます。どちらの変更も旧版と新版が同じ DB を同時に使えなくするため無停止は不可能で、 本番 DB なのでロールバック経路が必須でした。

こういう仕事で手順書を書く自然な方法は、公式ガイドを読んで推論することです。 私もそうやって 3 本書きました。

3 本とも前提が誤っていました。公式の経路はパッチを順に当てることではなく、 新しい DB を立ててデータを移すことでした。それが分かったのは推論を緻密にしたからでは ありません。隔離環境に旧バージョンを立て、再現できる区間を最後まで通してみたからです。

想定読者#

  • 稼働中の顧客現場の製品を上位バージョンへ上げる作業を持っている方
  • アップグレード手順書を文書だけ読んで書いたことがある方
  • 「パッチを日付順に当てればよい」を前提にしている方

そもそも同じものか#

再現には出発点が要ります。ところが現場に渡された旧バージョンのリリース版が2 部ありました。受領時期が 5 か月以上違う(2025-10-31 と 2026-04-15、166 日)。どちらを基準にするかを選ぶ前に、2 つが同じものかを確認しました。

diff -rq  <リリース版 A>  <リリース版 B>   # 差分なし (exit 0)
find . -type f -exec md5sum {} \;          # 両方の全ファイルで md5 が一致

中身は 100% 同じで、違いはファイルの mtime — つまり再ダウンロードした時刻だけでした。どちらを使っても 差し支えないと確定して先へ進みました。

この段階は些細に見えるが、飛ばすと後で高くつきます。再現が失敗したときに 「私のスクリプトが間違っているのか、出発点が違ったのか」を切り分けられなくなるからです。再現の 第一条件は出発点が固定されていることであり、それは確認して知ることであって仮定することではありません。

日付順を信じませんでした#

次はデルタの特定です。旧バージョンの Baseline にどのパッチが既に入っていて何が抜けているかを知る必要が あります。Baseline スキーマでマーカーテーブルの有無を 1 つずつ確認しました。

横にスクロールすると続きが見えます

旧 Baseline に存在するマーカーテーブルとその意味。
マーカーBaseline意味
設定テーブルあり—
ブロックリストあり10 月のパッチが Baseline に含まれている
スケジューラ関連なし7 月のバッチパッチが未適用
バッチジョブ情報なし新しいパッチがこれを参照する — 先行なしでは失敗する

ここで引っかかったものがあります。Baseline に10 月のパッチはあるのに、その前の 7・8 月のものが なかりました。

つまり Baseline はある日付で切ったスナップショットではなくキュレーションです。誰かがその ラインに必要だと判断したものだけを選んで入れています。すると「日付順に並べてその後のものを順に適用する」という 方針は安全を何も保証しません。既に入っているものを再度入れるか、先に入るべきだったものを 飛ばすことになります。

そこでデルタの正確な一覧・順序・冪等性は推論ではなく再現で確定すべきだと結論しました。これが 再現スクリプトを作った直接の理由です。

併せて、実査の過程で以前の文書が「要確認」として残していた項目が 1 つ解消しました。旧リリース版のパッチ フォルダに中間バージョンの移行 SQL がそもそも無かった — つまりその移行は未適用であり、 上位バージョンへ上げる際にデルタへ必ず含める必要があり、日付上いちばん前なので 最優先で先に適用しなければなりませんでした。

方式そのものが違っていました#

その次に公式移行ガイドを精読しました。そしてこの一文に出会いました。

このガイドはパッチの順次適用ではなく、新規 DB を再構築してデータを移行する 方式です。

私が先に書いた文書 3 本はすべて「パッチを順に適用する」を前提にしていました。デルタ一覧を作り、 順序を決め、冪等性を検討していました。その作業全体が別の方式の手順でした。

デルタの実査が無意味になったわけではありません。どのパッチが Baseline に入っているかは、再構築と移行でも必要な 情報です。無意味になったのは「パッチを順に適用すれば到達する」という結論のほうです。

3 本は消さずにそれぞれに訂正の注記を付けました。消すとなぜそう考えたのかが失われ、次に同じ 分岐で同じ推論をすることになります。残しておけば「この前提はこういう理由で誤りだった」が文書に残ります。

ここで得た教訓は「ガイドを先に読め」ではありません。ガイドは最初からあったし、私も見ました。正確に言えば ざっと見ました。方式が違うという一文は手順一覧の中ではなく概要にあり、私は手順一覧から読みました。 文書に何を探しに行ったかと、文書が何を伝えようとしているかは違うことがあります。

わざと不正確にした部分#

再現はワンショットのスクリプトにしました。隔離したポートに DB を立て、旧バージョンを構築し、バックアップし、 新バージョンを再構築し、データを移行し、バージョンを更新し、検証します。

隔離 DB 起動
  → 旧バージョン構築(スキーマ 2 種) + テストデータ投入
  → バックアップ
  → 新バージョン再構築
  → データ移行
  → VERSION 更新
  → 検証

移行部分では意図的に不正確な選択をしました。ガイドはカラムのマッピングを表で明示しているが、その表を当時は 入手できていませんでした。そこでスクリプトは元と新の共通カラムの積集合だけを INSERT IGNORE でコピーするようにしました。

これは正確な移行ではありません。それが意図でした。このスクリプトの目的は正確に移すことではなく、 どのテーブルが壊れるかを露出させることです。スキーマドリフトを吸収して進み、失敗した テーブルはログに残ります。するとFAIL ログはスキーマギャップの候補一覧になります。完全な一覧ではない — 対象に無い テーブルは SKIP で通り過ぎ、INSERT IGNORE はカラム欠落や型変換の警告を失敗にせず吸収します。 表に出るのは壊れるものであって違うもの全部ではありません。

移行が本当に行われたかを見るには、移ったものが確認できなければなりません。そこで性質の異なるテストデータを 3 種類、あらかじめ仕込みました。

再現できない領域を隠しませんでした#

ローカルには OpenStack もその認証 CLI もありません。したがって認証方式の変更に絡む部分 — アカウント・ロール テーブルの生成、ユーザー識別子を UUID から名前へ変換する処理、サービスアカウントの点検 — は 再現できませんでした。

選択肢は 2 つ。その段階をスクリプトから外して「全区間成功」と書くか、残して実施できなかったと言うか。

スクリプトがその段階ごとに明示的に SKIP または WARN をログに出すようにしました。 そうすれば実行ログを読む人が、何が検証され何が検証されていないかを同じ画面で見ます。検証されて いない区間がログから消えると、次の人はその区間も検証済みだと読みます。

これは「Ten Bugs, Zero Failed Tests」で扱った問題と 同じ種類です。「実行されなかった」と「通過した」を区別できない検証は、無いよりも悪い — あると信じ込ませるからです。

そして実際に 1 つ壊れました#

準備期間にカスタマイズ用ブランチをリモート最新へ上げました。39 コミットが一度に入り、 アプリが起動直後に終了しました。Tomcat のコンテキスト初期化でキャッシュ Bean の生成に失敗し、 プロセスが exit 1 で落ちました。

No enum constant ConfigureKey.FEATURE_SETTINGS
  ↑
BlocklistCache → RequestUrlServiceImpl → ConfigureServiceImpl.list → configures findAll

スタックトレースから呼び出し経路を逆にたどって Enum 変換の地点を突き止め、git 履歴から原因コミットを 特定しました。ある機能をロールバックする際にEnum 定数とパッチ SQL と初期データ行をまとめて削除した コミットでした。

コードは Enum を消しました。ところが既存 DB にはその値を持つ行が残っていました。起動時に ORM が その行を Enum へマッピングしようとして失敗し、コンテキストのロードに失敗すれば起動自体ができません。

重要なのはその次です。この種の欠陥は再起動のたびに 1 つずつ現れます。最初の地雷を除去すると 次の地雷が出ます。そこでローカル DB 3 つをコードの Enum 定数と全数照合し、残っている stale キーがそれ 1 つだけであることを先に確定してから削除しました。

この件の価値は DELETE 1 行ではありません。これを追跡する過程で 現場配備手順書の欠陥 3 件が明らかになりました。

3 件とも文書を読んで出てきたのではなく、実際に一度失敗して出てきました。手順書はそれまで内部的に は一貫して見えていました。存在しないファイルを指示していることは、そのファイルを探しに行ったときに分かります。

「新規インストールのほうが楽では」に数えて答えました#

準備中にもっともな意見が出ました。移行がこれほど複雑なら、いっそ新規インストールのほうがよいのでは? もっともらしかった — この現場のカスタムアカウントは1 つだけだったからです。移行でいちばん 面倒なアカウント・権限の部分が些細だという意味になります。

答え方は消えるものを先に数えることでした。

消えるのは課金・メータリングの累積履歴と、監査・作業履歴です。どちらも再計算が不可能です。 元となるイベントが残っていないので、バックアップから移す経路以外に取り戻す方法ぎません。一方で VM・ボリューム・ ネットワークといった実資源はこのポータルではなく OpenStack が所有し、ポータルは API から再同期するので そもそも心配の対象ではありませんでした。

残る反論は「それでも移行は大変では」でした。それは実測で答えました。保存すべきテーブル全部について、 information_schema で旧版と新版のカラムを比較しました。

保存対象テーブルのバージョン間カラム変化の実測結果。
まとまりテーブル数カラムの追加・削除
課金・メータリング400
監査・作業履歴80

48 テーブルでカラムの追加・削除が 0 でした。カラム集合が同じなら INSERT ... SELECT で移す経路が成り立つ可能性は高い — ただしこれはカラム名の集合だけを見たもので、 型・長さ・順序・NULL 可否・既定値・キー・外部キー・トリガまで同じかはこの比較が答えません。確認できた違いは、 課金・メータリングのテーブルが属するスキーマの位置が変わることだけです。

「移行は大変だ」という漠然とした懸念が数値 1 つで解消され、方向が決まった — 新規インストールではなく移行。

この節で実際にやったことは技術的に大したものではありません。information_schema のクエリ数行です。 要点は意見が割れたときに、数えて答えられる対象が何かを見極めたことです。「移行が大変だ」は 数えにくいが、「カラムがいくつ変わったか」は数えられます。

この記事が主張しないこと#

  • 製品名・バージョン番号・顧客名・チケット番号は書きません。数値の出所は混在しています。移行結果(3/3、FAIL 0)は隔離コンテナでの再現、コミット数・リリース版の照合・48 テーブルのカラム比較はリポジトリとスキーマの実査、起動失敗はローカルのトラブルシューティングです。
  • 現場の移行を完了したという主張ではありません。私がやったのは隔離環境で再現できる区間の 検証と、現場手順書・インストールランブックの準備までです。「全区間」ではない — 認証まわりの区間は下記のとおり再現されていません。
  • 移行失敗 0 件は「スクリプトが失敗と数えたテーブルが 0 個」という意味であり、隔離環境の 結果です。正確な移行や無損失を意味しません。現場の実データダンプで再現するのが最も正確だと 文書に後続課題として残しており、それは実施していません。
  • 共通カラムの積集合コピーは正確な移行方法ではありません。スモークテスト用にわざとそうした もので、正確なカラム対応はガイドの表に従う必要があります。
  • 認証まわりの区間は検証されていません。ローカルに認証 CLI が無く再現できず、スクリプトが その場所に SKIP/WARN を残します。
  • カラム変化 0 はカラムの追加・削除が無かったという意味であり、その 2 バージョン間の 事実です。型・長さ・順序・NULL 可否・既定値・キー・外部キー・トリガまで同一という意味ではなく、 どこまで比較したかはこの記事の根拠では確認していません。この製品の履歴テーブルが元々変わらないという 意味でもありません。

おわりに#

  • 手順書は読んで直るのではなく、一度失敗して直ります。文書だけを読んで分かったことは 1 つだけでした。
  • 「日付順に並べてその後を当てる」は Baseline が日付で切られているときだけ正しいです。 キュレーションなら、その規則は安全ではなく危険を作ります。
  • 誤った前提は消さず、なぜ誤りだったかを残します。消すと次に同じ場所で同じ推論をします。
  • 「移行が難しい」は数えられないが「スキーマの位置が変わる」は数えられます。 意見が割れたら数えられるものへ移します。

文書だけを読んで分かったことは 1 つだけだった — 方式がパッチの 順次適用ではなく再構築と移行だということ。しかもそれさえ最初にざっと見たときには見落としており、手順一覧では なく概要を読んで初めて引っかかったです。残りはすべて — リリース版が同一であることも、Baseline が日付で切った ものではないことも、手順書が存在しないファイルを指していることも — 実際に何かを確認する中で出てきました。ただ 1 つ、方式が違うことは文書を精読して分かったのだが、 それも最初にざっと見たときには見落としていました。本番 DB は、初めて試すのに最も高くつく場所です。
