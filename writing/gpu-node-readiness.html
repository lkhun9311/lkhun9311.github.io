A Stopped Kubelet Quarantined the Node in 46 Seconds
NodeHealth reflects the node condition and applies one taint. The GPU-level intake above it is still a target.

A GPU workload that lands on a node whose driver is not loaded does not fail politely. It fails after the scheduler has already committed the pod, on the most expensive hardware in the cluster. So the question is not “is the node up” but “has anything checked the things a GPU workload actually needs”.

So node readiness here is a CRD with an explicit phase (NodeHealth) rather than an operational assumption. The reconciler was built in two steps on purpose: observe first, enforce second. Observation is idempotent and recovers from drift; enforcement adds exactly one taint.

Four things were declined rather than postponed: cordon, a grace period, a fault-signal trigger, and automatic draining. Each has a reason below. Stopping a worker's kubelet produced Ready → Quarantine → Ready at 0 s, 46 s and 48 s, with the verdict Recovered.

Who this is for#

  • You admit GPU nodes to a cluster and have wondered what "ready" is supposed to mean
  • You have a controller that reflects state and are deciding whether it should also enforce
  • You have to say, in writing, what your platform does not automate

What "ready" has to mean for a GPU node#

The Kubernetes Ready condition says the kubelet is talking to the API server. For a CPU workload that is close enough. For a GPU workload it is not a claim about the device at all.

So NodeHealth carries its own phase, and the intake that would populate it is written as a runbook with tools attached, so that the gap between what is checked and what is assumed stays visible.

Observe first, enforce second#

The first version of the reconciler did not taint anything. It read the target node and reflected readiness into status: phase, a Ready condition, observedGeneration, and a finalizer whose cleanup was a logged no-op.

That sounds like a smaller milestone than it is. Splitting it this way is what made the following three properties testable on their own, before any of them could be confused with enforcement:

  • Idempotency. Status is written only when the computed status differs from the stored one. A reconcile that changes nothing performs no write.
  • Drift recovery. Edit the status by hand and the next reconcile restores it. A node change triggers the same path.
  • Finalizer lifecycle. Added on create, removed on delete after cleanup runs. At this point cleanup had nothing to remove, which is exactly why it was worth writing then.

Enforcement arrived next, and the finalizer's cleanup stopped being a no-op: it now removes the taint when the NodeHealth object is deleted.

One taint, and four things declined#

When the target node is not ready, the reconciler applies platform.lkhun9311.github.io/unhealthy=true:NoSchedule and drives the phase to Quarantine. When the node recovers, the taint is removed. It manages only that taint and never touches another.

The four declines are the part I would defend in a review, so here they are with their reasons.

  • Taint, not cordon. A cordon sets spec.unschedulable on the node, which is a blunt flag other tooling also writes. A taint is namespaced to us by key, and a deliberately opted-in workload can tolerate it.
  • No grace period. Flap damping would make the quarantine decision depend on a window length nobody has measured. A not-ready node quarantines immediately, which is simple and deterministic, and the cost of that choice is visible in the numbers below.
  • Readiness as the trigger, not a fault signal. Fault injection is a later milestone. Triggering on a signal that does not exist yet would make the guard untestable.
  • No automatic drain. Evicting running work is the one action here that destroys something. The platform surfaces what would be drained; a human or an explicit approval flag triggers it.

What stopping a kubelet produced#

Envtest can prove the reconciler writes the right status for a fabricated node object. It cannot prove that a real node going away produces that object in the first place. So the test was to take a throwaway kind cluster with a worker and stop that worker's kubelet.

The 46 seconds is almost certainly not the controller. The reconciler acts on the node's readiness condition, and Kubernetes does not flip that the moment a kubelet stops: it waits out a grace period first. Choosing readiness as the trigger bought simplicity and paid for it in that window, and the number makes the trade visible instead of arguable.

That attribution is read from the design, not measured. The run recorded three phase transitions and their times. It did not record which component spent the 46 seconds, and nothing here instrumented the node controller to find out.

What this does not claim#

  • Everything below runs on a local kind cluster against simulated nvidia.com/gpu capacity. The controller behaviour is real; the GPU-level checks it wants to run are not, and the article says which is which at every step.
  • The GPU-level intake is a target, not code. DCGM, fio, iperf3 and an NCCL baseline all need a real GPU node. When DCGM is unavailable the controller falls back to the Kubernetes node condition and records that the GPU checks were not run.
  • No GPU was checked. The device plugin here is a fake advertising nvidia.com/gpu. Nothing in this article observed a driver, a temperature, an XID or an ECC counter.
  • The intake table is a target. Stages 0 through 3 are a runbook with tools named. They are not implemented, and the controller does not pretend they passed.
  • DCGM absence is recorded, not simulated. When DCGM is unavailable the controller falls back to the node condition and writes down that the GPU-level checks did not run. That distinction is the whole reason the fallback exists.
  • 0s, 46s and 48s are one run on one kind cluster. They are not a distribution, and the 46 seconds in particular depends on kubelet and controller-manager settings that were left at their defaults.
  • Drain is not automated and is not going to be soon. The design defers it deliberately; calling that "next milestone" would overstate how close it is.

Wrapping up#

  • "Ready" has to be a claim about something. The Kubernetes condition is a claim about the kubelet. A GPU node needs a phase that says which checks produced it.
  • Observation and enforcement are separate milestones for a reason. Idempotency, drift recovery and the finalizer are all easier to prove when nothing is being tainted yet.
  • Write down what you decline. Cordon, grace period, fault-signal trigger and automatic drain each had a reason, and a reader who only sees the feature list cannot tell a decision from an omission.
  • A number makes a trade-off arguable instead of rhetorical. Immediate quarantine sounded strict until the measurement showed the strictness lives in a 46-second window owned by someone else.

A controller that reports a state it did not verify is worse than one that reports nothing, because the first one gets trusted. The fallback that records "the GPU checks did not run" exists so that the phase never has to lie.
