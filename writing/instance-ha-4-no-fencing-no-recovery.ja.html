Instance HA ④: Fencing の代わりにプロセスを終了していました
設計は電源が落ちたと確認できるまで移すなと言いました。実装にはその確認がなく、代わりに別の仕掛けが入っています。

③編で八つのシナリオのうち一つだけが 復旧へ進みました。判定が立ったからといって、すぐに移すわけではありません。

理由は①編で見たものと同じです。元がまだ生きてディスクへ書いているのに複製が同じボリュームへ付くと ファイルシステムが壊れます。だから設計は元の電源が確実に落ちたと確認できるまで移さないを 原則として立てました。

ところが資料を読み直して、この編を書き直します。現在の実装にはその確認がありません。 原則は設計書のもので、製品がそう動くという意味ではなかったのに、前の版はその差を書いていませんでした。

この記事の想定読者#

  • 自動復旧に Fencing を入れようとして前提条件を整理したい方
  • 設計書と実際の実装が食い違うとき、何を先に書くべきか迷っている方
  • 電源を確認できない環境で何がその代わりになるのか見たい方
  • ③編を読んで、判定が立ったあとに何をするのか気になる方

設計は確認なしに移すなと言いました#

復旧は VM を別のホストで立て直すことです。元が死んでいなければ、同じボリュームに二つが同時に 付きます。壊れるのは VM 一つではなくボリューム全体です。

横にスクロールすると残りが見えます

復旧手順の四段階。
段階すること
DetectHeartBeat の TTL 満了と Phase 1 の判定完了
VerifyPhase 2 の実行条件をすべて満たすか確認
Fence電源を落として落ちたか確認
RecoverEvacuate を実行

四段階に分けた理由は、戻せない動作を一番うしろに寄せるためです。前の三段階はいつでも止められ、 最後の一つだけが戻せません。

そして電源を落とす経路が障害と一緒に切れると、原則そのものが成り立ちません。だから専用の物理 スイッチを前提条件として求めました。

命令と確認のあいだに五秒を置きました#

Fence 段階で一番間違えやすいのがここです。電源を落とした直後に状態を照会すると、まだ off ではありません。命令が届くことと実際に電源が落ちることのあいだに時間があるからです。

# BMC 専用の物理スイッチ経路で電源を落とす
ipmitool chassis power off

# 最低五秒待つ。すぐ照会すると、まだ off ではない
sleep 5

# 必ず off と読めるか確認する
ipmitool chassis power status

# Storage 種別ごとの残存接続の整理を確認してから
# Evacuate へ進む

待機を外すと二方向に間違えます。きちんと動いた Fencing を失敗と読んで復旧を止めるか、逆に楽観的に 進んで落ちてもいないサーバの VM を移します。五秒は下限で、上限は別に置きます。

Storage の種別ごとに整理の条件が違います#

電源が落ちたからといって、すぐ移せるわけではありません。元がつかんでいた接続が整理される必要があり、 その方法が Storage の種別ごとに違います。

Storage確認すること

四行を一行にまとめなかったのは、確認の対象が違う層にあるからです。転送の規約と Volume の層と管理サービスが混ざっていて、一つの条件では覆えません。

実装にはその確認がありません#

ここまでが設計です。実装は違います。いまの製品は電源を落としも確認もせずに復旧します。 元が生きていないという根拠を、電源の状態ではなく通信の状態から得ています。

設計要素をコードと突き合わせると三つの層に分かれます。未反映ではなく導入待ちの ものがあるので、そう書きました。電源待ちと再試行の設定がコメントの骨組みとして入っています。

代わりにノードが自分の VM を終了します#

では元が書き続けるのを何が止めるのかが残ります。答えはノード自身です。各ノードで動く Agent が 自分で障害を確定すると、自分の上にある VM プロセスを終了します。

# ノードが自分で障害を確定する条件。どれか一つでも当たれば障害
  管理側から状態確認の要求が一定時間来ない
  指定した Gateway へ ping が届かない
  指定した IP と Port へ TCP 接続ができない
  指定した Network Interface が up でない、または loopback

# 確定が一定時間続けば
  自分の上の VM プロセスを探して終了
  ただし移動中と印が付いた VM は除外

条件は四つで、どれか一つでも当たれば障害と見ます。管理側の要求が途切れたこと、Gateway へ ping が 届かないこと、指定した IP と Port へ TCP 接続ができないこと、Network Interface が落ちたことです。

ところが終了が移動より早いことがあります。移している最中の VM を終了すると復旧が失敗します。 だから移動の開始と完了をメッセージで受け取り、終了の除外リストを別に持ちます。

この仕掛けは電源遮断と同じものではありません。ノードが自分の状態を読み違えれば終了も起きません。 電源遮断は外から確認しますが、これは中で判断します。

限界: この記事が主張しないこと#

  • ⚠️ この連作の成果物は設計書です。私は手順を設計して前提条件を求めただけで、BMC 網を構築したり この手順を運用で実行したりしたわけではありません。
  • 「導入待ち」はコメントの骨組みと進行中のアップグレードから推し量ったものです。採否を決めた 記録で確認したものではありません。
  • 五秒は提案値です。機器ごとに電源が落ちる時間を測って選んだ値ではありません。
  • Storage の四項目は排他的な分類ではありません。一つの構成で二つが同時に現れることがあります。
  • 社内資料なので、製品名と顧客名とアドレスとアカウントとホスト名は書いていません。

おわりに#

この編の結論は一行です。設計が求めたことと実装がすることを同じ文で書くと、読む人が だまされます。前の版の題がそうでした。だから題から変えました。

残る差は一つです。電源遮断は外から確認し、プロセス終了は中で判断します。観測者が自分を読み違えれば、 二つ目の方法は働きません。
