Instance HA ④: 電源が落ちたと確認できるまで復旧しません
電源を落とせと命じることと、落ちたと確認することは別の行為です。その間に五秒を置き、Storage の種別ごとに整理条件を分けた理由です。

③編では八つのシナリオのうち一つだけが 復旧へ進みました。この編はその一つが通ったあとの話です。判定が立ったからといって、すぐに移すわけでは ありません。

理由は①編で見たものと同じです。元がまだ生きてディスクを書いているのに複製が同じボリュームに付けば、 ファイルシステムが壊れます。そこで元のホストの電源が確実に落ちたという確認なしには移さないを 原則にしました。

この原則を手順に移すと三つが付いてきます。電源を落とす経路が障害時にも生きていること、命令と確認を 分けること、そして Storage の種別ごとに残存接続を別々に整理することです。

想定読者#

  • 自動復旧に Fencing を入れるため前提条件を整理している方
  • IPMI や BMC の経路をどのネットワークに置くか決める立場の方
  • Storage の種別ごとに残存接続の扱いが違う理由が気になる方
  • ③編を読んで、判定が立ったあとに何をするのかが気になる方

なぜ復旧より電源が先か#

復旧は VM を別のホストで立て直す作業です。ところが元が死んでいなければ、同じボリュームに両側が同時に付きます。壊れるのは VM 一台ではなくボリューム全体です。

そこで原則を「Fencing を確認できなければ復旧もしない」としました。確認しないまま進む経路を残せば、 その経路はいつか開きます。確認を選択ではなく通過条件として置きました。

VLAN 分離では足りませんでした#

電源を落とす経路が IPMI なのに、その経路が障害と一緒に切れれば原則そのものが成り立ちません。 三つの構成を同じ基準で並べました。

横にスクロールすると残りが見えます

BMC の三つの結線と障害時の結果。
構成L2/L3 障害時結果
BMC と MGMT が同じ物理スイッチMGMT と IPMI が同時に遮断Fencing 不可
BMC を VLAN でのみ分離スイッチ自体が死ねば VLAN も消失Fencing が不安定
BMC 専用の物理スイッチMGMT は遮断されるが IPMI は維持Fencing 可能

VLAN 分離は論理的な分離なので、スイッチが丸ごと死ぬ場合を防げません。そこで 専用の物理スイッチを前提条件として求めました。事故の当時このファームには BMC の経路が そもそもありませんでした。

四つの段階に分けました#

横にスクロールすると残りが見えます

復旧手順の四段階。
段階やること
DetectHeartBeat TTL の満了と Phase 1 の判定完了
VerifyPhase 2 の実行条件をすべて満たすかの確認
Fence電源を落とし、落ちたことを確認
RecoverNova Evacuate の実行

四段階に分けた理由は、取り消せない動作を最後に寄せるためです。手前の三段階はいつでも止められ、 最後の一つだけが取り消せません。

命令と確認のあいだに五秒を置きました#

Fence の段階で最も外しやすいのがここです。電源を落とした直後に状態を照会すると、まだ off では ありません。命令が届くことと実際に電源が落ちることのあいだに時間があるからです。

# BMC 専用スイッチの経路で電源を落とす
ipmitool chassis power off

# 最低五秒待つ - 直後の照会はまだ off ではない
sleep 5

# off と読めることを必ず確認する
ipmitool chassis power status

# Storage 種別ごとの整理を確認してから
# Nova Evacuate へ進む

待機を外すと二方向に外します。正常に働いた Fencing を失敗と読んで復旧を止めるか、逆に楽観的に進んで 落ちてもいないホストの VM を移します。五秒は電源が実際に落ちる時間を見る下限で、上限は別に置きます。

Storage 種別ごとに整理条件が違います#

電源が落ちたからといってすぐ移せるわけではありません。元が掴んでいた接続が整理される必要があり、 その方法が Storage の種別ごとに違います。

横にスクロールすると残りが見えます

移す前の Storage 種別ごとの確認。
Storage確認すること
iSCSIsession の終了と SCSI PR の解放
LVMVG Lock の解放
NFSmount の解除
Cindervolume attachment の整理完了

四行を一行にまとめない理由は、確認対象が別々の層にあるからです。転送規約と Volume の層と管理サービスが混ざっており、一つの条件では覆えません。

限界：この記事が主張しないこと#

  • ⚠️ この連作の成果物は設計書です。私は手順を設計し前提条件を求めただけで、BMC 網を実際に構築したり この手順を運用で実行したりはしていません。
  • 五秒は提案値です。機種ごとに電源が落ちる時間を測って選んだ値ではなく、直後の照会を禁じるための 下限として置いた値です。
  • Storage の四項目は排他的な分類ではありません。Cinder は他の三つを管理する側で同じ層ではなく、 一つの構成で二つが同時に現れることもあります。
  • 社内資料のため製品名・顧客名・アドレス・アカウントは書いていません。

おわりに#

この編の結論は一行です。命令を送ることと結果を確認することは別の行為です。 その二つを分けてあいだに待機を置くことが Fence 段階のほぼすべてで、確認の手段である BMC の経路を 前提条件として固めることがその手前にあります。

⑤編はこの手順を誰が実行するかを決める話です。三つのアーキテクチャを同じ基準で比べた結果へ 続きます。
