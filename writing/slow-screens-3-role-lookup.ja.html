ロール取得の 1,409ms が 1ms になりました
解決できない project id ごとに、プロジェクト全件を取り直していました。社内クラウド管理コンソール · 連載「遅い画面」③

こんにちは。社内クラウド管理コンソールの backend を作っています。ユーザー詳細画面で ロール一覧が 1 秒を超えて読み込み中のままでした。

⚠️ この記事の 1,409ms は画面の応答時間ではありません。コードに入れたタイマーが DB の取得が終わったあとに始まり、ロールの行を DTO に変える区間だけを測ります。 DB の取得もシリアライズも転送もその外です。ユーザーが待った時間はこれより長いです。 この記事の数値はすべてその区間の値です。

この画面には すでに cache がありました。ですからこの記事は 「cache を入れたら速くなった」ではなく 「cache があるのに、その cache のせいで遅かった」です。

想定読者#

  • cache を入れたのに、期待したほど速くならない画面を見たことがある方
  • cache が引けなかったとき 何を取り直すかを決めたことがある方
  • 存在しないものを探す取得がある、と気づかず通り過ぎたことがある方

どんな内容#

  • 画面のリクエスト 1 回にロールが 14 行ついてきて、行ごとに project id を 1 つずつ解決します。解決できたのが 8 行、できなかったのが 6 行です。
  • 解決できた 8 行はすべて 0ms でした。そして解決できなかった 6 行を足すと 1,409ms、つまり この実行でタイマーが記録した合計と同じです。
  • 原因は CacheBox.project() が解決できないたびにプロジェクト全件を 取り直していたことです。ところがその 6 つの id は 全件を取り直してもその中にありません。
  • 直したあと同じ区間が 1ms になりました。⚠️ ところが 解決できない行は今も 6 行です。減らしたのは解決できない回数ではなく、 解決できなかったときにかかる時間です。

⚠️ ログには [Hit]・[Miss] と出ますが、これは cache の中を 測ったものではありません。CacheBox を呼んだ結果プロジェクトが返ったかどうかで 付けた名前です。cache からきちんと読めたのに、その id が一覧にないので [Miss] になる こともあります。以下では 「解決できた・できなかった」と呼びます.

社内製品なのでコードもログもそのまま載せていません。製品名・顧客名・内部アドレスは 外し、構造と数値だけを残しました。ログは logger 名と project id を伏せて書き写しています。 ミリ秒は記録のままです。⚠️ 行ごとのミリ秒は 社内文書に貼られたログのスクリーンショットを見て 手で書き写した値です。文書に文字として書かれているのは合計(1,409ms・250ms・1ms)のほうです。

どんな画面#

ユーザーを 1 人開くと、下側にその人が どのプロジェクトでどのロールかが表で出ます。 ロール自体は自分たちの DB にあり、プロジェクト名は OpenStack 側にあります。 正確には、OpenStack でユーザーとプロジェクトを受け持つ Keystone です。 ですからロール 1 行ごとにプロジェクトを 1 回引く必要があります。

その引く場所に cache がありました。自作で (前編①に出てくるあの CacheManager です)、 保持期間は 10 分でした。

ログはすでに、遅れがどこにあるかを記録していました#

取得 1 件ごとに、解決できたかどうかと、かかった時間をすでに記録していました。修正前の 1 回を そのまま書き写すとこうです。

[Miss] projectId=project-A   elapsed  247 ms
[Miss] projectId=project-B   elapsed  235 ms
[Hit ] projectId=project-C   elapsed    0 ms
[Hit ] projectId=project-D   elapsed    0 ms
[Miss] projectId=project-E   elapsed  238 ms
[Miss] projectId=project-F   elapsed  228 ms
[Miss] projectId=project-G   elapsed  233 ms
[Hit ] projectId=project-H   elapsed    0 ms
[Hit ] projectId=project-I   elapsed    0 ms
[Hit ] projectId=project-D   elapsed    0 ms
[Miss] projectId=project-J   elapsed  228 ms
[Hit ] projectId=project-D   elapsed    0 ms
[Hit ] projectId=project-H   elapsed    0 ms
[Hit ] projectId=project-K   elapsed    0 ms
[Result] Total elapsed time: 1409 ms

ここですることは 1 つだけです。

247 + 235 + 238 + 228 + 233 + 228 = 1,409
解決できなかった 6 行の合計が この実行の合計と同じです。解決できた 8 行は 0ms でした。

⚠️ ミリ秒単位の 1 回測定なので 「残りがちょうど 0 だ」までは言えません。 DTO を作り、絞り、並べる費用は各行の区間の外にあり、それが 1ms 未満ならこう見えます。 言えるのは この分解能で 6 行の記録値の合計が総計と同じだったということです。

それでも見る場所は決まります。問うべきは「cache がなぜ効かないのか」ではなく 「解決できない 1 行がなぜ 235ms なのか」です。

原因: 解決できない 1 件が全件を取り直していました#

プロジェクトを引くコードはこうなっていました。

public static Project project(final String projectId) {
    CacheManager manager = CacheManager.getInstance().init(Project.class, 10);
    final Project project = manager.get(Project.class, projectId);

    if (project == null) {                       // ← キーが 1 つ無い
        client.identity().projects().list()      // ← 全件を取り直して
              .forEach(r -> manager.set(Project.class, r.getId(), r));
        return manager.get(Project.class, projectId);   // ← もう一度引く
    }
    return project;
}

読むともっともらしく見えます。無ければ詰めて、もう一度見る。cache を初めて書くときに 自然に出てくる形で、実際 最初の 1 回はこれで正しいのです。

問題は 「詰めても現れないキー」があるときです。

その 6 件は、詰め直しても存在しません#

ロール表は 自分たちの DB にあり、プロジェクトは OpenStack にあります。 OpenStack 側でプロジェクトを消しても こちらのロール表のその行はそのまま残ります。 その行が指す projectId は、もうどこにもありません。

すると上のコードはこう回ります。

  1. cache で引く → 無い
  2. 全件を取り直す → 235ms
  3. もう一度引く → やはり無い。消えたプロジェクトだからです
  4. 次の行でまた無い id に当たる → 1 に戻る

無い id に当たるたびに、プロジェクト全件を取り直していました。 取り直してもその 6 つの id は一覧に無いので、次の行でも同じように取り直します。

解決できなかった 6 行は 手元にある 3 回の実行すべてで同じ 6 つの id でした。 修正前 1 回と修正後 2 回で、日付も 1 日違います。たまたま cache が冷えていたのではなく、 埋まりようのない場所に見えます。⚠️ 3 回は 3 回です。それ以上は回していません。

修正: キーで引かず、一覧を絞りました#

直したのは 引き方 1 つです。

// 前: キー 1 つを cache に尋ねる。無ければ外部 API を呼ぶ
var project = CacheBox.project(roleAssignment.getProjectId());

// 後: 一覧を cache から受け取り、その中で絞る。無ければ無いまま終わり
var project = CacheBox.projects().stream()
        .filter(p -> p.getId().equalsIgnoreCase(roleAssignment.getProjectId()))
        .findFirst();

projects() も外部 API を呼ぶことがあります。違うのは 「その id が無い」がもう外部 API を呼ぶ条件ではないという点です。

正確にはこうです。projects() は cache から一覧を受け取りますが、そのときに 期限切れの項目を 1 つずつ取り除きます。そうして残ったものが 完全に空のときだけ外部 API を呼びます。

⚠️ ここに落とし穴が 1 つあります。一部だけ期限切れなら呼びません。 生き残った項目が 1 つでもあれば、その不完全な一覧をそのまま返し、その間に抜けたプロジェクトは 存在するのに「解決できない」になります。今回の実行では項目がまとめて詰められ まとめて期限切れになるので表に出ませんでした。出なかっただけで、無いという意味ではありません。

ログがそのまま示します。cache が期限切れの状態で 1 回回すと、

[Miss] projectId=project-A   elapsed  246 ms   ← 一覧を取りに行く呼び出し
[Miss] projectId=project-B   elapsed    0 ms
[Hit ] projectId=project-C   elapsed    0 ms
…
[Miss] projectId=project-J   elapsed    0 ms
[Result] Total elapsed time: 250 ms

解決できない行は今も 6 行です。ところがそのうち 5 回が 0ms です。 cache が有効な状態では最初の 1 回も 0ms になり、合計が 1ms になります。

横にスクロールすると残りが見えます

ロール取得 1 件の、cache 状態ごとの時間。
状態ロール行解決できない解決できない 1 行の時間区間の合計
修正前146228〜247ms1,409ms
修正後 · cache 期限切れ146最初の 1 件だけ 246ms250ms

真ん中の欄が 3 行とも 6 です。 解決できない回数を減らしたことはありません。変わったのは右の 2 欄です。 ⚠️ 3 行とも 1 回の観測です。繰り返して分布を見た値ではありません。

⚠️ 代わりに失ったもの: 新しいプロジェクトが遅れて見えます#

修正前のコードには 誰も当てにしていなかった働きが 1 つありました。知らない id に 当たると一覧を取り直すので、さっき作ったプロジェクトがすぐ見えたのです。 遅い代わりに、最新でした。

直したあとは、知らない id に当たっても何もしません。ですから新しいプロジェクトは cache が詰め直されるまで見えません。

⚠️ その「詰め直されるまで」を 10 分だと断言はできません。 保持期間は一覧単位ではなく 項目ごとに記録された保存時刻に掛かります。そして project() は消えずに残っているので、別の画面でその関数が 1 回回れば項目が まとめて詰め直されます。すると時刻が更新されて遅く見えることも、ちょうどその瞬間に 詰められて早く見えることもあります。言えるのは 他で詰めなければ、最後の項目が期限切れに なったあとの最初の取得に反映されるというところまでです。

遅延を無くしたのではなく 遅延と最新性を交換したのです。 この画面は人が目で読む一覧なので 10 分を受け入れられました。 その判断ができない画面もあります。

そしてデータ側の条件はそのまま残りました#

遅さの 直接の原因は、解決できないたびに全件を取り直していた 引き方で、その引き方を 6 回も踏ませたデータ側の条件が、 存在しないプロジェクトを指すロール行 6 つでした。2 つは別のものです。

私が直したのは 前者です。後者は 今もそのままあります。 その行が高くつかなくなっただけで、無くなってはいません。OpenStack でプロジェクトが消えたとき こちらのロール表も一緒に片づくようにするのが本来の仕事で、それはこの作業に入っていませんでした。

限界: この記事が主張しないこと#

  • 測定が System.currentTimeMillis() と log.info です。 currentTimeMillis() は単調時計ではなく、システム時刻が変われば値も動きます。 そして各行の区間の 中に ログ出力が 1 回入っていて、そのあとのログ 1 回は 入っていません。0ms は「1ms 未満」という意味で、「費用が無い」ではありません。 きちんとやるなら System.nanoTime() か timer metric で測り、外部 API の呼び出し回数は 別に数える必要があります。
  • 1 回の実行です。3 つの状態をそれぞれ 1 回ずつ回したログで、繰り返して分布を見た ものではありません。235ms という値もその 6 件の平均にすぎません。
  • なぜ一覧 1 回が 235ms なのかは掘り下げていません。ネットワークか、Keystone 側の 処理か、プロジェクト数のせいかを切り分けていません。
  • プロジェクトが何個だったかは記録にありません。ですから「一覧が大きくて遅い」のか 「呼び出し自体が高い」のかも、このログでは分かりません。
  • 直したコードも完全ではありません。projects() をロール 1 行ごとに 1 回呼びます。cache が温かいうちは 0ms で表に出ませんが、行がとても多くなると 一覧を繰り返し走査する費用が残ります。ループの外に 1 回だけ出すほうが良いです。
  • この cache は前編①の問題をそのまま抱えています。projects() に ロックが無いので、cache が空になる瞬間にリクエストが複数入ると それぞれが外部 API を 呼びます。⚠️ コードを読んで言っていることで、このログで確認したものではありません。 ユーザーを 1 人開いた実行なので、同時リクエストはありませんでした。
  • 運用統計ではありません。試験環境でユーザーを 1 人開いたログです。

おわりに#

まとめるとこうです。

  • cache があることと速いことは別です。ここでは解決できた行がすべて 0ms なのに 区間は 1,409ms でした。
  • 解決できなかったとき何をするかが cache 設計の半分です。「無ければ全部取り直す」は 最初の 1 回には正しく、詰めても現れない id の前では最も悪い選択です。
  • 減らせるものは 2 つです。解決できない 回数と、解決できなかった ときの 処理時間。今回減らしたのは後ろで、前はそのままです。
  • 速くなった代わりに何を失ったかも一緒に書くべきです。ここでは 10 分ぶんの 最新性です。

最後に 1 行だけ残すなら、これです。 すでに書かれていたログを、足してみるだけの仕事でした。 その 6 行を足すまでは「cache がなぜ効かないのか」を覗き込んでいました。
