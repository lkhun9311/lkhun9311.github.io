성공 2/2인데 왜 일부 작업 실패인가
Snapshot 생성 성공과 보관 정리·로컬 저장 실패를 분리해 결과의 의미를 명확히 했습니다.

2026년 9월

목차

  • 이 글의 예상 독자
  • 한 실행에는 같은 종류의 일이 들어 있지 않습니다
  • 분모를 Snapshot 생성 시도로 고정했습니다
  • 결과는 카운트와 후처리 상태에서 파생합니다
  • 외부 API 접수를 성공으로 세지 않았습니다
  • 색 하나에 모든 의미를 맡기지 않았습니다
  • 선택한 트레이드오프
  • 마치며

스냅샷 실행 이력 설계 연작의 한 편입니다. 여기서는 「몇 개 성공했나」와 「전체가 성공인가」를 왜 따로 세는지를 다룹니다. 전체 개요와 글 순서를 먼저 볼 수 있습니다.

볼륨 부팅 Instance에 Root Volume 하나와 Mount Volume 하나가 붙어 있었습니다. Scheduler가 둘의 Snapshot을 모두 만들었고 화면의 카운트는 2/2였습니다. 그런데 결과 칩은 성공이 아니라 「일부 작업 실패」였습니다.

처음 보면 모순입니다. 실제로 실패한 것은 새 Snapshot이 아니라 보관 개수를 맞추려고 지우던 이전 Snapshot이었습니다. 새 백업은 온전하지만 실행 전체는 끝까지 온전하지 않았습니다. 어느 한쪽만 결과로 삼으면 다른 쪽을 숨기게 됩니다.

저는 이력이 없던 실행 경로를 메운 뒤 한 실행의 생성·정리·로컬 저장을 분리하는 상태 모델을 설계하고 화면까지 연결했습니다. 설명은 실제 배치의 RunStats, recordRunHistory와 React 결과 셀을 다시 대조해 썼습니다.

이 글의 예상 독자#

  • 여러 대상과 후처리가 섞인 배치의 실행 결과를 설계하시는 분
  • 부분 성공을 Boolean이나 단일 상태값으로 표현하다 한계를 만난 분
  • 화면의 성공 카운트와 운영 상태가 왜 다른지 설명해야 하는 분

한 실행에는 같은 종류의 일이 들어 있지 않습니다#

스케줄 유형은 하나지만 생성 대상은 하나가 아닐 수 있습니다. 코드의 최상위 분기는 이름이 아니라 Volume 부착 여부와 부팅 형태를 따라갑니다. 이미지 부팅 Instance에 데이터 Volume이 붙으면 Instance Image와 Mount Volume Snapshot을 함께 만들고 Volume 부팅이면 Image 없이 Root와 Mount Volume을 만듭니다.

가로로 넘겨 표 전체를 볼 수 있습니다.
실행 유형생성 대상정상 카운트생성 뒤 작업
Image 부팅, Volume 없음Instance Image1/1보관 정리, 선택적 로컬 저장
Image 부팅, Mount 1개Instance Image + Mount Snapshot2/2대상별 보관 정리와 저장
Volume 부팅, Mount 없음Root Volume Snapshot1/1Root 보관 묶음 정리
Volume 부팅, Mount 1개Root + Mount Snapshot2/2서로 다른 보관 묶음 정리
단독 VolumeVolume Snapshot1/1보관 정리, 선택적 로컬 저장

여기에 준비 단계가 더 있습니다. 전용 사용자와 역할, 프로젝트, 스케줄 설정을 확인하다 실패하면 생성 API를 한 번도 부르지 않습니다. 이때 0/1을 보여 주면 존재하지 않은 시도를 만든 셈입니다. 그래서 대상 시도 전 실패의 카운트는 null로 두고 화면에서 배지를 숨겼습니다.

분모를 Snapshot 생성 시도로 고정했습니다#

분모에 생성·정리·저장을 모두 넣으면 기능 설정에 따라 숫자의 뜻이 바뀝니다. 로컬 저장을 켠 순간 2/2였던 실행이 4/4가 되고 오래된 Snapshot이 없으면 정리 시도 자체가 사라집니다. 같은 열의 숫자를 실행마다 다른 단위로 읽어야 합니다.

그래서 succeeded_count / total_count는 오직 이번 실행의 Snapshot 생성 대상만 셉니다. 정리와 로컬 저장은 이름 목록과 실패 목록으로 따로 모읍니다. 카운트는 백업 세트가 얼마나 완성됐는지, 최종 결과는 실행 전체가 얼마나 건강했는지 답합니다.

결과는 카운트와 후처리 상태에서 파생합니다#

저장할 결과는 SUCCESS, PARTIAL, FAILED 셋입니다. 하지만 코드가 이 값을 직접 여기저기 쓰게 두지 않았습니다. 종료 지점에서 생성 집계, 전파된 예외, 후처리 실패를 모아 결과를 한 번 계산합니다.

if (failure == null) {
    result = secondaryFailure ? PARTIAL : SUCCESS;
} else if (total == 0) {
    result = FAILED;              // 준비 단계 중단
} else {
    if (failed == 0) failed = 1; // 집계 전 예외의 모순 보정
    result = succeeded > 0 ? PARTIAL : FAILED;
}

성공 하나를 센 뒤 다음 대상에서 예외가 나면 그대로는 「1/1 일부 작업 실패」가 됩니다. 그래서 집계되지 않은 실패도 분모에 반영해 화면의 숫자와 문장이 충돌하지 않게 했습니다.

외부 API 접수를 성공으로 세지 않았습니다#

OpenStack 생성 API가 ID를 돌려준 것은 작업 접수입니다. Volume Snapshot은 나중에 available 또는 error로 바뀌고 Instance Image도 active를 기다려야 합니다. ID를 받자마자 성공을 올리면 시간 초과와 오류 상태가 이미 성공으로 집계됩니다.

실제 코드는 유효한 ID, 완료 상태, 내부 원장 저장을 모두 지난 뒤에만 recordRunSuccess를 부릅니다. 그 전 실패는 TIMEOUT, SNAPSHOT_ERROR_STATE, API_RESPONSE_INVALID처럼 실패 지점에서 구조화합니다.

색 하나에 모든 의미를 맡기지 않았습니다#

PARTIAL에는 두 상황이 들어옵니다. 생성 일부가 빠진 1/2와 생성은 모두 끝났지만 정리 또는 로컬 저장이 실패한 2/2입니다. DB Enum을 둘로 나누면 의미는 또렷하지만 기존 행 마이그레이션, API, 번역, 화면과 테스트까지 바뀝니다.

이번 범위에서는 Enum을 유지하고 reason_code로 시각적 심각도를 나눴습니다. 백업 누락이 있는 일부 실패는 주황, RETENTION_PRUNE_FAILED와 LOCAL_SAVE_FAILED처럼 백업 자체가 온전한 경우는 파랑입니다. 원인 열과 설명 배열은 무엇이 실패했는지 그대로 남깁니다.

선택한 트레이드오프#

  • 고정한 것: 카운트는 언제나 새 Snapshot 생성 성공 수와 시도 수만 뜻합니다.
  • 분리한 것: 백업 완성도와 실행 전체 건전성은 서로 다른 값으로 보여 줍니다.
  • 감수한 것: PARTIAL만으로는 부족하므로 사유 코드와 카운트를 함께 읽어야 합니다.

마치며#

성공 2/2와 일부 작업 실패는 모순이 아닙니다. 앞 숫자는 새 백업의 완성도를, 뒤 문장은 생성부터 정리와 저장까지 실행 전체의 건전성을 말합니다. 둘을 같은 축에 올려놓을 때만 모순이 됩니다.

배치 이력의 숫자를 설계할 때 먼저 정해야 할 것은 값이 아니라 분모의 계약입니다. 그 계약을 고정하면 상태값, 사유, 색과 설명의 책임도 따라 정리됩니다.

다음 글에서는 Scheduler를 삭제한 뒤에도 이력을 남기기 위해 현재 상태와 실행 시점 증거를 분리한 과정을 이어서 다룹니다.
