All Twenty-Three Recorded Runs Used the Same Condition
A tool being trustworthy and a comparison being finished are two different things.

In part one I put up four gates and fired each refusal path. With the tool finally trustworthy I laid its state out in a table, and a column came back that I had not expected.

All twenty-three recorded runs were the same condition. Twenty-three runs of the condition where no preemption happens, and zero runs each of the honouring and ignoring conditions.

Comparing those two is the entire reason this harness exists. I had been treating "the tool is trustworthy now" and "there are results" as the same statement.

Who this is for#

  • Anyone building a tool to compare A against B
  • Anyone spending their time getting guards to pass while the comparison waits
  • Anyone who wants to see what a queue policy buys and what it pays when it reclaims
  • Anyone who read part one and wondered what came after the gates

All twenty-three were the same condition#

Getting each gate to pass kept the view narrow. Something turned green every time, which felt like progress, and the comparison never ran once.

The same table produced a second empty column. Of the five gates, only three had their refusal path confirmed against a live cluster; the other two had proved refusal solely by breaking the code on purpose.

I removed exactly one verb from a role#

The observation continuity gate enforces one rule: do not submit unless the watch is established. Seeing that refusal for real means the watch has to fail. So I built a role with every permission the run needs and exactly one watch verb removed.

# Which condition the stored runs had used
arms exercised: {'no-preemption': 23}

# A role with exactly one verb removed on one stream
jobs   list  -> yes      workloads  watch -> yes
jobs   watch -> NO   <-  pods       watch -> yes
jobs   get   -> yes      nodes      patch -> yes

# Result: refused before anything was submitted
ERROR: setup-failed: the stream ended before it ever established a watch (403)
ledger: 0 events

Checking that the carve-out was precisely one verb mattered. Cut permissions broadly and the run fails at an earlier stage, and then it demonstrates some other gate rather than this one.

The result was exact. The run refused before submitting anything, and the artifact kept the raw 403. The remaining gate was checked by injecting a defect into a file, it passed when it should not have, and I wrote that up in another post.

Running the three conditions side by side#

With the refusal paths closed I ran the three conditions side by side for the first time. All three share a fixture and the owner arrives at the same moment in each.

Almost all of what preemption buys rides on whether the workload honours the termination signal. Owner wait dropping from 23 seconds to 3 is the gain, and when the borrower ignores the signal it is 19, so only 4 seconds came back.

And the ignoring condition loses on both sides. There is almost no latency gain, and the borrower's completed work is not credited, so it runs again from the beginning. The tool flagged this itself.

Five runs each, to settle the direction#

One run each says only which direction things move, so I ran five per condition off the same commit, fifteen in total. The rules for reading the result were written down before the results came in. Choosing the criteria afterwards is fitting, not measuring.

Getting quota and getting the device are different#

One of the pre-registered rules fired. The 19 seconds in the ignoring condition is not a measured value but a computed one. All five runs landed between 19.35 and 19.54 seconds.

Owner holds quota22.46 s0.12 s0.11 s
Borrower stops20.45 s0.16 s18.60 s
Owner is up again23.40 s2.79 s19.42 s

The owner in the ignoring condition holds quota after 0.11 seconds. Being up again takes 19.42. That whole difference is time spent waiting for the borrower to spend the rest of its service.

So I rewrote the sentence. I had been about to write "the ignoring condition recovers only 4 of the 20 seconds", and what actually happens is "it gets quota immediately and does not get the device". The 4 seconds that came back are an admission round trip skipped, not service restored, and the rest is decided by the borrower's remaining time.

Limits: what this post does not claim#

  • ⚠️ The 19 seconds is a floor set by the borrower's remaining service time, not by a forced kill. A longer job would be cut off at the grace deadline instead.
  • Five runs per condition is still not statistics. The spread is narrow because the fixture is deterministic, not because the measurement is precise, and this was one machine on one day.
  • The source record still carries an older line saying one run per condition can only show direction. The fifteen-run section was appended later without removing it. This post takes the fifteen-run figures and notes the inconsistency here.
  • The 40.7 GPU-seconds in the honouring condition is discarded progress, not idle time. Honouring the signal does not prevent progress from being thrown away.
  • These runs were on a kind cluster with a fake device plugin. Not real devices.

Wrapping up#

The conclusion is one line. A tool being trustworthy and a comparison being finished are two different things. While the gates went green one by one, the comparison this tool exists for stood at zero.

And once a number arrives, it has to be sorted into measured or computed. The 19 seconds looked measured, and the borrower's remaining time was setting it.
