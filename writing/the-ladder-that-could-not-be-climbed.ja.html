GPU 1枚を分けると、共有エンジンが届かない遅延目標に届きます
それを知る前に、答えがすでに決まっていた梯子にお金を使いました。

GPU 1枚を2テナントで分け合うとき、エンジンを1つだけ置いて共有する構成と テナントごとにエンジンを1つずつ与える構成の、どちらが遅延目標をより高い負荷まで 守るのかを測った話です。

ただしこの記事の半分は、私が設計を誤って、答えがすでに決まっている実験を買った という話です。基準も判定規則も停止規則もすべて正しかったのに、梯子を登れない場所に置きました。 そしてそれは、カードを借りる前に分かることでした。

先に留保をひとつ置きます。以下の結果は4つの到着率で測った合否であって、 持続可能な最大到着率の証明ではありません。どちらの構成についても最大値は特定できていません。 残りの留保は「この記事が主張しないこと」にまとめました。

この記事の想定読者

  • GPU 1枚を複数テナントで分け合う構成を検討している方
  • 性能実験を設計するとき、何を買えば答えが出るのか毎回迷う方
  • 測定ツールを自分で作って使っている方

どんな構成ですか

小さな言語モデル(Qwen2.5-3B)を GPU 1枚(NVIDIA A10G)で配信しながら、2種類のお客さん を同時に受けます。プレミアムテナントは短いプロンプトを頻繁に送り、最初のトークンが 早く出る必要があります。競合テナントは4万文字の長いプロンプトをときどき送り、 1件が GPU を長く占有します。

基準は1つに決めておきました。プレミアムの最初のトークンまでの時間(TTFT)の p99 が 139.0 ms 以下であることです。この値は競合テナントがいないときの基準線(69.5 ms)のちょうど2倍で、 実験を始める前に決めて文書に書いておきました。

固定した仕事量で容量が測れると思っていました

先の実験では、2つの構成にまったく同じ要求トレースを与えて回しました。3本の腕すべてが 要求を1件も失わずに終えました。それでスループットを比べたところ 589.3 / 586.9 / 584.0 tok/s となり、 「分割の容量コストは 0.9%」と書くところでした。

そう書けません。3本が同じ仕事量をすべて終えたなら、分子は定数です。

結論から申し上げます

梯子を先の実験の負荷の下に置き直して回すと、こうなりました。

4つのプレミアム到着率における両構成のプレミアム TTFT p99 と 139.0 ms 目標の達成可否。
プレミアム負荷共有構成 p99分割構成 p99目標 139.0 ms
1.16 req/s1,282.5 ms123.8 ms分割のみ達成
2.31 req/s1,694.7 ms130.4 ms分割のみ達成
4.61 req/s2,303.3 ms143.2 msどちらも未達
9.22 req/s1,896.0 ms1,013.2 msどちらも未達

共有構成はプレミアム負荷を 1.16 req/s まで下げても目標に届きません。競合テナントは すべてのセルで139件を送り139件すべてを完了し、目標に近かった2段は別のカードでもう一度買って 確かめました。2つのセルはそれぞれ 2.1 ms、0.3 ms 動きました。

登れない場所に梯子を置きました

梯子はこう動きます。低い負荷から始めて一段ずつ登り、両方の構成が目標を外す最初の段で 止まります。その直前の段が、各構成が耐えた最大負荷です。

私は底の段を 9.22 req/s に置きました。先の実験が回っていた負荷です。ところが 先の実験はまさにその負荷で、共有 1,892 ms、分割 1,007 ms を測っていました。 基準は 139 ms です。

私はこの数字を事前登録文書の第2段落に自分の手で引用しておきながら、見落としました。基準も判定も 停止規則もすべて正しかったのです。誤っていたのは探索の向きであり、探索の向きは設計の 一部です。すでに持っていた数字を確かめ直すのに、およそ 0.35 ドルを使いました。

判定は正しく、ランナーが終了コードを読み違えました

より痛いのはこちらです。判定は1段目でまったく正しく「両構成とも目標を外したので ここで止まれ」を終了コード10で返しました。ところが実行スクリプトがそれを0として 読みました。

# 誤ったコード
if "$BIN" ladder-verdict ... ; then
  ...
  continue
fi
verdict_code=$?          # if 文の終了状態です。コマンドの10ではありません

bash では if 文の直後の $? は条件コマンドの状態ではなく if 文自体の状態です。条件が失敗し else がなければ if 文は0を返します。そのため正しい停止が「採点できない段」として 報告され、お金を払ったセッションがそこで終わりました。

# 直したコード — 状態をコマンドの隣で捕まえます
verdict_code=0
"$BIN" ladder-verdict ... || verdict_code=$?
if [ "$verdict_code" -eq 0 ]; then ...

リハーサルではこれを捕まえられませんでした。GPU なしで回るリハーサルは ダミーのエンジンがミリ秒で答えるため目標を超えることがなく、停止の分岐が一度も 実行されません。私は判定コマンドの終了コード10をテストで固定していましたが、 それを読むスクリプト側は固定していませんでした。

今は判定コマンドだけを横取りする薄い代替スクリプトを挟んで、実際の実行スクリプトをその分岐へ 追い込むリハーサルがあります。そして直す前に、欠陥を復活させて赤くなることから 確かめました。

負荷を下げても共有構成が届かない理由

尾を作っているのがプレミアムがプレミアムの後ろに並ぶことではないからです。 4.61 req/s の共有構成で 139 ms を超えたプレミアム要求は651件でしたが、そのうち 649件(99.7%)が競合テナントの要求がまだ自分の最初のトークンを待っている 最中に送られたものでした。

p99 が隠していたもの

基準が p99 なので、「未達」がどれほど大きな未達なのかが見えません。すでに買ったデータを数え直し ました。

分割構成におけるプレミアム到着率別の p99 と 139 ms を超えた要求数。
プレミアム負荷分割 p99139 ms を超えた要求
1.16 req/s123.8 ms1件 / 585 (0.17%)
2.31 req/s130.4 ms5件 / 1,164 (0.43%)
4.61 req/s143.2 ms40件 / 2,327 (1.72%)
9.22 req/s1,013.2 ms823件 / 4,655 (17.68%)

4.61 の「未達」は40件です。そしてこの比率は4点すべてで単調に増えます。p99 は観測値 1つなので動きえますが、数千件のうち何件かという数は、分布が動かない限りあまり動きません。 本当の崖は 4.61 と 9.22 の間(1.7% → 17.7%)にあり、そこは測っていません。

ただではありません

分割構成は競合テナントの要求を1件も失いません。代わりに待たせます。

2.31 req/s における両構成の完了時間の比較。
2.31 req/s にて共有分割
プレミアム完了の中央値1.089 s1.987 s
競合テナント完了の中央値1.316 s4.654 s
競合テナント完了の p994.050 s16.344 s

プレミアムは中央値を差し出して尾を買います。そしてその代金はおおむね競合テナントが 払います。この構成を有効にするプラットフォームはそれを選んでいるのであり、料金を受け取る相手に 説明する義務があります。

この記事が主張しないこと

  • 持続可能な最大到着率は示していません。上の表は 4つの到着率で測った合否であり、その間や上が異なる振る舞いをしないことの証明ではありません。
  • 505秒より短い窓については何も保証しません。2.31 req/s で達成した実行も、最後の101秒だけを 取り出すと p99 が 141.7 ms で目標を超えます。
  • 競合テナントの到着パターンを変えたときの結果は分かりません。段ごとに競合要求の件数は139件で 固定しましたが、到着の時刻表は固定できていません。段をまたぐ比較には到着率の変化とスケジュールの 変化が混ざっています。
  • 原因がバッチ上限ではなくトポロジだとは言えません。分割するとエンジンあたりの同時処理 上限も64から32へ一緒に下がります。両者を切り分ける実験はしていません。
  • 139 ms が商業的に意味のある値だとは言えません。基準線の2倍というだけで、顧客要件では ありません。
  • 別のカード、別のモデル、MIG については何も分かりません。A10G 1枚、モデル1つ、プロンプトの 組み合わせ1つです。

おわりに

  • 固定した仕事量をすべて終えた実験は容量を測れません。分子が定数なので、余裕が どれだけあっても同じ数字が出ます。
  • 探索の向きは設計の一部です。基準も判定も停止規則もすべて正しくても、答えが ありえない場所から始めれば答えは出ません。そしてそれは借りる前に分かることでした。
  • ガードを固定することと、そのガードを読むコードを固定することは別の仕事です。 終了コード10はテストで縛られていましたが、それを if の後の $? で読むと いう事実は縛られていませんでした。
  • 結果は出ました。この競合負荷のもとで分割構成は 2.31 req/s まで 139 ms を守り、 共有構成は測ったどの負荷でも守れません。代わりに競合テナントの尾が4倍になります。

測定ツールをご自身で作って使っているなら、わざと壊して赤くなるかを先に確かめることを おすすめします。このプロジェクトで最も高くついた欠陥はすべて、存在していて、書かれた場所では 正しく、肝心の場所で参照されないガードでした。
