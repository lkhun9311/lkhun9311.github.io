통합 모니터링 이슈 01. UI Rendering 부분 실패: Cold Cache Regression

사내 Cloud 관리 Console의 통합 모니터링 대시보드를 만들고 있습니다. 어느 배포 직후, 토폴로지 UI는 평소처럼 빠르게 렌더됐는데 네트워크 노드 레이어의 프로젝트 박스만 안 보였습니다. 화면 전체가 아니라 한 레이어의 렌더링만 부분적으로 실패한 것입니다.

데이터가 아예 안 온 것이면 화면이 느리거나 비어야 하는데, 화면은 빨랐습니다. ‘빠른 렌더 + 박스만 없음’이 힌트였습니다. 화면은 그렸는데 그 레이어가 읽는 소스만 비어 있었던 것입니다.

원인은 앞서 부분 실패에 강하도록 공유 Cache를 리팩터한 변경이 cold(재기동 직후)라는 특정 초기 상태에서 새 조합을 만든 것이었고, 그걸 살렸어야 할 안전망 코드는 수년째 죽어 있었습니다. 이 글은 그 반쪽 상태와 죽은 폴백, 그리고 한 소스로 되돌린 수정에 대한 것입니다.

이 글의 예상 독자#

  • 구조 정보는 REST로, 실시간 값은 SSE로 받아 한 화면에 섞으시는 분
  • 부분 실패에 강하게 만든 변경이 특정 초기 상태에서 회귀를 낸 적이 있는 분
  • 폴백·안전망 코드가 실제로 도는지 확인해 본 적이 없는 분

증상: 빠르게 뜨는데 박스만 없다#

대시보드 토폴로지에는 노드 레이어가 여러 겹 있고, 그 위에 프로젝트가 사각형 박스로 얹힙니다. 증상은 네트워크 노드 레이어의 박스만 0개였습니다. 다른 레이어와 노드 자체는 정상으로 그려졌습니다.

배경: 부분 실패에 강하게 만든 리팩터#

이 대시보드는 구조 정보(노드·프로젝트)는 REST로 한 번 받고, 실시간 값은 SSE로 받습니다. 앞선 공유 Cache 설계에서, 한쪽이 실패해도 다른 쪽은 살리도록 SSE 페이로드의 node 반쪽과 instance 반쪽을 독립적으로 채택하게 했습니다. 부분 실패에 강해지는 견고화였습니다.

각 반쪽은 세대 번호(gen)와 degraded 플래그를 달고 옵니다. gen ≥ 1이면 실측이 붙은 fresh, gen 0이면 아직 실측 전입니다.

cold가 만든 반쪽 상태#

재기동 직후(cold)에는 그전에 없던 조합이 생깁니다. node는 이미 채워졌는데(gen ≥ 1), instance는 아직 실측이 안 붙어 빈 목록 + degraded + gen 0으로 옵니다. 실행 중인 인스턴스는 있지만 수집 값이 아직 매칭되지 않아 ‘빈 목록’으로 나가는 것입니다.

프론트가 빈 목록을 박스 소스로 읽었습니다#

프론트는 네트워크 노드 레이어의 프로젝트 박스를 instance 반쪽에서 가져옵니다. cold에서는 그 반쪽이 빈 목록이라 박스가 0개가 됩니다. node 반쪽은 채워졌으니 화면은 빨리 뜹니다.

원래는 SSE가 비면 REST로 받아 둔 구조 정보로 폴백했어야 합니다. 그 폴백이 있었다면 cold에도 박스는 REST 구조에서 채워졌을 것입니다.

죽은 안전망: 자기대입 no-op#

그 폴백을 담당하던 한 줄이 수년째 죽어 있었습니다.

// 안전망: SSE가 비면 REST 구조로 폴백해야 한다 — 그런데
data[0].items = arrayData(socketData)[0]?.items || [];
//              └─ socketData(자기 자신)에서 다시 읽는다 → 자기대입 no-op
// REST(server_info_list)로 가는 폴백이 아니라, 빈 값을 빈 값으로 덮어쓴다

REST 구조가 아니라 방금 본 빈 SSE 값을 자기 자신에서 다시 읽어 대입하고 있었습니다. 폴백은 한 번도 돌지 않았고, cold의 빈 목록이 그대로 화면에 남았습니다. 오래전부터 있던 줄이라 아무도 이상을 못 느꼈습니다 — 평소(warm)에는 SSE가 채워져 있어 이 줄이 무해했기 때문입니다.

수정: 한 소스에서 파생하도록#

먼저 좁게 고쳤습니다. 죽은 no-op을 지우고, instance 반쪽을 한 번이라도 정상 채택했는지로 판정해 cold 구간에만 REST 구조로 폴백했습니다. 인스턴스가 붙은 뒤의 빈 목록은 실제 상태로 둬서 ‘유령 프로젝트’가 되살아나지 않게 했습니다.

그다음 좁은 패치를 단일 소스로 교체했습니다. 박스·서버 상태 위젯·프로젝트별 카운트를 전부 하나의 파생값에서 뽑게 했습니다. 흩어져 있던 상태와 여러 참조를 걷어내 코드가 45줄 줄었습니다.

// 수정: 화면의 여러 요소가 '한 소스'에서 파생한다
const visibleInstances = arrayData(sse ?? rest);   // SSE 없으면 REST 구조로
// 프로젝트 박스 · 서버 상태 위젯 · 프로젝트별 카운트 → 모두 visibleInstances 하나에서

검증: 결정론적 재현#

프론트의 채택·렌더 로직을 그대로 떼어, cold 페이로드 시퀀스로 재현했습니다. 수정 전후를 같은 입력으로 돌려 박스 개수를 셌습니다.

시나리오수정 전 (죽은 no-op)수정 후
cold #1박스 0박스 2
cold #2박스 0박스 2
복구 (instance 매칭됨)박스 2박스 2
권위 있는 0개 (실제로 프로젝트 0)박스 0박스 0

마지막 줄이 중요합니다. 실제로 프로젝트가 0개일 때는 폴백이 유령을 되살리면 안 됩니다. 수정본은 이 경우 0을 유지했습니다 — cold의 빈 목록은 채우고, 권위 있는 0개는 그대로 둔 것입니다.

정석은 백엔드에 있습니다#

프론트가 REST 구조와 SSE 실측을 섞어 화면을 그리는 구조 자체가 이런 반쪽 상태에 약합니다. 진짜 해결은 백엔드가 cold에도 프로젝트·VM 구조를 ‘no-data/degraded’ 상태로 emit해서, 프론트가 한 소스만 읽게 하는 것입니다.

이건 아직 하지 않았습니다. 이 글의 수정은 증상을 없애고 정합을 되돌린 것이고, 구조적 정석은 백엔드 emit로 남아 있습니다. 또 cold가 아주 길면 마운트 시 한 번 받은 REST 스냅샷 이후에 생기거나 사라진 프로젝트는 못 따라갑니다 — 이 한계도 백엔드 emit로만 완전히 풀립니다.

마치며#

부분 실패에 강하게 만든 변경이 cold라는 특정 초기 상태에서 ‘반쪽만 참’인 조합을 만들었고, 그걸 살렸어야 할 안전망은 자기대입 no-op으로 죽어 있었습니다. 세 가지가 남습니다. 반쪽씩 독립 채택하면 그 반쪽을 소비하는 쪽의 가정을 다시 봐야 하고, 폴백 코드는 실제로 도는지 확인해야 하며, 화면 한 요소는 한 소스에서 파생하는 편이 안전합니다.
