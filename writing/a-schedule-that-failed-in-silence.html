A Snapshot Schedule Failed Every Run and the Screen Said STARTED
The FAILED state already existed; nothing wrote it.

I took over the snapshot scheduler on an OpenStack-based private cloud portal. It takes snapshots of volumes and instances at scheduled times. When a project's snapshot quota is full, every one of those creates is rejected with a 413.

The schedule state stayed STARTED. Not one snapshot was being made, and the screen looked healthy. The reason lived only in the batch log. The FAILED state turned out to exist already in the enum, and nothing anywhere wrote it.

Chasing the cause turned up something larger. In exactly the situation where a create fails for lack of quota, the code was deleting the previous snapshot first and creating the new one after.

Who this is for#

  • Anyone writing the code that lifts a scheduled job's failure onto a screen or an alert
  • Anyone handling a retention policy that deletes the old copy and makes a new one
  • Anyone who has never checked which scope a quota check is actually reading

The failure never reached the screen#

The batch calls create, and on an exception it logs and rethrows. That is all. Nothing above it catches that exception and changes the state. So the run fails and the state stays.

I got this wrong once. My first write-up said “a FAILED state has to be added”. Opening the code, the value was already there. What was missing was the logic that sets it. They sound alike and they are different repairs: one edits an enum, the other connects a failure path.

There was a second failure path. An instance with no volume attached returns silently on failure. Not even a log line. Fix only the throwing path and this one stays exactly as it was.

The check was reading someone else's project#

Registering a schedule ran a quota check. That check was reading two wrong things.

One was the limit. It read the quota class default rather than the per-project limit, so a limit the project had raised was ignored.

The other was the usage. It listed snapshots without passing the target project, which returns the list for the scope the client authenticated as. The check was comparing someone else's snapshot count against someone else's default limit.

Wrong in both directions at once. Plenty of snapshots in the scoped project and a valid registration is refused; a target project already full and the registration goes through. The edit path ran no check at all.

A full quota was the most dangerous moment#

There is a retention policy: keep N copies and delete the oldest beyond that. On the path for an instance with volumes attached, that delete ran before the create.

If the create succeeds, nothing is wrong. If it fails, the last backup is gone too. And a create is most likely to fail when the quota is full. The exact situation this ticket set out to fix was the condition that wiped the backups.

A quota gate does not fix it. The gate only stops the failures caused by quota; a create can still fail on an API error, a timeout, or a bad state. An ordering problem has to be fixed by ordering.

So the rule became code: do not delete the last copy until the new one is confirmed active. The wait function now returns whether it reached active, and anything short of that returns before reaching any delete.

Review found one more hole here. Returning on a failed confirmation leaves an image behind with no database row, and the retention policy counts rows, so nothing reclaims it. That was a leak the fix itself created. Unconfirmed images are now deleted on every failure path, which settles the invariant at “either a complete new snapshot or nothing”.

Registration, run and screen as one set#

Fix one point and another goes out of step. All three were decided together.

  • Registration and edit: check against the target project's real usage. Warn when short but allow it through; block only when not even one snapshot can be made. If the lookup itself fails, fail open. Blocking a registration because the check could not run turns a check outage into a feature outage.
  • Run: check the quota once more immediately before the create. When short, fail without creating or deleting anything.
  • Screen: show FAILED in the list and the detail, and return to STARTED when the next run succeeds.

The failure reason and time were deliberately kept out of the schedule row. One row holds only the last failure, so everything before it still lives in the log. The reason belongs to a per-run history, which went to a follow-up ticket.

Treating TIMEOUT as neutral was dropped#

The first design tried not to punish a timeout. It might still be under construction, so do not call it a failure.

Review raised two things. One was mistaking it for success: left neutral, the screen looks healthy while the snapshot is unconfirmed, the exact shape this article set out to fix. The other was orphans: leave an unconfirmed object alone and nothing owns reclaiming it.

So anything unconfirmed is now cleaned up and propagated as a failure. In exchange the wait scales with size, and that value is read at runtime from a settings table. Being able to adjust it without a restart is what makes “it only needed a little longer but it was marked failed” fixable in operations.

What this article does not claim#

  • No product name, version, customer, ticket number or server address. Code is described by behaviour, without class names.
  • Whether this defect ever actually destroyed a backup in production is unknown. What was confirmed is that the code path allows it; no incident record was consulted.
  • “Every run fails with 413, for every type” was an overstatement. An instance's own snapshot goes through the image service and has nothing to do with the volume quota. The ticket's sentence was split by path rather than taken as written.
  • Verification goes as far as compilation, unit tests, and confirming the registration warning and the FAILED display in a browser. Behaviour under load or over long operation was not measured.
  • Things are left. Fully reclaiming a snapshot that was mid-creation at timeout is still best effort. Name-based job keys mean renaming a schedule fires the old and new jobs together; that went to its own ticket.

Wrapping up#

  • A state value existing and a state value being written are different things. FAILED was there from the start and nobody wrote it. Counting enum members will not find this.
  • Code that checks a limit has to say whose limit it compares against whose usage. Both can be wrong and it still compiles.
  • The order of delete and create only shows itself on the day the create fails. And that is usually a day something else has already gone wrong.
  • A design that leaves failure neutral cannot be told from success on the screen. What cannot be told apart is not there.

Scheduled jobs run when nobody is watching. Unless how far a failure travels is written down in code, the failure ends inside a log file.
