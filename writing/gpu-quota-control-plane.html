Reclaim Admitted the Owner in 120 ms. The Device Came 10 Seconds Later.
A queue policy compared on admission latency alone always picks the reclaiming one.

A GPU budget is easy to declare and hard to place. Declare it in one object and something else still has to refuse work that exceeds it, and there is more than one “something else”. A training job is admitted by a queue; an inference request is admitted at the edge. Counting both in the same place double-counts the same cards.

So a tenant's budget is declared once in a GPUQuotaPolicy and enforced by whichever engine owns that kind of work: Kueue for training, a token bucket at the gateway for inference.

Kueue's reclaimWithinCohort knob was measured both ways on the same ledger. Reclaim off wasted nothing and made the owner wait 10.1 s. Reclaim on admitted the owner in about 120 ms and discarded 39.3 GPU-seconds. The first published reading of that second number was wrong about why, and an adversarial review is what produced the control experiment that corrected it.

Who this is for#

  • You are giving several tenants a share of the same GPUs
  • You are choosing between a queue policy that reclaims and one that waits
  • You have compared two policies on latency and wondered what the loser was buying

Where the budget is enforced#

GPUQuotaPolicy is cluster-scoped, because multi-tenant quota is something a cluster administrator declares rather than something a namespace owns. Its status carries a phase, conditions and observedGeneration, the same shape as NodeHealth, so the two objects can be read the same way.

The part worth arguing about is where it syncs to. The obvious answer is a namespace ResourceQuota, and for training GPUs that answer is wrong: Kueue already owns admission quota for those jobs. Writing the same GPU count into a ResourceQuota as well would mean two authorities counting one card, and the first one to refuse wins for reasons nobody can trace. So the policy syncs into Kueue's ClusterQueue and ResourceFlavor instead.

Inference is a different path with a different failure mode. It is limited at the gateway, per API key, with a token bucket. That limiter has been built and unit-tested and has never been deployed, which is worth saying out loud in an architecture description.

The knob that has two answers#

Kueue's cohort borrowing lets a tenant use another tenant's idle units. When the owner comes back, reclaimWithinCohort decides what happens: Never lets the owner wait, and Any takes the units back.

Two arms were run against a real Kueue on kind, with a censoring-aware lifecycle ledger joining events by controller UID rather than by timestamp guessing.

The waste is measured to the borrower's actual Pod termination, not to the preemption decision. Work done inside the grace window is discarded too, so ending the measurement at the decision would flatter the reclaiming policy by the length of that window.

The correction, published the same day#

The first version of this result described the 39.3 GPU-seconds as in-flight work cut short by preemption. Three rounds of adversarial review doubted it, a reproduction and a control experiment followed, and the mechanism turned out to be different.

Two consequences. The waste figure stands, because it is measured from timestamps that do not depend on the mechanism. The admission figure does not mean what it looked like: the owner's Workload was admitted in 111 ms on reproduction, and the owner's Pod became Ready about ten seconds after that, because the borrower had not released the device.

A third consequence is procedural. The first two live runs were executed without -out, so no ledger was preserved and the verdict had to come from a re-run rather than from re-reading the original. Ledger preservation is now an acceptance condition for a run.

The same question, on hardware#

Twelve kind runs that the runner's own gates accepted carried the banner device: NOT OBSERVED, which means every GPU-second in them is a second of reservation. A later paid session on four A10Gs ran eight more that passed -require-device.

Owner wait separated by 28.8 s there against 29.0 s on kind, so the result survived its own instrument. A follow-up study then separated reservation from use directly: two sets of runs reserved 51.084 and 50.802 GPU-seconds, the same to within a twentieth of their floor, while the card did 48.115 and 12.193 observed device-seconds. A factor of four, with every reservation-based figure unchanged.

What this does not claim#

  • The numbers below come from runs on a kind cluster with a fake device plugin, later carried to four A10Gs in a paid session. Where a figure is from simulated capacity, this article says so.
  • The quota sync is not a scheduler. Kueue admits; this project provides the MLTrainingJob abstraction and the status translation on top of it.
  • The gateway limiter has never been deployed. It is built and unit-tested. An architecture diagram that shows it in the request path is describing a design, not a system.
  • Neither reclaim number is a distribution. They are one pair of arms with a fixed borrower duration, and the 39.3 in particular scales with how long the borrower had been running.
  • The 120 ms was never device access. That is the correction above, and quoting it as a latency would repeat the error this article exists to record.
  • Enforcement is not the same as being unbreakable. Four guarantees built on this quota were later broken by attacking them, each because a check read a field the tenant writes.
  • The ledger and the CLI are designed only. There is no code for either.

Wrapping up#

  • Declare the budget once, enforce it where the work is admitted. Training and inference are admitted by different engines, and one shared counter would double-count the cards.
  • A queue policy compared on admission latency alone always picks the reclaiming one. The cost is in a different column of the same ledger.
  • Measure waste to the actual stop, not to the decision. The grace window is work too.
  • Admission is a reservation. A workload can be admitted while the device is still held by somebody else, and every reservation-based number stays the same while that is true.

The number survived the correction and the story did not, which is the ordinary shape of a measurement being right for the wrong reason. Keeping the first version next to the correction is the only way the next reader can tell which part was load-bearing.
