Instance HA ④: 펜싱 대신 프로세스를 종료하고 있었습니다
설계는 전원이 내려간 것을 확인한 뒤에만 옮기라고 했습니다. 구현에는 그 확인이 없고 대신 다른 장치가 들어가 있습니다.

2026년 9월

목차

  • 대신 노드가 자기 VM을 종료합니다
  • 한계: 이 글이 주장하지 않는 것
  • 마치며

③편에서 여덟 시나리오 가운데 하나만 복구로 넘어갔습니다. 판정이 섰다고 해서 바로 옮기지는 않습니다.

이유는 ①편에서 본 것과 같습니다. 원본이 아직 살아서 디스크를 쓰고 있는데 복제본이 같은 볼륨에 붙으면 파일시스템이 깨집니다. 그래서 설계는 원본의 전원이 확실히 내려갔다는 확인 없이는 옮기지 않는다를 원칙으로 세웠습니다.

그런데 자료를 다시 읽고 나서 이 편을 고쳐 씁니다. 현재 구현에는 그 확인이 없습니다. 원칙은 설계서의 것이고 제품이 그렇게 동작한다는 뜻이 아니었는데 이전 판은 그 차이를 적지 않았습니다.

이 글의 예상 독자#

  • 자동 복구에 Fencing을 넣으려는데 전제 조건을 정리해야 하는 분
  • 설계 문서와 실제 구현이 어긋날 때 무엇을 먼저 적어야 하는지 궁금한 분
  • 전원을 확인할 수 없는 환경에서 무엇으로 대신하는지 보고 싶은 분
  • ③편을 읽고 판정이 선 뒤에 무엇을 하는지 궁금하신 분

설계는 확인 없이는 옮기지 말라고 했습니다#

복구는 VM을 다른 호스트에서 다시 띄우는 일입니다. 원본이 죽지 않았는데 재기동된 쪽이 같은 볼륨에 붙어 두 쪽이 동시에 쓰도록 허용되면 깨지는 것은 VM 하나가 아니라 볼륨 전체가 될 수 있습니다.

가로로 스크롤하면 나머지가 보입니다

복구 절차 네 단계.
단계하는 일
DetectHeartBeat TTL 만료와 Phase 1 판정 완료
VerifyPhase 2의 실행 조건을 모두 충족하는지 확인
Fence전원을 내리고 내려갔는지 확인
RecoverNova Evacuate 실행

네 단계로 가른 이유는 서비스에 실제 영향을 주는 동작을 뒤로 몰기 위해서입니다. Detect와 Verify는 판단 단계라 확신이 서지 않으면 언제든 멈출(Hold) 수 있고 Fence부터는 전원을 내리므로 서비스에 실제 영향을 주기 시작합니다. 그중에서도 되돌릴 수 없는 것은 맨 끝의 Recover입니다.

그리고 전원을 내릴 경로가 장애와 함께 끊기면 원칙 자체가 성립하지 않습니다. 그래서 전용 물리 스위치를 전제 조건으로 요구했습니다.

명령과 확인 사이에 5초를 넣었습니다#

Fence 단계에서 가장 틀리기 쉬운 자리가 여기입니다. 전원을 내린 직후에 상태를 조회하면 아직 off가 아닙니다. 명령이 전달되는 것과 실제로 전원이 내려가는 것 사이에 시간이 있기 때문입니다.

# BMC 전용 물리 스위치 경로로 전원을 내린다
ipmitool chassis power off

# 최소 5초 대기. 즉시 조회하면 아직 off 가 아니다
sleep 5

# 반드시 off 로 읽히는지 확인한다
ipmitool chassis power status

# Storage 유형별 잔여 연결 정리를 확인한 뒤에야
# Nova Evacuate 로 넘어간다

대기를 빼면 두 방향으로 틀립니다. 멀쩡히 동작한 Fencing을 실패로 읽어 복구를 막거나, 반대로 낙관적으로 넘어가 내려가지도 않은 서버의 VM을 옮깁니다. 5초는 하한이고 상한은 따로 둡니다.

Storage 유형마다 정리 조건이 다릅니다#

전원이 내려갔다고 해서 바로 옮길 수 있는 것은 아닙니다. 원본이 잡고 있던 연결이 정리돼야 하고 그 방법이 Storage 유형마다 다릅니다.

가로로 스크롤하면 나머지가 보입니다

Storage 유형별 추가 확인.
Storage확인할 것
iSCSIsession 종료와 SCSI PR 해제
LVMVG Lock 해제
NFSmount 해제
Cindervolume attachment 정리 완료

네 줄을 한 줄로 묶지 않은 이유는 확인 대상이 서로 다른 층에 있기 때문입니다. 전송 규약과 Volume 계층과 관리 서비스가 섞여 있어 하나의 조건으로는 덮이지 않습니다.

구현에는 그 확인이 없습니다#

여기까지가 설계입니다. 구현은 다릅니다. 지금 제품은 전원을 내리지도 확인하지도 않고 복구합니다. 원본이 살아 있지 않다는 근거를 전원 상태가 아니라 통신 상태에서 얻습니다.

가로로 스크롤하면 나머지가 보입니다

설계 요소가 코드에 어디까지 들어갔나.
설계 요소상태코드에서 확인되는 것
관측자가 자기 상태를 먼저 본다활성복구 배치가 자기 노드 상태를 먼저 확인하고 비정상이면 복구를 넘김
복구 대상 선별 두 겹활성호스트 제어 속성과 Instance 메타데이터를 함께 사용
복구 방식 미설정 시 차단활성방식이 없으면 복구를 건너뜀
Fencing골격만 · 비활성전원 대기와 재시도 설정이 주석 골격으로만 존재
분산 합의 실행 제어골격만 · 비활성같은 골격에 딸려 있음
Phase 1과 Phase 2 분리코드에 없음해당 구조가 확인되지 않음

설계 요소를 코드와 맞춰 보면 세 층으로 갈립니다. 미반영이 아니라 도입 대기인 쪽이 있어서 그렇게 적었습니다. 전원 대기와 재시도 설정이 주석 골격으로 들어가 있습니다.

대신 노드가 자기 VM을 종료합니다#

그러면 원본이 계속 쓰는 것은 무엇이 막느냐가 남습니다. 답은 노드 자신입니다. 각 노드에서 도는 Agent가 스스로 장애를 확정하면 자기 위에 있는 VM 프로세스를 종료합니다.

# 노드가 스스로 장애를 확정하는 조건. 어느 하나만 걸려도 장애다
  관리 쪽에서 상태 확인 요청이 일정 시간 오지 않음
  지정된 Gateway 로 ping 이 닿지 않음
  지정된 IP 와 Port 로 TCP 연결이 되지 않음
  지정된 Network Interface 가 up 이 아니거나 loopback 임

# 확정이 일정 시간 이어지면
  자기 위의 VM 프로세스를 찾아 종료
  단, 이주 중으로 표시된 VM 은 제외

조건은 네 가지이고 어느 하나만 걸려도 장애로 봅니다. 관리 쪽 요청이 끊긴 것, Gateway에 ping이 닿지 않는 것, 지정한 IP와 Port로 TCP 연결이 안 되는 것, Network Interface가 내려간 것입니다.

그런데 종료가 이주보다 빠를 수 있습니다. 옮기는 중인 VM을 종료해 버리면 복구가 실패합니다. 그래서 이주 시작과 완료를 메시지로 받아 종료 제외 목록을 따로 둡니다.

이 장치는 전원 차단과 같은 것이 아닙니다. 노드가 자기 상태를 잘못 읽으면 종료도 일어나지 않습니다. 전원 차단은 밖에서 확인하지만 이것은 안에서 판단합니다.

한계: 이 글이 주장하지 않는 것#

  • ⚠️ 이 연작의 산출물은 설계서입니다. 저는 절차를 설계하고 전제 조건을 요구했을 뿐이고 BMC 망을 구축하거나 이 절차를 운영에서 실행한 것은 아닙니다.
  • 「도입 대기」는 주석 골격과 진행 중인 업그레이드에서 미루어 본 것입니다. 채택 여부를 정한 기록으로 확인한 것이 아닙니다.
  • 5초는 제안값입니다. 장비별로 전원이 내려가는 시간을 재서 고른 값이 아닙니다.
  • Storage 네 항목은 배타적인 분류가 아닙니다. 한 구성에서 둘이 함께 나타날 수 있습니다.
  • 사내 자료라 제품명과 고객사와 주소와 계정과 호스트명은 쓰지 않았습니다.

마치며#

이 편의 결론은 한 줄입니다. 설계가 요구한 것과 구현이 하는 것을 같은 문장으로 적으면 읽는 사람이 속습니다. 이전 판의 제목이 그랬고 그래서 제목부터 바꿨습니다.

가장 위험한 차이는 하나입니다. 전원 차단은 밖에서 확인하고 프로세스 종료는 안에서 판단합니다. 관측자가 자기를 잘못 읽으면 두 번째 방법은 작동하지 않습니다.

다음 편은 이 절차를 누가 실행할지 정하는 이야기입니다.
